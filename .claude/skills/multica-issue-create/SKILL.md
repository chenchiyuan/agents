# multica-issue-create

**版本**: 1.0.0
**创建日期**: 2026-10-28
**规范来源**: `multica/issue-creation-spec.md`（本 skill 的判断依据，修改规范不改本文件结构）

---

**CRITICAL: 绝不跳过用户确认直接创建——反射产出的草案必须完整展示，用户认可或修改后才调用 `multica issue create`。**

**CRITICAL: 绝不用模板套话填充验收标准/边界——这两项必须来自对用户原话的真实推理，推理不出来就在展示阶段留白并追问，不能编造"无特殊要求"糊弄过去。**

**CRITICAL: 绝不在创建后自动继续执行任务内容——本 skill 的职责止于"产出已确认的 issue"，任务本身的推进是另一个流程，除非用户这次要求的本来就是立刻执行。**

---

## 一句话职责

接收口语化需求，按 `multica/issue-creation-spec.md` 反射出结构化 issue 草案（标题/描述四件套/状态/拆分方案/指派建议），展示给用户确认，确认后才落地创建。

## 成功标准

- 产出的草案严格对照 `multica/issue-creation-spec.md` 第三节四个必备小节，没有空缺项（无内容时写"无特殊限制"等明确结论，而不是省略小节）
- 草案中所有推理得出的内容（而非用户原话直接给出的）标注为 `model_inferred`，用户能一眼看出哪些是转述、哪些是补充
- 用户确认或修改后，才调用 `multica issue create` / `multica issue update` 等写操作；未确认前不产生任何平台写入

## 策略哲学：对抗的惯性 vs 正确判断

| 模型惯性 | 真实情况 |
|---|---|
| 用户说了需求，直接建 issue 就行 | 口语化输入缺验收标准和边界，直接建会让执行者"自认为完成"或误执行 |
| 描述里写了用户原话就算完整了 | 规范要求的是"目标/验收标准"和"边界/不做什么"，这两项往往需要反射补充，不在原话里 |
| 拆子任务显得更规范、更专业 | 拆分有成本，只在"能独立验收"或"有阶段屏障"时才拆，否则是过度工程 |
| 状态先随便定一个，后面再改 | `todo` + agent assignee 会立即触发 run，创建时选错等于已经执行了不该执行的任务，无法"先建后改" |
| 用户没提属性/优先级，就不用管 | 要先查 `multica property list` 有没有现成结构化字段可用，不要把能结构化的信息堆进自由文本 |

**判断锚点**：
- 遇到"这次输入到底是要讨论还是要立刻执行"难以判断时，不猜，在展示草案时把这个判断作为待确认项列出，而不是默认选一个。
- 遇到"要不要拆子任务"难以判断时，用"这部分能不能脱离其他部分单独验收"自问，能则拆，不能则留在父任务描述的检查清单里。

## Workflow

### 1. 理解（不编造）

从用户的口语化输入里提取三类信息：要做什么、做完的样子、有没有约束。缺哪一类就标记为待确认，不要用默认值补齐。

### 2. 反射产出草案

按 `multica/issue-creation-spec.md` 第三节结构生成：
- 标题
- 描述四件套：用户原始需求 / 目标与验收标准 / 边界与不做什么 / 相关资源
- 状态建议（参照规范 3.3，说明选择理由，尤其是"是否会立即触发执行"这一点要点明）
- 是否需要拆子任务、是否需要 stage（参照 3.4，给出判断理由，不是直接给结论）
- 指派建议（参照 3.5）
- 需要的 property（先跑 `multica property list` 核对现有定义；没有合适的就在草案里注明"建议新增属性 X"，不要发明替代写法塞进描述）

所有非用户原话直接给出的内容标注 `model_inferred`。

### 3. 展示确认

把完整草案发给用户，不是摘要、不是"大概是这样"。明确区分"转述自原话"和"推理补充"。等待用户确认或修改意见。

### 4. 确认后才创建

- 用户认可：按草案调用 `multica issue create`（或 `issue update`，若是修改已有 issue）
- 用户要求调整：回到步骤 1 重新理解调整的部分，不是在现有草案上打补丁式小改
- 涉及子任务/stage 的，按规范 3.4 的 todo/backlog 规则逐个创建，不要图省事把所有子任务状态设成一样的

### 5. 交付

创建完成后，在结果说明里列出实际创建的 issue id/链接，以及这次草案里哪些判断是 `model_inferred`（方便用户下次调整表达方式减少反射成本）。不主动开始执行新建的 issue 内容，除非用户这次要求的就是"建完立刻做"。

## Tools and capability boundaries

**做什么**：
- 读 `multica/issue-creation-spec.md` 作为判断依据
- 读 `multica property list`、`multica issue list` 等只读命令核对现状
- 反射推理生成草案，展示确认
- 用户确认后调用 `multica issue create` / `issue update` / `issue status` / `issue assign` 等写操作

**不做什么**：
- 不在用户确认前调用任何 `multica` 写操作
- 不替用户编造验收标准或边界条件
- 不越权创建自定义 property（只能提建议，property 定义只能由 owner/admin 创建）
- 不在创建 issue 后自动继续执行其内容

---

## Safety

- 草案未经确认不创建、不更新、不改状态
- 子任务创建前必须确认 todo/backlog 选择，避免误触发不该启动的 run
- 发现需要的结构化字段（property）不存在时，提建议，不绕过去塞进自由文本
