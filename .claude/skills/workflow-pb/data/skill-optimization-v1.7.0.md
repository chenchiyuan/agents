# SKILL.md v1.7.0 优化记录

**日期**: 2026-09-05
**触发**: 迭代 `0005-pr-concurrent-execution`——用户在实际执行中发现 PR 被串行执行，追溯到 `workflow-pb.md` v0.3.0"依赖解锁式并发调度"这套协议文字从未被真实调度执行过一次，PR-001 把该协议补全为可执行细节（v0.3.0 → v0.4.0），本次同步更新 SKILL.md 精简版协议。

## 根因

`workflow-pb.md` v0.3.0 的阶段 5 只写了调度的"原则"（无依赖或依赖已合并即并发派发），没有写"技术手段"（怎么发起并发调用）、"槛位算法"（并发数从哪来、怎么爬升、上限是多少）、"状态记录字段"（`status.md` 怎么记录槛位占用和现场保留）、"核实项"（怎么核实失败/阻塞 PR 的现场是否还在）。SKILL.md 作为该规范的精简版协议，同样只字未提这些执行细节，导致主 agent 按 SKILL.md 调度时也没有依据落实真正的并发。

## 决策过程

- PR-001 已在 `workflow-pb.md` 正式规范里补全四处协议文字：阶段 5 章节（并发槛位算法 + 并发派发技术手段）、启动工作流章节（status.md 并发配置初始化）、status.md 格式模板（槛位状态列 + 失败/阻塞专属取值）、可观测性章节（progress-observer 新增核实项）
- SKILL.md 是精简版协议，不需要逐字复制 `workflow-pb.md` 全文，只需要在对应章节补充要点式描述，并保证与正式规范不矛盾
- 沿用项目既有惯例：每次 `workflow-pb.md` 协议实质变更都同步更新 SKILL.md 和对应的 `data/skill-optimization-v{版本}.md` 记录文件

## 改动

- 文件头版本号 1.6.0 → 1.7.0，"对应规范"号同步为 workflow-pb v0.4.0
- `description` 字段补充"含并发槛位算法"，反映阶段 5 的实质变更
- `## Purpose` 引用的规范版本号 v0.3.0 → v0.4.0
- 「### Step 5: 依赖解锁式并发 PR 派发」补充两点：
  - 明确并发派发的技术手段是"主 agent 在同一轮 assistant 响应中连续发起多个 `Agent()` 工具调用"，不是逐个顺序调用
  - 补充并发槛位算法要点（起始并发数默认 3、爬升公式 `min(起始 + 累计解锁次数×起始, 硬上限)`、硬上限公式 `2×起始-1`），完整公式指向 `workflow-pb.md` 正文

- 「## Important facts and constraints」新增第 7 条：失败/阻塞 PR 的 worktree 和分支现场原样保留不自动清理，`progress-observer` 每次生成 `progress.md` 须核实其是否仍存在于磁盘
