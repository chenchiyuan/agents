# SKILL.md v1.5.0 优化记录

**日期**: 2026-09-04
**触发**: 用户实际执行 workflow-pb 时发现，阶段 1~3 和进度核验确实读取并执行了对应角色文件（`demand.md`/`prd.md`/`architect.md`/`progress-observer.md`），但派发出去的执行实例名称是宿主工具层的通用命名（`DemandConverger`、`PrdDecomposer`、`ArchitectureConverger`），不是 `demand`/`prd`/`architect` 这些角色名——容易造成"没有使用 workflow-pb 角色"的误解。用户同时指出 brief 没有按标准字段逐项呈现，被揉进了任务描述。

## 根因

「§ 对外协议·角色派发契约」（v1.4.0 引入）只约束了"传什么内容"（角色文件路径 + 最小 brief），没约束"以什么形式呈现"和"呈现出来是否可辨认对应角色"。这留下两处退化空间：

1. 「§ Brief 构建规则」列出了字段清单，但没规定字段必须以可辨认结构呈现，导致字段可以被自由改写压缩进散文任务描述——内容可能没丢，但外部审阅者无法直接对照核验。
2. 派发时给执行实例起什么名字完全没有协议约束，宿主工具层的通用命名（工具限定，不存在名为 demand/prd/architect 的原生 agent 类型）成为唯一可见标签，让读者只能靠猜测判断是否用了对应角色。

两处本质是同一件事：v1.4.0 解决了"内容正确"（角色确实被读取执行），但没解决"正确性可被外部一眼核查"——这与协议里心照不宣的假设没有变成可核查不变量是同一类问题。

## 决策过程

- 用户明确排除了"这是主 agent 冒充角色执行"的可能性：确认是"通用执行器加载角色定义"，执行内容本身没问题，问题在呈现和格式约束缺失
- 用户明确要求命名规则不应该管宿主工具层的实例显示名（这本来就不受协议约束、也不该受约束），而应该在 brief 与调度说明里把"角色文件路径 + 角色名"作为显式、不可拆分的字段强制呈现——workflow-pb skill 作为协议入口，必须把"调用方法、调用路径、role"维护清楚

## 改动

- 新增一条 CRITICAL：角色文件路径 + 角色名必须在 brief 中逐行显式呈现，不得压缩进自由叙述；执行实例显示名不受约束也不能替代这两个字段；判断"是否使用了角色"只看 brief 与调度说明，不看实例显示名
- 「§ 对外协议·角色派发契约」新增两条：
  - "三元绑定，不可拆分"：派发方法 + 角色文件路径 + 角色名必须同时显式出现，任一项被省略或压缩进自由叙述都是违反
  - "执行实例的显示标签不是协议对象"：宿主工具层的实例命名不受约束，也不能作为判断依据；主 agent 必须保证角色路径和角色名在对外呈现（进度说明、status.md）中始终可辨认
- 「§ Brief 构建规则」代码块新增「角色名」字段（首行），并在字段清单前新增格式硬性要求：必须逐行 `字段名：值` 呈现，不得改写合并进任务描述；块后新增说明：执行实例名不受协议约束，但不能替代「角色名」字段

## 未变

- 阶段→角色映射、角色文件路径解析机制、需求问题搭置不回退协议（v1.2.0/v1.3.0）不受影响
- v1.4.0 引入的人机交互契约、文档协议、Step 0 前提声明不受影响，本次只强化角色派发契约的呈现约束
- 角色文件本身（`demand.md` 等）未修改——问题定位在 SKILL.md 呈现层协议，不是角色定义层
