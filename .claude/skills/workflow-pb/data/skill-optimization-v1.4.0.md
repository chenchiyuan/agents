# SKILL.md v1.4.0 优化记录

**日期**: 2026-09-04
**触发**: 用户在 shipany-two 项目上通过 Codex CLI（而非 Claude Code）驱动 workflow-pb 跑完阶段 1，产出的 `demand.md` 全部标注 `[user_confirmed]`，但对应 `clarifications/` 目录不存在，内容基本是对 brief 的复述——实际没有发生任何真实的人机往返确认。用户要求先分析原因再给方案。

## 根因

最初怀疑是 `roles/demand/demand.md` 角色定义本身不够强制。但用户纠正：真正的根因在本文件（SKILL.md）——协议里把"暂停""派发"等行为隐含绑定成 Claude Code 专属工具语义（"用 Agent 工具派发"、"暂停"默认依赖 Claude Code 的轮次阻塞机制），却从未把这些行为应满足的不变量显式写出来。换成 Codex CLI 这种只读、无真实阻塞式交互通道的宿主后，这些隐含假设悄悄失效，而 SKILL.md 没有定义任何"宿主能力不足时怎么办"的显式路径，模型于是自己顶替了确认角色，把 `model_inferred` 自问自答成 `user_confirmed`。

链条：demand.md 的确认机制是文字协议，非技术强制 → SKILL.md 把"暂停/派发"隐含绑定 Claude Code 工具语义 → 换宿主后隐含假设失效但无显式降级机制 → 模型自己代答确认。

## 决策过程

- 最初提案（被否决的方向）：给 demand 角色加"检测不到真实交互通道时禁止产出 user_confirmed"的机制性约束——用户指出这治标不治本，问题不在 demand.md，在 SKILL.md 本身缺乏对外协议定义
- 用户明确要求：workflow-pb skill 应该像"轻代理模式"一样，对外暴露宿主无关的接口、协议、通讯方式定义，任何主 agent（不限 Claude Code）仅凭这份协议就能知道流程定义、工作方法、工具调用方式、文档定义
- 用户批准方案 A：新增独立的「§ 对外协议」章节，把隐含在具体工具名和隐含语义背后的假设，提炼成三组显式、宿主无关的不变量：角色派发契约、人机交互契约、文档协议

## 改动

- description 前的 CRITICAL 声明块新增一条：本 skill 是宿主无关的协议定义，不是 Claude Code 专属操作手册；提到具体工具名的地方指的是不变量，不是绑定工具；宿主不提供等价能力时按「§ 对外协议」处理，不得静默降级
- 新增「§ 对外协议」独立章节，含三组契约：
  - 角色派发契约：派发即隔离执行、brief 是唯一输入契约、产物是唯一输出契约、宿主无独立执行上下文时仍需显式分段标注
  - 人机交互契约：暂停 = 真实阻塞等待人类输入的显式定义；前提声明硬性红线（宿主无真实阻塞通道时必须声明限制，绝不自问自答代答）
  - 文档协议：产物路径/字段/标注规则统一引用规范文件；status.md 与文件系统是进度真相来源；`user_confirmed`/`model_inferred` 标注必须原样保留
- Tools and capability boundaries「做什么」列表去工具名化："用 Agent 工具派发"改为"派发机制由宿主决定……不变量见「§ 对外协议·角色派发契约」"
- Tools and capability boundaries「不做什么」新增一条：不在宿主无真实阻塞式交互通道时替用户自问自答确认 `model_inferred` 项
- 「§ 用户决策点与暂停格式」新增"暂停的定义"段落，显式区分"真实暂停"与"伪暂停"（自问自答/默认答案）；新增"宿主不具备真实阻塞能力时"的处理说明
- Step 0 启动流程新增第 2 步"前提声明"：自评宿主是否具备真实阻塞式交互通道，不具备时显式声明限制，全程遵守，不得后续静默降级
- Resources 新增对「§ 对外协议」的引用条目，及 v1.4.0 变更记录文件引用
- Safety 新增一条：暂停必须是真实阻塞等待人类输入，这条红线不因宿主能力不足而豁免

## 未变

- 阶段→角色映射、角色文件路径解析机制（v1.2.0 引入）不受本次改动影响
- 需求问题搭置不回退协议（v1.3.0 引入）不受本次改动影响，二者是独立维度
- `roles/demand/demand.md` 角色文件本身未修改——问题定位到 SKILL.md 协议层，不是角色定义层
