# SKILL.md v1.14.0 优化记录（对应规范 workflow-pb v0.11.0）

**日期**: 2026-09-15

**触发**：用户反馈阶段 1（需求收敛）的用户沟通"感觉泛泛而谈"——目的性不够强、给用户反馈的空间不足、没有持续理解用户最新的输出。用户明确指导原则："不是让 demand 更复杂，而是让 demand 更智能"。经结构化讨论定位到根因是执行架构：阶段 1 走"主 agent 派发 demand 子 agent 执行、demand 向主 agent 汇报"，子 agent 和用户之间隔着"主 agent 转达"这一层，造成信息衰减和反馈延迟。规范文件 `roles/workflow-pb/workflow-pb.md` 升级到 v0.11.0，把阶段 1 改为主 agent直接内联执行；本文件（SKILL.md）是主 agent 调度协议的精简版，必须同步——用户明确要求同步更新（此前曾就"`.claude/skills/` 是否要跟随项目管理"有过讨论，用户确认这份 SKILL.md 属于历史上每次 workflow-pb.md 版本升级都同步的既有惯例，本次不例外）。

## 决策过程

- 最初讨论一度考虑"只改 demand.md 本身、不动执行架构"——被否决，因为诊断已定位根因在执行架构（子 agent 隔着主 agent 与用户对话），只改判断框架不解决转达损耗问题
- 确定方案：阶段 1 从"派发子 agent"改为"主 agent 内联执行"，不再有独立执行上下文
- 关键难点：SKILL.md 「§ 对外协议·角色派发契约」的核心不变量"派发即隔离执行"（该执行上下文运行期间主 agent 不能自己读完角色文件后"代入"该角色处理任务）与阶段 1 内联执行存在逐字冲突——不能简单删除或弱化该不变量，因为它对阶段 2~6 仍完全适用且重要。处理方式：在该条款正文后追加"显式例外（阶段 1 / demand）"一句，明确声明例外范围仅限阶段 1，阶段 2~6 的其余角色不受影响
- 判断哪些"派发"措辞需要改、哪些不需要：凡是描述"阶段 1 如何执行"的措辞（CRITICAL、Step 1~4、阶段执行卡片、用户决策点）都改为内联执行语义；凡是描述"阶段 2~6 如何派发"的措辞（§Brief 构建规则正文、§阶段执行卡片阶段 2~6 条目）不改，只在其顶部加排除说明
