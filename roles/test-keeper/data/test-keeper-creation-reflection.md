# test-keeper 创建反射依据

**创建日期**：2026-09-17
**触发**：用户提出"新增测试用例 role"，需求源头是 0026 迭代（`docs/iterations/0026-test-protocol-and-suite-reset/`）里被裁决整块后置的测试协议（Q15）与暂名 `test-keeper` 的横切角色空缺（Q10）。用户这次补充了三点 0026 未覆盖的细节：三级分级（PR内必测/项目冒烟/全局回归）、语言栈反射（不锁定 node/python）、workflow-pb 接入方式。

## 反射过程

**Step 1（核心任务类型提取）**：这个角色的核心任务不是"写测试"，是"治理测试资产的生命周期"——决定什么该沉淀、什么该清理、协议怎么写才能让别人不问作者就能裁决。现实世界对应的是多语言 monorepo 里的 test infra owner / build cop 角色：不亲自写业务测试，但管"测试基建该怎么组织"。

**Step 2（角色描述构造）**：
- identity 走"交叉稀缺"路线：多语言测试写法通识（不是某一种语言的专家）× 治理/协议维护（不是纯执行者）。类比对象定为 build cop / test infra owner，具象类比是"把一个测试套件从失控状态整治成可持续状态"，战绩暗示引用了仓库真实历史数据（0026 已实测：边际耗时 0.04s→0.14s、28处一次性脚本）。
- relationship 的关键决策点是"和 verifier 的边界"——反射时特意排除了"test-keeper 自证套件是否够用"这条能力，划给 verifier，避免两个角色的独立性互相污染。
- character 锚定"主动侦测但不越权"——直接对应用户澄清对话里"软性预算不阻塞交付"的裁决。

**Step 3（用户确认）**：反射结果一次性通过，用户回复"good，符合我需求，请继续"，未要求调整。

## 关键决策与已否决的备选方案

1. **角色定位 vs 挂靠 verifier**：在方案讨论阶段（此次创建之前）已经对比过"新增角色"与"挂靠 verifier"两个方案，用户选择新增角色。否决理由：verifier 的核心资产是"独立鉴定人格"（不接收执行过程上下文、不自证），测试编写是"参与建设"性质的工作，混入会污染 verifier 的判断纯度。这个决策记录在对话历史里，未在本角色的反射三步中重新做，是因为它是"要不要创建这个角色"层面的决策，不是"这个角色该长什么样"层面的决策。

2. **阶段5协作方式**：用户明确选择"test-keeper 不参与阶段5派发循环，L1 用例仍由 dev 自己写"，否决了"dev+test-keeper 两个子agent协作同一个PR简报"的备选方案。理由：改动面最小，且 dev.md:107 现有例外条款（"除非简报明确要求"）已经能覆盖 L1 场景，不需要新增协作结构。

3. **Q3 沿用方式**：0026 迭代的 Q3 裁决"不用物理指标做沉淀判据"。用户这次要求加一条"软性墙钟预算"，明确选择"延续必要性判据为主判据，软性预算只是追加的退化信号，不阻塞交付"，否决了"设硬性时长上限，超时阻塞交付"的备选方案——避免推翻 0026 已有裁决。

## Verify 阶段踩坑：identity 交叉稀缺要素连续 3 轮不通过

无上下文子agent 独立验证时，identity 的"交叉稀缺"要素连续 3 轮 Verify→Fix 未通过，触发了"同一问题连续3轮仍不通过，停下来向用户报告"的协议红线：

1. **第1轮**：`build cop / test infra owner` —— 被判定为同一领域内换标签（软件工程/QA内部常见组合），不构成"两个不相邻领域"。
2. **第2轮**：改为"测试基建治理 + SLA/API契约起草" —— 被判定两者仍都落在软件/运维大范畴内，不够跨域。
3. **第3轮**：改为"测试基建治理 + 企业档案保管期限表起草"（档案合规领域） —— 这次真正跨出了软件工程范畴，但被更严格的验证子agent判定"现实中不存在这种人，是为凑类比生拼出来的"，指出协议里的正例 `pr-planner`（依赖分析引擎作者+迁移排期工程师）其实也没有真正跨出软件工程大范畴，只是子领域不同。

**根因**：不同的无上下文验证子agent对"交叉稀缺"的严格程度不一致——有的用"是否完全跨出大范畴"判断，有的用"现实中是否存在可信的单人职业重叠"判断，这两条标准在 test-keeper 这个角色身上互斥（真正跨域会牺牲现实可信度，留在软件工程内部又可能被判"不够跨域"）。第3轮子agent自己的报告里也承认了这个矛盾，并反过来质疑已通过验证的 pr-planner 正例本身也没有真正跨域。

**处理方式**：按协议触发点，向用户报告了这个两难，用户明确裁决"按 pr-planner 同等标准即可"——即交叉点只需是软件工程内部两个不同子领域的组合（现实中稀少但可信），不需要跨出软件工程之外。据此第4次修订为"测试基础设施治理 + 平台级SLO/可观测性治理"，第4轮验证（按用户裁决口径显式告知验证子agent）通过。

**沉淀的经验**：向后续角色创建者的建议——当"交叉稀缺"验证连续失败且怀疑标准本身不稳定/不一致时，应尽早把"判断标准的裁决权"交还用户，而不是不断猜测下一个更极端的跨域组合；同时验证子agent的 prompt 里最好显式给出一个已通过的同水准正例作为标尺（本次第4轮验证就是这么做的，一次通过）。
