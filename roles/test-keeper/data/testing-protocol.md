# 测试三级分级协议（Testing Protocol）

**版本**: 1.0.0
**创建日期**: 2026-09-17
**维护者**: `test-keeper` 角色（见 `roles/test-keeper/test-keeper.md`）
**来源**：延续 `docs/iterations/0026-test-protocol-and-suite-reset/` 迭代 Q15 后置的测试协议缺口与 Q10 暂留的角色空缺。该迭代已反射出的六张协议卡（F03~F08，`git show 02fcc33` 可查）方向已被吸收；具体条款按本次新增的三级分级/语言栈反射/软性墙钟预算需求重新组织，不是逐条复制。

## 一句话职责

定义测试三级分级（L1 PR内必测 / L2 项目冒烟 / L3 全局回归）的判断标准、每条约束的判断方式、语言栈反射规则、软性墙钟预算阈值——供 `test-keeper` 角色维护和执行，也供 `dev`/`verifier`/`workflow-pb` 按需索引引用（本文件是这些规则的唯一权威定义处，其余文件只保留索引指针，不复制条款）。

---

## 分级总览

| 级别 | 定义 | 编写者 | 生命周期 | 落点 |
|---|---|---|---|---|
| **L1** | PR 内必测 | `dev`（仅当简报明确要求，见 `roles/dev/dev.md:107` 现有例外条款） | 一次性，跑完即删 | 不沉淀 |
| **L2** | 项目冒烟 | `test-keeper` | 沉淀，长期维护 | `tests/`（仓库既有目录） |
| **L3** | 全局回归 | `test-keeper` | 沉淀，长期维护 | `tests/`（与 L2 同一目录，全量执行） |

三级共享同一条**沉淀判据**（见「沉淀判据」章节）：是否有跨迭代契约意义，不用物理指标（行数/时长上限）判定是否该留。L1 因为生命周期只到 PR 结束，天然不进入这条判据的判断范围。

---

## L1：PR 内必测

**编写者**：`dev` 角色，仅在简报明确要求时（对齐 `roles/dev/dev.md:107` 现有措辞"不写测试用例（除非简报明确要求）"）。`test-keeper` 不编写、不参与阶段5派发循环，只在本协议里把规则定义清楚。

**规则**：
1. 只运行本 PR 生成的新测试用例，不在 PR 内触发全量套件。
   判断方式：读该 PR 的执行记录，核对本次运行的测试文件/用例范围是否限定在该 PR 新增或修改的文件内；出现触发 `tests/` 全量套件的命令即违反。
2. PR 内产生的用例跑完即清除，不沉淀进仓库。
   判断方式：PR 合并后核对 `tests/` 目录与该 PR 的文件范围声明，若该 PR 未在文件范围里显式声明"新增沉淀用例"却在 `tests/` 留下了新文件，即违反。
3. 若某条 L1 用例被判定有跨迭代契约意义（应该沉淀为 L2/L3），必须显式转交 `test-keeper`，不能自行决定沉淀。
   判断方式：`tests/` 目录出现的新沉淀文件，其提交记录或 PR 报告中能否找到"经 test-keeper 判断沉淀"的说明；找不到即违反。

**边界**：L1 的存在不改变 `dev.md` 现有边界，本协议不新增例外，也不撤销现有例外。

---

## L2：项目冒烟

**编写者**：`test-keeper`。触发时机：workflow-pb 阶段5某个/全部 PR 完成后，或用户/主 agent 直接单独调用。

**规则**：
1. 新增前必须能回答"这条断言的跨迭代契约意义是什么"，答不出来不沉淀（见「沉淀判据」）。
   判断方式：读该用例对应的报告契约第2项（"跨迭代契约意义"说明），若为空或只是"覆盖更全"这类无信息量表述，即违反。
2. 覆盖范围是"当前项目关键路径的最小验证集"，不是全量业务逻辑覆盖。
   判断方式：核对新增用例是否对应仓库现有工具/入口（如 `tools/*.sh`、`oamp/bin/*`）的核心可用性，而非某个内部实现细节。
3. 每条用例必须能确定性地区分"符合预期"和"不符合预期"，不能是偶发通过/失败。
   判断方式：同一用例连续运行 ≥2 次，结果必须一致；不一致即判定该用例不合格，须重写或移除。

---

## L3：全局回归

**编写者**：`test-keeper`。触发时机：迭代交付/合并前（workflow-pb 阶段6独立验证之前），或用户/主 agent 直接单独调用。

**规则**：
1. 覆盖面比 L2 更宽——跨模块、跨迭代的契约都要能被这一层捕捉到；判据仍是必要性，不是"尽量全"。
   判断方式：核对本次新增/保留的 L3 用例，每条能否指出它验证的是"哪个模块与哪个模块之间的契约"，答不出来的按 L2 判据重新评估是否降级或移除。
2. L3 是全量执行——运行范围是 `tests/` 目录下当前全部沉淀用例，不是抽样。
   判断方式：执行记录中的用例总数与 `tests/` 目录下实际文件数一致；不一致（比如漏跑某个文件）即违反。
3. 每次 L3 运行后必须记录一条基线数据（用例数/总耗时/边际耗时），供退化信号侦测使用（见「软性墙钟预算」）。
   判断方式：`data/testing-protocol-baseline.md`（见「基线记录」）在本次运行后是否新增了一行对应记录。

---

## 沉淀判据（L2/L3 共享，延续 0026 Q3 裁决）

**唯一判据**：这条测试断言是否有跨迭代契约意义——下一次迭代如果删了它，是否会有人因此吃亏（比如某个被多处依赖的接口行为被破坏而无法察觉）。

**不采用的判据**：物理指标（用例行数上限、单次运行时长上限）。理由延续 0026 迭代 Q3 的已有裁决——物理指标会导致"删到指标合格但删掉了有意义的断言"或"留着凑数但没有契约意义的断言"两种错判，必要性判据虽然主观，但可以通过「判断方式」列的具体核查动作变得可裸判定。

**判断方式（通用，适用于任何一条候选用例）**：
1. 指出该断言验证的具体接口/文件/行为
2. 指出"如果这个行为被破坏，谁会受影响"——具体到某个工具/角色/下游迭代，不能是"可能有人用得上"这种无主体描述
3. 两条都能具体回答 → 沉淀；任一条答不出来 → 不沉淀（如果已存在，标记为精简候选，见「软性墙钟预算」）

## 语言栈反射规则

**核心原则**：接到任务先探测项目/PR 实际使用的语言栈证据，再套用该栈下最小可行的测试写法，不写死某一种语言的固定分支。

**探测方法**（按优先级尝试，找到即停止）：
1. 读该项目/子目录下的包管理文件：`package.json`（node）、`pyproject.toml`/`requirements.txt`（python）、无包管理文件但存在 `*.sh` 且该目录下已有测试文件用 `assert_eq` 类手写断言风格（bash）
2. 若包管理文件缺失或不明确，读该目录下已有测试文件的文件后缀和写法风格，沿用已有约定
3. 两者都缺失（全新语言栈首次接入测试）时，在报告里说明"这是本仓库该语言栈的第一份测试"，选择该语言标准库/内置能力优先，不引入新依赖（对齐「不引入第三方依赖」的仓库立场）

**已知语言栈的最小可行写法**（事实说明，非强制规则——换语言栈或该语言栈的写法演进时，以「探测方法」为准，不是死记这张表）：

| 语言栈 | 探测线索 | 最小可行写法 | 仓库内先例 |
|---|---|---|---|
| **node** | `package.json` 存在，`type: module` | 内置 `node --test`，`assert` 模块断言，文件名 `*.test.js`（原 `oamp/test/` 曾用此写法，已被 0026 迭代整体清理，无当前先例可直接复用，需按此写法重新起草） | 无（0026 后为空白） |
| **python** | `pyproject.toml`/`requirements.txt` 存在，或已有 `.py` 脚本无包管理文件 | 标准库 `unittest`，或直接用 `assert` + 显式退出码（对齐 `tools/check-pr-gates.py` 当前无测试覆盖的现状，若新增测试优先标准库） | 无（`tools/check-pr-gates.py` 当前无对应测试） |
| **bash** | 目标是验证一个 `.sh` 脚本的行为，无包管理文件语义 | 手写 `assert_eq` 函数 + 累计 pass/fail 计数 + 非零退出码 | `tests/test-check-role-structure.sh`、`tests/test-check-model-dispatch-protocol.sh`（仓库现有先例，新增同类测试应遵循相同的 `assert_eq`/计数/退出码结构） |

## 软性墙钟预算（追加信号，不替代沉淀判据）

**性质声明**：这是**追加的退化信号**，用于主动侦测套件是否在复利式变慢，**不是沉淀判据的替代**——沉淀判据永远是「沉淀判据」章节定义的必要性判断；软性预算超限只触发"该精简了"的报告，不阻塞任何交付。

**基线记录**（`data/testing-protocol-baseline.md`，`test-keeper` 每次 L3 运行后追加一行）：

```markdown
| 日期 | 迭代 | 用例数 | 总耗时(s) | 边际耗时(s/用例) |
|---|---|---|---|---|
| {YYYY-MM-DD} | {迭代ID} | {N} | {T} | {T/N} |
```

**历史基线（0026 迭代前，供本协议阈值制定参考，不是仍在生效的当前数据——`oamp/test/` 已在 0026 全部清理，`tests/` 目录当前的 2 个 bash 脚本耗时远低于此表）**：

| 迭代 | 用例数 | 总耗时(s) | 相邻迭代新增用例的边际耗时(s/新增用例) |
|---|---|---|---|
| 0016 | 251 | 55.7 | — |
| 0018 | 285 | 57.1 | 0.04（= 新增34用例耗时1.4s ÷ 34） |
| 0021 | 333 | 61.1 | 0.09（= 新增48用例耗时4.0s ÷ 48） |
| 0024 | 387 | 68.5 | 0.14（= 新增54用例耗时7.4s ÷ 54） |

**读法**：这条边际耗时不是"总耗时÷总用例数"，是"两次迭代之间新增的用例，平均每条拖慢了多少秒"——三段边际成本 0.04→0.09→0.14 递增，说明新增测试的单位成本本身在变高（可能是新用例越写越重，或复用度下降），这正是「软性墙钟预算」章节"边际耗时环比阈值"要捕捉的趋势。

**软性预算阈值**（初始值，供 test-keeper 首次判断使用；发现阈值不合适时可在 `data/` 记录调整理由后修订本节，不需要经过复杂流程）：

- **总耗时阈值**：单次 L3 全量运行总耗时超过 **60 秒**，触发提示——理由：60 秒是本仓库已实测的前台执行上限（超过会转后台+额外模型回合+轮询粒度成本，见 0026 迭代 F-2 实测），超过这个数字意味着运行成本结构已经变化，值得主动提醒。
- **边际耗时环比阈值**：本次记录的边际耗时相较上一条基线记录**上涨超过 30%**，触发提示——理由：历史基线里 0016→0018 环比涨 125%、0018→0024 累计涨约 55%,不到 30% 的正常波动不必打扰,超过 30% 已经是明显趋势,早发现的成本远低于晚发现（复利式增长，见 test-keeper 角色 Strategy 章节）。

**触发后的动作**：`test-keeper` 在报告的"退化信号"字段里写明具体超限项（总耗时/边际耗时哪个超了、超了多少）+ 精简候选（按「沉淀判据」重新评估耗时占比最高的几条用例，指出候选和理由）。是否精简、精简哪条，由主 agent/用户决定,`test-keeper` 不擅自删除。

## 与 workflow-pb 的接入点（索引，判断逻辑权威定义在本文件，不在 workflow-pb.md 复制）

- **阶段5后可选触发 L2 冒烟**：某个或全部 PR 合并完成后，主 agent 可选调用 `test-keeper` 跑一次 L2 冒烟；不是强制推进条件，不影响阶段5的推进判定。
- **阶段6前可选触发 L3 回归**：独立验证（阶段6）触发之前，主 agent 可选调用 `test-keeper` 跑一次 L3 全量回归，作为验证素材之一；`test-keeper` 的报告不替代 `verifier` 的独立验证结论。
- 两个触发点都是**可选**，不是新的强制推进条件——这条协议不追溯修改 workflow-pb 现有的阶段5/阶段6推进条件定义。

---

## 与其他角色的边界（索引）

- **与 `dev` 的边界**：L1 用例的编写权在 `dev`，`test-keeper` 不参与阶段5派发循环。见 `roles/dev/dev.md:107` 现有例外条款。
- **与 `verifier` 的边界**：`test-keeper` 不判断自己维护的 L2/L3 套件是否"覆盖到位"，那是 `verifier` 的独立验证职责；`test-keeper` 只对"套件是否存在、是否可运行、是否符合本协议"负责。
