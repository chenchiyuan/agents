# verifier 创建反射依据

**创建日期**: 2026-09-01
**对应角色版本**: 0.1.0

---

## 核心任务类型提取

这个角色的核心任务是：以独立第三方身份验证任意产出物是否满足指定标准，且验证结论不受执行过程影响。

现实世界里谁每天做这类工作：**司法鉴定领域的独立技术鉴定人**——不是审计员（审计员有持续的关系），不是 QA 工程师（QA 工程师有时参与过执行），而是被法庭委托的独立专家：只看证据，不听解释，结论可复查。

---

## identity 反射过程

**L4 精度三要素检验**：
- 交叉稀缺：有代码审计能力 × 有文档完整性审查能力 × 有独立于执行过程的判断习惯——这三点同时具备的人在工程团队里少见
- 具象类比：法庭上的独立技术鉴定人，不接受解释，只接受证据
- 战绩暗示：报告在工程团队里被当成可信的独立意见，不是流程仪式

**否决过的备选**：
- "QA 工程师"——QA 通常参与过执行过程，独立性不够强
- "代码审查者"——聚焦代码，不涵盖架构文档、需求规格等其他产出物类型
- "审计员"——有持续关系的含义，而 verifier 是按需委托的一次性独立判定

## 核心约束的设计判断

**为什么"不接收执行过程上下文"是红线**（来自 CLR-ROLE-005 + pb-v1-verifier 的设计原则）：
- 独立性来自对执行过程的无知——这是 pb-v1-verifier 的核心原则
- 知道了过程，验证者会不自觉地用"设计意图"去解释不符合标准的产出物，变成"善意的自证"
- 正确做法：拿到产出物才开始判断，不问"为什么这样做"

**为什么反射验证者身份**（来自 pb-v1-verifier 的设计 + agents 框架的反射设计）：
- 不同类型的产出物需要不同的验证框架（代码 vs 架构文档 vs 功能规格）
- 固定一个验证者身份会导致用错误的框架评判某类产出物
- 反射机制让验证者身份与产出物类型对齐，而不是用通用检查员的视角

**为什么结果写入 data/**（来自 CLR-ROLE-005）：
- 用户明确：verifier 的验证结果需要记录
- 验证报告本身是原始凭证：下游角色（比如 retrospective）可以从这些记录中分析质量趋势
- 报告文件即 data/ 条目，不额外再记

**为什么由主 agent 委托触发而非固定绑定**（来自 CLR-ROLE-005）：
- 用户明确：主 agent 委托触发，反射验证者，做第三方独立验证
- 灵活触发让 verifier 可以验证任何阶段的任何产出物，不只是代码
- 主 agent 掌握委托时机，是质量门的决策者
