## 一、用户提出的问题（原话）

> "重点看与hub协作的地方，我发现了诸多问题：比如主agent与hub之间的联系似乎会断，任务完成了，但是主agent没拿到返回，一直在等，必须我主动询问才有后续。临时解决方案是用的watchdog，但是这种实现是不优雅的。说到底是本agent和hub，hub和任务agent的双向通讯机制有问题"

## 三、机制级根因（三层，逐条附代码位置）

### 3.1 主 agent → hub：**能发，不能收**（根因）

- 主 agent 与 hub 的每一次交互都是**一次性的 CLI 进程**（`node oamp/bin/hub.js …`）：进程建立 link、发请求、退出。
- `docs/multi-omp-agent-protocol.md:237` —— **协议自己写下了这个待办**：
  > "只有携带有效 `link_id` 的连接才能调用 `agent.register`、`message.send` 和接收 `message.deliver`。Router **不接受没有服务链接的"离线发送方"，除非后续明确增加持久化发送端身份机制**。"
- ⇒ 主 agent 属于"离线发送方"：**没有持久身份 ⇒ 没有可投递地址** ⇒ 结果无处可送。
- `oamp/src/router.js:101` 的投递原语 `holder.peer.request('message.deliver', …)` 需要**对端持有活连接**；主 agent 在两次工具调用之间**不存在这样的连接**。

### 3.2 hub → 主 agent：结果面只有"拉"和"挂住 link"，**没有"送达"**

- 结果的去处是**调用登记 + chat 消息**，不是"回给请求者"：
  - `oamp/src/web.js:1129-1145`（`GET /api/calls` roster）：`const rows = (r.tasks || []).filter((t) => t.from === SENDER_ID)` ——**范围收口 `from==='web'`**；代码注释（`:1138`）明写"CLI（`from='main'`）派发的任务无 chat 归属，**不进调用面**"。
  - `oamp/src/web.js:45`：`const SENDER_ID = 'web'; // web 服务作为常驻发送方身份（R2：客户端节点）` —— **只有 web 是"常驻发送方"**；主 agent 不是。
- 唯一"拿到终态"的正规路径是**把 link 挂住**：
  - `oamp/sdk/surface.js:88-94`：`mode: 'block'` 才延长响应头预算，上限 = `waitMs ?? 1800000 + margin`（30 分钟）⇒ **`--mode block` 是同步阻塞，不是回调**。
  - 本轮**两条 F08 实报就是靠 `--mode block` 拿到信封的**（`task-67cb177b…` / `task-84c498ea…` 均带 `--mode block` 并同步返回）⇒ 能力存在，但**只对"短调用"可用**：工作流的派发动辄数分钟到 30 分钟（G-9 上限），阻塞式等待在主 agent 的回合里不可用。
- ⇒ **结果面是"拉"或"挂住"，不存在"送到请求者手上"**。这就是用户说的"联系会断"。

### 3.3 `stream call` 死等 = 已有推送面**缺一个关闭动作**（G-14 的代码级根因）

- 推送面**早就齐全**（`oamp/src/web.js:13-21` 路由清单）：
  - `GET /api/stream?chat_id=` → SSE：`message / task_update / chat_state / notice`
  - `GET /api/events` → 全局 SSE：`agent_online / agent_offline / confirmation / chat_state`
  - `GET /api/calls/stream?chat_id=` → SSE：`call_state / call_update / **call_result**`
  - `GET /api/calls/<call_id>/stream` → 按调用订阅（同三类事件）
- 但**终态时没有任何人关掉订阅**：
  - `oamp/src/transport.js:75-77`：`handleCallStream` 只做 `subscribe(req, res, callKey(callId))`。
  - `oamp/src/transport.js:103-106`：`publishCall` 只 `publishTo(callKey/chatCallsKey, event)` —— **发帧，不 `closeKey`**。
  - `oamp/src/transport.js:60-72`：`subscribe` 仅在**客户端断开**时清理（`res.on('close', …)`）；`closeKey(key)`（`:120-127`）这个关闭原语**在调用终态路径上从未被调用**。
  - `oamp/sdk/cli.js:221-238`（`runStream`）：客户端只在**服务端关流**（或 EPIPE）时退出 ⇒ 服务端不关 ⇒ **CLI 永远挂着**。
- 附带缺口：`oamp/src/transport.js:84-90` `publishTo`：**"无订阅者 → 直接丢弃（不缓存、不排队、不补发，§5.4）"** ⇒ **晚订阅者一条也收不到**（调用先结束、后订阅 ⇒ 静默 + 永久挂着）。

### 3.4 hub ↔ 任务 agent：单 daemon 串行、队列不可见、不可取消（G-19）

- 任务 agent 的轮次由**每实例一个 daemon** 承担（实测：`bun omp --mode rpc --no-session …`，PID 唯一）⇒ **一次一轮**，且**没有并发队列的可见面**（`api agents` 只给 `state`，没有 queued/running 队列深度）。
- 派发给"执行者自己的实例"⇒ 外层轮次在等内层终态、内层要跑又占同一 daemon ⇒ **自排队死锁**（本轮 24 分钟）。内层信封原文即证据：`text: "上下文实例已不可用，排队轮次未执行"`。
- **无取消入口**（`hub api` 无 `calls cancel/abort`）⇒ 一旦互锁，唯一手段是外部杀进程，且**需要 operator 先怀疑它**。
- 对照组的决定性证据：同轮发往**另一个实例**的实报 **4.8 秒即成功** ⇒ 证明"同实例"才是互锁条件。

### 3.5 观测面：只有"状态查询"，没有"停滞信号"（G-20）

- `api calls list` 给的是**状态快照**（`state` / `started_at` / `ended_at` / `model`），**没有 `last_event_at` / `idle_ms`**；`agent` 的日志在磁盘上但 hub 不投影。
- ⇒ "正常长跑（35 分钟被上限切断）"与"卡死（24 分钟不动）"在观测面上**不可区分**，二者都以"还在 working"呈现。watchdog 只能等"终态"，而卡死恰恰不产生终态。

## 四、修复建议（按性价比排序；前两条是"消除 watchdog 存在理由"的关键）

### 4.1 外科级（几行代码，立刻可选）

1. **调用终态时关闭该调用的订阅**（修 G-14 的根因）：在发出 `call_result` 帧之后对 `callKey(callId)` 调 `closeKey` —— 仅关 `call:<callId>`，**不动** `chat-calls:<chatId>`（后者是控制台的长订阅）。
   - 改点：调用终态路径（`publishCall(callId, {type:'call_result', …})` 之后）+ 复用既有 `oamp/src/transport.js:120-127` 的 `closeKey`。
   - 效果：`hub api stream call <id>` **在终态当刻退出**，可直接作为工具调用使用 ⇒ **watchdog 的存在理由消失**。
2. **订阅时若调用已终态，补发终态帧后立即关流**（修"晚订阅者收不到"）：在 `handleCallStream` 里先 `router.task_get`，终态则写一帧 `call_result` 并 `closeKey`。
   - 有了 1+2，`stream call` 就是**幂等的"等这一次调用"**原语：无论先后订阅、无论快慢，都能拿到终态。
3. **给 layer A 增加等待入口**：`hub api calls wait <id…> [--timeout <ms>]` —— 一次工具调用返回全部信封，退出条件 = 全部终态（可基于 1+2 的流实现；多 id 时并发订阅）。
4. **`calls cancel <id>`**（G-19 ③）：让互锁/失控可被主动解除，而不是靠外部杀进程。

### 4.2 设计级（补上协议自己写下的待办）

5. **持久化发送端身份 + 会话收件箱**（`multi-omp-agent-protocol.md:237` 的 TODO）：让主 agent 这类"长期存在、但每次交互换进程"的调用方**注册一次、长期可寻址**，并拥有一个**跨工具调用存活**的收件箱。
   - **参照物就在仓库里**：确认（confirmation）链路已经跑通这套形状 —— `oamp/src/agent.js:283-299`：请求方**挂起一个 promise** → `sendNotice(…, kind:'confirmation_request')` **推给 chat** → 裁决回来 `resolve` 它。**"请求方挂起 + 事件推给一个可寻址的收件面"** 正是调用结果该有的形状。
   - 落地形态（二选一或并存）：① 调用终态时向 `from` 的收件箱投一条 `call_result`（新增事件类，复用既有推送面）；② 主 agent 长期订阅 `/api/events` 的一个"我的调用"过滤流。
6. **队列可见性**（G-19 ①）：`api agents` 增列每实例的 `queued` 数 / 当前轮次的 `since`；`calls create` 对**目标实例 = 调用者自身**做**前置拒绝或显式告警**（本轮若有一条告警，24 分钟的死锁根本不会发生）。
7. **停滞投影**（G-20）：`api calls list` 增列 `last_event_at` / `idle_ms`（或让 `transcript`）⇒ 监控从"猜状态"变成"看推进"。

### 4.3 客户端纪律（在 4.1/4.2 落地前，本工作流该怎么写）

8. **禁止把 watchdog 当"等待机制"的默认解**，改为按调用长度分流（写进执行方式规范）：
   - **短调用（秒级~1 分钟）**：直接 `--mode block` —— **这是 hub 已支持、最快、零自建的路径**（本轮两条 F08 实报即此形态）。
   - **长调用（分钟级~30 分钟）**：把等待**交给持有轮次的执行角色**（它在自己回合内阻塞本属自然），主 agent 只负责"派发 + 记录 + 事后核对产物"。
   - **必须由主 agent 等待时**：用**带停滞判定的**有界 watchdog（终态 + 实例日志推进 + `pane_dead` 三项），并且**只在持有在途调用的实例上判停滞**（我 v2 版本因为扫了全部实例、把 8 个空闲实例误报成停滞 —— 这条误报本身也是教训）。
9. **派发前先问"结果能回来吗"**：若答案依赖"我盯着"，就要求执行角色**把结论写进产物文件**（本轮全部 PR 的做法），让主 agent 的推进**依赖文件而非消息**——这是本次能在通讯面残缺的情况下仍跑完 10 个 PR 的真正原因。

## 五、做得好的地方

1. **三条绑定实报的对照设计**：同一 chat、命令除 `--agent` 外逐字一致、**均不带 `--model`** ⇒ 唯一变量被压到一个字段，`dev` → gpt / `verifier` → grok / `prd` → 默认链路三后端同时成立，**结论无法用巧合解释**。
2. **"禁止重跑探针"的克制**（pr-004）：探针信封随集群重建失效后，PR **没有**为了让证据好看去重跑（重跑会在阶段 2~6 内新增 `--model` 调用、直接破坏"例外通道唯一性"），而是**如实登记"登记面判据"** —— 宁可弱，不造假。
3. **不信自述、核产物**：pr-007 的 dev 被节点上限切断（`failed/timeout`），但 worktree 上**已有提交** ⇒ 按"现场保留 + 以文件系统为准"直接进验收，未白跑一轮。
4. **两轮独立验证各自抓到真问题**：pr-008 抓出我台账的 9 行 `truncated` 错记 + 1 行陈旧重复行；pr-006 抓出一处"不可复制执行"的证据块（含未绑定占位符、以散文充当管道阶段）⇒ 独立验证不是仪式，确实在拦错。
5. **同一实例/跨实例的对照**：G-19 的诊断之所以能一锤定音，是因为同一轮里有一条**发往另一实例并 4.8 秒成功**的调用作对照。
6. **收口期三次"同源缺陷"被自检抓住**：差距记录丢 3 条、10 份任务列表未跟踪、3 份孤儿产物（含阶段 4 的 Gate 报告）——**都在删工作区之前被拦下**，且我明确写下"这是同一类（G-13 家族）的第 N 次出现"。

## 六、原则候选（每条附三问）

**候选 A（通讯）**：{凡是"调用方等待被调方结果"的机制，必须在**协议层**给出**送达**或**有界等待**二者之一，且**等待的退出条件必须由终态驱动**；若只能由超时驱动，则该机制在语义上尚未完成 —— 不得把它当作已支持的能力来编排流程}。
三问：①三个月后成立？✓（"超时≠终态"是分布式通讯的长期规律）②换场景适用？✓（任何"派发—等待"链路）③一句话可执行？✓
Observation：本轮的直接代价是"7 个等待作业全部靠 15~30 分钟超时交付"，而**用户为此不得不多次主动推动**。仓内 `multi-omp-agent-protocol.md:237` 已自认缺"持久化发送端身份机制"，本条是把该缺口**从协议待办升级为编排前提**。

**候选 B（等待的归属）**：{等待应由**持有轮次的一方**在其回合内阻塞完成（`--mode block`），而不是由调度方在回合外轮询；调度方的推进应当**依赖产物文件**，而不是依赖"消息送达"}。
三问：①✓（轮次内阻塞是同步语义的自然位置）②✓（任何"调度者 + 执行者"分工）③✓
Observation：本轮在"结果不送达"的残缺通讯面上仍能跑完 10 个 PR，靠的正是"**每个角色把结论写进自己的 PR 文件**"这条产物契约（workflow-pb 的「产物是唯一输出契约」）——**它是本次事实上的通讯层**。

**候选 C（代理指标）**：{当"任务是否在推进"无法直接观测时，自建的监控必须同时检查**代理指标**（该实例日志的推进、进程存活），只等终态的监控在卡死场景下**等于没有监控**}。
三问：①✓ ②✓（任何"长任务 + 无心跳"的观测）③✓
Observation：我 v2 watchdog 的**误报**（把 8 个空闲实例判成停滞）与 v1 的**盲区**（卡死看不见）是同一枚硬币的两面：**判据的适用范围写错，监控就从"没用"变成"误导"**。
