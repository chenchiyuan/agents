# retrospective.md 变更历史

---

## v0.3.0（2026-09-02）

**需求**：用户发现所有复盘归档全部堆在 `roles/retrospective/data/`，违反"复盘得根据角色案例"的设计初衷——比如 dev 相关的复盘应该在 `roles/dev/data/` 下，不该全部混在 retrospective 里。

**变更原因**：v0.2.0 的「归档执行」步骤只写了"写入 data/"，没有说明写到哪个角色的 data/——历史执行时默认把所有复盘发现都塞进了 retrospective 自己的 data/，导致本该分散到各角色的执行案例、本该记在具体角色名下的设计依据，全部混在一起，破坏了三级记录体系"每个角色的 data/ 是自己的案例库"这条设计。

**决策过程**：
- 排除方案：新增一个独立的项目级记录位置（如 `docs/retrospectives/`）来承载所有找不到单一角色归属的发现——否决理由：这只是把"混装"从 retrospective/data/ 挪到另一个新目录，没有解决"该怎么判断归属"这个根本问题
- 采纳方案：补一条显式的「归属判断」规则，按"这件事的主体是谁"分五类判断落点（角色执行行为偏差 / 角色设计依据 / 工作流协议设计 / 跨角色案例 / 主 agent 过程级案例），只有后两类才留在 retrospective 自己的 data/
- 明确 retrospective/data/ 的边界：不是"复盘产出的默认归宿"，只装两类——跨角色案例（3+ 角色才归这里）、过程级案例（主 agent 会话/设计过程本身，不属于任何具体角色执行任务）；加上 retrospective 自己的 changelog/reflection（这和其他角色的 data/ 性质相同，不在归属判断范围内）
- 存量整理：历史 4 个混装文件（`retro-2026-09-02-workflow-scm.md`、`retro-2026-09-02-model-dispatch.md`、`retro-2026-09-02-workflow-pb.md`、`retro-2026-09-02-workflow-pb-v2.md`）按新规则重新拆分归位

**经验总结**：三级记录体系的"每个角色一个 data/"设计，前提是**归档时真的按角色归属写**，不是"谁执行归档动作，谁的 data/ 就是默认落点"。retrospective 角色执行归档不等于记录归属 retrospective——这是"执行者"和"记录主体"的角色混淆，和 `principles/execution/core-principles.md`「权责分离」原则是同一类问题的另一种表现形式。

## v0.2.0（2026-09-01）

**需求**：用户要求"复盘角色"能主动引导复盘讨论、分析根因、推导原则候选，而不只是被动接收原材料做记录管理。三个目标：①找错误+分析+防止再犯；②总结好的做法+沉淀原则；③归档更新 memory。

**变更原因**：v0.1.0 的 retrospective 是"记录管理员"定位（被动接收、判断放哪、写文件），只覆盖了用户目标的第三条（归档）。角色定位不匹配用户需求。

**决策过程**：

- 核心任务类型重新反射：从"判断经验值不值得记"改为"判断什么观察值得变成原则，并引导用户讨论确认"
- 现实世界对应原型：从"SRE post-mortem 文化建设者"改为"在多团队建立过复盘文化的敏捷教练"，原因是后者的核心能力和这里的需求更精准——核心技能是"从 8-12 条观察里过滤出 0.5-1 条真正的原则"
- 设计了"三问过滤"作为核心工具（三个月后还成立？换场景适用？能说清遇X做Y？）
- 确立两阶段模式：Phase 1（AI 主导扫描分析）、Phase 2（用户发起讨论确认）——这个分法来自自进化提升循环原则的阶段划分，保持一致
- 保留了 v0.1.0 的记录管理能力（data/ 写入 + memory.md 整理），作为归档阶段整合进去
- 新增原则"机制性描述优先"：来自本次迭代对反射设计原则描述的优化——原则应写判断框架（遇X做Y），不写约束清单（禁止/必须）

**用户确认**：用户在 Phase 1 扫描报告后回复"good，请继续"，视为对复盘发现和角色设计方向的整体确认。

**经验总结**：记录管理和复盘引导是两个不同能力——前者判断"信息放哪"，后者判断"这条观察值不值得变成原则"。v0.1.0 只有前者，本次重写补上了后者，同时把前者整合进归档阶段。

**经验总结**：retrospective 和 dev 的核心区别在于"判断是否值得记"——dev 的 Reflect 阶段只需判断有没有值得记的；retrospective 负责实际执行记录和维护索引，且引入"可检索性 > 完整性"作为记录质量的第一判断标准，这是 post-mortem 文化里真实的工程教训，不是从零推导的原则。
