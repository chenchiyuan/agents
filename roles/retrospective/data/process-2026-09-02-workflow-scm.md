## 案例：主 agent 在填 model_inferred 时脱离了元思想框架

**现象**：F05 的 `model_inferred` 需要确认 PR 粒度判断标准，主 agent 给出了"预估 diff < 400 行"的数字答案。这个数字传播到 workflow-scm.md §验证目标，直到用户在迭代交付后指出才修复。

**根因**：`model_inferred` 是"填空"场景——问题已经给好了（"上限值需主 agent 确认"），主 agent 进入了直接回答的模式，而没有先退一步问"这个位置是否应该是数字"。元思想原则失效的时机，往往不是面对空白设计，而是面对一个已经定型问题框架的填空。

**候选原则**（暂未升级）：遇到"请确认某个指标的具体值"类填空，先判断"这个位置是否应该是数字"，再回答；如果质量判断类问题用数字回答，要能说明为什么数字比原则框架更合适。

## 案例：批量修改多个同类文件，只独立验证了其中一个（第 1 次出现）

**现象**：prd 改完后做了无上下文子 agent 独立验证；demand/architect/planner/dev 改完后只做了 grep 模式检查，没有逐一独立验证。

**根因**："模式相同，抽检一个"的推论跳过了独立验证本身——每个文件可能有自己特殊的遗漏。

**候选原则**（**在 `process-2026-09-02-workflow-pb.md` 案例3中第 2 次独立出现，接近升级门槛**）：批量修改多个文件后，不能用"模式相同、抽检一个"代替逐一验证。如果独立验证成本高，至少用自动化检查（覆盖所有文件的 grep 模式列表）逐一跑。
