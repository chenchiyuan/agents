## 复盘案例：0003-workflow-scm 迭代（2026-09-02）

**迭代范围**：workflow-scm 工作流新建 + commit-planner 角色新建 + workflow-pb Phase 5 插入 + verifier 验证 + 400 行问题修复

---

### 案例 1：主 agent 在填 model_inferred 时脱离了元思想框架

**现象**：F05 的 `model_inferred` 需要确认 PR 粒度判断标准，主 agent 给出了"预估 diff < 400 行"的数字答案。这个数字传播到 workflow-scm.md §验证目标，直到用户在迭代交付后指出才修复。

**根因**：`model_inferred` 是"填空"场景——问题已经给好了（"上限值需主 agent 确认"），主 agent 进入了直接回答的模式，而没有先退一步问"这个位置是否应该是数字"。元思想原则失效的时机，往往不是面对空白设计，而是面对一个已经定型问题框架的填空。

**升级候选原则**：遇到"请确认某个指标的具体值"类填空，先判断"这个位置是否应该是数字"，再回答；如果质量判断类问题用数字回答，要能说明为什么数字比原则框架更合适。

---

### 案例 2：verifier 的验证标准严于项目约定，产生假阳性

**现象**：verifier 报 A1/B1 partial，理由是 frontmatter 缺少 version 和 created_at 字段。实际项目约定是版本/日期写正文（已在 dev.md/verifier.md 第 21-22、27-28 行确认），frontmatter 无此要求。

**根因**：verifier 的验证标准来自对"规范文件应有什么字段"的通用推断，不是对项目既有约定的核查。verifier 在比较"自己认为应该有什么"，不是"项目说应该有什么"。

**升级候选原则**：遇到 verifier 报 partial，先核查对应标准在项目约定中的出处，再判断是真实缺失还是标准过严；没有出处的验证标准要降级或修正，不当作真实问题处理。

---

### 案例 3：同一概念多处出现，改完后只验证了单点

**现象**：PR 路径结构在 workflow-scm.md 中完整表达，但 workflow-pb.md 的文档路径图没有同步加入 `prs/` 子目录，被 verifier 发现（NEXT-002）。

**根因**：修改后的验证只检查了"各自内容是否正确"，没有主动做"多处是否一致"的交叉检查。同一概念多处出现时，单点验证无法覆盖跨文件一致性。

**升级候选原则**：同一概念出现在多个文件时，改完后主动做显式的跨文件一致性检查，不依赖 verifier 兜底；可在任务完成前列出"该概念在哪些文件中有记录"，逐一核对。

---

### 案例 4：两层工作流在自然接缝处握手（好做法）

**做了什么**：workflow-pb（产品层）和 workflow-scm（git 层）以 tasks.md 为握手点，各自独立闭环，不相互侵入对方职责。

**为什么有效**：tasks.md 是"任务已确定、实现未开始"的天然分界线——产品层到这里完成了分解，git 层从这里开始规划提交。选这个点握手，两层各自的阶段划分都不需要妥协。

**升级候选原则**：在两个工作流之间插入握手时，找已有产物中的自然接缝点，而不是创造新的人造边界。

---

### 案例 5：迭代特定规则通过 brief 传递，通用角色文件不动（好做法）

**做了什么**：verifier 的验证标准通过派发 brief 内联传入，而不是修改 verifier.md 本身。

**为什么有效**：verifier 是通用角色，能力是"按给定标准验证"。把迭代特定的验证标准写进角色文件，是把上下文和能力混在一起，导致角色文件随每次迭代膨胀。用 brief 传递，角色保持通用，标准跟着迭代走。

**升级候选原则**：迭代特定的规则通过调用时的 brief 传递，不写进通用角色文件。
