### 发现的问题

#### 1. 子 agent 派发后中途停滞，19 次工具调用零 Write 却报告"completed"

- **现象**：0005 阶段 3 第一次派发 architect，运行约 10 分钟、19 次工具调用全部是 Read/Bash，从未调用 Write，未生成 `architecture.md`，任务通知却显示"completed"。记录末尾是连续多轮空的 thinking 内容，无 tool_use、无文本。主 agent 靠人工翻查原始 transcript（因文件过大，用 Python 逐行解析 JSON）才发现真相，未采纳其任何内容，重新派发才成功。
- **根因**：子 agent 的"completed"状态只反映"停止再产生 token"，不反映"完成了任务契约要求的产出"。当前调度侧没有一个轻量信号（如"该角色的报告契约要求必须有 Write 调用"）能在通知层面提前区分"真完成"和"静默耗尽/迷失方向"。
- **原则候选**：遇到子 agent 长时间运行后返回"completed"但该角色的报告契约本应产出文件，先检查 transcript 里是否存在与预期产出物路径匹配的 Write/Edit 调用，不能只看返回状态字样；若没有，视为未完成，不采信其自我报告，重新派发。
- **三问**：①三个月后成立？✓（子 agent 静默停滞是执行环境的常见故障模式，不会消失）②换场景适用？✓（任何要求"必须产出文件"的角色派发都适用）③一句话可执行？✓
- **Observation**：目前没有现成原则覆盖"子 agent 声称完成但未产出"这一检测环节——workflow-pb.md 的「产物是唯一输出契约」原则解决的是"信不信自称完成"，但没有解决"怎么快速识别自称完成是假的"，这次是靠人工深挖 transcript 发现的，成本较高。

#### 2. demand 角色把协议升级内容写入只读部署副本，而非源文件

- **现象**：0006 迭代里，demand 角色被主 agent 要求"把设计正式写入协议文件本身"后，实际把 v0.3.0 改动写进了 `.pb-agents/roles/demand/demand.md`（协议规定的只读部署副本，`.gitignore` 排除），而不是源文件 `roles/demand/demand.md`。主 agent 事后通过 `git status`（源文件无改动痕迹）才发现，用 `diff` 核实内容后手动 `cp` 修复。
- **根因**：`.pb-agents/roles/` 只读的约束目前只写在 workflow-pb.md/SKILL.md 里，供 workflow-pb 这个调度角色自己遵守（"本 skill 只读取，不修改"）。但当主 agent 把"直接改协议文件"这个非常规任务派发给 demand 角色时，brief 里没有显式指明"源文件路径是 X，不是 Y"——demand 角色自己没有理由知道这个只读约束的存在，它按最直觉的路径（当前会话里读到的那份文件）去写了。
- **原则候选**：遇到派发执行角色去直接修改协议/角色文件本身（而非产出该角色常规契约内的文件）这类非标准任务时，brief 必须显式写明"可写的源文件路径是 X，`.pb-agents/roles/` 下的同名文件是只读部署副本，不要写那里"，不能假设角色能自己推断这个区分。
- **三问**：①三个月后成立？✓（只读部署副本机制是项目长期架构，这类误写风险持续存在）②换场景适用？✓（任何"直接改协议文件"的派发都适用）③一句话可执行？✓
- **Observation**：`roles/retrospective/data/process-2026-09-03-workflow-pb-skill-optimization.md` 案例 3 记录过同一大类风险的另一种触发机制——"改动会被 copy 到 `.pb-agents/` 的文件时，没检查双环境路径引用是否都成立"，当时用户选择先记案例未升级。这次是同一大类风险（`.pb-agents/` 只读边界）的**第二次独立出现，但触发机制不同**（上次是"引用路径未检查两个环境"，这次是"子 agent 直接写错了目标文件"）——如果按"独立出现次数"累计，这类"只读部署副本边界"风险已经出现两次，值得在 Phase 2 讨论时提及。

#### 3. 用协议文字升级去解决"协议从未被真实执行"的问题，但升级后的文字本身同样没被执行验证

- **现象**：0005 迭代的根因诊断（demand.md）是"v0.2.0 依赖解锁式并发调度协议文字从未被真实调度执行过一次"。迭代交付后，阶段 6 独立验证显示：协议文字层面 F01~F05 共 20 条标准 16 pass/4 partial/0 fail，达到"描述精确、可执行"标准；但 demand.md §6 的裸判定测试 4 条里 2 条 blocked——因为本迭代阶段 5 自己只调度了 1 个无依赖 PR，从未产生真实的并发/爬升/槛位释放事件，`status.md` 也从未初始化协议新增要求的并发配置区块。
- **根因**：这是一个自指性根因——"协议文字描述得对不对"和"协议是否会被真实遵守"是两个不同维度的问题，前者可以在文字审查阶段（PR verifier、阶段6 verifier）被验证，后者只能靠"真的发生一次多 PR 并发场景"来验证。本迭代的验收标准设计（PR 文件的 8 条 + F01~F05 的 20 条）全部停留在第一个维度，没有一条要求"必须在真实场景里观察到"，这不是执行失误，是验收标准本身的设计空白——如果不显式要求"下一次真实场景要核对"，这类协议升级容易反复停留在"写得更好的文字"层面。
- **原则候选**：当一次迭代的根因诊断是"协议/规则从未被真实执行过"时，仅交付文字修订不能视为根因已解决，必须显式标注"待下一次真实触发场景验证"作为遗留风险（不是待办任务），并在下一次真实触发时把验证证据回填，否则同一根因会在文字层面被反复"修复"却从未真正闭环。
- **三问**：①三个月后成立？✓（"写协议不等于协议被遵守"是长期存在的规律，不会因为这次修复而消失）②换场景适用？✓（任何"协议/规则历史上没被真正执行过"的整改类迭代都适用）③一句话可执行？✓
- **Observation**：`roles/workflow-pb/data/status-protocol-and-phase-exit-gaps.md` 已经记录过"主agent回读验收"和"独立验证"要分字段区分的教训，这次是同一大类问题（"文字/自称层面的完备"和"真实执行层面的完备"要分开判断）在更高层次（整个迭代目标）上的再次出现，说明这条区分原则可能需要从"字段设计"扩展到"验收标准设计"层面。

#### 4. PR 级验收标准比功能卡级验收标准粒度更粗，导致 PR verifier 8/8 pass 后迭代级 verifier 又发现 4 条 partial

- **现象**：PR-001 的 PR 级 verifier 依据 PR 文件的 8 条 checkbox 判定，结果 8/8 pass。随后阶段 6 的迭代级 verifier 依据 F01~F05 功能卡的 20 条更细验收标准重新核对同一份 `workflow-pb.md`，发现 F01-2/F01-3（首批派发指令未绑定"取前N个"封顶）、F02-4（槛位空置不强派未解锁PR从未被正面陈述）、F04-3（无对主agent的显式禁止性清理指令）4 条 partial——这些细节缺口在 PR 级验收时完全没被捕捉到。
- **根因**：PR 文件的验收标准（由 pr-planner 拟定）是对 architecture.md 决策的摘要式转述（"章节包含并发槛位算法的具体描述"），没有下钻到功能卡（F01~F05）里那种带边界条件的具体行为断言（"没有已解锁 PR 排队时，槛位空置，不强行派发未解锁 PR"）。PR 级验收标准的抽象层级天然比功能卡粗，这种粒度落差在"写得对不对"层面容易被掩盖，只有拿功能卡原文重新逐条核对才会暴露。
- **原则候选**：pr-planner 拟定 PR 验收标准时，如果某条 architecture 决策对应的功能卡（prd/F*.md）本身带有"边界条件/否定式行为"（如"不强行做X""没有Y时不触发Z"）的具体断言，PR 验收标准应该直接引用或复制这类断言，而不是只摘要"应该包含XX描述"这种更抽象的说法——否则 PR 级验收会系统性地漏掉边界条件类缺口，只能靠更后置的迭代级验证补漏。
- **三问**：①三个月后成立？✓（PR 拆分/验收标准的抽象层级问题是协议设计的结构性特征，会持续存在）②换场景适用？✓（任何"功能卡→PR文件"的验收标准转写都适用）③一句话可执行？✓
- **Observation**：没有现成原则覆盖这一层级——pr-planner-reflection.md 记录的是"PR 边界怎么划"的判断依据，没有涉及"PR 验收标准的详细程度该参照哪一层文档"。这可能是新原则的来源。

#### 5.（附带发现，非要求覆盖项）0006 迭代走"demand 收敛后直接改协议文件"的简化路径，但这条路径本身未被写入协议

- **现象**：0006 迭代在阶段 1（demand.md）完成后，直接进入协议文件修改，跳过了 prd/architecture/PR 规划/worktree 隔离/planner-dev-verifier 三段式——完全由用户临时指示"这次改动足够具体明确，可以跳"，workflow-pb.md 本身没有定义这条"角色协议直改通道"的适用条件。
- **根因**：workflow-pb.md 目前只把"阶段 1 不可跳过"写成硬性规定，没有定义其他阶段在什么条件下可以被合法跳过（例如"产出物本身是协议/角色定义文档、非运行时代码，且改动范围足够具体明确"这类判断标准）。是否走简化流程完全靠用户临时拍板，协议里没有对应分支。
- **原则候选**：当迭代的产出物本身是协议/角色定义文档（非运行时代码）且改动范围足够具体明确时，可以跳过 prd/architecture/PR 拆分阶段直接进入实现——但这条豁免路径的适用条件应该被显式写入 workflow-pb.md，而不是每次靠用户临时拍板决定。
- **三问**：①三个月后成立？✓ ②换场景适用？✓（agents 项目自身协议开发经常出现"改动即元层文档"的场景）③一句话可执行？✓
- **Observation**：无现成原则覆盖，可能是新原则来源；但价值需要 Phase 2 讨论——如果这种简化路径出现频率不高，也可能只是案例。

### 做得好的地方

#### 1. pr-planner 用"共享文件+跨章节字段引用"判断依据合并 5 处改动点为单一 PR，未强行拆分

- **做了什么**：architecture.md 给出 5 处改动点，pr-planner 判断它们共享同一文件且存在跨章节字段互相引用（如"槛位状态"列取值对应阶段5章节的爬升公式变量名），按"文件范围无重叠"红线判断拆分会导致单点改动无法独立通过验收，合并为一个 PR。
- **为什么有效**：避免了"PR 数量多=拆分做得好"的错误惯性，真正按逻辑原子性和可独立验收性判断，没有为了凑数量而制造人工边界。
- **原则候选**：暂无——这是 pr-planner 角色本身既定判断依据（逻辑原子性/可审查性/独立性）的一次正确应用，`roles/pr-planner/data/pr-planner-reflection.md` 已经记录了这套判断依据的设计来源，本次是案例验证，不是新发现。

#### 2. planner 遗留的 model_inferred 项，主 agent 用 AskUserQuestion 逐一确认后才放行 dev 执行

- **做了什么**：planner 拆解任务时留下 2 项 model_inferred（memory.md 插入位置惯例、是否新建 data 文件），主 agent 没有代为判断，也没有直接让 dev 开始，而是先暴露给用户逐一确认，确认后才把结论显式写进 dev 的 brief。
- **为什么有效**：这正是 workflow-pb.md「用户决策点」章节要求的"model_inferred 未经确认不能生效"，本次执行严格遵守，没有出现"看起来无害就自己拍板"的越界。
- **原则候选**：暂无——协议本身已经把这条写成红线（demand.md/workflow-pb.md 均有），本次是协议按设计生效的案例，不是新发现。

#### 3. verifier 没有采信 dev 的自我报告，独立 grep 核实"模糊表述是否残留"这一争议项

- **做了什么**：dev 报告"这套协议文字从未被真实调度执行"这句模糊表述本来就不存在于 workflow-pb.md 正文（只在上游文档），verifier 没有直接采信，自己独立执行 `grep` 核实，确认属实后才在报告里写明"经独立核实，未发现与 dev 报告不一致"。
- **为什么有效**：避免了"自证清白"式验证——即便这次 dev 的报告是真的，独立核实的动作本身才是让"通过"这个结论可信的原因，而不是"dev 说了就信了"。
- **原则候选**：暂无——verifier.md 本身的 identity/Safety 已经把"不做自证清白式验证"写成核心行为标志，本次是设计生效的案例。

#### 4. 迭代级 verifier 面对"是否算完整交付"的模糊判断，明确拒绝代为下结论，原样交还用户

- **做了什么**：阶段 6 verifier 发现协议文字达标但根本诉求未被证实后，没有自己裁定"能不能收尾"，而是在报告里写"这不是 verifier 能替用户下的结论，需要用户决策"，把两种理解方式（文字达标 vs 实证解决）都摆出来，交给主 agent 和用户裁决。
- **为什么有效**：避免了验证角色在"结论存在解释空间"时用自己的价值判断替用户做主——这类"完整交付"的标准本身就是业务判断,不是技术判断，verifier 只应该把事实摆清楚。
- **原则候选**：{遇到验证结果存在多种合理解释（不是单纯 pass/fail 能覆盖），且这些解释会导向不同的业务决策时，verifier 应该把每种解释各自成立的条件说清楚，明确交还决策权，不代为选择} ← 这条比 verifier.md 现有的"报告契约"更具体（现有契约只说"只报告 pass/fail/blocked"，没有专门覆盖"结果本身有解释空间"的场景）
- **三问**：①三个月后成立？✓ ②换场景适用？✓ ③一句话可执行？✓
- **Observation**：verifier.md 的 Safety 已有"不因为理解了设计意图就放松判定"，但没有专门覆盖"判定结果本身需要业务解释"这一更细的场景，这次可能是对现有原则的一个有价值补充，而不是全新原则。
