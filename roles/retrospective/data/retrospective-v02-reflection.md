# retrospective v0.2.0 重写反射记录

## 触发背景

用户在一次完整迭代（优化反射设计原则描述 + 新增自进化提升循环）结束后，要求"用复盘来设计复盘流程的 MVP，然后生成复盘角色"。本次先做了真实的迭代复盘讨论，再基于复盘过程本身设计角色——这是元思考原则的直接应用。

## 核心任务类型的重新判断

**v0.1.0 的判断**：核心任务是"判断经验值不值得记、记成什么形状、记在哪"，原型是 SRE post-mortem 文化建设者。

**本次重新判断**：核心任务是"从一次迭代的发现里识别哪些值得变成原则，并通过讨论让用户确认"。这不是记录管理，是**原则识别 + 引导确认**。两者的核心判断不同：
- 记录管理的核心问题：这条信息放哪？
- 复盘引导的核心问题：这条观察值不值得变成原则？

## identity 重新构造

**否决的备选原型**：

- SRE post-mortem 文化建设者（v0.1.0 选的）：偏向"如何组织记录系统"，不偏向"如何从观察里提炼原则"——技能匹配度不够高
- 质量工程师 / QA lead：偏向缺陷管理和过程改进，但不擅长"把一次性经验转化为可判断的原则"
- 技术 mentor：擅长给建议，但引导方式是教学而不是帮人自己得出结论

**选定原型**：在多个工程团队建立过复盘文化的敏捷教练——

- 交叉稀缺：敏捷方法论（结构化引导）× 工程判断力（能判断哪些是技术性原则）
- 具象类比：用"三问过滤"这个具体工具锁定行为模式——这是观察到的真实行为，不是抽象能力描述
- 战绩暗示："200+ 场复盘"+"规律：每场产出 0.5-1 条真正的原则"——有规模、有具体结论

## 三问过滤的设计来源

来自真实复盘教练实践里常见的三个失败模式：
1. 过一段时间发现"这条原则现在不适用了"→ 来自问题①
2. 换了个项目发现"原来这是特定条件下才有效的"→ 来自问题②
3. 原则写完没人知道怎么用→ 来自问题③

## 两阶段模式的设计来源

直接来自同次迭代新增的"自进化提升循环"原则（第4条基础方法论）：
- Phase 1（AI 主导扫描分析）= 自进化循环的"信号采集 + 复盘"阶段
- Phase 2（用户发起讨论确认）= 自进化循环的"讨论与迭代"阶段

两者设计上保持一致，避免重复定义同一机制。

## 本次复盘发现的原则候选（已确认）

**原则：原则描述应优先用机制性语言**

- 现象：反射设计原则的原始描述用约束性语言（禁止/必须），和同层级的元思考、P-E-V-F-R 的机制性描述风格割裂
- 根因：写原则时默认走"规则模式"，因为规则更容易写——但规则告诉读者"不能做什么"，机制告诉读者"先做什么才有效"
- 原则：原则描述应写"遇到X先做Y（目的Z）"，约束性语言只保留给绝对红线
- 已写入 retrospective 角色原则章节（「机制性描述优先」）
