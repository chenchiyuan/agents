## workflow-pb 创建反射记录

**需求/背景**：现有执行角色（demand/prd/architect/planner）中有大量工作流耦合代码——角色文件里硬编码了上下游角色名、输入输出文档路径、切换条件。每次工作流调整都要改多个角色文件，且角色之间的引用超过 100 处。

**变更/踩坑原因**：工作流知识和执行能力混在同一个文件里，违反了"职责单一"原则。修改工作流等于修改能力定义，修改范围大且容易引入不一致。

**决策过程**：
- 反射出的 identity：在中型产品团队做过 PM、后来转做交付流程顾问的人，核心执念是出口定义（推进条件必须可验证）。
- 否决了"把工作流写在主 agent 的 CLAUDE.md 里"——那样工作流不可版本管理、不可复用、不可迭代。
- 否决了"工作流作为 skill 而不是 role"——skill 是执行能力，工作流是规范定义，形状不同。
- 确认了 role 形状：workflow-pb 是规范角色，不执行工作，只定义规则。
- 用户确认：6 个阶段完整；每阶段独立验证列；status.md 由主 agent 维护；独立验证可在任意阶段触发。

**经验总结**：
- 工作流规范和执行角色的分离点是"谁定义契约"——工作流定义输入输出契约，角色定义执行能力。两者通过 brief（包含工作流路径 + 迭代 ID）连接，不直接耦合。
- 推进条件是工作流最关键的内容，含糊的推进条件是未来返工的种子。
- status.md 解决了可观察性问题：每阶段"完成"列 + "已验证"列，进度一目了然。
