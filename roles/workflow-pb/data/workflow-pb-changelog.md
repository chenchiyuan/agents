# workflow-pb 变更历史

## v0.7.0（2026-09-07）

**触发**：迭代 `0007-workflow-history-log`——用户需要一份独立于 `status.md` 的、可事后阅读的历史记录，覆盖主 agent 派发、收到报告、调度决策三类事件，且不需要询问执行者或依赖会话记忆即可还原"发生了什么、为什么"。`status.md` 是覆盖式的当前进度快照，不承担"事件流水"这一职责，也不应该被改造承担——两者职责不同，混在一起会让 `status.md` 的格式变得臃肿且难以维护。

**方案**：新增独立文件 `docs/iterations/{迭代ID}/history.md`，只追加不覆盖不删除。四项具体决策：
1. 新增「历史记录协议（history.md）」一节，与「状态追踪协议（status.md）」平级并列，不把两者的格式定义混在同一章节内。
2. 落盘位置纳入「文档路径协议」现有目录树；创建时机为工作流启动创建 `status.md` 之后，若 `history` 字段开启立即创建仅含标题行的空文件（不惰性创建，让"文件是否存在"本身成为开关状态的可观察信号）；运行中途关闭时已存在文件保留不删除、不再追加。
3. `status.md` 头部字段区新增 `**history**: 开启` 一行，取值只有 `开启`/`关闭`，默认 `开启`。
4. 三类事件（派发/收到报告/调度决策）统一用三级标题 `### {YYYY-MM-DD HH:MM:SS} · {事件类型} · {对象}` + 字段行记录，时间戳精度到秒级（同一轮响应内连续记录可能同分同秒，秒级精度尽量保留时间信息，但不承担排序职责）；派发类摘录 brief 已内联字段；收到报告类逐条摘录该角色报告契约已定义的编号/字段项；调度决策类至少含"决策内容"和"触发依据"两个字段。
5. 顺序保真不引入序号字段和同步锁——history.md 的写入动作本身是主 agent 单线程顺序完成的，即使随后并发发起多个 `Agent()` 调用，文件物理顺序天然等于发起顺序；阶段 5 并发派发前先依次追加全部「派发」记录再发起并发调用，补位派发同理先记「调度决策·槛位释放」再记各补位派发条目。

**未改变的部分**：`status.md` 现有格式与维护时机（除新增 `history` 字段行）；并发调度算法本身；任何执行角色文件（`roles/<role>/<role>.md`）本身的报告契约字段定义——本次只在调度层新增"如何摘录"的规则。

**具体改动**：
- 「历史记录协议（history.md）」新节：落盘位置/创建关闭时机 + 三类事件格式与示例 + 顺序保真约定
- 「文档路径协议」目录树新增 `history.md` 一行
- 「状态追踪协议」status.md 格式定义新增 `**history**: 开启` 字段及取值域说明
- 「调度指南 § 启动工作流」新增一步：创建 status.md 后若 history 开启则创建空 history.md
- 「调度指南」阶段1~4推进、阶段5段落各补充一句"同时按历史记录协议追加 history.md 记录"的交叉引用
- 同步更新 `.claude/skills/workflow-pb/SKILL.md`（v1.9.0 → v1.10.0）

**未采纳的方案**：引入递增序号字段辅助排序——否决理由是写入本身已顺序完成，文件物理顺序已天然保真，序号字段不解决任何"序号字段之外解决不了"的问题，按奥卡姆剃刀不引入。

## v0.6.0（2026-09-07）

**触发**：用户报告实际执行中 demand 角色的指令没有被严格遵循（六维诊断记录、来源标注、方案雏形逐条询问等机械项被跳过，虽然语感贴近 demand 角色）。根因诊断：长角色文件里，叙事性内容（identity/character/判断框架的语感）比结构化强制字段（CRITICAL 清单/报告契约字段列表）更容易被"内化成语气"而不是"逐项对照执行"——原派发协议只把角色文件路径塞进 brief，靠子 agent 自觉阅读，机械性契约（尤其是需要精确对照的清单类内容）在这种"路径引用 + 自由阅读"模式下遵循度不稳定。

**用户提出的方向**：定义的 role 也要有一个对应的 skill，派发任务等价于给 agent 派发指定 skill 执行，skill 是 agent 标准协议，遵循度会更好。

**澄清过程**：最初讨论一度偏向"role 和 skill 是两份文件需要双轨同步"或"迁移到 `.claude/skills/` 目录"，均被用户纠正——role 文件本身就是 skill 定义，是同一份产物，不是两层概念；"skill" 是协议概念（agent 的标准协议单元），不是 Claude Code 的 `.claude/skills/` 文件系统机制；框架必须保持宿主无关，不能因为这次改动变成 Claude Code 专属。

**最终方案**：
1. **概念澄清**（`principles/meta/agent-design-protocol.md`）：新增"role = skill：协议等价性"章节，明确 role 文件本身就是 skill，"派发角色"和"加载 skill"协议语义等价
2. **派发机制升级**（`workflow-pb.md` + `SKILL.md`）：将「Brief 构建规则」从"传递角色文件路径，子 agent 自行决定要不要读"改为"主 agent 派发前先读出角色文件全文，将全文内容显性注入 brief"——用"内容前置注入"替代"路径引用+自觉阅读"，提高机械项遵循度
3. **物理结构不变**：不新建 `.claude/skills/<role>/` 目录，不产出额外文件；`roles/<role>/<role>.md` + `memory.md` + `data/` 三级记录结构原样保留

**验证策略**：先只在 demand 角色的派发路径上验证全文注入机制的效果，下次实际派发 demand 时观察遵循度是否改善，再决定是否推广到其余 8 个角色（prd/architect/planner/pr-planner/dev/verifier/progress-observer/retrospective）。这是刻意的小范围验证，不是一次性全量改动。

**具体改动**：
- `principles/meta/agent-design-protocol.md` 新增"role = skill"章节
- `roles/workflow-pb/workflow-pb.md` 新增「派发执行角色时的 brief 构建」一节（在"调度指南"下）
- `.claude/skills/workflow-pb/SKILL.md` 同步修改「§ Brief 构建规则」，版本号补齐至 v0.6.0（此前落后于完整规范文件，遗留自 v0.4.0/v0.5.0 未同步）
- 理解记录留痕：`roles/demand/data/demand-skill-migration-understanding.md`

## v0.5.0（2026-09-06）

**触发**：用户提出优化方向——"planner 拆分 pr 之后必须明确落盘，写清楚 depends_on 和依赖；后续派发执行者必须显式要求多子 agent 执行；每个 agent 独立完成一个 pr"。研究确认这三条在 v0.4.0 文本里已是显式要求，不是缺失机制；真实问题是 `docs/iterations/0005-pr-concurrent-execution/verification-report-stage6.md` 独立验证发现的文本歧义：v0.4.0 允许两种互相矛盾的读法，且协议自 v0.2.0 引入以来从未在真实多 PR 场景里被验证过执行结果。用户采用验证报告"下一迭代候选"给出的方案 B：应用验证报告的具体文字修复，并新增阶段 6 强制检查项。

**根因**：verification-report-stage6.md 逐条列出 4 个具体歧义点（详见该报告"下一迭代候选"段落）：
1. 「阶段 5」步骤 2 的"立即并发派发"没有封顶指令，真正带"取前 N 个"封顶算法的句子只出现在补位场景（原 `:220`），首批派发和补位派发用了两套不字面绑定的规则。
2. 验收标准"没有排队 PR 时槛位空置不强行派发"这一具体分支行为，协议原文没有一句话正面陈述。
3. 全文搜索找不到一句话正面禁止对失败/阻塞 PR 执行 worktree/branch 清理。
4. `累计成功解锁次数` 字段名暗示只在成功时累加，但实际规则是成功和失败/阻塞判定都累加，名实不符。
5. 本迭代自身阶段 5 只规划执行了 1 个 PR，因此"至少 2 个 PR worktree 时间窗口重叠"这类真实并发证据从未在交付中出现过——demand.md 里"协议文字从未被真实调度执行过一次"的风险原样成立。

**具体改动**：
- 「阶段 5」步骤 2 改为"按当前有效上限取前 N 个立即并发派发"，首批派发和补位派发共用同一条封顶规则；补一句"没有已解锁排队 PR 时，槛位空置，不因此放宽解锁条件"
- 「阶段 5」步骤 4 补一句"主 agent 不得对失败/阻塞 PR 执行 `git worktree remove`、`git branch -d` 或等价清理操作"
- 「并发槛位算法」`累计成功解锁次数` 改名为 `累计槛位释放次数`，并补充说明为何不含"成功"二字；`status.md` 初始化字段清单同步改名
- 「验证目标（阶段 6 独立验证读）」新增「并发调度真实执行证据（下一个多 PR 迭代强制核查）」子章节：触发条件为某迭代 `prs/` 产出 ≥2 个 PR 且依赖图有真实并发分支；强制核查 worktree 时间窗口重叠/并发配置区块真实初始化更新/爬升公式真实触发三项，均需文件证据，不接受"协议文本正确"代替
- 未新增角色、未新增文档产物（方案 C"新增派发计划文件"未采纳，见下）
- 同步更新 `.claude/skills/workflow-pb/SKILL.md`（v1.7.0 → v1.8.0）

**未采纳的方案**：
- 方案 A（仅做本次列出的 4 处文字修复，不加阶段 6 强制检查项）——用户未选择，理由是文字修复不能防止"下一次仍然是单 PR 迭代、协议依然没有被验证过"这一根本风险再次发生
- 方案 C（新增结构化"派发计划"产物文件，把依赖图渲染成显式清单供主 agent 消费）——评估为过度设计：v0.4.0 已有 `depends_on` 字段和依赖图构建步骤，新增产物文件不解决任何已确认的缺口，只是把已有信息换个格式重复存一份

## v0.4.0（2026-09-05）

**触发**：迭代 `0005-pr-concurrent-execution`——用户在实际执行中发现 PR 被串行执行，追溯发现 v0.2.0 引入的"依赖解锁式并发调度"这套协议文字，从未被真实调度执行过一次，只停留在纲要性描述层面，缺少可执行的具体细节。

**根因**：v0.2.0/v0.2.1 只写了调度的"原则"（无依赖或依赖已合并即并发派发），没有写"技术手段"（怎么发起并发调用）、"槛位算法"（并发数从哪来、怎么爬升、上限是多少）、"状态记录字段"（`status.md` 怎么记录槛位占用和现场保留）、"核实项"（怎么核实失败/阻塞 PR 的现场是否还在）——这些执行细节的缺失，导致主 agent 在阶段 5 实际派发时退化成逐个顺序调用，协议文字停留在纸面。

**具体改动**：
- 「阶段 5」章节补充并发派发的技术手段："主 agent 在同一轮 assistant 响应中连续发起多个 `Agent()` 工具调用"，替换掉此前对"协议从未被真实调度执行"这一问题现状的模糊表述
- 「阶段 5」章节补充并发槛位算法：起始并发数默认 3（从 `status.md` 读取）、爬升公式 `当前有效上限 = min(起始并发数 + 累计成功解锁次数 × 起始并发数, 硬上限)`、硬上限公式 `硬上限 = 2 × 起始并发数 - 1`
- 「调度指南 → 启动工作流」新增第 4 步：进入阶段 4→5 时须在 `status.md` 初始化 `## 并发配置（阶段 5）` 区块，字段为起始并发数/硬上限/当前有效上限/累计成功解锁次数/已派发总数
- 「状态追踪协议 → status.md 格式」的"PR 实现子状态"表新增"槛位状态"列（占用/排队(依赖未满足)/排队(等待槛位)/已释放），"状态"列新增 `❌失败(现场保留)`/`⏸阻塞(现场保留)` 两个专属取值，"worktree 分支"列新增 `(保留)`/`(已清理)` 标注约定
- 「可观测性」章节新增核实项：每次生成 `progress.md` 时，对失败/阻塞 PR 核实 worktree 和分支是否仍存在于磁盘（`git worktree list` + `git branch` 交叉核对），不一致记入"发现的不一致"
- 未改变「合并进主分支才算解锁」「PR 间文件范围无重叠」两条既有规则的适用范围，未引入新增语义耦合检测逻辑
- 同步更新 `.claude/skills/workflow-pb/SKILL.md`（v1.6.0 → v1.7.0）

## v0.3.0（2026-09-03）

**触发**：用户明确要求"需求实现全过程都是明确的实施与还原，变更都需要发起新迭代来完成"——即本迭代一旦通过阶段1产出 `demand.md`，执行过程中不应再被"发现需求问题"打断去回退修正，而是记录下来留给用户决定是否开新迭代。

**根因**：v0.2.1 的「阶段回退」表是逐行硬编码的"发现问题→回退上游阶段修正"模式（如"阶段2发现demand.md矛盾→回退阶段1重新收敛"），这与用户想要的"确定性还原"执行模型冲突——回退意味着本迭代中途被需求变更打断，需求实现路径不再是对已落盘 demand.md 的忠实还原。

**决策过程**：与用户多轮讨论收敛，关键决策点：
- 最初提案是新增强制性回退规则（demand.md 只能由 demand 角色修改，任意阶段发现问题都回退阶段1）——用户否决："这样改太重了，我不需要这么强制"
- 用户提出替代方案：不回退纠正，只"搭置记录"，本迭代按既定需求执行完，问题留给verifier交付报告，需要时再开新迭代处理
- 关键判断标准的确立：用户明确"发现更好的实现方式、发现问题都应该直接解决"，只有"更改需求"才需要开新迭代——这把判断标准从"哪个阶段发现的"改成了"解决这个问题是否要改变demand.md的结论"
- 记录归属：用户明确"执行者直接写，主agent的作用就是分发、调度、验证，主agent不干活"——搭置记录由发现问题的执行角色直接写入，不经过主agent转达

**具体改动**：
- 「阶段回退」章节从逐行硬编码表改为统一判断标准：解决问题是否要改demand.md第二段结论？否→当前阶段直接解决；是→执行角色直接写入 `deferred-demand-changes.md`，不回退不暂停，继续按现有demand.md推进
- 保留唯一硬停例外：`pr-planner` 报告依赖图有环（结构性错误，不是需求问题）
- 新增文档路径 `docs/iterations/{迭代ID}/deferred-demand-changes.md`，格式为可追加的需求变更/错误记录条目
- 阶段1新增硬性前置声明：无论迭代规模大小都不可跳过
- 阶段6验证目标新增：主 agent 若发现 `deferred-demand-changes.md` 存在，必须把路径显式塞进委托，要求 verifier 原文摘录内容进验证报告（verifier 自身边界是"只读委托指定的路径"，不会自己扫描目录），供用户判断是否开新迭代；verifier 不对搭置内容做二次判断，只透传
- 同步更新 `.claude/skills/workflow-pb/SKILL.md`（v1.1.0 → v1.2.0）：新增两条CRITICAL、Tools边界、Workflow步骤说明、Safety条目

## v0.2.0（2026-09-02）

**触发**：`docs/iterations/0004-model-dispatch` 迭代复盘（`project-retrospective.md` P2 条目）+ 用户在实际执行中发现 PR 被串行执行，与设计初衷（PR 解耦、可并行开发）不符。

**根因**：
1. 全局 `tasks.md`（原阶段 4「任务拆解」产出）在还没有真实 PR 文件边界时就要判断任务依赖，`tasks.md` 的"关键路径"章节把"最小风险的顺序偏好"误判成"技术依赖"，导致任务被串成一条链。原阶段 5「提交规划」的 commit-planner 只做机械分组（按 tasks.md 的顺序投影），没有独立判断真实依赖的能力和输入（不读代码库）。
2. `commit-planner.md` 明确写"主 agent 按报告中的文件列表顺序逐一 dispatch dev"——调度语义本身写死了串行，即使输入支持并行也会串行执行。
3. `workflow-pb.md` 和 `workflow-scm.md` 两个独立文件重复定义同一套 worktree 隔离和 PR 文件前置规则，违反权责分离原则（协调者只定义一次契约）。

**决策过程**：与用户多轮讨论收敛，关键决策点：
- 是否新增角色做"执行方案反射"——用户否决拆成两个角色（commit-planner 做分组 + execution-planner 做排期），理由"这个事情不需要做两次"，合并为一个角色 `pr-planner`
- 是否保留全局 tasks.md——用户指出"目前全局的 tasks.md 其实没什么意义，实际执行才有 tasks 一说"，改为每个 PR 反射产生后，任务拆解移入实现阶段、逐 PR 在子 agent 内完成
- workflow-scm 是否保留独立文件——用户明确要求并入 workflow-pb，"流程统一由 workflow-pb 管理"，并要求"问题先简化，如果有必要再新增 role"（结果：不新增额外角色，只新增 pr-planner 一个）

**具体改动**：
- 阶段从 7 个减到 6 个：原「任务拆解」+「提交规划」合并为「PR 规划」（阶段 4，pr-planner 执行，直接从 architecture.md+prd/*.md+代码库现状反射 PR 边界，不经过全局任务图）；原「后端实现」改为「PR 实现」（阶段 5），任务拆解变成该阶段内部、逐 PR 在子 agent 中执行的步骤（由 planner 承担，输入范围收窄为单个 PR）
- `roles/workflow-scm/` 整个删除，其定义的不变量（worktree 隔离、PR 文件前置）、PR 文件格式规范、验证目标全部并入本文件
