# 案例：status.md 状态协议设计缺口 + 阶段出口未覆盖提交快照

**记录日期**: 2026-09-02
**来源**：0004-model-dispatch 迭代复盘，原记录于 `roles/retrospective/data/retro-2026-09-02-model-dispatch.md`（2026-09-02 归属重整时移入本文件，理由见 `roles/retrospective/data/retrospective-changelog.md` v0.3.0）

## 案例 1：主 agent 回读与独立验证证据混用

**现象**：`status.md` 的阶段 1～5 标记为已验证，但没有 `clarifications/verify-*.md` 独立验证报告。

**根因**：状态字段没有区分"主 agent 回读验收"与 workflow-pb 独立验证阶段的证据。workflow-pb 已定义独立验证和验证报告路径，但 `status.md` 的字段设计没有把这两种不同强度的"验证"分开表达。

**候选原则**（暂未升级进 workflow-pb.md 正文）：没有逐项独立验证证据（`clarifications/verify-*.md`）时，`status.md` 只能记录为"主 agent 已验收"，不能标记为"独立验证通过"——两者证据强度不同，字段要能区分。

## 案例 2：规划产物没有形成完整提交闭环

**现象**：需求、规格、架构、任务和状态文件仍未进入 git 跟踪；规划提交只包含 PR 文件。

**根因**：阶段出口没有核对前置产物是否组成可恢复提交快照，只关注了当前阶段自己的产出物是否齐全。

**候选原则**（暂未升级）：规划阶段结束时，先确认全部阶段产物（demand/prd/architecture/prs）形成可恢复的 git 快照，再进入后续实现或交接——避免会话中断、worktree 切换时规划上下文丢失。

## 案例 3：多阶段重复固化协议边界（好做法）

**做了什么**：需求、PRD、架构和任务均明确排除配置加载器、ACP adapter、CLI 私有参数、常驻服务、队列、缓存、数据库及具体运行时实现，边界在每个阶段的交接处重复出现。

**为什么有效**：边界在交接处重复出现，降低了协议被下游误写成具体技术组件的风险——单处声明容易在传递中丢失，多处重复固化形成校验冗余。

**候选原则**（暂未升级）：跨阶段传递的"不做什么"边界，在每个阶段产物里都显式重申一次，不依赖"上游说过了"。
