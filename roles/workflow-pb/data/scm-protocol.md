# 提交管理与工作区隔离协议（SCM Protocol）

**版本**: 1.0.0（对应 workflow-pb v0.12.0）
**创建日期**: 2026-09-15
**来源**: 从 `workflow-pb.md` §提交管理约束拆分独立

---

## 一句话职责

定义 workflow-pb 的 git worktree 隔离规则、分支命名约定、跨工作区写入禁止、角色定义来源等提交管理基础设施协议。

---

## 提交管理约束

以下约束在每次使用本工作流的迭代中强制生效，每条措辞明确，可被客观判断是否违反。

### 规则 A：PR worktree 隔离

从阶段 4（PR 规划）完成之后，任何代码变更必须在独立 **PR** worktree 分支上进行，不得直接在主分支（main/master）或当前迭代的迭代分支上提交。

判断方式：每次提交所在分支不得为 `main`/`master`，也不得为当前迭代的迭代分支本身；所有变更必须通过 PR 合并进当前迭代的迭代分支。

### 规则 B：PR 文件前置

每个 **PR worktree** 变更必须对应一个 `prs/pr-{NNN-描述}.md` 文件（按 `formats.md` §PR 文件格式规范），merge 前该文件须存在。

判断方式：merge 操作执行前，对应的 PR 文件在 `docs/iterations/{迭代ID}/prs/` 目录中可读取。

### 规则 C：会话工作区隔离

会话可在项目内任意位置启动（含仓库主工作区）——启动位置不构成合规判据。开工时解析并以绝对地址声明其迭代工作区，此后写入与 git 操作按该地址寻址（见规则 D/H）。工作区不存在时由会话自行建立，建立成功即继续推进（不等候、不请示）。会话工作区 = 迭代工作区（每迭代一个），检出 `iteration/{迭代ID}` 并在阶段 1~6 期间保持不切换。`git worktree` 是唯一规范化形态；`git clone` 仅作"无法共享同一 `.git`"（跨机器/跨用户/无写权限）时的兜底声明，本协议不为其定义流程或隔离保证。

仓库主工作区不作为任何迭代的会话工作区；同一会话参续两个迭代须为第二个建立独立工作区，不得在上一迭代工作区里直接开下一迭代。

会话工作区是父层，阶段 5 的 PR worktree 是其下短生命周期层（base 为迭代分支）；PR worktree 不得充当会话工作区——不得在其内执行阶段 1~4 工作，也不得在 PR 结束后长驻。

落点与命名：
- 会话 / 迭代工作区：`<仓库主工作区>/.pb-agents/worktrees/{迭代ID}`
- PR worktree：`<会话工作区>/.pb-agents/worktrees/{迭代编号}-pr-{NNN}-{slug}`

判断方式：`git -C <工作区地址> branch --show-current` 输出 `iteration/{迭代ID}`，且 `git worktree list` 含该地址，两者同时成立方为合规；任一不成立而会话仍在推进即违反。

### 规则 D：启动与寻址契约

会话开工前确定其工作区绝对地址（不读取会话当前工作目录、不使用启动目录作输入）：

1. **仓库主工作区** = `git rev-parse --path-format=absolute --git-common-dir` 输出的父目录（在同一仓库的任意位置求值结果相同）
2. **工作区地址** = `<仓库主工作区>/.pb-agents/worktrees/{迭代ID}`
3. **显式覆盖**：派发简报携带的「工作区地址」字段优先于上步默认推导
4. **建立（仅当地址不存在）**：`git -C <仓库主工作区> worktree add .pb-agents/worktrees/{迭代ID} -b iteration/{迭代ID} main`，建立成功后直接继续推进
5. **建立成功依据**：`git worktree list` 含该地址，且 `git -C <该地址> branch --show-current` 输出 `iteration/{迭代ID}`

**硬停面**：仅当「本会话工作区无法确定或无法创建」（第 1 步无法确定，或第 4 步失败）时硬停——发现即停（不进入任何阶段、不产生任何写入含 status.md/history.md），输出下列形态：

```text
【本会话工作区无法确定或无法创建】
触发原因：<无法确定仓库主工作区 / 无法创建工作区：git 报告的错误原文>
当前状态：<已解析到的候选地址，或"未解析出候选地址">；当前检出：<分支名 或 "无（游离 HEAD）">
未完成事项：本会话工作区未就绪——未进入任何阶段，未产生任何写入。
```

硬停不复用 `⛔ 需要你的决策` 暂停格式（那是用户决策点的专用形态）。工作区就绪性硬停与「流程结构错误中止」（见 `workflow-pb.md` §阶段回退）、用户决策点暂停是三类并列机制。

约束主体：主 agent 会话（一次迭代校验一次），不是每次角色派发；阶段 5 的子 agent 以其简报给定的 PR worktree 地址为准。

判断方式：任取一次会话执行记录，核对 ① 地址可被第三者按上列链复算；② 该会话写入目标均位于该地址之下（`git -C` 形态）；③ 若地址不存在而会话未建立即继续推进、或已建立而无第 5 步两条依据，即违反。

### 规则 E：分支命名

会话创建的所有分支名必须含该迭代的编号（`{迭代编号}`）。迭代分支本身为 `iteration/{迭代ID}`（含完整迭代 ID）；阶段 5 的 PR worktree 分支为 `feat/{迭代编号}-pr-{NNN}-{slug}`。本条款只约束新创建的分支，不追溯已完成迭代的既有分支。

判断方式：`git branch --list` 逐条核对分支名是否包含该迭代的编号（字符串包含即可），同名分支被两个会话争用即违反。

### 规则 F：跨工作区写入禁止

会话的写操作（文件写入、`git -C`、`--work-tree`）必须落在本会话工作区内；以绝对路径写入非本会话工作区（另一会话的迭代工作区、他人PR worktree、仓库主工作区）不得发生。必须恢复他人工作区内容时，先取备份、后操作，两步均须在执行记录中可查。

worktree 是目录分离而非访问控制；本协议不引入 hook、访问控制或路径守卫，跨工作区写入**不可能被 git 强制阻止，只能事后核查判定**（见「隔离边界声明」）。

例外（闭集，仅两项）：① 会话工作区的创建动作（必然发生在目标工作区之外）；② 收口三步及其前置游离动作（固定在仓库主工作区执行，见 `workflow-pb.md` §迭代分支合并进 main）。

判断方式：取一次会话执行记录（会话日志/`history.md`/提交diff/`progress.md`均可），逐条比对"写入动作→目标路径"是否位于本会话工作区内（阶段 5 子 agent 以其简报给定的 PR worktree 地址为准）；出现区外路径时，须有位于其之前的备份动作，否则违反。

### 规则 G：暂停 / 终止迭代的现场保留

暂停或终止的迭代，其会话工作区与分支原样保留、不被自动清理；清理权仅归其归属会话或用户。本条款的判定对象是会话/迭代工作区与迭代分支，与判定对象为 PR worktree 的既有「失败/阻塞 PR 现场保留」条款（`workflow-pb.md` §阶段 5 第 4 点、`formats.md` §status.md 的 `❌失败(现场保留)`/`⏸阻塞(现场保留)` 定义）并列、不互相替代。

判断方式：对照 `git worktree list` 与 `git branch --list 'iteration/*'`，核对某暂停/终止迭代的工作区目录与分支在他人提交/分支切换/清理动作前后是否仍然存在；任一项消失即违反。

### 规则 H：显式寻址纪律

会话的一切文件写入以工作区地址下的绝对路径进行；一切 git 写操作使用 `git -C <工作区地址>` 形态，不依赖 cwd。该寻址不阻止跨工作区写入（不可能被 git 强制，见规则 F），只能事后核查判定。

判断方式：取一次执行记录逐条核对写入目标是否为绝对路径且位于声明地址之下、git 写操作是否带 `-C <地址>`；出现依赖 cwd 的裸 git 写命令即违反。

### 协议产物：工作区间与生效规范（`docs/worktrees/README.md`）

本项目的工作区间与生效规范由一份声明式协议产物承载——`<项目根>/docs/worktrees/README.md`，被 git 跟踪、随 `git worktree add` 检出即得（新工作区零安装动作可读；不改 `.gitignore`、不扩展规则 F 闭集例外）。产物必须覆盖五类信息（模板顺序即此序）：① 本项目工作区间定义（会话/迭代工作区落点、PR worktree 落点与层级、工作区范围）；② 本项目生效的规范与其版本（规范文件路径+版本号）；③ 寻址纪律引用（显式寻址、地址声明的三层落点、越界判定是事后核查）；④ 落点语义澄清的一行区分句；⑤ 声明不含任何脚本/钩子/守卫。

**地址声明的三层分工**：源 = 本产物（项目级静态声明：工作区间规则+生效规范版本）；投影 1 = `status.md` 的 `**工作区地址**` 字段（迭代级）；投影 2 = 派发简报的 `工作区地址` 字段（派发级，阶段 5 为该 PR worktree 地址）。三层不一致时以源为准并登记差异（载体不限，须可被第三者读到"以源为准"的处置）。硬约束：任一次运行的动态地址只落后两者，不得写进本产物（否则每次会话都产生一次仓库改动，与规则 A/规则 B 相撞）。

**落点语义（三者互不替代）**：`docs/worktrees/` 是协议产物的文档位置（被跟踪，不承载任何运行态工作区）；`.pb-agents/worktrees/` 是会话/PR工作区池（运行态，被 `.gitignore` 忽略）；`docs/iterations/{迭代ID}/` 是迭代产物（每迭代一份，不承载跨迭代的协议声明）。任何会话/PR worktree 不得建在 `docs/worktrees/` 下。

本产物是规范的实例化投影——规范性陈述均以引用规范条款的形态出现，不自行创立规范中没有的约束。

判断方式：① 读该产物逐类核对五类信息是否覆盖、是否出现脚本/钩子/守卫/可复制命令块；② 在三处（产物/`status.md`/一次派发简报）比对同一事实是否一致、产物内容是否不随会话变化（两个不同会话的检出中逐字节相同）；③ 把产物中每条规范性陈述回指规范条款，出现无对应条款的约束即违反；④ `git ls-files --error-unmatch docs/worktrees/README.md` 成功、且 `git worktree list` 无 `docs/worktrees/` 前缀项、`ls docs/worktrees` 无工作区目录。

### 约束主体

**对人（使用者）**：本规范不设任何前置——不要求进入某目录、执行任何命令、预先创建工作区、重开会话。

**对会话（主agent与派发的执行角色）**：会话承担三项纪律：① 声明其迭代工作区地址；② 一切写入与git写操作按该地址显式寻址；③ 需恢复他人工作区内容时,先取备份、后操作。三项违反由事后核查判定（见规则F与「隔离边界声明」），不被阻止。

判断方式：核对「对人」段四项零要求逐项存在、无相反要求；「对会话」段三项纪律逐项存在；违反判定方式指向事后核查而非阻止。

### 隔离边界声明（隔离到什么层为止）

**覆盖（被git worktree隔离的共享状态）**：工作树（每个工作区自己的目录）／ 索引（`.git/worktrees/<id>/index`）／ HEAD（各工作区各自检出）。

**不覆盖**：
- 仓库级 refs（含stash与分支命名空间）：不得依赖stash跨会话传递状态；分支名必须自带迭代编号（见规则E），不得把分支命名空间当跨会话通道；不得依据 `git branch --merged` 之类输出直接判定归属——同点分支会被误判为"已合并"（0017实测先例）。
- 对象库（objects）：共享的，不得做破坏性操作（`gc --prune`、`fsck --lost-found`等）。
- config / hooks / remotes：不得通过修改共享config/hooks/remotes解决会话级问题；本协议不引入hook参与强制。
- **cwd（会话的当前工作目录）**：cwd从来不是隔离的一部分——隔离覆盖的是工作树/索引/HEAD三层；会话在哪个目录启动与其产物落在哪个工作区无关（归属由声明的地址承担，见规则C/规则D）。

**同一分支不能在两处同时检出**是git硬约束：会话工作区永不checkout `main`，`main` 上的合并动作只能在仓库主工作区发生（见 `workflow-pb.md` §迭代分支合并进main）。

**非git共享资源（不被隔离）**：

| 资源 | 声明 | 约束 |
|---|---|---|
| 默认端口（真实服务默认7788，可经环境变量覆盖） | 不被隔离 | 真实服务不得并发占用默认端口。判断方式：并发运行真实服务的两个会话，核对监听端口必须不同，或核对规范是否要求并发场景显式指定非默认端口。本约束不要求修改默认端口值；测试面自带的随机端口不受约束。 |
| CPU / 负载 | 不被隔离 | 受负载影响的偶发失败不得当回归依据。判断方式：检查该失败记录是否含"同一代码在安静环境下重跑"的结果——只凭单次失败下结论即违反。 |
| 临时目录（`/tmp`） | 不被隔离 | 临时产物不得作为最终事实载体；本协议不新增任何清理动作。 |
| 进程内作业注册表 | 不跨会话、会过期 | 不得把"作业列表为空"读成"作业丢失"；判断另一会话的作业状态以git落盘事实（commit/分支/产物文件）为准。 |

**已知代价**：
- 隔离层不含refs与对象库，因此会话内不会自动发现与他人改动的冲突——冲突后移到收口合并期处置；本协议不定义冲突的自动解决流程，冲突发生时报错上报。
- 跨工作区写入不可能被git强制（worktree是目录分离而非访问控制）⇒ 越界不会被阻止，只能在事后核查中发现。"未被阻止"不等于"条款作废"——越界写入仍是规则F判定为违规的行为。核查判据：① 取该会话 `status.md` 的 `**工作区地址**` 字段；② 取该次派发简报的 `工作区地址` 字段；③ 取该会话执行记录中每条写入动作的目标路径；④ 逐条判"是否位于声明地址之下"——区外路径若其之前存在备份动作则不判违反，否则判违反。

判断方式：按上列四类（覆盖/不覆盖/非git共享资源/已知代价）逐项核对其各自内嵌的判据（见各条与表格"约束"列），未参与讨论者对照一次执行记录与一次派发简报即可判定；任一项无法判定或与结论不符即本节结论不成立。

## 角色定义来源与部署

**真源规则**：角色定义的读取来源是被git追踪的内容。以角色文件是否被跟踪判定：`git ls-files --error-unmatch <角色定义根>/<role>/<role>.md` 成功者即为真源。
- 上游（本仓库，agents源码仓）：`{角色定义根}` = `roles/`。角色定义随每次检出即得，新工作区零安装动作即可读到完整角色定义。
- 下游（业务项目）：`{角色定义根}` = `.pb-agents/roles/`（由 `tools/install-pb-agents.sh` 分发；该步骤是可选的分发动作，不是本协议的运行前提）。

**解析规则**：每次会话在Step 0解析一次、会话内复用——先判真源（被跟踪的 `roles/` 可用则用它），否则回退 `.pb-agents/roles/`；解析结果写入每次brief的「角色定义」字段。上下游共用同一份规范与同一份skill，差别只在解析结果。

**"零动作"的准确含义**：该承诺只覆盖"角色定义真源随检出即得"的场景（本仓库）；下游仍可有"先分发角色文件"这一步，但该步骤不算本协议的运行前提，未执行它不构成停止推进的理由。

**只读约束**：角色定义在执行期只读（真源与分发副本皆然）；角色的 `data/`、`memory.md` 不随分发部署。

判断方式：在任一工作区内按本节解析出 `{角色定义根}`，`git ls-files --error-unmatch <根>/<role>/<role>.md` 必须成功；某次派发前若该判定失败且未回退到下游副本即违反。

## 约束生效范围

上述约束仅从下一个使用本工作流的迭代起生效，不追溯已完成迭代。
