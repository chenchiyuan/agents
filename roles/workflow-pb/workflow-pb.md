# workflow-pb

**版本**: 0.1.0
**创建日期**: 2026-09-02
**变更历史**: 见 `data/workflow-pb-changelog.md`

---

**CRITICAL: 本文件只定义规范，不执行工作。所有执行判断由主 agent 和执行角色完成。**

**CRITICAL: 修改本文件不得侵入任何执行角色文件。角色文件只定义能力，工作流文件定义契约。**

---

## 一句话职责

定义 pb 产品研发工作流的完整规范，让主 agent 知道怎么调度，让执行角色知道读什么、写什么、交付什么。

---

## 阶段定义

工作流包含 6 个阶段。每个阶段有独立的验证步骤，验证通过才算该阶段完成。

| # | 阶段 | 职责描述 | 输入 | 输出 | 推进条件 |
|---|---|---|---|---|---|
| 1 | 需求收敛 | 通过结构化对话消除模糊、界定边界，产出有澄清依据的需求合同 | 用户原始表述 / 迭代目标 / 草稿文本 | `demand.md`（两段：澄清依据 + 带最小边界的结论） | 两段均有内容；所有 `model_inferred` 结论经用户确认；无活跃冲突 |
| 2 | 功能规格 | 将需求合同原子化为可独立验证的功能卡，只做产品维度，不做架构决策 | `demand.md` | `prd.md`（报告级索引）+ `prd/*.md`（每功能点独立卡，含验收标准和边界） | 所有功能点有独立卡片；无 demand.md 外新增功能；架构待定项已标注 `[架构待填]` |
| 3 | 技术架构 | 在现有架构上演进，补全功能卡的架构维度，产出技术方案 | `prd/*.md` + 现有代码库 / 架构文档 | `architecture.md` + `prd/*.md` 中 `[架构待填]` 项补全 | L1 决策经用户确认；所有功能卡有技术路径；无架构内部冲突 |
| 4 | 任务拆解 | 将技术方案转为有向无环任务图，每条任务有可追溯验收标准 | `architecture.md` + `prd/*.md` | `tasks.md`（DAG 任务图，每条任务含前置依赖、验收标准、优先级） | 依赖图无环；所有验收标准可追溯到输入原文或直接推导；粒度 1-2 天 |
| 5 | 后端实现 | 按任务简报执行编码，产出最小实现，不做简报外的决策 | 单个任务简报（来自 `tasks.md`） | 代码 + 通过验证标准的测试 | 简报要求的验证标准全部通过；无简报外改动 |
| 6 | 独立验证 | 不接收执行过程上下文，独立评判任意阶段产物的质量 | 待验证产物（路径由主 agent 指定） | `clarifications/verify-{timestamp}.md`（pass / fail / partial / blocked + 逐项证据） | 每项有明确结论和文件证据；无"基本通过"模糊表述 |

> 阶段 6（独立验证）可在任意阶段结束后触发，不局限于最终产物。推进条件中"已验证"指该阶段产物经过阶段 6 且结论为 pass。

## 文档路径协议

所有阶段产物统一落在 `docs/iterations/{编号-迭代名}/`。

```
docs/iterations/{编号-迭代名}/
├── status.md           ← 工作流进度（由主 agent 维护）
├── demand.md           ← 阶段 1 产物
├── prd.md              ← 阶段 2 产物（索引）
├── prd/                ← 阶段 2 产物（功能卡）
│   └── {功能名}.md
├── architecture.md     ← 阶段 3 产物
├── tasks.md            ← 阶段 4 产物
└── clarifications/     ← 澄清记录 + 验证报告
    └── verify-{timestamp}.md
```

**`{编号-迭代名}` 由主 agent 在工作流启动时确定，并写入每个任务 brief。**

## 状态追踪协议（status.md）

`status.md` 由主 agent 在每次阶段状态变更时更新，是工作流唯一的进度视图。

### status.md 格式

```markdown
# 工作流进度

**工作流**: workflow-pb v{版本}
**迭代**: {编号-迭代名}
**当前阶段**: {阶段名}（阶段 {#}）
**状态**: {进行中 / 等待确认 / 已完成 / 已终止}

## 阶段状态

| # | 阶段 | 完成 | 已验证 | 备注 |
|---|---|---|---|---|
| 1 | 需求收敛 | ✅ | ✅ | |
| 2 | 功能规格 | ✅ | ⬜ | |
| 3 | 技术架构 | ⏸ | ⬜ | 2 个 L1 决策待确认 |
| 4 | 任务拆解 | ⬜ | ⬜ | |
| 5 | 后端实现 | ⬜ | ⬜ | |
| 6 | 独立验证 | — | — | 按需触发，不计入线性进度 |

## 待确认项

- [ ] {类型}：{描述}（见 {文档路径} §{章节}）

## 更新日志

- {日期}: {变更描述}
```

**状态符号**：`✅` 已完成 / `⏸` 进行中或阻塞 / `⬜` 未开始

### 主 agent 何时更新 status.md

- 工作流启动时：创建 `status.md`，所有阶段标记 `⬜`
- 每次派发执行角色前：将对应阶段标记为 `⏸`
- 每次阶段产物通过主 agent 验收后：标记 `✅`
- 每次独立验证（阶段 6）通过后：对应阶段"已验证"列标记 `✅`
- 每次出现待确认项：写入"待确认项"列表
- 每次用户确认后：勾选对应项，清空已解决的待确认项

## 调度指南（主 agent 读）

### 启动工作流

1. 确认迭代 ID（`{编号-迭代名}`）
2. 创建 `docs/iterations/{编号-迭代名}/status.md`，初始化阶段表
3. 从阶段 1（需求收敛）开始

### 阶段推进

每次推进前对照该阶段的"推进条件"逐项核查，全部满足才推进：
- 所有条件满足 → 更新 `status.md`，进入下一阶段
- 有条件未满足 → 回到执行角色补充，或视情况回退上游阶段

### 阶段回退

| 触发情况 | 回退目标 | 主 agent 动作 |
|---|---|---|
| 阶段 2 发现 demand.md 有矛盾或范围不清 | 阶段 1 | 附具体矛盾描述，重新派发需求收敛 |
| 阶段 3 发现功能与技术约束根本冲突 | 阶段 2 | 附具体冲突描述，调整功能卡 |
| 阶段 4 发现 architecture.md 信息不足 | 阶段 3 | 附缺失信息清单，补充架构方案 |
| 任意阶段发现上游产物有矛盾 | 产生矛盾的阶段 | 不在当前阶段自行修正上游产物 |

### 需要用户决策的情况

主 agent 遇到以下情况必须暂停并通知用户，不得自行推进：
- 产物中出现 `[model_inferred]` 标注项
- 架构方案中出现 L1 决策（不可逆的技术判断）
- 执行角色报告"阻塞"且主 agent 无法在不修改上游产物的情况下解决
- 阶段 1 执行角色反馈"根本没有问题要解决"

### 终止工作流

在 `status.md` 中将状态标记为"已终止"，写明终止原因。

## 角色读取指南（执行角色读）

你被派发时，brief 里会包含：
1. **工作流文件路径**：`roles/workflow-pb/workflow-pb.md`
2. **当前迭代 ID**：如 `0003-user-profile`
3. **当前阶段编号**：如 `阶段 2`

你的动作：
1. 读本文件"阶段定义"表，找到你负责的阶段行
2. **输入**：从"输入"列确定文档性质，路径 = `docs/iterations/{迭代ID}/` + 输入文档名
3. **输出**：从"输出"列确定文档性质，路径 = `docs/iterations/{迭代ID}/` + 输出文档名
4. **交付标准**："推进条件"列是你的完成定义
5. 读 `status.md` 了解当前进度和是否有待处理的上下文

**不要从自己的角色文件里找输入输出路径**——角色文件只定义能力，工作流定义契约。

## 原则

**工作流规范不定义执行细节**

本文件定义"做什么、交什么、满足什么标准"，不定义"怎么做"。执行细节由对应的执行角色文件定义。

**出口定义优先于流程顺序**

推进条件是每个阶段最重要的内容。顺序是结果，推进条件是原因。含糊的推进条件（"完成了就推进"）是未来返工的种子。

**不指定执行角色名**

本文件描述每个阶段的能力要求，不绑定具体的角色文件名。角色文件会迭代、会重命名，工作流的阶段职责应该稳定。

---

## 何时更新本文件

- 某个阶段的推进条件导致下游返工 → 收紧该阶段的推进条件
- 某个阶段的职责边界不清导致执行角色越界 → 在对应阶段的职责描述里明确排除项
- 发现遗漏了某类工作（如 review）→ 新增阶段，不改动现有阶段
- 不得因"方便执行角色"而在本文件里加入执行细节

变更历史写入 `data/workflow-pb-changelog.md`，保留旧版推进条件被修改的原因。
