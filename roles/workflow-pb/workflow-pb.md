# workflow-pb

**版本**: 0.11.0
**创建日期**: 2026-09-02
**变更历史**: 见 `data/workflow-pb-changelog.md`

---

**CRITICAL: 本文件只定义规范，不执行工作。所有执行判断由主 agent 和执行角色完成。**

**CRITICAL: 修改本文件不得侵入任何执行角色文件。角色文件只定义能力，工作流文件定义契约。**

**CRITICAL: 本文件是提交管理约束的唯一来源——不得再有独立的 workflow-scm 文件重复定义 worktree/PR 规则；发现重复定义视为耦合未解。**

## 一句话职责

定义 pb 产品研发工作流的完整规范（含从 PR 规划到代码合并的提交管理约束和并发调度契约），让主 agent 知道怎么调度、怎么并发，让执行角色知道读什么、写什么、交付什么。

## v0.7.0 变更说明（相对 v0.6.0）

**新增 history.md 记录协议**：新增独立于 `status.md` 的 `history.md` 记录产物（「历史记录协议」一节），按主 agent 派发、收到报告、调度决策三类事件的发起顺序逐条追加记录，与 `status.md` 并存、职责不同、格式互不侵入。`status.md` 头部新增 `history` 开关字段（默认开启），控制该文件是否被创建和维护。

**目的**：让复盘者/debug 者事后阅读 `history.md` 就能看懂"这次迭代派发了什么、收到了什么反馈、主 agent 基于什么做了什么调度决策"，不需要询问执行者或依赖会话记忆。

**不改变的部分**：`status.md` 现有格式与维护时机中除新增 `history` 字段行之外的任何部分；并发调度算法本身（起始并发数/爬升公式/硬上限不变）；任何执行角色文件（`roles/<role>/<role>.md`）本身的报告契约字段定义。

**验证方式**：本次迭代（`0007-workflow-history-log`）自身阶段 1~5 执行时使用的是发明本机制之前的旧协议，未真实开启过 `history` 字段，不产出可自证的 `history.md`——阶段 6 独立验证已确认这一点（`roles/verifier/data/verify-20260907-225754.md`，裸判定 4 条判定为 blocked：协议自诞生以来零次真实执行，无实例可查）。下一个走 workflow-pb 的迭代应将"生成并核查 history.md 是否满足 demand.md §5 的 4 条裸判定"列为该迭代阶段 6 的强制核查项，类比「并发调度真实执行证据」已有的先例模式。

## v0.8.0 变更说明（相对 v0.7.0）

**新增迭代分支层**：新增独立于 main 的中间分支层"迭代分支"（`iteration/{迭代ID}`），形成 `main ← 迭代分支 ← PR worktree 分支` 两层结构。demand 阶段完成后立即创建，PR 的 base 和合并目标改为迭代分支，阶段 5 解锁判据同步改为"合并进迭代分支"，迭代分支在阶段 6 独立验证 pass 后由主 agent 自动合并进 main。

**目的**：main 应始终只包含已完成、已验证的迭代产出；此前 PR 直接合并 main 意味着单个迭代未完成时其中间产出已落地 main，一旦迭代中途终止或需求有变，main 已被污染，难以整体回退。

**不改变的部分**：PR 文件七字段格式；阶段数量（仍为 6 个）；任何执行角色文件本身；并发槛位算法公式（起始并发数/爬升公式/硬上限不变，只是判据的检查对象从 main 变为迭代分支）。

**生效范围**：仅从下一个使用本工作流的迭代起生效，不追溯 0005/0007。

## v0.9.0 变更说明（相对 v0.8.0）

**新增会话工作区层与隔离边界声明**：把"会话"与"工作区"在文本层绑定起来——新增规则 C（会话工作区隔离：`git worktree` 为默认且唯一被规范化的会话工作区形态，每迭代一个、阶段 1~6 全程检出 `iteration/{迭代ID}`，落点 `<仓库主工作区>/.pb-agents/worktrees/{迭代ID}`；PR worktree 落在会话工作区内的子目录）、规则 D（启动契约：三条 git 原语判据 + 发现即停 + 硬停输出形态）、规则 E（分支命名必须含迭代编号）、规则 F（跨工作区写入禁止，含闭集例外两项）、规则 G（暂停 / 终止迭代的现场保留），并新增「隔离边界声明」（覆盖 / 不覆盖 / 非 git 共享资源 / 已知代价）与「角色定义来源与部署」（真源 = 被 git 追踪的内容，安装脚本降级为面向下游业务项目的可选分发手段）；规则 A / 规则 B 与阶段定义表的 worktree 术语限定为「PR worktree」；阶段 5 的 PR worktree 落点移到会话工作区内的子目录，收口三步改为固定 `git -C <仓库主工作区>` 形式并加第 3 步的前置游离动作。

**目的**：此前规范把会话的工作目录默认指向仓库主工作区、把角色定义读取来源固定在 `.pb-agents/roles/` 部署副本上——并行会话之间在工作目录 / 索引 / HEAD 三个层面互相踩踏（0017 实测），且新工作区必须先跑一次安装脚本才能读到角色定义。本次把会话绑定到自己的会话工作区、把角色定义来源改回随检出即得的被追踪内容，让并行会话互不干扰、让新工作区零安装动作即可开工。

**不改变的部分**：PR 文件七字段格式；阶段数量（仍为 6 个）与各阶段职责 / 输入 / 输出 / 推进条件；并发槛位算法（起始并发数 / 爬升公式 / 硬上限）；规则 A / 规则 B 的实质语义（代码变更仍须走 PR worktree、PR 文件仍须在 merge 前存在）；状态追踪协议与历史记录协议的格式；任何执行角色文件；`tools/install-pb-agents.sh` 与仓库根 `.gitignore`。

**生效范围**：仅从下一个使用本工作流的迭代起生效，不追溯已完成迭代，也不要求本迭代（0019）自身迁移。

## v0.11.0 变更说明（相对 v0.10.0）

**阶段 1（需求收敛）改为主 agent 内联执行**：把阶段 1 从"主 agent 派发 demand 子 agent 执行、demand 向主 agent 汇报确认结果"改为"主 agent 直接内联执行 demand 的判断框架，直接和用户对话"——不再走 `Agent()` 派发。demand 角色文件本身的判断框架（六维诊断、提案确认循环）不变，改变的只是承载它的执行架构。

**目的**：用户反馈阶段 1 的用户沟通"泛泛而谈"——子 agent 隔着主 agent 与用户对话，存在转达损耗（子 agent 收到的是转述的起点材料，不是用户原话）和反馈延迟（确认要先回报主 agent 再转给用户）。拿掉这层间接性，让判断框架直接面对用户；同时 demand.md 自身也做了呈现方式上的优化（批量提问、收敛前显式向用户确认，见 `roles/demand/data/demand-changelog.md` v0.4.0）。

**「派发即隔离执行」不变量的例外**：本变更是「§ 对外协议」核心不变量"派发即隔离执行"（该执行上下文运行期间主 agent 不能自己读完角色文件后"代入"该角色处理任务）在阶段 1 上的**显式例外**——阶段 1 不再有独立执行上下文，主 agent 自己代入 demand 判断框架直接执行。该不变量对阶段 2~6（prd/architect/pr-planner/planner/dev/verifier/progress-observer）**继续完整有效**，未被削弱。

**「全文注入 brief」机制对阶段 1 天然失效**：v0.6.0 引入的"派发前读出角色文件全文注入 brief"机制以"存在 brief 这个载体"为前提；阶段 1 没有派发动作，也就没有 brief。主 agent 内联执行时仍需完整读取 `roles/demand/demand.md` 全文来获得判断框架，只是不再需要"注入"这一动作——读取对象从"子 agent 的初始指令"变成"主 agent 自己的工作记忆"。

**不改变的部分**：阶段数量（仍为 6 个）；阶段 2~6 的派发机制（「派发执行角色时的 brief 构建」「§ Brief 构建规则」的适用范围与措辞不变）；demand.md 判断框架本身的实质内容（六维诊断维度、提案确认循环的判断标准）；「阶段回退」的判断标准（是否要改 demand.md 第二段结论）——只是现在主 agent 自己就是那个"发现问题"的执行者；PR 文件七字段格式；并发槛位算法；状态追踪协议与历史记录协议的格式。

**生效范围**：仅从下一个使用本工作流的迭代起生效，不追溯已完成迭代。

## v0.10.0 变更说明（相对 v0.9.0）

**入口绑定改为寻址绑定**：把 v0.9.0 的「会话必须在自己的会话工作区里启动」（以当前工作目录（cwd）为基准的启动门）换成「会话在开工时解析并以绝对地址声明其迭代工作区，此后一切写入与 git 写操作按该地址显式寻址」（地址锚定）；契约从散落在规则正文的 cwd 判据变成一份随检出即得的声明式协议产物 `docs/worktrees/README.md`（工作区间 + 生效规范）；硬停面收窄为「本会话工作区无法确定或无法创建」一处（输出三行事实陈述，不含命令块与指向人的动作要求）；「对人」的强制面归零（无目录要求 / 无前置命令 / 无 `cd` / 无重开会话）；检测改为挂执行现场（简报 `工作区地址` 字段 + `检测项` 一行）。

## 阶段定义

工作流包含 6 个阶段。每个阶段有独立的验证步骤，验证通过才算该阶段完成。

| # | 阶段 | 职责描述 | 输入 | 输出 | 推进条件 |
|---|---|---|---|---|---|
| 1 | 需求收敛（**主 agent 内联执行，不派发子 agent**，见「阶段 1~4 推进」） | 通过结构化对话消除模糊、界定边界，产出有澄清依据的需求合同 | 用户原始表述 / 迭代目标 / 草稿文本 | `demand.md`（两段：澄清依据 + 带最小边界的结论） | 两段均有内容；所有 `model_inferred` 结论经用户确认；无活跃冲突 |
| 2 | 功能规格 | 将需求合同原子化为可独立验证的功能卡，只做产品维度，不做架构决策 | `demand.md` | `prd.md`（报告级索引）+ `prd/*.md`（每功能点独立卡，含验收标准和边界） | 所有功能点有独立卡片；无 demand.md 外新增功能；架构待定项已标注 `[架构待填]` |
| 3 | 技术架构 | 在现有架构上演进，补全功能卡的架构维度，产出技术方案 | `prd/*.md` + 现有代码库 / 架构文档 | `architecture.md` + `prd/*.md` 中 `[架构待填]` 项补全 | L1 决策经用户确认；所有功能卡有技术路径；无架构内部冲突 |
| 4 | PR 规划 | 反射出可独立合并的提交单元划分及单元间真实依赖，从架构方案+代码库现状出发，不经过全局任务图这一中间环节 | `architecture.md` + `prd/*.md` + 代码库现状 | `prs/pr-{NNN-描述}.md`（七字段，见「PR 文件格式规范」） | 每个 PR 文件满足格式规范；`prd/*.md` 中每个功能点被某个 PR 引用；PR 间文件范围无重叠；依赖图无环 |
| 5 | PR 实现 | 逐 PR 在独立 **PR worktree** 分支、独立子 agent 中执行：先拆该 PR 内部的任务（子 agent 内部步骤，不产出全局任务图），再实现，产出最小实现 | 单个 `prs/pr-{NNN}.md` 文件 | `prs/pr-{NNN}-tasks.md`（该 PR 内部任务列表，供 dev 消费）+ 代码 + 通过验证标准的测试 | 该 PR 验收标准全部通过；无简报外改动；对应 PR 文件存在（合并前置） |
| 6 | 独立验证 | 不接收执行过程上下文，独立评判任意阶段产物的质量 | 待验证产物（路径由主 agent 指定） | `clarifications/verify-{timestamp}.md`（pass / fail / partial / blocked + 逐项证据） | 每项有明确结论和文件证据；无"基本通过"模糊表述 |

> 阶段 6（独立验证）可在任意阶段结束后触发，不局限于最终产物。推进条件中"已验证"指该阶段产物经过阶段 6 且结论为 pass。
>
> 阶段 5「PR 实现」内部的任务拆解由 `planner` 角色承担，但触发方式与 v0.1.0 不同：**不是一次性对全架构拆解，而是主 agent 逐 PR 派发、在该 PR 专属的子 agent 会话内完成**，输入范围收窄为单个 PR 文件（+ architecture.md/prd 作背景）。这样任务粒度天然被 PR 的真实文件边界约束，不会重复出现"把顺序偏好当依赖"的问题。

## 提交管理约束（原 workflow-scm 内容，并入本文件）

以下约束在每次使用本工作流的迭代中强制生效，每条措辞明确，可被客观判断是否违反。

### 规则 A：PR worktree 隔离

从阶段 4（PR 规划）完成之后，任何代码变更必须在独立 **PR** worktree 分支上进行，不得直接在主分支（main/master）或当前迭代的迭代分支上提交。

判断方式：每次提交所在分支不得为 `main`/`master`，也不得为当前迭代的迭代分支本身；所有变更必须通过 PR 合并进当前迭代的迭代分支。

### 规则 B：PR 文件前置

每个 **PR worktree** 变更必须对应一个 `prs/pr-{NNN-描述}.md` 文件（按下方「PR 文件格式规范」），merge 前该文件须存在。

判断方式：merge 操作执行前，对应的 PR 文件在 `docs/iterations/{迭代ID}/prs/` 目录中可读取。

### 规则 C：会话工作区隔离（v0.10.0 改写）

会话（主 agent 会话）可在**项目内任意位置启动**（含仓库主工作区）——启动位置不受约束，不构成合规判据。会话在开工时**解析并以绝对地址声明**其迭代工作区，此后一切写入与 git 写操作按该地址显式寻址（见规则 H）。**工作区不存在时由会话自行建立**，建立成功即继续推进（不等候、不请示）。会话工作区 = 该迭代的迭代工作区（本规范两词同指一个实体），**每迭代一个**，检出 `iteration/{迭代ID}` 并在阶段 1~6 期间保持在该分支上、不中途切到别的分支。`git worktree` 是本协议**默认且唯一**被规范化的会话工作区形态；`git clone` 仅在"无法共享同一 `.git`（跨机器 / 跨用户 / 无写权限）"时作为兜底形态**被声明**，本协议不为它定义任何流程，也不保证该场景的隔离。

**仓库主工作区不作为任何迭代的会话工作区。** 同一会话参与连续两个迭代时，必须为第二个迭代建立它自己的会话工作区，不得在上一迭代的工作区里直接开下一迭代。

会话 / 迭代工作区是**父层**，阶段 5 的 PR worktree 是它下面的**短生命周期层**（base 仍为当前迭代的迭代分支）；**PR worktree 不得被当作会话工作区使用**——不得在其内执行阶段 1~4 的工作，也不得在 PR 生命周期结束后继续充当长驻工作区。

落点与命名（唯一约定）：
- 会话 / 迭代工作区：`<仓库主工作区>/.pb-agents/worktrees/{迭代ID}`
- PR worktree：`<会话工作区>/.pb-agents/worktrees/{迭代编号}-pr-{NNN}-{slug}`

判断方式：以**地址**为对象、可从任意位置复核——`git -C <该迭代工作区地址> branch --show-current` 输出 `iteration/{迭代ID}`，且 `git worktree list` 的输出含该地址。两者同时成立即该工作区存在且形态合规；任一不成立而会话仍在推进即违反。

### 规则 D：启动与寻址契约（原「启动契约」改写，v0.10.0）

会话开工前确定其迭代工作区的**绝对地址**（下称工作区地址），并在此后的一切动作中按该地址寻址。解析链（**不读取会话的当前工作目录、不使用启动目录作为输入项**）：

1. **仓库主工作区** = `git rev-parse --path-format=absolute --git-common-dir` 的输出（共享 `.git` 的绝对路径）的**父目录**；该取值在同一仓库的任意位置相同——以"两个不同位置求值结果相同"作为其不可变性的核对方式。
2. **工作区地址** = `<仓库主工作区>/.pb-agents/worktrees/{迭代ID}`（输入项 = 迭代 ID + 共享 `.git` 路径，**不依赖 cwd**）。
3. **显式覆盖**：派发简报携带的「工作区地址」字段优先于上一步的默认推导；覆盖值同样进入地址声明链（见「协议产物」）。
4. **建立（仅当该地址不存在）**：`git -C <仓库主工作区> worktree add .pb-agents/worktrees/{迭代ID} -b iteration/{迭代ID} main`。建立动作由**会话**执行；"谁建立"不作预设（规则 F 例外① 对执行者中性）。建立成功后**直接继续推进**。
5. **建立成功 / 存在性核查依据**：`git worktree list` 的输出含该地址，且 `git -C <该地址> branch --show-current` 输出 `iteration/{迭代ID}`。

**唯一硬停面**：仅当「**本会话工作区无法确定或无法创建**」（第 1 步无法确定，或第 4 步失败）时硬停——**发现即停**（不进入任何阶段工作、不产生任何写入，含 `status.md` / `history.md` 的创建），输出下列形态（**不含指向人 / 用户的动作要求**）：

```text
【本会话工作区无法确定或无法创建】
触发原因：<无法确定仓库主工作区 / 无法创建工作区：git 报告的错误原文>
当前状态：<已解析到的候选地址，或“未解析出候选地址”>；当前检出：<分支名 或 “无（游离 HEAD）”>
未完成事项：本会话工作区未就绪——未进入任何阶段，未产生任何写入。
```

硬停**不复用** `⛔ 需要你的决策` 暂停格式（那是用户决策点的专用形态，两者互不替代）。工作区就绪性硬停与「流程结构错误中止」（见「阶段回退」）、用户决策点暂停是三类并列机制，不互相替代。

**约束主体**：主 agent 会话（一次迭代校验一次），不是每一次角色派发；阶段 5 的子 agent 以**其简报给定的 PR worktree 绝对地址**为准。

判断方式：任取一次会话的执行记录，核对①地址是否可被第三者按上列解析链复算得到；②该会话的写入目标路径是否均位于该地址之下（`git -C` 形态）；③若该地址不存在而会话未建立即继续推进、或已建立而无第 5 步的两条依据，即违反。

### 规则 E：分支命名（v0.9.0 新增）

会话创建的所有分支名必须含该迭代的**编号**（`{迭代编号}`）。迭代分支本身为 `iteration/{迭代ID}`（含完整迭代 ID，自然满足）；阶段 5 的 PR worktree 分支规范化为 `feat/{迭代编号}-pr-{NNN}-{slug}`。分支的 base 与合并目标不变（PR worktree 的 base 与合并目标仍为迭代分支）。本条款只约束新创建的分支，不追溯已完成迭代的既有分支。

判断方式：`git branch --list` 逐条核对分支名是否包含该迭代的编号（MI-04 口径：字符串包含即可，不要求统一格式）；同名分支被两个会话争用即违反。

### 规则 F：跨工作区写入禁止（v0.9.0 新增）

会话的写操作（**文件写入、`git -C`、`--work-tree`**）必须落在**本会话的工作区内**；以绝对路径写入**非本会话的工作区**（另一个会话的迭代工作区、他人的 PR worktree、仓库主工作区）**不得发生**。必须恢复他人工作区的内容时，**先取备份、后操作**，两步都必须在执行记录中可查。

**本条款不可能被 git 强制执行**：worktree 是目录分离，不是访问控制；本协议不引入 hook、访问控制或路径守卫来"实现"它。

**例外（闭集，仅两项）**：① 会话工作区的**创建**动作（它必然发生在目标工作区之外）；② **收口三步及其前置游离动作**（固定在仓库主工作区执行，见「迭代分支合并进 main」）。除此两项外不存在其他获准的跨工作区写入。

判断方式：取一次会话的执行记录（会话日志 / `history.md` / 提交 diff / `progress.md` 均可），逐条比对"写入动作 → 目标路径"是否位于本会话工作区内（阶段 5 的子 agent 以其简报给定的 PR worktree 绝对地址为准）；出现区外路径时，必须同时存在位于其**之前**的备份动作，否则违反。

### 规则 G：暂停 / 终止迭代的现场保留（v0.9.0 新增）

暂停或终止的迭代，其**会话工作区与分支原样保留、不被自动清理**——不因迭代状态变化被清理，也不被其它会话清理；清理权**仅归其归属会话或用户**。本条款与既有「失败 / 阻塞 PR 现场保留」条款（阶段 5 第 4 点、「状态追踪协议」的 `❌失败(现场保留)` / `⏸阻塞(现场保留)` 定义）**并列、不互相替代**——既有条款的判定对象是 PR worktree，本条款的判定对象是会话 / 迭代工作区与迭代分支。本条款**不含任何清理动作**。

判断方式：对照 `git worktree list` 与 `git branch --list 'iteration/*'`，核对某暂停 / 终止迭代的工作区目录与分支在他人提交 / 分支切换 / 清理动作**前后**是否仍然存在；任一项消失即违反。

### 规则 H：显式寻址纪律（v0.10.0 新增）

会话的一切**文件写入**以工作区地址下的**绝对路径**进行，落在该会话声明的工作区地址之下；一切 **git 写操作**使用 `git -C <工作区地址>` 形态。寻址**不依赖 cwd、不依赖任何工具**（无包装脚本、无钩子、无守护进程、无环境变量前置）。本纪律**不主张可以阻止跨工作区写入**——该写入不可能被 git 强制（见规则 F 与「隔离边界声明」），只能事后核查判定。

判断方式：取一次执行记录逐条核对写入目标是否为绝对路径且位于声明地址之下、git 写操作是否带 `-C <地址>`；出现依赖 cwd 的裸 git 写命令、或出现"必然不会写错 / 越界会被拦住"类断言即违反。

### 协议产物：工作区间与生效规范（`docs/worktrees/README.md`）（v0.10.0 新增）

**协议先行**：本项目的工作区间与生效规范由一份**声明式协议产物**承载——`<项目根>/docs/worktrees/README.md`，**被 git 跟踪**，随 `git worktree add` 检出即得（新工作区零安装动作即可读到；不改 `.gitignore`、不扩展规则 F 的闭集例外）。产物**必须覆盖**五类信息（模板顺序即此序）：① 本项目的工作区间定义（会话 / 迭代工作区落点、PR worktree 落点与层级、工作区的范围）；② 本项目生效的规范与其版本（规范文件路径 + 版本号）；③ 寻址纪律引用（显式寻址、地址声明的三层落点、越界判定是事后核查）；④ 落点语义澄清的**一行**区分句；⑤ 声明不含任何脚本 / 钩子 / 守卫。

**地址声明的三层分工**：**源** = 本产物（项目级**静态**声明：工作区间规则 + 生效规范版本）；**投影 1** = `status.md` 的 `**工作区地址**` 字段（迭代级）；**投影 2** = 派发简报的 `工作区地址` 字段（派发级，阶段 5 为该 PR worktree 的绝对地址）。三层不一致时**以源为准**并登记差异（载体不限，须可被第三者读到"以源为准"的处置）。**硬约束**：任一次运行的**动态地址只落后两者**，**不得写进本产物**——否则每次会话都会产生一次仓库改动，与规则 A / 规则 B 相撞。

**落点语义（三者互不替代）**：`docs/worktrees/` 是**协议产物的文档位置**（被跟踪，**不承载任何运行态工作区**）；`.pb-agents/worktrees/` 是**会话 / PR 工作区池**（运行态，被 `.gitignore` 忽略）；`docs/iterations/{迭代ID}/` 是**迭代产物**（每迭代一份，**不承载跨迭代的协议声明**）。任何会话 / PR worktree **不得**建在 `docs/worktrees/` 下。

**非第二真源**：本产物是规范的**实例化投影**——规范性陈述均以引用规范条款的形态出现，不自行创立规范中没有的约束。

判断方式：① 读该产物逐类核对五类信息是否覆盖、是否出现脚本 / 钩子 / 守卫 / 可复制命令块；② 在三处（产物 / `status.md` / 一次派发简报）比对同一事实是否一致、产物内容是否**不随会话变化**（两个不同会话的检出中逐字节相同）；③ 把产物中每条规范性陈述回指规范条款，出现无对应条款的约束即违反；④ `git ls-files --error-unmatch docs/worktrees/README.md` 成功、且 `git worktree list` 无 `docs/worktrees/` 前缀项、`ls docs/worktrees` 无工作区目录。

### 约束主体（v0.10.0 新增）

**对人（使用者）**：本规范不设任何前置——不要求进入某目录、不要求执行任何命令、不要求预先创建工作区、不要求重开会话。人不承担任何"使会话合规"的动作。

**对会话（主 agent 会话与其派发的执行角色）**：会话承担三项纪律——① 声明其迭代工作区地址；② 一切写入与 git 写操作按该地址显式寻址；③ 需恢复他人工作区内容时，先取备份、后操作。三项的违反**由事后核查判定**（见规则 F 与「隔离边界声明」），不主张被阻止。

判断方式：逐句核对——「对人」段四项零要求逐项存在且与任何相反要求不并存；「对会话」段三项纪律逐项存在；两段不混写在同一句内；且违反的判定方式指向事后核查而非阻止。

### 隔离边界声明（隔离到什么层为止，v0.9.0 新增）

**覆盖（被 git worktree 隔离的共享状态，逐项）**：工作树（每个工作区自己的目录）／ 索引（`.git/worktrees/<id>/index`）／ HEAD（各工作区各自检出）。

**不覆盖（逐项 + 负面约束）**：
- 仓库级 refs（含 stash 与分支命名空间）：不得依赖 stash 跨会话传递状态；不得把分支命名空间当作跨会话通道（分支名必须自带迭代编号，见规则 E）；不得依据 `git branch --merged` 之类的输出直接判定归属——同点分支会被误判为"已合并"（0017 实测先例）。
- 对象库（objects）：不得假设对象库被隔离（它是共享的）；不得对共享对象库做破坏性操作（`gc --prune`、`fsck --lost-found` 等）。
- config / hooks / remotes：不得通过修改共享 config / hooks / remotes 来解决会话级问题；本协议不引入 hook 参与强制。

- **cwd（会话的当前工作目录）**：**cwd 从来不是隔离的一部分**——隔离覆盖的是工作树 / 索引 / HEAD 三层；会话在哪个目录启动与其产物落在哪个工作区无关（归属由声明的地址承担，见规则 C / 规则 D）。

**同一分支不能在两处同时检出**是 git 硬约束（不是本协议可选的保守做法）：因此会话工作区**永不** checkout `main`，`main` 上的合并动作只能在仓库主工作区发生（见「迭代分支合并进 main」）。

**非 git 共享资源（不被隔离，逐项声明 + 两条约束）**：

| 资源 | 声明 | 约束（判断方式在其后） |
|---|---|---|
| 默认端口（真实服务默认 7788，可经环境变量覆盖） | 不被隔离 | ① 真实服务不得并发占用默认端口。判断方式：并发运行真实服务的两个会话，核对两次运行的监听端口必须不同，或核对规范是否要求并发场景显式指定非默认端口。本约束不要求修改默认端口值；测试面自带的随机端口不受约束。 |
| CPU / 负载 | 不被隔离 | ② 受负载影响的偶发失败不得当回归依据。判断方式：检查该失败记录是否含"同一代码在安静环境下重跑"的结果——只凭单次失败下结论即违反。 |
| 临时目录（`/tmp`） | 不被隔离 | 临时产物不得作为最终事实载体；本协议不新增任何清理动作。 |
| 进程内作业注册表 | 不跨会话、会过期 | 不得把"作业列表为空"读成"作业丢失"；判断另一会话的作业状态以 git 落盘事实（commit / 分支 / 产物文件）为准。 |

**已知代价（声明，不定义流程）**：隔离层不含 refs 与对象库，因此会话内不会自动发现与他人改动的冲突——冲突被有意**后移到收口合并期**处置；本协议不定义冲突的自动解决流程，冲突发生时报错上报。

**已知代价（越界写入）**：跨工作区写入**不可能被 git 强制**（worktree 是目录分离，不是访问控制）⇒ 越界**不会被阻止**，只能在**事后核查**中发现。"未被阻止"**不等于**"条款作废"——越界写入仍是规则 F 判定为违规的行为。核查判据（第三者可按步执行）：① 取该会话 `status.md` 的 `**工作区地址**` 字段；② 取该次派发简报的 `工作区地址` 字段；③ 取该会话执行记录中每条写入动作的目标路径；④ 逐条判"是否位于声明地址之下"——区外路径若其**之前**存在备份动作则不判违反，否则判违反。

判断方式：本节四类结论逐一对照一次运行——① 覆盖：该运行的写入是否只改变本工作区的工作树 / 索引 / HEAD；② 不覆盖：是否依赖 refs / stash / 分支命名空间 / 对象库 / config / hooks / remotes 传递会话级状态，或把 cwd 当作归属判据；③ 非 git 共享资源：是否并发占用默认端口、是否以受负载影响的偶发失败当回归依据、是否把临时产物当最终事实载体、是否把"作业列表为空"读成"作业丢失"；④ 已知代价与事后核查：冲突是否被后移到收口合并期处置、越界写入是否按上列四步判据判定（且未被表述为"会被阻止"）。四项均可由未参与讨论者对照一次执行记录与一次派发简报判定；任一项无法判定或与本节结论不符即本节结论不成立。

### 角色定义来源与部署（v0.9.0 新增）

**真源规则**：角色定义的读取来源是**被 git 追踪的内容**。以角色文件是否被跟踪判定：`git ls-files --error-unmatch <角色定义根>/<role>/<role>.md` 成功者即为真源。
- 上游（本仓库，agents 源码仓）：`{角色定义根}` = `roles/`。角色定义随每次检出即得 ⇒ **新工作区零安装动作即可读到完整角色定义**。
- 下游（业务项目）：`{角色定义根}` = `.pb-agents/roles/`（由 `tools/install-pb-agents.sh` 分发；**该步骤是可选的分发动作，不是本协议的运行前提**）。

**解析规则**：每次会话在 Step 0 解析一次、会话内复用——先判真源（被跟踪的 `roles/` 可用则用它），否则回退 `.pb-agents/roles/`；解析结果写入每次 brief 的「角色定义」字段。上下游两个场景**共用同一份规范与同一份 skill**，差别只在解析结果。

**"零动作"的准确含义**：不需要人手动执行安装脚本、不需要额外动作。该承诺只覆盖"角色定义真源随检出即得"的场景（本仓库）；下游仍可有"先分发角色文件"这一步，但该步骤**不算本协议的运行前提**，未执行它不构成停止推进的理由。

**只读约束**：角色定义在执行期只读（真源与分发副本皆然）；角色的 `data/`、`memory.md` 不随分发部署。

判断方式：在任一工作区内按本节解析出 `{角色定义根}`，`git ls-files --error-unmatch <根>/<role>/<role>.md` 必须成功；某次派发前若该判定失败且未回退到下游副本即违反。


**恢复派发**（迭代中断后再派发）时，简报的「工作区地址」字段即覆盖被恢复迭代既有文本中的任何"须在该目录内启动 / 不得在该目录外推进"类前置；**被恢复迭代的既有文本不改写**。

### 阶段 1~4 推进

每次推进前对照该阶段的"推进条件"逐项核查，全部满足才推进：
- 所有条件满足 → 更新 `status.md`，进入下一阶段
- 有条件未满足 → 回到执行角色补充（本阶段自己没做完，不是需求问题，见「阶段回退」判断标准）

**阶段 1 是硬性前置，且由主 agent 内联执行**：无论迭代规模大小、需求看起来多简单，主 agent 都必须先读取 `{角色定义根}/demand/demand.md` 全文、直接以该判断框架和用户对话走一轮（**不派发子 agent**），产出 `demand.md` 并通过阶段 1 推进条件，才能进入阶段 2。不得因"这次需求很清楚"跳过阶段 1。

每次派发执行角色、收到执行角色报告、做出阶段推进核查决策时，同时按「历史记录协议」追加 history.md 记录（不在本段重复定义格式）。

### 阶段 5（PR 实现）：依赖解锁式并发调度

这是本工作流与 v0.1.0 最大的差异所在。**不是按 PR 文件列表顺序逐一 dispatch**，而是：

1. 读取 `prs/*.md`，抽取每个 PR 的 `depends_on`，构建依赖图。构建时校验无环——发现环，停止并向用户上报，这是规划阶段的错误，不在调度层绕开。
2. 对所有 `depends_on` 为空、或所依赖的 PR 均已**合并进当前迭代的迭代分支**的已解锁 PR，按当前有效上限取前 N 个（`N = 当前有效上限`，首批派发时"仍在执行中的 PR 数量"为 0）立即并发派发：为该 PR 创建独立 worktree 分支（`git worktree add .pb-agents/worktrees/{迭代编号}-pr-{NNN}-{slug} -b feat/{迭代编号}-pr-{NNN}-{slug} iteration/{迭代ID}`，**在该 PR worktree 的绝对地址下执行**（`git -C <该地址>`；该地址按派发简报的「工作区地址」字段解析），落点即该工作区内的子目录；base 为当前迭代的迭代分支，不是 main），在子 agent 里依次完成「派发 planner 产出该 PR 的 `prs/pr-{NNN}-tasks.md`」→「派发 dev 实现」→「验收」→「merge 进当前迭代的迭代分支」。首批派发和后续补位派发共用同一条封顶规则（见「并发槛位算法」），不是两套不同的算法。没有已解锁排队 PR 时，槛位空置，不因此放宽"合并进迭代分支才算解锁"这一条件去提前派发未解锁的 PR。
3. 每当一个 PR merge 完成，重新扫描依赖图，检查是否有新的 PR 因此解锁，立即派发，不等待其他并发中的 PR。
4. 某个 PR 阻塞或失败：只暂停依赖它的下游 PR，不影响其他无关 PR 的并发推进。**主 agent 不得对状态为失败/阻塞的 PR 执行 `git worktree remove`、`git branch -d` 或等价清理操作**——现场必须原样保留供人工排查，这是失败/阻塞状态的固有属性（见「状态追踪协议」`❌失败(现场保留)`/`⏸阻塞(现场保留)` 定义），不是可选的保守做法。

**为什么必须以"合并进迭代分支"作为解锁条件，不是"dev 自称完成"**：每个 PR 在独立 worktree 分支上工作，如果 PR-B 依赖 PR-A 的产出，PR-B 的 worktree 分支必须是从"已经合入 PR-A 之后的迭代分支"拉出来的，否则 PR-B 的子 agent 在自己的分支里根本看不到 PR-A 的代码。这是技术约束，不是可选的保守做法。

**`batch` 字段的定位**：仅供人工在 `prs/` 目录里快速扫一眼大致分组，主 agent 的调度判断永远以 `depends_on` 的实际合并状态为准，不读 `batch` 数字做栅栏同步。

**并发派发的技术手段**：主 agent 在同一轮 assistant 响应中，连续发起多个 `Agent()` 工具调用——同一条 assistant message 里的多个工具调用会并发执行，不需要等待前一个返回结果，这是"并发"在本工作流里的具体实现方式，不是描述性的比喻。每个 `Agent()` 调用对应一个独立 PR 的完整执行流程（创建 worktree → 派发 planner → 派发 dev → 验收 → merge）。

**并发槛位算法**：

- 起始并发数从该迭代的 `status.md` 的 `## 并发配置（阶段 5）` 区块读取，默认值为 3（见「启动工作流」的初始化步骤）。
- 硬上限公式：`硬上限 = 2 × 起始并发数 - 1`（起始并发数为 3 时，硬上限为 5）。
- 爬升公式：`当前有效上限 = min(起始并发数 + 累计槛位释放次数 × 起始并发数, 硬上限)`。每当任一并发中的 PR 返回"成功合并"或"失败/阻塞"判定，`累计槛位释放次数` 加 1，重新计算 `当前有效上限`；达到硬上限后，无论再有多少 PR 返回，`当前有效上限` 维持硬上限不变。这个字段名不含"成功"二字是有意的——失败/阻塞判定同样释放槛位、同样计入累加，只是不解锁下游依赖，与"成功合并"是两件不同的事，不要混用判断标准。
- 每次有槛位释放（PR 完成合并或判定失败/阻塞）时，主 agent 从"已解锁且排队中"的 PR 里取前 N 个（`N = 当前有效上限 - 仍在执行中的 PR 数量`），在同一轮响应内发起新的并发 `Agent()` 调用补位——爬升带来的新增槛位，仍然只能分配给依赖已合并的排队 PR，不改变「合并进迭代分支才算解锁」这一前提。**没有已解锁且排队中的 PR 时，释放出的槛位保持空置，不触发任何派发，不得因为槛位空闲而放宽解锁条件去提前派发依赖未合并进迭代分支的 PR。**

每次派发、收到报告、槛位释放/爬升、PR 失败或阻塞判定时，同时按「历史记录协议」追加 history.md 记录（不在本段重复定义格式）。

### 可观测性：progress-observer 自动/按需触发

并发调度带来一个新风险：`status.md` 由主 agent 手动维护，并发度越高，人工记录和真实 git 状态脱节的概率越高（`docs/iterations/0004-model-dispatch/project-retrospective.md` P1 条目是先例）。`progress-observer` 角色专门做独立核实，不采信任何自我声明，只信 git 一手记录。

**触发时机**（角色文件本身不描述这一点，调度契约定义在这里）：
1. **自动触发**：每次一个 PR 完成 merge 之后，或阶段 1~4 中任一阶段推进完成后，主 agent 自动派发一次 `progress-observer`，保持 `docs/iterations/{迭代ID}/progress.md` 新鲜
2. **按需触发**：用户或主 agent 想查看当前客观进度时，随时可以手动派发，不需要等触发条件

**核实项**：每次生成 `progress.md` 时，对状态为失败/阻塞的 PR，须核实其 worktree 目录和分支是否仍存在于磁盘（技术手段：`git worktree list` + `git branch` 交叉核对）。若发现已被清理（与"现场保留"的预期不一致），记入 `progress.md` 的"发现的不一致"部分。这一核实项是调度契约层的具体核实内容清单，不改变 `progress-observer` 角色文件本身"核实一手记录"的能力定义。当前迭代存在迭代分支时，核实合并状态的 git log 命令以迭代分支为基准（如 `git log iteration/{迭代ID} --grep="pr-001"`），而非 main。

**主 agent 拿到 `progress.md` 后的动作**：
- 报告中的"发现的不一致"和"并发度分析"（尤其是"可并发但闲置"的 PR）是主 agent 优先处理的信号——闲置 PR 应立即补派发，不一致状态应先核实 `status.md` 记录错误还是真实的执行异常
- `progress-observer` 只报告事实，不做严重性判断或调度建议；是否重新派发、是否修正 `status.md`，由主 agent 决定
- 不用 `progress-observer` 的报告替代阶段 6 独立验证——两者职责不同：`progress-observer` 判断"状态是否一致"，独立验证判断"产物质量是否达标"

### 阶段回退

**判断标准（执行角色发现问题时先自问，再决定怎么处理）**：解决这个问题，是否要改变 `demand.md` 第二段的结论（做什么/不做什么/大概怎么做/达到什么效果/为什么）？

- **否**——技术方案、实现路径、架构完整度问题（如 `[架构待填]` 项本来就没填完、发现更好的实现方式、发现的 bug）→ 执行角色在当前阶段直接解决，不上报、不搭置、不新开迭代。这类问题本来就是当前阶段自己的职责范围
- **是**——需求本身有矛盾、范围不清、技术上根本做不到、上游产物在需求层面自相矛盾 → **不回退修正、不暂停等待用户**，执行角色直接把问题写入 `docs/iterations/{迭代ID}/deferred-demand-changes.md`（见「文档路径协议」），继续按当前 `demand.md` 完成本迭代——需求变更只能通过发起新迭代来处理，本迭代是对已落盘需求的确定性还原

**唯一的流程结构错误中止**：阶段 4→5 入口 `pr-planner` 报告依赖图有环——这是 PR 规划的结构性错误，不是需求问题，调度层无法排出执行顺序，必须停下修正，不能搭置。（与「规则 D」的工作区就绪性硬停、与「需要用户决策的情况」的暂停**三类并列、互不替代**。）

### 需要用户决策的情况

主 agent 遇到以下情况必须暂停并通知用户，不得自行推进：
- 产物中出现 `[model_inferred]` 标注项
- 架构方案中出现 L1 决策（不可逆的技术判断）
- 执行角色报告"阻塞"且主 agent 无法在不修改上游产物的情况下解决
- 阶段 1（主 agent 内联执行）判断"根本没有问题要解决"
- `pr-planner` 报告依赖图有环

### 终止工作流

在 `status.md` 中将状态标记为"已终止"，写明终止原因。

### 迭代分支合并进 main（在仓库主工作区执行）

阶段 6（独立验证）对本迭代最终产物判定 pass 之后，主 agent 在**仓库主工作区**依次执行以下三步（动作顺序与触发时机不变）：
1. `git -C <仓库主工作区> checkout main`
2. `git -C <仓库主工作区> merge --no-ff iteration/{迭代ID}`
3. `git -C <仓库主工作区> branch -d iteration/{迭代ID}`

**第 3 步的前置动作（在三步之前单独执行，不是新增收口步骤）**：若 `iteration/{迭代ID}` 仍被该迭代的工作区检出，先执行 `git -C <该迭代的工作区地址> checkout --detach` 把检出点游离——「同一分支不能在两处同时检出」是 git 硬约束，故该动作是 `git branch -d` 的**必然前置**（见「隔离边界声明」）。

commit message 格式：`merge: iteration {迭代ID} {该迭代一句话目标} into main`。

若步骤 2 报告冲突：停止推进，向用户上报（结构性错误，类比"PR 依赖图有环"，不在调度层绕开）。

合并完成后，status.md 的 `**迭代分支**` 字段改为 `iteration/{迭代ID}（已合并）`。

## 验证目标（阶段 6 独立验证读）

阶段 4/5 的验证由 verifier 角色执行，主 agent 派发时将以下验证目标内联写入 brief。

### 搭置的需求变更/错误报告

verifier 只读委托里给的产出物路径和验证标准，不会自己扫描目录找 `deferred-demand-changes.md`——主 agent 触发阶段 6 时，若该文件存在，必须把它的路径作为委托的一部分显式传入，要求 verifier 将其内容原文摘录进验证报告。这是用户判断"是否需要发起新迭代"的依据，verifier 不对搭置内容本身做二次判断（是否真的是需求问题、是否应该搭置），只做透传。

### PR 粒度判断框架

pr-planner 分组时使用，verifier 验证时使用。以下三条是判断依据，不是可量化指标：

- **逻辑原子性**：该 PR 只做一件可描述的事，回滚它不影响无关功能。
- **可审查性**：reviewer 能在不切换心智模型的情况下完整审查——逻辑跳跃、跨模块混合是信号。
- **独立性**：验收标准可在不依赖其他 PR 合并的情况下判断。

对于自动生成代码、纯格式化、纯文档变更，行数不是粒度信号，逻辑原子性才是。

### 依赖正确性验证

- **指标**：`depends_on` 中声明的每一条依赖，都能在代码库中找到对应的真实耦合证据（共享符号/接口/文件引用）
- **判断方式**：verifier 对每条 `depends_on` 逐一核实证据是否存在；找不到代码级证据的依赖判定为不合规（可能是把顺序偏好误判成依赖）
- **通过条件**：所有 `depends_on` 条目均有证据支撑；依赖图无环；PR 间文件范围无重叠、无遗漏功能点

### 并发调度真实执行证据（下一个多 PR 迭代强制核查）

`docs/iterations/0005-pr-concurrent-execution/verification-report-stage6.md` 指出：截至 v0.4.0，本协议的并发调度文本从未在真实的多 PR 场景里被验证过执行结果——历次迭代阶段 5 都只规划了一个 PR，阶段 6 的验证只能停留在"协议文字读起来自洽"这一层级，demand.md 里"这套协议从未被真实调度执行过一次"的风险原样成立。

**触发条件**：某次迭代的 `prs/` 目录在阶段 4 产出了 ≥2 个 PR，且依赖图存在真实的并发分支（即存在至少两个互不依赖、或依赖已满足从而可同时进入阶段 5 的 PR）。

**该迭代的阶段 6 验证必须额外核查以下三项，缺任何一项均判定该验证目标 partial，不接受"协议文本正确"代替真实证据**：

1. **worktree 时间窗口重叠**：核实是否存在至少 2 个 PR 的 worktree 分支在磁盘上同时存在过（技术手段：结合 `progress.md` 历史记录或 `git worktree list` 输出的时间信息判断创建/清理区间是否重叠），证明"并发"确实发生过，不是先后串行执行后误报为并发。
2. **并发配置区块真实初始化与更新**：核实该迭代 `status.md` 的 `## 并发配置（阶段 5）` 区块是否在阶段 4→5 入口被真实初始化（五个字段均有值），且随后续 PR 合并/失败判定被真实更新（不是初始化后再未变化）。
3. **爬升公式真实触发**：若该迭代并发中的 PR 数量达到过触发爬升的条件，核实 `当前有效上限` 是否按爬升公式 `min(起始并发数 + 累计槛位释放次数 × 起始并发数, 硬上限)` 被正确重新计算，而不是维持初始值不变。若该迭代 PR 数量始终未触发爬升条件，本项记为"不适用"并说明原因，不算未通过。

三项核查结论均需附文件证据（`status.md` 历史版本、`progress.md`、git 命令输出），不接受"应该没问题"式的模糊判断。

### 验证触发时机

`pr-planner` 完成 PR 规划、`prs/` 目录中所有 PR 文件生成后，主 agent 触发 verifier：

```
产出物路径: docs/iterations/{迭代ID}/prs/
验证标准: [内联自本文件 §验证目标 的两项条目]
```

## 历史记录协议（history.md）

`history.md` 与 `status.md` 并存、职责不同、格式互不侵入：`status.md` 是当前进度的快照视图（可被覆盖更新），`history.md` 是按发起顺序逐条追加的事件流水（只追加，不覆盖、不删除）。

### 落盘位置与创建/关闭时机

- **落盘位置**：`docs/iterations/{迭代ID}/history.md`，与 `status.md` 同级（见「文档路径协议」）。
- **创建时机**：工作流启动创建 `status.md` 之后（见「调度指南 § 启动工作流」），若该迭代 `history` 字段（见「状态追踪协议」）为开启，立即创建仅含一行标题 `# history.md — {迭代ID}` 的空文件——不等到第一次派发才惰性创建。
- **关闭时的行为**：
  - 启动时 `history` 即为关闭 → 不创建 `history.md`。
  - 运行中途 `history` 被改为关闭 → 已存在的 `history.md` 保留不删除，但主 agent 后续不再对其追加写入。

### 三类事件的记录格式

每条记录是一个三级标题 + 若干字段行：

```markdown
### {YYYY-MM-DD HH:MM:SS} · {事件类型} · {对象}

- {字段1}：{值1}
- {字段2}：{值2}
```

- **时间戳**：`YYYY-MM-DD HH:MM:SS`，本地时间 24 小时制，精度到**秒级**（不是日期级或分钟级）——同一轮响应内连续发起的多条记录很可能落在同一分钟甚至同一秒，只有秒级精度才能保留"大致何时发生"这一独立于顺序保真之外的信息量（顺序本身由下方「顺序保真约定」保证，不依赖时间戳）。
- **事件类型**取值三选一：`派发` / `收到报告` / `调度决策`。
- **对象**：派发/收到报告类填角色名（如 `architect`）；调度决策类填决策类别（`阶段推进核查` / `Gate确认` / `槛位释放` / `PR失败判定`）。

**派发类字段**（对应「派发执行角色时的 brief 构建」里已内联进 brief 的字段，只摘录不复制角色定义全文）：

```markdown
- 阶段：阶段 3（技术架构）
- 任务：在现有架构上演进，补全功能卡的架构维度，产出技术方案
```

阶段 5 额外加一行：
```markdown
- PR：prs/pr-{NNN-描述}.md
```

**收到报告类字段**：逐条摘录该角色「报告契约」已定义的编号/字段项，每项压缩为一句话结论值——不复制角色报告原文的解释性长文，只留判断性结论。字段序号与角色报告契约的编号严格对应，不合并、不跳过；对于非编号列表式的报告契约（如 `verifier` 用固定模板字段代替编号），改为摘录模板字段名+对应结论值，规则同源。

示例：
```markdown
### 2026-09-07 14:32:10 · 收到报告 · architect

- 1. architecture.md 路径：docs/iterations/0007-workflow-history-log/architecture.md；核心组件：history.md 记录协议、开关字段、三类事件格式、顺序保真规则
- 2. L1 决策清单：无
- 3. 新引入技术组件：无
- 4. 架构待填补全数：4（AR-01~AR-04）
- 5. 疑问/越界：无
```

**调度决策类字段**：至少包含"决策内容"和"触发依据"两个字段，"触发依据"必须是具体的触发条件、依据的文件路径或状态值，不是"因为需要"这类无信息量占位：

```markdown
- 决策内容：{具体决策是什么}
- 触发依据：{具体触发的条件、依据的文件路径或状态值}
```

示例：
```markdown
### 2026-09-07 14:33:00 · 调度决策 · 阶段推进核查

- 决策内容：阶段 3（技术架构）推进条件全部满足，进入阶段 4（PR 规划）
- 触发依据：L1 决策清单为空（architecture.md §L1 决策清单）；prd/F01~F04.md 的 `[架构待填]` 项均已补全为具体技术路径（architecture.md §prd 补全记录）；架构方案内部无冲突（architecture.md §验证）
```

### 顺序保真约定

不引入序号字段，不引入同步锁/写入互斥机制。`history.md` 的写入动作本身永远是主 agent 单线程顺序完成的，即使随后在同一轮 assistant 响应中并发发起多个 `Agent()` 工具调用（子 agent 的执行是并发的）——"记录这些即将发起的派发"这一步骤发生在发起 `Agent()` 调用之前，主 agent 依次调用文件写入工具追加多条记录，这些写入调用本身不并发。因此记录在文件中出现的物理先后顺序，天然等于主 agent 实际发起这些派发的顺序，读者从上到下阅读即可还原发起顺序，不需要额外排序字段。

**具体操作约定**：
- 阶段 5 同一轮响应内准备并发发起 N 个 `Agent()` 调用前，主 agent 先依次追加 N 条「派发」记录（记录顺序 = 即将发起 `Agent()` 调用的顺序），再在同一轮响应内发起这 N 个并发调用。
- 补位派发同理：先记录一条「调度决策·槛位释放」，再依次记录每个补位派发的「派发」条目——两者是相邻但独立的两条记录，不合并。

## 角色读取指南（执行角色读）

**本节适用于阶段 2~6 被派发的执行角色。demand（阶段 1）由主 agent 内联执行，不被派发，不适用本节**——主 agent 直接从「阶段定义」表读取阶段 1 的输入/输出/推进条件。

你被派发时，brief 里会包含：
1. **工作流文件路径**：`roles/workflow-pb/workflow-pb.md`
2. **当前迭代 ID**：如 `0003-user-profile`
3. **当前阶段编号**：如 `阶段 3`
4. **（阶段 5 专属）当前 PR 文件路径**：如 `docs/iterations/{迭代ID}/prs/pr-002-xxx.md`——阶段 5 的角色（planner、dev）只拿到单个 PR 文件，不拿到全部 `prs/` 目录

你的动作：
1. 读本文件"阶段定义"表，找到你负责的阶段行
2. **输入**：从"输入"列确定文档性质，路径 = `docs/iterations/{迭代ID}/` + 输入文档名
3. **输出**：从"输出"列确定文档性质，路径 = `docs/iterations/{迭代ID}/` + 输出文档名
4. **交付标准**："推进条件"列是你的完成定义
5. 读 `status.md` 了解当前进度和是否有待处理的上下文

**不要从自己的角色文件里找输入输出路径**——角色文件只定义能力，工作流定义契约。

## 原则

**工作流规范不定义执行细节**

本文件定义"做什么、交什么、满足什么标准"，不定义"怎么做"。执行细节由对应的执行角色文件定义。

**出口定义优先于流程顺序**

推进条件是每个阶段最重要的内容。顺序是结果，推进条件是原因。含糊的推进条件（"完成了就推进"）是未来返工的种子。

**不指定执行角色名**

本文件描述每个阶段的能力要求，不绑定具体的角色文件名。角色文件会迭代、会重命名，工作流的阶段职责应该稳定。

**约束和调度契约只存在于本文件一处**

提交管理约束（**PR worktree** 隔离、PR 文件前置）和并发调度逻辑只在本文件定义，不允许再拆出独立文件重复表达同一套规则——这是 v0.2.0 从"workflow-pb + workflow-scm 两处重复"吸取的教训。

## 何时更新本文件

- 某个阶段的推进条件导致下游返工 → 收紧该阶段的推进条件
- 某个阶段的职责边界不清导致执行角色越界 → 在对应阶段的职责描述里明确排除项
- 发现遗漏了某类工作（如 review）→ 新增阶段，不改动现有阶段
- PR 粒度判断导致执行角色产出与实际工作量不匹配 → 修订判断框架描述
- 依赖正确性验证出现误判 → 收紧判断规则
- 不得因"方便执行角色"而在本文件里加入执行细节
- 不得为图省事再拆出独立文件重复表达本文件已有的约束

变更历史写入 `data/workflow-pb-changelog.md`，保留旧版推进条件被修改的原因。
