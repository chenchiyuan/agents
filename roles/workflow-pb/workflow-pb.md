**版本**: 0.7.0
**创建日期**: 2026-09-02
**变更历史**: 见 `data/workflow-pb-changelog.md`

---

**CRITICAL: 本文件只定义规范，不执行工作。所有执行判断由主 agent 和执行角色完成。**

**CRITICAL: 修改本文件不得侵入任何执行角色文件。角色文件只定义能力，工作流文件定义契约。**

**CRITICAL: 本文件是提交管理约束的唯一来源——不得再有独立的 workflow-scm 文件重复定义 worktree/PR 规则；发现重复定义视为耦合未解。**

## 一句话职责

定义 pb 产品研发工作流的完整规范（含从 PR 规划到代码合并的提交管理约束和并发调度契约），让主 agent 知道怎么调度、怎么并发，让执行角色知道读什么、写什么、交付什么。

## v0.7.0 变更说明（相对 v0.6.0）

**新增 history.md 记录协议**：新增独立于 `status.md` 的 `history.md` 记录产物（「历史记录协议」一节），按主 agent 派发、收到报告、调度决策三类事件的发起顺序逐条追加记录，与 `status.md` 并存、职责不同、格式互不侵入。`status.md` 头部新增 `history` 开关字段（默认开启），控制该文件是否被创建和维护。

**目的**：让复盘者/debug 者事后阅读 `history.md` 就能看懂"这次迭代派发了什么、收到了什么反馈、主 agent 基于什么做了什么调度决策"，不需要询问执行者或依赖会话记忆。

**不改变的部分**：`status.md` 现有格式与维护时机中除新增 `history` 字段行之外的任何部分；并发调度算法本身（起始并发数/爬升公式/硬上限不变）；任何执行角色文件（`roles/<role>/<role>.md`）本身的报告契约字段定义。

**验证方式**：本次迭代（`0007-workflow-history-log`）自身即在阶段 5 执行中开启 `history` 字段验证协议文字的可执行性，阶段 6 独立验证核查该迭代产出的 `history.md` 是否满足格式与顺序要求。

## v0.6.0 变更说明（相对 v0.5.0）

**派发机制升级为全文注入**：明确主 agent 派发执行角色时必须读出角色文件全文并显性注入 brief，不再是路径引用让子 agent 自觉阅读。补充"§ 派发执行角色时的 brief 构建"一节，与 SKILL.md 的"§ Brief 构建规则"保持一致。目的是提高机械性契约（CRITICAL 清单、报告格式、字段定义）的遵循度。

**协议等价性澄清**：在 `principles/meta/agent-design-protocol.md` 补充"role = skill"的协议等价性说明——role 文件本身就是 skill（agent 的标准协议单元），"派发角色"和"加载 skill"在协议语义上等价。

**验证方式**：先只在 demand 角色的派发路径上应用全文注入机制，下次派发 demand 时验证是否真的改善了遵循度，再决定要不要推广到其余 8 个角色。

## v0.5.0 变更说明（相对 v0.4.0）

`docs/iterations/0005-pr-concurrent-execution/verification-report-stage6.md` 独立验证发现 v0.4.0 文本本身允许两种互相矛盾的读法（详见 `data/workflow-pb-changelog.md`）。对应改动：

1. 「阶段 5」首批派发补上与补位派发相同的封顶规则（原来只有补位场景写了"取前 N 个"）。
2. 补一句负面约束：无排队 PR 时槛位空置不触发任何派发，不得因此放宽解锁条件。
3. 补一句负面约束：主 agent 不得对失败/阻塞 PR 执行 worktree/branch 清理操作。
4. `累计成功解锁次数` 改名为 `累计槛位释放次数`——原名暗示只在成功时累加，但实际规则是成功和失败/阻塞都累加，名实不符。
5. 新增「阶段 6 验证目标」下的强制检查项：下一个真实涉及 ≥2 个可并发 PR 的迭代，阶段 6 验证必须核查真实执行证据（worktree 时间窗口重叠、并发配置区块真实初始化更新、爬升公式真实触发），不能停留在"协议文字读起来正确"这一层级。

## v0.2.1 变更说明（相对 v0.2.0）

新增「可观测性：progress-observer 自动/按需触发」章节（见「调度指南」）。触发背景：v0.2.0 的依赖解锁式并发调度让 `status.md` 更容易与真实 git 状态脱节——并发度越高，人工维护状态的偏差概率越高。新角色 `progress-observer` 独立核实真实状态，不采信任何自我声明。角色文件本身不定义触发时机，触发时机（自动+按需）作为调度契约写在本文件里，遵循既有权责分离原则。

## v0.2.0 变更说明（相对 v0.1.0）

`docs/iterations/0004-model-dispatch` 迭代复盘发现两个根因问题（见 `data/workflow-pb-changelog.md` 完整记录）：

1. **全局 `tasks.md` 在没有真实 PR 边界时判断依赖**，导致"最小风险的顺序偏好"被误判成"技术依赖"，PR 之间本该并行的工作被串行执行。
2. **两个独立工作流文件（workflow-pb + workflow-scm）重复定义同一套 worktree/PR 规则**，违反"协调者定义契约，不重复定义"的权责分离原则。

对应改动：
- 阶段从 7 个减到 6 个：原「任务拆解」（全局一次性产出 tasks.md）与「提交规划」合并为「PR 规划」，直接从架构方案+代码库现状反射 PR 边界；原「任务拆解」里"单个任务怎么拆"的部分移入新的「PR 实现」阶段，改为**逐 PR 在子 agent 中执行**——任务拆解是执行阶段的事情，不是独立的全局规划阶段
- `commit-planner` 退役，新角色 `pr-planner` 取代，不再消费/产出全局 `tasks.md`
- `workflow-scm` 整个并入本文件，`roles/workflow-scm/` 目录删除
- 调度指南新增"依赖解锁式并发"：不再是"按列表顺序逐一 dispatch"，而是无依赖或依赖已合并的 PR 立即并发派发

## 阶段定义

工作流包含 6 个阶段。每个阶段有独立的验证步骤，验证通过才算该阶段完成。

| # | 阶段 | 职责描述 | 输入 | 输出 | 推进条件 |
|---|---|---|---|---|---|
| 1 | 需求收敛 | 通过结构化对话消除模糊、界定边界，产出有澄清依据的需求合同 | 用户原始表述 / 迭代目标 / 草稿文本 | `demand.md`（两段：澄清依据 + 带最小边界的结论） | 两段均有内容；所有 `model_inferred` 结论经用户确认；无活跃冲突 |
| 2 | 功能规格 | 将需求合同原子化为可独立验证的功能卡，只做产品维度，不做架构决策 | `demand.md` | `prd.md`（报告级索引）+ `prd/*.md`（每功能点独立卡，含验收标准和边界） | 所有功能点有独立卡片；无 demand.md 外新增功能；架构待定项已标注 `[架构待填]` |
| 3 | 技术架构 | 在现有架构上演进，补全功能卡的架构维度，产出技术方案 | `prd/*.md` + 现有代码库 / 架构文档 | `architecture.md` + `prd/*.md` 中 `[架构待填]` 项补全 | L1 决策经用户确认；所有功能卡有技术路径；无架构内部冲突 |
| 4 | PR 规划 | 反射出可独立合并的提交单元划分及单元间真实依赖，从架构方案+代码库现状出发，不经过全局任务图这一中间环节 | `architecture.md` + `prd/*.md` + 代码库现状 | `prs/pr-{NNN-描述}.md`（七字段，见「PR 文件格式规范」） | 每个 PR 文件满足格式规范；`prd/*.md` 中每个功能点被某个 PR 引用；PR 间文件范围无重叠；依赖图无环 |
| 5 | PR 实现 | 逐 PR 在独立 worktree 分支、独立子 agent 中执行：先拆该 PR 内部的任务（子 agent 内部步骤，不产出全局任务图），再实现，产出最小实现 | 单个 `prs/pr-{NNN}.md` 文件 | `prs/pr-{NNN}-tasks.md`（该 PR 内部任务列表，供 dev 消费）+ 代码 + 通过验证标准的测试 | 该 PR 验收标准全部通过；无简报外改动；对应 PR 文件存在（合并前置） |
| 6 | 独立验证 | 不接收执行过程上下文，独立评判任意阶段产物的质量 | 待验证产物（路径由主 agent 指定） | `clarifications/verify-{timestamp}.md`（pass / fail / partial / blocked + 逐项证据） | 每项有明确结论和文件证据；无"基本通过"模糊表述 |

> 阶段 6（独立验证）可在任意阶段结束后触发，不局限于最终产物。推进条件中"已验证"指该阶段产物经过阶段 6 且结论为 pass。
>
> 阶段 5「PR 实现」内部的任务拆解由 `planner` 角色承担，但触发方式与 v0.1.0 不同：**不是一次性对全架构拆解，而是主 agent 逐 PR 派发、在该 PR 专属的子 agent 会话内完成**，输入范围收窄为单个 PR 文件（+ architecture.md/prd 作背景）。这样任务粒度天然被 PR 的真实文件边界约束，不会重复出现"把顺序偏好当依赖"的问题。

## 提交管理约束（原 workflow-scm 内容，并入本文件）

以下约束在每次使用本工作流的迭代中强制生效，每条措辞明确，可被客观判断是否违反。

### 规则 A：worktree 隔离

从阶段 4（PR 规划）完成之后，任何代码变更必须在独立 worktree 分支上进行，不得直接在主分支（main/master）上提交。

判断方式：每次提交所在分支不得为 `main` 或 `master`；所有变更必须通过 PR 合并进主分支。

### 规则 B：PR 文件前置

每个 worktree 变更必须对应一个 `prs/pr-{NNN-描述}.md` 文件（按下方「PR 文件格式规范」），merge 前该文件须存在。

判断方式：merge 操作执行前，对应的 PR 文件在 `docs/iterations/{迭代ID}/prs/` 目录中可读取。

### 约束生效范围

上述约束仅从下一个使用本工作流的迭代起生效，不追溯已完成迭代。

## PR 文件格式规范

每个 PR 文件必须包含以下七个字段，缺一不可（相对 v0.1.0 新增 `depends_on`/`batch`，`涉及 tasks` 改为 `涉及功能点`——因为不再有全局 tasks.md）：

### 1. 上下文摘要

```markdown
## 上下文摘要

[描述该 PR 的目标、背景和关键约束，200 字以内]
```

### 2. 涉及功能点

引用 `prd/*.md` 的 F-ID 无序列表。

```markdown
## 涉及功能点

- F01
- F03
```

### 3. 文件范围

```markdown
## 文件范围

- roles/pr-planner/pr-planner.md（新建）
```

### 4. 验收标准

至少一条，可独立判断，不依赖其他 PR 完成才能判断。

```markdown
## 验收标准

- [ ] 文件 `roles/pr-planner/pr-planner.md` 存在且可独立读取
```

### 5. 参考资料

```markdown
## 参考资料

- docs/iterations/0004-model-dispatch/prd/F01-xxx.md
```

### 6. depends_on

该 PR 真正依赖的其他 PR 文件名列表，可为空列表，但字段必须存在。每一条依赖必须有代码级证据（共享符号/接口/文件），不能是文档叙述顺序。

```markdown
## depends_on

- pr-001-xxx.md（理由：消费 pr-001 新增的 XxxAdapter 接口）
```

无依赖时写 `（无）`。

### 7. batch

人工速览用的粗粒度分组标记，**不是调度依据**——调度依据是 `depends_on` 的合并状态。

```markdown
## batch

1
```

## 调度指南（主 agent 读）

### 启动工作流

1. 确认迭代 ID（`{编号-迭代名}`）
2. 创建 `docs/iterations/{编号-迭代名}/status.md`，初始化阶段表
3. 创建 `status.md` 之后，若 `history` 字段为开启，创建空 `history.md`（见「历史记录协议」）
4. 从阶段 1（需求收敛）开始
5. 进入阶段 4→5 时（阶段 5 第一次并发派发之前），须在该迭代的 `status.md` 中初始化 `## 并发配置（阶段 5）` 区块，字段包括：
   - `**起始并发数**`（默认 3）
   - `**硬上限**`（公式 `2×起始-1`）
   - `**当前有效上限**`（初始等于起始并发数）
   - `**累计槛位释放次数**`（初始 0）
   - `**已派发总数**`（初始 0）

### 派发执行角色时的 brief 构建

每次派发执行角色时，主 agent 必须先读出角色文件全文（`.pb-agents/roles/<role>/<role>.md`），将全文内容显性注入子 agent 的初始指令（brief）中——不是只传递文件路径让子 agent 自行决定要不要读、读多细。这确保机械性契约（CRITICAL 清单、报告格式、字段定义、停止条件）的遵循度。

brief **至少**包含以下字段，且必须逐行以 `字段名：值` 的形式呈现（不得改写、合并或省略字段名）：

```
角色名：<role>（如 demand/prd/architect，供对外呈现时可辨认角色对应关系）
角色定义（全文注入）：
---
{读出的 .pb-agents/roles/<role>/<role>.md 完整内容，原样注入}
---
工作流规范：.pb-agents/roles/workflow-pb/workflow-pb.md
当前迭代 ID：{迭代ID}
当前阶段：阶段 {N}（{阶段名}）
任务：{阶段职责，一句话，读自本文件 §阶段定义"职责描述"列}
输入：docs/iterations/{迭代ID}/{输入文档，读自本文件 §阶段定义"输入"列}
输出：docs/iterations/{迭代ID}/{输出文档，读自本文件 §阶段定义"输出"列}
完成定义：{内联该阶段推进条件清单，读自本文件 §阶段定义"推进条件"列}
```

阶段 5 额外必填：
```
当前 PR：docs/iterations/{迭代ID}/prs/{pr文件名}
worktree 分支：{分支名}
注意：只处理该 PR 文件范围内的功能，不拿全部 prs/ 目录
```

### 阶段 1~4 推进

每次推进前对照该阶段的"推进条件"逐项核查，全部满足才推进：
- 所有条件满足 → 更新 `status.md`，进入下一阶段
- 有条件未满足 → 回到执行角色补充（本阶段自己没做完，不是需求问题，见「阶段回退」判断标准）

**阶段 1 是硬性前置**：无论迭代规模大小、需求看起来多简单，主 agent 都必须先派发 demand 角色走一轮，产出 `demand.md` 并通过阶段 1 推进条件，才能进入阶段 2。不得因"这次需求很清楚"跳过阶段 1。

每次派发执行角色、收到执行角色报告、做出阶段推进核查决策时，同时按「历史记录协议」追加 history.md 记录（不在本段重复定义格式）。

### 阶段 5（PR 实现）：依赖解锁式并发调度

这是本工作流与 v0.1.0 最大的差异所在。**不是按 PR 文件列表顺序逐一 dispatch**，而是：

1. 读取 `prs/*.md`，抽取每个 PR 的 `depends_on`，构建依赖图。构建时校验无环——发现环，停止并向用户上报，这是规划阶段的错误，不在调度层绕开。
2. 对所有 `depends_on` 为空、或所依赖的 PR 均已**合并进主分支**的已解锁 PR，按当前有效上限取前 N 个（`N = 当前有效上限`，首批派发时"仍在执行中的 PR 数量"为 0）立即并发派发：为该 PR 创建独立 worktree 分支，在子 agent 里依次完成「派发 planner 产出该 PR 的 `prs/pr-{NNN}-tasks.md`」→「派发 dev 实现」→「验收」→「merge 主分支」。首批派发和后续补位派发共用同一条封顶规则（见「并发槛位算法」），不是两套不同的算法。没有已解锁排队 PR 时，槛位空置，不因此放宽"合并进主分支才算解锁"这一条件去提前派发未解锁的 PR。
3. 每当一个 PR merge 完成，重新扫描依赖图，检查是否有新的 PR 因此解锁，立即派发，不等待其他并发中的 PR。
4. 某个 PR 阻塞或失败：只暂停依赖它的下游 PR，不影响其他无关 PR 的并发推进。**主 agent 不得对状态为失败/阻塞的 PR 执行 `git worktree remove`、`git branch -d` 或等价清理操作**——现场必须原样保留供人工排查，这是失败/阻塞状态的固有属性（见「状态追踪协议」`❌失败(现场保留)`/`⏸阻塞(现场保留)` 定义），不是可选的保守做法。

**为什么必须以"合并进主分支"作为解锁条件，不是"dev 自称完成"**：每个 PR 在独立 worktree 分支上工作，如果 PR-B 依赖 PR-A 的产出，PR-B 的 worktree 分支必须是从"已经合入 PR-A 之后的主分支"拉出来的，否则 PR-B 的子 agent 在自己的分支里根本看不到 PR-A 的代码。这是技术约束，不是可选的保守做法。

**`batch` 字段的定位**：仅供人工在 `prs/` 目录里快速扫一眼大致分组，主 agent 的调度判断永远以 `depends_on` 的实际合并状态为准，不读 `batch` 数字做栅栏同步。

**并发派发的技术手段**：主 agent 在同一轮 assistant 响应中，连续发起多个 `Agent()` 工具调用——同一条 assistant message 里的多个工具调用会并发执行，不需要等待前一个返回结果，这是"并发"在本工作流里的具体实现方式，不是描述性的比喻。每个 `Agent()` 调用对应一个独立 PR 的完整执行流程（创建 worktree → 派发 planner → 派发 dev → 验收 → merge）。

**并发槛位算法**：

- 起始并发数从该迭代的 `status.md` 的 `## 并发配置（阶段 5）` 区块读取，默认值为 3（见「启动工作流」的初始化步骤）。
- 硬上限公式：`硬上限 = 2 × 起始并发数 - 1`（起始并发数为 3 时，硬上限为 5）。
- 爬升公式：`当前有效上限 = min(起始并发数 + 累计槛位释放次数 × 起始并发数, 硬上限)`。每当任一并发中的 PR 返回"成功合并"或"失败/阻塞"判定，`累计槛位释放次数` 加 1，重新计算 `当前有效上限`；达到硬上限后，无论再有多少 PR 返回，`当前有效上限` 维持硬上限不变。这个字段名不含"成功"二字是有意的——失败/阻塞判定同样释放槛位、同样计入累加，只是不解锁下游依赖，与"成功合并"是两件不同的事，不要混用判断标准。
- 每次有槛位释放（PR 完成合并或判定失败/阻塞）时，主 agent 从"已解锁且排队中"的 PR 里取前 N 个（`N = 当前有效上限 - 仍在执行中的 PR 数量`），在同一轮响应内发起新的并发 `Agent()` 调用补位——爬升带来的新增槛位，仍然只能分配给依赖已合并的排队 PR，不改变「合并进主分支才算解锁」这一前提。**没有已解锁且排队中的 PR 时，释放出的槛位保持空置，不触发任何派发，不得因为槛位空闲而放宽解锁条件去提前派发依赖未合并的 PR。**

每次派发、收到报告、槛位释放/爬升、PR 失败或阻塞判定时，同时按「历史记录协议」追加 history.md 记录（不在本段重复定义格式）。

### 可观测性：progress-observer 自动/按需触发

并发调度带来一个新风险：`status.md` 由主 agent 手动维护，并发度越高，人工记录和真实 git 状态脱节的概率越高（`docs/iterations/0004-model-dispatch/project-retrospective.md` P1 条目是先例）。`progress-observer` 角色专门做独立核实，不采信任何自我声明，只信 git 一手记录。

**触发时机**（角色文件本身不描述这一点，调度契约定义在这里）：
1. **自动触发**：每次一个 PR 完成 merge 之后，或阶段 1~4 中任一阶段推进完成后，主 agent 自动派发一次 `progress-observer`，保持 `docs/iterations/{迭代ID}/progress.md` 新鲜
2. **按需触发**：用户或主 agent 想查看当前客观进度时，随时可以手动派发，不需要等触发条件

**核实项**：每次生成 `progress.md` 时，对状态为失败/阻塞的 PR，须核实其 worktree 目录和分支是否仍存在于磁盘（技术手段：`git worktree list` + `git branch` 交叉核对）。若发现已被清理（与"现场保留"的预期不一致），记入 `progress.md` 的"发现的不一致"部分。这一核实项是调度契约层的具体核实内容清单，不改变 `progress-observer` 角色文件本身"核实一手记录"的能力定义。

**主 agent 拿到 `progress.md` 后的动作**：
- 报告中的"发现的不一致"和"并发度分析"（尤其是"可并发但闲置"的 PR）是主 agent 优先处理的信号——闲置 PR 应立即补派发，不一致状态应先核实 `status.md` 记录错误还是真实的执行异常
- `progress-observer` 只报告事实，不做严重性判断或调度建议；是否重新派发、是否修正 `status.md`，由主 agent 决定
- 不用 `progress-observer` 的报告替代阶段 6 独立验证——两者职责不同：`progress-observer` 判断"状态是否一致"，独立验证判断"产物质量是否达标"

### 阶段回退

**判断标准（执行角色发现问题时先自问，再决定怎么处理）**：解决这个问题，是否要改变 `demand.md` 第二段的结论（做什么/不做什么/大概怎么做/达到什么效果/为什么）？

- **否**——技术方案、实现路径、架构完整度问题（如 `[架构待填]` 项本来就没填完、发现更好的实现方式、发现的 bug）→ 执行角色在当前阶段直接解决，不上报、不搭置、不新开迭代。这类问题本来就是当前阶段自己的职责范围
- **是**——需求本身有矛盾、范围不清、技术上根本做不到、上游产物在需求层面自相矛盾 → **不回退修正、不暂停等待用户**，执行角色直接把问题写入 `docs/iterations/{迭代ID}/deferred-demand-changes.md`（见「文档路径协议」），继续按当前 `demand.md` 完成本迭代——需求变更只能通过发起新迭代来处理，本迭代是对已落盘需求的确定性还原

**唯一的硬停例外**：阶段 4→5 入口 `pr-planner` 报告依赖图有环——这是 PR 规划的结构性错误，不是需求问题，调度层无法排出执行顺序，必须停下修正，不能搭置。

### 需要用户决策的情况

主 agent 遇到以下情况必须暂停并通知用户，不得自行推进：
- 产物中出现 `[model_inferred]` 标注项
- 架构方案中出现 L1 决策（不可逆的技术判断）
- 执行角色报告"阻塞"且主 agent 无法在不修改上游产物的情况下解决
- 阶段 1 执行角色反馈"根本没有问题要解决"
- `pr-planner` 报告依赖图有环

### 终止工作流

在 `status.md` 中将状态标记为"已终止"，写明终止原因。

├── prd/                   ← 阶段 2 产物（功能卡）

## 验证目标（阶段 6 独立验证读）

阶段 4/5 的验证由 verifier 角色执行，主 agent 派发时将以下验证目标内联写入 brief。

### 搭置的需求变更/错误报告

verifier 只读委托里给的产出物路径和验证标准，不会自己扫描目录找 `deferred-demand-changes.md`——主 agent 触发阶段 6 时，若该文件存在，必须把它的路径作为委托的一部分显式传入，要求 verifier 将其内容原文摘录进验证报告。这是用户判断"是否需要发起新迭代"的依据，verifier 不对搭置内容本身做二次判断（是否真的是需求问题、是否应该搭置），只做透传。

### PR 粒度判断框架

pr-planner 分组时使用，verifier 验证时使用。以下三条是判断依据，不是可量化指标：

- **逻辑原子性**：该 PR 只做一件可描述的事，回滚它不影响无关功能。
- **可审查性**：reviewer 能在不切换心智模型的情况下完整审查——逻辑跳跃、跨模块混合是信号。
- **独立性**：验收标准可在不依赖其他 PR 合并的情况下判断。

对于自动生成代码、纯格式化、纯文档变更，行数不是粒度信号，逻辑原子性才是。

### 依赖正确性验证

- **指标**：`depends_on` 中声明的每一条依赖，都能在代码库中找到对应的真实耦合证据（共享符号/接口/文件引用）
- **判断方式**：verifier 对每条 `depends_on` 逐一核实证据是否存在；找不到代码级证据的依赖判定为不合规（可能是把顺序偏好误判成依赖）
- **通过条件**：所有 `depends_on` 条目均有证据支撑；依赖图无环；PR 间文件范围无重叠、无遗漏功能点

### 并发调度真实执行证据（下一个多 PR 迭代强制核查）

`docs/iterations/0005-pr-concurrent-execution/verification-report-stage6.md` 指出：截至 v0.4.0，本协议的并发调度文本从未在真实的多 PR 场景里被验证过执行结果——历次迭代阶段 5 都只规划了一个 PR，阶段 6 的验证只能停留在"协议文字读起来自洽"这一层级，demand.md 里"这套协议从未被真实调度执行过一次"的风险原样成立。

**触发条件**：某次迭代的 `prs/` 目录在阶段 4 产出了 ≥2 个 PR，且依赖图存在真实的并发分支（即存在至少两个互不依赖、或依赖已满足从而可同时进入阶段 5 的 PR）。

**该迭代的阶段 6 验证必须额外核查以下三项，缺任何一项均判定该验证目标 partial，不接受"协议文本正确"代替真实证据**：

1. **worktree 时间窗口重叠**：核实是否存在至少 2 个 PR 的 worktree 分支在磁盘上同时存在过（技术手段：结合 `progress.md` 历史记录或 `git worktree list` 输出的时间信息判断创建/清理区间是否重叠），证明"并发"确实发生过，不是先后串行执行后误报为并发。
2. **并发配置区块真实初始化与更新**：核实该迭代 `status.md` 的 `## 并发配置（阶段 5）` 区块是否在阶段 4→5 入口被真实初始化（五个字段均有值），且随后续 PR 合并/失败判定被真实更新（不是初始化后再未变化）。
3. **爬升公式真实触发**：若该迭代并发中的 PR 数量达到过触发爬升的条件，核实 `当前有效上限` 是否按爬升公式 `min(起始并发数 + 累计槛位释放次数 × 起始并发数, 硬上限)` 被正确重新计算，而不是维持初始值不变。若该迭代 PR 数量始终未触发爬升条件，本项记为"不适用"并说明原因，不算未通过。

三项核查结论均需附文件证据（`status.md` 历史版本、`progress.md`、git 命令输出），不接受"应该没问题"式的模糊判断。

### 验证触发时机

`pr-planner` 完成 PR 规划、`prs/` 目录中所有 PR 文件生成后，主 agent 触发 verifier：

```
产出物路径: docs/iterations/{迭代ID}/prs/
验证标准: [内联自本文件 §验证目标 的两项条目]
```

## 状态追踪协议（status.md）

`status.md` 由主 agent 在每次阶段状态变更时更新，是工作流唯一的进度视图。

### status.md 格式

```markdown
# 工作流进度

**工作流**: workflow-pb v{版本}
**迭代**: {编号-迭代名}
**当前阶段**: {阶段名}（阶段 {#}）
**状态**: {进行中 / 等待确认 / 已完成 / 已终止}
**history**: 开启

## 阶段状态

| # | 阶段 | 完成 | 已验证 | 备注 |
|---|---|---|---|---|
| 1 | 需求收敛 | ✅ | ✅ | |
| 2 | 功能规格 | ✅ | ⬜ | |
| 3 | 技术架构 | ⏸ | ⬜ | 2 个 L1 决策待确认 |
| 4 | PR 规划 | ⬜ | ⬜ | |
| 5 | PR 实现 | ⬜ | ⬜ | 逐 PR 状态见下 |
| 6 | 独立验证 | — | — | 按需触发，不计入线性进度 |

## PR 实现子状态（阶段 5 展开）

| PR 文件 | depends_on | 状态 | worktree 分支 | 已合并 | 槛位状态 |
|---|---|---|---|---|---|
| pr-001-xxx.md | （无） | ⏸ | feat/pr-001 | ⬜ | 占用 |
| pr-002-xxx.md | pr-001-xxx.md | ⬜ | | ⬜ | 排队(依赖未满足) |
| pr-003-xxx.md | pr-001-xxx.md | ✅ | (已清理) | ✅ | 已释放 |
| pr-004-xxx.md | （无） | ❌失败(现场保留) | feat/pr-004(保留) | ⬜ | 已释放 |

## 待确认项

- [ ] {类型}：{描述}（见 {文档路径} §{章节}）

## 更新日志

- {日期}: {变更描述}
```

**`history` 字段取值**：只有 `开启`/`关闭` 两种取值，默认 `开启`（工作流启动创建 `status.md` 时写入该行）。该字段控制「历史记录协议」中 `history.md` 的创建与追加行为，具体规则见「历史记录协议」章节。

**状态符号**：`✅` 已完成 / `⏸` 进行中（未阻塞） / `⬜` 未开始 / `❌失败(现场保留)` 失败，worktree 和分支原样保留未清理 / `⏸阻塞(现场保留)` 阻塞，worktree 和分支原样保留未清理。`⏸` 单独出现时表示"进行中"；阻塞状态改用 `⏸阻塞(现场保留)` 这一更具体的取值，不再用裸 `⏸` 表示阻塞。

**槛位状态列取值**：`占用`（该 PR 的子 agent 正在执行，占用一个并发槛位）/ `排队(依赖未满足)`（依赖的 PR 尚未合并进主分支）/ `排队(等待槛位)`（依赖已满足但当前槛位已满，等待释放）/ `已释放`（该 PR 已判定完成，成功或失败均算，不再占用槛位）。

**worktree 分支列标注约定**：成功合并后清理的 PR 标注 `(已清理)`；失败/阻塞现场保留的 PR 标注 `(保留)`，例如 `feat/pr-004(保留)`——两者对比便于人工扫一眼区分现场是否还在。

### 主 agent 何时更新 status.md

- 工作流启动时：创建 `status.md`，所有阶段标记 `⬜`
- 每次派发执行角色前：将对应阶段标记为 `⏸`
- 每次阶段产物通过主 agent 验收后：标记 `✅`
- 阶段 5：每个 PR 并发派发时更新"PR 实现子状态"表对应行；merge 完成后标记"已合并"并重新扫描依赖解锁
- 每次独立验证（阶段 6）通过后：对应阶段"已验证"列标记 `✅`
- 每次出现待确认项：写入"待确认项"列表
- 每次用户确认后：勾选对应项，清空已解决的待确认项

## 历史记录协议（history.md）

`history.md` 与 `status.md` 并存、职责不同、格式互不侵入：`status.md` 是当前进度的快照视图（可被覆盖更新），`history.md` 是按发起顺序逐条追加的事件流水（只追加，不覆盖、不删除）。

### 落盘位置与创建/关闭时机

- **落盘位置**：`docs/iterations/{迭代ID}/history.md`，与 `status.md` 同级（见「文档路径协议」）。
- **创建时机**：工作流启动创建 `status.md` 之后（见「调度指南 § 启动工作流」），若该迭代 `history` 字段（见「状态追踪协议」）为开启，立即创建仅含一行标题 `# history.md — {迭代ID}` 的空文件——不等到第一次派发才惰性创建。
- **关闭时的行为**：
  - 启动时 `history` 即为关闭 → 不创建 `history.md`。
  - 运行中途 `history` 被改为关闭 → 已存在的 `history.md` 保留不删除，但主 agent 后续不再对其追加写入。

### 三类事件的记录格式

每条记录是一个三级标题 + 若干字段行：

```markdown
### {YYYY-MM-DD HH:MM:SS} · {事件类型} · {对象}

- {字段1}：{值1}
- {字段2}：{值2}
```

- **时间戳**：`YYYY-MM-DD HH:MM:SS`，本地时间 24 小时制，精度到**秒级**（不是日期级或分钟级）——同一轮响应内连续发起的多条记录很可能落在同一分钟甚至同一秒，只有秒级精度才能保留"大致何时发生"这一独立于顺序保真之外的信息量（顺序本身由下方「顺序保真约定」保证，不依赖时间戳）。
- **事件类型**取值三选一：`派发` / `收到报告` / `调度决策`。
- **对象**：派发/收到报告类填角色名（如 `architect`）；调度决策类填决策类别（`阶段推进核查` / `Gate确认` / `槛位释放` / `PR失败判定`）。

**派发类字段**（对应「派发执行角色时的 brief 构建」里已内联进 brief 的字段，只摘录不复制角色定义全文）：

```markdown
- 阶段：阶段 3（技术架构）
- 任务：在现有架构上演进，补全功能卡的架构维度，产出技术方案
```

阶段 5 额外加一行：
```markdown
- PR：prs/pr-{NNN-描述}.md
```

**收到报告类字段**：逐条摘录该角色「报告契约」已定义的编号/字段项，每项压缩为一句话结论值——不复制角色报告原文的解释性长文，只留判断性结论。字段序号与角色报告契约的编号严格对应，不合并、不跳过；对于非编号列表式的报告契约（如 `verifier` 用固定模板字段代替编号），改为摘录模板字段名+对应结论值，规则同源。

示例：
```markdown
### 2026-09-07 14:32:10 · 收到报告 · architect

- 1. architecture.md 路径：docs/iterations/0007-workflow-history-log/architecture.md；核心组件：history.md 记录协议、开关字段、三类事件格式、顺序保真规则
- 2. L1 决策清单：无
- 3. 新引入技术组件：无
- 4. 架构待填补全数：4（AR-01~AR-04）
- 5. 疑问/越界：无
```

**调度决策类字段**：至少包含"决策内容"和"触发依据"两个字段，"触发依据"必须是具体的触发条件、依据的文件路径或状态值，不是"因为需要"这类无信息量占位：

```markdown
- 决策内容：{具体决策是什么}
- 触发依据：{具体触发的条件、依据的文件路径或状态值}
```

示例：
```markdown
### 2026-09-07 14:33:00 · 调度决策 · 阶段推进核查

- 决策内容：阶段 3（技术架构）推进条件全部满足，进入阶段 4（PR 规划）
- 触发依据：L1 决策清单为空（architecture.md §L1 决策清单）；prd/F01~F04.md 的 `[架构待填]` 项均已补全为具体技术路径（architecture.md §prd 补全记录）；架构方案内部无冲突（architecture.md §验证）
```

### 顺序保真约定

不引入序号字段，不引入同步锁/写入互斥机制。`history.md` 的写入动作本身永远是主 agent 单线程顺序完成的，即使随后在同一轮 assistant 响应中并发发起多个 `Agent()` 工具调用（子 agent 的执行是并发的）——"记录这些即将发起的派发"这一步骤发生在发起 `Agent()` 调用之前，主 agent 依次调用文件写入工具追加多条记录，这些写入调用本身不并发。因此记录在文件中出现的物理先后顺序，天然等于主 agent 实际发起这些派发的顺序，读者从上到下阅读即可还原发起顺序，不需要额外排序字段。

**具体操作约定**：
- 阶段 5 同一轮响应内准备并发发起 N 个 `Agent()` 调用前，主 agent 先依次追加 N 条「派发」记录（记录顺序 = 即将发起 `Agent()` 调用的顺序），再在同一轮响应内发起这 N 个并发调用。
- 补位派发同理：先记录一条「调度决策·槛位释放」，再依次记录每个补位派发的「派发」条目——两者是相邻但独立的两条记录，不合并。

## 角色读取指南（执行角色读）

你被派发时，brief 里会包含：
1. **工作流文件路径**：`roles/workflow-pb/workflow-pb.md`
2. **当前迭代 ID**：如 `0003-user-profile`
3. **当前阶段编号**：如 `阶段 3`
4. **（阶段 5 专属）当前 PR 文件路径**：如 `docs/iterations/{迭代ID}/prs/pr-002-xxx.md`——阶段 5 的角色（planner、dev）只拿到单个 PR 文件，不拿到全部 `prs/` 目录

你的动作：
1. 读本文件"阶段定义"表，找到你负责的阶段行
2. **输入**：从"输入"列确定文档性质，路径 = `docs/iterations/{迭代ID}/` + 输入文档名
3. **输出**：从"输出"列确定文档性质，路径 = `docs/iterations/{迭代ID}/` + 输出文档名
4. **交付标准**："推进条件"列是你的完成定义
5. 读 `status.md` 了解当前进度和是否有待处理的上下文

**不要从自己的角色文件里找输入输出路径**——角色文件只定义能力，工作流定义契约。

---

## 原则

**工作流规范不定义执行细节**

本文件定义"做什么、交什么、满足什么标准"，不定义"怎么做"。执行细节由对应的执行角色文件定义。

**出口定义优先于流程顺序**

推进条件是每个阶段最重要的内容。顺序是结果，推进条件是原因。含糊的推进条件（"完成了就推进"）是未来返工的种子。

**不指定执行角色名**

本文件描述每个阶段的能力要求，不绑定具体的角色文件名。角色文件会迭代、会重命名，工作流的阶段职责应该稳定。

**约束和调度契约只存在于本文件一处**

提交管理约束（worktree 隔离、PR 文件前置）和并发调度逻辑只在本文件定义，不允许再拆出独立文件重复表达同一套规则——这是 v0.2.0 从"workflow-pb + workflow-scm 两处重复"吸取的教训。

---

## 何时更新本文件

- 某个阶段的推进条件导致下游返工 → 收紧该阶段的推进条件
- 某个阶段的职责边界不清导致执行角色越界 → 在对应阶段的职责描述里明确排除项
- 发现遗漏了某类工作（如 review）→ 新增阶段，不改动现有阶段
- PR 粒度判断导致执行角色产出与实际工作量不匹配 → 修订判断框架描述
- 依赖正确性验证出现误判 → 收紧判断规则
- 不得因"方便执行角色"而在本文件里加入执行细节
- 不得为图省事再拆出独立文件重复表达本文件已有的约束

变更历史写入 `data/workflow-pb-changelog.md`，保留旧版推进条件被修改的原因。
