# demand.md 变更历史

---

## v0.5.0（2026-09-15）

**需求**：用户看过 v0.4.0 交付摘要（demand.md 两段结构）的示例演示后，反馈摘要不够简明——希望能更清楚地说清四件事：项目边界（做什么）、实施方案（怎么做，要求明确具体方法，因为"做出需求的方法很多，但不是每条路径都是需要的"）、达到什么效果、验证方法。

**变更原因**：v0.4.0 的 Deliver 步骤只要求"第一段摘要 + 第二段摘要"，摘要结构直接照搬 demand.md 正文的段落划分（澄清依据 / 需求结论），不是为呈现给用户设计的结构——用户读到的是"哪些维度确认了什么"，不是"边界 + 方法 + 效果 + 怎么验证"这种可直接行动的四要素。另外原摘要格式里"方案雏形"只是罗列用户已有想法，没有要求交代"为什么选这条、否决了哪些候选路径"，导致方案选择的依据不透明。

**决策过程**：
- 用户最初的表述容易被理解为"demand 应该像架构师一样比较技术实现路径"——需要先澄清边界：demand 的红线是"不做架构决策"（技术架构阶段的职责），所以"实施方案明确方法"不能是 demand 自己发明或比较技术实现路径
- 收窄为可行范围：demand 能做、也应该做的是——当讨论过程本身已经出现多条候选路径、且已经在需求层面选定一条并否决其他时，摘要必须点名选了哪条、否决了哪条、为什么。否决路径本质上是"不做什么"的一种具体形式，属于需求边界的一部分，不是技术选型
- 最终确定四段摘要结构：边界（做什么/不做什么）、实施方案（选定方法 + 被否决路径及理由，若有）、达到什么效果（裸判定陈述）、验证方法（具体检查动作，不是主观感受词）

**具体改动**：
- Workflow 第 7 步（交付）重写：从"第一段摘要 + 第二段摘要 + 方案雏形摘要"三项改为「边界 / 实施方案 / 达到什么效果 / 验证方法」四段摘要
- "实施方案"一项新增要求：若讨论中出现过其他候选路径，必须点名被否决的路径和否决理由，同时明确这不是技术选型（技术选型仍留给架构阶段）
- 版本号从 0.4.0 升级到 0.5.0

**经验总结**：这次修改再次确认了 v0.4.0 changelog 里提到的经验——"更智能不等于更多规则"。这次的解法不是新增诊断维度或检查项，而是调整"结论怎么呈现给用户"这个交付层面的格式；同时守住了"不做架构决策"这条红线，把"方案选择的依据透明化"和"技术路径选型"两件事分开——前者是需求边界该管的（为什么选这条而不是那条），后者不是（哪条技术路径更优是架构阶段的判断）。

## v0.4.0（2026-09-15）

**需求**：用户反馈阶段 1（需求收敛）的用户沟通"感觉泛泛而谈"——目的性不够强、给用户反馈的空间不足、没有持续理解用户最新的输出。用户明确指导原则："不是让 demand 更复杂，而是让 demand 更智能"——不通过增加更多机械步骤/表单来解决，而是让它基于反射思考动态生成更有针对性的追问，围绕"边界"和"需求"本身深挖。

**变更原因**：诊断定位到根因不在 demand.md 本身的判断框架（六维诊断、提案确认循环这套逻辑已经足够），而在**执行架构**——此前 demand 是由主 agent 派发给独立子 agent 执行，子 agent 和用户之间隔着"主 agent 转达/汇报"这一层，导致：(1) 子 agent 收到的是主 agent 转述的起点材料，不是用户最新的原话，容易信息衰减；(2) 所有确认要先回报给主 agent 再由主 agent 转给用户，反馈链路长，用户体感"隔了一层"；(3) v0.6.0 引入的"全文注入 brief"机制虽然解决了机械项遵循度问题，但子 agent 执行期间用户仍无法直接参与调整。用 pb-v1-talk skill 的方法论（Gate 0 三要素确认 + 结构化讨论循环）做参考，确认"批量提问、每轮 3-5 个问题带推荐方案"的呈现方式比"逐条问答"更有目的性。

**决策过程**：与用户九轮讨论收敛，关键决策点：
- 最初倾向"让 demand 的提示词写得更细/更多检查项"——用户否决，明确"不是让 demand 更复杂，而是让 demand 更智能"，方向应该是提升反射质量和呈现方式，不是加机械步骤
- 定位到根因是执行架构（主 agent 派发子 agent）而非判断框架本身——子 agent 隔着主 agent 与用户对话，天然存在转达损耗和反馈延迟
- 确定方案：阶段 1 从"主 agent 派发 demand 子 agent 执行"改为"主 agent 内联执行"（不再走 `Agent()` 子 agent 派发），主 agent 直接以 demand 的判断框架和用户对话，去掉中间层
- 参考 pb-v1-talk 的 Workflow 结构（Gate 0 三要素确认 → Phase 1 调研 → Phase 2 结构化讨论，每轮 3-5 个问题带推荐方案），调整 demand Work 阶段的呈现方式为批量提问（同一轮草稿暴露的多个独立缺口一次性呈现，而非逐条来回）
- 停止条件从"六维诊断跑不出新缺口即自动收敛"改为"六维诊断跑不出新缺口是收敛信号，仍需向用户显式确认"——收敛的最终判断权在用户，不是六维诊断本身

**具体改动**：
- `relationship` 字段重写：去掉"主 agent 是决策者""对话确认回报给主 agent 做最终拍板"的子 agent 汇报语义，改为"由主 agent 直接内联执行、和用户直接对话，不存在中间层"
- `description` 字段调整："只在需要…阶段被主 agent 派发"改为"作为工作流阶段 1，由主 agent 直接内联执行（不派发子 agent）"
- Strategy「判断锚点」停止条件改写：六维诊断无新缺口降级为"可以收敛了"的信号，需向用户显式确认才算真正收敛
- Workflow 第 4 步（Work）新增批量提问指引：同一轮暴露的多个独立缺口一次性呈现（通常 3-5 个），只有后一个缺口依赖前一个答案时才拆开顺序问
- Workflow 第 7 步（交付）改写：不再是"按报告契约回报"，改为直接向用户呈现收敛结果摘要并确认
- 整节删除"报告契约"——该契约的汇报对象是主 agent，内联执行后不再需要独立的汇报格式，其内容（demand.md 路径、两段摘要等）已内联进 Deliver 步骤的描述里
- 全文其余"主 agent 确认/回报"表述改为"用户确认"（CRITICAL 声明、Tools 边界、原则红线、Safety 各一处）；仅 `relationship` 字段中描述执行架构本身（主 agent 直接内联执行）的两处"主 agent"保留，因为这里指的是执行者身份，不是汇报对象
- 版本号从 0.3.0 升级到 0.4.0
- 同步：`roles/workflow-pb/workflow-pb.md` 升级到 v0.11.0（阶段 1 由"派发"改为"内联执行"）、`.claude/skills/workflow-pb/SKILL.md` 同步升级到 v1.14.0

**经验总结**：这次修改的关键洞察是"更智能"不等于"更多规则"——demand.md 原有的六维诊断和提案确认逻辑已经是足够智能的判断框架，真正削弱沟通质量的是架构层的转达损耗（子 agent 隔着主 agent 和用户对话）。解法是拿掉这层间接性，让判断框架直接面对用户，而不是给判断框架本身加更多检查项。这与 v0.6.0"全文注入 brief"想解决的问题（机械项遵循度）是同一根因的两次不同应对——v0.6.0 是在"必须走子 agent 派发"的前提下尽量减少转达损耗，这次是直接判断阶段 1 不需要子 agent 这一层。

## v0.3.0（2026-09-05）

**需求**：用户提出 demand.md 目前只收敛"边界"（做什么/不做什么/为什么/达到什么效果），没有主动收敛"大致方案/方向"，导致后续 prd/architecture 阶段容易在大方向上偏移。具体例证：0005-pr-concurrent-execution 迭代收敛过程中，用户中途补充了"起始并发3，最大不超过2×3-1"这样的具体机制，但 demand 角色当时没有主动问，是用户自己想起来才补充的。用户要求"demand 有必要在执行的过程中询问，如果提及，则探讨/讨论（甚至需要调度其他角色提前沟通）。有点像提前开头脑风暴碰头会，把该聊的提前聊清楚"。

**变更原因**：v0.2.0 的五维诊断框架里没有一维专门检查"用户脑子里是否已有具体机制/约束的方案想法"，导致这类信息只能靠用户自己想起来在收尾时主动补充，而不是被 demand 角色结构性地在收敛早期引出。"大概怎么做"这条虽然在需求结论第二段里存在，但被当作一句话带过的弱检查点，没有对应的主动诊断动作。

**决策过程**：与用户四轮范围确认和提案迭代：
- 范围确认 A：用户最初提到"调度其他角色提前沟通"，经讨论明确为「修改需求，使用 demand 反射来实现，不调度其他角色」——即 demand 遇到需要技术可行性判断时，自己基于已有知识做反射式思考给出参考意见（类似 architect 会怎么看），而不是真的派发 architect 子 agent，这样范围收窄为纯 demand.md 协议升级，不涉及 workflow-pb.md 阶段定义改动
- 范围确认 B：用户明确"讨论"的形态是「话术/检查点变化」——不改变现有"草稿→提案→确认"多轮循环的格式/流程，只是新增开放性问题和检查点
- 范围确认 C：「主动问（每轮必查）」——"方案雏形"维度需要成为每轮必跑的主动检查项，demand 要主动问用户"你对这件事有没有已经想到的具体做法"，不能只等用户自己提及
- 范围确认 D：「现有五维需要微调」——新增维度后，现有五维的检查范围需要相应调整，不是无限期往后加第7/8维
- 提案确认：用户确认四点草稿更新——(1) 新增第六维"方案雏形"，主动逐条问；(2) demand 自我反射机制（"参考视角"子流程，有严格的写入限制——demand 给的意见不能直接进结论，只有用户吸收后自己确认的说法才进合同）；(3) 逻辑闭环、内部一致性维度扩展；(4) 成功标准和报告契约新增对应项

**具体改动**：
- 版本号从 0.2.0 升级到 0.3.0
- Strategy「判断锚点」从"五维诊断"升级为"六维诊断"：新增第 6 维"方案雏形"，主动检查用户对"怎么做"是否已有具体想法（机制/约束/参数/流程），每轮必查，收敛判据是问完所有"做什么"条目且用户明确表示"没有更多想法"
- Strategy 第 2 维"逻辑闭环"扩展：新增"方案雏形真的能达成已确认的效果吗"这个检查
- Strategy 第 4 维"内部一致性"扩展：新增"方案雏形和'不做什么'是否矛盾"这个检查
- Workflow Work 阶段新增"参考视角子流程"：demand 基于自身知识给出类似 architect 视角的参考意见，但只用于讨论过程，不写入结论段；用户基于参考意见调整或确认后的说法才作为 user_confirmed 写入"大概怎么做"
- 成功标准新增："草稿里每个'做什么'条目都经过一次'方案雏形'主动询问"
- 报告契约新增第 4 项："方案雏形/参考视角摘要（用户已有的具体想法 + demand 给出但未被采纳为结论的参考视角，如有）"
- 所有"五维"表述批量替换为"六维"

**经验总结**：这次升级揭示了 demand 角色的能力边界可以通过"自我反射"机制扩展——当需要跨阶段知识（如技术可行性参考）时，不一定要派发其他角色，demand 可以基于自身已有知识给出"参考视角"，但必须有严格的写入限制（不能直接进结论），这样既满足"提前把该聊的聊清楚"，又不违反"不做架构决策"红线。"方案雏形"维度和"参考视角"机制两者配合，形成了 demand 角色在需求阶段引出用户方案想法并辅助用户想清楚的完整能力。

## v0.2.0（2026-09-03）

**需求**：用户提出 workflow-pb 阶段1（需求收敛）的提问机制需要重新设计——目标是"排除歧义，也排除用户错误的需求"，过程要"基于上下文和对话持续思考，反射出新的问题"，是"沟通→清晰→再沟通→更清晰"的迭代，且"AI 要多反射思考，减少用户思考"。

**变更原因**：v0.1.0 的 Workflow 隐含模型是"列 3-5 个模糊点清单，逐条问完就收敛"。这个模型有两个根本缺陷：
1. 清单是静态的，一次性列出后不会随对话动态调整，覆盖不到执行过程中才暴露的新缺口
2. 提问方式停留在"追问、前提挑战、选项确认"的抽象描述，没有强制"AI 先给方案再让用户确认"，容易退化成把生成负担丢给用户的开放式提问

**决策过程**：与用户多轮讨论收敛，关键决策点：
- 用户明确要求"方向上是逐步趋近于让需求明确，有逻辑闭环，有边界，可实现，可验证"——这五个词被直接采纳为诊断维度（明确性/逻辑闭环/边界完整性/内部一致性/可验证性），取代原来偏形式化的停止条件
- 用户强调"排除用户错误的需求"不能靠列举触发信号（列不全就漏判），改为强制机制：每轮从已确认的"为什么"反推"应该做什么"，和用户给的"做什么"做差异比对，差异本身就是下一个问题的来源
- 用户最后一轮明确要求"问之后要带方案推荐，AI 多反射思考，减少用户思考"——这条把整个机制从"诊断出缺口→问用户"改成"诊断出缺口→AI 先给填法和理由→用户只做确认或纠偏"，用户输入负担从"生成答案"降到"看一眼对不对"
- 验证条件的可衡量性沿用方案 C（不新增字段，只加"裸判定测试"校验规则），不引入 Volere Fit Criterion 或 Given-When-Then 这类新概念，因为改动范围明确限定在"只改 demand.md"，不新增字段结构

**具体改动**：
- Strategy「判断锚点」从"两段有内容+model_inferred已确认+无冲突"改写为"五维诊断"：既是每轮生成问题的依据，也是收敛完成的判据（五维跑不出新缺口即收敛），废弃了原来固定的模糊点清单模型
- Workflow 新增「草稿 v0」概念（Align 阶段立即产出，哪怕大半是猜的），五维诊断的对象是这份实时更新的草稿，不是记忆中的清单
- Workflow 「工作（Work）」步骤的 Action 改写为强制"提案格式"：草稿更新+理由，用户确认或纠偏；无依据可推断时给 2-3 个限定选项+推荐，禁止空手开放提问
- 新增 CRITICAL：绝不用开放问题替代提案
- character 描述从"追问到底、不接受都可以"改写为"先反射思考、后提案确认"，与新机制对齐
