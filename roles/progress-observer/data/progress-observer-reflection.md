# progress-observer 反射依据记录

**创建日期**: 2026-09-02
**触发背景**: workflow-pb v0.2.0 重构（pr-planner + 依赖解锁式并发调度）完成后，用户提出需要迭代过程可观测性——PR 并发执行后，status.md 完全靠主 agent 手动维护，容易和实际 git 状态脱节。

## 根因案例

`docs/iterations/0004-model-dispatch/project-retrospective.md` P1 条目已经指出过一次同类问题："已验证"字段被泛化解释，声称的验证和实际证据（`clarifications/verify-*.md`）不一致。这次的问题是同一模式在并发场景下的放大版：PR 数量越多、并发度越高，人工维护的 status.md 和真实 git 状态之间的偏差概率越高。

## 反射过程

**核心任务类型识别**：不是"看 dashboard 汇报数字"，是"任何状态声明都视为未经核实的流水，必须拿一手记录核对一遍"。

**反射出的身份交叉**：财务对账稽核（银行流水 vs 总账不一致时只信银行流水）× 分布式构建系统依赖图故障排查（查"job B 声称等了 job A，但产物物理上不存在"的幽灵依赖）。这两种技能很少长在一个人身上——做稽核的人通常不碰 git ref，查依赖图故障的人通常没有稽核那种"绝不采信二次转述"的纪律。

**用户确认过程**：反射结果（identity/relationship/character/Strategy/输出契约）一次性确认通过，无调整，用户直接回复"没问题，请继续"。

## 与 verifier 的边界确认

verifier 判断"产物质量是否达标"（对象是单个产物）；progress-observer 判断"当前状态和声称的状态是否一致"（对象是整体迭代进度）。两者都不自证、都独立于执行过程，但问的问题不同，不是同一角色改名。

## 与主 agent 的调度边界

角色文件只定义"给定触发，怎么产出报告"，不定义"谁来触发、什么时候触发"——自动触发逻辑（每次 PR 合并/阶段推进后自动派发）写在 workflow-pb.md 的调度指南里，不写进这个角色文件本身，遵循 workflow-pb.md 已确立的权责分离原则（协调者定义调度契约，执行角色不描述自己在哪个调度关系里）。

## Verify → Fix 记录（第一轮独立验证）

第一次派发的无上下文子 agent 独立验证发现两处不通过项，五项内容层检查（占位符/原则内联/Strategy 具体性/harness循环完整性/能力边界区分度/反射留痕）和结构脚本检查全部通过：

1. **frontmatter description 违反权责分离原则，且与自己的反射依据自相矛盾**：description 里写了"由主 agent 按需或在 PR 合并/阶段推进后派发"这句触发时机描述，但 `workflow-pb.md` 明确写"触发时机（角色文件本身不描述这一点）"，且这份反射依据文档自己也在上一节写明"不写进这个角色文件本身"——反射的意图和最终落盘的产物不一致。Fix：删除 description 中描述触发时机的半句，只保留角色能力边界描述，补一句"触发时机由工作流定义，不在此描述"提示读者去 workflow-pb.md 找。
2. **输出契约第 5 部分命名在索引/模板/报告契约三处不统一**："发现的不一致清单"（索引）vs "发现的不一致"（模板标题）vs "不一致条数"（报告契约）。Fix：统一为"发现的不一致"，改索引处的标题去掉"清单"二字。

验证还标注了一条非阻塞的改进建议：identity 的战绩暗示是单次事件+具体数字（"一次…核实出3个…识别出2个"），规模化程度弱于项目内其他角色（如 dev 的"多个百万行代码库"、planner 的"30+次冲刺计划会"）。这条不计入不通过项，但顺手改成了跨场景累计的表述，强化战绩暗示的规模感。

## 第二轮独立验证结果（Reflect）

修复后重新派发一个全新的无上下文子 agent（不复用第一轮的子 agent）做第二轮验证，结论：全部通过。

- 两处遗留问题均确认修复到位：description 已删除触发时机描述，改为"触发时机由工作流定义，不在此描述"，与 workflow-pb.md 和本文件的反射依据三方一致；输出契约第 5 部分命名统一为"发现的不一致"，索引/模板/微循环回指三处完全同名
- 常规复检七项全部通过；identity 战绩暗示的修改被判定为"真实改进"（从单次事件+具体数字改为跨迭代累计规模+前后对比结构，与项目内其他角色的战绩暗示句式结构一致）
- 结构脚本检查、占位符、原则内联、Strategy 具体性、harness 循环完整性、能力边界区分度全部复检通过
