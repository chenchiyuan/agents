## 决策：F02"建议拆分为多个迭代"结论的呈现形式——仅报告文本 vs 落盘独立文件

比较过两个方案：
- **仅报告文本**：pr-planner 在报告契约里用文字描述拆分建议，不产生新的落盘文件。优点是不新增文件类型，改动面最小。
- **落盘独立文件（采纳）**：写入 `prs/split-suggestion.md`，仅当合并循环因违反原子性/可审查性锚点而受阻时创建。

选择落盘的理由不是"哪个实现更省事"（仅报告文本明显改动更小），而是与 workflow-pb 全篇贯穿的核心原则一致：
"文件系统是唯一真相，不采信执行角色的口头自称"（SKILL.md 对抗惯性表原文："子 agent 状态声明可信？文件系统是
唯一真相"）。这条原则目前只应用在阶段 5 的 PR 合并状态判断上，但本次面对的是同一类问题的另一个场景：阶段4→5
之间的方案确认门，本身就是要靠"读文件内容呈现给用户"完成的动作——如果"是否建议拆迭代"这条对用户决策至关重要
的信息只存在于 pr-planner 一次性的报告文本里，一旦会话中断、上下文被压缩，或者 verifier 需要在阶段6独立验证
时核实这条信息是否被正确呈现过，都无法找到依据。

这是一个非显然的判断：直觉上"建议"类的结论似乎适合用口头汇报承载（毕竟不是可执行代码或最终产物），但这次判断
的关键点在于——只要这条信息要跨越"pr-planner 这次执行"和"主 agent 之后的确认门呈现"这两个不同的执行阶段边界，
它就必须落盘，不能依赖同一个会话上下文的连续性。同时，"文件是否存在"这个二元信号本身也比"解析报告文本里有没有
提到拆分建议"更可靠、更适合被下游（workflow-pb 阶段4推进条件核查、方案确认门呈现逻辑）以确定性方式消费。
