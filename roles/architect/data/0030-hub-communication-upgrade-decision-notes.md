## 记录一：`reason` 归类的落点——消费侧唯一映射函数，而不是"在产生点分码"

这是本迭代唯一一处"更精确的方案被否掉、选了更保守的方案"的取舍（对应 prd 疑问 1 / MI-5 与 F04 验收 2/4/5）。

比较过两个方案：

- **产生点分码（直觉上更"正确"）**：给"agent 执行体失败"与"会话/子进程基础设施失败"分别产出不同的机器码（新增一个轮次级 `ProtocolError` 码），再由信封读取——这是唯一能让 `agent_error` 与 `infra_error` **语义精确**的做法，也直接呼应 MI-5 指出的"`agent_error` 无对应源字符串"。
- **消费侧唯一映射（采纳）**：既有失败产生点**零改动**，归类全部落在新增叶子模块 `src/reason.js` 的纯函数里（精确匹配 → 三条前缀规则 → 兜底），`agent_error` 明确为**兜底类**。

否掉"更精确"方案的关键证据不是"哪个更聪明"，而是三条**既有约束的叠加**：
① G01 验收 3 要求既有 `error` 的"键位、拼写、取值形态（**含既有文案**）不变"，F04 验收 5 同向；
② F04 边界明文"**不做既有错误文案的统一/重写**：`error` 原文保留"——把 `rpc prompt` 失败串从 `context_crashed` 改成新码，正是"改既有取值"；
③ 现状里 `context_crashed` 一族**既装会话崩溃、也装命令级失败**，想分开就必须同时扩展 `context-pool._failSession` 的"轮次级码集合"（否则轮次失败会被误当会话崩溃而**拆掉会话**）——一处改码会牵动会话生命周期判据，超出本迭代的必要范围。

采纳方案的代价已如实登记在 `architecture.md` §9-1 与 §4 A-04：消费侧归类是**近似**（`context_crashed` 一族整体归 `infra_error`），精确化路径（新码 + `_failSession` 集合扩展）列为跨迭代候选。同时补强了 MI-5 的结论：`executor:'omp'` 失败路径**直接透传 `err.message`**，形态不可穷举 ⇒ 纯枚举比对在数学上不可能完备，"显式兜底"不是补丁而是必要结构；`dispatch_failed` 也**不进入信封**（只落在对话 `out` 记录），MI-5 的"13 种"是字符串扫描口径，架构层收窄为"进入信封的 11 种形态 + 1 个开放文本来源 + 兜底"。

## 记录二：超时判据落在**既有实现处**，而不是新增一个 web 看门狗；并因此发现一处必须联动的既有旋钮

对应 F05（D-26~D-29），且是本迭代唯一一处**跨能力面（F01×F05）的真实冲突**，故记入。

- **需求侧**：D-26 要求判死由"固定 30 分钟总时长"改为"空闲为主判据 + 宽松安全网"，F05 验收 7 进一步要求"判据取代既有上限的**全部**生效位置"，并特别点名 `mode:block` 的路径（"上限在通道层不可绕"）。
- **候选一（更有"架构感"）**：在 web 侧新增一个**调用级看门狗**（按 `last_event_at` 判空闲、按安全网判总时长），到点由 web 调 `router.task_cancel` 落终态。它看起来更贴"调用级判死"的措辞，且集中在一处。
- **候选二（采纳）**：把**既有的轮次计时原语**（`acp-client` / `rpc-client` / `oneshot-client` 各一份同构实现，即既有 30 分钟绝对上限的唯一实现处）原地改为 `idle` + `net` 双计时，保留既有"门挂起冻结"语义。

选候选二的理由基于三条实测事实，而不是偏好：
① **"取代全部生效位置"的字面形态**：既有 30 分钟的生效处就在执行侧的四个默认值上，原地替换即天然覆盖全部路径（含 `mode:block`——它只是 web 侧挂起 HTTP，执行路径与 `background` 相同）；
② **避免第二判死源与僵尸轮次**：web 侧判死只能改 Router 任务表状态，**杀不掉 agent 侧那一轮**（进程仍在跑），会产生"终态已 failed、执行还在继续"的双事实；执行侧判死则走既有失败收口，一条路径、一个终态源；
③ **门挂起语义**：既有实现刻意在人工审批/提问等待期间**冻结**轮次计时（0029 L1-1）；判死逻辑若搬去 web 侧（看不见审批门），会让"等人工"变成"空闲"，直接回归一个已被修掉的旧缺陷。

**冲突（本次发现的真实问题，非本卡验收项）**：执行侧判死一旦放宽到 4 小时，web 侧既有的**对账登记软 TTL（默认 30 分钟）** 就会先一步把调用登记删掉；登记删除后迟到的 `task.result` 在 `handleDeliver` 查不到 `entry` 被**静默丢弃** ⇒ 终态永不发布 ⇒ 同时打破 F05 验收 6 与 **F01 的"必达"**。代码注释本身已自述这层耦合（"agent 侧 omp 超时上限亦为 30 分钟 ⇒ 覆盖关系由『有余』变为『持平』，待优化"）。

处置：作为 **L2-05** 自主决定（默认值改为 `taskNetMs + 30min`，env 覆盖保留），并在 `architecture.md` §10 疑问 B 显式提请主 agent 在阶段 4→5 门一并确认——理由是该改动跨越 F01/F03/F05 三张卡，虽属局部参数，但影响面不是单卡内部事务。

另：显式 `timeout_ms` 的语义**不改**（调用方声明的本轮绝对上限，含 30 分钟上限），只移除"缺省即 30 分钟"这一档；`shell` 路径的整体保留（命令硬上限是调用方期望的语义，与"推理空转"不是同一件事）。客户端等待预算（CLI/SDK 的 30 分钟）**不改**（`API.md` §2.4 明文"超时只表示放弃等待"），后果登记在 `architecture.md` §9-6（长任务的 `--wait` 会先 `timed_out:true`，结果仍可经取件面拿到——F05 与 F01 的协同，不是冲突）。
