## 决策 1：既有库的加字段——按列存在性守卫的幂等 ALTER vs 引入版本号迁移机制

比较过两个方案：
- **`PRAGMA user_version` + 迁移表**（行业常见做法）：给数据层加一套"版本 → 迁移脚本"的机制，`openDb` 按版本号决定跑哪些迁移。
- **按列存在性守卫的幂等 `ALTER TABLE`**（采纳）：`migrate(db)` 用 `pragma_table_info('chats')` 查该列是否存在，缺则 ADD；每次 `openDb` 都跑，第二次起全部 no-op，不写任何版本号。

选择后者不是因为它"更简单"，而是因为**这两条 ALTER 所需的全部状态就是"列在不在"**。版本号机制会引入第二处真相：以后有人改 SCHEMA 忘了加版本条目，迁移会被静默跳过，而列存在性守卫不可能出现这种"机制与事实脱节"。同时它天然满足两个硬约束：① 幂等（守卫是事实而非记账）；② 新库与迁移库同构（新库由 SCHEMA 建成同样两列，且必须声明在 `closed_at` 之后，与 `ADD COLUMN` 的追加语义对齐——`persist.test.js` 的列名断言是顺序敏感的，列序错了迁移库与新建库就过不了同一条断言）。

再评估条件写进架构 §15 R-2：迁移条目超过约 5 条或出现破坏性变更（改列类型 / 拆表）时，再引入版本号。

## 决策 2：列表双视图——单条语句 + 条件排序键 vs 拆第二组 SELECT/COUNT

比较过两个方案：
- **拆第二组语句**：`listArchivedChats` + `countArchivedChats`，各自 ORDER BY，语义直白。
- **仍用单条语句**（采纳）：CTE 加第 6 个槽 `archived`，`LIST_FROM` 加互斥谓词，排序改为 `ORDER BY (CASE WHEN p.archived = 1 THEN c.archived_at ELSE c.updated_at END) DESC, c.chat_id DESC`。

现有代码有一条明确的不变式："单条预编译语句覆盖全部查询组合"，且 `listChats` 与 `countChats` **共用同一个 `LIST_FROM` 与同一份参数数组**。拆第二组语句会让 `total` 与列表有分叉的可能（两处 FROM、两份参数），而归档视图的翻页恰恰把 `total` 当"是否还有更多"的判据——分叉的代价是"加载更多"按钮出现/消失错判。用 CASE 表达两种排序把这条不变式保住了；代价是排序走不了索引（架构 §15 R-2 已写明量级判断与再评估条件）。

这个判断的反直觉之处：一般会认为"两种视图 = 两条 SQL"，但这里的视图差异只有**一个过滤谓词 + 一个排序键**，共用一个 FROM 的价值（total 恒一致）高于拆开后各自直白的价值。

## 决策 3：奥卡姆剃刀与产品需求的真实冲突——为一条 UI 提示落一个库列

**冲突**：本迭代的每个新增实体都过了"不引入它，哪个功能无法实现"的检验，唯独 `chats.context_released` 卡住：F05 验收 6 经用户确认的口径是"激活后打开该对话可见提示，**持续显示直到该对话产生新的回答后自动消失**"。纯前端内存标记（激活时记一份、刷新即丢）能满足"点激活 → 打开对话 → 看到提示"的验收动作，却会在"激活 → 刷新页面 → 尚未提问"的窗口里提前消失，违反确认过的持续期。

**取舍**：采纳一个 `INTEGER NOT NULL DEFAULT 0` 的列（归档置 1、激活不动、`insertOutput` 置 0），把这条"为 UI 服务"的状态落库。这是本次唯一一个不能只靠"前端内存 + 既有数据"推出的新实体，因此按角色契约记在这里并在架构 §13 K-2 / §15 R-4 明确标为 L2 取舍、给出退回方案（退回代价 = 提示跨刷新不再重现，与 M-04 口径不符）。

**这条记录的意义**：奥卡姆剃刀检验的正确用法不是"能少一个实体就少一个"，而是"问清楚不引入它到底是**哪个**行为不成立"。这里不引入它的代价被产品口径显式认定过（用户确认的持续期），所以它通过检验；反过来，如果产品只要求"激活后当场提示一次"，这一列就该被删掉。
