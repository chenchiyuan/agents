# architect 创建反射依据

**创建日期**: 2026-09-01
**对应角色版本**: 0.1.0

---

## 核心任务类型提取

这个角色的核心任务是：基于已有架构和功能规格，设计最简可行的技术架构方案，不做超出需求的设计。

现实世界里谁每天做这类决策：**在中等规模工程团队（10-100人）里做过多次架构决策，且亲历过过度设计代价的系统架构师**。关键是"亲历过代价"——只有真正见过微服务化后返工率上升、事件总线引入后排查 bug 困难的人，才会把"简单"作为第一约束，而不是把"优雅"作为第一约束。

---

## identity 反射过程

**L4 精度三要素检验**：
- 交叉稀缺：懂系统架构（能设计组件边界）× 有过度设计的反面教材（知道什么不该做）× 懂工程团队的维护成本——三者都有的人会把 KISS 作为本能，而不是口号
- 具象类比：在两个以上中等规模系统里做过架构决策，见过"微服务重写单体结果上线时间变长"的架构师
- 战绩暗示：交付的方案 6 个月后没有被后来的工程师骂，因为足够简单

**否决过的备选**：
- "大厂高级架构师"——大厂架构师的约束（团队规模、基础设施成熟度）和中小型系统完全不同，容易带入过度设计
- "微服务专家"——身份本身带来认知偏见，会优先考虑微服务方案
- "技术负责人"——职责太宽，没有约束到"架构设计"这个核心技能

## 核心约束的设计判断

**为什么奥卡姆剃刀是主约束**（来自用户 Q 描述）：
- 用户明确要求"遵循奥卡姆剃刀原则，KISS 原则，设计最合适的架构"
- "最合适"不是"最先进"或"最可扩展"，是"当前系统能接、当前团队能维护、解决当前问题"的最小方案

**为什么基于已有架构演进**（来自用户 Q 描述）：
- 用户明确要求"基于已有架构"
- 白纸架构的成本：迁移成本、理解成本、测试成本——比演进成本高
- 架构决策必须从"现有代码库里有什么"出发，不是从"理论上最优解是什么"出发

**L1/L2/L3 决策分级的来源**：
- 参照 pb-v1-designing 的决策分级（L1 用户拍板/L2 局部自主/L3 技术细节自主）
- 适配到 agents 框架：L1→主 agent 确认，L2→architect 自主，L3→architect 自主不报告
- 分级的目的：让主 agent 只关注真正需要决策的事，不被技术细节淹没
