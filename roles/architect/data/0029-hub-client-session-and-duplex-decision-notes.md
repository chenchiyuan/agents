## 记录一：三态承载形态——独立字段（`connected`）而不是既有状态词的第三取值

**这是 D-18 / prd 疑问 5 明确交给本阶段的选边**，也是本迭代唯一一处"简单方案 vs 直觉上更贴需求原文的方案"的取舍。

比较过两个方案：

- **既有状态词加第三取值 `reconnecting`（直觉方案）**：demand 原文写的是"`agents` 必须能区分 `online` / `reconnecting` / `offline`"，加第三取值看起来是"照需求原文实现"，读代码的人也一眼能在 `state` 里看到 `reconnecting`。
- **独立字段（采纳）**：`state` 词表保持 `online` / `offline` 二值不动；新增 `connected: boolean`，三态由 `state` + `connected` **派生**（在线 = online ∧ connected；重连中 = online ∧ ¬connected；离线 = 既有墓碑）。

选择独立字段的关键证据不是"哪个更优雅"，而是**第三取值会改掉既有可观察行为**（事实 F-11 的实测）：
① 服务端 `GET /api/agents?state=online` 的判据就是 `state === 'online'` —— 加第三取值会让"重连中"的实例被该过滤排除，直接违反 G01 验收 3（既有实例状态过滤参数的既有行为不变）；
② 既有控制台 `web/app.js:renderAgentPanel` 客户端**也**按 `state === 'online'` 过滤 —— 第三取值会让"正在回来"的实例从顶栏列表**消失**，恰好制造 F16 要消灭的那类误判（"正在回来"与"已经死了"混为一谈）；
③ `state` 是 Router 租约机的状态位（`register` / `heartbeat` / `findExpired` / `markOffline` 的分支判据），第三取值会侵入租约核心模块；
④ 仓库既有取向是"同一事实不落两处"（0016 的元数据体例：是否有请求体由 `params` 派生、不另设布尔位），三态可由既有 + 一个新增字段派生，故不新增三值字段。

**代价已如实登记**：`reconnecting` 不会作为字面取值出现在载荷里，调用方需要按 `API.md` 记录的派生口径读三态；为此在 `architecture.md` §4 A-13 与路由元数据的 `response` 字段里把口径写死（避免"能区分但没人知道怎么读"）。

## 记录二：两处端点命名偏离 demand §大概怎么做 的字面形态

- `GET /api/events?principal=&kinds=&agents=` → **`GET /api/subscribe`**；
- `GET /api/inbox` + `POST /api/inbox/ack` → **`GET /api/pickup` + `POST /api/pickup/<call_id>/ack`**。

订阅面的理由：既有 `GET /api/events` 是**无参、4 类事件**的全局面，把新面的 7 类事件塞进同一路由会让"既有 4 条推送面的事件类集合逐字不变"（G01 验收 1 的判定方式就是比对面上的事件类集合）从**结构保证**退化成**条件保证**——同一路由在"不带参"与"带参"时是两套词表，6 个月后的工程师读不出该按哪套理解。

取件面的理由：`inbox` 在本仓已经被占用——既有 `src/inbox.js` 是**在途确认项表**，控制台第三栏就叫"待确认 inbox"，全局 `confirmation` 帧也挂在它上面；再用 `inbox` 命名"未取件的终态结果"会让同一术语指两件不同的事。

选择偏离而非沿用字面名的依据：prd 在"架构待填汇总"的前言里明写"「大概怎么做」给出的端点路径与参数名只作**来源引用**，其最终形态属架构面"。已作为 **O-1** 在 `architecture.md` §11.2 声明，并写明"若要求贴回字面路径，改动成本 = 3 处字符串（路由 path + 入口 cmd + 文档行），语义设计不变"——即这是一处**可低成本回退**的偏离，不是不可逆判断。

## 记录三：奥卡姆剃刀与需求之间的真实冲突——F16 验收 2（软重启窗口的"重连中"可见性）

这是本迭代唯一一处**剃刀原则与验收条文直接冲突**的地方，故按"真实冲突"记入。

- **需求侧**：F16 验收 2 要求"只重启 hub、保留 agent 进程 ⇒ **在快照中可观察到**该实例先处于'重连中'、随后回到'在线'（不是'直接消失'或'直接在线'）"；验收 5 同时要求"重启后的快照中不出现指向已丢失调用登记的'在跑'投影"——后者只有在"重启后的视图里**确实存在**这些实例的行"时才有约束对象，两条合起来指向"重启后的 hub 应当知道重启前在册的实例"。
- **现实侧**：Router 的注册表与任务表**全在内存**，hub 重启后名册为空；而"重连中"的自然判定（`state='online' && !connected`）依赖**Router 还在记得这个实例**。于是纯派生方案下，软重启窗口里实例只能"直接消失 → 直接在线"，**验收 2 的字面要求无法满足**。
- **剃刀侧**：满足它必须引入一个**新的运行态产物**（`<包根>/.runtime/roster.json` 名册提示：web 在正常退出与每次投影时写、启动时读），这与本迭代"内存登记、重启即丢"的既有口径（D-3/D-4）和"不把 hub 记忆当恢复依据"（不做什么#4）**相邻**——所以我没有自行拍板。

处置：列为 **L1-01 待主 agent 确认**，同时给出建议（纳入）与**完整回退口径**（否决则"重连中"仅在 Router 存续的窗口可观察，F16 验收 2 需由主 agent 收窄措辞——**不由我改卡**）。并在设计里把提示的边界写死：只带实例 id、不含任何在跑投影（满足验收 5）、宽限期复用既有 `heartbeatTimeoutMs`（不新增配置键）、明确"仅用于重启窗口的视图呈现，不作为任何恢复依据"。

## 记录四：取件面拒绝"游标"与"正文副本"两个提案形态

提案（`docs/hub-bidirectional-delivery-proposal.md` P-C）给了 `since=<cursor>` 与 `/api/inbox/ack {principal, cursor}` 的形态，本方案**不采纳**：

- **不存正文副本**：F07 验收 5 明写"取件面不是第二真源"，正文改为读取时经既有 `router.task_get` 现算——代价是 N 条未取件 = N 次 UDS 查询（已在 `architecture.md` §10 R-3 登记，未取件集合由调用方取件即确认而自然收敛）。
- **不引入游标**：游标会把语义从"**未取件**的结果"改成"**自某位置以来**的结果"，与 F07 验收 2（未取件不消失）正交却增加客户端状态与理解成本，且没有一条验收项要求它；未取件集合天然有界且小（YAGNI）。若将来集合变大，分页/游标是下一迭代的事，本轮不夹带。
