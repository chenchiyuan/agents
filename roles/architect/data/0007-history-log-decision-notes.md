## 决策 1：history.md 创建时机——启动时立即创建 vs 首次事件惰性创建

比较过两个方案：
- **惰性创建**：首次派发/收到报告/调度决策发生时才创建 history.md。优点是"没有事件就没有文件"，逻辑更直觉。
- **启动时立即创建**（采纳）：工作流启动、`history` 开关为开启时立即创建空文件。

选择启动时创建的理由不是"哪个更简单"（两者实现复杂度几乎相同），而是**可观测性**：文件是否存在本身可以作为"该迭代 history 开关是否开启"的信号，不需要读 status.md 内容才能判断。这是非显然的判断——直觉上"惰性创建"更符合"按需产生"的简单直觉,但会让"文件不存在"这个状态同时对应"开关关闭"和"开关开启但还没发生任何事件"两种不同含义，产生歧义。启动时创建消除了这个歧义。

## 决策 2：并发场景顺序保真——序号字段 vs 依赖物理写入顺序

比较过两个方案：
- **序号字段**：每条记录加一个递增序号（如 `#0007-015`），显式标注顺序。
- **依赖物理写入顺序**（采纳）：不加任何顺序字段，依赖"history.md 写入动作本身是主 agent 单线程顺序完成"这一技术事实。

这是奥卡姆剃刀检验的典型案例：先问"不引入序号字段，F04 哪条验收标准无法满足"——逐条核对后发现四条验收标准（各自独立记录、顺序与发起顺序一致、可交叉核对、补位派发不合并）全部只依赖"文件里条目出现的顺序"，不依赖"条目携带的顺序标注"。因为并发只发生在"子 agent 执行"层面，"写 history.md"这个动作本身在主 agent 侧永远是顺序完成的（不存在两个主 agent 实例同时写同一文件的场景），所以文件的物理行序天然就是发起顺序，序号字段是纯冗余信息。

这个判断依赖一个不那么显然的架构洞察：**"并发调度"和"记录并发调度的动作"是两个不同的执行层，前者并发、后者永远顺序**——如果不明确拆开这两层,容易直觉地认为"并发场景需要额外的顺序保证机制"，从而过度设计。
