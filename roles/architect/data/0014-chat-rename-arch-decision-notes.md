## 决策 1：改名写口的返回值形态——`string | null`（而非 `boolean` + 回读）

需求层已锁定"只写 `title` 一列、不复用 `upsertChat`"（demand D-13），所以语句本身没有取舍空间。真正的判断在**包装函数的返回值**上，比较过三个方案：

- **返回 `boolean`**（与既有 `closeChat`/`archiveChat` 同家族，最"一致"）：但 web 侧需要响应里带上"写入后的权威标题"。要拿到它只能 ① 再 `getChat` 读一次库（多一次查询）或 ② 在 web 里重新 `trim` 一遍（**第二处归一逻辑**，将来必分叉）。两条都不好。
- **返回 `{ ok, title }`**：信息完整，但引入了与 `closeChat`/`archiveChat` 不同的返回形状，且多一层解包——为一个单列写入造一个结果对象。
- **返回 `string | null`**（采纳）：`null` = 未写入（不存在 / 已归档 / 已关闭，即 `changes === 0`），字符串 = 已写入的 trim 后权威标题。一次语句同时给出"是否写入"与"写了什么"，web 零额外查询、零第二处 trim。

选它的理由不是"更聪明"，而是**它把 `changes` 校验和一个真实需求（响应要回权威标题）压成了同一个返回值**。`boolean` 方案看着更一致，代价是把归一逻辑复制到第二层去——而 F02 的三条校验规则只允许有一个落点（验收 6）。

`changes === 0` 在本方案里必然被翻译成 404/409，**不存在"改了但没成功却报 200"的静默失败路径**——这正是 demand C-2 要防的那件事。另附实测（`node:sqlite` 直接验证，非推断）：SQLite 的 `changes` 按**命中行数**计，新值与旧值相同时也计 1 ⇒ 同名重复改名是幂等成功（无任何可观察状态变化），不是失败。若当时按 MySQL 的直觉（同值更新返回 0）写这段契约，就会凭空造出一条错误的失败分支。

## 决策 2：改名成功后的同步——就地更新 vs 重新拉取

比较过三个方案：

- **`loadChats()` 全量重拉主列表**：最"保险"，但改名不改排序键、不改 `message_count`、不涉归档视图 ⇒ 拉回来的数据与内存里的**逐字相同**，换来一次往返 + 整列表重排闪烁。
- **`refreshChat()` 重拉详情**：只多一次请求，同样没有任何字段会变。
- **就地回填**（采纳）：`state.chat.title` + `state.chats` 命中项 + 一次 `renderChats()`/`renderChat()`。

采纳就地更新的关键在于**"不置顶"不是前端保证的**：它由写入语句不碰 `updated_at` 结构性保证，前端重拉与否都不影响位置。既然位置无关，重拉唯一的收益就只剩"确信内存与服务端一致"——而这次改动写入的值恰好就是服务端响应里回来的那一个（决策 1）。另外它保住了既有数据流的一条不变式："主列表只在 `loadChats()` 时刷新，不由 SSE 驱动"（0013 S-6）。为改名单开一条"偷偷全量刷新"的路径，会让以后读代码的人多一个"列表什么时候会变"的分支。

代价写进架构 §15 R-4：若该对话不在当前主列表页（第一页 50 条之外），左栏不会闪现新标题——但那一项本来就不可见，符合 M-06 的"当前可见列表中的对应项"。

## 决策 3：Esc 优先于失焦的实现——状态门控 + 调用顺序（而非 `cancelled` 标志位）

需求 D-11 要求"Esc 取消优先于失焦"。技术上有两条常见路子：

- **`cancelled` 标志位**：Esc 置位、`blur` 处理器见位即 return 并复位。
- **`state.titleEdit` 单一门控 + 先清 state、再复位 DOM**（采纳）：`exitTitleEdit()` 的第一行是 `state.titleEdit = null`，之后才隐藏 input；随后**必然发生**的 `blur` 在 `commitTitle()` 首行 `if (edit === null) return` 被挡掉。

选后者的理由：编辑态本来就**已经**需要一个状态（"编辑中不被 SSE 重渲染覆盖输入"必须靠它，见 `renderTitle` 的 early-return）。既然已经有这个门，`cancelled` 就是为同一件事造第二个状态——两个状态就有"谁先复位"的时序问题。用一个门 + 明确的赋值顺序，把"Esc 之后不会再补一次保存"变成读一遍函数就能确认的事实，而不是"两个标志位的组合推理"。

顺带定死了一个容易踩的坑：Enter 提交后隐藏 input 也会触发 `blur`。因为 `commitTitle()` 进入即清 `state.titleEdit`，第二次调用在首行返回 ⇒ 一次编辑**恰好一次**提交。这个"清 state 在前"的顺序同时覆盖了 Enter-后-blur、Esc-后-blur、失败-后-blur 三种情形。

## 决策 4：非乐观更新——选了"更简单"而不是"更爽"的方案

`commitTitle()` 的时序是：**退出编辑（h1 回到原值）→ 发请求 → 成功才回填新标题**。本地回环往返约毫秒级，所以用户其实看不到中间那一帧；但在"响应慢"的假设下，这个顺序意味着短暂显示旧标题（先退后进）。

- **乐观更新**：先 `chat.title = next` + 渲染，再发请求，失败回滚（需要暂存"保存前的值"并在失败分支恢复两处）。
- **非乐观**（采纳）：显示值只有一个写入点（服务端响应回填），"失败恢复原值"这条需求**零额外代码**——因为 `exitTitleEdit()` 已经把 h1 还原成 `chat.title`，而该字段只在成功路径被改写。取消 / 拒空 / 未改动 / 失败四条路径共用同一个恢复动作。

按"可测试 > 可读 > 一致 > 简单 > 可逆"的顺序裁决：两条在可测试性上等价（都能断言最终值），可读性上非乐观少一个"保存前的值"状态，所以选它。代价（慢网络下的一帧旧值）明确记进架构 §15 R-3，并写明若主 agent 要求瞬时感，改成乐观更新是 4 行 + 一个分支的可逆改动。

**顺带记下的一个"看起来该做但没做"**：本迭代**没有**给 `chats.title` 加 `CHECK(length(title) <= 100)`。不是没想到，而是 SQLite 加约束必须整表重建（12 步 CREATE/COPY/DROP/RENAME），而本次的写入点唯一且已内建校验 ⇒ 约束的收益（防未来调用方越界）被"写口自校验 + 唯一调用方"等价覆盖，成本却是一次真实的数据迁移。这个取舍的前提是**写入点唯一**：一旦将来出现第二个写 `title` 的路径，就必须复用 `readTitle()`（架构 §3.3 与代码注释都已写明）。
