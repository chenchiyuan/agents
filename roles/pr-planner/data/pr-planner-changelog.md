# pr-planner.md 变更历史

## v0.2.0（2026-09-15）

**触发**：此前 PR 粒度判断只覆盖"文件范围不重叠""逻辑原子性/可审查性/独立性"三条锚点，缺一条显式检查"拆出来的 PR 真的能并发执行"——存在拆了但和所有其他 PR 都有依赖路径、实际只能串行的候选拆分点未被拦截的风险。

**方案**：新增"并发可行性"判断维度——Strategy/判断框架章节新增"并发可行性（推进条件）"子章节：拆出一个独立 PR 前，必须能在依赖图上找到该 PR 与至少一个其他 PR 的并发重叠窗口（两者互不为对方的祖先/后继），否则判定为"反向实践"，须合并回其他 PR 或调整依赖关系，不单独拆出。并发重叠窗口的计算方法采用依赖图可达性判定，复用已有 `depends_on` 依赖图，不引入时间调度模型。

**具体改动**：
- Strategy/判断框架章节新增"并发可行性（推进条件）"子章节
- Workflow 的 Verify 阶段同步新增对应检查项
- 版本号从 0.1.0 升级到 0.2.0

**不改变的部分**：PR 文件七字段格式；`depends_on` 的证据标准（代码级引用，不采信文档顺序）；依赖图有环时的上报处理方式。

## v0.3.0（2026-09-15）

**触发**：0025 迭代的真实案例（`pr-001→pr-002→pr-003→pr-004→{pr-007,pr-008,pr-009,pr-010}`，关键路径长度 5）证明此前的三条粒度锚点和 v0.2.0 的并发可行性检查都是逐个/逐对判断——每一对局部依赖判断都合理，但没有一条约束"整条依赖链有多深"，链条整体可无限累加，实际执行时被迫串行等待。

**方案**：新增"关键路径长度（Work 阶段硬约束）"判断维度——定义为依赖图最长链节点数（复用已有 `depends_on` 依赖图，不引入工时估算），硬上限 3，检查时机在 Work 阶段（不是仅 Verify 阶段事后核查），超限时执行四步合并循环：计算关键路径长度→在关键路径上按"B 的验收标准必须等 A 的产出才能判断"排序取最优候选对→对候选对做合并前置检查（是否违反逻辑原子性/可审查性锚点）→不违反则合并回步骤1重新计算，违反则立即停止循环并转出"建议拆分为多个迭代"结论。转出结论落盘为 `prs/split-suggestion.md`（仅触发时创建），包含拆分边界算法（以触发违反的相邻对为分割点，下游划入迭代2，其余划入迭代1）。

**具体改动**：
- Strategy/判断框架章节新增"关键路径长度（Work 阶段硬约束）"小节，插在"PR 粒度判断锚点"之后、"并发可行性（推进条件）"之前，含"合并受阻：建议拆分为多个迭代"子节
- Workflow §4 Work 阶段追加"关键路径压平"段落；§5 Verify 新增对应检查项
- 成功标准、报告契约（新增第 5 项）、红线（绝不）、Tools and capability boundaries §不做什么、决策记录判断标准，五处各新增一条
- 新增"v0.3.0 变更说明"章节（正文）
- 版本号从 0.2.0 升级到 0.3.0

**决策过程**：关键路径的度量方式在"依赖图最长链节点数"与"预估工时求和"两个候选方案中选择前者——前者直接复用 pr-planner 已有的 `depends_on` 图结构，后者需要新增工时估算字段（现有七字段格式之外的新数据），属于不必要的实体膨胀，与 v0.2.0"并发可行性"维度已经做出的同一选择保持一致。"建议拆分为多个迭代"结论的呈现形式在"仅报告文本"与"落盘独立文件"两个候选方案中选择后者——落盘后"文件是否存在"本身可作为无歧义的判断信号，且不会因会话中断或上下文压缩丢失这一关键决策信息。

**不改变的部分**：PR 文件七字段格式；`depends_on` 的证据标准（代码级引用，不采信文档顺序）；依赖图有环时的上报处理方式；v0.2.0 新增的"并发可行性"判断维度及其检查时机（Verify 阶段）。
