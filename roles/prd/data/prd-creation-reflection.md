# prd 创建反射依据

**创建日期**: 2026-09-01
**对应角色版本**: 0.1.0

---

## 核心任务类型提取

这个角色的核心任务是：将需求合同拆解为工程师可以直接对照验收的原子功能规格卡（产品维度，不含架构维度）。

现实世界里谁每天做这类工作：**在早期 B2B SaaS 产品里跨过"第一个 10 个客户"阶段的产品负责人**——需要写出工程师不需要追问就能交付的 spec，且 spec 不能越界包含技术决策（因为技术决策是工程师的责任）。

---

## identity 反射过程

**L4 精度三要素检验**：
- 交叉稀缺：懂产品逻辑（能写用户价值）× 懂工程接口（知道"验收标准"和"技术选型"的边界）——两者都有的人能写出不越界的 spec
- 具象类比：B2B SaaS 产品里写过被工程师当做唯一判据的 spec 卡的产品负责人
- 战绩暗示：返工率低，不是因为写得够长，是因为"不包含什么"写得和"包含什么"一样清楚

**否决过的备选**：
- "BA（业务分析师）"——偏咨询流程，不聚焦功能卡粒度
- "需求工程师"——太偏系统工程，暗示会做架构决策
- "产品经理"——太泛，没有约束到"写可测试的 spec 卡"这个核心技能

## 产出结构的设计判断

**为什么是二级结构（prd.md + prd/*.md）**（来自 CLR-ROLE-004）：
- `prd.md` 作为索引，让主 agent 一眼看到本次迭代的全貌（功能列表 + 边界）
- `prd/*.md` 每功能点独立，让 architect 和 planner 可以精确消费单个功能点，不需要在一个大文件里定位
- 用户在讨论中明确要求二级结构

**"原子功能卡"的粒度判断**：
- 能独立测试 + 能独立交付 = 粒度合适
- 不是"功能越细越好"——过细会把架构决策拉进产品维度

**为什么架构维度留空**：
- 产品维度和架构维度是两个不同的职责域
- prd 角色写架构决策 = 给 architect 角色设了隐性约束，且这个约束没有经过架构审查
- 正确做法：标注 `[架构待填]`，由 architect 角色填写
