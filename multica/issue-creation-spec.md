# Multica Issue/任务新建规范

**版本**: 1.0.0
**制定日期**: 2026-10-28
**适用范围**: 在 Multica 工作区中新建 issue/任务的所有场景（人工或 agent 创建）
**来源**: 讨论自 POWERBY-10（陈驰远提出"研究并提出新建规范"的需求）

---

## 一、问题背景

用户发布的任务通常是口语化、零散的表达（例如"调研 pushdeer"、"新增智能体破甲"）。这种表达直接变成 issue 标题和描述时，会丢失验收标准和边界条件，导致：

- 执行者（agent）不知道做到什么程度算完成，容易自认为完成就转 `in_review`
- 不该立刻执行的讨论性任务（如本次"先讨论不要落地"）被直接执行
- 子任务/stage/property 等结构化能力长期闲置，issue 退化成纯文本聊天记录

本规范解决的问题：**把口语化需求反射理解为结构化 issue，但不替用户做决定** —— 结构化结果必须经用户确认才能真正落地执行。

## 二、核心原则

1. **反射不替代确认**：根据口语化输入推理出的标题、描述、状态、拆分方案，都是草案（`model_inferred`），必须展示给用户，用户认可后才创建或推进。
2. **描述要能回答"做完是什么样"**：没有验收标准的 issue 不算完整的 issue。
3. **状态即触发器，不是标签**：`todo` 对 agent-assignee 会立即触发 run；创建时选错状态等于提前执行了不该执行的任务。创建前必须想清楚这一条，而不是创建后才发现。
4. **拆分有成本**：子任务/stage 只在"需要独立验收"或"需要阶段屏障"时使用，不为了显得规范而拆分。
5. **结构化字段优先于正文堆砌**：能用 property/priority/due_date 表达的状态，不要塞进描述文本当自然语言。工作区尚无自定义 property 时，先在描述里用固定小节占位，不绕过去发明新的非结构化约定。

## 三、必备结构

### 3.1 标题（title）

- 格式：`动作 + 对象/范围`，一行内看出产出物，不堆过程说明（"讨论"、"不要落地"等放描述）
- 不加 Markdown H1，标题本身是 H1

### 3.2 描述（description）固定小节

```markdown
## 用户原始需求
<原话或忠实转述，不改写丢失信息>

## 目标 / 验收标准
<做完是什么样才算完成；没有可验证标准的任务必须先补充，不能留空>

## 边界 / 不做什么
<尤其是"仅讨论不落地""不改配置""不读取其他文件"这类约束，必须显式写出>

## 相关资源
<涉及的仓库/项目/文件路径，用仓库内相对路径，不写本地绝对路径>
```

四个小节都要有；没有边界限制的任务可以写"无特殊限制"，但不能省略小节本身——省略会让后续 agent 默认"无限制"，这和明确写"无限制"不是同一件事（前者是遗漏，后者是确认过的结论）。

### 3.3 状态（status）选择

| 场景 | 选择 |
|---|---|
| 需要立刻开始执行 | `todo` |
| 讨论/确认阶段，不该触发执行 | `todo` 但描述里明确写边界（本规范不新增"讨论状态"，用描述约束执行范围），或暂不指派 agent |
| 依赖其他任务未完成 | `backlog`，待依赖满足后由负责人 `issue status <id> todo` promote |
| 严格串行的多步任务 | 当前步 `todo`，后续步骤先建 `backlog`，禁止一次性把整条链都设成 `todo` |

### 3.4 父子任务与 stage

- 拆子任务的判断标准：**能否独立验收**。不能独立验收的"子步骤"应该留在父任务描述里的检查清单，而不是拆成 issue。
- 使用 `--stage <N>` 的判断标准：**是否存在"全部完成才能进入下一组"的屏障语义**。没有这种屏障的并行子任务不需要 stage。
- 拆分前先确认：现有角色/agent 能否承接这个子任务粒度，不要拆到无人能独立判断完成标准的程度。

### 3.5 指派（assignee）

- 指派 agent 且状态非 `backlog`：会立即触发一次 run。创建/确认拆分方案时必须同步想清楚这一条。
- 指派人类：仅产生 inbox 通知，不触发 run。
- 不确定该派给谁时，宁可先不指派（或指派人类做路由决策），不要为了"看起来流程完整"随便指派一个 agent。

### 3.6 优先级 / 截止日期

- 默认 `priority: none`，仅在"会阻塞他人工作"或用户明确给出紧急程度时设置非 none 值。
- `due_date` 仅在用户给出明确时间约束时填写，不臆造。

### 3.7 自定义属性（property）

- 创建前用 `multica property list` 检查工作区是否已有可用属性；有则用，不新造非结构化等价物。
- 工作区没有需要的属性、且判断确有必要时，在结果评论中向用户提出属性申请建议（属性定义只能由 owner/admin 创建），不要绕过去把它硬塞进描述自由文本。

### 3.8 附件与图表

- 本地文件路径禁止直接写入描述正文，用 `multica issue update <id> --attachment <path>` 生成正确引用。
- 需要流程图/关系图时用 mermaid 代码块，不用截图附件。

## 四、反射流程（供执行规范的 skill 使用）

1. **理解**：读用户口语化输入，提取「要做什么」「做完的样子」「有没有约束」三类信息。信息不全时不要编造，标记为待确认项。
2. **产出草案**：按第三节结构生成 title + description + 建议的 status/assignee/拆分方案，所有推理得出而非用户原话直接给出的内容标 `model_inferred`。
3. **展示确认**：把草案完整展示给用户（不是摘要），明确哪些是直接转述、哪些是推理补充。用户未确认前不调用 `multica issue create`。
4. **用户确认后才创建**：用户认可或修改后的版本才用于实际创建；用户要求调整的，回到第 1 步重新理解，不是在草案上小修小补。
5. **创建后的推进交给后续流程**：创建只是产出一个待确认/待执行的 issue，不代表创建者本身要继续执行里面的任务——除非这正是用户当下要求的下一步。

## 五、不符合本规范的典型反例

- 标题是"处理一下那个事"：看不出产出物，不合规。
- 描述只有用户原话一段，没有验收标准：不合规。
- 讨论阶段的任务配上 agent assignee + `todo`，直接触发执行：不合规（除非这次"讨论"本身就是要产出的 deliverable，如本任务）。
- 把五个强依赖顺序的步骤一次性全部建成 `todo`：不合规，会同时触发五个 run。
- 本地绝对路径写进描述：不合规。

## 六、决策记录

反射依据、否决过的备选方案、用户确认过的调整，记录在 `multica/data/`（只增不减，格式参考仓库其他 `data/` 目录：一条记录包含「背景/原因/决策/后续验证结果」）。
