# 2026-10-28 规范 v1 起源记录

## 背景

陈驰远在 POWERBY-10 要求"研究并推荐 Multica issue/任务的新建规范"，明确要求先讨论方案、不要直接落地。讨论阶段产出了一份方案草稿（覆盖标题/描述/状态/父子任务/property 等维度），经用户确认方向后，用户提出：

> 我希望把规范持久化到 agents 项目中（新建 multica 目录），然后基于规范新建 skill，新建 issue/任务的时候调用此 skill 规范化创建。我发布的任务/issue 是口语化的，需要反射理解我需求，按照规范产出 issue/任务，并交由我判断。我同意的 issue/任务再交由后续流程推进。

## 原因

工作区现状：
- 历史 issue 标题风格不统一，描述基本只有用户原话转述，缺少验收标准和边界说明
- `multica property list` 为空，没有任何自定义属性
- 父子任务/stage 机制基本未被使用
- priority/due_date 字段几乎不用（全是默认值）

直接按口语化输入创建 issue，容易导致执行者"自认为完成"或误触发不该执行的任务（例如讨论类任务被当成执行任务直接跑掉）。

## 决策

1. 规范落地为 `multica/issue-creation-spec.md`，作为协议文档（仿照仓库内 `docs/skill-design-protocol.md` 等协议文档的定位：被 skill/角色读取引用的规范来源，不是用户直接调用的 skill 本身）。
2. 新建 `.claude/skills/multica-issue-create/` skill，职责是"反射口语化需求 → 产出结构化 issue 草案 → 展示给用户确认 → 用户确认后才创建"，不是"自动把口语化输入直接建成 issue"。
3. 遵循仓库 `create-role` skill 的闭环范式：确认优先于落地，禁止占位符填空，判断类内容（验收标准、拆分方案）必须来自真实反射，不是模板套话。

## 否决过的备选方案

- **直接把规范塞进 CLAUDE.md 运行时约束**：否决。CLAUDE.md 是本次任务执行环境的运行时上下文，不是 agents 仓库的持久资产，换一个 workspace/runtime 就会丢失；用户明确要求"持久化到项目中"。
- **规范和 skill 合并成一个文件**：否决。遵循仓库现有协议文档与 skill 分离的惯例（协议被多个 skill/角色引用，skill 是针对单一触发场景的可调用能力），分离后规范可以被其他未来的 multica 相关 skill 复用。

## 待验证

- skill 实际使用后，反射产出的草案是否真的覆盖了用户的隐含约束（尤其是边界/不做什么这一项，容易被用户在口语化表达里省略）
- 工作区后续是否会新增自定义 property，若新增需要回写本规范第 3.7 节
