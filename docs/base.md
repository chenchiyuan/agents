# 让 AI 住进项目里：小团队 AI 协作工作流（可复制版）

> 一句话：**别用"网页聊天式"开发，把 AI agent 和记忆都搬进 Git 仓库里。**
> 谁 clone 了仓库，谁打开就拿到同一套 agent、同一份记忆、同一批决策——越用越聪明，最后接近"一句话需求就出活"。

---

## 0. 先讲清楚：这套东西解决什么问题

群里聊的那种"古法"——发一句话、等模型回复、再复制粘贴——最大的问题是：

1. **记忆是散的**：每次对话从零开始，模型不知道项目背景、不知道之前踩过的坑。
2. **人和人不一致**：同一个项目，A 打开问一套、B 打开问另一套，结论还不一样。
3. **不沉淀**：踩过的坑、定过的规矩，聊完就没了，下个模型、下个人又来一遍。

这套方案的核心就一句话：

> **让 agent 和记忆跟着项目走（放进 Git），谁打开都是同一套。**

模型只是"发动机"，真正让产出稳定、越用越顺的，是**项目里沉淀下来的那堆 Markdown**。

---

## 1. 目录结构：一个项目长这样

```
你的项目/
├── AGENTS.md                # ← 项目入口/地图（冷启动先读这个）
├── CONTEXT.md               # ← 领域术语表（术语定一次，不许乱叫）
├── .pi/agents/              # ← 跟着项目走的子代理（谁打开都是这几个）
│   ├── developer.md         #     写代码的
│   ├── tool-test-runner.md  #     在虚拟机里实测 CLI 工具行为的
│   └── ui-test-runner.md    #     在虚拟机里跑 UI 测试的
├── memory/                  # ← 记忆跟着项目走
│   ├── MEMORY.md            #     台账索引（一行一条，先查索引再展开）
│   ├── constraints/         #     必保行为台账（"不写下来就会被改回去"的规矩）
│   ├── pitfalls/            #     踩过的坑（前车之鉴）
│   └── TEMPLATE.md          #     台账条目模板
├── docs/
│   ├── adr/                 # ← 架构决策记录（ADR）
│   └── dispatch-protocol.md # ← 派发协议（怎么指挥子代理）
└── plans/                   # ← 计划文件夹（多步任务跨会话可续）
    └── 0010-2026-08-30-auto-update/
        ├── task_plan.md     #     任务计划
        └── progress.md      #     进度
```

**全部是纯文本 Markdown，全部进 Git。** 没有私有平台、没有锁死工具，就是仓库里几个文件夹。

## 2. 逐块拆解（带栗子）

### 2.1 AGENTS.md —— 项目的地图，不是说明书

这是整个仓库的**总入口**，冷启动（新开会话）先读它。

关键设计是**"薄"**：只放指针，不放细节。就像地图只画"哪条路通哪"，不把沿途每棵树都画上去。

栗子（我们项目 AGENTS.md 里的记忆索引表）：

```markdown
## 记忆索引（改代码前先查这里）

| 记忆 | 位置 | 何时读 |
| --- | --- | --- |
| 台账索引 | `memory/MEMORY.md` | 按 description 判断相关性再展开 |
| 必保行为红线 | `memory/constraints/` | 改对应代码前必读 |
| 踩过的坑 | `memory/pitfalls/` | 写工具适配前必读 |
| 派发协议 | `docs/dispatch-protocol.md` | 派子代理前必读 |
```

**为什么这样：** 大模型上下文是有限的，你把 20 个文档全塞进去，它就读不到重点。正确姿势是：
入口文件 → 按需展开 → 只读本次任务相关的那几条。这叫**渐进式披露**。

> 加东西的硬规矩（防腐）：往项目里加任何东西，AGENTS.md 只加一行指针，细节放到对应的
> memory/ docs/ plans/ 里去。不然入口文件会越来越臃肿，最后变成一坨没人读的长文，整套机制就废了。

### 2.2 CONTEXT.md —— 术语表，让所有人说同一种话

术语一旦定下来就更新到这里，不许攒着、不许乱叫。栗子：

```markdown
## 语言

**中转站（AICodeWith）**：CLI 工具连接的后端 API 中继
  _Avoid_: 中转、代理、API 网关

**会话恢复（resume）**：跨重启把某段 CLI 对话恢复到终端继续
  _Avoid_: 续聊、恢复对话、断点续传
```

**为什么：** AI 写代码时，同一个东西你这次叫"中转"、下次叫"代理"，它会写出两套不一致的实现。
术语统一，代码命名才统一。

### 2.3 memory/ —— 项目记忆，这是整套东西的灵魂

#### MEMORY.md = 索引（一行一条）

```markdown
## 必保行为（memory/constraints/）

- [[happymomo-cli-config-merge-no-clobber]] - 给 CLI 写中转站配置：读不懂必须报错不改、
  字段归属二分是硬契约；唯一写入口是 tool.js【必保行为】
- [[happymomo-electron-renderer-contract]] - Electron 渲染进程硬契约：file:// 下必须 HashRouter、
  不能加 StrictMode、无边框窗口拖拽条要 -webkit-app-region【必保行为】
```

用 wikilink（`[[名字]]`）互链，先看 description 判断"这次改动会不会碰到这条"，相关才展开读。

#### constraints/ = 必保行为台账（重点！）

记的是**"不写下来，下次重构就会被悄悄改回去"**的约束。判断标准（满足任一条就记）：

- 违反后果是线上/用户实报的 bug，且从代码本身看不出为什么要这么写
- 来自某个外部工具的反直觉行为
- 跨两处以上必须同步修改的契约

栗子（真实条目节选）：

```markdown
---
name: happymomo-cli-config-merge-no-clobber
description: 给 CLI 写中转站配置时「读不懂→当空表」会覆盖用户整个配置文件；
             字段归属二分是硬契约，写入口已 OTA 化为 tool.js
type: 必保行为
---

## 事故

2026-08-27 修掉：两边的「读现有配置」函数在 JSON 解析失败时都返回空表，
调用方把我们这一小段配置合并进空表后写回原路径 ——
**等于用一小段配置覆盖用户的整个文件**。
实际后果：`~/.openclaw/openclaw.json` 写完只剩 `models` 一个键，`gateway.auth.token` 全没了。
```

**写约束的硬要求：**

- 极简追加：只写「日期 + 涉及文件 + 必保行为」，长背景收敛到 pitfalls/
- 必保行为要具体到可验证，并写清**违反后果**（最好是实际发生过的那个后果）
- 带日期和来源（`2026-08-27 用户实报`）
- 给出**回归测试命令**，让后来的人能直接验证约束还在

#### 台账防腐（最重要的一条纪律）

> **台账过期比没有台账更危险**——它会成为判据，把后来的改动引向错误结论。
> 改动了被台账覆盖的代码，必须**同一轮**回头更新对应条目。更新时保留旧结论被推翻的痕迹
> （写明"原为 X，YYYY-MM-DD 改为 Y，原因…"），不要直接抹掉。

#### pitfalls/ = 踩坑记录（前车之鉴）

主 agent 自己犯的错记这里。栗子：

```markdown
7. **写 brief 时没把台账必保行为写进契约**（2026-08-29）：Task 3 的 env 契约漏了
   `PATH: effective_path()`，developer 照 brief 实现后自己揪出来回报。
   教训：写 brief 前先查 memory/MEMORY.md 相关必保行为条目，把每条约束显式写进 brief，
   不假设 developer 会自己去读台账——它只按 brief 干活，brief 漏了 = 我漏了。
```

### 2.4 .pi/agents/ —— 跟着项目走的子代理

每个子代理是一个 Markdown 文件，frontmatter 里写死名字、职责、**用哪个模型**。谁打开项目，
谁就拿到这几个 agent，行为一致。

我们分三个，边界互不重叠：

| agent | 职责  | 模型  | 不做什么 |
| --- | --- | --- | --- |
| `developer` | 写生产代码，让主 agent 写好的测试通过 | deepseek flash | 写测试、架构决策、派 subagent |
| `tool-test-runner` | VM 里实测 CLI 工具真实行为 + 据实写 tool.js | deepseek flash | 架构决策、app 代码、UI 测试 |
| `ui-test-runner` | VM 里用 Playwright 跑 UI e2e | deepseek flash（vision） | 架构决策、app 代码、CLI 行为 |

栗子（developer.md 的 frontmatter 和边界）：

```markdown
---
name: developer
description: 写生产代码，让主 agent 写好的测试通过。只写实现，不写测试用例。
tools: read, write, edit, grep, find, ls, bash
model: deepseek/deepseek-v4-flash
---

## 边界（不做什么）
- 不写测试用例：测试是主 agent 的活
- 不改测试：除非测试本身有笔误导致跑不起来
- 不做架构/范围决策：拿不准就回报主 agent
- 不派 subagent、不跑全量测试、不碰真实 key
```

**核心分工思想（关键）：**

- 主 agent 是**控制器**：写 spec + **写测试用例**（它懂业务和边界）→ 拆任务 → 派发 → 验收
- 子代理是**执行者**：不继承主 agent 的上下文，只拿 brief + 测试文件干活

### 2.5 docs/dispatch-protocol.md —— 派发协议

子代理**不继承**主 agent 会话上下文，它只知道 brief + 自己读到的文件。所以派活要遵守几条铁律：

1. **brief 落文件**：每个任务写一份 `plans/<计划>/task-<N>-brief.md`，派发只给路径
2. **测试就是规格**：主 agent 写好的测试文件是唯一对错判据
3. **好 reference**：只给本任务相关的 memory 条目，不让它读整个仓库
4. **报告契约写死**：brief 里写明"回报什么"
5. **一个任务一份 brief**
6. **模型已定**：agent 文件 frontmatter 里写了 model，不用再传

#### Task brief 固定模板（这是关键资产）

```markdown
# Task brief: <任务名>

## 任务目标
<一句话：这个任务在项目里的位置 + 要产出什么>

## 需求（精确值，逐字写死）
- 行为 / 字段 / 默认值 / 边界 / 错误态：...

## 测试与验收
- 测试文件：<path>（已写好，别改）
- 验收：这些测试全绿 = 完成

## 必读 reference（按需读，别读整个仓库）
1. memory/...（本任务触及的必保行为条目）
2. docs/...（相关章节）

## 涉及文件
- 主进程 / 渲染进程 / 测试：...

## 边界 / 禁止
<不做什么、拿不准就回报主 agent>

## 报告契约（回报这四件事）
1. 改了什么文件 2. 测试结果 3. 疑问/待办 4. 违反边界的事（若有）
```

#### 归因铁律（这套东西"越用越聪明"的秘密）

子代理干完活，主 agent **必须手动验收**，绝不只看报告就放过。验收发现问题时：

> **第一归因永远是自己，不是子代理：**
> "一定是我的问题——brief 没写清 / reference 给错了 / 模板缺字段。"

然后**定位到环，当场修**：

| 出问题的环 | 修哪里 |
| --- | --- |
| brief 没说清需求 | 改 Task brief 模板（补字段、补示例） |
| reference 给错 | 改 reference 底稿表 |
| agent 纪律有漏洞 | 改对应 `.pi/agents/*.md` |
| 验收时才发现的坑 | 追加到 `memory/pitfalls/` |

**这就是"越用越厉害"的机制**：修完模板，下次派发就少踩同一个坑。记忆不在某个人脑子里，
而在这些不断迭代的模板文件里，而且可以**跨项目复用**。

### 2.6 docs/adr/ + plans/ —— 决策和计划也进 Git

- **ADR**：大的架构决策写成文档（比如"为什么从 Tauri 重写成 Electron"），后来的人知道当初为啥这么定。
- **plans/**：多步任务开一个文件夹，`task_plan.md` + `progress.md`，跨会话、换人、断掉都能续上。

## 3. 完整日常工作流（从"一句话需求"到"出活"）

```
用户一句话需求
    ↓
主 agent 读 AGENTS.md 冷启动 → 查 MEMORY.md 相关台账
    ↓
（多步任务）开 plans/NNNN-日期-标题/ 写 task_plan.md
    ↓
主 agent 拆任务 + 写测试用例（测试=可执行规格）
    ↓
写 brief 文件 → 派给 developer / tool-test-runner / ui-test-runner
    ↓
子代理只拿 brief + 测试，干活，按报告契约回报
    ↓
主 agent 手动验收（读 diff、跑测试、核对没越界）
    ↓
验收通过 → 记账：该进台账的进台账、该记坑的记 pitfalls、
           该更新 AGENTS.md 指针的更新指针
    ↓
下次同样的活，AI 直接查台账、照模板走，又快又稳
```

## 4. 从零搭一套（步骤清单）

1. **git init**，建下面几个文件夹：`.pi/agents/`、`memory/constraints/`、`memory/pitfalls/`、`docs/adr/`、`plans/`
2. 写 `AGENTS.md`：项目定位（2 句）+ 记忆索引表 + 冷启动顺序。**保持薄，只放指针。**
3. 写 `CONTEXT.md`：先把 3~5 个核心术语定下来（随用随加）
4. 写 `memory/MEMORY.md`（索引）+ `memory/TEMPLATE.md`（台账模板）
5. 建子代理：`.pi/agents/developer.md`（先只建一个，够用了再加）
6. 写 `docs/dispatch-protocol.md`：抄上面的 brief 模板 + 归因铁律
7. 定好"一句话需求 → 派发 → 验收 → 记账"的节奏，**先跑通一个小需求**
8. 之后每次踩坑、每次改架构，都**当场**记进对应文件——这是唯一需要坚持的习惯

## 5. 几个关键原则（背下来）

1. **渐进式披露**：入口薄、按需展开、只读相关。别一次读整个 memory。
2. **测试就是规格**：主 agent 写测试，子代理只实现。对错判据是测试，不是感觉。
3. **归因铁律**：出问题先怪自己的 brief/模板，不甩锅给模型——因为模板是你的，修模板才有复利。
4. **台账防腐**：改了被台账覆盖的代码，同一轮更新台账。过期台账比没台账更危险。
5. **决策沉淀吊打一切模型**：把决策偏好、踩过的坑写进文件，比换个更强的模型管用得多。

## 6. 最后：关于"工具"的选择

群里吵的那些（pi / codex / claude / multica / linear……）其实是两件事，别混：

- **线性问题（多人协作、看板、PR/issue）**：用你们已经顺手的（GitHub PR/issue 就够，真需要看板再加 Linear），
  这部分是"流程管理"，跟 AI 关系不大。
- **AI 写代码效率问题**：核心不是换更强的模型，而是**把记忆和决策沉淀进仓库**。

我们实践下来的体会：

- **速度 > 智商**：开发大部分是纯体力活，用快且便宜的模型（deepseek flash）做执行者，
  主 agent 用更强的模型做"控制器/决策者"，是最划算的配比。
- **不迷信"高级工具"**：一堆 skill 流程约束堆上去，自动化强了，效率反而低、token 消耗高。
  大道至简——就是"agent 住进项目 + 记忆跟着项目走 + 台账/决策进 Git"这一套。
- **新项目复利**：memory 和偏好是可以跨项目复用的。开新项目时直接让 AI "复盘老项目的
  AGENTS.md + memory/"，架子瞬间搭好。
