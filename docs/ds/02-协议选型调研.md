# 02 协议选型调研

**版本**：0.2.0　**日期**：2026-09-09（信息截至当日，来源均为一手仓库/站点）　**状态**：方案建议

## 1. 调研问题

为"多个 OMP 常驻实例，实例间按**标准协议**消息投递 + Ack 保活 + 任意路由"，需要回答两个独立问题：

- **Q1 语义层**：agent 之间协作的"行业标准协议"是什么、发展到什么程度、能否直接采用？
- **Q2 传输/投递层**：本机多进程的可靠投递（Ack、重试、去重）用什么承载？

结论先行（DS-01）：**两个问题没有单一答案，分层组合**——语义层对齐 A2A v1.0，投递/生命周期层自研受限协议 OAMP，传输层用 JSON-RPC 2.0 over UDS。下文给出每层的候选与证据。

## 2. 语义层候选调研

### 2.1 A2A（Agent2Agent Protocol）—— 结论：采纳为语义参照

**事实（检索自官方仓库 a2aproject/A2A 与 a2a-protocol.org，2026-09-09）：**

- 起源：Google 发起，2025-06 捐赠 Linux Foundation 治理；技术指导委员会（TSC）含 **AWS、Cisco、Google、IBM Research、Microsoft、Salesforce、SAP、ServiceNow** 八家。
- 版本：**v1.0.0（2026-03-12）** 发布"production-ready 标准"；**v1.0.1（2026-05-26）** 为最新 patch。规范权威源是 `specification/a2a.proto`（Protobuf），人类可读版在 `docs/specification.md`。
- 定位：**agent 与 agent 之间**的互操作与任务委派；官方明确与 MCP 互补而非替代（"MCP inside agents, A2A between agents"）。
- 语义对象：**Agent Card**（`.well-known/agent-card.json`：身份、能力、skill、安全方案、`supported_interfaces`）；**Task**（有状态工作单元 + `context_id`）；**Message/Part**（一次对话轮次；Part 为 text/raw/url/data 联合类型）；**Artifact**（任务产物）。
- Task 状态机：`SUBMITTED → WORKING → { COMPLETED | FAILED | CANCELED | REJECTED | INPUT_REQUIRED | AUTH_REQUIRED }`；终态不可重启，续作走新 task + 同 `context_id` + `reference_task_ids`。
- RPC 面（v1.0）：`SendMessage`、`SendStreamingMessage`、`GetTask`、`ListTasks`、`CancelTask`、`SubscribeToTask`、`GetExtendedAgentCard`、推送通知配置 CRUD（`Create/Get/List/DeleteTaskPushNotificationConfig`）。
- 多绑定架构：v1.0 大重构把**应用协议与传输解耦**——官方绑定为 JSON-RPC 2.0（HTTP/SSE）、gRPC、HTTP/REST；并允许**自定义协议绑定**（AGNTCY 已实现 SLIMRPC 绑定，见 2.4）。SDK：Python、JS/TS、Java、Go、C#/.NET、Rust。
- v1.0 企业特性：多租户单端点、签名 Agent Card（加密验证身份）、OAuth 现代化（PKCE/device code）。

**与需求的差距（为什么不能直接整套使用）：**

1. A2A 是 **client↔server 点对点**语义：谁发起、谁是远端 agent。它**没有**"任意 agent 间路由/广播/selector"的中心路由模型——多跳编排是调用方的职责。
2. A2A **没有**心跳/租约/在线探测：推送通知是"任务事件 webhook"，接收方须回 HTTP 2xx 表示收讫（等价的 HTTP 层 ack），但**没有 agent 级 liveness**。
3. A2A **没有**本地投递队列语义（at-least-once、Ack 状态机、重试上限是 OAMP 自己的事）。
4. 完整 v1 合规（多绑定、多租户、签名卡、OAuth 流）对单机 MVP 是重负担。

**证据链**：CHANGELOG.md（v1.0.0/v1.0.1）、docs/blog/posts/announcing-1.0.md、docs/topics/{key-concepts,life-of-a-task,streaming-and-async,what-is-a2a}.md、docs/llms.txt。

### 2.2 MCP（Model Context Protocol）—— 结论：不用于 agent 间通信

- 定位：连接 **LLM ↔ 工具/数据/上下文**（model 层），工具通常无状态、单次、预定义。
- 官方与 A2A 的边界声明：MCP 解决 agent 内部的工具/上下文接入，A2A 解决 agent 之间的通信与协调；把 agent 包装成工具会损失其协商/多轮能力（"agents are not tools"）。
- 对本需求：MCP 不提供 agent mailbox、Ack、路由、生命周期语义，故不承担通信主干。但**未来每个 OMP 实例把自身能力以 MCP 暴露给其他实例做工具化调用**是可行的旁路（本方案标记为可选 enhancement，非 MVP）。

### 2.3 ACP —— 三个同名不同物，必须区分

| 名称 | 归属 | 状态 | 定位 | 与本需求关系 |
|---|---|---|---|---|
| **ACP（项目内）** | `model-dispatch-protocol`（agents 仓库） | 现行执行协议 | 一次子 agent 派发的统一契约（role/executor/model/brief → completed/failed/blocked） | **复用**：OAMP 的实例启动沿用其解析与审计语义 |
| **ACP（Cisco）** | agntcy 组织 `acp-spec` 仓库 | **已归档**（仓库 archived，最后 push 2025-05-23） | Agent Connect Protocol，曾是 Cisco 阵营的 agent 连接规范 | 不采用；其方向已转向 SLIM/DIR/A2A 集成（见 2.4） |
| **ACP（Zed）** | agentclientprotocol.com（Zed，2025-08 发布） | 活跃 | **客户端（IDE/工具）↔ coding agent**（Claude Code/Codex 等）的 JSON-RPC 控制协议；agent 作为 server 被驱动 | 与"agent 间 peer 通信"不同构；若未来需要 IDE 或外部系统直接驱动 OMP 实例可作参考，非本包主干 |

### 2.4 AGNTCY（"Internet of Agents"，Cisco Outshift）—— 结论：生态参照，非 MVP 依赖

**事实（检索自 agntcy GitHub 组织仓库列表与 agntcy.org，2026-09-09）：** AGNTCY 定位"agents 的互联网基础设施"，官网四支柱：**discovery、identity、messaging、observability**。组件：

- **DIR（Agent Directory Service）**：agent 目录/发现服务（`dir-spec`、`dir-sdk-python/js`、`dir-mcp`、`dir-runtime`、`dir-gui`）。
- **SLIM（Secure Low-Latency Interactive Messaging）**：低延迟消息协议（`slim-spec`）；并提供 **SLIMRPC 传输绑定到 A2A SDK**（`slim-a2a-python/go/js/dotnet/java`），即"把 A2A 语义搬到 SLIM 传输上"的先例——正是本方案"语义与传输解耦"的行业印证。
- **identity**（agent 身份 + `identity-service` + OIDC gateway）、**OASF**（Open Agentic Schema Framework）、**observe**（多 agent 可观测性）、**workflow-srv**（运行 agent 并"通过 ACP 暴露"）。

评估：AGNTCY 是一整套跨组织"agent 互联网"栈，成熟度与运维成本远超单机多实例需求；但它印证两点——(1) agent 语义标准（A2A）与消息传输解耦是行业方向；(2) 未来需要跨机器发现/身份时，**DIR 与 agent identity 可作为 northbound 替换物**，OAMP 信封不必推倒。

### 2.5 first-tree（用户指定参考）—— 借鉴拓扑与上下文，不借鉴协议

**事实（检索自 first-tree-ai/first-tree，README 指向 agent-team-foundation 组织，2026-09-09）：**

- 组件五件套：**Context Tree**（Git 原生的团队记忆：决策/归属/约束）、**Web workspace**、**CLI + daemon**（把机器/agent 接入）、**Agent runtime**（"runs agents on your machine and routes messages through First Tree"）、**GitHub integration**。
- 明确适配 Claude Code / Codex / MCP；Apache-2.0。

**对本需求的借鉴与不借鉴：**

- ✅ 借鉴 **daemon 连接模式**：agent 不各自维护连接管理，统一由本机 daemon 注册与转发——与本方案星型 Router 同构；first-tree 是"跨机 + 团队空间"形态，OAMP 是其单机最小版。
- ✅ 借鉴 **共享上下文注入**：Context Tree 回答"agent 干活前先读团队记忆"；本方案 R-03 的 prompt_profile（含 AGENTS.md/role 文件）是同一思想的最小落地。
- ❌ 不借鉴其**协议本体**：first-tree 不开源 wire 协议作为标准，消息路由是其私有 server 行为；不可作为"标准协议"引用。

## 3. 传输/投递层候选调研（Q2）

| 候选 | Ack/投递语义 | 路由 | 本机部署成本 | 结论 |
|---|---|---|---|---|
| **UDS + JSON-RPC 2.0（OAMP Router 自研）** | 应用层 Ack 状态机（queued→delivered→acked）+ NDJSON 持久化 | 中心 Router：agent_id/topic/selector | 零新依赖，文件权限即安全 | **MVP 采纳（DS-02）** |
| **NATS（JetStream）** | JetStream 消费 Ack + 自动重投（at-least-once） | subject 层级通配天然支持 topic 路由 | 需引入 broker 进程与运维面 | 跨机/多项目时作为 Router 替换项（06 §1） |
| **Redis Streams** | XACK + consumer group + 死信 | 无内建通配路由，需自建 | 需 Redis 依赖 | 同上，若项目已用 Redis 可考虑 |
| **RabbitMQ/AMQP** | 逐消息 ack、queue/TTL/DLX 完备 | exchange/routing key | 重；单机杀鸡用牛刀 | 不采用 |
| **MQTT 5** | QoS1/2 + PUBACK，topic 通配 | 强 topic 模型 | 面向 IoT/弱网，语义偏 pub/sub | 不采用 |
| **WebSocket** | 无投递语义，需自建 | 需自建 | 本机无优势，跨机才有 | 跨机阶段启用 |
| **gRPC** | 无消息队列语义；HTTP/2 长连接 | 需自建 registry | 需 protobuf schema；本方案信封已定 | 与 A2A gRPC 绑定一并留到跨机阶段 |

**决策依据（DS-02）**：MVP 约束是"零新增常驻基础设施 + 可审计 + 可替换"。UDS 文件权限（0600）天然是本机唯一性/授权边界；JSON-RPC 2.0 是既有标准，外层无歧义；NDJSON 追加日志与现有 `.pb-agents/project/` 记录体系一致。外部队列引入的唯一理由（跨机、持久化 broker、fan-out 规模）在 MVP 均不成立——**不做推测性开发**；信封不变，未来 Router 内部可整体换成 NATS 适配器（04 §9 明确升级路径）。

## 4. "用什么协议"的最终回答（DS-01）

```
┌─ 应用语义层：对齐 A2A v1.0（AgentCard 能力声明 / Message+Part / Task 状态机 / context_id）
├─ 消息与生命周期层：OAMP/1（agent.register / agent.heartbeat / message.send / message.deliver
│                     / message.ack / control.* …——本包 04 定义，含 Ack 状态机与租约）
└─ 传输层：JSON-RPC 2.0（既有标准）over Unix Domain Socket（本机）
      └─ northbound adapter（未来）：A2A HTTP(S)/gRPC 绑定 或 NATS —— 信封与语义不变
```

三点定性，避免过度承诺：

1. **OAMP 是"A2A 语义的本地受限方言"，不是 A2A v1.0 实现**：只借 Message/Part/Task/Agent Card 的词汇与状态概念，不声明协议版本兼容、不实现多绑定/签名卡/多租户。互操作责任放在未来的 northbound adapter（A2A SendMessage ↔ OAMP task.request 的翻译层），adapter 才是"A2A 合规实现"的边界。
2. **Ack ≠ 保活**：消息确认（Ack）与节点存活（心跳/租约）是两种机制，OAMP 显式区分（04 §6）。这是对用户"Ack 可以保活"的精确化——Ack 是投递语义，保活是生命周期语义，混用会造成"收了消息但已死"与"活着但没收到"无法区分。
3. **标准协议组合优于单协议**：agent 协作语义用 A2A（唯一大厂联盟背书的 agent↔agent 标准，LF 治理）；请求-响应外层用 JSON-RPC 2.0（IETF 生态事实标准）；两者都不覆盖的部分（本地注册/路由/租约/队列）由 OAMP 以最小面补齐。这与 AGNTCY 把 A2A 绑到 SLIMRPC 的做法同构——语义标准与传输分离是当前行业共识形态。
