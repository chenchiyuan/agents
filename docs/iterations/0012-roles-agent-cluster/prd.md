## 本次迭代边界说明

### 包含

- **角色实例身份与生命周期**（W1 / W2 / W7）：10 个角色 → `pb-<role>` 实例；形态 = oamp 节点进程（注册 + 心跳 + 注销，LLM 子进程按 `(chat, agent)` 懒起）；单起与批量起两条入口并存。
- **角色规则加载与生效**（W3）：角色真源 = `roles/<role>/<role>.md`；加载必须真实生效、可验证、跨对话稳定，且不污染仓库根上下文、不使工作目录偏离角色 cwd。
- **默认模型与按角色覆盖**（W4）：默认 `deepseek/deepseek-v4-flash`；配置文件内可按角色覆盖。
- **工具能力**（W5 前半）：工具默认全开、可按角色关闭，且对默认（web 常驻）对话路径真实生效。
- **permission 策略**（W5 后半）：默认档 = 允许 + 每次工具调用写事件日志（审计）；拒绝档可配且**快速失败、绝不挂起**。
- **集群入口脚本与配置**（W6）：配置文件纳入 git（零凭据字段），角色清单配置驱动不硬编码；一条命令在**一个 tmux session** 内拉起 Router + Web + N 个角色（各占窗口/pane，可 attach 观察）；提供 up / down / status；日志同步落盘（落点被 gitignore）。
- **按角色工作目录**（W8）：配置文件的每个角色支持 `cwd`（缺省 = 仓库根），tmux 各窗口在对应 cwd 下启动该角色 agent。

### 不包含（边界，源自 demand 第二段 §2 N1~N12）

- **N1 不修改任何角色定义文件**——`roles/**` 只读消费（落 F02 验收 8 + 边界）。
- **N2 不为 `cdp-debug-skill`（及 `_template`）建实例**（落 F01 验收 2 + 边界）。
- **N3 不做集群调度 / 任务编排 / 负载均衡 / 自动派活**——脚本只管进程生命周期（落 F06 / F01 边界）。
- **N4 不做跨机器部署 / 远程 Router / 容器化**（全局边界 + F01 / F06 边界）。
- **N5 不做鉴权 / 多用户 / 凭据管理**（落 F06 验收 7 + F05 边界）。
- **N6 不做工具调用的细粒度沙箱 / 命令白名单 / 路径限制**——只承诺"开关配置化 + permission 允许/拒绝两档不挂起"（落 F04 / F05 边界）。
- **N7 不做系统级进程守护 / 崩溃自动重启 / 开机自启**（落 F06 边界）。

## 拆分理由（原子粒度判断）

- **F01 独立成卡**：W1/W2/W7 是"实例存在且可寻址"这一件事——命名规则、实例形态、单起入口三者共享同一个可观察面（`oamp status` + web `@` 列表），失败模式一致，合并成一张卡；W7 未单独成卡的理由是"单起可用"不是独立可交付的机制（它是否成立由 F01 的实例启动路径直接决定），故作为 F01 验收 4 并被 F06 反向约束"批量入口不是唯一入口"。
- **F02 与 F01 分拆**：节点注册成功 ≠ 角色规则真的生效（V-4 明确"不能假定文件注入生效"）。F01 的失败模式是"实例不在拓扑里"，F02 的失败模式是"实例在拓扑里但答的不是该角色的话"——两者独立可测、独立可交付（注入机制是独立于实例化的一块改造），故拆开。
- **F03 独立成卡**：模型是"每角色一个参数面"，其验收（改配置→该角色换模型、其他角色不受影响）不依赖实例命名也不依赖工具，单独可测；合入 F01 会让实例卡同时承担参数语义。
- **F04 与 F05 分拆（W5 一分为二）**：W5 含两个各自独立可测的行为——"工具开关按角色可配且真实生效"（E4：同一指令在两个角色上得到相反结果）与"permission 策略两档行为"（E5：拒绝档不挂起 + 允许档留痕）。两者的配置项、失败模式、判定手段都不同（前者判"有没有产生文件"，后者判"这一轮有没有明确终态/有没有留痕"），故按独立验收拆成两张卡，而不是一张"工具相关都归它"的大卡。两卡的耦合点已显式写明：F04 的"工具真实可用"必须以 F05 的 permission 应答为前提（V-6），F05 的验收 4 必须在工具已放开的实例上执行。
- **F06 不拆成"配置文件"与"脚本"两张**：配置文件只有在被入口脚本消费后才可被判定（"配置驱动"的观察面是"改配置 → 集群实例集合/参数随之变化"），拆开会产生一张无法独立验收的卡。up / down / status 也不拆：down 与 status 的判定都以 up 的结果为基准，是同一生命周期的三个方向，共享 E7 这一组端到端用例，拆开只会让验收互相引用同一组用例而产生重复。
- **F07 独立成卡**：W8 是用户改判后的独立配置面，其判定（同一指令在两个角色上落点不同）与 F06 的生命周期判定完全不同，且可在 F06 之后单独交付（脚本先起得来，再按角色换 cwd），故独立。
- **未单立"基线兼容与回归"卡**：demand 的 E2（上下文回指不回退）与 E6（判活语义不回退）已分别落为 F01 验收 7 与 F01 验收 6——它们判定的是"新实例正确接入既有拓扑与对话模型"，属 F01 的验收范围内，另立卡片会构成 demand 之外的新增功能点（本阶段不做，见「疑问与越界」第 7 条）。

## 疑问与越界

1. **E4 的二选一措辞**：demand E4 允许两种可接受结果——"不产生该文件"**或**"以明确回绝结束"。F04 验收 3 按原文保留二选一（QA 可断言"文件不存在"即通过），F04 验收 5 额外要求"该轮以明确结论结束、不得静默失败"并标 `[user_confirmed]`（M-01，2026-09-10 用户确认）——该收窄已确认成立。
