# F02：角色规则加载与生效

**功能 ID**: F02
**来源**: `demand.md` W3（G-2 / M-1）、TC-09；效果条款 E3；约束 C-3 / M-4；实测事实 V-1~V-5；验收 6 判定面经用户确认（M-02，2026-09-11）
**迭代**: 0012-roles-agent-cluster

---

## 用户价值

每个角色实例**真的按它自己那份角色定义干活**：问架构问题得到架构角色的回答、问验证问题得到验证角色的回答；而且换一个对话重问，回答依然来自同一份角色定义（人格不随对话重建）。

## 验收标准

1. **规则真源 = 仓库根角色文件**：`pb-<role>` 的运行期规则来自 `roles/<role>/<role>.md`（10 个角色各自的同名文件），不读取 `.pb-agents/` 下的安装副本（G-2 / F-1）。
2. **加载真实生效（原文可比对）**：向 `pb-architect` 提问"照抄你角色定义里『成功标准』的第一条原文"→ 回答与 `roles/architect/architect.md` 中对应条目一致（E3 首段）。判定不依赖任何自我声明，只与文件原文比对（V-4：不得假定文件形态注入必然生效）。
3. **跨对话稳定**：新开一个 chat 重复同一提问，回答依然与该角色文件中的条目一致（E3 后半 / M-4：角色规则不随 chat 创建销毁而变）。
4. **抽样覆盖多角色**：对 `pb-verifier`、`pb-dev` 以同一问法抽样，各自回答分别与 `roles/verifier/verifier.md`、`roles/dev/dev.md` 中对应条目一致（E3 抽样条款）。
5. **两条 LLM 执行路径都注入**：同一角色实例，无论指令走常驻对话路径还是一次性任务路径，回答都来自同一份角色规则（TC-09；shell 执行路径与角色规则无关，不受影响）。判定观察面见 AR-05。
6. **不污染仓库根上下文**：角色规则加载不在仓库根新增或修改任何会影响其他会话（主 agent、用户自身会话）的规则类文件——判定：加载前后仓库根不存在由本迭代新增的规则文件，既有仓库级规则文件（如仓库根 `AGENTS.md` / `.claude/CLAUDE.md`，若存在）内容与加载前一致（W3 约束②）`[user_confirmed]`（M-02，2026-09-11 用户确认）。
7. **不使工作目录偏离角色 cwd**：角色规则加载不改变实例的工作目录——未配置 `cwd` 的实例（如 `pb-architect`）在其默认工作目录（仓库根）下创建文件时，文件出现在仓库根（W3 约束③；`cwd` 的配置与判定见 F07）。
8. **只读消费**：加载是只读行为——集群运行前后 `roles/**` 的全部文件内容与 git 状态不变（N1）。

## 边界（不包含）

- 不含注入机制的实现选择（进程级 `--append-system-prompt` vs 固定 cwd + `AGENTS.md` vs 其它）——需求层只锁 W3 的三条约束与验收 2 的可验证性，机制定案归 AR-04（V-1 / V-2 / V-3 是候选机制的实测依据，不是产品结论）。
- 不含角色定义文件本身的修改 / 优化 / 补全（N1）——加载是消费，改文件会让"注入是否生效"失去比对基准（C-3）。
- 不含 `roles/_template` 与 `roles/cdp-debug-skill`（N2）。
- 不含模型、工具、permission 的注入内容（F03 / F04 / F05）。
- 不含角色上下文的持久化 / 跨对话长期记忆（N9）——"跨对话稳定"指的是规则来源稳定，不是对话记忆。
- 不含动态角色发现 / 热重载（N11）。

## 架构维度（阶段 3 已填，2026-09-11；详见 `architecture.md` §3.2 / §3.3）

- **AR-04 注入机制定案**：**进程级 `--append-system-prompt <角色 md 的绝对路径>`**。依据：omp 该 flag 的值在不含换行时**按文件路径读取**并注入全文（读不到才回退为字面文本），且 `--append-system-prompt` 是**追加**（保留默认编码助手提示与 context files）、非 `--system-prompt` 的**替换**语义。三条约束因此天然成立：① 与 cwd 完全解耦（注入不依赖也不改变进程工作目录 ⇒ 约束③/验收 7）；② **不写任何文件**（仓库根不新增规则类文件 ⇒ 约束②/验收 6）；③ 与 per-session 无关，两条 LLM 路径用同一参数（验收 5）。**否决候选**：固定 cwd + `AGENTS.md`（必须往仓库根或角色目录写文件，且同深度 `.claude/CLAUDE.md` 会遮蔽 `AGENTS.md`，并与 cwd 双语义纠缠）、`.pb-agents/roles/` 副本注入（真源错误，验收 1 要求 `roles/<role>/<role>.md`）、`--system-prompt`（替换掉 omp 的基础提示，工具链路质量风险）、ACP per-session 注入（V-3 实测该面不存在）。
- **AR-05 两条路径的落点与判定观察面**：常驻路径 = `AcpClient.start()` 拼装的 argv 追加该参数（角色文件绝对路径由 `ContextPool` → `ContextSession._ensureClient()` 透传）；一次性路径 = `runOmpTask()`（`omp -p`）的 argv 追加同一参数；`shell`（`!`）路径不注入（卡边界）。判定面三条：① **argv 断言**（自动化、零 LLM：测试用既有 `FAKE_ACP_ARGS_LOG` 注入点断言两条路径的 argv；人工用 `ps` 看子进程命令行）；② **真实生效**（阶段 6：验收 2~4 的原文比对与换 chat 复测）；③ **启动事件**：agent 启动落一行 `ROLE_BOUND role=<r> file=<绝对路径> source=flag|instance_id`。
