# F02：角色规则加载与生效

**功能 ID**: F02
**来源**: `demand.md` W3（G-2 / M-1）、TC-09；效果条款 E3；约束 C-3 / M-4；实测事实 V-1~V-5；验收 6 判定面经用户确认（M-02，2026-09-10）
**迭代**: 0012-roles-agent-cluster

---

## 用户价值

每个角色实例**真的按它自己那份角色定义干活**：问架构问题得到架构角色的回答、问验证问题得到验证角色的回答；而且换一个对话重问，回答依然来自同一份角色定义（人格不随对话重建）。

## 验收标准

1. **规则真源 = 仓库根角色文件**：`pb-<role>` 的运行期规则来自 `roles/<role>/<role>.md`（10 个角色各自的同名文件），不读取 `.pb-agents/` 下的安装副本（G-2 / F-1）。
2. **加载真实生效（原文可比对）**：向 `pb-architect` 提问"照抄你角色定义里『成功标准』的第一条原文"→ 回答与 `roles/architect/architect.md` 中对应条目一致（E3 首段）。判定不依赖任何自我声明，只与文件原文比对（V-4：不得假定文件形态注入必然生效）。
3. **跨对话稳定**：新开一个 chat 重复同一提问，回答依然与该角色文件中的条目一致（E3 后半 / M-4：角色规则不随 chat 创建销毁而变）。
4. **抽样覆盖多角色**：对 `pb-verifier`、`pb-dev` 以同一问法抽样，各自回答分别与 `roles/verifier/verifier.md`、`roles/dev/dev.md` 中对应条目一致（E3 抽样条款）。
5. **两条 LLM 执行路径都注入**：同一角色实例，无论指令走常驻对话路径还是一次性任务路径，回答都来自同一份角色规则（TC-09；shell 执行路径与角色规则无关，不受影响）。判定观察面见 AR-05。
6. **不污染仓库根上下文**：角色规则加载不在仓库根新增或修改任何会影响其他会话（主 agent、用户自身会话）的规则类文件——判定：加载前后仓库根不存在由本迭代新增的规则文件，既有仓库级规则文件（如仓库根 `AGENTS.md` / `.claude/CLAUDE.md`，若存在）内容与加载前一致（W3 约束②）`[user_confirmed]`（M-02，2026-09-10 用户确认）。
7. **不使工作目录偏离角色 cwd**：角色规则加载不改变实例的工作目录——未配置 `cwd` 的实例（如 `pb-architect`）在其默认工作目录（仓库根）下创建文件时，文件出现在仓库根（W3 约束③；`cwd` 的配置与判定见 F07）。
8. **只读消费**：加载是只读行为——集群运行前后 `roles/**` 的全部文件内容与 git 状态不变（N1）。

## 边界（不包含）

- 不含注入机制的实现选择（进程级 `--append-system-prompt` vs 固定 cwd + `AGENTS.md` vs 其它）——需求层只锁 W3 的三条约束与验收 2 的可验证性，机制定案归 AR-04（V-1 / V-2 / V-3 是候选机制的实测依据，不是产品结论）。
- 不含角色定义文件本身的修改 / 优化 / 补全（N1）——加载是消费，改文件会让"注入是否生效"失去比对基准（C-3）。
- 不含 `roles/_template` 与 `roles/cdp-debug-skill`（N2）。
- 不含模型、工具、permission 的注入内容（F03 / F04 / F05）。
- 不含角色上下文的持久化 / 跨对话长期记忆（N9）——"跨对话稳定"指的是规则来源稳定，不是对话记忆。
- 不含动态角色发现 / 热重载（N11）。

## 架构维度（待阶段 3 填写）
