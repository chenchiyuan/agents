### 4.2 逻辑闭环（从已确认的 why 反推 what，与用户给的 what 做差异比对）

**M-1（方案雏形与机制的矛盾，必须在需求层指出）**：用户原话把角色 md 类比为"此 omp agent 的 AGENTS.md 文件"。但 V-3/V-4/V-5 表明字面执行会撞墙：
- ACP 无 per-session 注入面 → 注入只能进程级；
- `AGENTS.md` 的生效依赖进程 cwd → 若把文件写进**仓库根**（cwd = 仓库根），会污染整个仓库的上下文（影响主 agent 与用户自身会话），与 F-9 的仓库卫生约定冲突；若把 cwd 缩到**角色目录**，agent 的"读写文件/执行命令"就落在错误位置（dev 无法在仓库里干活）；
- 同深度 `.claude/CLAUDE.md` 还会遮蔽 `AGENTS.md`（V-4）。

> **改写提案（不委婉）**：你的目标是「角色 agent 加载各自角色规则并能在仓库里干活」，而"把 md 当成 cwd 下的 AGENTS.md"这个具体机制会同时破坏这两点中的至少一点。真正需要的可能是：**以"角色规则必须作为进程级注入真实生效"为需求约束，文件形态（AGENTS.md 注入）只是候选机制之一，由阶段 3 在"不污染仓库根上下文 + 工作目录 = 仓库根 + 注入可被验证"三条约束下定案**。用户确认的是"效果"，不是"AGENTS.md 这个文件形态"。

**M-2（用户已确认决策 1 与现有实现的冲突）**：D-1 要"带工具干活"，但 F-7 显示 web 的默认对话路径（`omp-daemon`/ACP）硬编码 `--no-tools`，且 V-6 显示放开工具后若不回 `session/request_permission` 会挂起。→ 需求层必须把"工具开关配置化"从"payload 可选"提升为"**角色/agent 级配置，且对默认工作路径生效**"，并同步定义 permission 应答（否则 E2 永远不成立）。

**M-3（表述与资源的表面冲突）**：D-2 要 10 个 agent 常驻，听起来像 10 个 LLM 常驻。→ 澄清为 10 个**轻量 oamp 节点进程**（无 LLM 常驻；LLM 子进程按对话懒起、LRU 上限 `context.max`）——与 G-1 同一结论，不改变 D-2 的范围。

**M-4（角色规则 vs 会话隔离的一致性检查）**：0011 定的是"新 chat = 新上下文"，而角色规则必须**跨 chat 稳定存在**。两者不矛盾的前提是：**角色规则走进程级注入，会话上下文走 ACP session**——规则不随 chat 创建/销毁而变。这是对 W3 的隐含约束（写进效果 E3：换一个 chat 再问同一角色问题，答案仍来自同一角色 md）。

**M-5（"能使用"与"怎么用"的落差）**：用户说"注册到 router 上并且能使用"——集群起完但没人知道怎么用，等于没交付。→ 效果条款里必须有一条"经 web `@` 列表可见 + 能对话 + 能干活"的端到端判定（E2）。

# 第二段：需求结论（v1.0.0，`user_confirmed`，可进入阶段 2）

## 1. 做什么

- **W1**（`user_confirmed` D-2 + `仓库事实` F-2）：为 10 个角色各建一个可寻址的 agent 实例，instance_id = `pb-<role>`，即 `pb-architect` / `pb-demand` / `pb-dev` / `pb-planner` / `pb-pr-planner` / `pb-prd` / `pb-progress-observer` / `pb-retrospective` / `pb-verifier` / `pb-workflow-pb`。`cdp-debug-skill` 与 `_template` 不建实例。
- **W2**（`user_confirmed` 原话 + G-1，2026-09-10 确认）：实例形态 = **oamp agent 节点进程**（注册 + 心跳 + 注销，沿用现有节点语义），**不是常驻 LLM 进程**；LLM 子进程仍按 `(chat, agent)` 懒启动（沿用 0011）。
- **W3**（`user_confirmed` 原话 + G-2/M-1，2026-09-10 确认）：每个角色实例**加载自己那份角色定义**（`roles/<role>/<role>.md`）作为运行期规则，且该加载**必须真实生效、可被验证**（E3）；具体注入机制交阶段 3 定案，需求层只锁三条约束：① 注入对角色 agent 的 LLM 执行路径生效；② 不污染仓库根上下文（不得为注入在仓库根新增影响其他会话的规则文件）；③ 不使 agent 的工作目录偏离**其角色的 cwd**（缺省 = 仓库根，见 W8）。
- **W4**（`user_confirmed` 原话 + TC-01，2026-09-10 确认）：角色实例的**默认模型 = `deepseek/deepseek-v4-flash`**；模型可按角色覆盖（全局默认 + 配置文件内每角色可写），解析链沿用 0011（请求 `model` > `OAMP_OMP_MODEL` > 配置 `defaults.model` > 内置默认）。
- **W5**（`user_confirmed` D-1）：角色实例**带工具干活**——文件读写与命令执行真实可用；**工具开关配置化**（可按角色开/关），且**对默认工作路径（web 常驻对话路径）生效**（现状该路径硬编码禁用工具，`仓库事实` F-7）；同时定义 **permission 策略**，要求"拒绝"时**快速失败、绝不挂起**（`实测` V-6）；工具开关**默认全开**（可按角色关闭，TC-02）；permission **默认档 = 允许，且每次工具调用写事件日志（审计）**，拒绝档可配（TC-03）。
- **W6**（`user_confirmed` D-3 + 原话 + TC-04 用户改判）：交付**一个集群入口脚本 + 一份集群配置文件**（配置文件纳入 git，TC-07）：脚本读配置，一条命令在**一个 tmux session** 内挂起 **Router + Web + N 个角色 agent**（各占窗口或 pane，用户可 `tmux attach` 实时观察各角色输出），并提供 **up / down / status** 三个动作；**日志同步落盘**（每进程至少一份，落点被 gitignore）；**角色清单不得硬编码在脚本里**（由配置驱动）。
- **W7**（`user_confirmed` 原话 + G-4，2026-09-10 确认）：角色实例**既可被集群脚本批量拉起，也可单独启动**（单独起一个 `pb-<role>` 同样能注册到 Router 并被 web 看见）。
- **W8**（`user_confirmed` TC-08 用户改判）：集群配置文件的每个角色支持 **`cwd` 字段**（**缺省 = 仓库根**）；tmux 各窗口在对应 cwd 下启动该角色 agent——"角色在哪儿干活"是可配事实，不是写死的仓库根。

## 2. 不做什么

- **N1** 不修改任何角色定义文件（`roles/**` 只读消费）——*理由*：本迭代目标是"让既有角色可被实例化"；改内容会污染 10 个角色，并使"注入是否真实生效"（E3）失去比对基准。
- **N2** 不为 `cdp-debug-skill` 建实例——*理由*：它是 Claude skill（`SKILL.md`），无同名角色文件，`tools/install-pb-agents.sh` 同样跳过它；它不在 D-2 的 10 个之内。
- **N3** 不做集群调度 / 任务编排 / 负载均衡 / 自动派活——*理由*：调度契约在 workflow-pb 与主 agent；本迭代脚本只管进程生命周期，角色 agent 是"被寻址的载体"，不是自主调度者。
- **N4** 不做跨机器部署 / 远程 Router / 容器化——*理由*：沿用 0010 D-3 与「UDS 本机 MVP」边界；跨机传输待跨机需求出现再评估。
- **N5** 不做鉴权 / 多用户 / 凭据管理——*理由*：沿用 0010 N6（监听 127.0.0.1 + UDS 属主访问）；且 F-9 的"零凭据字段"是已声明红线。
- **N6** 不做工具调用的细粒度沙箱 / 命令白名单 / 路径限制——*理由*：本迭代只承诺"工具开关配置化 + permission 允许/拒绝两档不挂起"；细化策略是独立安全课题，会显著扩大验证面（TC-03 的"按工具类别分档"选项未被采纳：用户确认为"允许／拒绝"两档）。
- **N7** 不做系统级进程守护 / 崩溃自动重启 / 开机自启（launchd / systemd / pm2）——*理由*：tmux session 只提供"可 attach 的可视前台"（TC-04 确认的用户改判），不承担自愈职责；沿用 0010 N7"可观察优先"，异常退出后由人工或脚本重新 up。
- **N8** 不做角色 agent 的直连通信 / 广播 / 新消息语义——*理由*：星型拓扑（0010 R1/R2），一切经 Router；本迭代不新增协议方法。
- **N9** 不做角色上下文的持久化 / 跨对话长期记忆——*理由*：沿用 0011（上下文活在进程内，进程亡即失忆）；记忆体系在 `docs/memory-system.md` 另有规划，不在本轮。
- **N10** 不做 Web 前端与协议改造——*理由*：复用 0011 的控制台、`@agent` 派发、SSE、SQLite；角色 agent 只是多注册 10 个节点。
- **N11** 不做动态角色发现 / 运行期热重载（不自动扫 `roles/` 增删实例）——*理由*：配置声明 + 重启生效已够；热重载引入并发变更面与"配置与运行态不一致"的新故障模式。
- **N12** 不改 workflow-pb 的派发路径（主 agent 仍按现协议派子 agent 干活）——*理由*：本迭代只建"载体"；把阶段产物改由常驻角色承接是流程变更，牵动 6 个阶段契约，应单独起迭代决策（→ TC-06 征询用户）。

## 3. 大概怎么做（方向性事实与机制轮廓，不锁架构细节；`[架构待填]` 交阶段 3）

- **角色真源与命名**（`仓库事实` F-1/F-2）：角色规则文件 = 仓库根 `roles/<role>/<role>.md`；实例 id = `pb-<role>`（满足既有 instance_id 校验）。

- **模型**：默认链沿用现有 0011 定稿（请求 `model` > `OAMP_OMP_MODEL` > 配置 `defaults.model` > 内置默认），新增"按角色可覆盖"（配置文件内）；默认值 `deepseek/deepseek-v4-flash`。
- **工具与权限**（TC-02/TC-03 确认）：改造点为 ① 常驻 ACP 路径的 `--no-tools` 硬编码改为**按配置传参**（`仓库事实` F-7 + `实测` V-7）；② 实现 `session/request_permission` 应答（不实现则挂起，`实测` V-6）；权限档位 = **允许（默认：放行 + 每次工具调用写事件日志）／拒绝（快速失败、不挂起，可配）**；工具开关默认全开、可按角色关闭。
- **集群配置与脚本**（TC-04 / TC-07 / TC-08 确认）：一份**纳入 git 的配置文件**（零凭据字段）描述——角色清单（含启用开关）、每角色参数（模型 / 工具开关 / 权限档 / `cwd`，**cwd 缺省 = 仓库根**）、router 与 web 参数（socket / 端口）；脚本入口提供 `up`（在**一个 tmux session** 内依次挂起 router → web → N 个角色 agent，各角色的窗口在各自 cwd 下启动）/ `down`（收口该 tmux session 并优雅停止各进程）/ `status`，**日志同步落盘**（路径 gitignore，`仓库事实` F-9）。**配置文件名 / 落点 / 与现有 `oamp/config.json` 的关系** → `[架构待填]`（倾向独立文件，理由：现有 config.json 是"单进程运行参数"，集群描述是"多进程编排输入"，两者生命周期不同）。
- **复用面**：0011 的对话落盘 / SSE / 同 chat 上下文池 / web `@agent` 派发全部不改语义；角色 agent 只是以新 agent_id 进入该模型。

- **E3（角色真的被加载，且跨对话稳定）**：向 `@pb-architect` 提问"照抄你角色定义里『成功标准』的第一条原文"，回答与 `roles/architect/architect.md` 中对应条目一致；**新开一个 chat 重复同一提问，回答依然一致**（M-4：规则不随对话重建）。对 `pb-verifier`、`pb-dev` 抽样同问，各自回答与其各自角色文件一致。
- **E4（工具开关可配置且真实生效）**：在配置里把 `pb-prd` 的工具开关置为关闭后重启集群，对 `pb-prd` 发同一条"创建文件"指令 → 不产生该文件（或以明确回绝结束）；同一时刻 `pb-dev` 仍能创建 → 开关粒度到角色且真实生效。
- **E5（permission 策略：允许放行 + 审计、拒绝不挂起）**：把 permission 档位置为"拒绝"并重启后，对任一角色 agent 发一条需要工具的指令：该轮在配置超时之前以明确的失败/拒绝结论结束，**不出现长时间挂起**；置为"允许"（默认档）时同一指令成功，且**每一次工具调用**都在事件日志中留下放行记录（审计面，TC-03）。
- **E6（拓扑一致性）**：kill 任一角色 agent 进程后，`oamp status` 中该 id 在租约超时后变为 `offline`（沿用 0010 判活语义，不回退）。
- **E7（tmux 可视观察 + 可收口 + 日志落盘）**：集群启动后 `tmux ls` 能看到该集群 session，`tmux attach` 后各窗口/pane 分别呈现 router / web / 各 `pb-*` 角色的实时输出；执行停止入口后 `tmux ls` 中该 session 消失，且 `ps` 中不存在本次集群的 router / web / 角色 agent 残留进程；落盘日志目录中每个角色 agent 至少一份日志文件、含启动行与停止行，且该日志目录未被 git 跟踪。
- **E8（按角色 cwd 生效）**：在配置里给某角色（如 `pb-dev`）设 `cwd` = 一个临时目录后重启集群，向其发"在当前目录创建 `cwd-check.txt`"指令 → 该文件出现在这个临时目录（而非仓库根）；同时未配 `cwd` 的角色（如 `pb-architect`）收到同指令 → 文件出现在仓库根（缺省生效）。

## 5. 为什么这么做

- **触发点**（`user_confirmed`）：用户要把 `agents roles` 下定义的 10 个角色变成"可注册、可使用"的常驻 agent 载体，并用一份配置驱动的脚本统一拉起集群。
- **现状缺口**（`仓库事实` F-5/F-6/F-7）：oamp 的 agent 目前是**匿名节点**——参数面只有 instance_id，没有角色、没有按实例的模型、默认路径还禁用了工具。不补上这三样，"角色"就只是文档，不是载体。
- **为什么现在做**（`仓库事实` F-8/F-10）：0010（拓扑 + 消息契约）与 0011（对话持久化 + 上下文 + Web 控制台）已合入 main；"可寻址常驻 agent + 可对话 web"两块地基已就位，把角色绑上去是下一个最小增量，也是后续"由角色本体承接阶段产物"（N12 / TC-06）的前置条件。
- **为什么带工具**（`user_confirmed` D-1）：角色的价值在干活；工具是"干活"的必要条件，因此工具开关配置化与 permission 策略是本迭代不可裁剪的核心，而非附加项（现状默认禁工具，等于角色只能聊天）。
- **为什么用 tmux 形态**（`user_confirmed` TC-04 用户改判）：本迭代要交付的是"能被观察的常驻角色"，tmux 一个 session 内一眼看到 router / web / 10 个角色的实时输出，沿用 0010 以来"可观察优先"的手测风格；日志落盘作为事后追溯，两者互补而非二选一。
- **为什么边界这么画**：每条 N 都附"为什么这次不做"（见 §2）；共同原则是——只做"角色实例化 + 可寻址 + 能干活 + 可批量启停"这条最小闭环，调度、鉴权、跨机、沙箱、热重载、流程变更全部留给后续迭代。
