### 标准 9：隔离性事实（已知风险核实）

**判定：pass（事实已确认——风险成立，已在偏差记录中登记）**

**事实：测试共享仓库级 `oamp/.runtime/cluster` 目录，并发运行会互相干扰。**

- 代码证据：`test/cluster-actions.test.js:20` `const LOG_DIR = path.join(OAMP_ROOT, '.runtime', 'cluster')` —— 固定指向包内**同一个**目录，非每个用例的临时目录；用例的 `snapshotLogs()`/`cleanupTest()`（`:132-148`）本身就是为了在这种共享目录里"只删自己新建的文件"而存在的补丁式防护。实现侧 `cluster.js:20` 同样是固定包根路径（`PKG_ROOT` 由模块位置推导，与 config 所在 root 无关）。
- 实测证据（并发）：同一 worktree 内**同时**启动两个 `node --test test/cluster-actions.test.js`（各自独立 fixture、独立 fake tmux、独立 Router socket），结果 run A `# fail 1`（`not ok 1 - up：session/窗口名与数量、每窗 -c、命令串、日志 truncate 与 git check-ignore（F06 验收 1/2/6）`），run B `# pass 13`。再跑一次同样并发，仍为 1 进程失败、1 进程全绿。串行执行时该用例稳定通过（我串行运行两次均 13/13：直接运行该文件一次 + `npm test` 内含一次）。
- 结论：**测试套件不可并发执行**；这是共享日志目录的直接后果（一个进程的 `prepareLogs` 清空/另一个进程 teardown 删除，与 `assert.ok(fs.existsSync(...))`/哨兵读取断言竞争）。PR 卡验收标准 9 的"全绿"在**串行**前提下成立，故不判 fail；该事实按委托要求如实记录，并登记为偏差 D-3 + 候选 NC-2。

## 下一迭代候选

> 本轮发现的优化点、边界问题或遗留限制，不在当前验收标准范围内，供决策是否纳入下一迭代。

- **NC-1（tmux target 前缀匹配 → 幂等/收口可能打错 session）**：`hasSession` 用 `tmux has-session -t <session>`（`cluster.js:131-133`），而 tmux 的 `-t` 对 session 支持**唯一前缀匹配**。实测（真实 tmux 3.6a）：仅存在 session `zz-vrf-<pid>-cluster` 时，`tmux has-session -t zz-vrf-<pid>` **退出 0**（被判定为"命中"）。可复现后果：若机器上残留一个同前缀 session（如 `oamp-cluster-old`）而 `oamp-cluster` 不存在，`up` 会打印"集群已在运行"而不建集群；`down` 的 `list-windows`/`send-keys`/`kill-session` 会作用到那个 session。建议改用精确匹配（`-t "=<session>"`）或 `list-sessions -F '#{session_name}'` 精确比对。
- **NC-2（测试并发隔离）**：同 D-3 的修复方向——为集群日志目录提供可注入根，使 `cluster-actions.test.js` 可在任意并发度下运行。
- **NC-3（`--wait 0` 的生产误用面）**：`--wait 0` 会**整体跳过** Router 就绪与实例 online 检查（`cluster.js:396` / `:410`），仍然建窗口并**退出 0**、且不打印拓扑表（仅打印"（--wait 0：未等待就绪，跳过拓扑表）"）。该语义是为测试注入设计的（env `OAMP_CLUSTER_WAIT_MS=0`），但 CLI flag `--wait 0` 对用户同样可达，会得到"看起来成功但 Router 可能未起"的假象。建议：跳过就绪等待仅允许经 env 注入，或 `--wait 0` 至少保留一次 Router socket 探活。
- **NC-4（日志截断范围）**：`prepareLogs` 清空 `LOG_DIR` 下**全部** `*.log`（`cluster.js:208-214`），而 `LOG_DIR` 固定为包根（非 config 所在 root）。同仓库用不同 `--config`（不同 `session`、不同角色集）并行跑两个集群时会互相清空日志。现实现与 PR 卡字面（`<PKG_ROOT>/.runtime/cluster/*.log` 逐个 truncate）一致，故仅作候选：可考虑按 session 分子目录，或只截断本次预期日志名。
- **NC-5（陈旧 session 的可观察性）**：`up` 幂等分支只打印窗口数（`cluster.js:371-372`），不呈现 `pane_dead`；架构 R-8 已知"session 在但窗口已死时 up 不重建"，但 `up` 侧不给任何提示，用户需另跑 `status`。候选：幂等命中时用已有 `listWindowRows` 顺带提示死窗口数。
