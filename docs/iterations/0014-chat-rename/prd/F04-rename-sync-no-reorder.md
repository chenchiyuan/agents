# F04：改名后的同步范围与排序不变（详情头 + 左栏即时更新、不置顶）

**功能 ID**: F04
**来源**: `demand.md` A-4（同步与排序）；决策 D-4；澄清 M-5 / M-11；矛盾处理 C-1；效果 E-2；边界 N-5
**迭代**: 0014-chat-rename

---

## 用户价值

改完名立刻在左栏看到新名字，不用刷新页面；但它不会因为改了个名就跳到列表最上面——列表的位置和"最近更新时间"都保持原样，你的空间记忆不被打乱。

## 验收标准

1. **详情区标题立即更新**：保存成功后，详情区的标题立即显示为新标题，无需刷新页面（A-4 / D-4 / M-5 / E-2）。判定：保存后不刷新，直接读详情区标题 = 新值。
2. **左栏对应列表项立即更新**：保存成功后，左栏列表中该对话的标题立即显示为新标题，无需刷新页面（A-4 / D-4 / M-5 / E-2）。判定：保存后不刷新，读左栏中该对话项显示的标题 = 新值。
3. **同步范围 = 当前可见列表中的对应项**：左栏当前可见列表（All / Working / Completed 等过滤结果）中的该对话项同步更新；若当前左栏处于「归档」视图，则不涉及该对话（可改名的对话必为非归档项，不出现在归档列表中）（M-06）`[user_confirmed M-06]`。判定：在 All 视图下改名，对应项更新；切到「归档」视图，其中不含该对话、内容无需变化。
4. **不改排序位置、不置顶**：保存成功后，该对话在左栏的位置与改名前完全一致——即使它不是列表第一项，也不会因改名跳到最前；其"最近更新时间"的显示值也不变（A-4 / D-4 / M-5 / N-5 / C-1）。判定：改名前记录左栏的完整顺序与该项的时间显示，改名后逐项比对，顺序与该项时间显示均一致（例：给第 3 项改名，它在修改后仍是第 3 项）。
5. **改名不刷新最近更新时间**：改名成功后，该对话的最近更新时间保持改名前的时间（这是验收 4"不置顶"的成因，单独断言）。判定：改名前记录该项的时间显示，改名后重读一致；重启服务后仍一致。
6. **改名不改变其他属性**：对话状态、所属 agent、归档标记、历史消息均不变（与 F03 验收 6 同一组判据，本卡只重申同步不引入副作用）。

## 边界（不包含）

- 不含**编辑交互本身**——那是 F01。
- 不含**校验规则**——那是 F02。
- 不含**只读边界**——那是 F03。
- 不含**自动生成规则**——那是 F05。
- 不做**改名后置顶 / 重排**（N-5）——列表排序规则保持不变。
- 不做**跨标签页 / 跨窗口的标题同步**（M-08 / `demand.md` §7 P-3；2026-09-11 用户确认本次不做；另一标签页需刷新后才可见新标题）`[user_confirmed M-08]`。
- 不含**左栏列表项的改名入口**（N-1）。
- 不含改名后对**搜索结果**的处理要求（改名后按新标题可检索到该对话属自然收益，`demand.md` C-5 已明确无需处理，不作为本迭代的验收项）。

## 架构维度（阶段 3 已填，2026-09-11；详见 `architecture.md` §6.4 / §3.1）

- **AR-10 左栏列表项标题就地更新的范围与数据来源**：**数据来源 = `state.chats`（主列表内存数据）**——`commitTitle()` 成功后取 `state.chats.find((c) => c.chat_id === chat.chat_id)` 命中项改其 `title`，再调用既有 `renderChats()` **整体重绘左栏一次**（不做增量 DOM：百条量级下一次 `innerHTML` 拼接即可，且能正确覆盖 TODAY/OLDER 分组与各过滤视图的既有渲染逻辑，无需为"改名"开辟第二条渲染路径）。**同步范围**：仅主列表中当前可见 / 已持有的那一项；**`state.archive.chats` 不同步**（可改名对话必为非归档项，不在归档列表内 —— `demand.md` D-16 / M-06）；其他标签页不涉及（`demand.md` D-8）。若当前列表不含该对话（例如它落在第一页 50 条之外），`find()` 返回 `undefined` ⇒ 跳过（没有可见项需要同步）。**不改排序**：`renderChats()` 是既有渲染函数、排序键取自 `updated_at`（本次未被写入）⇒ 位置与时间显示天然不变。
- **AR-11 "不置顶"的落点**：落在**语句层**（`architecture.md` §3.1 的逐列声明）——改名语句 `UPDATE chats SET title = ? WHERE ...` 的 `SET` 子句**只有 `title`**，`updated_at` **不被写入** ⇒ 主列表既有排序 `ORDER BY (CASE WHEN p.archived = 1 THEN c.archived_at ELSE c.updated_at END) DESC, c.chat_id DESC` 的结果**逐字不变**（服务端可直接断言：改名前后的 `GET /api/chats` 的 `chat_id` 顺序一致 + 该条 `updated_at` 逐字相等）。**既有排序规则不被改动**：`LIST_FROM` / `ORDER BY` / `listChats` / `countChats` 与前端 `loadChats()` **一行不改**；前端同步走就地回填（AR-10）⇒ 不做第二次拉取、不做第二次排序。`demand.md` C-1 的语句层约束由此**结构性**成立（而不是靠"记得别改 updated_at"的自觉）。
