# F03：标题只读边界（已归档 / 已关闭 / 空态不可编辑）

**功能 ID**: F03
**来源**: `demand.md` A-3（只读边界）；决策 D-3 与 D-7（后续提案确认）；澄清 M-6（只读边界面）/ M-8（已关闭未归档不可改）/ I-7（空态不可编辑，卡内编号 M-05）；矛盾处理 C-3 / C-6；效果 E-7；边界 N-1（卡内另有"不含多用户 / 权限"一条，属既有产品全局边界，`demand.md` 的 N 条款为 N-1~N-7，本条不引用编号）
**迭代**: 0014-chat-rename

---

## 用户价值

归档或关掉的对话不会被随手改名——"收起来的"和"关掉的"都保持原样；能改的一定是还能继续用的那条对话，不会出现"能改名却不能发消息"这种自相矛盾的状态。

## 验收标准

1. **已归档对话的标题不可进入编辑**：打开一条已归档对话，点击详情区标题**不进入编辑态**（标题保持纯文本、不可输入），标题不被修改（A-3 / D-3 / M-6 / E-7）。判定：归档项与未归档项对比点击结果——未归档项出现编辑框，归档项无任何编辑入口出现。
   > 说明：已归档对话仍可被打开查看（0013 既有能力，本迭代不改），本卡只规定"标题不可进入编辑"。
2. **已关闭（未归档）对话的标题同样不可进入编辑**：一条处于已关闭状态的对话，点击详情区标题不进入编辑态（2026-09-11 用户确认：与既有只读判定对齐，即"已归档 或 已关闭"均不可改）（M-8 / `demand.md` §7 P-1）`[user_confirmed]`。判定：关闭一条对话后点击其标题，无编辑入口出现。
3. **只读边界与既有只读面一致，不分叉**：不可改标题的对话集合 = 详情区已被判定为只读的对话集合（已归档 或 已关闭）；不出现"能改名但不能发消息"或"能发消息但不能改名"的两套边界（C-3）。判定：任取一条对话，其"可否改标题"与"可否继续发送消息"的结论一致。
4. **非只读对话可正常改名**：未归档且未关闭的对话（进行中 / 已完成 / 失败）均可进入编辑并保存标题（A-3 / D-3 / M-6；A-3 明示"激活后可改"——激活即退出归档只读面）。判定：分别对进行中 / 已完成 / 失败各一条对话执行改名，均保存成功。
5. **空态文案不可编辑**：未选中任何对话时，详情区显示的空态文案不是任何对话的标题，点击不可进入编辑（C-6 / `demand.md` I-7 = D-15）`[user_confirmed 卡内 M-05]`。判定：未选对话时点击该处，无编辑入口出现。
6. **改名不改变对话的其他属性**：改名只改变标题——对话状态、所属 agent、归档标记、历史消息均不变。判定：改名前记录上述值，改名后逐项比对一致。

## 边界（不包含）

- 不含**编辑交互本身**（进入方式、保存 / 取消 / 失败恢复）——那是 F01。
- 不含**校验规则**——那是 F02。
- 不含改名成功后的**同步与排序**——那是 F04。
- 不含**自动生成规则**——那是 F05。
- 不做**左栏列表项的改名入口**（N-1）。
- 不新增**其他只读判定维度**：除"已归档 / 已关闭"外，不因其他条件（例如对话是否进行中、所属 agent 是否在线）禁止改名（demand 未要求）。
- 不含**多用户 / 权限**边界——本迭代沿用既有的单用户全局边界，不引入按用户 / 按角色的改名权限（`demand.md` v0.2.0 的边界条款为 N-1~N-7，本条不在其中，属沿用既有产品全局边界而非新增需求条款）。
- 不含**归档动作与关闭动作本身**（属 0013 已交付能力与本迭代的既有只读面，本卡只引用其结果，不修改其行为）。
- 不含只读对话能否发送消息 / 能否激活等既有行为的任何改动（既有行为，非本迭代范围）。

## 架构维度（阶段 3 已填，2026-09-11；详见 `architecture.md` §4.1 / §4.2 / §6.5）

- **AR-08 只读判定的落点**：**共用同一判据，不分叉**。把 0013 既有、当时**内联**在 `web.js:515-522` 的表达式 `chat.archived_at !== null || chat.state === 'closed'` 提取为模块级具名谓词 **`isReadonly(chat)`**，并让**两处服务端 409 共用它**：`POST /api/messages`（既有；**求值结果、文案与状态码逐字不变**）与 `POST /api/chats/<id>/rename`（本次新增）。前端同样提取一份**同值**（字面顺序 `closed` 在前——`web.test.js:1235` 的既有静态契约断言按该顺序逐字匹配，故前端字面受其约束；`||` 交换不影响求值结果）的 `isReadonly(chat)`（`app.js`），让"标题能否进入编辑"与"「关闭对话」按钮是否禁用"（原 `:165` 的内联表达式）**共用它** ⇒ 前端也不再存在第二处判定。持久层另设**结构性兜底**：`stmts.renameChat` 的 `WHERE ... AND archived_at IS NULL AND state != 'closed'` 与谓词同值（SQL 无法调用 JS，故是同规则的第二次字面书写，不是第二套口径；未命中 ⇒ `changes = 0` ⇒ 上层报 409，**不静默成功**）。**三处同值、须同步修改**（`architecture.md` §4.1 代码注释已标注）。可判定等价（验收 3）：任取一条对话，"可否改标题" ⇔ "可否继续发送消息" ⇔ `isReadonly(chat) === false`。**文案与判据分离**：两条 409 的**文案**按操作语义不同（「不可改名」/「不接受新输入」），**判据**同值——文案差异不是口径分叉。
- **AR-09 只读对话标题"点击无响应"的呈现承载**：**交互侧**——`h1` 上只绑一个点击处理函数（`beginTitleEdit`），其首行按 `!chat || isReadonly(chat) || state.titleEdit !== null` return ⇒ 只读（已归档 / 已关闭）与空态点击**无任何反应**：不进入编辑态、不弹提示、不产生第二个处理分支，标题保持纯文本（验收 1、2、5）。**视觉侧**——`renderTitle(chat)` 只在可编辑时给 `h1` 挂 `.editable`（`cursor: text` + 悬浮浅边框，且几何与 `.detail-title-input` 对齐以免进出编辑时标题跳动）；只读与空态不挂类 ⇒ `cursor: default`、无悬浮态，与同屏既有的只读线索（禁用的「关闭对话」按钮、状态徽标、「· 已关闭（只读）」）一致。**不新增"不可改名"文案**：验收 1/2/5 只要求"不进入编辑态"，再加文字属重复信息。
