## 第一段：澄清依据

### 1. 用户原始表述（2026-09-11，user_confirmed）

> 对话支持修改名字，直接在右侧详情修改标题即可。目前默认以第一个对话作为标题

**目标陈述拆解**：用户要的是"给对话标题一个手动兜底"——当前标题由系统按首条输入自动生成且只生成一次，用户无法纠正；本迭代加入"在详情区直接改名"这一条最小能力，**不改变自动生成规则**。

**对原话中现状描述的纠偏（重要）**：用户说"目前默认以第一个对话作为标题"，与代码实际不符——实际规则是**以该对话的首条输入消息**为标题（不是"第一个对话"；对话本身即 chat，不存在"以另一个对话作标题"的机制），且只在标题首次写入时生效，后续输入不改标题。该纠偏不影响本次"做什么"（用户要的就是手动改名，且已确认生成规则不变），但记录在此，避免后续阶段沿用错误前提。锚点：`persist.js:203`、`persist.js:145-149`。

#### 4.2 逻辑闭环 —— why 能否推出 what

- **Why**：自动标题是"首条输入截断"，同一用户的多条对话经常得到难以区分的标题；用户需要一个手动兜底给对话起名。
- **What**：在详情区提供"点击标题 → 改名"这一条最小路径，**不改生成规则、不改排序、不改对话内容**。从 why 可推出 what：只有"手动覆盖"能解决"自动标题不可控"；而列表的空间记忆要求"改名不重排"——D-4 与 why 一致。
- **发现一个需要显式记录的后果**：改名**不会**触发列表重排（D-4），因此改名后该对话仍停在原位、显示时间（`updated_at`）不变。这与"改完名立刻能在最上面找到它"的直觉相反（人会期待刚操作的项跳到最前），但与用户已确认的决策一致，必须写入结论避免实现后的争议——这是本迭代唯一一处"反直觉但已确认"的设计。

#### 4.3 边界完整性

用户**明说**的边界两条：**在右侧详情改**（= 不做左栏入口）、**自动生成规则不变**（D-2）。其余"不做什么"（第二段 §2）均为推导所得，逐条给出"为什么这次不做"。

#### 4.4 内部一致性

| # | 矛盾 / 约束 | 处理 |
|---|---|---|
| C-1 | **改名若刷新 `updated_at` 会直接违反 D-4"不改排序位置"**：主列表按 `updated_at DESC` 排序（`persist.js:196`），改名一旦写入 `updated_at`，对话会跳到列表顶部 | 改名只能写 `title` 单列，**不得触碰 `updated_at`** |
| C-2 | **不能复用 `upsertChat`**：其 `ON CONFLICT DO UPDATE ... WHERE chats.state != 'closed'` 会让 closed 对话改名**静默失败**（`changes=0` 且不检查返回值），且它覆盖 `agent_id`、刷新 `updated_at`，并且**完全不检查 `archived_at`** → 复用会让 D-3 / D-7"归档 / 已关闭不可改"这条边界根本不生效 | 需要一条**独立的单列写语句**（已确认 D-13；具体形态留架构阶段） |
| C-3 | 只读判定口径可能分叉：现有代码把 `archived_at !== null \|\| state === 'closed'` 视为**同一个只读面**（`web.js:515-522`、`app.js:165`）；若改名只排除 archived，则出现"能改名但不能发消息"的 closed 对话 | 已确认（D-7）：改名判定与现有只读面**统一为** `archived_at !== null \|\| state === 'closed'`，二者不分叉 |
| C-4 | 自动生成规则与改名是否互相干扰 | 无冲突：`ensureChat` 是 `DO NOTHING` → 改名后用户再发消息**不会**把标题改回首条输入 |
| C-5 | 搜索按标题命中（`persist.js:66` 的 `q` 匹配 `c.title`）→ 改名后搜索结果随之变化 | 属改名的**自然收益**（让对话可被新名字检索到），非副作用，无需处理 |
| C-6 | 详情标题与空态文案共用 `#detail-title`（`app.js:156` 空态 vs `:163` 详情） | 编辑能力只在 `state.chat` 存在时启用；空态（未选对话）不可编辑（D-15） |

第二段 §4 每条效果已过裸判定测试：不点名工具、不依赖背景知识、第三方可直接观察判断真假（读写标题、观察列表与详情、重启服务）。

### 3. 大概怎么做（产品级形态；写口命名 / 接口形态 / 语句写法留架构阶段）

- 前端把详情头标题变为**可点击进入编辑的行内输入控件**；编辑能力仅在该对话存在且**不处于只读面**时可用（复用 `app.js:165` 已有的只读判定表达式 `archived_at !== null || state === 'closed'`）；输入框硬上限 100（`maxlength`）。
- 需要一条**只写标题一个字段的写入路径**：只更新 `title`，**不得刷新 `updated_at`**（C-1）、**不得覆盖 `agent_id` / `state` / `archived_at`**；因此**不能复用 `upsertChat`**（C-2）。写口命名（如 `POST /api/chats/<id>/rename` 或 PATCH）与语句写法留架构阶段。
- 校验规则（trim、非空、≤100）在**服务端**执行；前端以 `maxlength=100` 做输入硬上限并做即时反馈；错误语义沿用项目既有约定（拒绝 → 保持原值 / 不写入）。
- **无需数据层变更**：`title` 列已存在，无新列、无迁移。
- 已知受影响的既有契约（属已知成本，实现阶段同步更新）：`web.test.js:1000+` 的前端静态契约正则、`README.md` 的左栏 / 右栏描述与 API 表需新增改名说明；`persist.test.js:233-244`（生成规则）与 `web.test.js:419-431`（后续输入不改标题）**必须保持通过，不得修改**。

### 5. 为什么这么做

- **为什么是"手动改名"而不是"改自动生成规则"**：自动标题的问题在于"它不一定对"，而任何规则都无法替用户判断"这条对话叫什么"；给一个手动覆盖入口，成本最低、收益直接（用户已确认生成规则不变）。
- **为什么点击即编辑、不用编辑按钮**：详情头只有标题一个可编辑对象，多一个按钮 = 多一次点击与一个永久冗余的控件（user_confirmed）。
- **为什么空标题拒绝、而不是回退「新对话」**：兜底值会让多条空名对话在左栏无法区分（M-3）。
- **为什么 100 而不是沿用 40**：40 是"自动截断"的容差上限，不是用户手动表达的合理上限；100 给用户足够表达空间，同时保持单行标题可控（user_confirmed）。
- **为什么归档与已关闭都不可改、改名不改排序**：三者都是"只读面一致"与"列表空间记忆"的直接推论（user_confirmed，D-7 / D-4）。
