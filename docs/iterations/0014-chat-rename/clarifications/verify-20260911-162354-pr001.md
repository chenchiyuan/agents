## 下一迭代候选

- **写口未校验 `chatId`**：`renameChat({ title })`（缺 `chatId`）与 `chatId: undefined` 会由 `node:sqlite` 抛 `TypeError: Provided value cannot be bound to SQLite parameter 2`，错误族与「标题非法」不一致；`chatId: null` / 数字类型则静默 `null`（无匹配行）。当前 PR 卡未定义该边界，也无静默成功风险，但 web 侧 `/rename` 路由若未先做路径参数校验，缺字段请求将落到外层 catch → 502 而非 400。建议 PR-002（rename 端点）在路由层以 `readBody` 既有形态先行校验，或下一迭代为写口补 `chatId` 校验。
- **`readTitle` 未导出**：当前只能经 `renameChat` 间接测试；若 web 路由后续需要在入库前做"预检 400"（例如为了先判只读再判标题，保证 409 优先于 400），会需要复用该函数或产生第二处校验实现——建议在 PR-002 定案优先级后回看是否需要导出（架构 §5.2 已定义 404 → 409 → 400 的顺序，故该需求可能真实存在）。
- **手动标题无 DB 层长度约束**：>100 的标题可被绕过写口的直接 SQL 写入（架构 §3.3 已记录否决 `CHECK` 的取舍理由）。属已知接受的取舍，若后续出现第二个写口（例如批量导入）需重新评估。
