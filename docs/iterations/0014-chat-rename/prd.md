## 本次迭代边界说明

### 包含

- **标题行内编辑与提交**（A-1 → F01）：详情区标题点击即进入编辑；编辑框预填当前标题并全部预选；Enter 保存、失焦保存、Esc 取消；取消或未改动不发生保存；保存失败恢复原值并提示；保存结果持久化（重启仍在）。
- **标题校验**（A-2 → F02）：保存前去除首尾空白；长度上限 100 字符；空或全空白拒绝保存并恢复原值（**不**回退为「新对话」）；同一组规则在保存的完整链路上生效，不依赖编辑框单点。
- **标题只读边界**（A-3 → F03）：已归档对话的标题不可进入编辑；已关闭（未归档）对话同样不可；未归档且未关闭的对话可改；空态文案不可编辑；只读判定与既有只读面一致，不分叉。
- **同步范围与排序不变**（A-4 → F04）：改名成功后详情头与左栏对应项立即显示新标题；该对话在左栏的位置不变，最近更新时间不变（不置顶）。
- **自动生成规则不变**（A-5 → F05）：新建对话标题仍 = 首条输入去首尾空白后截断 40 字符（空则「新对话」），只在首次写入时生成；`@agent` 前缀计入；改名后再次发送消息，标题保持手动值。

## 拆分理由（原子粒度判断）

- **按"可独立出现的失败"拆成 5 张，而不是"1 张改名大卡"**：本迭代的失败模式有五个互相独立的观察面——①点不出编辑框 / 保存不了（F01）；②能保存但接受了非法标题（F02）；③能改名但只读边界错，归档或关闭的对话也被改了（F03）；④能保存但左栏不更新、或改名把对话顶到列表最前（F04）；⑤改名的实现把自动生成规则弄坏了（F05）。任一失败都不蕴含另一项失败，也不依赖另一项的修复，因此每张卡都能被独立测试、独立交付。
- **F01 与 F02 分拆（交互与校验）**：A-1 判"用户能不能发起并提交一次改名"，A-2 判"什么内容允许被提交"。交互完好但校验错（全空白被存成空标题）、或校验完好但交互不可达，都是可独立出现的失败；两者共用一次保存动作但判定面不同，故不合并。
- **F01 承载"失败恢复"与"持久化"**：M-10（保存失败的恢复与提示）与 E-8（重启后仍在）都是"这次保存动作"的结果属性，脱离 F01 的提交动作没有独立触发条件，故并入 F01 作为验收 5 与验收 4，不另立卡片。
- **F03 独立成卡（只读边界）**：A-3 的失败模式是"编辑入口对不该开放的对象开放了"，与"编辑本身能不能用"（F01）正交——最典型的独立失败是"未归档对话改名完全正常，但归档对话也能被改名"。
- **F04 独立成卡（同步与排序）**：A-4 的失败模式是"保存成功了但界面或列表没同步 / 位置被改"，发生在保存动作**之后**，与保存动作本身（F01）和校验（F02）都是独立失败。其中"不置顶"（C-1 / N-5）与"左栏即时更新"共享同一次保存后的观察窗口，故同卡。
- **F05 独立成卡（回归约束）而非常规功能**：A-5 在 `demand.md` 中是"做什么"条目（用户明确确认"自动生成规则不变"），其失败模式是"新增的改名能力污染了既有自动命名路径"——这是本次改动引入的新回归风险，必须有一条可独立测试的卡承载（E-9 / E-10），否则该风险无人验收。本卡只声明"既有行为保持不变"，**不新增任何能力**。
- **未单立"输入单位计数"卡**：M-9（UTF-16 code unit）是 F02 验收 2 的计数口径，脱离长度上限没有独立交付物，故并入 F02。
- **未单立"受影响既有契约同步"卡**：`demand.md` §3 列出的已知受影响契约（前端静态契约断言、README 描述与 API 表）属实现的已知成本，不构成独立功能能力，列为全局 `[架构待填]` AR-13，不另立卡片（另立会构成 demand 之外的新增功能点）。
