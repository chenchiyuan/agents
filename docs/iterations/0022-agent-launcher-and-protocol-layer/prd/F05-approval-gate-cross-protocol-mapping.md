**迭代**: 0022-agent-launcher-and-protocol-layer
**产品对象（引用 `demand.md` 只读实测，非本阶段决策）**: 既有确认面 = 7 字段信封 `confirmation_id / chat_id / agent_id / tool / title / options / created_at` → 收件箱 → 既有裁决回路（`confirmation_id` + 选项 + 文本）；三事件通知 `chat_completed` / `chat_failed` / `confirmation_required`

## 用户价值

换了协议，危险的调用照样会停下来等我拍板——而且一次调用只问我一次，不多问也不漏问。

## 验收标准

1. **上浮到既有确认面**（W4 / M4 / F12）：rpc 链路下的工具审批门请求进入**既有确认面**——以既有 **7 字段信封**（`confirmation_id / chat_id / agent_id / tool / title / options / created_at`）落到收件箱；裁决沿用**既有回路**（`confirmation_id` + 选项 + 文本）。
   *判定*：rpc 链路触发一次受门禁调用 → 收件箱出现该条且 7 字段齐备；裁决后该轮据此继续或中止。
2. **不重不欠**（E4 / F16）：一次受门禁工具调用在 rpc 链路下**恰好产生一条确认项**（条目数 = 1）；裁决后**条目消失**。
   *判定*：数确认栏条目数（= 1）+ 看该轮是否推进 / 中止 + 条目是否消失。
3. **字段集合与语义等价、值域随协议声明**（A3/P5）：两条链路在**字段集合与语义**上等价；**值域随协议能力声明**——RPC 下选项**恒为二元** `Approve` / `Deny`；**不要求跨协议逐字等价**（不要求把 `Approve` 翻译成 acp 侧的选项名）。
   *判定*：对照两条链路的确认条目 → 字段与语义一致；rpc 选项恰为二元；不存在"要求跨协议选项名逐字对齐"的断言。 〔呈现形态与多行 `title` 的呈现见 T-08〕
4. **工具名复用既有提取原语**（A3/P5 / F15）：rpc 下 `tool` 名从审批门的 `title` 提取，**复用既有提取原语**（两者同源）；`title` 含多行不影响提取结果。
   *判定*：取 rpc 门的多行 `title` → 提取出的 `tool` 名与既有原语在该形态下的结果一致。

## 边界（不包含）

- 不含门在确认栏与通知里的**呈现形态**（含多行 `title` 如何呈现，→ T-08）。
- 不含 **acp 侧门的改造**（N12 / A4：acp 保持现状、不补能力）。
- 不含确认面的**承载形态 / 生命周期 / 路由**（0021 既有，本迭代不新增 —— 见 F10 与 0021 的既有边界）。
- 不含 RPC 是否可能存在第二道门的**实测**（→ 移交阶段 3 承接项 M-5；若存在第二道门，需要合并策略，属阶段 3 处置）。
- 不含宿主工具面（`hostTools` / 宿主 UI 请求）的形态与是否实现（→ T-09）。
- 不含已裁决项的历史 / 审计台账（0021 既有边界，本迭代不触碰）。
- 不含为"跨协议逐字等价"做任何翻译层（A3/P5 明文不要求）。
