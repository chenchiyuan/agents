## 用户价值

以后接一个新 agent（claude / codex），只是加一份启动配置数据，不用改通讯与展示那两层的代码。

## 验收标准

1. **统一服务管理「起 agent」这件事，并由它定义协议 / 标准**（W1 / U-2 / J1 / A2）：启动管理是**一个统一服务**，不是一个写死在调用点的动作；所有 host 的会话启动都经**同一入口**，该入口可服务**多个宿主**（不是一个宿主一条独立启动路径）；**由它定义协议 / 标准**——会话语义接口（开会话 / 提示 / 取消 / 关闭 + 三类增量 + 两类反向请求 + 能力位）作为标准被写定，对外表达"怎么起、怎么说话"。
   *判定*：以两个不同宿主的启动配置各起一轮 → 二者都经该入口成立、入口不因宿主不同而分叉；且查调用点 → 各调用点**没有各自的启动 / 会话写法**，用的是**同一份被写定的标准**（标准的**内容**由 F02 验收 1 判、**签名**留 T-04，本卡不重复判）。 〔`[user_confirmed MI-02]`：用户原话口径「有统一的服务管理启动agent这件事情，定义协议/标准，抽象方法和工具使用」；标准的形态与签名留 T-01 / T-04（本卡只判"标准被写定且被统一使用"）〕
2. **启动信息数据化，工具使用按同一标准表达**（W1 / U-2 / M1）："怎么起一个 agent 进程"的信息以**可直接编辑的数据形态**（profile）承载，而不是写死在会话语义里；**工具使用（工具开关）**等取值也在这份数据里按同一标准表达，不散落在各调用点。
   *判定*：改 profile 的取值（模型 / 角色 / 工具 / 权限任一项）→ 会话按新取值启动；改取值不需要改会话语义与展示层的代码。 〔`[user_confirmed MI-02]`：用户原话口径「…抽象方法和工具使用」；承载形态留 T-02〕
3. **新增宿主 = 新增 profile 数据**（E7）：新增一个宿主（claude / codex 中任一）只需**新增一份 profile 数据**，协议层与消费层源码**零改动**。
   *判定*：加一份 profile → `git diff` 看协议层与消费层源码，为空即真。
4. **claude / codex 只留 profile 结构与能力位**（N1 / J1）：本迭代**不做**它们的真实接入与实测。
   *判定*：查本迭代产物 → 只有 profile 结构与能力位，无真实接入链路、无实测证据。

> 备注（§内容维度，**非验收阈值**）：`demand.md` W1 括注列出 profile 的内容维度 = 宿主 / bin 解析 / argv 构造 / env / cwd / 模型 / 角色 / 工具 / 权限。该清单来源为非结论材料，本阶段**仅登记为内容维度参考**，其形态（字段集 / 字段名 / 序列化）留 T-02；见 `prd.md`「MI 判定口径」报告级事项 1。
