## 2. W8 定稿：依赖注入口径与判据全文（本轮核心改写）

**用户口径（逐字，A1）**：

> 这里应该使用依赖注入模式，指定协议（此协议如果已经实现），通讯层就应该使用该协议。

**由该口径推导的需求表述（写入 W8）**：协议实现以**注入**方式提供给通讯层；**指定已实现的协议即生效**（被注入的实现就是被使用的实现，**硬要求**，不是尽力而为）；消费层不自行构造 / 不自行选择协议实现；切换协议只改**注入配置**一处，消费层代码不变。

**可机械复核判据（写入 §2 的 W8 子表）**：

| 判据 | 内容 | 机械复核方式 |
|---|---|---|
| D-1 注入点决定实现 | 协议实现的选取只发生在注入点（注入配置 / 解析链）；通讯层实际使用的实现 = 注入点给出的实现（指定即生效，不回落内置默认） | 指定 `acp` 起一轮 → 该轮走 acp；指定 `rpc` → 走 rpc。**指定后仍走内置默认即为不通过** |
| D-2 消费层不自行构造 / 选择 | 生产消费层不存在具体协议实现的构造、导入，也不存在按协议取值的分支 | grep 生产消费层：无具体协议实现符号的导入 / 构造、无按协议值分支 |
| D-3 切换只改注入配置 | 切换 = 改一处注入配置；消费层源码 diff 为零 | 切换前后 `git diff` 看生产消费层：为空 |

**未采纳口径的显式记录（防误引）**：

- kickoff §五 的「判据① 源码中不出现协议名与 argv 字面量 / 判据② 切换只改一处配置且 L3 diff 为零 / 判据③ 新增宿主只加 profile」三条原文 —— **未采纳，不作为结论**（A1 明确）。
- 「只留判据②」这一退让方案 —— **未被接受**。
- 因此 **D-2 不是旧判据① 的改写**：D-2 的对象是「**具体协议实现的构造 / 选择行为**」，不是「协议名 / argv 字符串是否出现」；选择点（注入点）本身可以命名协议，这正是依赖注入语义的必然结果。
- 「新增宿主只加 profile 数据」（原判据③）**不作为 W8 判据**，而由 **W1**（U-2 + J1）与 **E7** 承接，避免超出 A1 的改写范围。

**顺带闭合的一致性问题（本轮新发现并当场闭合）**：用户括注「此协议如果已经实现」在本迭代 **恒成立** —— 选择域 = {`rpc`, `acp`}（A2）且两者本次均落地（J1 + J2）⇒「指定未实现的协议」**不存在合法入口**；越界值处理属既有配置校验范畴，不进需求结论。故 D-1「指定即生效」无悬空情形，也无需新裁决。
