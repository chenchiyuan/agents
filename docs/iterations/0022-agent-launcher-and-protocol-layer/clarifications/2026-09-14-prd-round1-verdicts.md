## MI-01 · F04「三类增量不被丢弃」的验收落在哪一层

用户原话过程：
1. 第一次回：「没明白具体意思，需要详细沟通」
2. 第二次回：「需要具体讨论起含义。我没懂你表达的意思」
3. 主 agent 改用具体验收动作表（A 在数据传输层数 / B 在控制台里看）解释后裁决。

**裁决 = 分两处判**：

- **F04（管道面）**：验收时**不看浏览器**，在 hub 与 omp 进程之间流动的数据里数三类——(1) 思考片段、(2) 工具调用参数（边生成边流出）、(3) 工具执行中的输出——三类都数得到即通过。管的是"管道有没有把三类东西带上"。
- **F08（界面面）**：验收时打开控制台对话详情，确认这些内容**确实在界面上出现**。管的是"界面有没有把它画出来"。
- 理由（用户选择该判法的实际收益）：界面上看不到时，能区分是**管道丢了**（F04 的问题）还是**管道有、界面没接**（F08 的问题）；两卡各自独立可测。
- 不得把 F04 的判据并进 F08（那会让两卡判据面重叠、"思考被丢掉"这类问题失去独立可测面）。

## MI-02 · 「统一起会话入口」怎么算统一

**用户原话（逐字）**：「有统一的服务管理启动agent这件事情，定义协议/标准，抽象方法和工具使用」

**主 agent 提出的范围选项与用户确认**：

| 选项 | 用户裁决 |
|---|---|
| **(A) 落在现有需求内，作为验收口径** | ✅ **已选** |
| (B) 超出本迭代，记为新需求、开下一迭代 | ✖ |

**生效口径（F01 / F02 / F09 的验收据此表述）**：

1. **统一服务管理「起 agent」这件事**——启动管理是一个统一服务，不是一个写死在调用点的动作；
2. **由它定义协议/标准**——会话语义接口作为标准被写定（开会话 / 提示 / 取消 / 关闭 + 三类增量 + 两类反向请求 + 能力位）；
3. **抽象方法面与工具使用**——方法面（会话动作）与工具使用（工具开关、宿主工具面）按同一标准表达，不散落在各调用点；
4. 上述三条**均落在已落盘需求 W1 / W2 / M6 范围内**（F01 / F02 / F09 承载），**不新增功能点**；形态细节仍留 T-01~T-05。

## MI-03 · 能力位候选清单在验收中的定位

**裁决 = 可表态检查点**：验收时只要能力位「可表态」（每一项候选能力都可被协议显式表态：有 / 无 / 降级），**不是**最终集合门槛；最终集合与签名留阶段 3（与 M6 的 `[架构待填]` 一致）。

## MI-04 · F07「oneshot 无会话语义」怎么判

**裁决 = 产物/日志显示 + 无续接行为**：两条可观察信号——
(i) 该轮的执行记录 / 日志能看出这一轮走的是一次性启动方式；
(ii) 前后两轮之间无上下文续接（例如第二轮问它"上一轮问了什么"答不上来，或查不到该对话的常驻会话对象）。
