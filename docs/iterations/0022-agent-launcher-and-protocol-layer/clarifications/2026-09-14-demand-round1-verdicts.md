## 逐项裁决

### 1 · 提案 P1（零侵入判据）—— **用户改写了口径（非三选一）**

用户原话（逐字）：

> 这里应该使用依赖注入模式，指定协议（此协议如果已经实现），通讯层就应该使用该协议。

主 agent 的转述边界（只做搬运与拆句，不做技术决策）：

- 口径从「源码里出现不出现协议名」改为 **依赖注入**：协议适配器以**注入**方式提供给通讯层；
- **指定某协议（且该协议已实现）时，通讯层必须使用被指定的那个实现**——即"指定即生效"是硬要求，不是尽力而为；
- 因此 W8 的判据需要重写为可复核的注入语义判据（例如：协议实现在注入点决定、消费层不自行构造/选择协议实现、切换协议只改注入配置且消费层代码不变）。
- 用户**未**确认 kickoff §五 的三条判据原文，也**未**接受"只留判据②"——三条判据按用户口径重新推导，旧措辞不作为结论。
- 适用范围以第 8 项裁决为准（仅生产消费层）。

### 2 · 提案 P2（协议指定粒度与入口）—— **采纳**

配置面 + 角色级覆盖 + 全局默认 + 内置 `rpc`；选择域 = 常驻会话协议（`rpc` / `acp` 二选一），`oneshot` 不在选择域；不做 per-chat / per-request 指定；不做控制台可切。

### 3 · 提案 P3~P6 —— **四项全部采纳**

- P3 L2 需求级语义面 = 会话四动作（开会话 / 提示 / 取消 / 关闭）+ 三类增量回调（文本 / 思考 / 工具）+ 两类反向请求回调（审批门 / 宿主 UI）+ 能力位显式声明（缺能力必须显式降级）。
- P4 展示落点 = 复用按对话的运行时通道（等价 `task_update` 语义），不新增 UI 载体、不做透出开关/过滤策略、不入库。
- P5 确认面口径 = 字段集合与语义等价、值域随协议能力声明（RPC 恒二元 `Approve` / `Deny`）；不要求跨协议逐字等价。
- P6 验收证据 = rpc 真实 omp 链路端到端一条（思考增量可见 + 受门禁调用一次上浮与裁决 + 不入库核查）+ acp 兜底链路回归一条。

### 4 · 待裁决 V1（acp 兜底是否能力对齐）—— **选 (a) 仅保留 + 显式声明降级**
