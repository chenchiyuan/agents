## 0. 本轮性质与硬性限制

- 本 agent 运行在**无实时对话通道**的子 agent 中，**无法直接与用户对话**。
- 因此「提案 → 用户确认」循环的**每一轮都落盘到本文件**：提案（推断 + 理由 + 推荐填法）在此，**未获用户明确确认的推断一律标 `[model_inferred]`**，集中列在 §5 与本文件末尾的**转呈件清单**，由主 agent 阻塞式转呈用户裁决后，再派发 demand 做下一轮。
- **零自问自答**：本轮不把任何 `[model_inferred]` 当作已确认，也不替用户回答 §7 的方案雏形询问。
- 开工前 4 项用户裁决（kickoff §四）是 `user_confirmed`，**不重新提问、不推翻**。

### 2.3 事实 → 需求的直接后果（推导，非产品判断）

- **F7 + F8 + F10 + F11** ⇒ U-2 / U-3 的痛点实测成立：换协议要同时动三处（argv、消费层 import、任务面分派），且 argv 知识有两份。这不是"想优化"，是"接入成本线性增长"。
- **F9** ⇒ U-4 的目标今天**物理上不可达**（思考在客户端被丢弃）——所以 U-1「rpc 更适合」不只是启动方式偏好，它同时是**可观测性的前置**。
- **F15 + F6** ⇒ kickoff **R1 的严重度需下调**（登记②）：RPC 的 `title` 形状与 ACP 审批门**同源**，`tool` 名提取可复用既有原语，剩余差异只在**选项值域**（二元 Approve|Deny vs `allow_once`/`reject_once`）。
- **F16** ⇒ RPC 是**单门二元**：一次受门禁调用在 RPC 下只产生一条上浮请求 ⇒ W4 的「不重不欠」是可在验收层直接数出来的判据（E4）。
- **F14 + F12 + F19** ⇒ 过程增量与确认面**都已有挂靠点**：本迭代是"接线 + 抽象"，不是"新造语义"——这支撑 N2（不改 omp）。
- **F17 + F18** ⇒ kickoff **R4 可量化**（登记③）：抽象层会移动代码，且既有测试面**本身携带协议知识**（argv 断言），最小更新是必然动作；「零侵入」判据的适用范围因此成为必须裁决的口径问题（V2）。

### P1 · 「零侵入」判据的内容（推荐：三条全采纳）

- **草稿更新**：W8 的判据写为三条 —— ① L3 生产源码中不出现协议名（`'acp'` / `'rpc'`）与 argv 字面量；② 切换协议只改**一处配置**，L3 生产源码 diff 为零；③ 新增一个宿主（claude / codex）只新增 profile 数据，L2 / L3 源码零改动。
- **理由**：U-3 提出的是"希望零侵入"，而 kickoff §五 给的正是这三条可复核判据（**这是主 agent 的建议文本，不是我或用户的结论**，故按提案处理）。三条各自都有机械判法（grep / `git diff` / diff 面），可过裸判定；缺判据则 W8 无法验收。
- **适用范围未定**：判据 ① 是否适用于**测试面**（F17 的 6 个文件 argv 断言）→ 见 V2。
- 如果不对，请直接说改成什么（例如：只保留判据 ②、或要求 ① 扩到全仓）。

### P2 · 协议「指定」的粒度与入口（推荐：配置面 + 角色级覆盖 + 默认 rpc）

- **草稿更新**：协议选择点**唯一且落在配置面**；解析链 = 角色级配置 > 全局默认 > 内置 `rpc`（体例对齐既有模型解析链：请求 > env > 角色级 > 全局 > 内置）；**选择域 = 常驻会话协议（rpc / acp 二选一）**；`oneshot` **不在该选择域内**（它由 web 的「一次性」勾选选中，与常驻协议并存）；不做 per-chat / per-request 指定。
- **理由**：① J2 说"配置可切回 acp 兜底"⇒ 入口在配置面；② P1 判据 ②「切换只改一处配置」与"控制台可切"不兼容（后者会引入新 UI/API + 在飞上下文迁移问题）；③ 选择域澄清来自登记①：`rpc`/`acp` 是**互斥的常驻会话协议**，`oneshot` 是**执行方式**（无会话语义），两者不在同一维度上，混在一个枚举里会让"协议"这个概念在后续阶段失真。
- 如果不对，请直接说改成什么（例如：希望控制台里也能切、或希望每个角色之外还能按 agent 实例指定）。

### P3 · L2 接口的需求级语义面与能力位候选清单（推荐：会话四动词 + 三类增量 + 两类反向请求 + 显式能力位）

- **草稿更新**：L2 内部接口的需求级语义面 = ① 会话动作：开会话 / 提示（prompt）/ 取消 / 关闭；② 三类增量回调：文本、**思考**、工具（参数与输出）；③ 两类反向请求回调：审批门、宿主 UI 请求；④ **能力位显式声明**（候选清单：`streaming` / `thinking` / `approvalGate` / `hostTools` / `introspection` / `queueControl`），缺能力必须**显式降级**而不是静默缺失。
- **理由**：F2（完成 ≠ 受理）、F3（三类增量）、F5（反向请求）逐条来自 RPC 实测；F9/F16 说明 acp 与 rpc 的**能力不同**，不显式声明能力位就会在消费层产生"偶发缺失"的隐形分支。签名与最终清单仍 [架构待填]。
