## 组 A · 契约形态（机制长什么样）

### P-1 · 「寻址契约」是否就是 v0.9.0 启动契约的正确替代形态？★

- **问题**：v0.9.0 用「cwd 判据 + 硬停」把会话钉在工作区里；用户原话排除了这种强制。替代方案是「会话声明自己的工作区地址，此后所有写操作显式寻址它」吗？还是用户心中的"定义好 git 的工作方式"指的是别的东西（例如用环境变量 / 参数把工作区传给会话）？
- **选项**：
  - **① 推荐**：**寻址契约** —— 会话开始时**解析并声明**自己的迭代工作区地址，此后所有**文件写入**用该地址下的绝对路径、所有 **git 写操作**用 `git -C <该地址>`；不依赖 cwd、不依赖任何工具。规则 C / 规则 D 的判据全部重写为"地址声明 + 寻址正确性"，规范与 SKILL 两份载体同改（沿用 0019 的 v0.9.0 ↔ v1.12.0 同步体例）。
  - ② 只删掉规则 D 的判据 1（cwd）与硬停，其余不动（保留判据 2/3 作为"如果会话恰好在工作区里"的可选核对）。
  - ③ 换机制：用环境变量 / 命令行参数把工作区地址固定注入会话（例如 `GIT_DIR` / `GIT_WORK_TREE` 或 `git -C` 包装）。
- **推荐理由**：①是**唯一同时满足用户四条约束**的形态 —— 无工具依赖（全部 git 原语 + 文本纪律）、不依赖 cwd、不需要会话自迁移目录、不需要宿主提供新能力；且它把"绑定"建立在一个**协议可控**的信号上（显式地址），而不是宿主行为（cwd 的传递）。②会留下一半的 cwd 依赖，且"可选核对"给不出一个可判定的合规状态（判据存在但不必成立 = 判据失效）。③在本项目里已被 0019 用户裁决排除了同类型方案（P-8 答复排除"依赖工具"的解法），且 `GIT_DIR`/`GIT_WORK_TREE` 会绕过 worktree 的既有语义，引入新的失败模式。
- **不确定时的影响面**：本项决定 P-2 ~ P-16 的**全部写法**。若选②，E1（任意位置启动仍可交付）无法成立（判据 2 仍排除主工作区启动）；若选③，本迭代范围重置，需重开澄清轮。
- **R-1（参考视角，不是架构结论）**：寻址契约把正确性从"环境"移到"纪律"。纪律的代价是**它不会自己生效**：0017 的 pr-003 dev 在自己的 worktree 里仍然误写了主工作树三笔（`0017/history.md:204`），当时的 `cwd` 判据对它毫无作用。反过来说，0019 那次"dev 用相对路径写进主工作区"（`0019/history.md:377`）之所以能被**发现**，靠的是 dev 自己主动上报 —— 不是任何自动判据。你若要的是"错不了"，寻址契约给不了；你若要的是"能说清楚该在哪写、且事后查得出来"，它给得了。**这个取舍是本轮最需要你亲自确认的一点**（对应 P-13）。

### P-2 · 硬停保留给什么？★

- **问题**：用户说"不应该对使用者有任何强制"。硬停（发现即停、不产生任何写入）是否还需要保留？保留给什么情况？
- **选项**：
  - **① 推荐**：**硬停只保留一个触发面** —— "本会话的迭代工作区**无法确定或无法创建**"（客观失败：解析不出、创建被 git 拒绝、路径被占用等）。硬停的语义是"协议无法工作"，不是"你做错了"；输出形态不再含"请你去做某事"的祈使句，只说明失败事实与可选的人工干预点。
  - ② 完全取消硬停（任何情况都继续推进，把问题记入搭置文件）。
  - ③ 保留现有硬停，只把判据从 cwd 换成"地址未声明"。
- **推荐理由**：①保留了协议的**失败可见性**（静默地把产物写错地方比停下来更贵），同时把触发面收敛到"客观失败"而非"人的行为不正确"。②会让"工作区根本不存在"这种情形也往下跑，产物落在哪不可预测 —— 等于把本迭代要修的静默写错问题制度化。③把"未声明地址"当硬停，等于给会话加一个新强制点，且与"寻址纪律事后可核查"的模型重复（同一件事既有硬门又有事后核查）。
- **不确定时的影响面**：决定 E4 的写法；也决定 P-3（工作区缺失时是自建还是硬停要人来做）。

### P-3 · 「不强制使用者」的边界：工作区不存在时，谁创建？★

- **问题**：现状下"建工作区"是一个**人的前置动作** —— 0018 `status.md:24` 原文写「**操作前置（宿主限制，必须由用户执行）** …… 本迭代的恢复会话需以 **cwd = 上述会话工作区** 启动」。用户说"不用我 cd 到对应目录"、"不应该对使用者有任何强制"：那么 ① 人是否仍需**先建好**工作区？② 人的启动位置是否可以就是仓库主工作区？
- **选项**：
  - **① 推荐**：**会话自建 + 人零前置** —— 工作区地址可确定性解析（P-5）；解析出的路径**不存在时由会话自己**按固定命令创建（这仍是规则 F 闭集例外① 覆盖的动作），创建成功即继续；只有**创建失败**才硬停（P-2 ①）。人不需要 cd、不需要预先执行任何命令、可以在仓库主工作区启动。覆盖范围 = **仓库内任意位置启动**（含仓库根、任意子目录、任一已存在的 worktree 内）。
  - ② **人零 cd，但仍需预先建工作区**（保留"前置命令"，只去掉 cd）。
  - ③ 会话自建，但**仓库外任意 cwd** 也要保证（把"项目中"扩展到"任何地方"）。
- **推荐理由**：①把 U-5 的"强制面归零"做到彻底，且成本极低（创建命令已存在，只是把执行者从人换成了会话 —— 会话本来就要在阶段 1 之前建好这个工作区，v0.9.0 只是把这一步派给了人）。②只解决了 U-3，仍与 U-5 冲突，且"忘了建"的失败模式（发现即停）仍在。③超出用户原话（U-1 说的是"在项目中启动"），且需要额外机制来确定"哪个仓库"，属新范围（对应 N8）。
- **不确定时的影响面**：决定 E1 / E4 的写法；也决定"创建失败"是否成为唯一硬停面。若选②，"人零前置"不能写成效果。
- **与既有条款的关系（`实测`）**：规则 F 的闭集例外① 是「会话工作区的**创建**动作（它必然发生在目标工作区之外）」—— 该例外**不预设由谁执行**，故会话自建不违反规则 F，无需新增例外。

### P-4 · 「仓库主工作区不作为任何迭代的会话工作区」在新模型下如何重述？★

- **问题**：v0.9.0 规则 C 有一句「**仓库主工作区不作为任何迭代的会话工作区。**」，且规则 D 判据 2 明确"排除在仓库主工作区里启动"。新模型允许在仓库主工作区启动，这句话要改成什么？
- **选项**：
  - **① 推荐**：**拆成两句** ——「主工作区**可以**作为会话的**启动位置**；它**不得**作为任何迭代的**工作区**」。同时明确主工作区的**写入面**：对它的写入仍受跨工作区写入禁止（规则 F）约束，闭集例外之外不得写入；`main` 上的合并动作仍固定在主工作区执行（既有裁决不变）。
  - ② 干脆允许主工作区充当会话工作区（去掉这一整句）。
  - ③ 保留原句，只是把"启动"从"工作区归属"里剥离（措辞不动）。
- **推荐理由**：①保住了这句话原本要防的事 —— 主工作区是多会话共享目录，一旦被当工作区用，就回到 0017 的事故形态（三会话共用同一工作树）；同时不再与 U-1 冲突。②的危险是具体的：0017/0018 的事故正是"主工作区被判给某一迭代"造成的（`028ca8a` 落到他人分支、未跟踪产物混合）；且 `main` 与迭代分支的检出冲突（"同一分支不能两处检出"）会让主工作区无法同时承担两个角色。③会让读者仍以为"不能在主工作区启动"（判据 2 的排除句还在），与 U-1 冲突未解。
- **不确定时的影响面**：决定 E6 的写法；也决定规则 C 首句与规则 D 判据 2 的改写幅度。

### P-5 · 工作区地址怎么"定义到指定路径"？（确定性推导 vs 显式指定）

- **问题**：用户说「worktree **定义到指定路径**就能工作」。这个"定义"是谁做的、以什么形式？
- **选项**：
  - **① 推荐**：**默认确定性推导 + 允许显式覆盖** —— 默认从共享 `.git` 推出仓库主工作区，再据迭代 ID 推出地址 `<仓库主工作区>/.pb-agents/worktrees/{迭代ID}`（与 0019 已生效的落点裁决一致，零新增约定）；同时允许由人 / 主 agent **显式给出一个地址**覆盖默认值（"定义到指定路径"就是这个动作）。
  - ② 只允许确定性推导（不接受显式指定）。
  - ③ 每次显式指定（取消默认推导）。
- **推荐理由**：①同时满足"零动作"（默认路径不需要任何人输入）与用户字面的"定义到指定路径"（人若要指定就能指定）。②会让人无法在特殊场合（不同磁盘、外包目录）指定落点，且用户原话的"定义到"暗示存在这个动作。③每迭代都要人输入一个路径 = 新增一个前置动作，与 U-5 冲突。
- **不确定时的影响面**：决定 E1 / E2 的判据形态（推导不出来时如何判定失败 → 与 P-2 的硬停面联动）。

## 组 B · 寻址的载体（地址写在哪儿）

### P-6 · 声明落在什么产物里？

- **问题**：会话声明的工作区地址必须**可被第三方核查**（否则寻址纪律无从核对）。写在哪里？
- **选项**：
  - **① 推荐**：**两处** —— ① `status.md` 增加一个「会话工作区」字段（本迭代的 `status.md` 已有一个同名的临时字段，见其头部；0018 的 `status.md` 也有"会话工作区"一行），② **每次派发的简报**新增「工作区地址」字段（见 P-7）。两处都是**声明**（不是发现），第三方读任一产物即可知道该会话在哪个工作区工作。
  - ② 只写 `history.md`（事件流水）。
  - ③ 不落盘，只在会话的输出里说明。
- **推荐理由**：①与既有产物形态一致（`status.md` 是迭代级视图、brief 是派发契约），零新增文件类型。②`history.md` 是逐条追加的事件流，地址声明是**会话级常量**，每次派发都追加一遍是噪声，且早期记录会被后来者淹没。③不可核查 —— 会话结束后无从追溯。
- **不确定时的影响面**：决定 E2 的判定方式；若选②/③，"地址已声明"无法作为裸判定判据。
- **术语附注（`实测`）**：v0.9.0 混用「会话工作区」与「迭代工作区」两词。寻址模型下工作区**归属迭代**、会话只是它的使用者 —— 字段命名取"会话工作区"还是"迭代工作区"由用户定（推荐沿用既有两处已出现的"会话工作区"字样，减少改动面）。
- **R-2（参考视角，不是架构结论）**：若把地址写进 `status.md`，注意 `status.md` 是**迭代级**视图而地址是**会话级**事实：同一迭代被两个会话接力（0018 的暂停 / 恢复就是这种形态）时该字段会被后一个会话覆盖。若你认为"一次迭代只会有一个会话"，这不是问题；若要留痕，需另加会话标识（那会扩大改动面）。

### P-7 · 简报必须携带绝对地址、产物路径以它为根？★

- **问题**：0019 事故的直接成因是**简报里用的是未限定的相对路径**，而 dev 的 cwd 是仓库根（`0019/history.md:377`：14 次编辑落在主工作区）。同时现行规范与 SKILL 的简报字段清单**都没有"工作区地址"字段**，而文档路径协议却把相对路径的基准定在"会话所在的迭代工作区根目录"上 —— 会话一旦不在该目录，基准就消失了。
- **选项**：
  - **① 推荐**：**简报两级寻址纪律** —— ① 简报新增「工作区地址」字段（绝对路径）；② **所有产物路径以该地址为根写出**，相对路径不得作为唯一寻址方式；③ 文档路径协议的基准句从"该会话所在的迭代工作区根目录"改为"**该会话声明的工作区地址**"。规范与 SKILL 两侧同改。
  - ② 只在简报里加一个"注意用绝对路径"的提示句，不改文档路径协议与字段清单。
  - ③ 维持现状，靠执行角色自觉。
- **推荐理由**：①直接对准事故的机械成因（基准缺失 + 相对路径），改动面小（一个字段 + 一句基准句），且**可核查**（读简报即可判定）。②提示句不是契约：没有字段承载时，产物路径的基准仍无处安放，判定者也无法核对"简报给没给地址"。③已验证无效 —— 0017（`0017/history.md:204`）与 0019（D-5）两次事故都发生在"自觉"之下。
- **不确定时的影响面**：本项不裁决，则 P-1 的寻址契约**缺载体**，E2 无法成立；也是本迭代与 0019 D-5 唯一的直接对接口。

### P-8 · 需要显式的 supersede 声明吗？取代哪些句子？★

- **问题**：本迭代不是新增条款，而是**改写** v0.9.0 刚交付的规则 C / 规则 D。是否必须在规范里显式声明"哪几句被取代"？如果是，清单多长？
- **选项**：
  - **① 推荐**：**要，逐句**。在 v0.10.0 变更说明中列"被取代的 v0.9.0 句子"，并在规则 C / 规则 D 正文内写"本版取代 …"。拟定的被取代清单（5 条）：① 规则 D 判据 1（`--show-toplevel` == `pwd`）作为启动门；② 规则 D 判据 2（`--git-dir` ≠ `--git-common-dir`）作为**启动门**（其"当前是否链接工作区"的事实判定能力可保留于其他用途）；③ 规则 D 判据 3 作为**启动门**（其"该工作区检出 `iteration/{迭代ID}`"的断言转为**工作区属性**核对）；④ 规则 C「会话必须运行在自己的会话工作区里」与「随后会话在该工作区根目录内启动」；⑤ 规则 D 的硬停形态块与启动工作流首段（引用三条判据的那句）。**同时保留**：规则 C 的「每迭代一个工作区」「落点 `…/worktrees/{迭代ID}`」「PR worktree 为子层」。
  - ② 只写 v0.10.0 变更说明，不在规则 C / D 正文内留痕。
