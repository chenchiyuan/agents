## P-17 · 协议产物落在 `<项目根>/.pb-agents/` 下的**精确落点与跟踪方式**（含三处地址落点的分层）

### 问题（一句话）

用户要求把"工作区间 + 规范"写成 `<项目根>/.pb-agents/` 下的协议产物；但**本仓库的 `.gitignore` 第 2 行是 `.pb-agents/`，整个目录被忽略** ⇒ 产物**不会随 `git worktree add` 出现在任何新会话工作区里**（本迭代的会话工作区里 `ls .pb-agents` 确认不存在），于是"会话在自己的工作区里读不到自己的协议"。**要怎么解决这个冲突？**

**一条必须说明的技术事实**（决定选项②的代价）：`gitignore(5)` 明文规定「**被排除的目录下无法再用负例规则包含文件**」—— 只要第 2 行仍是 `.pb-agents/`，新加 `!.pb-agents/协议产物/` 是**无效的**。所以"纳入跟踪"不是加一行，而是要把第 2 行**改写**成 `.pb-agents/*` 之类，再加负例。

### 选项

#### ① 主工作区本地声明（不跟踪）

- **做法**：产物落在 `<仓库主工作区>/.pb-agents/<协议产物>`，**不被跟踪**（零 `.gitignore` 改动，因为该目录本来就被忽略）。任何位置的会话都通过"解析主工作区"（`git rev-parse --git-common-dir` 的父目录）拿到它的**绝对路径**再读它 —— 与"显式寻址"同源，也与 `.pb-agents/worktrees/`（工作区池本来就在主工作区下）同一锚点。产物缺失时由会话按规范模板**自建**（与 P-3① 的"会话自建"同精神）。
- **代价**：① 会话**创建/更新**该产物是一次**跨工作区写入** ⇒ 必须把规则 F 的**闭集例外从 2 项扩到 3 项**（本轮未裁决该扩展，选①就要一并裁决）；② 新 clone、新机器、任何没跑过会话的检出里**没有**这份产物；③ **无版本历史、无 diff**，改动不可追溯；④ 与 0019 W8 的取向**相反** —— 0019 刚裁决"真源 = 被跟踪内容"，并把 `.pb-agents/` 副本降级为"下游可选分发手段"（`demand.md` §2.2 F16）。
- **收益**：零 `.gitignore` 改动；**单点**（全仓只有一份声明）；与工作区池同锚点。

#### ② 纳入跟踪（**demand 推荐**）

- **做法**：产物落在 `<项目根>/.pb-agents/<协议产物>`，**被 git 跟踪**；落地方式 = 把 `.gitignore` 第 2 行由 `.pb-agents/` **改写为** `.pb-agents/*`，并新增负例 `!.pb-agents/<协议产物子路径>`。产物随检出即得 ⇒ 会话在**自己的工作区里**就能读到，**无需跨区读、无需自建、没有"读不到协议"这一失败模式**。
- **代价**：① 本迭代须改一次 `.gitignore`（**0019 曾把它列为零改动面** —— 这是要用户点头的地方）；② 与 0019 W8 对 `.pb-agents/` 的"下游可选分发、不纳入跟踪"表述有**局部张力**，需在 v0.10.0 变更说明写明"**仅协议产物子路径纳入跟踪；`roles/`、`principles/` 的分发语义与 install 脚本行为零变化**"；③ 产物在 N 个工作区各有一份副本 —— 但它承载的是**项目级静态声明**，各副本应一致（不一致会直接出现在 `git status` 里）。
- **收益**：**零跨区写、零规则 F 例外扩展**；新机器 / 新 clone 随检出即得；有版本历史与 diff；与 0019 W8 的"真源 = 被跟踪内容"**同族**。
- **变体 ②-b（不推荐，仅供知悉）**：不改 `.gitignore`，用 `git add -f` 强制跟踪（已跟踪文件不受 ignore 影响）。技术上可行，但反直觉、每个新文件都要 `-f`、容易被后续提交误操作 —— **不推荐**。

#### ③ 不新增产物（基线对照）

- **做法**：认定"协议先行"已由既有的被跟踪规范（`roles/workflow-pb/workflow-pb.md`）满足，`.pb-agents/` 下不新增任何文件。
- **代价**：**直接违背用户原话**（「写入项目根目录的.pb-agents/ 下面」「定义好工作区间和规范就行了」）。列在此处仅为让用户看到"不做"的代价。

### 推荐

**②（纳入跟踪）**。理由三点：① 唯一能同时满足"用户原话的落点要求"与"0019 已生效的『真源 = 随检出即得的被跟踪内容』取向"的选项；② 消除"会话在自己的工作区里读不到自己的协议"这一失败模式，且**不需要**给跨工作区写入开口子（规则 F 的闭集例外保持 2 项）；③ 代价集中且可见（一次 `.gitignore` 改写 + 一段变更说明），而 ① 的代价是分散的（例外扩展 + 无版本历史 + 新检出无产物）。

### 影响面（无论选哪个都要一并定的两件事）

**（a）三处地址落点的分层（同源问题）**

载体出现后，"工作区地址"这个事实会有**三个落点**。demand 推荐**分层**，不建议替代或并列：

| 层 | 落点 | 承载什么 | 性质 |
|---|---|---|---|
| 源 | **协议产物**（`.pb-agents/` 下） | **静态**：工作区间规则 + 本项目生效的规范与其版本 | 项目级、单点 |
| 投影 1 | `status.md` 字段 | 本迭代的会话工作区 | 迭代级 |
| 投影 2 | 简报字段 | 本次派发的绝对地址（`git -C` 用） | 派发级 |

不一致时以**协议产物**为准，并在 `status.md` / 简报中登记差异。**硬约束**：本次运行的**动态地址**只能落 `status.md` / 简报，**不得写进被跟踪的协议产物** —— 否则每次会话都会产生一次仓库改动，与规则 A/B（变更必须走 PR worktree）相撞。

**（b）与 0019 W8 /「角色定义来源与部署」的一致性**

- **对象不同，不构成直接冲突**：W8 管"角色定义从哪读"，P-17 管"工作区间与规范的声明落在哪"。
- **取向须一致**：选② = 取向一致（真源随检出即得）；选① = 在本迭代内重建 0019 刚废除的"读不随检出即得的 `.pb-agents/` 副本"模式。
- **选②时须写进变更说明**：`.gitignore` 改写**不改变** W8 的任何结论 —— `roles/`、`principles/` 仍被忽略；`install-pb-agents.sh`（先 `rm -rf roles/ principles/` 再 copy）行为零变化。

## 参考视角（不进结论段，**无需裁决**）

> 以下三条来自"如果是 architect 会怎么看"的角度，已逐条标注"这是参考视角，不是架构结论"。第一轮的 R-1（"寻址纪律不会自己生效"）已由用户裁决**升级为 W14**（越界不可阻止 = 显式已知代价），故不再列出。

- **R-2 · 声明字段的迭代级 / 会话级错配**：把地址写进 `status.md` 时，同一迭代被两个会话接力会覆盖该字段（0018 的暂停 / 恢复即此形态）。若认为"一次迭代只会有一个会话"，这不是问题；若要留痕需另加会话标识。`[INFERENCE]`，未实测。
- **R-3 · 事后核查的实际盲点**：一次"相对路径写入"到底落在哪，取决于**执行者的 cwd**，而 cwd **不写在任何产物里**。因此"取一次执行记录逐条比对写入路径"（规则 F / 0019 E13 的判定方式）在路径不是绝对路径时，判定者只能看出"它不是绝对路径"，**看不出它实际落在哪**。若要让越界事后可判定，记录里需要的是**动作的 cwd 或绝对路径** —— 建议阶段 3 定形判据时一并考虑。`[INFERENCE]`，基于 F4/F6 的报告文本形态推断。
- **R-4 · 一个新的暴露点（未实测）**：`git worktree add <路径> -b iteration/{迭代ID} …` 在**该分支已被别处检出**时会被 git 拒绝（"同一分支不能两处检出"是硬约束）。0019 的形态正是"主工作区检出 `iteration/0019-…`"—— 若在那种状态下按寻址契约去建 0019 的工作区，git 会拒绝。⇒ 解析与创建步骤需要包含"该分支是否已被检出"这一核对，并给出可恢复的失败输出（与 W11 的硬停面联动）。具体判据形态留阶段 3。
