### 维度 2 · 逻辑闭环（★ 本轮最严重缺口）

**比对方式**：以「消除 0017/0019 四类损害」为已确认的 why，检验两种"绑定"形态。

| 形态 | 检验 | 结论 |
|---|---|---|
| (a) **入口绑定**（v0.9.0：把会话的 cwd 钉在工作区里） | 代理判据（F4：cwd 与写入落点不等价；F5：cwd 正确仍会写错）+ 宿主层不可靠（F7）+ 成本转嫁给人（F3、0018 `:24`） | 用户已排除（U-1/U-3/U-5）；**其失效不依赖用户偏好，已有独立一手证据** |
| (b) **寻址绑定**（声明 + 显式寻址） | 能推出 E1~E4 的前提 = 工作区物理分离（已有）+ 所有写入被显式寻址（新增） | **成立，但引出三条必须显式处理的补偿缺口 ↓** |

**缺口 ①（★ 最严重）· 风险从"无法开工"变成"静默写错"**
v0.9.0 用"发现即停"把「会话不在工作区」前置消灭；换成寻址后，**会话忘记寻址 = 写入静默落错地方**，事后才发现（F4/F5 即此形态的真实样本）。⇒ 需求层必须**显式接受这一残留风险**并规定补偿（声明 + 可核查记录 + 事后判定），不能把"寻址纪律"说成等价于"硬停"。→ P-13。

**缺口 ② · 寻址的载体（简报）目前没有地址字段**
规范 `### 派发执行角色时的 brief 构建` 与 SKILL `§ Brief 构建规则` 的字段清单**均无"工作区地址 / 落盘根路径"**（F8）；而 `## 文档路径协议` 把相对路径的基准定在"该会话所在的迭代工作区根目录"上 —— 会话不在该目录时**基准消失**，四个执行角色只能按自己的 cwd 猜落点。⇒ 这是 F4 的直接机械成因，也是本迭代最直接的修复面。→ P-7。

**缺口 ③ · 宿主层不可控**
"cwd 是本会话工作区"取决于宿主如何设置子进程 cwd（阶段 5 的子 agent 尤其），**协议无法保证**（F7 实测该口径未成立）。⇒ 用户 U-4「这是git协议的问题」读作：把正确性建立在**协议可控**的东西上（显式地址 + git 原语），而不是宿主行为。→ P-1 / P-15。

**反向比对（what → why）**：寻址契约是否仍对着"会话身份与工作区身份无绑定"？**是** —— 绑定改由「声明 + 寻址」承担，只是把人从绑定公式里去掉（人不再被强制）。
