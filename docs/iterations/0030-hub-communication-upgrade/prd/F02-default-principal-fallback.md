# F02 · 缺省身份兜底（不声明身份也有收件箱）

**来源**：demand.md 做什么#1（"无论是否显式传 `requester`，都保证有一个可查询的身份"）；§大概怎么做（送达："不传时用 `chat:<chat_id>` 派生缺省身份"）；决策 D-21；效果#1；HB-02（主 agent 无身份 ⇒ 结构性收不到结果）；决策文档 §六（"缺省身份与显式 `requester` 同时存在时的优先级/合并规则"指派给本阶段）

## 用户价值

我**不需要记得**"派发时要声明身份"这件事——不声明，结果照样有地方可取；默认路径就是正确路径。

## 验收标准

1. **不声明身份也有收件箱**：调用方**不传** `requester` 派发一次 `mode=background` 调用 ⇒ 该调用终态后仍可从取件面取到（身份 = 按 `chat_id` 派生的缺省身份）[D-21；效果#1"无论调用方是否显式声明身份"]。
2. **派生粒度 = `chat_id`（不细分到 `agent`）**：同一 `chat_id` 下多次派发（含派给不同角色）⇒ 都落在同一缺省身份的取件面上；不同 `chat_id` ⇒ 落在不同缺省身份上 [决策文档 决策 2"兜底粒度"；D-21]。
3. **派生形式对调用方是确定性可推导的**：缺省身份的字符串形式（`chat:<chat_id>`，口径见 MI-2）由调用方**无需读服务端状态**即可自行构造 ⇒ 调用方能自发拼出取件查询 [D-21"照常生效"的可操作性前提]。
4. **显式优先、不合并**（[model_inferred MI-1]）：请求同时具备显式 `requester` 与 `chat_id` 时，取件归属取**显式声明**；不双写、不做两者合并、不产生第二条条目。
5. **调用方零额外操作**：不传身份时响应面与迭代前逐字一致（不新增必填参数、不因缺省派生而报错或新增告警）[D-21"调用方无需额外操作即获得必达保证"；G01 验收 10]。

## 边界（不包含）

- **不做鉴权**：不校验身份与实例的同一性（唯一相关动作是既有 0029 F14 的自派发告警，本卡不动它）[体例沿用 0029 D-2]。
- **不做"身份缺失 ⇒ 拒绝派发"**：缺省兜底就是"不强制身份"的实现方式，禁止把它变成新的必填前置 [D-21 明文"不强制"]。
- **不改变显式 `requester` 的既有校验**：非法值仍按既有错误口径拒绝（空串归属"未显式声明"从而触发兜底，见 MI-3）。
- **不做多身份合并 / 转发 / 别名映射 / 身份托管**。
- **不改变显式身份路径的既有响应契约**（含 0029 的 `warnings` 出现条件）[G01 验收 10]。
- 不做身份的注册/查询语义变更（既有身份面不动）。

## 架构维度

**A-02（已填定，全文见 `architecture.md` §4 A-02）**

- **派生点（唯一）** = `/api/calls` handler 的逐项装配处：`principal = 显式 requester ?? 'chat:' + chatId`（既有代码已把空串归一为 `null` ⇒ MI-3 天然成立）；结果写进 `call.principal`（由 `call.requester` **改名**，仍是进程内单字段）。
- **承载与传递路径** = `call.principal` → `entry.call` → `publishCallResult` → `inbox.principal` 列；**不进** UDS 信封、**不进** Router 任务表。
- **合流位置** = 该三目本身：显式优先、不合并、不双写（MI-1），无第二分支；`warnings` 的出现条件仍只看出否**显式**给出身份 ⇒ 验收 5「不传身份时响应面逐字一致」由构造满足。
- **取件面过滤实现** = `WHERE principal = ?`（SQL 单条件）；`chat:<chat_id>` 形态满足既有 `validPrincipalId`（实测 46 字符 ≤64、全可打印 ASCII）⇒ 取件端点参数校验**零新增分支**；缺省身份**不写入** `principals` 表（它是纯过滤键，登记面只服务显式声明与自派发判定）。

## model_inferred

- **MI-1**（验收 4 的口径）：demand 只写"缺失时兜底"，未定义**显式 `requester` 与 `chat_id` 同时存在**时的优先级/合并规则（决策文档 §六 明确把该项留到本阶段）。本卡按"显式优先、不合并、不双写"落卡，等主 agent 确认。
- **MI-2**（验收 3 的口径）：demand 与决策文档均以"例如 `chat:<chat_id>`"举例，未把该字符串形式定为契约。本卡按"缺省身份形式确定性可推导（`chat:<chat_id>`）、取件面接受该形式"落卡，等主 agent 确认。
- **MI-3**（验收 3 的边界情形）：demand 只说"缺失"，未定义 `requester` 传空串时的归属。本卡按"空串等同未显式声明 ⇒ 触发缺省兜底"落卡（与既有实现"空串按 `null` 处理"一致），等主 agent 确认。
