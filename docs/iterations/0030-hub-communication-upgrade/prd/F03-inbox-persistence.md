# F03 · 收件箱轻量持久化（跨 hub 重启仍可查）

**来源**：demand.md 做什么#2；§大概怎么做（送达："必然写入 inbox（SQLite 新表），只在终态发布那一刻写一次"）；决策 D-22；效果#2；事实 F-2（现状取件面为进程内表）；决策文档 §六（"inbox 表的清理策略"指派给本阶段）

## 用户价值

hub 重启一次不再等于"没取的结果就没了"——"必达"不再挂在"进程别重启"这个隐藏前提上。

## 验收标准

1. **跨重启仍可查**：派发一次 `mode=background` 调用，等其到达终态且**不做 ack** ⇒ 重启 hub 进程后，同一身份再次取件**仍能取到**该终态结果 [效果#2]。
2. **ack 后不再出现**：已 ack 的条目在重启前后**都不出现**在未取件集合中（持久化不改写既有确认语义）[既有面保持；G01 验收 4]。
3. **只在终态写一次、不承载流式进展**：处于 `submitted`/`working` 的调用在持久层**无记录** ⇒ 重启后未终态调用不出现在取件面上（不存在"半成品记录"）[做#2"只在终态发布那一刻写一次"]。
4. **持久化范围仅限收件箱**：Router 任务表仍纯内存、重启即丢；重启后既有调用登记行为与迭代前一致（对重启前的 `call_id`，既有调用面仍按既有"不存在"口径回答）[不做什么#1；D-22]。
5. **内容前后一致、且不是第二真源**：重启前后取到的同一条结果内容一致；持久化不引入独立的状态/正文副本语义（不伪造、不覆盖）[D-14 延续；F01 验收 5]。

## 边界（不包含）

- **不做 Router 任务表全面持久化**（原方案 3-C 延后，不是本迭代）[不做什么#1；D-22]。
- **不做流式进展的持久化与落盘节流**：写入只发生在终态一个时间点 [D-22；决策文档 决策 3"明确不做的事"]。
- **不做归档 / 导出 / 历史台账面**：持久化只服务"取件面必达"。
- **不做跨重启的其它内存投影恢复**（订阅、等待句柄、实例投影等不随之持久化）。
- **不在本卡决定收件箱条目在存储层的清理策略**（ack 后何时移除、如何抑制无限增长）：上游决策文档把该项指派给本阶段，本阶段判定它属**实现层**决策（不影响调用方可见行为），落 [架构待填] A-09，不在本卡拍板。
