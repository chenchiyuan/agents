# F05 · 空闲超时判据 + 绝对安全网（取代固定总时长上限）

**来源**：demand.md 做什么#4；§大概怎么做（超时）；决策 D-26 / D-27（空闲阈值 10 min）/ D-28（安全网 4 h）/ D-29（触发后统一 `reason=timeout`）；效果#4；事实 F-5（30 分钟为**绝对总时长**，非空闲检测；三个实测案例产物提前 20~26 分钟落盘仍空转到 30 分钟，合计浪费 70 分钟）/ F-6（`last_event_at`/`idle_ms` 已存在但未驱动任何判死逻辑）；HB-01（本迭代最贵的一条）

## 用户价值

一个一直在干活的长任务**不会因为"跑得久"被砍**；真正停下来的任务仍会有人收尸——不再出现"产物早落盘、调用还空转二十多分钟"。

## 验收标准

1. **长任务不因累计时长被判死**：构造一个持续产出进展信号（`task.update` 类）且累计时长远超旧上限（30 分钟）的任务 ⇒ 只要进展信号持续出现，调用**不**被判死（终态不是 `failed`）[效果#4 前半；D-26]。
2. **停止产出进展后才判死**：构造一个停止产出进展的任务 ⇒ 距最后一次进展信号超过空闲阈值（初始值 10 分钟）后该调用被判死，终态 `state=failed` 且 `reason=timeout` [效果#4 后半；D-27；D-29；边界口径见 MI-7，计时起点见 MI-8]。
3. **绝对安全网独立生效**：构造一个"持续有噪音信号但无有效进展"或累积时长超长的调用 ⇒ 距开始时间超过绝对安全网（初始值 4 小时）后仍被判死并落 `reason=timeout`；同时确认安全网**不是**常态判据（阈值内的正常长任务不受其影响）[D-28；阈值边界口径见 MI-7]。
4. **两种触发在人类可读面可区分**：空闲触发与安全网触发的 `error`/`detail` 文本可区分，`reason` 均为 `timeout`、不新增子枚举 [D-29；F04 验收 3]。
5. **阈值是初值、可调**：10 分钟 / 4 小时为本迭代初始取值；调整阈值不改变调用方可见的语义契约（只改数字）[D-27 / D-28"初始取值，可调"]。
6. **判死走既有唯一终态路径**：超时判死后，取件面、订阅面、等待面看到的是**同一条**终态（不是第二个真源、不出现"某面还是 working"）[F01 验收 5；G01]。
7. **判据取代既有上限的全部生效位置**：不存在"某条执行路径仍按固定 30 分钟截断"的残留（含 `mode: block` 的调用路径——事实 F-5：上限在通道层不可绕）[D-26；F-5]。

## 边界（不包含）

- **不做"可续做"**：撞上限不转 `suspended`、不提供继续/产物不重做的语义（HB-01 备选②未入选，demand 无对应条目——见 prd.md 疑问 4）[不新增 demand 之外功能点]。
- **不在调用面新增 `timeout` 参数**（HB-01 备选①未入选，demand 无对应条目）。
- **不做"剩余额度 / 已用时长"投影**（HB-01 备选③未入选）。
- **不看产物、不判断交付是否完成**：判据只看进展信号 [不做什么#2；D-25]。
- **不修惰性启动竞态**（`completed` 但产物缺失）[不做什么#7]。
- **不做实例级 / 看门狗级判死**：本卡只覆盖**调用级**判死；hub 不管理实例生命周期 [不做什么#4；D-30]。
- 不做判死后的自动重派 / 重试。

## 架构维度

**A-05（已填定，全文见 `architecture.md` §4 A-05）**

- **进展信号源的接入点** = 轮次内的**每一个增量事件**（`onDelta`：`chunk` / `thinking` / `tool_call` / `tool_output` / `stdout` 行 / `truncated` 控制条目）+ 轮次开始事件（`started`）。这与 MI-7 的"`task.update` 类事件（复用既有 `last_event_at` 口径）"是**同一批事实**：agent 对每个增量都调 `sendUpdate('working', …)` 产出 `task.update`，Router 记 `updated_at`（既有 `last_event_at` 的来源）。
- **计时落点 = 执行侧轮次计时原语**（既有 30 分钟绝对上限的**同一实现处**，`acp-client` / `rpc-client` / `oneshot-client` 各一份同构实现）改为 `idle`（自最近一次进展或轮次开始起算，达 `taskIdleMs` 判死）+ `net`（自轮次开始起算，达 `taskNetMs` 判死）**双计时**；**门挂起冻结语义保留**（人工审批/提问等待期间两个计时器同冻结，0029 L1-1 不回归）。不新增 web 看门狗、不新增 Router 判死（避免第二判死源与僵尸轮次）。
- **两条执行形态的统一实现位置** = 上述轮次计时原语**一处**：`mode:block` 只是 web 侧 HTTP 挂起（`call.resolve`），执行路径与 `background` 完全相同 ⇒ 验收 7 的 `mode:block` 项由构造满足，web 侧零新增分支。
- **阈值配置面位置** = `src/config.js` 的 `loadConfig()`：`taskIdleMs`（默认 `600000`）/ `taskNetMs`（默认 `14400000`），env `OAMP_TASK_IDLE_MS` / `OAMP_TASK_NET_MS`（沿用既有 `readPositiveInt` 校验，非法即启动报错）；env 的存在理由 = 验收 5「初值可调」+ 阶段 5/6 必须压缩时间轴取证（先例 = 既有 `OAMP_WEB_RECONCILE_*` 的"供测试压缩时间轴"）。
- **判据取代既有上限的全部生效位置**（验收 7 的可核对清单）：① `agent.js DEFAULT_OMP_TIMEOUT_MS`（默认档）**移除**；② `acp-client.prompt` 默认 `1800000` **改为双计时**；③ `rpc-client DEFAULT_TURN_TIMEOUT_MS` 同上；④ `oneshot-client DEFAULT_TIMEOUT_MS` 同上；⑤ `agent.js MAX_TIMEOUT_MS` **保留**（只约束"调用方显式声明的上限"，不再是默认截断）；⑥ **`web.js RECONCILE_TTL_DEFAULT_MS`（30 分钟）默认值与 `taskNetMs` 联动**（**不变式**：缺省 TTL ≥ `config.taskNetMs`；算式 = `taskNetMs + RECONCILE_SLOW_DEFAULT_MS` = 4h + 30s，env `OAMP_WEB_RECONCILE_TTL_MS` 覆盖保留）（口径随实测更正，2026-09-17）——**不联动即破 F01**（登记被清后，长任务的终态在 `handleDeliver` 查不到 `entry` 被丢弃 ⇒ 永不发布；代码注释自述"覆盖关系由有余变为持平，待优化"）；⑦ `shell` 的 `timeout_ms` **保留**（命令硬上限语义）；⑧ 客户端等待预算（`sdk/cli.js` / `surface.js` 的 30 分钟）**不改**（`API.md` §2.4 明文"超时只表示放弃等待"，非判死位置；后果见 `architecture.md` §9-6）。
- **显式 `timeout_ms` 的边界裁决**：语义**不变**（调用方声明的本轮绝对上限，≤30 分钟），仅移除"缺省即 30 分钟"这一档；理由 = shell 命令需硬上限、显式值是调用方显式预算、call 面不暴露该参数 ⇒ 效果#4 的全部观测面都在新判据下。
- **触发后**：仍走既有失败收口（`ProtocolError('timeout')` → `task.result{state:'failed', error:'timeout'}` → Router 唯一终态写点 → web 唯一发布点）⇒ 落 `reason=timeout`、取件/订阅/等待三面同一条（验收 6）；两种触发在**人类可读文本**中区分（ProtocolError message，落既有 `text` 或 `error`），**不新增枚举值/子层级**（D-29）。

## model_inferred

- **MI-7**（验收 2/3 的边界口径）：demand 只给阈值数字，未定义边界判定（`>` 还是 `≥`）与"什么算进展信号"。本卡按"**达阈值即判死**、进展信号 = `task.update` 类事件（复用既有 `last_event_at` 口径）"落卡，等主 agent 确认。
- **MI-8**（验收 2 的口径）：demand 未定义空闲计时的起点。本卡按"**计时起点 = 调用开始时刻**（即'开始到首个进展信号之间'同样受空闲阈值约束）"落卡，等主 agent 确认。
