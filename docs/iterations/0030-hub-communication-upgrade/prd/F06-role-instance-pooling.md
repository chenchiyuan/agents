# F06 · 角色实例池化与并发分流

**来源**：demand.md 做什么#5（"允许一个角色对应多个已在线的实例"）；§大概怎么做（并发："查询当前在线的角色实例池"）；决策 D-30（池化、hub 不管生命周期）/ D-32（固定配置、不做伸缩）；效果#5 前半；事实 F-7（`ContextPool` 按 `(chat_id, agent_id)` 单 in-flight）/ F-8（角色↔实例硬编码 1:1）；HB-04（单实例串行：真实吞吐 = 1）

## 用户价值

一个角色**不再等于一个排队口**——我起两个实例，两条派发就真的能并行跑，而不是被"槽位并发"骗着排队。

## 验收标准

1. **并发分流**：手动启动**同一角色的两个在线实例**后，对同一角色的**两条不同 `chat_id`** 的调用并发派发 ⇒ 两条调用被分派到**不同实例**上执行（不再因单实例串行而排队等待）[效果#5 前半；D-30]。
2. **单实例情形不回归**：同一角色只有**一个**在线实例时 ⇒ 派发行为与迭代前一致（既有单实例路径不回退、不因池化改造而报错或额外排队）[事实 F-8；G01]。
3. **池成员 = 当前在线实例**：路由只在"当前在线的同角色实例"中选择；离线实例不参与 [D-32"hub 只感知当前在线的池子有几个"]。
4. **hub 不管理实例生命周期**：hub **不**启动、不关闭、不伸缩实例（不出现"池里只有 1 个 ⇒ hub 自动再拉起一个"或"闲置 ⇒ 自动回收"的行为）；池中实例数完全由使用者决定 [D-30；不做什么#4]。
5. **池化与既有身份面不冲突**：一次派发在既有投影/响应面上仍能看出落在哪个实例（沿用既有实例标识，不新增第二套标识）[D-31 的可判定前提；G01]。

## 边界（不包含）

- **不做无状态负载均衡**（池内任意实例接单、不保证会话延续——已否决路径）[不做什么#5；D-31]。
- **不做实例生命周期管理**：不自动拉起 / 关闭 / 健康重建 [不做什么#4；D-30]。
- **不做动态扩缩容 / 按负载伸缩**：固定配置 [D-32]。
- **不做队列深度 / 占用者的新投影面**（HB-04 的可见性诉求无 demand 条目，见 prd.md 疑问 4）。
- **不做跨角色共享实例、不做一实例承载多角色**。
- 不改变既有 `ContextPool` 的键语义（同 `(chat_id, agent_id)` 的串行/上下文复用仍是既有语义；池化改变的是"落哪个实例"，不是"同一实例内怎么排队"）[事实 F-7；F07 验收 4]。
