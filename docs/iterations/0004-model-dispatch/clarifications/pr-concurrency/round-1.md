# PR 并发执行 - Round 1

## 大原则确认

### 目标

默认并行执行无真实依赖的 PR；显式表达真实依赖；提高多 agent 交付吞吐，同时保持 worktree 隔离、合并顺序可控、失败可恢复。

### 范围

- 包含：workflow-pb、workflow-scm、commit-planner、planner 的 PR 调度与协议；PR 依赖声明；多 PR worktree；并发执行与串行合并；依赖失败隔离；协议校验。
- 包含：后续迭代采用新协议的迁移规则。
- 不包含：本轮实际 dispatch runtime / harness 的实现；该实现后续按本轮协议单独落地。
- 不包含：已存在的 0004-model-dispatch PR 文件迁移；新协议仅影响后续迭代。

---

## 讨论清单

### CLR-PC-001: 默认调度采用显式 DAG 并行

- **模糊点**：现有 workflow-pb、commit-planner 和 architecture 文档要求主 agent 按 PR 文件列表逐一派发，导致真实可并行任务被串行执行。
- **影响范围**：PR 派发吞吐、主 agent 调度方式、任务依赖处理。
- **推荐选项**：采用显式 DAG 调度协议；无依赖 PR 默认并行，真实依赖按 DAG 顺序推进。
- **结论**：采用方案 A。默认并行 ready PR；只有显式依赖约束顺序。并发上限受 executor 容量限制。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-002: PR 依赖必须显式声明

- **模糊点**：当前 PR 文件没有机器可读的依赖字段，依赖只存在于自然语言上下文中。
- **影响范围**：ready 判断、循环检测、恢复调度、并发安全性。
- **推荐选项**：每个 PR 强制声明 `depends_on`；独立 PR 显式写 `depends_on: []`；缺失字段校验失败。
- **结论**：强制声明 `depends_on`；独立 PR 写 `depends_on: []`。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-003: 依赖以实现完成解除

- **模糊点**：依赖是在前置 PR merge 后解除，还是在前置实现已完成后解除。
- **影响范围**：并发吞吐、下游启动时机、分支堆叠。
- **推荐选项**：前置实现完成即解除，以 commit SHA 作为下游可消费快照。
- **结论**：采用实现完成即满足；前置 PR 验收通过、主 agent 接受结果并提供 commit SHA 后，解除下游依赖，不等待 merge。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-004: 依赖 worktree 采用 stacked 模式

- **模糊点**：下游 PR 在前置 PR 未 merge 时如何消费前置实现。
- **影响范围**：worktree 创建、分支基线、PR 合并顺序。
- **推荐选项**：下游从前置 PR 完成分支创建 stacked worktree；不共享 worktree。
- **结论**：采用 stacked worktree。每个 PR 仍拥有独立 worktree 和分支；下游通过 `depends_on` 消费前置已完成分支。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-005: 多依赖采用依赖快照

- **模糊点**：一个 PR 同时依赖多个已完成但未 merge 的前置 PR 时，如何生成其可消费基线。
- **影响范围**：DAG 汇合、临时分支、依赖冲突、阻塞判定。
- **推荐选项**：将所有依赖完成 commit 合并为临时依赖快照基线；快照冲突显式阻塞，不自动隐藏或重试。
- **结论**：允许多依赖；通过临时依赖快照基线启动下游。依赖快照冲突时显式阻塞该 PR，不静默换基线。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-006: worktree 采用迭代内分层路径

- **模糊点**：当前模型派发协议的单一迭代 worktree 路径不能表达同一迭代多个并发 PR。
- **影响范围**：V-01 校验、分支归属、并发隔离、worktree 回收。
- **推荐选项**：使用 `.pb-agents/worktrees/{项目标识}-{迭代标识}/{pr-id}`。
- **结论**：采用项目/迭代/PR 三段式 worktree 路径；每个 `pr-id` 对应唯一 worktree 和分支。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-007: 开发并行、合并串行

- **模糊点**：并发开发完成后，合并是否也允许并行推进。
- **影响范围**：集成基线、冲突、验证、回滚。
- **推荐选项**：开发可并行，merge queue 一次只推进一个集成基线。
- **结论**：采用串行合并队列。merge 失败只阻塞该 PR 及其依赖闭包；无关 PR 继续执行或排队。回滚以 PR 为最小单位。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-008: 失败不自动换基线

- **模糊点**：前置 PR merge 失败、下游已完成时，是否由调度器自动迁移下游并重试。
- **影响范围**：失败隔离、回滚边界、隐式范围变化、恢复可预测性。
- **推荐选项**：阻塞依赖闭包，由主 agent 显式决定修复、重派或放弃。
- **结论**：前置 PR merge 失败后，下游进入 `blocked-by-dependency`；无关 PR 不受影响；不自动换基线、不自动重派、不静默重试。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-009: 当前迭代不迁移

- **模糊点**：新协议是否回溯改写当前 0004-model-dispatch 的 8 个 PR。
- **影响范围**：历史迭代稳定性、本轮验证样本、迁移工作量。
- **推荐选项**：仅影响后续迭代，当前 0004 保持原貌。
- **结论**：新协议仅从后续迭代生效；不迁移当前 0004 的 8 个 PR 文件。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02

### CLR-PC-010: 协议先行，runtime 后续实现

- **模糊点**：当前仓库没有实际 dispatch runtime，是否在本轮扩大范围实现外部 harness 调度器。
- **影响范围**：本轮交付边界、实现路径、可验证性。
- **推荐选项**：本轮先完成协议与校验；后续按协议单独实现 runtime / harness adapter。
- **结论**：本轮不改实际 dispatch runtime；先更新协议、workflow 文档、角色契约、校验器和后续迭代模板，之后再实现 fan-out 与完成事件驱动。
- **来源分类**: user_confirmed
- **状态**: 生效
- **确认时间**: 2026-09-02
