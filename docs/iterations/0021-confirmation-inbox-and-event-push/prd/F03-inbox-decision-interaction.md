# F03：栏内裁决交互（选项为主、文本为辅、一并提交）

**功能 ID**: F03
**来源**: `demand.md` 第二段 §2 **W2**（`user_confirmed`：U-2「有交互可以确认选项，输入答案」+ P4「选项为主、文本为辅」+ P10-E2 的交互面）；§4 **M1**（选项集合来自请求本身）；效果 **E2**（"条目从栏内消失"）
**迭代**: 0021-confirmation-inbox-and-event-push

---

## 用户价值

在栏里点一下就完事，顺带能写一句理由或补充说明，不用跑去别处回复。

## 验收标准

1. **选项为主：点选即完成裁决**（W2 / P4 / M1）：点选请求方给出的选项即构成一次完整裁决，**不需要额外输入**。
   *判定*：只点选一个选项并提交 → 该次裁决成立（agent 侧可观测到对应裁决）。
2. **文本为辅：可附自由文本**（W2 / P4）：可随裁决附一段自由文本，用途为**拒绝理由 / 给 agent 的补充说明**。
   *判定*：附文本提交 → 文本与该选项**一并**被提交（可从 agent 侧收到的内容核对）。
3. **一并提交，非两段式**（W2 / P4）：选项与文本作为**同一次**裁决提交——不存在"先提交选项、再单独提交文本"的两步。
   *判定*：一次提交动作 → agent 侧同时收到该选项与该文本。
   〔**文本是否必填 / 空白可否提交**由 `demand.md` M6 明列为架构待填（T-04）；本卡只要求"可附加"，不判必填性〕
4. **裁决完成后该条从栏内消失**（W2 / E2）。
   *判定*：提交裁决 → 该条不再出现在栏内。

## 边界（不包含）

- 不含裁决**如何**回到 agent 以及 agent 侧后果（→ F04）。
- 不含选项之外的自定义裁决动作（`demand.md` 只定义"选请求方给出的选项 + 附文本"，本阶段不新增）。
- 不含批量裁决 / 一次处理多条（`demand.md` 未要求，本阶段不新增）。
- 不含文本是否必填 / 空白可否提交的形态（→ T-04）；不含控件形态（→ T-03）。
- 不含对已消失条目的历史回看（不做，→ F11）。
- 不含通知的触发与投递（→ F07 / F08）。

## 架构落定（阶段 3）

> 架构维度结论；产品维度**未改动**。详见 `../architecture.md` §5.1(R-2) / §5.4 / §7 T-03、T-04。

- **T-02 选项集合呈现**（§7 T-02）：每个 `optionId` 一个 `<button>`；`label` 缺失时以 `optionId` 为文字。
- **T-03 控件形态**（§7 T-03）：**点选项按钮即提交**（无独立"提交"按钮）——`POST /api/confirmations/<id>/decision` body `{option_id, text?}`；提交中按钮 `disabled` + "提交中…"；`200` 即**整条移除**（不等 SSE）。
- **T-04 文本必填性**（§7 T-04）：**永远可选**；空白可提交，服务端 `trim()` 后为空则不追加 `chat` 输入。
- **文本的落地**（§5.3）：ACP 应答体只有 `optionId`（无自由文本通道）⇒ 文本实现为**追加一条该对话的 `chat` 输入**（复用既有落库 + 派发路径），不新增协议。
- **选项合法性**由服务端校验（不在该条选项集合内 → `400 INVALID_PARAM`）；重复提交同一 id → `404 NOT_FOUND`（§5.1 R-2）。
