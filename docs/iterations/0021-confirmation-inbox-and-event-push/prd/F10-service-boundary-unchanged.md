## 用户价值

这次不把服务开到局域网或公网去——本机和以前一样，别人连不上也不需要登录。

## 验收标准

1. **服务边界不变**（N1）：服务仍**仅在本机（`127.0.0.1`）监听**、**零鉴权**、**不做多用户 / 跨机接入**。
   *判定*：从另一台机器 / 局域网访问 → 仍不可达；访问服务仍不需要任何凭据。
2. **该边界只约束服务本身**（T-2 裁决）：通知的**投递路径**经浏览器厂商推送服务**不在禁止范围内**——不得把 N1 读成"投递不得出本机"。
   *判定*：读通知投递路径的说明 → 服务的监听 / 鉴权边界与投递路径分列，投递路径不被读作受限。

## 边界（不包含）

- 不含投递路径的实现（→ T-13）。
- 不含鉴权、多用户、跨机接入的任何新增（N1 封死）。
- 不含服务监听的其它变更（本迭代不改服务边界）。

## 架构落定（阶段 3）

> 架构维度结论；产品维度**未改动**。详见 `../architecture.md` §3.1(L1-4) / §7 T-13 / §11.2。

- **T-13 投递路径的边界结论**（§7 T-13）：服务端 → 既有 SSE → **前端** `notify.js` → 浏览器 `Notification` API。**服务端零新增出网路径**（不接触任何推送服务）⇒ "仅 `127.0.0.1` 监听 / 零鉴权 / 不做多用户"**结构性保持**；`web.js` 的 `http.createServer` 构造处（监听地址、鉴权）**零改动**。
- **N1 只约束服务本身**（T-2 裁决）：浏览器厂商推送服务的**投递路径不在禁止范围内**；本迭代**恰好不涉及**该路径（L1-4 选择页面内 Notification API，不引入 Service Worker / Web Push / VAPID）。
- **必然变更（派生面，与边界无关）**：新增 2 条路由 ⇒ 必须同步 ① `API.md` 追加 §3.20 / §3.21（既有 19 条逐字不动）② 重生成 `llms.txt`（`api-routes.test.js:278-315` 两条漂移锁）。**既有 19 条路由与 `GET /api/stream` 的 4 类事件零改动**。
