# F06：在途项的可见性（刷新 / 断线重连后仍在栏内）

**功能 ID**: F06
**来源**: `demand.md` 第二段 §2 **W6**（`user_confirmed`：**T-3 第 2 批裁决**「未裁决的确认项必须在栏内（前端重连后重建在途列表）」+ 实测 F9「SSE 事件不补发」）；效果 **E5**；边界 **N2** 的范围澄清（只覆盖已裁决项的历史）
**迭代**: 0021-confirmation-inbox-and-event-push
**产品对象（引用 `demand.md` 只读实测，非本阶段决策）**: F9（订阅建立前 / 断开期间发生的事件不会排队重放，重连需以全量补齐）

## 用户价值

刷一下页面，等着我处理的事不会凭空消失——agent 还在那边等，我却看不见了。

## 验收标准

1. **刷新后仍在栏内**（W6 / E5）：页面刷新后，**未裁决**的确认项仍在栏内。
   *判定*：栏内有未裁决项时刷新页面 → 该条仍在栏内。 〔**判定样本**（`[user_confirmed MI-05]`）：**构造样本 + 真实样本各半**——"刷新 / 断线重连"半句由阶段 6 的构造样本覆盖；真实样本取自本迭代自身的执行记录，**须标明来源与场景**〕
2. **断线重连后仍在栏内**（W6 / E5）：连接中断（含网络中断）后恢复，未裁决项仍在栏内。
   *判定*：断开连接 → 恢复 → 该条仍在栏内。
3. **重建后内容一致**（E5）：重建后的条目内容与刷新前一致（请求方、请求的操作、可选项集合）。
   *判定*：对照刷新前后同一条目的内容 → 一致。 〔`[user_confirmed MI-04]`：**"内容一致" = 条目存在 + 内容（请求方 / 请求的操作 / 可选项集合）一致，不含栏内相对顺序 / 位置**〕
4. **只重建在途项，不重建已裁决项**（N2 的范围澄清 / W2）：刷新 / 重连只让**未裁决**的项回到栏内；**已裁决**的项不会因此回到栏内。
   *判定*：先在栏内裁决掉一条、再刷新页面 → 已裁决的那条不回来，未裁决的那条仍在。

## 边界（不包含）

- **不含持久化历史 / 审计台账**（N2 → F11）：本卡只要求"在途项在刷新 / 重连后仍在栏内"，**不要求**保留任何已裁决记录。
- **不含刷新 / 重连时是否重复触发通知**（`[user_confirmed MI-01]`：重建在途列表**不重复触发** `confirmation_required` 通知，见 F08 验收 2；本卡只判条目可见性，不判通知）。
- 不含重建机制（前端内存态与服务端的职责划分、承载形态）→ T-07 / T-08。
- 不含条目的来源与上浮条件（→ F02）；不含栏内裁决交互（→ F03）；不含未裁决时的挂起语义（→ F05）。
- 不含对已裁决项的任何留存形态。

## 架构待填（本阶段留白）

- **T-07** 在途列表的重建机制（前端重连后如何重建；前端内存态与后端职责划分）。
- **T-08** inbox 项的承载形态与生命周期（是否落服务端、存活期、与"无历史台账"的关系）。
