# F09：通知服务与通道分离（扩展通道不改事件类型契约）〔形态约束〕

**功能 ID**: F09
**来源**: `demand.md` 第二段 §2 **W4** 的分离面（`user_confirmed`：P5 用户原话「新建通知服务，先走Notification。 后续可以扩展成web push」）；§4 **M4**（服务承载"什么事件要通知"，通道决定"怎么投递"；扩展通道不改事件类型契约）
**迭代**: 0021-confirmation-inbox-and-event-push

---

## 用户价值

以后想加一种送达方式（比如真 web push）时，不用重新定义"什么事该通知"——事件该发什么不会跟着投递方式一起重做。

## 验收标准

1. **服务与通道是两件事**（M4 / P5）：通知服务承载"**什么事件要通知**"，通道决定"**怎么投递**"——二者可分别描述、互不决定；不以某个通道为中心定义事件。
   *判定*：读通知服务的形态说明 → "要通知什么"与"怎么投递"分列，且事件的定义不依赖某个具体投递方式。
2. **扩展 / 替换通道不改事件类型契约**（M4 / P5）：在新增或替换投递方式的情形下，事件类型集合（3 类）与其定义**不发生改变**。
   *判定*：对照扩展 / 替换投递方式前后的事件类型集合与定义 → 不变（判据 = 换通道不需要改事件定义）。

## 边界（不包含）

- 不含服务与通道的组织形态与衔接方式（→ T-12）。
- 不含具体要扩展哪些通道（`demand.md` P5 只说"后续可以扩展"，本迭代不指定、不实现）。
- 不含事件类型集合与产生时机本身（→ F07）；不含本迭代的投递行为（→ F08）。
- 不含投递路径是否出本机（→ F10 验收 2，T-2 裁决）。
