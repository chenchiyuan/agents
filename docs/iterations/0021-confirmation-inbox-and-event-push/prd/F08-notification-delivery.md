# F08：通知投递（首个通道 = 浏览器通知）

**功能 ID**: F08
**来源**: `demand.md` 第二段 §2 **W4** 的通道面（`user_confirmed`：P5 用户原话「新建通知服务，先走Notification。 后续可以扩展成web push」）；§4 **M4**；效果 **E3**；边界 **N4**
**迭代**: 0021-confirmation-inbox-and-event-push

---

## 用户价值

不盯着屏幕也知道有结果了——切到别的页面照样被叫到。

## 验收标准

1. **首个通道 = 浏览器通知**（W4 / P5 / M4）：本迭代的通知经**浏览器通知**（Notification API）投递；不引入第二种投递形式。
   *判定*：触发一次通知 → 以浏览器通知的形式出现；不存在并行的第二种投递形式。
2. **权限已授予时，三类事件各触发一次浏览器通知**（E3）：通知权限已授予时，对话完成 / 对话失败 / 出现待裁决项各触发一次浏览器通知。
   *判定*：授予通知权限后分别构造三种情形 → 各出现一条浏览器通知。 〔`[user_confirmed MI-01]`：`confirmation_required` **只在确认项首次进入 inbox 时通知一次**；刷新 / 断线重连**重建在途列表不重复触发**通知〕
3. **不依赖用户停留在该对话**（E3）：用户停留在别的对话 / 别的页面时，通知照常出现。
   *判定*：切到别的页面后触发一次事件 → 仍能看到该通知。

## 边界（不包含）

- **不含通知权限未授予时的降级形态**（`demand.md` M6 明列为架构待填 → T-11；本卡只判"权限已授予"分支，与 E3 的措辞一致）。
- **不含通知偏好设置**（N4）：不做分级、免打扰、声音等设置。
- **不含 web push**：真 web push 是"后续可扩展"方向（P5 / F09），本迭代不做。
- 不含通知标题 / 内容 / 点击去向（→ T-09）、多条通知的合并 / 覆盖策略（→ T-10）。
- 不含事件类型集合与产生时机（→ F07）；不含服务与通道的划分与扩展契约（→ F09）。
- 不含投递路径的服务边界说明（→ F10 验收 2 / T-13）。
