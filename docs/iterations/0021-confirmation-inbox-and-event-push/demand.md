# 第二段 · 需求结论

## 1. 目标与价值（为什么）

**目标（`user_confirmed`，P8 = 两者都要）**：让**受门禁的工具调用授权**从"被静态档位一刀切"改为"由人在一个集中的入口裁决"；并让**需要人知道的事**（对话完成 / 失败 / 出现待裁决项）**主动推到人面前**，而不是等人去看。

**两条驱动（各自独立成立，共同支撑全部"做什么"）**：

| # | 驱动 | 现状痛点（`实测`） | 推导出的需求 |
|---|---|---|---|
| V1 | **安全驱动**（P8 前半） | 受门禁调用被档位一刀切：`allow` 恒放行（有风险）、`deny` 恒拒绝（agent 干不了活）；人**无法对具体某一次操作**介入（F1 / F3） | W3（确认源上浮）+ W2（裁决交互） |
| V2 | **注意力驱动**（P8 后半） | 审批结果只落 agent 的 tmux 窗口与日志，Web 控制台零显示（F4）——不盯屏就不知道"跑完没有 / 是否在等我" | W4 / W5（通知）+ W1（集中入口） |

**价值**：人的注意力从"常驻盯屏"变为"按需介入"；危险操作从"全放行"变为"逐次可裁决"。

## 2. 做什么

| # | 条目 | 来源 |
|---|---|---|
| W1 | **待确认 inbox（第三栏）**：Web 控制台新增独立一栏（对话列表 \| **待确认 inbox** \| 对话详情），**跨对话集中列出**所有"等待用户裁决"的确认项 | `user_confirmed`（U-1 + P3②） |
| W2 | **栏内交互**：每条确认项呈现**请求方给出的选项集合**（点选即裁决，**选项为主**）+ **自由文本**（**文本为辅**：拒绝理由 / 给 agent 的补充说明），文本与选项**一并提交**；裁决完成后该条从栏内消失 | `user_confirmed`（U-2 + P4 + P10-E2） |
| W3 | **确认源接入**：把 **agent 侧受门禁工具调用的授权请求**（omp `session/request_permission`：`bash` / `edit` / `delete` / `move`）从"档位自动答复"改为"**上浮到 inbox、由人裁决**" | `user_confirmed`（P2 + F1 + F2） |
| W4 | **通知服务**：新建**通知服务**，**服务与通道分离**（服务 = 能力承载体，通道 = 具体投递方式）；**首个通道 = 浏览器 Notification API**；后续可扩展通道（如 web push） | `user_confirmed`（P5 用户原话） |
| W5 | **事件类型体系**：本迭代定义**封闭 3 类**事件 —— `chat_completed`（对话完成）/ `chat_failed`（对话失败）/ `confirmation_required`（出现需用户裁决的事项） | `user_confirmed`（U-4 + P6） |

## 3. 不做什么

| # | 边界 | 为什么这次不做（每条均有理由） | 来源 |
|---|---|---|---|
| N1 | 不做**跨机 / 公网 / 多用户**推送 | 服务只绑 `127.0.0.1`、零鉴权（既有安全边界，`API.md` §1.3）——推送面跟随该边界 | `user_confirmed`（P9 全保留） |
| N2 | 不做确认项的**持久化历史 / 审计台账**（"我看过哪些确认"） | 最小闭环 = 处理掉即可；工具审计已落在 agent 日志侧（F4），重复建设无收益 | 同上 |
| N3 | **不改 omp / harness 侧协议** | oamp 侧已有可接线之处（F2），无需动上游 | 同上 |
| N4 | 不做通知**分级 / 免打扰 / 声音**等偏好设置 | 未提出；先有信号，再谈调优 | 同上 |
