## 3. 提案清单（每条 = 推断 + 理由 + 「如果不对，请直接说改成什么」）

### P1 · 「按照」的读法（brief 必答项 ①）

**草稿更新**：把第 1 条结尾的「按照」判为**断句残留**，不写入需求合同；第 1 条完整语义 = 「agent 中需要用户确认的事项单独一栏列出，有交互：可确认选项、可输入答案」。

**理由**：字面无宾语、无法构成可执行约束；且「确认选项 + 输入答案」在语义上已完整覆盖交互面。若强行给「按照」补宾语，只能补出"按照请求方给出的选项确认"——而这一点本来就被"确认选项"覆盖，补与不补结果相同。

**其他两种读法**：①「按照 [agent 给出的选项] 确认」——则它是一条真实约束：**确认项必须原样呈现请求方给出的选项集合，人的回答只能是其中之一**（不自由发挥）；②「按照」是下一条的开头串行（读不通，已排除）。

**如果不对，请直接说**：改成什么（或直接确认"残留、删除"）。

### P2 · 「需要用户确认的事情」的外延（**本轮最关键**）

| 选项 | 含义 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | = **受门禁的工具调用授权**（omp 的 `session/request_permission`：`bash` / `edit` / `delete` / `move`）。把当前"档位自动答复"改为"上浮给人拍板" | 产品里**唯一已存在**的"需要确认"实体（F1）；已有未被使用的接线缝（F2）；范围最小、可端到端跑通 | 「输入答案」的自由文本成分只能落在"拒绝理由 / 附加说明"这类附属输入上 |
| B | A **+** agent 主动向用户提问（"我需要你回答 X"），用户输入答案回传 | 最贴合「输入答案」的字面 | 产品里**不存在**这条通路（omp ACP 无"向用户提问"原语，模型只能在回答文本里问）⇒ 落地 = 新协议，成本显著 |
| C | **仅**自由问答，不含工具授权 | 若你真正关心的是"agent 提的问题别被淹没" | 与 F1 这个现成的、真实存在的确认源脱钩 |

**推荐 A**，理由：先接上真实存在的确认源，端到端跑通"挂起 → 人裁决 → agent 继续"的闭环；B 是它之上的通路扩展，适合下一次迭代。

**如果不对，请直接说**：选 A / B / C，或给出你的第三条读法。

### P4 · 「输入答案」与「确认选项」的关系

**草稿更新**：**选项是主、文本是辅**——每个确认项由请求方给出**选项集合**（按钮点选）；自由文本作为该条确认的**附加输入**（如拒绝理由 / 给 agent 的补充说明），与选项一并提交。

**理由**：受门禁授权这类确认，其可执行语义就是"选一个选项"（放行 / 拒绝），纯自由文本无法映射成裁决；而文本输入在"说明理由"上有真实价值。

**备选读法**：文本是独立通路（即 P2 的 B）。

**如果不对，请直接说**：改成什么。

### P5 · 「web push」的形态（brief 必答项 ②）

| 选项 | 含义 | 优点 | 缺点 |
|---|---|---|---|
| **①（推荐）** | **浏览器通知**（Notification API）：前端收到既有 SSE 的新增事件 → `new Notification()`，点击聚焦到对应对话 | 零外部依赖；`127.0.0.1` 属安全上下文，可直接申请通知权限；与现有 SSE 通道天然衔接（F5） | **页面 / 标签关掉就收不到**——不是严格意义的"推送" |
| ② | **真 Web Push**（Service Worker + Push API + VAPID 密钥 + 订阅持久化）：浏览器关掉也能收到 | 唯一满足"关掉页面也收得到"的选项 | 投递**依赖浏览器厂商推送服务**（Chrome 走 FCM，需外网），与"本机运行时、仅 127.0.0.1、零鉴权"的既有安全边界冲突（`API.md` §1.3）；新增订阅存储 / 密钥管理，范围显著变大 |
| ③ | 仅服务端 SSE 通道：页面开着时前端渲染角标 / 高亮，不做系统级通知 | 零额外权限 | 不算"推送"；页面不可见时无信号 |

**推荐 ①**，理由：本产品定位是**本机单用户控制台**（127.0.0.1、零鉴权、无外网依赖假设），① 在此定位下零成本拿到"切走标签也能看见"的核心价值；② 引入的对外部推送服务的依赖，与"本机运行时"是方向性冲突。

**如果不对，请直接说**：选 ① / ② / ③；**若选 ②**，需同时接受"依赖浏览器厂商推送服务（可能需外网）"这一代价。

### P6 · 首批事件类型集合（brief 必答项 ③）

**草稿更新**：本迭代定义**封闭的 3 类**事件：

| 事件类型 | 触发点 | 为什么是它 |
|---|---|---|
| `chat_completed` | 对话 `working → completed` | 你已点名（"会话完成"） |
| `confirmation_required` | 新的待确认项进入确认栏 | 你已点名（"回传用户需求确认的事情"，对应第 2 条的"中间确认"） |

**如果不对，请直接说**：删掉 `chat_failed` / 换一组 / 补充你想要的类型。

### P7 · 确认项的阻塞与超时语义（**内部一致性缺口，我主动发现**）

**问题**：确认栏一旦上线，"agent 等着人拍板"就成了常态。两个方向都危险——
- **不阻塞**：确认就没有意义（工具总得放行或拒绝）；
- **阻塞且无上限**：本迭代自己的执行方式正是 hub **后台派发**（F8），dev 角色默认 `permission: allow`（F3）；一旦某个后台任务触发确认而人不在，**任务永久挂起**。

| 选项 | 含义 |
|---|---|
| **①（推荐）** | **阻塞等待 + 有等待上限**：超时后**退回既有 permission 档的默认行为**（`allow` 档 → 视为放行；`deny` 档 → 视为拒绝），并把该条标记为"已超时" |
| ② | 阻塞且无上限（等到人来为止） |
| ③ | 不阻塞（只通知、不裁决）——与第 1 条"可以确认选项"冲突，不建议 |

**推荐 ①**，理由：把"人在场就人来定、人不在就按既有档位"作为明确退化路径——**无人值守场景的行为与今天逐字一致**（不引入新的挂死风险），这是本迭代能安全上线的关键。等待上限的具体时长与承载形式留 `[架构待填]`。

**如果不对，请直接说**：选 ① / ② / ③；若选 ①，是否允许配置超时（我建议本迭代不新增用户可见参数）。

### P8 · 为什么（why）—— 用户未给出，全文推断

**草稿更新**：本次迭代的价值 = **把人的注意力从"常驻盯屏"改为"按需介入"**：有事才响，响了能就地把事办掉。

两条现状痛点支撑它（均为 `实测`）：
