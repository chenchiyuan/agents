## 9. 下一迭代候选

> 本轮发现的优化点、边界问题或遗留限制。不在当前验收标准范围内，供主 agent 和 planner 决策是否纳入下一迭代。

- **notice 投递异步失败时挂起无兜底（轮次可永久冻结）**：`raiseConfirmation`（`agent.js:319-337`，`sendNotice` 返回值 `:335` 未被消费）在 `client.send` 异步 reject 时被 `.catch(() => {})` 吞掉，但函数仍返回**未结算 Promise**；由于该 Promise 冻结了 `AcpClient` 的轮次计时（L1-1）且 Q2 禁止 agent 侧计时，该轮将既无终态也无超时。`sendNotice` 已改为返回"是否同步写出"，但 `raiseConfirmation` 未消费该返回值。当前可达性低（`client && client.peer && origin` 前置守卫与 `sendNotice` 同源，仅剩"守卫通过后连接骤断"的窄竞争窗口）。若下一迭代决定处理，需在「发送失败即回落静态档位」与「pending TTL」之间取舍（后者触碰 Q2 的禁令边界）。
- **`cancelPending` 的 `chatId` 默认值与"全量清扫"隐式耦合**：签名 `cancelPending(client, logger, pending, { chatId = null } = {})`（`agent.js:359-364`）中 `chatId === null` 语义为"清扫全部"。当前唯一按-chat 调用点传 `task.chatId`，经 `parseTaskBody` 校验恒为非空串（`agent.js:103-105`）⇒ 安全。但若未来新增调用点误传 `undefined`，会静默退化为全量清扫、误伤其它 chat 的挂起项。建议改为显式双入口（`cancelPendingForChat` / `cancelAllPending`）。
- **`settleConfirmation` 不做 `option_id ∈ entry.options` 校验**：agent 侧直接 `resolve({optionId})`（`agent.js:344-352`），合法性完全依赖 web 侧 R-2（pr-003 已实现）。当前唯一投递路径经 web 校验，无风险；若未来出现绕过 web 的直投路径（如多 web 实例/运维脚本），agent 侧无独立防线（`AcpClient` 会对未知 optionId 回落默认项，行为安全但语义静默）。
- **pending 表不跨 web 重启对账**：web 进程重启后 agent 侧挂起项仍在，但 web 的在途表已空，裁决无从发起（architecture §9.2 K2 已明示为设计代价）。本轮按设计不处理，登记以备后续评估。
