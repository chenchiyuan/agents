# F06：分支命名必须含迭代 ID

**功能 ID**: F06
**来源**: `demand.md` W7（P-7 ①，`user_confirmed`）；效果 E7；实证 `retro-0017-phase1.md` Q-a A-4.1（共享 refs 与分支命名空间不隔离，证据来源）
**迭代**: 0019-worktree-isolation-protocol
**产品对象（引用 `demand.md` 只读事实，非本阶段决策）**: 既有迭代分支名 `iteration/{迭代ID}`、阶段 5 的 PR worktree 分支命名（形如 `feat/pr-00N`）、既有「PR 实现子状态」表的 worktree 分支列

---

## 用户价值

扫一眼分支名列就知道它属于哪个迭代、哪个会话——两个会话不会再撞上同名分支，事后也不会把别人的分支读成自己的。

## 验收标准

1. **条款存在：会话创建的所有分支名必须含迭代 ID**（W7）：规范要求会话创建的**所有**分支名含迭代 ID；迭代分支本身即 `iteration/{迭代ID}`；阶段 5 的 PR worktree 分支**规范化为含迭代 ID 的形式**。
   *判定*：读规范条款 → 未覆盖"阶段 5 的 PR worktree 分支"或仍允许无名约束的会话自建分支，即不通过。
2. **真实记录逐条对照**（E7）〔`[user_confirmed MI-04]`〕：任取一次执行记录，列出该会话创建的**全部分支名**，逐个检查是否含该迭代 ID；且**不存在同名分支被两个会话争用**。
   *判定*：分支名逐条核对（"含"= 分支名中字符串包含该迭代编号即可、不要求统一格式，见 MI-04）→ 出现任一无迭代 ID 的分支、或出现同名争用，即不通过。
3. **既有分支语义不变**（W7 / N8）：分支的 base 与合并目标不变——PR worktree 的 base 仍为迭代分支、合并目标仍为迭代分支；分支与 PR 的对应关系不变。
   *判定*：对比改动前后「规则 A」与阶段 5 调度文本中的 base / 合并目标表述 → 出现变化即不通过。
4. **不含对既有分支的追溯改名**（N3）：规范只约束新创建的分支，不要求对已完成迭代的既有分支改名。
   *判定*：读规范条款的生效范围 → 出现"追溯改名"要求即不通过。

## 边界（不包含）

- 不含分支名的具体格式细则（前缀 / 分隔符 / slug 形态）（→ `[架构待填]` T-03）。
- 不含分支创建 / 清理命令（→ `[架构待填]` T-05；清理权见 F10）。
- 不含"同一分支不能两处检出"的硬约束声明（→ F12）。
- 不含 PR 文件七字段格式与 PR 编号规则的改动（N1）。
- 不含既有分支的追溯改名（N3）。
