**产品对象（引用 `demand.md` 只读事实，非本阶段决策）**: 既有「提交管理约束」的文本级"条款 + 判断方式"体例；既有 worktree / PR worktree 机制

## 用户价值

规范自己说清"隔离到哪一层为止"——不夸大能力（不说隔离了 refs），也不让人事后才发现有东西没被隔开。

## 验收标准

1. **覆盖项逐条列出**（E10 / P-9 ①）：规范中存在一条**隔离边界声明**，逐项列出**覆盖**的共享状态：**工作树 / 索引 / HEAD**。
   *判定*：读规范文本，三项逐条可核对 → 缺任一项即不通过。
2. **未覆盖项逐条列出**（E10 / P-9 ①）：同一声明逐项列出**不覆盖**的：**仓库级 refs（含 stash 与分支命名空间）/ 对象库 / config · hooks · remotes**；并写明"**同一分支不能两处检出**"是 git 硬约束。
   *判定*：读规范文本，逐项可核对且硬约束句存在 → 缺任一项即不通过。
3. **针对未覆盖项的负面约束**（E10 / P-9 ①）：声明对未覆盖项附负面约束（例如不得依赖 stash 跨会话传递状态、不得把分支命名空间当作跨会话通道等——具体措辞留 `[架构待填]` T-09）。
   *判定*：读规范文本，每一条未覆盖项都能找到对应的一句约束 → 出现"只声明不约束"的未覆盖项即不通过。
4. **已知代价被写明**（E10 / P-10 ①）：合并期冲突的处置被声明为"**冲突后移到合并期**"的已知代价，**不被写成"自动解决"**。
   *判定*：读规范文本，找得到该已知代价声明，且无"冲突自动解决"表述 → 任一不满足即不通过。
5. **不夸大能力**（P-13 ① / N6 / N10）：声明中不出现"跨机器隔离""跨工作区写入会被阻止""refs 也被隔离"这类超范围承诺。
   *判定*：逐句核对声明文本 → 出现任一超范围承诺即不通过。
6. **落点范围**〔`[user_confirmed MI-09]`〕：声明以**规范文件为真源**，SKILL 按既有"不重复定义"原则**引用**而不重复定义。
   *判定*：读两处文本，SKILL 侧为引用而非平行定义 → 两处各写一份完整声明即不通过。

## 边界（不包含）

- 不含声明的落点章节与具体措辞（→ `[架构待填]` T-09）。
- **不引入任何机制**：不新增 hook / 守卫 / 访问控制（N4 / N10）；声明只描述能力边界与负面约束。
- 不含共享 refs 的**技术性隔离手段**（不承诺隔离，只声明不隔离 + 附约束）。
- 不含非 git 共享资源声明（→ F11，那是另一条声明）。
- 不含阶段 5 的 PR worktree 机制改动（→ F07）。
- 不含合并冲突的解决流程（P-10 ①：只声明为已知代价，不定义流程）。
