---

## 用户价值

不用装任何工具就能遵守这套规范——规则写在文本里，读一遍就能自己判断有没有做到，不用先跑脚本、不用先装 hook。

## 验收标准

1. **零工具依赖**（W11 / §1.2 约束②④⑤）：本迭代产出的**全部**规范条款（F01~F12、F14、F15），其落地手段均落在 **git 原生命令 + 文本规范**内；**不存在"必须先安装或运行某工具（安装脚本、hook、守护进程、外部服务）才能满足该条款"的前置条件**。
   *判定*：逐条读本迭代新增 / 改写的条款，对每条问"遵守它需要什么？"——答案只需**读文本 + 用 git 原生命令**即通过；出现任一工具前置即不通过。
2. **条款自带判断方式**（E5 / P-11 ①）：每条新增 / 改写条款都附带"**判断方式**"，**没参与本迭代讨论的人**可据此对一次真实执行判定"违反 / 未违反"。
   *判定*：把任一条款连同其判断方式交给未参与讨论的人，让他对一次真实执行判定 → 结论与规范预期一致即通过；条款**无判断方式**即不通过。
3. **不引入自动化守卫**（N4 / N10）：不新增 hook、访问控制、路径守卫；不把任何文本级条款写成"可被强制执行的门"。
   *判定*：检索规范与 SKILL 全文，确认无新增强制机制条款 → 出现即不通过。
4. **既有形态约束不变**（C-5 / 既有条款）：既有"提交管理约束与并发调度逻辑只在本文件定义、不得再拆独立文件重复表达"的约束不变；不得因本迭代而另起一份重复定义的文档。
   *判定*：对比改动前后的相关段落 + 检查是否新增平行定义文档 → 出现平行定义即不通过。
5. **不依赖宿主特有能力**（W11）：条款的落地不要求宿主提供特定工具能力（不出现"必须用 XX 工具派发 / 必须用某宿主特性"作为满足条款的前提）。
   *判定*：逐条读条款，检查是否存在宿主特性前置 → 出现即不通过。

## 边界（不包含）

- 不含"判断方式"的体例形态（与条款同段还是独立子句）（→ T-16，见 `architecture.md` §8.0）。
- 不含条款的落点章节与具体措辞（分散在各卡 T-01~T-16，见 `architecture.md` §5 / §8）。
- **不含任何自动化守卫 / hook / 脚本的实现**（N4）：本卡是**否定式**约束，只规定"不做什么形态"。
- 不含既有工具（安装脚本）的定位调整（→ F08，那是"可选分发手段"的定位改写，不是新增依赖）。
- 不含回归核对手法（→ F14 验收 1，其判据由本卡验收 2 提供体例支持）。

## 架构落地（阶段 3 已填，见 `architecture.md` §8.0 / §9 / §3.2；产品维度未改一字）

- **T-16 体例形态**：**沿用既有体例**——条款正文一段（含动机与约束），**紧跟一行**以 `判断方式：` 开头的独立段落，与条款**同属一个 `###`**，**不新增子标题、不写入独立小节**。先例：`roles/workflow-pb/workflow-pb.md:129/131`（规则 A）、`:135/137`（规则 B）；本次 5 条新规则与全部改写条款同此形态（本卡验收 2 的"未参与讨论者可判定"由此满足）。
