# F05：合并动作固定在仓库主工作区

**功能 ID**: F05
**来源**: `demand.md` W6（P-6 ①，`user_confirmed`）；效果 E8；C-2（git 硬约束）；实证 `retro-0017-phase1.md` Q-a A-4.2（证据来源）
**迭代**: 0019-worktree-isolation-protocol
**产品对象（引用 `demand.md` 只读事实，非本阶段决策）**: 既有「迭代分支合并进 main」三步（`checkout main` → `merge --no-ff` → `branch -d`）

---

## 用户价值

收口合并不再"切走"任何一个会话的地盘——正在干活的会话不会因为别人合并而被打断，也不会被拽到 main 上。

## 验收标准

1. **合并固定在主工作区执行**（W6 / P-6 ①）：规范要求"迭代分支合并进 main"的动作**固定在仓库主工作区执行**；**动作顺序与触发时机不变**（仍是阶段 6 判定 pass 之后、仍是同样的三个动作序列）。
   *判定*：读规范条款 + 任取一次收口记录，确认该动作序列是在仓库主工作区执行的 → 出现"在会话工作区内执行合并"即不通过。
2. **会话工作区永不 checkout main**（E8）：任取一次迭代收口：`main` 的合并提交出现在**仓库主工作区**，而该迭代的工作区在**合并动作前后始终检出在迭代分支上**（未 checkout main）。
   *判定*：对照收口记录中两个位置的检出分支（合并动作前后各取一次）→ 迭代工作区出现 main 检出即不通过。
3. **消除"假定工作区可切到 main"的残留表述**（W6 / C-2）：既有条款中任何隐含"工作区可以被切到 main"的表述已被一并消除或改写为指向仓库主工作区。
   *判定*：全文检索相关表述（切到 main / checkout main / 当前工作区在 main），逐条对改后的主体 → 任一条仍假定会话工作区可切到 main 即不通过。
4. **不引入自动化合并**（N4 / W11）：本卡只要求文本级条款，不引入任何脚本 / hook / 工具来自动执行合并。
   *判定*：检索规范文本，不存在"自动执行合并"的机制条款。

## 边界（不包含）

- 不含具体命令、前置检查与"如何确认当前工作区是仓库主工作区"（→ `[架构待填]` T-07 / T-08）。
- 不含迭代分支的创建时机与合并进 main 的触发条件改动（N1）——两者均保持现状。
- 不含现场保留（→ F10）、不含指代改写（→ F04）。
- 不含"合并冲突的自动解决"——冲突后移到合并期是**已知代价**（P-10 ①），由 F12 声明，不在本卡。
