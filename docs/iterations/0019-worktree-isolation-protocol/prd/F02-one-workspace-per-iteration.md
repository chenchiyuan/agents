# F02：每迭代一个工作区（绑定迭代分支）

**功能 ID**: F02
**来源**: `demand.md` W2（P-3 ①，`user_confirmed`）；效果 E3 / E4；C-2（git 硬约束）；实证 `retro-0017-phase1.md` Q-a A-1 / A-4.2（证据来源）
**迭代**: 0019-worktree-isolation-protocol
**产品对象（引用 `demand.md` 只读事实，非本阶段决策）**: 既有「迭代分支」层（`iteration/{迭代ID}`）与「启动工作流」第 4.5 步

---

## 用户价值

每个迭代的活都在自己的地盘上——谁也不会在别人迭代的分支上留下提交，谁也不会因为别人的迭代而找不到自己的产物。

## 验收标准

1. **工作区绑定迭代分支并全程保持**（W2 / P-3 ①）：规范要求迭代工作区检出 `iteration/{迭代ID}`；且阶段 1~6 期间**保持在该分支上**（不中途切到别的分支）。
   *判定*：读规范条款；并任取一次迭代执行记录，检查该会话工作区的检出分支在整个阶段 1~6 期间恒为 `iteration/{迭代ID}` → 中途出现别的检出分支即不通过。
2. **提交只出现在自己所在的分支上**（E3）〔`[user_confirmed MI-05]`：判定样本 = 本迭代阶段 6 构造的两个工作区〕：一个会话产生的提交**只出现在它自己所在的分支上**；另一个会话所在分支的提交历史里找不到这次提交（除非经由显式合并）。
   *判定*：取两会话的执行记录，用 git 历史对照"哪条分支包含该提交" → 出现"提交落在他人分支"即不通过。
3. **两会话并发产出都能完整找回**（E4）〔`[user_confirmed MI-05]`：判定样本同上〕：两个会话在一段时间窗口内各自持续产出并提交（**提交时间交叉**），且两边的产物都能在**各自分支上完整找回**。
   *判定*：取时间交叉的提交清单，逐条在两个分支上核对产物存在性与内容完整性 → 任一侧找不回即不通过。
4. **工作区按迭代划分、不跨迭代复用**〔`[user_confirmed MI-03]`〕：同一会话参与连续两个迭代时，必须为第二个迭代建立 / 切换到**该迭代自己的工作区**，不得在上一迭代的工作区里直接开下一迭代。
   *判定*：读规范条款；并取一次"会话连续参与两个迭代"的记录，检查两个迭代各自的工作区身份不同 → 同一工作区跨两个迭代即不通过。
5. **与 git 硬约束自洽**（C-2）：规范不出现"同一分支在两处同时检出"的隐含要求（例如要求会话工作区与主工作区同时停在同一条分支上）。
   *判定*：检索规范文本中与"同一分支两处检出"相关的表述 → 出现即不通过。

## 边界（不包含）

- 不含工作区落点目录与创建 / 识别方式（→ `[架构待填]` T-01 / T-05）。
- 不含启动契约（→ F03）、不含合并动作的执行位置（→ F05）。
- 不含阶段 5 的 PR worktree（其为子层，→ F07）。
- **不追溯已完成迭代**（N3）；**不改变迭代分支层自身的语义**（改动前后均为 `iteration/{迭代ID}`，见 F14 验收 2）。
- 不含"一个会话同时参与多个迭代"的并发形态（W2 只要求每迭代一个工作区，未要求单会话多迭代并行；该形态不在本卡验收面内）。
