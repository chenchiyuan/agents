### 5. 当前暂用推荐（**在复盘证据回传前不生效，不写入结论**）

**① worktree 为规范默认且唯一被规范化的形态**；clone 保留为"无法共享同一 `.git`（跨机器/跨用户/无写权限）"时的兜底，规范只声明该场景不受本协议保证，不为其定义流程。

- **备选 ②**：两者并列，由会话自选（会让"隔离程度"变成会话自由变量，无法写出统一的裸判定）。
- **备选 ③**：以 clone 为默认（改动面更大；现有证据里没有对应痛点支撑）。
- **回传后动作**：demand 依据 §4 判定规则重写本项选项集与推荐，**交主 agent 转呈用户裁决，不自行定案**。

### 6. 影响面

决定 §5 效果 **E1 ~ E3 的判定方式写法**（clone 形态下"另一方分支上是否出现对方提交"需换成"另一仓库的提交历史"）；同时决定 **N8**（clone 是否作默认）能否转 `user_confirmed`，进而决定阶段 1 推进条件第 2 项能否满足。

### 7. R-1（参考视角，**不是架构结论**，仅供讨论）

worktree 隔离的是**工作树 + 索引 + HEAD 三者**，不隔离仓库级共享的 refs（stash 条目、分支命名空间、对象库）。事故四类损害全部由工作树/索引/HEAD 共享导致，故 worktree 足以覆盖；clone 则连 refs 也隔离。**你若要的是"本次观察到的损害不再发生"，worktree 足够；若要的是"两个会话在任何共享状态上都不互相可见"，clone 更彻底。** 这条只供你判断用，最终由复盘证据 + 你的裁决共同决定。

## P-8 · 角色定义如何在任一新建工作区内天然可用？（按用户约束重拟）

### 1. 用户对本项的答复（逐字）

> 我需要你给我方案，目前的方案似乎不完美。 我希望修改的只是agent工作的时候在独立worktree上工作，工作各自独立。最好不要依赖任何工具，自己就知道怎么干活。正常来说这属于git使用规范，不依赖工具才对

**用户已否决的首轮两个方案**：① 每个工作区各自执行 `tools/install-pb-agents.sh`（依赖工具 + 安装动作）；② 角色文件检测指向仓库主工作区的绝对路径（依赖"主工作区已安装"这一外部状态，且多会话共享一份可变 copy）。

### 2. 从答复中提取的需求级约束（`user_confirmed`）

| # | 约束 | 直接推论 |
|---|---|---|
| ① | 改动面只限"agent 工作在独立 worktree 上、工作各自独立" | 解法不得引入新机制族／新框架 |
| ② | 不依赖任何工具，agent「自己就知道怎么干活」 | 不得依赖安装脚本、hook、守护进程、环境变量约定 |
| ③ | 角色定义在**任一新建工作区内必须天然可用**，无需安装动作或额外工具 | 可得性必须来自 **git 检出本身** |
| ④ | 这属于 **git 使用规范**范畴 | 手段必须落在 git 原生用法 + 文本规范内 |
| ⑤ | 现有两个方案"似乎不完美" | 选项集必须重建，不是二选一 |

### 3. 问题重述（需求级，不含机制）

**根因事实（`实测`）**：`.gitignore` 整体忽略 `.pb-agents/`，而 SKILL 的 CRITICAL 把角色文件根路径**固定**为 `.pb-agents/roles/` ⇒ `git worktree add` 只检出被追踪内容 ⇒ **任何新建工作区都没有角色文件**，Step 0 必然停在"请先执行安装脚本"。也就是说：**现行规范让工作流跑起来的第一道门，依赖的是一个部署动作。**

**要回答的需求级问题**：**怎样让"角色定义"成为 git 检出即得的东西，使一个新工作区在零动作的前提下就能读到完整角色定义？**（而不是：怎样把安装做得更优雅。）

### 4. 选项（重建后，含推荐）

#### ① **推荐**：把"角色定义的读取来源"从部署副本改为**被 git 追踪的内容**

- **做法（需求级表述）**：规范规定"角色定义由 git 追踪、随工作区检出即得"；`roles/**` 这类**被追踪**的角色定义目录成为工作流的读取来源。`.pb-agents/` 与 `tools/install-pb-agents.sh` 从"工作流运行前提"**降级**为"仅面向外部业务项目的可选分发手段"——本仓库自身工作不再依赖它们。
- **为什么推荐**：唯一一个**同时**满足约束②③④的方案——可得性完全来自 `git worktree add`/`git clone` 的检出行为，不需要任何动作、任何工具、任何外部状态；且改动面最小（改的是"规范读哪里"这一处定位 + 相关 CRITICAL 的措辞）。
- **代价（必须说清）**：① SKILL 现有 CRITICAL「**不得退回读 `roles/` 源码目录**」与该方案直接冲突，必须改写或删除——这条 CRITICAL 的存在理由是"业务项目里没有 `roles/` 源码，只有部署副本"，本仓库场景不需要它；② 需在 architecture 阶段决定"上游研发场景"与"下游部署场景"如何共用同一份规范描述（同一份 `workflow-pb` 同时服务两种部署形态）。
- **连带检查（用户要求显式说明）**：采纳①后，P-4 的 PR worktree 落点约定（`.pb-agents/worktrees/`）**不需要跟着改**（角色文件来源与 worktree 落点互不依赖）；但该目录名将只剩"PR worktree 落点"一义，架构阶段可顺带统一。

#### ② 把角色定义纳入被追踪的 `.pb-agents/roles/`

- **做法**：把 `.pb-agents/`（至少 `roles/`）从 `.gitignore` 移出并提交入库；路径与"只读 copy"语义保留。
- **代价**：仓库内出现**两份同源内容**（`roles/**` 与 `.pb-agents/roles/**`），需要同步纪律或生成步骤——这正是本仓库 v0.2.0 明确吸取过的教训（"两处重复表达同一套规则视为耦合未解"）。且"同步"本身会重新引入一次动作 ⇒ 与约束②③的边界模糊。
- **评价**：改动命名最小，但把"零动作"重新变成"某处总要有人同步"。

#### ③ 新工作区用 git 原生手段定位到仓库主工作区的部署副本

- **做法**：新工作区通过 git 自身提供的仓库公共信息（worktree/common-dir 类信息）推导出主工作区路径，从那里的 `.pb-agents/roles/` 读取角色定义。
- **不依赖自建工具**（满足约束②的字面要求），但**不满足约束③的"天然可用"**：它依赖"主工作区已安装且未被并发清空"这一外部状态；且多会话共享同一份可变 copy，回到本次要消除的"共享可变状态"模式（安装脚本的 `rm -rf` 幂等覆盖会在并发时互相清空）。
- **评价**：比首轮方案②略好（不硬编码路径），仍是治标。

### 5. 影响面

| 若采纳 | 正面 | 负面/待处理 |
|---|---|---|
| ① | E9 可写成生效效果（"任一新建工作区零动作即可读到完整角色定义"）；W4/N8 之外的 C-3、C-7 全部闭合；机制真正落在 git 使用规范内 | 需要改写 SKILL 的一条 CRITICAL + 重新定位 `.pb-agents/` 的用途（架构阶段） |
| ② | 路径不变、改动点集中在 `.gitignore` 与一次入库动作 | 引入同源双份与同步纪律，与"不依赖工具/零动作"存在张力；E9 的判定需附加"两份内容一致"这一额外检查 |
| ③ | 不需要改 CRITICAL | **E9 无法成立**（仍需外部状态），C-3/C-7 不闭合 |

**不裁决的后果**：阶段 1 推进条件第 2 项（所有 `model_inferred` 经用户确认）与第 3 项（无活跃冲突）**继续不满足**，本迭代无法进入阶段 2。

### 6. R-5 ~ R-7（参考视角，**不是架构结论**，仅供讨论）

- **R-5**：`.pb-agents/` 这套"部署副本"设计服务的是**把 agents 框架安装进业务项目**的场景；而本次要解决的是"agents 仓库自身开发时的并行会话"。这两种场景对"角色定义从哪读"的诉求本来就不一样——上游要"随代码走"，下游要"随部署走"。这条区分是否成立，由你判断。
- **R-6**：若角色定义改为被追踪内容，则 SKILL 的 Step 0 检测可以退化为一个纯 git 事实（"检出的工作区里是否存在规范定义的角色定义"），不需要再出现"请执行某脚本"的失败路径——这可能正是你说的"自己就知道怎么干活"。
- **R-7**：`git worktree add` 与 `git clone` 在这一点上行为一致：**两者都只带来被追踪内容**。因此 P-8 与 P-1 是两个正交问题——无论 P-1 最终选 worktree 还是 clone，P-8 的答案都必需（除非选②把内容放进追踪集）。
