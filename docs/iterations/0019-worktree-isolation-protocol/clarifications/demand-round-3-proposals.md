## P-16 · 是否把"跨工作区写入不得发生"写成一条负面约束条款？

### 1. 问题

本迭代已裁决的机制（W1~W11）隔离的是**工作目录 / 索引 / HEAD 三层**。复盘 Q-a A-4.5 明确指出：**worktree 不构成访问控制**——绝对路径写入、`git -C <他人工作区>`、`--work-tree` 都能跨工作区生效，且这类操作**不会被任何已裁决条款约束**。

因此需要裁决的问题是：**要不要在规范里写一条针对"跨工作区写入"的负面约束？** 还是把它当作个别操作失误、只记案例、不写条款？

### 2. 证据（`实测`，全部来自 0017 复盘）

| # | 证据 | 内容 |
|---|---|---|
| 1 | `0017/history.md:204`（pr-003 dev 报告"违反边界的事"） | 「**主工作树误写三笔 edit 已完全还原**（发现后 `cp` 备份 → `git checkout --` 还原主工作树 → 复核 `-- oamp/` diff 为空 → 同一内容改写入 worktree）」——即在自己的 worktree 内工作时，写入落到了主工作树 |
| 2 | Q-a A-4.5 | 「**隔离不是强制**：绝对路径写入可以跨工作区生效」；恢复动作本身又是在**共享工作树**上执行了一次写操作 |
| 3 | 复盘 P-8 的建议处置 | 「本迭代可作为 P-9/P-11 相邻边界的一句话负面约束；若用户认为属个别操作失误，记案例」——**复盘未替用户定案**，给出的是二选一 |

### 3. 选项

#### ① **推荐**：写为一条文本级负面约束 + 判断方式（与 P-9 / P-11 相邻）

- **条款内容（需求级表述）**：会话的写操作（含文件写入、`git -C`、`--work-tree`）**必须落在本会话的工作区内**；以绝对路径写入非本会话工作区**不得发生**；若必须恢复他人工作区的内容，**先取备份再操作**（复盘对该案例给出的两条纪律）。
- **判断方式（可客观判断）**：任取一次会话的执行记录，其产生的所有写入/提交所指向的路径均位于本会话工作区之内；若记录中出现对非本会话路径的写入，则该记录必须同时体现"先备份、后操作"两步。
- **为什么推荐**：成本是一句话，且**完全符合已裁决的强制力级别**（P-11 ①：只做文本级"条款 + 判断方式"，不做 hook）与"不依赖任何工具"约束（W11）；收益是把一个 0017 **真实发生过**的越界动作变成可判断的规范项——本迭代的承诺是"消除四类损害"，而跨工作区写入正是损害 1/损害 4 的变体通道。
- **代价**：条款**不可能被 git 强制**（worktree 是目录分离，不是访问控制），所以它只能约束"记录中可判断的行为"，不能阻止动作发生；规范里必须把这一点写明，避免下游误以为它是一条硬门。

#### ② 不写条款，只在本次案卷记案例

- **理由**：属个别操作失误（0017 中该 dev 自己发现并完全还原），规范无法强制一个无法强制的行为；写一条"做不到的约束"会稀释其他条款的严肃性。
- **代价**：跨工作区写入这一通道在本迭代后仍无任何书面约束；同一形态若再发生（尤其在"恢复他人在途现场"这类高危场景），没有判断依据可依。

#### ③ 写为更强的形式：要求"跨工作区恢复前必须先备份"成为独立强制纪律

- **说明**：把案例中的恢复动作（`cp` 备份 → `git checkout --` → 复核 diff → 改写入自己工作区）抽象为一条**必走的恢复流程**，而非附带说明。
- **代价/风险**：比 ① 更重，且**与 P-11 ① 的强制力级别不一致**（那条裁决明确"不做机制化守卫"）；同时把"恢复他人现场"这一本应由 P-12 归属方决定的事，变成了任何会话都可执行的流程——**可能削弱 P-12 ①「现场原样保留、只由归属方清理」**。因此 **demand 不推荐 ③**，除非用户明确希望把恢复流程标准化。

### 4. 影响面

| 若采纳 | 影响 |
|---|---|
| ① | 本迭代新增 1 条一句话条款 + 1 条判断方式（零机制成本）；`demand.md` 补一条 W12 与对应裸判定效果 E13；C-1~C-8 无新增冲突，**不影响阶段 2 启动** |
| ② | `demand.md` 保持现状；该风险以"仅案例记录"形式留在 0017 复盘报告中 |
| ③ | 需与 P-11 ①、P-12 ① 的裁决一起复检（可能产生内部冲突），成本高于 ① |

**若不裁决的后果**：**不阻塞阶段 1 收口与阶段 2 启动**——P-16 已隔离在 `demand.md` §7 待确认清单，结论段无对应条目。但**在裁决前，架构阶段不得把"跨工作区写入禁令"当作既定需求**写入 `architecture.md` 或功能卡。

### 5. R-8（参考视角，**不是架构结论**，仅供讨论）

worktree 是把工作目录、索引、HEAD 分成三份，**不是给文件系统加护栏**——所以任何"防住绝对路径写入"的期待在 git 层面都无解，唯一的缓解手段是**操作纪律**（写入前确认路径归属）+ **恢复前先备份**。这条只供你判断"该不该把它写进规范"用，不代表最终方案。
