## 组 A · 形态与生命周期（机制长什么样）

### P-1 · `worktree` 与 `clone` 谁是规范默认形态？

- **问题**：用户原话写的是"独立 worktree/clone（`git worktree add`）"。斜杠是"二者择一由每个会话自选"，还是"worktree 为默认、clone 仅在特定场景兜底"？
- **选项**：
  - **① 推荐**：**worktree 为规范默认且唯一被规范化的形态**；clone 保留为"无法共享同一 `.git`（跨机器/跨用户/无写权限）"时的兜底，规范只声明该场景不受本协议保证，不为其定义流程。
  - ② 两者并列，由会话自行选择。
  - ③ 以 clone 为默认（worktree 仅作可选）。
- **推荐理由**：worktree 与阶段 5 现有机制（`git worktree add <path> -b <pr分支名> iteration/{ID}`）同构，规范只需加一层、不需要第二套流程；两者共享同一对象库与 refs，无重复下载成本、无多份 `.git` 的同步负担。选项②会让"隔离程度"变成会话自由变量，后续无法写出统一的裸判定（E1 ~ E3 的判定方式对两者不同）；选项③用更大的改动面换取本项目未观察到问题的额外隔离。
- **不确定时的影响面**：本项决定 §5 效果 E1 ~ E3 的**判定方式写法**——clone 形态下"另一个会话的提交是否出现在我的分支上"要换成"另一个仓库的提交历史"，判定者需要两套标准；也决定 P-9 的答案范围（clone 不共享 refs，P-9 的残留风险在 clone 下自动消失）。
- **R-1（参考视角，不进入结论，仅供讨论）**：worktree 隔离的是**工作树 + 索引 + HEAD 三者**，不隔离仓库级共享的 refs（stash 条目、分支命名空间、部分 reflog）与 `.git` 下的对象库。也就是说：**事故四类损害**能被 worktree 覆盖（它们全部由工作树/索引/HEAD 共享导致），但"stash 被另一会话 pop 走""两个会话想用同一个分支名"这类共享状态仍会发生。clone 则连这些也隔离。你若关心的是"本次观察到的损害不再发生"，worktree 已足够；若关心的是"两个会话在任何共享状态上都不互相可见"，clone 更彻底。

### P-2 · 会话如何"进入"自己的独立工作区？（本轮最关键的一项）

- **问题**：用户说"各用独立 worktree"，但**现行规范对"会话从哪里启动"零约束**（第 4.5 步只规定"切到迭代分支"，不规定"在哪个工作树切"）。谁创建工作区、会话怎么保证自己就在里面？
- **选项**：
  - **① 推荐**：**启动契约 + 硬停**。规范在"启动工作流"最前面加一步：主 agent 检测当前工作区是否为本会话专属（判据由架构阶段定形），**不是专属则停止推进并输出创建命令**，由用户确认后在新工作区重开会话。
  - ② 只写文档约定（"请各会话使用独立工作区"），不做任何检测、不硬停。
  - ③ 主 agent 自动创建 worktree 并把自身会话迁移进去。
- **推荐理由**：选项①把"隔离"从口号变成**可判断的入口条件**，与现有 SKILL Step 0「`.pb-agents/roles/` 不存在 → 停止推进」的硬停体例一致，不需要新机制类型。选项②无法裸判定（E1 无从验证"这次运行真的隔离了吗"）——事故的根因正是"没有人检查过会话在哪个工作树"。选项③存在**宿主能力不确定**问题（见 R-2）。
- **不确定时的影响面**：本项不裁决 = 机制可能落空（详见 `demand.md` 维度 2 的 P-A）。若选②，则 §5 的 E1 ~ E4 全部退化为"无法判定"，本迭代只能交付一段无法验证的文本。
- **R-2（参考视角，不是架构结论）**：主 agent 能否"把自己搬进新工作区"取决于宿主——一个会话的工作目录通常在启动时确定，Task 子 agent 继承会话目录，因此**推断会话无法自迁移 cwd**（`[INFERENCE]`，未经宿主能力核实）。若成立，可选形态只有两种：用户启动前手工 `cd` 进工作区，或由用户在会话中确认后、由主 agent 用绝对路径参数化所有后续命令（但子 agent 的继承目录不受此参数控制）。**这是给你判断"谁来创建、谁来进入"用的，不是最终方案。**

### P-3 · 工作区粒度：每会话一个，还是每迭代一个？

- **问题**：一个会话先后做多个迭代时（例：0017 收口与 0018 启动、或 0018 暂停后转做 0019），是复用同一个工作区（切分支），还是每个迭代一个新工作区？
- **选项**：
  - **① 推荐**：**每迭代一个工作区**（工作区绑定 `iteration/{迭代ID}` 分支，贯穿阶段 1~6；迭代暂停/结束前保留现场）。
  - ② 每会话一个工作区，跨迭代复用、靠 `checkout` 切分支。
- **推荐理由**：①与第 4.5 步"阶段 1 通过后创建迭代分支并切换工作区"的现有时序天然对齐（工作区就是迭代分支的检出点），且**暂停迭代的现场自动保留**（0018 被暂停时，其工作区仍在磁盘上，不需要任何额外动作）；②把"会话"当作跨迭代容器，工作区在迭代间切换时，未提交内容仍会互相影响（回到今天的问题形态）。
- **不确定时的影响面**：若选②，P-4（PR worktree 关系）与 P-12（暂停现场保留）都要按"工作区会跨迭代切换"重写；E6（暂停迭代现场仍在）需要额外规则才有判定依据。

### P-4 · 会话工作区与阶段 5 的 PR worktree 是什么关系？

- **问题**：阶段 5 已经在用 worktree（PR 级、短生命周期、base = 迭代分支、落点 `.pb-agents/worktrees/`）。新增的"会话/迭代工作区"是它的父层还是平行层？PR worktree 落在哪？
- **选项**：
  - **① 推荐**：**父子关系**——会话/迭代工作区是父层（长生命周期）；PR worktree 仍是其下短生命周期工作区，**base 仍为迭代分支**（不变），落点保持"相对当前工作区根目录的 `.pb-agents/worktrees/`"（即父层工作区内的忽略目录）；并显式声明"**PR worktree 不得被当作会话工作区使用**"。
  - ② 平行关系：PR worktree 仍落在仓库主工作区的 `.pb-agents/worktrees/`，与会话工作区平级。
- **推荐理由**：①不改变阶段 5 任何实质规则（base、解锁判据、命名都不动），只明确层级；落点保持在 `.pb-agents/` 下可继续复用现有 `.gitignore` 条目，且 PR worktree 天然随父层工作区的删除而清理。②会让 PR worktree 落回"仓库主工作区"，主工作区重新变成多会话共享的目录（虽然仅 `.pb-agents/` 被忽略，但 `git worktree list` 与现场排查会混在一起）。
- **不确定时的影响面**：本项与 P-3 联动；若 P-3 选②而 P-4 选②，则"每会话独立"在阶段 5 会被打破一半（PR 现场仍在共享目录）。E6 的判定方式也随之变化。
- **R-3（参考视角，不是架构结论）**：落点选择有一个具体的安全差异值得你判断**（`[INFERENCE]`，基于 `.gitignore` 与 `git clean` 语义推断，未实测）：若会话工作区放在仓库主工作区内的 `.pb-agents/worktrees/` 下，则主工作区里一次 `git clean -fdx` **会删掉该目录**——连带删掉散落在里面的其他会话的未提交内容（分支内容尚可从 git 恢复，未提交内容不能）。放在仓库外的同级目录则不受主工作区清理动作影响，代价是路径需要人工记忆与传递。`.worktrees/`（仓库根现存空目录）目前**不在 `.gitignore` 也不在 `.git/info/exclude` 里**，直接用它会让该目录出现在每个工作区的 `git status` 中。**这三条只供你判断方向，落点最终由架构阶段决定。**

### P-5 · 规范里"主 agent 根目录"改指谁？

- **问题**：现行规范第 4.5 步原文是"此后阶段 2~5 期间**主 agent 根目录**保持在该分支上"。"根目录"在新模型下如果仍指"仓库根工作树"，条款字面就意味着所有会话共用一个目录并轮流切换。
- **选项**：
  - **① 推荐**：把"主 agent 根目录"统一改写为"**该会话所在的迭代工作区根目录**"，并显式补一句"**仓库主工作区不作为任何迭代的工作区**"（它的角色见 P-6）。
  - ② 保留"根目录"措辞，另加一段说明"多会话时每个会话有自己的根目录"。
  - ③ 不做任何改写，留给架构阶段处理。
- **推荐理由**：①把隐含主体显性化，且不改变条款语义（"阶段 2~5 保持在该迭代分支上"这条规则本身是对的，只是对象变了）；②在两处定义同一概念，违反仓库既有教训（v0.2.0：`workflow-pb` + `workflow-scm` 两处重复表达同一套规则的耦合问题）；③属于需求层面的指代不清，留到架构阶段会导致"规范里每个'根目录'都要重新解释一遍"。
- **不确定时的影响面**：不改写则维度 4 的 C-1 张力原样存在；架构阶段需要为每一处"根目录"做一次语义仲裁，成本远高于现在改一句话。

## 组 B · 与现行规范的接缝改写（不改则机制在若干环节失效）

### P-6 · "迭代分支合并进 main"在哪执行？（git 硬约束，必答）

- **问题**：现行规范要求阶段 6 pass 后在主 agent 工作区依次执行 `git checkout main` → `git merge --no-ff iteration/{ID}` → `git branch -d iteration/{ID}`。一旦主 agent 的工作区变成了"某迭代的独立工作区"，`checkout main` 意味着**该工作区要放弃迭代分支、切到 main**——而 git 层面同一分支不能同时被两个工作区检出，多会话并发时这一步必然互相撞。
- **选项**：
  - **① 推荐**：**合并动作固定发生在仓库主工作区**（"main 的常驻检出点"），由发起合并的会话以显式路径在其中执行；会话工作区**永不 checkout main**。
  - ② 每次合并临时创建一个一次性 worktree 检出 main，合并后删除。
  - ③ 允许会话工作区 checkout main（并声明"同一时刻只允许一个会话做合并"）。
- **推荐理由**：①让 main 有且只有一个检出点，与会话工作区彻底解耦，且复用现有"合并三步"的动作顺序（只改执行位置，不改语义与触发时机）；②更干净但引入一次性 worktree 的创建/清理规则（本迭代不需要新增这类机制）；③把并发正确性重新交回人的纪律，正是本次要消除的模式。
- **不确定时的影响面**：不裁决则 E3/E4 的"两边产物都能各自找回"在**合并那一刻**断裂——两个会话若同时走到阶段 6，会有一方的合并动作直接失败，且失败现象与事故损害 3 同类。

### P-7 · 分支命名唯一性

- **问题**：所有会话共享同一个仓库的分支命名空间。两个会话若各自创建 `feat/pr-001` 这类不含迭代 ID 的分支名，会互相抢用或直接创建失败（阶段 5 的 `git worktree add -b <branch>` 在分支已存在时会失败）。
- **选项**：
  - **① 推荐**：规定"会话创建的**所有**分支名必须含迭代 ID"——迭代分支已是 `iteration/{迭代ID}`（不变）；PR worktree 分支规范化为含迭代 ID 的形式（如 `feat/{迭代ID}-pr-{NNN}-{描述}`，与 0005 迭代已出现过的命名先例同构）。
  - ② 只规定 PR 分支名的前缀，不要求含迭代 ID（沿用现状：`feat/0007-pr-001-history-log-protocol` 这类已含迭代 ID 的历史惯例并未写入规范）。
  - ③ 不做规定，撞名时人工处理。
- **推荐理由**：①用一句话消除整类碰撞，且与历史命名先例一致（只需把既有惯例写进规范）；②依赖"每个会话自觉带上迭代 ID"，今天的惯例之所以带 ID 是因为恰好只有一个会话；③会引入一种可预防的运行时失败。
- **不确定时的影响面**：与 P-4 的落点、P-3 的粒度共同决定阶段 5 在并发会话下能否跑通；不规定则 E1/E4 在阶段 5 有现实失败路径。

### P-8 · 每个工作区里的 `.pb-agents/roles/` 从哪来？（机制能否启动，必答）

- **问题**：SKILL 的 CRITICAL 规定"角色文件根路径**固定**为 `.pb-agents/roles/`"，Step 0 检测该目录不存在就**停止推进、不得退回读 `roles/` 源码目录**。而 `.pb-agents/` 在 `.gitignore` 里（整体忽略）⇒ **新建的 worktree 里没有这个目录** ⇒ 新机制下每个工作区都会在 Step 0 硬停，除非有额外动作。
- **选项**：
  - **① 推荐**：规范明确规定"**会话工作区创建后、进入 Step 0 前，必须在该工作区执行 `tools/install-pb-agents.sh`**"（安装目标 = 该工作区根目录），并把"检测失败即硬停"保留为兜底；同时声明 SKILL §已知代价（改 `roles/` 源码后须重装才同步）在每条会话工作区上分别成立。
  - ② 让角色文件检测改为指向"仓库主工作区的绝对路径"（一处安装、多会话共用一份 copy）。
  - ③ 不处理，视为用户启动前的环境准备（与规范无关）。
- **推荐理由**：①保持"角色文件是工作区本地状态"这一既有性质，安装脚本已经是幂等覆盖、无需改造（只需把目标参数指到工作区）；②会让多个会话**共享同一份可变 copy**——恰好重回本次要消除的模式（一个会话跑安装脚本 `rm -rf` 就会清空其他会话正在读的角色文件），且违反 SKILL "`.pb-agents/` 是只读 copy"的定位；③把必然发生的失败留给每个用户手工发现。
- **不确定时的影响面**：**这是机制能否真正跑起来的门槛项**。不裁决（或选③），则本迭代交付的规范在第一次真实执行时就会卡在 Step 0；同时决定 §5 的 E7 是否要写成效果。
- **R-4（参考视角，不是架构结论）**：安装脚本当前的行为是"先 `rm -rf` 目标 `.pb-agents/roles` 与 `.pb-agents/principles`，再重新 copy"，且默认目标是 `$(pwd)`——因此"在每个工作区各装一份"在脚本层面**不需要改造**，只需规范规定执行时机与目标。反过来，"共享一份 copy"在脚本层面反而是危险的（并发 `rm -rf` 竞态）。这只是脚本现状的客观描述，最终怎么做由架构阶段决定。

## 组 C · 残留风险与边界（写不写进规范）

### P-9 · 共享 refs（stash 等）的残留风险是否纳入本迭代范围？

- **问题**：worktree 不隔离仓库级共享的 refs。事故中出现过一次相关症状：S-0018 尝试 stash 0017 残留时"已无内容可 stash"（incident §2，17:52 行）——换成 worktree 后，"一个会话的 stash 被另一个会话 pop 走"这类事仍可能发生。
- **选项**：
  - **① 推荐**：**纳入为一条负面约束**——"会话工作区内不得使用 `git stash` 处理非本会话产生的残留；不得 `stash clear/drop` 清理非本会话的条目"，并在规范里显式声明"worktree 只隔离工作树/索引/HEAD，不隔离仓库级 refs（为什么只保证到这一层写成一句）。
  - ② 不写（承认风险但不落条款）。
  - ③ 升级形态为 clone，彻底消除（= P-1 选③）。
- **推荐理由**：①成本是一句话，收益是把一处真实发生过的症状变成可判断的禁令；同时把"隔离边界到哪里为止"写成显式声明，避免下游误以为 worktree = 完全隔离（这正是维度 2 · P-D 的缺口）。②会重复"假定不会有人碰到"的老问题。
- **不确定时的影响面**：不写则 E1 ~ E4 的覆盖面被读者过度解读为"完全隔离"，后续验证阶段会出现"这算不算违反"的争议。

### P-10 · 跨会话共享文件被并发修改：接受"冲突后移到合并期"吗？

- **问题**：工作区隔离后，两个会话各自修改**同一份被追踪文件**（如 `roles/**`、`principles/**`、顶层 `docs/*.md`）时不再互相改写，但两侧最终合并到同一目标分支时会产生真实冲突。这是从"运行时丢写"变成"合并期冲突"。
- **选项**：
  - **① 推荐**：**接受为已知代价并写进规范**（一句声明），不增加额外约束；补充说明"本迭代产物 `docs/iterations/{迭代ID}/**` 本来就按迭代分目录，天然不冲突"。
  - ② 要求"共享文件在任一时刻只允许一个会话修改"（引入新的协调纪律）。
  - ③ 不声明，等实际撞上再说。
- **推荐理由**：①合并期冲突是 git 的正常语义——**可见、可回滚、不会静默丢内容**，与事故中的"运行时静默覆盖"不是同一类风险；为它加协调纪律会引入本迭代边界外的新机制。③会让读者以为隔离等于不冲突。
- **不确定时的影响面**：若用户认为共享文件的并发修改必须被阻止，本迭代的改动面会显著扩大（需要引入锁/协调机制），这属于范围变化，建议明确说"是"或"否"。

### P-11 · 强制力级别：只做文本级"判断方式"，还是加机制化守卫？

- **问题**：本仓库既有约束（规则 A/B）的体例是"条款 + **判断方式**"，即人可客观判断但不自动拦截。新条款是否也要（或更要）机制化强制？
- **选项**：
  - **① 推荐**：**只做文本级"判断方式"**，与规则 A/B 体例一致；不做 hook/脚本守卫。
  - ② 额外提供一条可执行的辅助检测（脚本或命令清单），但不做 hook 拦截。
  - ③ 引入 hook（如 commit 前检测是否在共享工作区）强制拦截。
- **推荐理由**：①体例统一、零新增技术组件、验证方式与既有条款相同；③引入一类新的技术面（hook 的安装/绕过/可移植性），与用户"迭代优化流程"的诉求不等价。
- **不确定时的影响面**：本项决定 §5 的 E5 写法（"条款自带判断方式" vs "存在自动拦截"），也决定本迭代是否引入脚本类产物。**若用户希望"绝对不可违反"，需明确选③**，那会影响 PR 边界划分。

### P-12 · 暂停/终止迭代的工作区与分支现场保留与清理权责

- **问题**：迭代暂停（如 0018）或终止后，其工作区与分支谁保留、谁能清理？
- **选项**：
  - **① 推荐**：**现场原样保留**，只有该迭代的归属会话或用户可清理；其他会话一律不得对其执行删除/清理动作。（与现行"失败/阻塞 PR 的 worktree 与分支现场保留"体例同构）
  - ② 暂停时自动清理工作区（仅保留分支）。
  - ③ 不做规定。
- **推荐理由**：①复用既有体例、无新概念；且 0018 当前正处暂停态——用户原话"0018 分支与其未跟踪目录我未触碰"正是希望现场不被波及，这条规则把该意愿固化为通用条款。②会让未提交的中间产物消失（回到事故损害 1 的形态）。
- **不确定时的影响面**：与 P-3 联动；不规定则 E6 无判定依据。

### P-13 · 跨机器/多人场景：明确不保证？

- **问题**：规范是否要覆盖"两台机器各自开会话指向同一远端仓库"或"多人协作"？
- **选项**：
  - **① 推荐**：**只保证"同一仓库、同一台机器、多个主 agent 会话"**；跨机器/多人场景在"不做什么"里显式声明不保证（clone 形态可自然覆盖，但不作为本协议的义务）。
  - ② 一并纳入跨机器场景（需要定义远端的检出与同步规则）。
- **推荐理由**：①事故场景与用户诉求都是同机同仓库（一手记录明确是同一工作树上的两个会话）；②会引入远端拓扑与同步规则，属于另一个课题，违背最小边界。
- **不确定时的影响面**：只影响"不做什么"的一句话；选②会让本迭代的范围显著扩大。

### P-14 · 生效范围 + 0019 自身是否立即采用新形态？

- **问题**：（a）新条款是否沿用 v0.8.0 的"仅从下一个使用本工作流的迭代起生效、不追溯已完成迭代"？（b）**正在执行的 0019 自己**要不要立即迁到独立工作区（考虑到 D-1 记录显示第二写入方的风险仍在）？
- **选项**：
  - **① 推荐**：(a) **沿用不追溯原则**（与历次协议变更一致）；(b) **本迭代自身不强制迁移**，但要求主 agent 在阶段产物落盘后立即提交到本迭代分支、并在每次分支切换前核对工作区状态（= 延续 `status.md` 现有的自保措施），迁移动作留给下一个迭代作为首个真实执行样本。
  - ② (a) 沿用；(b) 本迭代立即可迁移到独立工作区（需要中断当前会话、在新工作区重开）。
  - ③ (a) 要求追溯已暂停的 0018（为其补建工作区）。
- **推荐理由**：①(a) 与 0008 先例一致；(b) 0019 的产物是**文档规范**，主 agent 的自保措施（落盘即提交）已能覆盖当前窗口，中断重开会让本迭代的收敛上下文丢失；而"迁移"这件事本身需要一个真实执行样本，下一个迭代做首个样本更合适。③ 0018 已被用户明确裁决暂停（其现场已被要求不要触碰），追溯与用户裁决冲突。
- **不确定时的影响面**：本项只影响"何时开始生效"与"当前会话是否要中断"，不影响条款内容；但若用户选②，需要主 agent 立即安排会话重启（属用户的即时操作决策）。
