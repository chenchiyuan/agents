### F02 — 并发度爬升机制

## demand.md §6「预期效果与验证标准（裸判定）」逐条验证

> 判断方式：假设一个完全没参与本迭代讨论的人，只拿到最终的 `workflow-pb.md`，能否判断"并发调度问题解决了"。

1. **并发确实发生**：**blocked**
   理由：这条标准的原文是"能观察到……"，要求的是可查证的实际执行证据（`git worktree list`、分支时间窗口），不是"协议文字写没写"。而本迭代自身在阶段 5 只规划、执行了**一个** PR（`pr-001`，`depends_on: (无)`，见 `status.md:23`），从未有第二个可并发的 PR 存在，因此本迭代自己的交付过程里不存在、也不可能产生任何"至少 2 个 PR �� worktree 分支时间窗口重叠"的真实证据。协议文字本身（F01-1）写得足够精确，若未来被忠实执行理论上能产生这一效果，但"理论上能"和"已经观察到"是两回事——裸判定标准问的是后者。这是本次验证中最重要的一条：**demand.md 根因诊断里指出的"这套协议文字从未被真实调度执行过一次"这一风险，在本迭代交付后依然原样成立，只是风险载体从"v0.3.0 的协议文字"换成了"v0.4.0 的协议文字"，尚未被证伪。**

2. **爬升机制生效**：**blocked**，同一根因——本迭代没有产生任何一次真实的槛位释放/补位事件，`status.md` 里从未出现过`## 并发配置（阶段 5）`区块被实际填写和更新的记录（核实：当前 `status.md` 全文没有"并发配置"或"起始并发数"字段，见下方「偏差记录」）。协议文字定义了公式和字段（F02 已判 pass/partial），但字段本身在本迭代里从未被实际初始化过、更没有被更新过一次，无法从本迭代产物中读出任何"从 3 爬升到 5"的真实记录。

3. **失败现场保留**：**pass（有保留意见）**
   理由：本迭代的唯一 PR（pr-001）以成功合并收尾，没有产生失败/阻塞的真实案例，因此同样没有本迭代自己的实证。但与前两条不同，这条的判断可以只依赖协议文字的完整性——协议文字对失败态的标签、状态表、progress-observer 核实机制三者齐全且互相印证（见 F04 逐项判定），一个不知情的人读到这套标签+审计机制，能够合理判断"设计上现场会被保留、且有兜底核查手段防止被静默清理"，用文字自洽性支撑判定为可信通过，同时明确指出：F04-3 缺少显式禁止清理指令这一文字缺口仍然存在，不构成 fail 但降低了确定性。

4. **失败不阻塞并发效率**：**pass**

## 下一迭代候选

- **协议文字的核心风险尚未被证伪**：本迭代解决的是"协议怎么写"，没有解决"协议会不会被真实遵守"——这正是 demand.md 根因诊断点名的问题本身。强烈建议下一个涉及多个可并发 PR（`depends_on` 图有真实分支）的迭代，把"是否观察到 worktree 时间窗口重叠""并发配置区块是否被正确初始化和更新""爬升是否真的按公式发生"作为该迭代阶段 6 验证的必查项，用真实数据把 demand.md §6 的四条裸判定标准补齐证据，而不是永远停留在"协议文字写得对不对"这一层。
- **阶段 5 首批派发缺少显式封顶指令**：`workflow-pb.md:205`"对每个已解锁 PR 立即并发派发"这句话本身没有绑定"取前 N 个（N=当前有效上限）"，封顶算法（`:220`）只在"槛位释放"场景下出现。建议下一版本把 `:205` 改为"对每个已解锁 PR，按当前有效上限取前 N 个立即并发派发"，让首批派发和补位派发共用同一条封顶规则，消除歧义。
- **"槛位空置不强行派发未解锁 PR"缺少正面陈述**：F02-4 后半句的行为从未被协议文字直接写出，建议补一句明确的负面约束（"没有已解锁排队 PR 时，空出的槛位不触发任何派发，不得因槛位空闲而放宽解锁条件"）。
- **F04 缺少对主 agent 的显式禁止性指令**：建议补一句"主 agent 不得对状态为失败/阻塞的 PR 执行 `git worktree remove`、`git branch -d` 或等价清理操作"，把现在"靠标签+事后审计"的间接约束，变成协议文字里可以直接对照检查的正面规则。
- **默认参数下爬升是"一步到顶"，不是渐进多级爬升**：`2×起始-1` 的硬上限公式在起始值较小时（如 3）会让第一次槛位释放就直接命中硬上限，实质上观察不到"逐步爬升"的中间状态。这是过渡期参数选择的自然结果（demand.md 已声明不锁定长期数值），供未来调大起始值或重新设计爬升步长时参考。
