# 需求合同：PR 并发执行

## 澄清依据

本合同基于以下多轮提案确认收敛，所有结论均标注来源，均为 `user_confirmed`，无遗留 `model_inferred`。

1. **根因定位**（`user_confirmed`）：用户确认"迭代都是串行执行 PR，一个个执行"，这是**主 agent 在阶段 5 实际派发时的操作层面**退化成逐个顺序调用，不是 `pr-planner` 的 `depends_on` 依赖判断错误，也不是 worktree/环境本身的限制。经代码库核实：`workflow-pb.md`（v0.3.0）"依赖解锁式并发调度"这套协议文字，在本项目里从未被真实调度执行过一次——仅有的一次 PR 拆分产出（`0004-model-dispatch` 迭代的 `prs/*.md`）用的是该机制引入之前的旧格式（"涉及 tasks"字段，无 `depends_on`），不构成"协议判断错误"的证据。这次迭代要解决的是**把已有协议文字变成主 agent 真正遵守的调度纪律**，不是修正协议判断逻辑本身。

2. **并发调度模型**（`user_confirmed`）：不是"上限=3 封顶"，而是"起始并发数=3（默认值，可配置），允许向上爬升，存在一个高于起始值的硬上限"。爬升触发条件是"有 PR 执行成功或失败返回"（即某个并发槛位释放时，不是简单补 1 个回到起始值，而是新增派发一批与起始值相同数量的 PR）。用户举例："最开始 3，一个返回后实际剩 2，再新增派发 3 个，达到同时 5 个在跑，之后维持在 5"。具体的爬升算法和硬上限数值（用户举例参考公式为 `2×起始值-1`）**不写入本合同**，只作为架构阶段的设计参考，避免需求阶段过早锁定一个后续可能需要调整的算法细节。

3. **"3+爬升"是过渡期保守值，不是永久设计意图**（`user_confirmed`）：用户原话"并发也只是为了方便测试，后期最理想的情况还是拉大并发"。当前选择小起始值和保守爬升，是因为并发安全性还在验证阶段，先用小起始值降低风险；这次迭代交付的是"机制"（从串行到有爬升能力的并发调度），不是"最终数值"。后续迭代可以在验证信心提升后调大起始值或重新设计爬升公式，本合同不视为对具体数值的长期承诺。

4. **"安全并发"范围界定**（`user_confirmed`）：`workflow-pb.md` 现有协议已经通过两条机制覆盖并发的正确性风险——"依赖必须以合并进主分支为解锁条件"（避免下游 worktree 看不到上游代码）和"PR 间文件范围无重叠"（避免并发改动同一文件产生隐藏冲突）。用户确认这两条已经足够，这次迭代**不新增语义耦合检测机制**（例如检测两个不改同一文件但语义上仍相互依赖的 PR），只需要让主 agent 真正执行这两条已有规则。

5. **PR 粒度判断标准不变**（`user_confirmed`）：`pr-planner.md` 现有的粒度判断标准（逻辑原子性、可审查性、独立性三条锚点）不在本次范围内调整。用户提到"控制粒度方便测试与回滚"这个诉求，已经被现有标准覆盖；这次迭代只解决"切好的 PR 怎么调度执行"，不涉及"怎么切 PR"。

6. **失败/阻塞 PR 的现场保留**（`user_confirmed`）：某个 PR 在并发执行中被判定失败或阻塞时，保留其占用的 worktree 目录和分支现场，不自动清理，方便排查。同时确认：**并发槛位的释放**只取决于该 PR 的状态（已合并 / 已判定失败或阻塞），与其 worktree 是否还留在磁盘上无关——即失败判定发生的那一刻，槛位立即释放可以补位派发新 PR，同一时刻该 PR 的 worktree 现场原样保留，两者不冲突、不互斥。

## 需求结论

### 1. 目标与价值

这次迭代要让 `workflow-pb.md` 阶段 5（PR 实现）已经写在协议文字里的"依赖解锁式并发调度"，从"从未被真实执行过的文字"变成主 agent 实际会遵守的调度纪律——同一时刻能观察到多个已解锁 PR 处于并发执行状态，而不是逐个顺序派发。

价值：PR 拆分的初衷是"尽量拆开有利于并发执行、控制粒度方便测试与回滚"，但如果调度层面始终退化成串行，拆分本身的收益就没有兑现。这次迭代把拆分的收益真正落到执行效率上。

### 2. 并发调度行为契约

- 起始并发数可配置，默认值为 `3`。
- 执行过程中允许向上爬升：每当一个正在并发执行的 PR 返回结果（成功或失败/阻塞），触发一次新增派发，新增数量与起始并发数相同（例：起始 3，1 个返回后剩 2 个在跑，触发新增 3 个，同时在跑数量变为 5）。
- 存在一个高于起始值的硬上限，达到后维持不再继续爬升；硬上限的具体数值和爬升算法（如 `2×起始值-1`）**留给架构阶段设计**，本合同不锁定。
- 已解锁但暂无槛位可用的 PR 排队等待，不是等所有并发中的 PR 全部完成才批量派发下一批。
- 该并发数配置是迭代级配置（如写入 `status.md`），不是全局固定值。

### 3. 失败/阻塞处理

- 某个并发中的 PR 被判定失败或阻塞：
  - 立即释放其占用的并发槛位，可被排队中的下一个已解锁 PR 补位，不等待人工处理。
  - 其 worktree 目录和分支现场原样保留，不自动清理（不执行 `git worktree remove`/`git branch -d` 等操作），方便排查。
  - 沿用 `workflow-pb.md` 现有规则："只暂停依赖它的下游 PR，不影响其他无关 PR 的并发推进"，本合同不改变这条规则本身。

### 4. 安全边界（本次不新增机制）

- 依赖解锁条件维持不变：只有依赖的 PR 已**合并进主分支**才算解锁，不是"dev 自称完成"。
- PR 间文件范围无重叠的校验维持不变。
- 本次不新增语义耦合检测机制（现有两条正确性保证已被确认足够）。

### 5. 本迭代包含与不包含

**包含：**

- 把 `workflow-pb.md` 阶段 5 的并发调度协议文字，落实为主 agent 实际执行时会遵守的调度纪律，达到可观察的并发执行效果。
- 起始并发数可配置（默认 3）+ 允许向上爬升 + 存在高于起始值的硬上限，这一行为契约本身。
- 并发槛位释放与 PR 状态（合并/失败/阻塞）绑定，与 worktree 现场清理与否解耦。
- 失败/阻塞 PR 的 worktree 现场保留、不自动清理这一行为契约。

**不包含：**

- 不改 `pr-planner` 的 `depends_on` 依赖判断逻辑本身（根因已确认不是判断错误）。
- 不新增语义耦合检测机制（现有两条正确性保证已确认足够）。
- 不改变 PR 粒度判断标准（逻辑原子性/可审查性/独立性三条锚点维持不变）。
- 不做具体的并发调度技术实现选型（用什么工具/API 发起并发子 agent 调用，属于架构阶段）。
- 不锁定爬升算法公式和硬上限的具体数值（架构阶段设计，本合同只定义行为契约存在）。
- 不锁定长期理想并发度——起始值 3 和当前爬升机制是过渡期保守选择，不是这次要固化的最终产品决策。

### 6. 预期效果与验证标准（裸判定）

进入功能规格/架构阶段后，应能从本合同拆出至少覆盖以下可观察信号的功能点，每条不依赖任何一方自我声明，只依赖客观可查证据（如 `git worktree list`、分支创建/合并时间、`status.md` 记录）：

- **并发确实发生**：给定一批同一时刻已解锁且数量大于 1 的 PR，能观察到至少 2 个 PR 的 worktree 分支同时处于"已创建、未合并"状态的时间窗口重叠。
- **爬升机制生效**：同时执行的 PR 数量从起始值开始，随着有 PR 返回结果而增加，直至达到某个高于起始值的上限后不再增加；该上限值可从状态记录或调度日志中读出。
- **失败现场保留**：某个 PR 被判定失败或阻塞后，其 worktree 目录和分支在判定发生之后仍存在于磁盘上，未被自动清理。
- **失败不阻塞并发效率**：某个 PR 判定失败后，其占用的并发槛位在判定发生的同一时刻即可被下一个已解锁 PR 占用，不需要等待该 PR 的 worktree 被清理。

**阶段交接标准**：本合同完成阶段 1 交付条件——两段内容均完整；所有结论均为 `user_confirmed`；没有活跃冲突或待确认的 `model_inferred` 项；未锁定爬升算法公式、硬上限具体数值或并发调度的技术实现方案。

**待确认疑问：无（`user_confirmed`）。**
