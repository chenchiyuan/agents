# F02 — 并发度爬升机制

**功能 ID**: F02
**来源**: `demand.md` §2「并发调度行为契约」（爬升触发条件、硬上限部分）、§6「爬升机制生效」判定
**迭代**: 0005-pr-concurrent-execution

---

## 用户价值

让并发调度不是固定在保守的起始值上，而是能随着"并发已验证安全"这一信号（PR 陆续成功返回）逐步释放更高的并发容量，直到触及一个安全上限，兼顾"起步保守、后期提效"的诉求。

---

## 验收标准

1. 每当一个正在并发执行的 PR 返回结果（判定为成功合并，或判定为失败/阻塞），触发一次新增派发；新增派发的数量与起始并发数相同。
   - 示例（来自 demand.md）：起始并发数 3，1 个 PR 返回后，当前在跑数量降为 2，此时触发新增派发 3 个，使同时在跑数量变为 5。
2. 同时执行的 PR 数量随着上述触发条件反复发生持续增加，直至达到某个高于起始并发数的硬上限后不再继续增加；即使后续再有 PR 返回结果，在跑数量也维持在该上限，不超过它。
3. 该上限值可以从状态记录或调度日志中读出（即"当前生效的上限是多少"这件事本身是可查证的，不是只存在于某次调度决策的隐含计算里）。
4. 爬升机制只影响"允许同时在跑的 PR 数量上限"，不改变 F01 中"已解锁 PR 才能被派发"的前提——爬升带来的新增派发槛位，仍然只能分配给已解锁、排队中的 PR；没有已解锁 PR 排队时，槛位空置，不强行派发未解锁的 PR。

---

## 边界（不包含）

- 不包含具体的爬升算法公式（如 `2×起始值-1`）——`demand.md` 明确本合同不锁定该公式，仅作为架构阶段的设计参考。
- 不包含硬上限的具体数值。
- 不包含"新增派发数量与起始并发数相同"之外的其他爬升速率设计（如按比例递增、指数增长等）——本合同只确认这一种触发和增量方式。
- 不包含把当前的起始值 3 和爬升机制视为长期理想并发度的最终决定；这是过渡期保守选择（见 demand.md 澄清依据第 3 条），后续迭代可调整。

---

## 架构维度

**爬升算法**：`当前有效上限 = min(起始并发数 + 累计成功解锁次数 × 起始并发数, 硬上限)`，每当一个并发中的 PR 返回结果（成功合并或失败/阻塞），`累计成功解锁次数 += 1` 并重新计算。

**硬上限数值**：`硬上限 = 2 × 起始并发数 - 1`（采纳 demand.md 给出的参考公式）。起始 3 → 硬上限 5；起始 2 → 硬上限 3。

**记录字段**：`status.md` 的 `## 并发配置（阶段 5）` 区块新增 `**硬上限**`、`**当前有效上限**`、`**累计成功解锁次数**` 三个字段，上限值可直接从 `当前有效上限` 字段读出，不需要独立调度日志。

详见 `architecture.md` §决策 D2。
