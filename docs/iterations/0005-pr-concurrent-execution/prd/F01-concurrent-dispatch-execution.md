# F01 — 并发派发执行（替代顺序 dispatch）

**功能 ID**: F01
**来源**: `demand.md` §2「并发调度行为契约」（起始并发数、排队机制部分）
**迭代**: 0005-pr-concurrent-execution

---

## 用户价值

让同一时刻已解锁的多个 PR 真正同时执行，而不是逐个顺序派发排队，把 PR 拆分"利于并发"的初衷真正兑现为可观察的执行效率。

---

## 验收标准

1. 给定一批同一时刻已解锁（无依赖，或依赖的 PR 均已合并进主分支）且数量大于 1 的 PR，能观察到至少 2 个 PR 的 worktree 分支同时处于"已创建、未合并"状态，且这两个分支的存在时间窗口有重叠。
2. 同时进入执行状态的 PR 数量以"起始并发数"为上限；起始并发数可配置，默认值为 `3`。
3. 已解锁但因并发槛位已满暂无法派发的 PR 进入排队等待状态；一旦有槛位释放，排队中的下一个已解锁 PR 立即被派发，不需要等待当前所有并发中的 PR 全部完成后才批量派发下一批。
4. 起始并发数是迭代级配置（例如记录在该迭代的 `status.md` 中），不是写死在工作流文字里的全局固定值；同一工作流规范下，不同迭代可以配置不同的起始并发数。

---

## 边界（不包含）

- 不包含并发数向上爬升的触发条件和硬上限（见 F02）。
- 不包含具体的并发执行技术手段：以何种方式并发调用子 agent、如何创建独立 worktree 分支的实现细节（已在下方「架构维度」补全）。
- 不包含依赖图的判定逻辑本身——"哪些 PR 已解锁"沿用 `pr-planner`/`depends_on` 现有判断，本卡不改变判断依据。
- 不包含起始并发数配置的具体存储字段名和文件格式（已在下方「架构维度」补全）。

---

## 架构维度

**并发调用技术手段**：主 agent 在同一轮 assistant 响应中连续发起多个 `Agent()` 工具调用，同一响应内的多个 tool use 并发执行，不逐一等待返回。派发前先读取 `prs/*.md` 构建依赖图，筛选出已解锁 PR，取前 N 个（N = 当前有效并发上限）发起并发调用。

**起始并发数配置存储**：记录在该迭代 `status.md` 新增区块 `## 并发配置（阶段 5）`，字段 `**起始并发数**`（默认 3）。

**排队机制**：不使用独立数据结构，排队状态即"已解锁但暂未被选中派发的 PR"，通过重新扫描 `prs/*.md` 依赖图 + `status.md` 的"PR 实现子状态"表现有状态列判断，见 `architecture.md` 决策 D1/D3。

详见 `architecture.md` §决策 D1、D3。
