# F04 — 失败/阻塞 PR 的 worktree 现场保留

**功能 ID**: F04
**来源**: `demand.md` §3「失败/阻塞处理」（现场保留部分）、§6「失败现场保留」判定
**迭代**: 0005-pr-concurrent-execution

---

## 用户价值

PR 失败或阻塞后，排查者能直接在原始 worktree 目录和分支上复现问题现场，不必凭记忆或日志重建执行环境。

---

## 验收标准

1. 某个 PR 被判定为失败或阻塞后，其占用的 worktree 目录在判定发生之后仍原样存在于磁盘上。
2. 该 PR 对应的分支在判定发生之后仍存在，未被删除。
3. 不对失败/阻塞 PR 执行任何自动清理操作，包括但不限于 `git worktree remove`、`git branch -d` 及等价操作。
4. worktree/分支现场是否保留，与该 PR 占用的并发槛位是否已释放两者互相独立——槛位在判定发生的同一时刻释放（见 F03），worktree/分支现场在同一时刻原样保留，两个行为同时成立、不互斥。

---

## 边界（不包含）

- 不包含成功合并的 PR 的 worktree/分支处理方式——本卡只约束失败/阻塞场景，不改变成功场景下现有的清理规则。
- 不包含现场保留后的人工排查流程或清理触发条件（何时、由谁清理失败现场，不在本次迭代范围内定义）。
- 不包含失败/阻塞判定逻辑本身（见 F03 边界）。

---

## 架构维度

**标识方式**：`status.md` "PR 实现子状态"表的"状态"列使用专属取值 `❌失败(现场保留)` / `⏸阻塞(现场保留)`，"worktree 分支"列同时标注 `(保留)`（对比成功合并后的 `(已清理)`），不新增独立字段——现场保留是失败/阻塞状态的固有行为，不需要额外布尔标记。

**核实机制**：`progress-observer` 每次生成 `progress.md` 时，对状态为失败/阻塞的 PR，额外核实其 worktree 目录和分支是否仍存在于磁盘（`git worktree list` + `git branch` 交叉核对），不一致则记入"发现的不一致"。该核实项写入 `workflow-pb.md`"可观测性"章节的调度契约，不修改 `progress-observer.md` 角色定义本身。

详见 `architecture.md` §决策 D4。
