# F03 — 失败/阻塞后的并发槛位即时释放

**功能 ID**: F03
**来源**: `demand.md` §3「失败/阻塞处理」（槛位释放部分）、§6「失败不阻塞并发效率」判定
**迭代**: 0005-pr-concurrent-execution

---

## 用户价值

单个 PR 失败或阻塞不应拖慢其他并发工作的推进速度——槛位要在判定发生的那一刻就还给调度池，让排队中的下一个 PR 立即补位，不必等人工介入或等 worktree 清理。

---

## 验收标准

1. 某个并发中的 PR 被判定为失败或阻塞时，其占用的并发槛位在判定发生的同一时刻即被释放。
2. 释放出的槛位可被排队中的下一个已解锁 PR 立即占用，不需要等待该失败/阻塞 PR 的 worktree 目录被清理（因为按 F04，worktree 本来就不会被清理）。
3. 槛位释放不需要等待人工处理或确认，是判定发生后的即时行为。
4. 某个 PR 被判定失败或阻塞时，只暂停依赖它的下游 PR（如有）；不依赖它的其他并发中或排队中的 PR 不受影响，按原有节奏继续推进——这一规则沿用 `workflow-pb.md` 现有定义，本迭代不改变该规则本身，只确认它在新的并发+爬升调度下依然成立。

---

## 边界（不包含）

- 不包含失败/阻塞的判定逻辑本身（如何判断一个 PR 属于"失败"还是"阻塞"，属于既有验收流程职责，本卡不重新定义）。
- 不包含 worktree/分支的清理或保留行为（见 F04）。
- 不包含依赖它的下游 PR 恢复推进的触发条件（该下游 PR 何时能重新解锁，取决于失败/阻塞 PR 后续如何处理，不在本次迭代范围内新定义）。

---

## 架构维度

**实现时机**：主 agent 收到任一 PR 子 agent 的完成通知（成功或失败/阻塞）时，在同一轮 turn 内立即：更新 `status.md` 状态 → 重新计算当前有效上限 → 重新扫描依赖图筛选已解锁排队 PR → 同一响应内发起补位的并发调用，不等待其他并发中的 PR。

**槛位状态记录方式**：`status.md` 的"PR 实现子状态"表新增"槛位状态"列，取值为"占用"/"排队(依赖未满足)"/"排队(等待槛位)"/"已释放"。

详见 `architecture.md` §决策 D3。
