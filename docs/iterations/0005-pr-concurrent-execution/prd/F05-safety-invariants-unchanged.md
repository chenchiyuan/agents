# F05 — 并发调度下的既有安全边界维持不变

**功能 ID**: F05
**来源**: `demand.md` §4「安全边界（本次不新增机制）」
**迭代**: 0005-pr-concurrent-execution

---

## 用户价值

让用户确信并发和爬升带来的执行效率提升，不是靠放宽正确性检查换来的——两条已确认足够的正确性保证在并发场景下同样生效，不因为调度变复杂而被绕开或弱化。

---

## 验收标准

1. 在并发调度下，一个 PR 被判定为"已解锁"仍然要求其 `depends_on` 列出的所有 PR 均已**合并进主分支**；仅"该 PR 的 dev 自称完成"或"该 PR 的 worktree 分支存在提交"不构成解锁条件。
2. PR 间文件范围无重叠的校验维持不变，且在并发派发场景下依然对每个被派发的 PR 生效——即并发派发多个 PR 不改变、不放宽这条校验的适用范围。
3. 本次迭代交付的调度机制中，不出现任何新增的语义耦合检测逻辑（例如检测两个不改同一文件但语义上仍相互依赖的 PR）；如果实现中出现此类新检测，视为超出本迭代范围。
4. F03 的槛位即时释放，仅解除对"已完成判定 PR"的占用，不改变、不绕过第 1、2 条列出的解锁前置条件——即槛位释放让排队中的 PR 有机会被派发，但该 PR 是否真正满足解锁条件，仍要独立判断。

---

## 边界（不包含）

- 不包含对依赖判断逻辑本身的修改——`pr-planner` 的 `depends_on` 判断标准、PR 粒度判断标准（逻辑原子性/可审查性/独立性）均不在本次范围内调整，沿用现状。
- 不包含新增的语义耦合检测机制的设计——本卡的验收标准是"确认不新增"，不是"设计一个新的检测方式"。
- 不包含对现有两条正确性保证本身的实现方式说明或改造，本卡只确认它们在并发场景下继续适用。

---

## 架构维度

无需架构阶段新增设计——本卡对应的是"确认现状不变"，不产生新的技术决策点。若技术架构阶段发现并发实现方式本身对这两条保证产生了技术影响（如需要显式的调度前置检查代码路径），由架构阶段在其他功能卡（F01/F02/F03）的架构维度中承接，不在本卡新开条目。
