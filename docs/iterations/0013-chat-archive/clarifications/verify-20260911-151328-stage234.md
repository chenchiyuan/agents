### 5. 两处硬契约的可执行性：**pass**（对照 `oamp/src/persist.js` 现状 + 真实 SQLite 行为实验）

实验方式：以 `node:sqlite` 建**内存库**复现（未写入仓库、未修改任何产出物）：① 用现行 7 列 SCHEMA 建库并插行，再执行新 SCHEMA + `migrate()`；② 按架构 §3.3 的 SQL 原文建 61 条归档 / 5 条未归档混合数据，跑缺省视图、`archived=1`、条件排序、`limit=20` 三轮分页、`state=closed` 组合。结果：共执行 37 项断言，其中 35 项通过；2 项失败经复核为验证脚本自身的断言写法错误（在同一行已被归档后又断言它"未归档"），与被验证设计无关——重写该断言的对照项均已通过。

- **§3.2 迁移写法（AR-05）可执行**：`SELECT name FROM pragma_table_info('chats')` 在 `node:sqlite` 下可作 `prepare().all()` 使用——**该函数已被现有测试当作列名真源使用**（`test/persist.test.js:71`），可用性无需假设。实验确认：对既有库先 `exec(新 SCHEMA)`（`CREATE TABLE IF NOT EXISTS` 静默 no-op，不报错、不加列），随后 `ALTER TABLE chats ADD COLUMN archived_at INTEGER` 与 `ADD COLUMN context_released INTEGER NOT NULL DEFAULT 0` 均成功（`NOT NULL` + 常量默认值可 ADD）；迁移库与新建库 `pragma_table_info` 顺序**逐位相同** = `['chat_id','title','agent_id','state','created_at','updated_at','closed_at','archived_at','context_released']`；既有行得 `NULL` / `0`；第二次 `migrate` 全 no-op。M-1~M-3 的三条可断言项均成立。
- **`CHAT_COLUMNS` 与写口白名单的影响面**：`CHAT_COLUMNS` 全仓仅 `getChat` 一处使用（`persist.js:45` 定义、`:141` 引用），追加两列只影响详情返回体 → 与 `persist.test.js:303-305` 的键白名单断言一致；写口白名单断言（`persist.test.js:108-111`）是 `Object.keys(db)` 动态枚举 + `.sort()`，`listArchivable` 进"读口排除名单"后断言集才成立——**改法可行且必要**，且不影响 `insertInput({direction:'out'})` 那条结构面断言（`persist.test.js:112-113`）。

## 下一迭代候选

- **`context_released` 的语义窄化**：见 D2——当前一位标志同时承载"归档已释放上下文"与"激活后待新回答"两种含义，导致归档态详情页出现"激活后…"文案。若下一迭代引入"激活"专属位或改为中性文案，可消除歧义。
- **迁移机制的第二档**：本次以"列存在性守卫"引入首个迁移块（架构 §15 R-2/M-4 已给再评估条件）。当迁移条目增多或出现破坏性变更（改列类型/拆表）时，需要 `user_version` 或迁移目录——建议下一迭代或专门迭代评估。
- **归档视图的索引与排序成本**：`ORDER BY (CASE …)` + `archived_at IS NOT NULL` 必然全表扫描（R-2）。chats 达万级时需拆 `listArchivedChats` 第二组语句 + `idx_chats_archived(archived_at DESC)`。
- **`failed_ids` 分支的可测性**：单进程 `DatabaseSync` + 逐条 `UPDATE` 的现实失败场景极少（R-9），失败分支实际上无法被端到端覆盖，现有测试只能用"working 不可归档/已归档跳过"覆盖边界。建议下一迭代决定：是否接受"防御性死分支"，或提供可注入的失败缝。
- **归档视图无实时刷新**（R-5）：多标签页/多窗口下归档视图不会自动更新（主列表本亦如此）。若用户实际有多窗口使用习惯，需补 SSE 或轮询。
- **批量归档不可中断**（R-8）：N 大时无进度与取消（F01 边界已排除）。若真实使用中出现"取消"诉求，属产品口径变更。
- **测试期望集的书写方式**：`persist.test.js` 的写口白名单是"导出枚举 + 排序"的断言，每加一口都要同步（本次已因排序写错而在文档层暴露）。可评估改为显式 `Set` 白名单以减少笔误面。
