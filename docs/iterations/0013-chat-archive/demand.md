## 第一段：澄清依据

### 1. 用户原始表述（2026-09-11，user_confirmed）

> 新增小功能，chat 列表新增一键归档。可以把当前的对话全部移到归档分类（按时间排序），归档的对话也支持单个激活。这样我就有最简单的管理对话功能了

**目标陈述拆解**：用户要的是"最简单的管理对话功能"——一个由三件事组成的最小闭环：**收起（一键归档）→ 分类（归档分类页）→ 捞回（单个激活）**。这三件事互相依存，去掉任一件，闭环不成立（只能收不能捞 = 单向丢失；只能分不能收 = 无动作可分类）。

#### 4.2 逻辑闭环 —— why 能否推出 what

- 从已确认 why（"最简单的管理对话功能"）反推 what，三件事（归档 / 分类 / 激活）齐备且互相依存（见 §1 拆解），**无脱节**。
- 但发现一个**用户可感知的后果需要显式记录**：D-1 的范围是"除 working 外全部"，因此一次一键归档会把**当前主列表里的所有对话**（包括刚刚完成、可能还在看的）统统移入归档页，主列表只剩进行中的对话。这与用户已确认的范围一致（user_confirmed），不属于错误需求，但需求合同必须写明这个后果，避免实现后用户对"列表突然空了"感到意外。

#### 4.3 边界完整性 —— "不做什么"哪些是用户明说的、哪些是推导的

用户明说的边界只有一条：**进行中的对话不归档**（D-1）。其余 9 条"不做什么"（见第二段 §2）均为推导所得，属薄弱点，逐条给出"为什么这次不做"的理由，并已于 2026-09-11 逐条确认（见 §2.2；其中 N-5 是唯一具有规范冲突性质的边界，见 4.4）。

#### 4.4 内部一致性 —— 草稿内部及与既有规范的矛盾

| # | 矛盾 | 处理 |
|---|---|---|
| C-1 | **归档对话可激活 ↔ 0011"closed 是终态、不可重开"**（`oamp/README.md:162,175`）。D-1 明确归档范围**包含此前已 closed 的对话**，而 D-2 要求激活 = 恢复可继续对话 → 激活一个原本 closed 的对话，必然要解除 closed 终态。这是本迭代对 0011 已确认规范的**直接收窄例外**，必须在需求阶段显式确认，不能留给架构阶段发现 | 已确认（D-6）：需求结论按"**仅归档路径可获得可重开，非归档的已关闭对话仍不可重开**"收窄（N-5） |
| C-2 | 只读出现**两条路径**（`state=closed` 与"已归档标记"） | 显式并存且优先级不冲突：任一条命中即拒收新输入；状态还原规则 A-5 保证激活后不残留第二条路径 |
| C-3 | 归档若不改变 `state`，归档的 completed 对话仍会命中 `?state=completed` 过滤 → 分类泄漏 | M-8：默认列表（含 state 过滤）一律排除已归档，仅"归档页"返回已归档 |
| C-4 | 激活若保持原 `state=closed`，则"可继续对话"不成立 | A-5：激活时对 `state=closed` 的对话恢复为 `completed`（清除关闭时间），其余状态原样保留 |
| C-5 | "归档时间倒序"要求时间戳每次归档刷新（重复归档同一对话——虽然归档范围排除已归档，但激活后可再次归档） | A-2 规定每次归档写入**当次**归档时间；A-1 对已归档对话跳过（幂等） |

#### 4.5 可验证性 —— 裸判定

每条"达到什么效果"（第二段 §4）已过裸判定测试：不点名具体工具、不依赖背景知识、可由第三方直接观察判断真假。

#### 4.6 方案雏形 —— 用户对"怎么做"是否已有具体想法

**澄清说明**：第一轮派发无实时用户对话通道，无法按角色既定流程向用户直问"关于『一键归档/激活』你有没有已想到的做法"，故先以推导 + 参考视角替代（原提案 P-6）。2026-09-11 经主 agent 转呈后用户已明确回应：**未提出额外机制想法，下列做法 A 即为其确认的机制**（见 §2.2 D-14 / D-5）。

**参考视角（不进入结论段，仅供讨论；不是架构结论）**：

> 为了让"归档可逆且不影响对话原状态"成立，常见有两种做法：
> **做法 A（归档标记独立于状态）**：归档只写标记 + 归档时间，释放上下文，只读由标记承担；激活 = 清标记（若对话处于已关闭态，则同时恢复为已完成）。优点：对话原状态完整保留，"激活 = 恢复"语义自然；代价：只读判定多一条路径。
> **做法 B（归档复用关闭）**：归档即把对话置为 `closed`（复用现有只读与释放流程）；激活 = 恢复为 `completed` 并清归档标记。优点：复用既有只读路径与哨兵保护，新增判断更少；代价：归档期间对话原状态（completed/failed）丢失，全部显示为"已关闭"。
> 两种做法在需求层面对用户可见的差异是：归档项是否保留原状态 badge。本条只是判断依据，不代表最终方案。

**裁决（2026-09-11，user_confirmed）**：采用**做法 A**（独立归档标记），见 §2.2 D-5/D-14；做法 B 不采用。

### 2. 不做什么

| # | 边界 | 为什么这次不做 |
|---|---|---|
| N-1 | 不做**对话删除** | 用户要的是"管理"（收起/分类/捞回），归档已满足；删除是独立且不可逆的能力，去掉它最小闭环仍成立 |
| N-2 | 不做**自动归档策略**（按时间/数量阈值自动触发） | 用户明确说的是"一键"手动触发；自动策略引入阈值语义与用户预期管理，属下一次迭代 |
| N-3 | 不做**批量激活** | 用户明确只要"单个激活"；批量激活会让"激活后待处理的对话"一次涌入主列表，收益低 |
| N-4 | 不做**上下文还原**（激活不恢复被释放的常驻 LLM 上下文） | 0011 的 `context_release` 已是既成语义；还原上下文需要持久化会话态，成本与本次"最小管理功能"不匹配 |
| N-5 | 不新增**通用"重开对话"能力**：非归档状态下已关闭的对话仍不可重开，可重开仅通过"归档 → 激活"路径获得 | 这是对 0011「closed 终态不可重开」的最小收窄例外（C-1）；放开通用重开是更大的产品决策，超出本次范围。（已确认：D-6） |
| N-6 | 不新增**归档专属的搜索/时间过滤维度** | 沿用现有 q/agent 过滤能力（若实现天然复用则保留，不作功能要求）；新增过滤维度对"最简单"无贡献 |
| N-7 | 不做**归档项的手动排序 / 排序自定义** | D-4 已定死归档时间倒序，无额外诉求 |
| N-8 | 不做**多用户 / 权限** | 沿用 0011 既有边界（无鉴权） |
| N-9 | 不做**历史数据迁移**：库中已有的 `closed` 对话视为"未归档"，保持现状（仍出现在 All） | 无法区分"用户主动关闭"与"本应归档"，推测性迁移会污染数据；新标记默认 NULL 即正确语义 |

### 3. 大概怎么做（产品级形态；字段名/接口形态/批量编排/迁移写法留架构阶段）

- **归档标记独立于 `state`**（M-1，已确认 D-5）：需要一个"是否归档 + 归档时间"的持久化标记，使归档可逆、不污染对话原状态。
- **只读由归档标记承担**，叠加在既有 `state=closed` 只读之上（C-2）；列表查询增加"是否归档"维度，默认排除已归档（C-3）。
- **上下文释放复用现有 `context_release` 通道**，不新造机制。
- **数据层必须显式迁移**：现状 `openDb` 仅 `CREATE ... IF NOT EXISTS`，对已存在的库改 SCHEMA 文本不会新增列（§3 事实）。
- **批量归档的编排**（前端逐条调用现有单条接口，或后端批量接口）与接口命名/字段名，属架构决策，本文件不预设。
- **已知受影响的既有契约**（属已知成本，实现/架构阶段同步更新）：`persist.test.js` 列名与字段白名单断言、`web.test.js` 前端静态与 API 契约断言、`README.md` 中"closed 不可重开"的描述需按 N-5 收窄。

### 5. 为什么这么做

- **为什么是这三件事**：用户的目标是"最简单的管理对话功能"；管理的最小闭环 = 收起 + 分类 + 捞回。三件缺一，功能即退化为单向操作。
- **为什么用独立归档标记而不是新增 state 值**：用户措辞是"分类标记"，且 `state=closed` 在 0011 被定义为不可重开的终态；把它当成归档会让"激活"变成"重开终态"，与既有规范正面冲突且不可逆（M-1/C-1）。
- **为什么排除 working**：进行中的对话被归档会在中途释放上下文、产生用户不可预期的失败轮次（用户已确认）。
- **为什么归档时间倒序**：归档页的第一诉求是"最近收起的在最上面"（用户已确认）。
- **为什么保留原状态**：使"激活 = 恢复"语义成立（C-4），且归档页能区分"归档了一个失败的对话"与"归档了一个已完成的对话"。
- **为什么是收窄例外而非放开通用重开**：最小化对 0011 既有约定的推翻面（N-5）。
