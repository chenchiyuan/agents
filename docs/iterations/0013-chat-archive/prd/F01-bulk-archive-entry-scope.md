# F01：一键归档（入口、范围、确认、结果可见性）

**功能 ID**: F01
**来源**: `demand.md` A-1（入口与范围）、A-9（二次确认）、A-8（结果可见性）；澄清 M-2 / M-6 / M-7；决策 D-1 / D-8 / D-10 / D-11；效果 E-1（首段）、E-5；边界 N-1 / N-2 / N-3 / N-7 / N-8 / N-9
**迭代**: 0013-chat-archive

---

## 用户价值

主列表堆满历史对话时，一次操作就能把所有"已经结束的"收起来，而且不会误伤正在进行中的对话。

## 验收标准

1. **入口存在且位置可辨**：过滤栏（All / Working / Completed 所在行）右侧存在一个按钮，文案为「归档全部」（D-11 / M-2）。判定：该按钮与过滤标签处于同一区域且位于其右侧，用户无需进入其他页面即可点击到它。
2. **范围正确（进行中对话不动）**：点击并确认后，所有当时"未归档且非进行中"的对话被归档，即**已完成 / 失败 / 已关闭**的未归档对话全部落入本次范围（D-1）。判定：执行前后，任何处于**进行中**的对话仍留在主列表且其状态不变（E-5）；其中已完成 / 已关闭的对话同样被归档，不因"仍在看"或"已经关闭"而被跳过。
3. **范围后果是预期结果**：一次「归档全部」执行完成后，主列表（All）中只剩进行中的对话——这是本迭代既定范围的直接后果，不是缺陷（demand §4.2 显式记录）；归档视图按归档时间倒序列出被归档的对话（E-1）。
4. **已归档的跳过（幂等）**：执行时已被归档的对话不在本次范围内，其归档时间不被本次操作改动（A-1 末句）。
5. **一次轻确认**：点击按钮后先弹出一次轻量确认；确认后才执行归档；取消则不对任何对话执行归档（D-8 / A-9 / M-6）。确认文案不显示待归档条数（D-8），内容为「将归档全部非进行中的对话，是否继续？」（A-9）。
6. **结果可见（不静默）**：执行结束后给出结果反馈——至少包含本次成功归档的条数；存在失败项时，同时给出失败条数或失败项清单（D-10 / A-8 / M-7）。执行结束后主列表立即反映归档结果（被归档的对话不再出现在 All 列表），无需用户手动刷新页面 `[user_confirmed M-05]`。
7. **失败不回滚、失败项可重试**：批量执行中单条失败不影响其他已成功项（不回滚已成功的）；失败项仍留在主列表，仍可被下一次「归档全部」再次尝试（D-10 / A-8）。
8. **零可归档项时同样有反馈**：当没有符合条件的对话可归档时（例如全部已归档、或只剩进行中对话），执行结束后仍给出结果反馈（0 条），不得静默无响应 `[user_confirmed M-01]`。

## 边界（不包含）

- 不含"归档"这一动作对单条对话产生的语义（归档标记、归档时间、只读、历史保留）——那是 F02；本卡只规定"由谁触发、范围多大、结果怎么反馈"。
- 不含归档视图的入口、内容、排序与容量（F03 / F04），也不含激活（F05）。
- 不做**对话删除**（N-1）——归档不是删除，操作后数据仍在且可恢复。
- 不做**自动归档策略**（按时间 / 数量阈值自动触发）——归档仅由用户手动一键触发（N-2）。
- 不做**批量激活**（N-3）。
- 不做**归档项的手动排序 / 排序自定义**（N-7）——归档视图排序由 F03 按归档时间倒序固定。
- 不做**多用户 / 权限**（N-8）。
- 不做**历史数据迁移**：操作前库中已存在的对话一律视为"未归档"（N-9），本卡不因其既有状态做特殊处理。
- 不含批量执行的中断 / 取消 / 暂停能力，也不含"正在执行中"的进度条（demand 未要求）。

## 架构维度（阶段 3 已填，2026-09-11；详见 `architecture.md` §5.1 / §6.1 / §6.2）

- **AR-01 归档动作的接口形态与批量编排**：**后端一次编排的批量端点** `POST /api/chats/archive`（无请求体；范围由服务端按 A-1/D-1 计算，前端不参与范围判定）。内部逐条执行 `UPDATE chats SET archived_at=?, context_released=1 WHERE chat_id=? AND archived_at IS NULL AND state != 'working'`（每条语句独立提交 ⇒ 成功项天然不回滚，逐条结果可计数）。**不提供单条归档端点**：产品没有单条归档触发点（F01 只有「归档全部」，F03 的归档视图只有「激活」）。否决前端逐条调用（N 次往返 + 范围判定搬到只持有第一页的前端）与单条全量 UPDATE（语句级原子 ⇒ F01-6/7 的失败反馈成死代码）。
- **AR-02 批量结果的可见性承载**：响应体 `{ archived, failed, failed_ids }`（三键恒存在，无失败时 `0` / `[]`）；`archived` = 本次真正归档的条数（不含已归档跳过与进行中），零可归档项时返回 `{archived:0,failed:0,failed_ids:[]}`（验收 8 / M-01 的"不静默"）。界面承载 = 既有 `#hint` 行（与"发送失败 / 关闭失败"同一位置）：「已归档 N 条」/「已归档 N 条，M 条失败——失败项仍留在主列表，可再次点击「归档全部」重试」。失败项能重试是因为其 `archived_at` 仍为 `NULL` ⇒ 下次调用自然重新入选。**不发 SSE 事件**（归档不改 `state`、主列表不由 SSE 驱动、N 条事件是噪声）；可见性由响应 + 前端在响应后调用 `GET /api/chats` 重载承载（验收 6 / M-05"无需手动刷新页面"）。
- **AR-03 一键归档入口的落位承载**：`web/index.html` 的 `.filters` 容器内新增 `<button id="btn-archive-all" class="archive-all">归档全部</button>`（第 5 个元素），CSS 以 `.archive-all{margin-left:auto}` 抵到该行最右侧（与 All/Working/Completed/归档 同一区域，验收 1）；文案固定「归档全部」（D-11）。视觉 token 复用既有 `.filter` / `.new-chat` 一族，零新增 CSS 变量。点击后 `window.confirm('将归档全部非进行中的对话，是否继续？')`（验收 5 / A-9 逐字、不显示条数 D-8），取消即不发请求。
