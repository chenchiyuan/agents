# F05：单个激活（恢复可续、置顶、状态还原、上下文不延续提示）

**功能 ID**: F05
**来源**: `demand.md` A-4（单个激活）、A-5 后半（状态还原规则）、A-6（上下文不延续提示）；澄清 M-11；决策 D-2 / D-5 / D-6 / D-9 / D-12；效果 E-4、E-8；边界 N-1 / N-3 / N-4 / N-5 / N-8
**迭代**: 0013-chat-archive

---

## 用户价值

想接着某段对话聊下去时，一键把它从归档里捞回来，落回主列表最上面，马上就能继续；同时明确知道它已经不记得之前说的话了。

## 验收标准

1. **单个激活的结果**：对某条归档对话执行激活后，它的归档标记被移除，从归档视图消失，并出现在 All 列表（D-2 / E-4）。
2. **立即恢复可继续对话**：激活后该对话可再次发送消息并收到回复（E-4 第三步）；激活后该对话不再处于只读状态。
3. **回到主列表顶部**：激活后该对话位于 All 列表顶部——其最近更新时间前移到当前时刻，符合"刚操作的排最前"（D-9 / M-11）。
4. **状态还原规则**：归档不改变对话状态，激活后保持原状态；**例外**——若激活时该对话处于**已关闭**状态，则恢复为**已完成**并清除其关闭时间（D-5 / A-5 / C-4）。判定：分别激活一条"归档前为已完成"与一条"归档前为已关闭"的对话——前者激活后仍为已完成；后者激活后变为已完成且不再带关闭时间。
5. **激活不恢复上下文**：激活只恢复"可继续对话"，**不**恢复归档时被释放的常驻上下文（N-4 / A-4 末句）。
6. **上下文不延续的显式提示**：激活后打开该对话时，界面在对话头部给出说明"此后不再记得此前内容"（该说明与既有上下文释放提示同级，D-12 / A-6）；该提示持续显示，直到该对话产生新的回答后自动消失 `[user_confirmed M-04]`（2026-09-11 用户确认取值）。判定：激活后打开该对话可见该说明；随后提问归档前让它记住的内容，回复不含该内容（E-8）。
7. **激活是单个操作**：一次激活只作用于被点击的那一条归档对话，不波及其他归档项（N-3）。
8. **可重开范围收窄不越界**：可重开（使已关闭对话恢复为可继续）仅通过"归档 → 激活"这条路径获得；**非归档状态下**已关闭的对话仍不可重开（N-5 / D-6）。判定：一条从未归档、直接被关闭的对话，尝试继续对话仍被拒绝。

## 边界（不包含）

- 不含归档动作本身（F01 / F02）与归档视图的展示与容量（F03 / F04）——本卡只规定"从归档回到可用"这条路径。
- 不做**批量激活**（N-3）——一次只激活一条归档对话。
- 不做**上下文还原**（N-4）——激活不恢复被释放的常驻上下文，并通过验收 6 的提示显式管理用户预期。
- 不做**通用"重开对话"能力**（N-5）——非归档状态下已关闭的对话仍不可重开；本卡只承载"归档 → 激活"这一收窄例外（验收 8）。
- 不做**对话删除**（N-1）。
- 不做**多用户 / 权限**（N-8）。
- 不含激活失败时的重试 / 回滚编排（activation 是单条操作，demand 未要求）。

## 架构维度（阶段 3 已填，2026-09-11；详见 `architecture.md` §4.2 / §5.3 / §6.4）

- **AR-13 激活的接口形态**：**新增** `POST /api/chats/<chat_id>/activate`（无请求体），与既有 `POST /api/chats/<id>/close` 逐字同构的单条动作子资源；**不引入通用 PATCH/PUT**（demand 明示"无通用 PATCH/PUT"）。处理链 = 预检 `getChat`（不存在 → 404；`archived_at === null` → **409**「chat 未归档，无法激活」，即 N-5 的 API 面表达）→ `db.activateChat(chatId)` → `publishState(chatId, state)`（复用既有 SSE `chat_state`，与 close 对称）→ `200 { chat_id, state }`。**不提供单条归档端点**（对称的另一半：产品无该触发点，故不做）。
- **AR-14 状态还原的落点**：**一条 `UPDATE` 完成三件事**（原子、无"标记已清但状态未还原"的中间态）：`UPDATE chats SET archived_at = NULL, state = CASE WHEN state = 'closed' THEN 'completed' ELSE state END, closed_at = CASE WHEN state = 'closed' THEN NULL ELSE closed_at END, updated_at = ? WHERE chat_id = ? AND archived_at IS NOT NULL`。SQLite 的 `UPDATE ... SET` 右值按**更新前行值**求值 ⇒ `CASE WHEN state = 'closed'` 判定的是**激活前**状态，逐字实现验收 4 / D-5 / A-5 后半（closed → completed 且清 `closed_at`；completed / failed 原样保留、`closed_at` 不动）。**收窄关系（N-5）**：`WHERE archived_at IS NOT NULL` 使未归档的 closed 对话**匹配不到任何行**（`changes = 0`），"可重开仅经归档 → 激活"成为结构性保证（验收 8）；`POST /close` 的语义与 `setWorking` / `setOutputState` 的 closed 哨兵逐字不变。**幂等**：重复激活第二次 `changes = 0`，`updated_at` 不再前移。
- **AR-15 置顶的实现位置**：**同一语句内的 `updated_at = ?`**（= 激活时刻）——命中主列表既有 `ORDER BY c.updated_at DESC, c.chat_id DESC` 即天然排到最前（验收 3 / D-9 / M-11）。**不新增排序字段（如 `pinned_at`）、不改排序规则、无第二次写入**。
- **AR-16 上下文不延续提示的承载**：**同级复用既有上下文释放提示**：同一样式 `.notice-bar`、同一渲染位（消息区顶部，即对话头部；在流式槽与运行时提示条之前）。**驱动源 = 服务端状态位 `chats.context_released`**（归档时置 1；`insertOutput` 置 0），前端 `renderChat()` 在 `chat.context_released === 1` 时渲染「激活后上下文已重置，本对话后续回复不再记得此前内容」⇒ **持续显示直到该对话产生新的回答**（`insertOutput` 置 0 → 该轮 `message(out)` 事件触发 `refreshChat()` 时自动消失，M-04 已确认口径）；跨刷新 / 重开页面仍在（落库而非前端内存）。既有 SSE `state.notices`（运行时事件、刷新不重现）链路**保持原样**，两者同级并存。**上下文确实不延续（验收 5 / N-4）零代码**：归档已 `release` 该 chat 的全部常驻上下文，激活不做任何恢复动作 ⇒ 下一轮新建 ACP 会话，模型看不到归档前内容；提示条只负责管理用户预期。
