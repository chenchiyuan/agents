# F04：归档列表容量（全部可达、加载更多）

**功能 ID**: F04
**来源**: `demand.md` A-7（归档列表容量）；澄清 M-9 / M-10；决策 D-7；效果 E-7；边界 N-6
**迭代**: 0013-chat-archive

---

## 用户价值

归档再多也找得到——不会出现"明明归档了、却翻不出来"这种对不上账的情况。

## 验收标准

1. **全部可达**：归档视图能够访问到**全部**已归档对话，不因主列表默认单页容量（50 条）而丢失（A-7 / E-7 / M-9）。判定：归档数量超过该默认容量后，归档视图仍可浏览到最后一条归档项。
2. **首屏覆盖较大范围**：进入归档视图时首屏即取到远超主列表默认单页容量的数量（demand 指向现有查询能力的上限；具体取值见「架构维度」AR-11）（A-7 / M-10）。判定：归档数量不超过首屏覆盖数时，首屏即列出全部归档项。
3. **超出部分可继续加载**：归档数量超过首屏覆盖数时，视图底部提供「加载更多」入口；每次加载出后续对话，可反复进行直至全部可见（A-7 / M-10）。判定：归档 60 条后，通过「加载更多」可浏览到第 60 条。
4. **加载后排序不乱**：继续加载出的部分与首屏保持同一排序规则（归档时间倒序、归档时间相同按对话标识倒序），不出现重复项或缺项（A-3 排序规则 + A-7）。
5. **末尾无死控件**：已经没有更多可加载的对话时，不再提供继续加载入口 `[user_confirmed M-03]`。

## 边界（不包含）

- 不含归档视图的入口、内容与排序规则本身（F03）——本卡只规定"全部已归档对话都可被访问到"。
- 不含主列表（All）自身的分页能力改造——demand A-7 只针对归档视图的容量，主列表沿用现状。
- 不含归档视图的搜索 / 过滤能力（N-6）——容量问题通过分页解决，不通过新增过滤维度解决。
- 不含归档数量的统计 / 总数展示（demand 未要求）。
- 不含查询能力单页上限值本身的重新定义（demand 指向沿用现有查询能力上限，见「架构维度」AR-11）。

## 架构维度（阶段 3 已填，2026-09-11；详见 `architecture.md` §5.2 / §6.2）

- **AR-11 每页条数与翻页参数形态**：**沿用既有分页协议，不新增后端形态**（demand M-10 / D-7 已锁）。首屏与续页同为 `limit=200`（既有 API 上限 `LIMIT_MAX`，前端常量 `ARCHIVE_PAGE_SIZE = 200`），续页为 `GET /api/chats?archived=1&limit=200&offset=<已持有条数>`（`offset` 递增，不引入游标 / 不新增参数 / 不新增端点）。排序由服务端保证 `archived_at DESC, chat_id DESC` ⇒ 续页与首屏同一排序、无重复无遗漏（验收 4）。首屏 `limit=200` 已覆盖 60+ 条场景（验收 1 / E-7）；分页用例另用 `limit:20` 强制走三轮续页，保证续页路径本身被断言（不被"200 足够大"掩盖）。
- **AR-12 归档视图的加载状态维护**：归档视图状态**独立承载**于 `state.archive = { chats, total, loading }`（与主列表 `state.chats` 互不污染）：**已加载范围** = `state.archive.chats.length`（`loadArchived({append:true})` 时 `offset` 取该值并把新页追加进 `chats`）；**是否还有更多** = `chats.length < total`（`total` 来自与列表同源的 `countChats`，见 AR-08）⇒ 「加载更多」按钮**只在有更多时渲染**，到达末尾不再留控件（验收 5 / M-03）；**与筛选条件的联动** = 切到 `archived` 时按缺省视图加载一次、切走不销毁（归档 / 激活动作后按需重载）；`loading` 标志防重复点击（请求在途时忽略再次触发）。
