### 4.4 事实 → 需求的直接后果（`实测` 支撑的推导，非产品判断）

1. **K11** ⇒ 用户指令的两个半边（默认 yolo / 上浮提问）若原样落在默认链路（`--mode rpc`），"提问"这一半**不会自动出现**（原生 `ask` 不注册）⇒ 提问必须由**宿主侧**承载（hub 注册的 host tool），而不是等待 omp 的 `ask`（A1）。
2. **K12 + K3** ⇒ 两条链路各自有承载且**都能落同一收件箱**：默认 rpc = host tool（`host_tool_call` → `host_tool_result`）；acp = 原生 elicitation 表单 ⇒ 需求按**协议能力位**表达提问通道，不要求逐字等价（A1 + M7）。
3. **K4** ⇒ 提问类答案（自由文本）**必须回传**，现载荷（只有 `optionId`）不足以承载；且既有"文本 → 追加一条 chat 输入"旁路必须对提问类停掉（A3/P6）。
4. **K5 + K3** ⇒ 信封无法承载多问题表单（多 property + 多选 + 每题自由文本）⇒ 信封扩展必做；"一问一条"是**用户已裁的可见形态**（A3/P5），且**不引入 `questions[]` 大信封**。
5. **K6** ⇒ R2 从"与 0021 冲突"缩小为"是否补偿 ACP 审批行丢失"；用户裁决 = **不补偿**（A5/P9），RPC 链路本就零审批行，属存量状态。
6. **K7 + K8** ⇒ Q1（随实例切档）与 Q3（可配 + 默认 yolo）在同一层摩擦：静态 profile 数据行表达不了"随 permission 变"⇒ 需要解析归属（A5/P3）；取值域按 A2 只落两档。
7. **K9** ⇒ deny 能力的物理前提是"该实例非 yolo"⇒ `deny ⇒ always-ask` 必须由**唯一汇聚点**保证（A5/P3/P12）。
8. **K10** ⇒ 「yolo = 恒零门」不成立 ⇒ `kind:'permission'` 通路与 always-ask 档**不可删、必须验收**（A5/Q3′）。

| **E4** | **作答回传（含自由文本，且不产生额外 chat 输入）**：在条目上作答后，提问方拿到答案本体（**含自由文本**），该轮继续（不再以 cancelled 收尾） | 输入一段自由文本答案 → 提问侧的答案文本与输入一致、该轮状态从等待变为继续；**同一动作在对话记录里零新增用户消息**（旁路已停） | `user_confirmed`（**A3/P6**）+ K4 |
| **E5** | **未作答保持阻塞**：未作答的条目持续停留（无上限），该轮保持等待——不自动选推荐项、不超时收尾、**也不出现代答拒绝** | 放着不管一段时间后再看：条目仍在、轮次未推进；且该轮**未以 cancelled 收尾** | `user_confirmed`（**A4/P13 + A3/P7**）+ F4/F9 + 0021 E4 |
| **E6** | **`always-ask` 档不退化且必须验收**：显式 `always-ask` 时，受门禁调用仍上浮为 `kind:'permission'` 条目，裁决后该轮继续或中止 | 以该档发起一次受门禁调用 → 栏内出现 `permission` 类条目并可裁决。**本项是 deny 能力的唯一验收载体，必须实际跑通（不是"仅保留代码路径"）** | `user_confirmed`（**A5/Q3′**）+ 0021 E1/E2 + K9 |
| **E7** | **默认档下的门仍可被处理**：门因用户策略（`tools.approval.<tool>: prompt`）偶发出现时，仍作为 `permission` 类条目被处理，不被丢弃 / 代答 | 构造一次被用户策略强制的门 → 栏内出现条目并可裁决 | `user_confirmed`（A3/P4 的 `permission` 分支）+ K10 |
| **E8** | **档位可配且默认正确**：未配置任何档位时默认 `yolo`；配置面只接受两个取值；`deny` 不被显式档位覆盖 | 读配置面（仅两值合法，其余被拒）+ 观察 argv / 行为面：默认无门；改配置后行为随之变；`--permission deny` 与显式 `--approval-mode yolo` 同时给出时仍自动拒绝 | `user_confirmed`（Q3 + **A2 + A5/P12**） |
| **E9** | **多问题一问一条**：agent 一次提多个问题时，栏内出现**多条独立条目**（每条一个问题），逐条作答后该轮继续（齐答后回包） | 让 agent 一次提 N 问（acp 单帧多问形态）→ 数栏内条目数（= N，非 1 条表单）+ 逐条作答 → 该轮继续 | `user_confirmed`（**A3/P5**）+ K3 |

## 6. 已知代价与风险

| # | 代价 / 风险 | 性质 |
|---|---|---|
| **R1** | **默认档下工具调用无人工确认、无审批审计**：ACP 链路的 `TOOL_APPROVED` / `TOOL_DENIED` 行随 `yolo` 消失（RPC 链路本就零，K6）；`TOOL_CALL` 面仍在 | **用户显式接受的代价**（A5/P9）；语义上"yolo 下不存在批准事件" |
| **R2** | **提问承载的定义权移到 hub 侧**：默认链路用 hub 自建的 host tool（A1），omp 原生 `ask` 在该链路不注册（K11）⇒ 提问工具的**命名 / 描述 / 参数 schema / 注册时机**由 hub 决定（形态 `[架构待填]`）；omp 原生 `ask` 的既有语义（`timeout` / `recommended` / 多选 / askDialog 形态）**不自动继承**（其中"超时自动选"已由 A4/P13 明确不做） | 形态性待定 + 适配成本（非需求缺口）；原「`rpc-ui` 副作用未知」风险**已随 A1 否决该路径而解除**（登记⑨） |
