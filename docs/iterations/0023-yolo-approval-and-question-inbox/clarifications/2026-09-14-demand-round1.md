### 2.4 事实 → 需求后果（`实测` 支撑的推导，非产品判断）

1. **K1 + K2** ⇒ 用户指令「默认 yolo + 只上浮 agent 主动提问」若原样落在当前默认链路（`--mode rpc`）上，**"提问"这一半物理上不存在**——不是"实现难"，是工具未注册。⇒ 本迭代必须先解决"默认链路是否具备提问能力"，这是一条**前置性需求缺口**（P1）。
2. **K3 + K4** ⇒ ACP 链路的提问面可行，但 oamp 现在一律 `decline`；而 `decline` 的后果（起点材料 + 0021 验证报告已实测）是 **ask 工具 abort ⇒ 该轮以 cancelled 结束**——即"agent 一提问就把整轮弄死"。⇒ 提问面必须**有回应通道**，不能保留代答拒绝（P7）。
3. **K4** ⇒ 提问类条目的答案**必须能回传**（RPC 回退路径的回答本质是 `editor` 自由文本；ACP 表单的 `__other` 亦然），而现载荷只有 `optionId`。⇒ 裁决回传载荷必须扩展（P6）。
4. **K5 + K3** ⇒ 7 字段信封无法承载 ACP 的多问题表单（多 property + 多选 + 每题自由文本）⇒ 信封必须扩展，且"一问一条 / 一表单一条"是需要**用户拍板**的可见形态（P4 / P5）。
5. **K6** ⇒ R2 的准确形态：RPC 链路**本来就**没有审批审计行（0022 之后默认链路已然如此）；yolo 后**新增消失的只有 ACP 链路的 `TOOL_APPROVED`/`TOOL_DENIED`**，而 ACP 的 `TOOL_CALL` 行不受影响。⇒ 审计面问题从"与 0021 冲突"缩小为"是否需要补偿 ACP 的审批行丢失"（P9）。
6. **K7 + K8** ⇒ Q1（deny ⇒ 自动切回 always-ask）与 Q3（可配 + 默认 yolo）在**同一层**发生摩擦：档位现状是 profile 数据的一部分，而"随实例的 permission 变"不可能由静态数据行表达 ⇒ 必须有一个解析归属（P3）。

## 5. 提案 P1~P13（每条：缺口 → 提案 + 理由 → 备选 → 不问清会怎样）

> 呈现格式遵循角色规范：**先给填法与依据，再请用户确认或纠偏**。全部提案在本轮标 `[model_inferred]`；用户裁决后由第 2 轮改写为 `user_confirmed`。

### P1（结构性 · 最高优先）默认链路是否需要具备 UI 的 RPC 会话

- **缺口**：默认链路 `--mode rpc` 下 `ask` 工具不注册（K1），「上浮 agent 主动提问」在默认配置下不可达。
- **提案（草稿更新）**：**默认 RPC 链路的会话形态改为"具备 UI 的 RPC 会话"**（候选 = `--mode rpc-ui`），使 `ask` 在默认链路可用；提问帧面 = `select`（问题文本 + 选项）/ `editor`（自由文本）（K2）。
- **理由**：`rpc-ui` 是 omp **既有的** RPC 形态——同协议、同传输、同 argv 位置，仅多注入 UI 上下文（K2），不引入新协议、不违反 0022 的默认 `rpc` 选择；否则用户指令"只上浮 agent 主动提问"在默认配置下只剩一半。
- **备选读法**：① 保持 `--mode rpc`，提问上浮**仅 ACP 链路可用**（默认链路无此能力）；② 默认协议改为 `acp`（与 0022 A2 的"内置默认 rpc"相撞，**不推荐**）。
- **不问清会怎样**：选① ⇒ 用户在默认配置下永远看不到 agent 的提问，"只上浮提问"的验收只能在切换协议后才成立；选② ⇒ 推翻上一迭代的默认链路裁决，且思考增量等 rpc 独有面回退。
- **附带登记（后果，非结论）**：`rpc-ui` 置 `PI_NO_PTY=1`（K2）⇒ bash 工具的 PTY 形态可能变化，须列为阶段 3 首步实测项（与 0022 M7 同体例）。
- **来源**：`[model_inferred]`（依据为 `实测` K1/K2；用户 Q2 只裁了"上浮哪些帧"，未裁"默认链路是否具备该能力"）。

### P2 档位取值域：本迭代落几档、`tier` 是否在域内

- **缺口**：Q3 明写"具体取值域待阶段 2/3 定"，而取值域决定验证矩阵与配置校验面。
- **提案**：取值域 = **{`always-ask`, `yolo`}**，默认 `yolo`；**不落中间档**；若将来要落，取值名必须与 omp 域一致（**`write`**），不得用 `tier`。
- **理由**：① 用户指令的方向是"默认全放行 + 只在提问时上浮"，中间档的方向是"按工具档位部分上浮工具"，与指令不同；② 中间档把验证矩阵从 2 档增到 3 档，而本迭代真正要保的能力只有两个（默认放行 / 可拒绝）；③ `tier` 是 omp 域里不存在的名字（K7），落它就必须加一层名字翻译，而现状是"档位值直通 argv"（K8）。
- **备选读法**：三档全落（`always-ask | write | yolo`）——把 `write` 也作为可配项，代价是"只问 exec 档"的行为需要独立验收。
- **不问清会怎样**：阶段 2 的配置卡无法冻结（校验取值域 / CLI 参数域 / 文档面都悬空）。
- **来源**：`[model_inferred]`（K7 + 用户指令方向）。

### P3 yolo × deny 的实现归属

- **缺口**：Q1 裁"deny ⇒ 自动切回 always-ask"，但档位现状是静态 profile 数据（K8），归属未定。
- **提案**：**需求层只钉行为**（默认 `yolo`；实例显式 `--permission deny` ⇒ 该实例档位为 `always-ask`，且仍不上浮、走既有自动拒绝三步），**解析归属标 `[架构待填]`**；同时补一条**需求级硬约束**：档位解析必须存在**唯一汇聚点**，"deny ⇒ always-ask"不得依赖每个调用点各自记得覆写。
- **理由**：K8 显示两条路径都物理可行（profile 数据 / `buildArgv` 的 `approval` 覆写位），是设计选择不是需求分歧；但"漏一个调用点 ⇒ deny 静默失效"是需求级后果（用户要的是能力保留，不是"某些路径保留"），所以汇聚点必须是需求约束。
- **备选读法**：明确指定走调用方覆写面（即 L2 在起会话前统一算档位）；或明确指定由 L1 提供 `permission → approval` 的解析函数。
- **不问清会怎样**：阶段 3 可能把解析散在两条链路各自实现，deny 的保证变得依赖调用点完备性。
- **来源**：`[model_inferred]`（K8 + K9 + Q1 行为裁决）。

### P4 上浮面的信封扩展（类别 + 提问形状）

- **缺口**：信封 7 字段无类别字段，且 `options: string[]` 承载不了"多选 / 自由文本 / 无选项"的提问形状（K3 / K5）。
- **提案**：信封增加 **`kind`**（`'question'` / `'permission'`，Q2 已裁）+ 提问类必须能表达：**问题文本**、**选项集合（含是否多选）**、**是否允许/需要自由文本**、**允许无选项的纯自由文本提问**；`permission` 类保持 0021 形状（选项 = 请求方给出的集合）。
- **理由**：K3 的 ACP 形状（`q{i}` + `q{i}__other`、`oneOf` / `array`）与 K2 的 RPC 回退路径（`select` + `editor`）都要求这三样信息才可无损呈现；RPC 的 `input` / ACP 的 `type:'string'` 无 `enum` 形态即"纯自由文本提问"。
- **备选读法**：提问类只支持"带选项 + 可选自由文本"，纯自由文本提问不做（登记为边界）。
- **不问清会怎样**：阶段 2 无法写出提问卡；实现期会把形状差异压进渲染层（最坏情况 = 自由文本答案无处可填）。
- **来源**：`[model_inferred]`（K2/K3 `实测` + Q2 的 `kind` 裁决）。

### P5 多问题表单的栏内形态（一问一条 vs 一表单一条）

- **缺口**：ACP 的 `ask` 可一次提多问（单帧多 property，K3），RPC 的回退路径天然逐问（K2）；栏内呈现与裁决面必须二选一。
- **提案（推荐）**：**一问一条** —— 每个问题一条独立条目，沿用现裁决面（`option_id` + `text` 即可表达"选一个选项 + 自由文本"）；ACP 单帧多问时由 hub 侧逐问登记、**齐答后一次性回包**（组内暂存的最小状态）。
- **理由**：① 复用现裁决面与在途表语义（一条 = 一次裁决），不引入新的裁决载荷形状；② 与 RPC 的天然逐问形态一致；③ 栏内"每条可独立处理"与 0021 的交互体例一致。
- **备选读法**：一条条目承载整表单（信封加 `questions[]`，裁决面加 `answers[]`）——与 ACP 帧一一对应、回答原子性更强，但要改裁决载荷与栏内控件成"表单"，且 RPC 侧仍要合并逐问。
- **不问清会怎样**：信封与裁决载荷契约无法冻结（P4 的扩展形状取决于此），阶段 2 的 F 卡无法拆。
- **来源**：`[model_inferred]`（K2/K3 + K5）。

### P6 回答必须回传（含自由文本），且不再走"追加一条 chat 输入"

- **缺口**：现裁决只回传 `{optionId}`，自由文本被当成一条用户 chat 输入追加（K4）⇒ 提问类靠文本作答时**答案丢失 + 产生一条无关消息**。
- **提案**：`kind:'question'` 条目的裁决回传载荷**必须携带答案本体**（选中的选项 + 自由文本），并**停止**对提问类条目复用"文本 → 追加 chat 输入"的路径；`kind:'permission'` 条目维持既有口径（文本仍是拒绝理由/补充说明）。
- **理由**：RPC 回退路径的回答本质就是 `editor` 自由文本，ACP 的 `__other` 亦然（K2/K3）；不扩展就永远只有"选项"能作为答案。
- **备选读法**：提问类只允许选选项（自由文本仅作附加说明），RPC 的 `editor` 帧则一律按取消处理——但这会使 `ask` 的"Other (type your own)"选项失效。
- **不问清会怎样**：实现期会退回"文本当消息"的既有路径，提问答不上，且污染对话记录。
- **来源**：`[model_inferred]`（K4 `实测` + K2/K3）。

### P7 提问请求不得被代答拒绝（decline 会终止整轮）

- **缺口**：现状对非 `Approve|Deny` 的 elicitation 一律 `decline`（起点材料 F4）；起点材料与 0021 验证报告均实测到：`ask` 被 `decline` 后工具 abort、**该轮以 cancelled 结束**。
- **提案**：hub 侧对提问类请求**不得**以 `decline`/`{cancelled:true}` 代答；一律登记为待答条目并**保持阻塞**（沿用 0021 的挂起语义）。
- **理由**：代答拒绝的用户可见后果不是"问题没被回答"，而是"agent 突然中止了这一轮"——比不回答更坏；且提问类请求正是本迭代要上浮的对象。
- **备选读法**：保留"无人在场时可拒绝"的兜底（与 0021 N6「不做自动裁决」直接冲突，**不推荐**）。
- **不问清会怎样**：默认行为会变成"agent 一提问就整轮失败"。
- **来源**：`[model_inferred]`（F4 + 0021 验证报告实测 + 0021 M3/N6 的既有裁决）。

### P8 0021 / 0022 验收口径的更替清单（显式登记被取代与保留的条款）

- **缺口**：0021 的机制建立在"每次受门禁调用恰一条确认项"上，0022 W4/E4 沿用该口径；默认 yolo 后该口径在默认档下不再被触发，但档位切回 `always-ask` 时仍需成立（R3）。
- **提案（草稿更新：显式登记，不由读者自行推断）**：

| 处置 | 条款 | 依据 |
|---|---|---|
| **取代**（触发条件改变，机制不删） | 0021 `F02` 验收 1「`allow` 档的受门禁调用上浮」（触发条件从 `permission=allow` 改为"档位 = `always-ask`"）；0021 `M1` / `R3` 的档位语义句；0022 `W4` / `E4`「一次受门禁调用恰一条确认项」在默认档下的适用性 | Q1（默认 yolo ⇒ 门不存在）+ Q2（上浮面改为提问）+ K9 |
| **保留（不退化）** | 0021 `W1` 第三栏 / `W2` 栏内交互 / `W4` 通知服务 / `W5` 三事件 / `W6` 在途可见性 / `F05` 挂起语义（默认阻塞、无上限、无自动裁决）/ `N1` 服务边界 / `N2` 不做历史台账 / `N4` 不做通知分级 / `N5` 不含 `call_completed` / `N7` 不做其它入口载体；0021 `F12` 不改上游协议 | 用户指令未触及这些面；沿用既有 `user_confirmed` 裁决 |
| **条件化（仅 `kind:'permission'` 成立）** | 0021 `F03` 的"选项为主、文本为辅"在 `permission` 类保持；提问类还需支持"无选项纯文本 / 多选 / 多问题" | K3/K5 + P4/P5/P6 |
| **改写（口径分化）** | 「自由文本不参与应答」（`web.js` 既有口径）→ 按 `kind` 分化：`permission` 类维持原文，`question` 类必须回传文本 | K4 + P6 |
| **保留但适用范围收窄** | 「受门禁调用恰一行审计」（0021 `F05` 架构落定 T-16）→ 仅 `always-ask` / `deny` 档成立；`yolo` 档零审批行（RPC 链路本就零） | K6 + P9 |

- **理由**：两个口径并存是最坏的中间态（R3 点名的风险）；显式登记可在阶段 2 直接照表拆卡，不留解释空间。
- **备选读法**：不列清单，靠阶段 2 自行发现冲突（**不推荐**——0021 的 12 张卡已落地，冲突会以"验收标准互相打架"的形式暴露，成本远高）。
- **来源**：`[model_inferred]`（条款对照，依据 = 0021/0022 原文 + Q1/Q2 + K9）。

### P9 审计面：是否补偿 `yolo` 后消失的审批审计行（R2）

- **缺口**：`yolo` 默认后工具调用无人工确认，ACP 链路的 `TOOL_APPROVED` / `TOOL_DENIED` 行随之消失（K9/K6）。
- **提案（推荐）**：**不新增工具审计面**（记为已知代价）：yolo 语义下不存在"批准"这一事件，硬造一行"自动批准"是伪事件；ACP 的 `TOOL_CALL`（每次工具调用一行，与门无关，K6）仍保留，作为工具调用面的既有可观测点。
- **理由**：① 与用户指令的最小边界一致（用户只要"少确认"，没要"新审计"）；② RPC 链路**本来就**零审批行（K6）⇒ "审计面随 yolo 消失"在默认链路是**存量状态**，不是本迭代引入的新损失；③ `TOOL_CALL` 已覆盖"哪些工具被调用了"这一主要可观测诉求。
- **备选读法**：把 RPC 的 `tool_execution_*` 事件映射为 `TOOL_CALL` 行（对齐 ACP 面）——代价是新增一个本迭代未被要求的能力面；或保留 `permission` 类条目的审计语义不变（仅 `always-ask` 档有行）。
- **不问清会怎样**：若用户其实依赖审批审计（合规 / 复盘），本迭代结束后将无任何"工具被自动放行"的痕迹可查。
- **来源**：`[model_inferred]`（K6/K9 `实测` + 0021 F05 既有落定）。

### P10 能力位 `approvalGate` 在默认 yolo 下的取值

- **缺口**：0022 `M6` / `A3-P3` 规定"缺能力必须显式降级"；yolo 默认后 `approvalGate` 是否随档位变化未被裁决（起点材料 §四.6）。
- **提案（推荐）**：**能力位不随档位变** —— 能力位描述"该协议是否有工具门这一机制"（RPC 有、ACP 有），**档位声明**单独表达"本次生效形态"（profile 的 `approval` 字段即该声明）。
- **理由**：把"配置状态"混进"协议能力"，会让 0022 `W8` D-1「指定即生效」判据失去单一含义（可能被读成"yolo 档下 rpc 不生效"）。
- **备选读法**：能力位随生效档位求值（yolo ⇒ `approvalGate=false`，属"显式降级"声明）——与"缺能力显式声明"的字面更贴近，但语义边界更难把持。
- **不问清会怎样**：阶段 3 可能同时改能力位与档位声明，两处表达同一件事，互相矛盾时无从判定。
- **来源**：`[model_inferred]`（0022 A3/P3 原文 + K8）。

### P11 通知事件类型是否新增提问类

- **缺口**：0021 `W5` 的事件集合是**封闭 3 类**（`chat_completed` / `chat_failed` / `confirmation_required`）；提问类是否算 `confirmation_required`，或需新类型。
- **提案**：**不新增事件类型**；提问类条目沿用 `confirmation_required`（语义仍成立："出现需用户裁决/回应的事项"）。
- **理由**：最小边界（用户未提出通知分级需求）；新增类型会同时改通知服务、前端文案表与既有文档面。
- **备选读法**：新增 `question_required`（区分提问与工具门）——若用户认为"agent 问我问题"与"agent 要动我的文件"需要不同的注意力等级。
- **不问清会怎样**：阶段 2 会在 F07 卡上产生一次小型口径分叉。
- **来源**：`[model_inferred]`（0021 W5 原文 + Q2 的 `kind` 裁决）。

### P12 `--permission` 与 `--approval-mode` 的优先级

- **缺口**：两者都影响档位，同时给出时谁赢未定。
- **提案**：`permission === 'deny'` ⇒ 档位强制 `always-ask`（Q1），**与显式 `--approval-mode` 冲突时以 deny 为准**；`permission === 'allow'` ⇒ 档位取配置值（默认 `yolo`）。
- **理由**：deny 是更强的安全约束（"不许自动放行任何受门禁调用"）；若被 `--approval-mode yolo` 覆盖，deny 会静默失效（= Q1 要保住的能力被自己关掉）。
- **备选读法**：显式 `--approval-mode` 优先，deny 在 yolo 下退化为"无门可拒"（等于 deny 失效，**不推荐**）。
- **不问清会怎样**：`deny` 与配置项的组合行为无定义，验收时无法判真假。
- **来源**：`[model_inferred]`（Q1 + K7/K9）。

### P13 提问类条目的阻塞语义

- **缺口**：0021 `M3`/`E4`/`N6` 的"默认阻塞且无上限、无自动裁决、无超时退化"是为工具门定的，提问类是否同样适用未明说（起点材料 §四.3）。
- **提案**：提问类**同样适用**：未作答则保持阻塞（无上限）、不自动选推荐项、不超时收尾；`ask.timeout` 保持默认 `0`（不设超时），`recommended` 仅作展示。
- **理由**：替用户回答问题等于伪造用户意图，比工具门的自动放行更不可接受；`ask.timeout=0` 是 omp 默认（起点材料 F9），不设即符合"无超时退化"。
- **备选读法**：提问类带超时（超时后按 `recommended` 自动选）——与 0021 `N6` 直接冲突，**不推荐**。
- **来源**：`[model_inferred]`（0021 M3/E4/N6 + 起点材料 F9）。

## 8. 参考视角（**不进入 `demand.md` 结论段**，仅供讨论）

> 规范要求：参考视角只用于把方案雏形想清楚，**不得**当作 `user_confirmed` 写入结论；以下内容标 `[参考视角]`。

- **[参考视角 A]** 若选 `rpc-ui`，要注意它不是"另一个协议"，而是"同一协议的 UI 变体"——协议层（L2）的抽象接口不需变，变的只是 profile 的 `modeArgs` 与"该链路是否具备宿主 UI 能力"这一声明。若将来 claude/codex 也走类似变体，能力位里可能需要一个 `hostUI` 之类的位。**这只是一个方向提示，不是架构结论。**
- **[参考视角 B]** "一问一条 + 齐答后回包"在 ACP 侧需要一个组内暂存状态；如果将来 agent 频繁一次提 4~5 问，栏内会一次涌出多条条目，人的体感是"现在有 5 件事要我做"。若更在意"一次决策原子性"，则选第二条路。**取舍取决于用户对人机交互体感的偏好，不由我代决。**
- **[参考视角 C]** `ask` 的 `ToolAbortError` 语义意味着"取消提问 = 中止轮次"：如果将来要做"用户忽略提问并让 agent 继续"，那不是本迭代的问题，而是需要上游把"取消"与"拒绝回答"分开。**登记为后续方向，不进边界。**
