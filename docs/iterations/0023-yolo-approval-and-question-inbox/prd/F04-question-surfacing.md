# F04：提问上浮（agent 主动提问登记进收件箱，不再被自动取消）

**功能 ID**: F04
**来源**: `demand.md` 第二段 §2 **W3**（`user_confirmed`：U-3 + Q2 + A1 + A3-P7）；§4 **M6**（登记待答、不代答）；§5 **E3**（可见性面）、**E5**（放弃兜底的对照面）；§3 **N6** / **N7** / **N12**；事实 **F2**（RPC 非门交互自动回 `{cancelled:true}`）/ **F4**（ACP 非 `Approve|Deny` 的 elicitation 一律 `decline`）

**产品对象（引用 `demand.md` 只读实测，非本阶段决策）**: F2 / F4（两条链路现状都把提问当场取消）；0021 既有交付物 = 待确认收件箱（第三栏）+ 既有通知事件集合

## 用户价值

agent 说不清要什么的时候，终于是它在等我——而不是它自己猜一个、或者整轮直接死掉。

## 验收标准

1. **提问类请求登记进收件箱**（W3 / E3）：agent 发起提问时，控制台**待确认栏出现该条目**（**无需刷新页面**），条目内容等于提问内容。
   *判定*：构造一次提问 → 盯控制台看条目是否出现、内容是否等于提问内容。 〔判定方式逐字取自 E3 的裸判据〕
2. **不再被自动取消 / 拒绝**（W3 / N12 / M6）：提问请求**不再**被自动回 `{cancelled:true}` / `decline`；该轮**未在无人介入下被中止**。
   *判定*：同一构造动作 → 条目出现 + 该轮**不以 cancelled 收尾**（对照现状：提问必被取消）。
3. **通知沿用既有事件类型**（**N6** / A4-P11）：提问条目产生时的通知沿用既有事件类型（`confirmation_required`），**不新增事件类型**。
   *判定*：提问期间通知事件类型 ∈ 既有集合（`chat_completed` / `chat_failed` / `confirmation_required`）→ 无新类型。 〔措辞例外：既有事件类型名〕
4. **上浮不随档位变**（W3 / A4-P10）：提问类上浮与档位无关——**两个档位下提问均上浮**。
   *判定*：分别以 `yolo` 与 `always-ask` 各触发一次提问 → 两次都出现条目。
5. **人的注意力只花在有歧义的地方**（U-3 / U-4）：上浮的判据是"方案执行有歧义"（= agent 主动提问），不是"某种工具 / 某种帧"。
   *判定*：读上浮来源 → 指向 agent 的主动提问；不含"因工具类型而上浮"的通路（工具门是另一类条目 → F10）。

## 边界（不包含）

- 不含提问的**形状**（问题文本 / 选项 / 多选 / 自由文本 → F05）、**多问题**（→ F06）、**作答回传**（→ F07）、**未作答语义**（→ F08）、**两条链路的承载**（→ F09）。
- 不含 `kind:'permission'` 类条目（工具门 → F10）。
- **不含通知分级 / 免打扰 / 其它入口载体**（**N7** 封死，沿用 0021 既有裁决）；不含通知服务本身的改造（0021 既有）。
- 不含一次性 `omp -p` 路径与 `!` shell 路径（**N5**：无反向请求通道，维持现状、不上浮）。
- 不含**代答拒绝 / 自动作答**的任何形式（**N12** → F08 验收 3）。
- 不含信箱的信封字段名与形状承载（→ T-02）、不含两条链路的提问工具形态（→ T-05）。
