## 用户价值

收紧档位下我仍然能逐次拍板放行——"少打扰"不是把这道门整个拆掉。

## 验收标准

1. **`always-ask` 档不退化，且必须实际跑通**（W6 / **A5-Q3′** / E6）：该档下受门禁调用仍上浮为 `kind:'permission'` 条目，裁决后该轮继续或中止。
   *判定*：以该档发起一次受门禁调用 → **栏内出现 `permission` 类条目并可裁决**。 **本项是 `deny` 能力的唯一验收载体，必须实际跑通（不是"仅保留代码路径"）**——不通过即本迭代失败。
2. **`yolo` 档下的偶发门仍可处理**（W6 / E7 / K10）：门因用户策略（如把某工具的审批策略设为强制询问）或 provider 安全校验**偶发出现**时，仍作为 `permission` 类条目被处理——**不被丢弃、不被代答**。
   *判定*：构造一次被用户策略强制的门 → 栏内出现条目并可裁决。
3. **`permission` 类维持既有形状与口径**（**登记⑧ ③条件化** / 0021 `F03` 验收 1~4 / **N11**）：选项为主、文本为辅、点选即裁决、可一并提交、裁决后消失；选项集合 = **请求方给出的集合**（不新增、不删减、不替换）。
   *判定*：以 0021 `F03` 验收 1~4 同法复核一遍（点选即裁决 / 可附文本 / 一并提交 / 裁决后条目消失）。
4. **"一次受门禁调用恰一条条目"的适用面 = 档位 `always-ask`**（**登记⑧ ①取代**；0022 `W4` / `E4` 的口径）：在该档下成立——**不重不欠**，裁决后条目消失。
   *判定*：数栏内条目数（= 1）+ 裁决后条目消失 + 该轮据此继续或中止。 〔触发条件从 0021 的「`permission = allow` 档」改为「档位 = `always-ask`」；**机制不删**〕
5. **`deny` 实例的门不入本卡**（与 F03 的分界）：`deny` 实例下门产生后由 hub 自动拒绝、**不上浮**，收件箱零新增条目——本卡只覆盖"门给人裁决"这一支。
   *判定*：分别以 `always-ask` 与 `deny` 各发起一次受门禁调用 → 前者栏内出现条目，后者栏内**零条目**。
