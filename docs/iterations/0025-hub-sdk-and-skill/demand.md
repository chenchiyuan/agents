### 4.2 逻辑闭环：why 能否推出 what

**Why**：agent / skill 与 hub 之间**没有稳定通道**，每次协作都临场拼装通信代码。这带来三重代价——重复劳动、易错、**无法被 skill 固化**（不能固化的能力必然每次重写，这是根因）。

逐条对照用户确认的 what：

| 做什么 | 从 Why 能否推出 | 结论 |
|---|---|---|
| 封装 Web 开放接口面 | **能**。0021 记录的全部痛点都发生在这一层（通道 = `POST /api/calls`；截断靠 transcript 重建；工作目录纪律靠人工核验） | 闭环成立 |
| 封装 Router UDS 的 8 个方法 | **需要补理由**——痛点里未直接出现 UDS 需求。补：它是**非 oamp 启动的 agent** 注册进拓扑的唯一入口，也是 `oamp cluster status` 逐角色对齐的数据源；缺它则"稳定通道"只覆盖"消费 hub"，不覆盖"成为 hub 的节点" | 闭环成立（理由已登记） |
| 封装 oamp CLI 运维命令 | **需要划界**——`cluster up/down` 与 `agent start` 属**进程生命周期**。划界：封装的是**既有**命令、**零语义变更**；**不得把启停能力搬进 hub 的 HTTP 面**（那才是 0015 N1/N2 禁止的事） | 闭环成立（边界已写成 N-4） |
| CLI + 同源库 | **能**。B-5 的"跨宿主一致"要求同一能力既能在 shell 里被调用，也能被 Node 侧直接消费 | 闭环成立 |
| `hub` skill | **能**。根因即"无法被 skill 固化"——skill 正是固化的载体 | 闭环成立 |

**方案雏形能否达成已确认的效果**：C-1 选定严格 1:1 后，仍需复核 E-1（回放 0021 五类操作且零手写 HTTP/JSON）是否可达。结论——**可达，但 E-1 的口径须按 C-1 收窄**：截断恢复从"SDK 代做"变为"消费方用两个子命令组合"，因此 E-1 的判据是"**不出现手写 HTTP 请求与响应解析**"，不是"不出现任何组合代码"。此收窄已写入 §4.4 与第二段 E-1。

### 4.3 边界完整性

- 用户**明说**的边界：三层都封装（A-2）；不改角色文件（A-5）；严格 1:1（C-1）；skill 与 SDK 同包（D-1）。
- 其余边界（N-1 ~ N-8）为推导所得，逐条给"为什么这次不做"。
- **主动的边界收敛判断**：新增五处"看起来相关但不做"的分支——改 hub 自身（N-1）、跨机/鉴权（N-2）、agent 生命周期能力（N-3/N-4 的划界面）、高层编排命令（N-5）、下游分发（N-6）。去掉它们，最小闭环仍成立。

## 3. 大概怎么做（产品级形态）

- **包结构**（W1）：`oamp/` 内新增 `sdk/`（实现）+ bin 入口；`package.json` 的 `bin` 增加一项；沿用零依赖（`dependencies: {}`）与 `engines.node >= 22`。
- **子命令结构**（W2/W3）：按 `API.md` 的资源分组同构；每个子命令对应一个端点 / UDS 方法 / 既有 CLI 命令，参数与字段名尽量与 `API.md` 一致。**具体拼写与层级组织留阶段 2 / 3**（见 §7 O-1）。
- **调用契约**（W4）：stdout 恒为 JSON（除 `--human`）；错误走 stderr + 固定退出码；`--wait` 控制阻塞上限；订阅类走前台 NDJSON 流。
- **契约自检**（W5）：`doctor` 类子命令，对着运行中的 hub 校验接口面与 `API.md` 的一致性；**校验判据留阶段 3**（见 §4.6-B3 的坑）。
- **skill**（W6/W7）：与 SDK 同包落在 `oamp/` 内，三段式；入口定位用"仓库根绝对路径"模板；**"其他 skill 如何引用它"的机制留阶段 3**（见 §4.6-B4）。
- **`[架构待填]`**：子命令拼写与命名空间组织、`doctor` 的校验判据与只读端点范围、三层封装在库 API 上的表达（函数签名 / 命名空间）、NDJSON 流的字段形态、skill 的具体路径与跨 skill 引用机制、测试组织。

## 4. 达到什么效果（裸判定：不问作者也能判真假）

| # | 效果 | 裸判定说明 |
|---|---|---|
| **E1** | **回放 0021 的五类操作全程不出现手写 HTTP**：用 SDK 完成 ①派发角色任务 ②取终态 ③取转录（含 `truncated` 场景）④订阅事件 ⑤盘点 agent 状态；**消费方侧不出现任何手写 HTTP 请求与响应解析**（组合 SDK 子命令、拼接 JSON 不违反此条） | 逐条执行并把用到的命令列成清单；清单里出现 `curl` / socket 手写 / 自建 HTTP 客户端即不通过 |

## 5. 为什么这么做

- **为什么必须做 SDK**（Why 的直接回应）：根因不是"接口不通"，是"**没有可固化的形态**"。0021 的一手记录证明接口是通的——但每次都要临场写 curl、每次都要重新发现 `truncated` 要重建、每次都要人工核验工作目录纪律。**能被固化的能力才会被复用**；SDK + skill 是把"临场拼装"变成"可被引用"的唯一路径。
- **为什么以 `API.md` 为真源而不是让 SDK 成为真源**（A-4）：`API.md` 是 0015 交付并经独立验证的接口合同，且有既有的验证方式（E7 的"照抄文档示例调通"）。让 SDK 成为真源等于搬家，会把 0015 的验证面整体重写；薄封装 + 契约自检则以最小代价守住一致性。
- **为什么落点在 `oamp/` 内**（B-1/D-1）：SDK 封装的就是 oamp 的接口，同仓可让契约自检直接对着 `API.md` 与源码；零依赖与 Node 版本约束天然继承；`bin/oamp.js` 已有先例，不需要新造包管理形态。skill 与 SDK 同包则让"SDK + skill"成为一个内聚单元。
- **为什么严格 1:1 而非吸收语义**（C-1，用户改判）：语义吸收会让 SDK 成为"有观点的中间层"——一旦它对 `truncated`、分页、续查有了自己的处理，接口的演进就必须同时改两处。1:1 让 SDK 的失效面等于接口的失效面。**代价已显式记录**：0021 的截断痛点**从代码层搬到 skill 层**（由 W6 的"典型序列"承接）。
- **为什么 CLI 无状态**（B-3）：跨调用状态会引入缓存失效、并发、stale 三类新问题，而这三类问题与"通道稳定"目标正相反。
- **为什么本迭代不动 `roles/**`**（A-5）：改角色文件等于改工作流协议面，会把 0024 刚定稿的派发机制卷进来；且 skill 只有在自身稳定之后才有资格被角色依赖。**先把工具做对，再谈接入**。
