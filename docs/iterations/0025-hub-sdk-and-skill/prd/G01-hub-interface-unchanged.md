## 用户价值

这次**只在接入侧加东西**——服务端的合同一个字没动，既有的消费方（控制台、其他客户端）不会因为我装了 SDK 就受影响。

## 验收标准

1. **接口清单零变更**（N1）：`API.md` §3 的接口清单**条目数与路径逐条不变**（不新增、不删除、不重命名、不改路径）。
   *判定*：比对改动前后的清单 → 21 行逐条一致（路径与顺序均不变）。
2. **方法面零变更**（N1）：Router 的 8 个方法名与语义不变。
   *判定*：逐条比对 8 个方法 → 名称与参数 / 返回语义未变。
3. **既有接口行为不变**（N1）：对同一请求，改动前后的**响应形态一致**（既有控制台与既有客户端的行为不受影响）。
   *判定*：对若干既有接口各发一次相同请求 → 响应体字段与取值一致；既有测试面**仍然全绿**（不因本迭代的改动而需要修改既有断言）。
4. **服务边界声明不变**（N1 / A-4）：仅本机回环、零鉴权、HTTP 面不提供 agent 启停路径——这些既有声明与实现保持一致（不是"文档没改但实现改了"）。
   *判定*：读声明并实测：接口清单中仍无启停路径；连接面仍只在本机。
5. **真源关系成立**（A-4 / W5）：`API.md` 仍是唯一规范真源——SDK 侧不出现与之并存的第二份接口定义（对接口的校验以文档为基准，见 [F11](F11-doctor-contract-selfcheck.md)）。
   *判定*：改动 `API.md` → SDK 的契约自检结论随之变化（不是"两份定义各自为政"）。

## 边界（不包含）

- 不含 SDK 侧新增的接入能力（→ [F01](F01-sdk-package-and-dual-consumption.md)~[F14](F14-layered-command-structure.md)）——本卡只保证**服务端不变**。
- 不含 Router / Web 的**内部实现**约束（只约束对外合同：路径、方法、语义、响应形态）。
- 不含新增端点 / 新参数的评估——**N1** 直接封死。
- 不含既有 Web 控制台前端面的改动要求——本迭代不涉及。

## 架构落定（阶段 3）

> 架构维度结论；**产品维度（用户价值 / 验收标准 / 边界）逐字未改动**。详见 `../architecture.md` §5 / §4。

- **架构维度**：**无待填项**（保证项：约束是对既有合同的保持）。
- **落定（保证项的架构承载）**：本迭代**不新增任何路由**、不改 `src/**` 任一既有模块 ⇒ `API.md` / `llms.txt` / `web.js` 路由登记三面 **零 diff**；两把既有漂移锁（`test/api-routes.test.js:278` 的逐字节快照、`:303` 的路径级双向覆盖）**零影响**（`../architecture.md` §4.3 Z-1~Z-3 / §8 C6）。
- **真源关系（验收 5）**：`doctor`（F11）只**读** `API.md`、只调既有 21 条接口与既有 8 方法；SDK 侧不存第二份接口定义或字段 schema。唯一对外变化 = 包的第二个可执行入口（`bin.hub`），**不触及服务端合同**。
