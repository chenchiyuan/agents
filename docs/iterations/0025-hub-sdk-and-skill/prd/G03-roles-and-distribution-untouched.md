# G03 · 既有协议面与分发面零改动 〔保证项〕

**功能 ID**: G03
**来源**: `demand.md` 第二段 §1 **W8**（本迭代零改动 `roles/**`；角色接入留独立迭代）、§2 **N6**（不做下游业务项目的分发，不进分发脚本的分发面）；§4.1 **A-5**；§4.5 A-5 的理由（"先把工具做对，再谈接入"）
**迭代**: 0025-hub-sdk-and-skill
**卡型**: **保证项**——不引入新能力，只承载"本仓既有其他消费面 / 分发面没被这次改动碰到"这一可独立核对的保证

---

## 用户价值

工作流的角色定义**一个字没动**，其他项目拿到的分发面也没变——这次交付只加了新东西，没有改旧东西。

## 验收标准

1. **`roles/**` 零改动**（W8 / A-5）：本迭代的改动集合中**不含** `roles/` 下的任何文件（不修改、不新增、不删除）。
   *判定*：比对改动范围 → `roles/**` 下 diff 为空；本迭代产物只落在 SDK / skill 与迭代文档目录内。
2. **不进分发脚本的分发面**（N6）：既有的分发脚本未被修改，SDK 与 skill **不进入**其分发内容。
   *判定*：比对分发脚本 → 零改动；其分发内容仍只含既有条目。
3. **角色接入留待独立迭代**（A-5 / §5 的"为什么"）：本迭代**不要求**任何角色 / 工作流协议引用新 skill 或其 SDK；角色文件与工作流规范对新工具保持零引用。
   *判定*：通读改动后的角色定义与规范 → 无对 SDK / skill 的引用（若出现即越界）。
4. **不改 `.claude/skills/**`**（D-1 / C-E）：skill 的落点是 `oamp/` 内（与 SDK 同包），不落在 `.claude/skills/` 下，也不新增指向它的转发 / 副本（副本会与"`API.md` 单一真源"的防分叉精神相悖）。
   *判定*：比对改动范围 → `.claude/skills/**` 下 diff 为空。

## 边界（不包含）

- 不含"其他 skill 如何引用它"的机制（**D-1 登记为 `[架构待填]`**，→ T-06）——本卡只核"本迭代不去改那些面"。
- 不含工作流规范文件（→ 同样零改动；见验收 1、3 的核对范围）。
- 不含把 SDK / skill 装进分发脚本的**将来**动作（N6 封死本迭代的"做"）。
- 不含对既有分发脚本行为的评价或改进——未要求即不做。

## 架构落定（阶段 3）

> 架构维度结论；**产品维度（用户价值 / 验收标准 / 边界）逐字未改动**。详见 `../architecture.md` §5 / §4。

- **架构维度**：**无待填项**（保证项：约束是"不改既定面"）。
- **落定（保证项的架构承载）**：本迭代改动面 = `oamp/{bin,sdk,skill,test}` 的**新增** + `package.json` **加一行** `bin.hub` ⇒ `roles/**`、`tools/**`（分发脚本）、`.claude/skills/**` **零 diff、零副本、零转发**（`../architecture.md` §4.3 Z-5）。
- **引用机制不落实体**：F12/F13 的"跨 skill 引用机制"（T-06）只定义**写法**（`<项目根>/oamp/skill/hub.md` 的路径模板）——不新增转发文件、不新增副本、不改任何既有 skill 的正文（G03 验收 4）。
- **角色接入留待独立迭代（验收 3）**：本迭代不要求任何角色 / 工作流协议引用新 skill 或 SDK；SDK 的入口定位不依赖 `roles/**`（模板中的"项目根"由调用方提供）。
