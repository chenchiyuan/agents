# F05 · 默认 JSON 输出与 `--human` 切换

**功能 ID**: F05
**来源**: `demand.md` 第二段 §1 **W4**（`user_confirmed`：B-2 输出约定）；§4.6-A（用户雏形"默认 JSON + `--human` 切换"）；§4 **E4**（跨宿主一致的一半：JSON 结构）
**迭代**: 0025-hub-sdk-and-skill

---

## 用户价值

管道里拿到的是**可直接解析的 JSON**（脚本、agent、另一段程序都能吃）；人要看的时候，加一个开关就变成人话，不破坏前一种用法。

## 验收标准

1. **默认输出 = JSON，且只走 stdout**（W4 / B-2）：不加任何开关时，成功调用的 stdout **是一个可被直接解析的 JSON 文档**；诊断 / 人类信息不混进 stdout。
   *判定*：执行任一成功的只读命令 → `stdout` 单独可被 JSON 解析；*跨宿主*：同一命令在 ①shell ②Node `import` ③另一个 agent（经 shell 调用）三处的 JSON 结构一致。〔判定方式取自 `demand.md` E4 的裸判据〕
2. **`--human` 切换为人类可读**（W4 / B-2）：加上该开关后输出变为**给人看的形态**（不再是需要解析才能读懂的一条 JSON）。
   *判定*：同一命令分别不加 / 加该开关各执行一次 → 两次输出形态明显不同；不加开关时仍是 JSON。
3. **开关不改变结果本身**（W4 / C-1）：切换形态不改变被查询 / 被执行的**结果内容**，只改变呈现。
   *判定*：同一命令的两种输出 → 其承载的事实一致（如清单条数、实例名、状态逐项一致）。
4. **失败时同样不污染 stdout**（W4 / B-2）：错误信息走 stderr，stdout 里不出现半截 JSON 或人话混合体。
   *判定*：执行一条必然失败的命令 → 正常错误信息出现在 stderr；stdout 为空或不含可解析残片。

## 边界（不包含）

- 不含退出码语义（→ [F07](F07-exit-code-semantics.md)）；不含订阅类的流形态（→ [F06](F06-subscription-ndjson-stream.md)）。
- 不含 `--human` 的**具体排版形态**（列宽 / 颜色 / 表格样式）→ `[架构待填]` T-09。
- 不含子命令拼写与命名空间（→ T-01）、不含库 API 表达（→ T-03）。
- 不含"机器可读"的额外格式（YAML / CSV 等）——**未要求即不做**（`demand.md` 只约定 JSON 与人类可读两态）。

## 架构落定（阶段 3）

> 架构维度结论；**产品维度（用户价值 / 验收标准 / 边界）逐字未改动**。详见 `../architecture.md` §5 / §4。

- **T-09 · `--human` 的呈现形态**（§5.3）：`--human` = 对齐文本 —— 列表类 → **表头行 + 数据行**，列宽 = `max(表头, 各单元格)`、两空格分隔（逐字沿用既有 `src/status.js:renderTable` / `src/task.js:renderList` 的手法）；对象类 → `键: 值` 逐行、键 `padEnd(12)`（沿用既有 `src/task.js:renderTask` 的手法）；订阅帧 → 一行 `事件名 key=value …`。
- **不做**：颜色 / ANSI、时间戳本地化、字段语义解释 —— 这些都需要"第二份字段知识"，会与 `API.md` 分叉（L2-7 / F11 验收 5 / G01 验收 5）。
- **默认输出（验收 1/4）**：单结果条目 = 一个可 `JSON.parse` 的 JSON 文档走 stdout（层 A = 服务端响应体原样；层 B = JSON-RPC `result` 原样）；失败 = stderr 单行 JSON `{"code":…,"error":…,"exit_code":…}`，stdout 保持干净。
- **开关不改事实（验收 3）**：两面共用**同一个结果对象**，`--human` 只换渲染器（§5.3 末段）。
