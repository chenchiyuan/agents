## 用户价值

**不看源码也能判断某条命令走哪一层**，并且同一个东西只有一种走法——不会出现"这个 agent 列表是从 HTTP 拿的还是从 UDS 拿的"这种要试了才知道的情况。

## 验收标准

1. **分层可判定**（W2 / O-1 倾向）：把子命令清单交给**没读过源码的人**看 → 他能逐条说出每条命令走的是哪一层（Web 接口面 / Router 方法 / 既有 CLI 命令），判断依据来自命令结构本身。
   *判定*：找一位未参与实现的人，只给子命令清单（不给源码）逐条判断层次 → 判断正确率 100%（对照实现者可陈述的层次归属）。
2. **跨层无歧义**（W2 / W3 / §4.6-B2）：同一资源同时经两层可达时，**依据命令结构即可判定走哪一层**，不需要先试一次。
   *判定*：找出"同一资源在两层的两组命令"各处一例 → 仅从名字 / 结构即可判断层次归属；不出现两条命令名面相同而落层不同的情况。
3. **清单中不含编排命令**（W3 / N5）：子命令清单里**不存在**跨端点 / 跨方法的编排命令（如"一次完成派发并等结果""按工作流自动推进"这类带业务语义的命令）——多步闭环以 skill 文本的序列表达（[F12](F12-hub-skill-three-sections.md) 验收 4）。
   *判定*：逐条读子命令清单 → 每条都对应单一端点 / 方法 / 既有命令；出现需要组合多步才能完成语义的命令即不通过。
4. **编号与命名不靠解释**（O-1 倾向）：清单中两层之间不存在**同名同形**的条目；存在近义命名时，其层次归属可由结构唯一确定。
   *判定*：对清单做一次重名 / 近名检查 → 无同名同形条目；近名条目各自的层次归属无歧义。

## 边界（不包含）

- 不含**具体拼写与层级组织**——本卡只要求"可判定 + 无歧义"，拼写形态全部留 `[架构待填]` T-01（O-1 的承接项）。
- 不含各层的覆盖面（→ [F02](F02-web-api-surface-coverage.md) / [F03](F03-router-uds-method-coverage.md) / [F04](F04-oamp-cli-command-coverage.md)）。
- 不含带业务语义的高层编排命令的定义形态（**N5** 直接封死"做"这一项；本卡验收 3 只核"没做"）。
- 不含命令的帮助文本、补全、别名等外围体验——未要求即不做。

## 架构落定（阶段 3）

> 架构维度结论；**产品维度（用户价值 / 验收标准 / 边界）逐字未改动**。详见 `../architecture.md` §5 / §4。

- **T-01 · 本卡判定的对象本体**（§5.1）：三层用**唯一前缀**区分 —— `api`（Web 21 条）/ `uds`（Router 8 个方法）/ `cli`（既有命令 11 个叶子），共 **40 条入口**。
- **验收 1（分层可判定）**：层归属 = 命令的**第一个 token**，无需读源码即可判定；flag 名由 `API.md` 字段名机械推导（`_` → `-`），路径参数走位置参数。
- **验收 2 / 4（跨层无歧义、无同名同形）**：跨层同资源的三处判定样例（实例拓扑 / 任务清单 / 单任务终态）见 §5.1 末尾 —— 三处命令名面互不相同（`api agents` ｜ `uds router.status` ｜ `cli status` 等），层次归属唯一确定。
- **验收 3（无编排命令）**：40 条入口**逐条对应单一端点 / 单一方法 / 单一条既有命令**；多步闭环只以 **skill 文本的序列**表达（F12 验收 4/5），SDK 侧零跨端点组合逻辑（W3 / N5）。
- **验收 1 的判定面（P-4，待主 agent 拍板）**：分层判定面 = **三层封装的 40 条覆盖入口**（`api` / `uds` / `cli`）；`hub doctor` 是**第四个顶层入口**（自检面），不对应三层中的任何一层，故不参与本卡验收 1 的"逐条判层"（F11 的 `doctor` 仍逐项给结果与依据）。若要求 `doctor` 也须归入某一层，只能挂到 `api` 层下 —— 但那会让 F02 验收 1 的 21 行双向对照多出一个非端点条目。详见 `../architecture.md` §3.3 P-4 / §5.1。
