## 用户价值

长任务等多久由**我**定；等超了得到的是"超时"这一类明确结果（可被脚本识别），而不是一个看不出原因的失败。

## 验收标准

1. **等待上限由调用方显式给出**（W4 / C-2）：存在一个显式的等待上限参数（形如 `--wait <ms>`）；给出它即按其等待，未给出时行为可预期且不无限等待。
   *判定*：对同一次长任务分别给出①较小上限 ②较大上限 → 观察 ①先返回、②后返回；不给出时命令不会永久挂起。
2. **等待内拿到终态即返回终态**（W4 / E1 的 ② 类操作）：任务在上限内完成时，命令直接给出该次调用的终态结果（不是"仍在进行中"）。
   *判定*：对一次会在上限内完成的任务 → 返回含终态的结果；消费方记录用于取终态的命令清单里**不出现 `curl` / socket 手写**。
3. **超时是单独一类可区分错误**（W4 / C-2）：等待超上限时，输出**明确表达"超时"这一事实**（不是堆栈、不是与业务失败同形的模糊失败），且**不与其它失败混淆**。
   *判定*：对一次超过上限仍未完成的任务 → 输出里能读出"等待超时"这一事实；错误标识 / 文案形态见 `[架构待填]` T-08。
4. **超时后可继续处置，不损失任务**（W4 / B-3 / C-D）：超时只结束**本次等待**——该次调用仍可随后用其调用标识取到终态或过程记录（本地不留状态，重新问一次即可）。
   *判定*：任务超时返回后，用该次调用标识在新的调用中取终态 → 任务完成后能取到终态（不因超时而丢失）。
5. **超时与另外两类失败可区分**（W4 / B-2）：超时、业务失败、连接失败三者，消费方仅凭退出码 + 输出即可区分（超时的退出码归属见 `[架构待填]` T-08，本卡只要求"可区分且固定"）。
   *判定*：分别构造 ①超时 ②业务失败 ③连接失败 → 三者的可观察结果互不相同且各自稳定。

## 边界（不包含）

- 不含**跨调用的续查 / 本地缓存**——**N9** → [F09](F09-stateless-cli.md)；超时后的继续处置是"重新调用"，不是"本地接着等"。
- 不含**自动重试 / 自动重新派发**——N3 / C-D（那是新能力，不是封装问题）。
- 不含超时错误在退出码与字段上的**具体落点** → `[架构待填]` T-08。
- 不含把等待上限**写死为某个默认数值**——上限由调用方给出（B-3 / C-2）；默认值形态（若有）留 T-08。
- 不含订阅类命令的时限（前台流由 `--wait` 之外的方式管理）→ [F06](F06-subscription-ndjson-stream.md)。

## 架构落定（阶段 3）

> 架构维度结论；**产品维度（用户价值 / 验收标准 / 边界）逐字未改动**。详见 `../architecture.md` §5 / §4。

- **T-08 · 超时这一类错误的可区分表达形态**（§5.4）：
  - **`--wait <ms>` 只被 `api calls create` 接受**（其余条目给出该选项 = 用法错误 `2`，避免"给了却不生效"）；**缺省值 `1800000` ms**（30 分钟，逐字沿用既有 `DEFAULT_OMP_TIMEOUT_MS`）⇒ "未给出时不无限等待"（验收 1）成立。
  - **超时归类**：`WAIT_TIMEOUT` → 退出码 **`1`**（业务失败类），与上游业务错误（`NOT_FOUND` 等）**同码不同 `code`** ⇒ "仅凭退出码 + 输出即可区分"（验收 5）；与连接失败（`3`）、用法错误（`2`）码本身即不同。
  - **实现**：到达上限即中止**本地**等待（`req.destroy()`），stderr 输出 `{"code":"WAIT_TIMEOUT","error":"等待超时（<ms>ms）：调用仍在进行","exit_code":1}`；**调用不被终止**（`API.md` §5.13：客户端断连不终止调用）。
- **验收 4 的口径（P-1，待主 agent 拍板）**：`mode: "block"` 的响应体是**唯一**携带 `call_id` 的载体，而它在终态才到达 ⇒ 超时后 SDK 手里没有标识；"不丢任务、可随后取回"落在 **background 形态**（`calls create` 缺省**立即返回 `calls[].call_id`**，随后 `api calls get <id>` / `api calls transcript <id>` 取回）。**不**为 block 路径做 roster 反查（那属跨端点语义，撞 W3 / F02 验收 2）。详见 `../architecture.md` §3.3 P-1 / §9.1。
- **未给上限时的默认行为**：可阻塞条目恒有上限（默认 1800000 ms）；非可阻塞条目走 5000 ms 响应上限（归 `3`）—— 两条上限语义不同、文案不同、不会混淆。
