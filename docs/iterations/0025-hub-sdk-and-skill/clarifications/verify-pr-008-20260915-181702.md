## 2. 关键独立复核（简报指定的 7 项重点）

### ② 8 个 UDS 方法各自真实执行且与 `RpcPeer` 直连逐键一致 —— 成立

**E-01（实测 TAP 输出，现算生成，非手抄）**：

```
uds agent.register	↔	RpcPeer 直连 result 键集 [instance_id, last_heartbeat, lease_follows_interval, lease_timeout_ms, session_id, state] ⇄ 直连 [instance_id, last_heartbeat, lease_follows_interval, lease_timeout_ms, session_id, state]
uds agent.heartbeat	↔	RpcPeer 直连 result 无 result（notify 语义）
uds message.send	↔	RpcPeer 直连 result 键集 [accepted, message_id, status] ⇄ 直连 [accepted, message_id, status]
uds message.ack	↔	RpcPeer 直连 result 键集 [acked, status] ⇄ 直连 [acked, status]
uds router.status	↔	RpcPeer 直连 result 键集 [nodes] ⇄ 直连 [nodes]
uds router.task_get	↔	RpcPeer 直连 result 键集 [task] ⇄ 直连 [task]
uds router.task_list	↔	RpcPeer 直连 result 键集 [tasks] ⇄ 直连 [tasks]
uds agent.deregister	↔	RpcPeer 直连 result 键集 [removed] ⇄ 直连 [removed]
```

直连 oracle 与 SDK 会话是**两条独立连接/两个独立实例**，对照在运行期现算（非手抄常量表）。变异 M1（包信封）、M14（接错方法）均检出 ⇒ 对照具判别力。

### ③ `message.deliver` 的传输层应答与「无自动 ack」是否真被观测 —— 成立

- **传输层应答**：变异 M8（删去 `respond.ok({received:true,message_id})`）→ 4 条用例失败（含 T2/T3/边界样本），说明该应答被真实观测（缺失会使 Router 侧 `deliverTo` 超时 → 发送方拿不到 `delivered`）。
- **无自动 ack**：显式 `ack` 得 `{acked:true,status:'accepted'}` ⇒ 未受理前 pending 仍在；二次 `ack` 得 `UNKNOWN_MESSAGE` ⇒ 前一次受理唯一。**变异 M2b（Router 在投递成功后自动 `resolvePendingAck`）被 5 条用例检出** ⇒ 该判据对"自动受理"确有判别力。
- **配套确证（SDK 侧）**：变异 M2a（SDK 在 deliver 分支自动发 `message.ack`，带合法 `status`）被 4 条用例检出。

### ④ 库面闭环是否真的走通（register→heartbeat→send→ack→deregister→close）—— 成立

`AGENT_REGISTERED` → `HEARTBEAT` → `MESSAGE_DELIVERED` → `MESSAGE_ACKED … status=accepted` → `AGENT_DEREGISTERED` 五类事件行齐备且**行序单调**断言通过；闭环中 `status()` 为 `online`、注销后不含该实例；`close()` 后 200ms 零新增事件行。变异 M5（`deregister` 变本地 no-op）使该用例失败 ⇒ 闭环不是"看起来通了"。

### ⑤ 2000ms 上限的「注入桩 + 上限值观测 + 清零点」三面对照 —— 成立，且不依赖真实等待

| 面 | 观测 | 独立变异确证 |

| 注入桩 | `net.connect` 被替换后记录 `opts.timeout === 2000`；以 `HUB_UNREACHABLE/3` 拒绝；文案含 `connect timeout (>2000ms)`；`destroy()` 被调用；用时 < 2000ms | **M6**（2000→5000）被检出（唯一失败项即该用例） |

### ⑥ 「零重试 / 零自动重连」的观测面是否可信 —— 成立
