## 5. 关键发现（#13 / F10 的完整证据链）

**现象**：`--wait` 的声明上限（缺省 `1800000` ms）对 `--mode block` 调用**不可达**；上限 > 5000ms 时由 `sdk/http.js` 的响应头 5000ms 上限先行终止，并按「连接失败 `3` / `REQUEST_TIMEOUT`」归类，而不是「等待超时 `1` / `WAIT_TIMEOUT`」。

**复现（自建记录型 HTTP 服务端）**

| 场景 | 观测 |
|---|---|
| `api calls create --wait 1000`，服务端 6000ms 后响应 | `1042ms` → `1` + `WAIT_TIMEOUT` + `等待超时（1000ms）：调用仍在进行`；服务端请求数 **1**（无重试） |
| 同上，**不给** `--wait` | `5041ms` → `3` + `REQUEST_TIMEOUT`（`等待响应超时（5000ms；…）`） |
| `--wait 8000`，服务端 6000ms 后响应（上限内应成功） | `5042ms` → `3` + `REQUEST_TIMEOUT` |
| `--wait 8000`，服务端 3000ms 后响应 | `3044ms` → `0` + 终态体（上限内成功分支正常） |

**复现（真实 hub + 真实 agent）**

| 场景 | 观测 |
|---|---|
| `api calls create --chat-id <已有> --agent dev --mode block --wait 60000 --task "Write a 250-word description…"` | `5048ms` → `3` + `{"code":"REQUEST_TIMEOUT","error":"等待响应超时（5000ms；127.0.0.1:47022）","exit_code":3}`，stdout 空 |
| 对照：`--mode background`（同 agent、同 chat） | `51ms` → `0` + `{"calls":[{"call_id":"task-…","state":"submitted"}]}`；随后 `calls get` → `working` → `completed`（`text:"OK"`、`duration_ms:2993`）；`calls transcript` → `0` |

**归因**：5000ms 上限位于 `oamp/sdk/http.js`（pr-001 已合并冻结模块，本 PR 契约明令零 diff）。在本 PR 的可写面（3 个新文件）内，唯一替代方案是自建第二套 HTTP 客户端 —— 直接违反 §2.3「复用而非重建」与 N-4，因此**本 PR 无法单方满足 #13**；这属阶段 3/4 的跨 PR 上限语义未对齐。
