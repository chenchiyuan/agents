### 三、澄清过程中确认的边界与否决路径

- **否决路径 ①：为每个调用打补丁**（不引入客户端会话）⇒ 否决理由：症状会在每个新调用形态上重演。
- **否决路径 ②：持久事件日志 / 事件回放**⇒ 否决理由：D-10 已确认实时信息可丢；回放带来的复杂度不换任何用户价值。
- **否决路径 ③：约定"任务期间不重启"** ⇒ 否决理由：这是**回避**而非韧性（D-12 用户明确纠正）。
- **否决路径 ④：新增 `cancelled` 终态** ⇒ 否决理由：D-5 选择不触碰信封键集与既有判据。
- **否决路径 ⑤：扩 harness 导出会话身份作为前置** ⇒ 否决理由：D-2 选择最小实现 + 协议留扩展点（不把本迭代卡在外部改造上）。

## 第二段 · 需求结论

### 做什么

1. **把"客户端会话"做成一等入口**：身份（幂等、无租约）+ 实时事件订阅（含纳管 agent 的实时状态投影）+ 终态结果取件（离线/晚订阅也不丢结果）。
2. **把"等"做对**：调用终态即关流（补上那根 0 调用点的线）、晚订阅补发终态、提供一次调用即返回的等待入口，并统一"等待退出条件必须是终态"的语义。
3. **把控制面与恢复做成契约 + 可观测**：取消 / 队列可见 / 自派发告警 / `reconnecting` 状态 / 恢复判据（`health`）/ 进展字段（`last_event_at`、`idle_ms`）。

### 不做什么（每条附"为什么这次不做"）

1. **不做事件回放与持久事件日志** —— 因 D-10：实时信息允许丢；**续接由快照与结果取件承担**，回放换不到用户价值。
2. **不做鉴权体系、不做跨机/多 hub 联邦** —— 本机边界既有约定不变；引进鉴权会把"最小身份"复杂化，与 D-2 的最小实现相悖。
3. **不新增第三个终态**（取消复用 `failed + error`）—— 因 D-5：避免牵动 §3.19 信封键集与 F11 等价性判据。
4. **不把"hub 记忆"当作恢复依据** —— 因 D-14：重启后以**产物与 DB** 为准（hub 登记易失是**明文**，不是隐患）。
5. **不扩 harness / 不改 omp 侧** —— 因 D-2：身份来源留成可替换的一层，本迭代不依赖外部改造。
6. **不重做既有推送面**（4 条 SSE 的事件语义保持）—— 仅做加法与补线，避免控制台行为回归。

### 大概怎么做（用户已确认的机制；技术选型留给架构阶段）

- **身份**：`POST/GET /api/principals`（幂等 upsert、无租约无心跳）+ 层 A 的 `calls` 相关条目开 `--as`。
- **实时**：`GET /api/events?principal=&kinds=&agents=`（SSE，**明示 best-effort**）+ Router 侧 `events.subscribe`（第二形态）；agent 投影增 `busy / current_call_id / queued / since`。
- **结果取件**：`GET /api/inbox` + `POST /api/inbox/ack`；`POST /api/calls` 增 `requester`；**不传 `requester` 时行为与今天逐字一致**。
- **续接**：`epoch` 代次 + `409 STALE_EPOCH`；客户端流程固定为 **epoch 校验 → 一轮快照 → 继续订阅/调度**。
- **等待**：终态关流（复用 `closeKey`）+ 晚订阅补发 + `GET /api/calls/wait`；条文"等待退出条件必须是终态，超时≠失败"。
- **控制面**：`POST /api/calls/<id>/cancel`、`agents` 增队列字段、自派发告警（`warnings[]`）。
- **恢复**：`GET /api/health`（router / web / agents 三项判据）+ `agents` 增 `reconnecting` 状态。
- **服务化**：以上全部按 `{summary, params, response, errors, docLink}` 元数据体例声明 ⇒ 自动进入 `/api/docs` 与 `llms.txt`。

### 达到什么效果（每条均可裸判定）

1. 在一个**未参与开发的人**看来：用 `hub` 派发一个长任务后，**不做任何轮询、不写任何监控脚本**，也能在结果产生时**自动拿到**（在线靠订阅、离线靠取件）。
2. 派发出的调用**在终态当刻**，其订阅流结束（不再挂在 `stream call` 上等超时）。
3. 客户端**断开任意时长后拉起**，**两次快照查询**（`agents` + `calls`）即可准确回答**四问**：哪些实例在线/重连中、哪些调用在跑、各自进行到哪、有没有停滞；**第五问「有无未取结果」由取件面回答**（收窄依据 D-15：原表述「两次查询答五问」与事实不符）。
4. 对**执行者自身实例**派发会**当场出现告警**（可判定：响应含 `warnings[]`）。
5. 任一调用的终态结果，在客户端**未取件时不消失**（保留窗内），且在**调用登记存活期内** `calls get` 始终可查；**重启后以产物与 DB 为准**（收窄依据 D-15 + D-14：原表述「永远可查」与内存易失的事实冲突）。
6. `hub doctor`（或新增 `health`）能回答"**router 起没起 / web 起没起 / 几个 agent 在线（含重连中）**"。
7. 以上所有端点都能在 `GET /api/docs` 与 `llms.txt` 中**被发现**（无需读源码）。

### 为什么

- **根因**（0028 复盘结论）：hub 现有两种投递语义——"投递给活连接"与"按 id 查询"，**缺第三种"投递给一个可寻址的身份"**；而主 agent 这类调用方**结构上不是活连接**。于是"任务完成了但主 agent 不知道"成为必然，watchdog 成为被迫的补丁。
- **不做会怎样**：每个新调用形态都会重演同一症状（0028 已发生：7 个等待作业全部靠超时交付；一次 24 分钟死锁无人知晓）。
- **为什么现在做**：复盘已把根因定位到代码位置、修复路径已收敛、且**大部分地基已存在**（Router 双向消息、确认链路的挂起-通知范式、agent 退避重连、`closeKey` 原语）——增量小、收益贯穿所有后续迭代。
- **为什么按这个顺序**：D-9 选择**完整闭环**（身份→实时→取件→续接→等待→控制面→恢复），因为其中任一环单独做都无法达成 D-13 的体感目标。

### 执行方式约束（本次迭代专用，过程要求）

1. **派发一律经 `hub`**（`oamp/skill/hub.md`），不使用其它派发通道；本迭代的**过程本身**就是 hub 体感的实测场。
2. **全程度量 D-13**：每次派发记录"是否需要人/agent 额外盯守、结果如何到手、耗时"，作为体感证据。
3. **hub 使用中的任何摩擦**（文档缺口、语义不清、能力未被 skill 暴露等）**当场搭置**到 `deferred-demand-changes.md`，不回退、不暂停（按 workflow-pb 既有机制）。
4. 迭代产物落在工作区 `docs/iterations/0029-hub-client-session-and-duplex/`；阶段推进按 `roles/workflow-pb/workflow-pb.md`。
