# F18 · 过程证据与摩擦搭置（**过程契约卡**）

**来源**：demand.md §执行方式约束 1 / 2 / 3；决策 D-13（"像使用 subagent 一样使用 hub"的体感目标）

> **本卡不引入任何新的产品能力**：它把 demand 已确认的**本迭代过程要求**变成可核查的证据面（体例先例：0028 的 F12「执行方式差距记录」）。

## 用户价值

下一迭代与用户**不用回头采访**就知道这次 hub 用起来到底顺不顺——每次派发是否要人盯、结果是自动到手的还是查出来的、哪里卡了手，全部留痕。

## 验收标准

1. **派发通道单一**：本迭代**全部角色派发**经 hub（既有 `hub` 入口及其子命令面），不出现"宿主本地 subagent 派发"充当角色协作手段 [约束 1]。
2. **每次派发一行可核对记录**：派发台账逐条含 角色（节点）/ 用途 / `call_id` / 终态，并额外含 **D-13 三问**：① 是否需要人 / agent 额外盯守 ② 结果如何到手（自动送达 / 主动查询 / 阻塞等待）③ 耗时 [约束 2 + D-13 度量]。
3. **体感目标的度量可读**：从记录中能直接读出"多少次派发结果自动到手 / 多少次靠主动查询 / 多少次靠阻塞等待 / 有无需要额外盯守的情形" —— 这是 D-13 的裸判定载体 [D-13 / 效果#1 的过程侧证据]。
4. **摩擦当场搭置**：hub 使用中出现的摩擦（文档缺口 / 语义不清 / 能力未被 skill 暴露等）逐条写入迭代目录的搭置记录，**不回退、不暂停** [约束 3]；已知应被登记的摩擦至少包括"既有 skill 未教等待原语"这一条 [事实 F-8]。
5. **搭置条目三要素齐**：每条搭置含"问题 / 为什么判定为需求层面问题 / 本迭代如何处理"（按工作流既有格式）。

## 边界（不包含）

- 不把摩擦搭置当作阻塞理由（不因搭置而暂停、回退或改需求）。
- **不做 hub 体感的产品改造**：例如改写既有 skill 文档不在本迭代范围内（demand 的"做什么"无此条目 —— 见报告疑问）。
- 不新增"过程度量工具"：记录落在既有派发台账与既有搭置文件里，不另建文件格式。
- 不做派发耗时 / 盯守时长的自动采集（人工记录即可）。
- 不把本卡当作"派发必须成功"的约束（失败与阻塞同样要留痕）。

## 架构维度

无待填项（本卡是对既有记录面与既有文件的使用要求，不涉及技术选型 / 数据模型 / 接口设计）。
