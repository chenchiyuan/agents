# F13 · 调用的取消

**来源**：demand.md 做什么#3（"取消"）；§大概怎么做（控制面：`POST /api/calls/<id>/cancel`，转 `state=failed, error="cancelled"`）；决策 D-5；不做什么#3；复盘 G-19（现状无取消入口，互锁只能靠外部杀进程）

## 用户价值

**失控的调用可以被收回来**——不必等它自己跑完、也不必有人去外部杀进程；发起方即可解除。

## 验收标准

1. **取消可生效**：调用方对一次尚未终态的调用发起取消 ⇒ 该调用进入**既有终态** `failed`，且 `error` 给出机器可读的取消原因（`"cancelled"` 语义）[D-5]。
2. **不新增终态**：`state` 的封闭词表仍为既有四值，取消**不引入第五个取值** [不做什么#3；G01 验收 2]。
3. **当刻可判定**：取消成功后，调用方按 `calls get` 看到的状态**即为终态**（不出现"取消已受理但长时间仍显示在跑"）。
4. **幂等**：对同一调用的重复取消不报错、不产生第二个终态、不改变已确定的终态与原因。
5. **不覆盖已定终态**：对已终态调用取消 ⇒ 原 `state` / `error` / `exit_code` **保持不变**，并以可判定的方式告知"已终态"。
6. **不存在的调用有明确结论**：对不存在的 id 取消 ⇒ 给出明确的"不存在"结论（不静默成功）。
7. **与关流协同**：被取消的调用，其订阅流在取消生效当刻结束（与 F09 同一时点语义）。
8. **客户端断开不影响控制面**：一个调用方断开期间，另一调用方的取消与派发**照常生效**（hub 与其 agent 不受客户端连接影响）[§大概怎么做 P-E.2]。

## 边界（不包含）

- **不保证执行侧"立即停止"**：本卡要求的是"取消当刻状态面到达终态且以取消原因表达"，执行侧进程的终止强度见 MI-7 [本卡不把它纳入判据]。
- 不做批量取消 / 不做"取消我的全部调用"。
- 不做取消的权限控制（与 D-2 的最小实现一致）。
- 不新增终态的展示语义（既有渲染按既有 `failed` 呈现，不回归）。
- 不做取消后的自动重派 / 自动清理现场。

## 架构维度

**已回填 · A-10（完整契约见 `architecture.md` §4 A-10）**：通路 = `POST /api/calls/<call_id>/cancel` → **新增 Router 方法 `router.task_cancel`** → Router 在**既有唯一终态写点** `registry.finishTask` 置 `state='failed'` + `result.error='cancelled'`（对已终态幂等拒写）→ web 经**既有唯一终态发布点**发布终态帧 + 关流（与 F09 同一时点语义）+ 释放等待句柄 + 落一条对话 `out`（`error='cancelled'`）+ 推 `chat_state`（避免对话停在 `working`）。**"避免两个终态源"** = 不在 web 侧做状态覆盖、让 Router 任务表真的变终态；**竞态与幂等** = Router 单线程 + `finishTask` 拒写 + web 侧既有 `call.published` / `entry.landed` 闸门 ⇒ 重复取消不报错、不改已定终态（响应 `{call_id, cancelled:false, state, error}`，原值原样）；不存在 ⇒ 404。**执行侧不强停**（不纳入判据、也不实现；被取消调用后续回报在状态面被忽略）。

## model_inferred

- **MI-7**（验收 1 与边界）：demand 只定义"取消复用 `failed` + `error`"，未定义取消的**执行强度**（标记取消并尽快终止 / 保证执行侧立即停止）。本卡按"以状态面的当刻终态为判据、不把执行侧立即停止纳入判据"落卡，等主 agent 确认。
