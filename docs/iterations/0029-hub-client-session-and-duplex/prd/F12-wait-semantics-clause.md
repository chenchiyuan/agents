# F12 · 等待语义条文（终态退出 / 超时≠失败）

**来源**：demand.md 做什么#2（"统一'等待退出条件必须是终态'的语义"）；§大概怎么做（等待条文）；决策 D-13；事实 F-6（既有 `--mode block` 声明"不设人为上限"与客户端 30 分钟预算并存 ⇒ 语义未统一）；复盘原则候选 A

## 用户价值

接入方**读得到一条不会变的口径**：等，是以"结论产生"为出口，不是以"时间到了"为出口——不必自己去猜哪种等待是可靠的。

## 验收标准

1. **条文存在且可被接入方读到**：协议 / 接口文档面存在明文条文，至少覆盖 ① 等待的退出条件**必须**是终态 ② 超时**只表示放弃等待**，不改变任务状态、不产生失败结论 ③ **禁止**把"轮询 + 超时"当作等待的实现 [落点见 A-09]。
2. **条文与行为一致（反向验证）**：对一个仍在跑的调用等待到超时 ⇒ 返回后该调用的 `calls get` 仍为非终态（`submitted` / `working`）、`error` 为空、`exit_code` 未变 ⇒ "超时没有产生失败结论"成立。
3. **三条等待路径口径一致**：订阅式等待（F09 / F10）与一次调用式等待（F11）的退出时刻**都不由超时值决定**（对照：调大 / 调小超时，退出时刻不变）。
4. **调用方可判定地放弃**：超时放弃与全部终态两种情形有**可判定的区分方式**（不得靠"没拿到结果"反推）[MI-6，与 F11 验收 6 同一条款的两面]。
5. **既有"人为上限"类表述被口径统一**：既有的客户端等待预算（如 30 分钟）在条文下**不被表述为等待的语义上限**（它是放弃等待的预算，不是失败判据）[事实 F-6]。

## 边界（不包含）

- **不规定具体超时默认值**（属既有配置 / 架构面）。
- **不重写既有等待原语的实现**：条文统一的是语义，既有命令的行为按 G01 保持。
- 不做自动重试 / 自动续等 / 失败重派。
- 不把条文当作"必须由服务端阻塞实现等待"的技术要求（实现形态留 A-09）。
- 不承担"等待期间的状态可观测"（F05 / F06）。
