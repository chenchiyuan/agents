# F17 · 服务化声明与可发现

**来源**：demand.md 做什么#1 / #3 的交付形态；§大概怎么做（"服务化：以上全部按 `{summary, params, response, errors, docLink}` 元数据体例声明 ⇒ 自动进入 `/api/docs` 与 `llms.txt`"）；决策 D-8；效果#7

## 用户价值

**接入方不用读源码就能发现能力**——打开文档面或索引文件就看得见本迭代新增的每一条能力，知道它解决什么问题、怎么调。

## 验收标准

1. **元数据齐备**：本迭代新增 / 变更的每条接口能力都按既有路由元数据体例声明（摘要 / 参数 / 响应 / 错误 / 文档链接五项语义齐备）[D-8]。
2. **两处可见（裸判定）**：这些能力**同时**出现在 `GET /api/docs` 的投影与 `llms.txt` 中 [效果#7 的原文判据]。
3. **逐条对应，缺一即失败**：本迭代的每一处新增面都能在上述两处被找到 —— 清单 = 身份（F01）/ 请求方身份（F02）/ 订阅第一形态（F03）/ 订阅第二形态（F04）/ 实例投影字段（F05）/ 调用进展字段（F06）/ 取件面（F07）/ 代次语义（F08）/ 等待入口（F11）/ 取消（F13）/ 告警（F14）/ 恢复判据（F15）/ 重连三态（F16）。**存在一条找不到 ⇒ 本卡失败**。
4. **摘要以调用方视角写**：摘要说明"这个能力解决什么问题"，不是仅罗列入参出参。
5. **既有条目不漂移**：既有端点的既有元数据不因本次新增被改坏（既有条目的摘要与字段说明保持）[G01]。

## 边界（不包含）

- 不做文档站重构、不做新的文档格式、不做示例站。
- 不把本卡当成"必须新增文档文件"（投影面是既有机制）。
- 不要求 SDK 层一一封装（既有 SDK 面是否同步属 A-14）。
- 不承担各端点自身的行为正确性（各卡自负）。
- 不做文档的国际化 / 版本化。
