# F08 · 续接契约与一轮快照重建

**来源**：demand.md 做什么#1（"离线/晚订阅也不丢结果"的续接侧）；做什么#3（"把控制面与恢复做成契约"）；§大概怎么做（续接：`epoch` 代次 + `409 STALE_EPOCH`；客户端流程固定为 epoch 校验 → 一轮快照 → 继续订阅/调度）；决策 D-10 / D-11 / D-12 / D-14；效果#3

## 用户价值

调用方**断多久都能接着干**——回来说两句话就重新掌握全局（谁在、谁在跑、跑到哪、有没有卡住），并且**绝不会被"看起来连续"骗过去**。

## 验收标准

1. **代次校验 —— 绝不给假连续**：hub 代次发生变化（至少覆盖"hub 重启"这一必现场景，口径见 MI-4）后，持旧代次的调用方在订阅 / 取件时得到**明确的可判定结论"你的视图已过期、不可续"**（`409 STALE_EPOCH` 语义），而**不是静默继续**；代次未变化时，同一动作**不**产生该结论。
2. **一轮快照即可重建视图（裸判定）**：调用方断开任意时长（长于其订阅存活）后拉起、且 hub 未重启时，**两次查询**（实例快照 + 调用快照）即可准确回答 ① 哪些实例在线 ② 哪些实例在重连中 ③ 哪些调用在跑 ④ 各自进行到哪（含"距最近一次事件多久" ⇒ 有没有停滞）[效果#3 的原文形态]。
3. **断开不产生结论性错误**：断开窗口内丢失的实时事件**不导致调用方得出错误的结论性判断**（不出现"调用失败 / 实例死亡"一类由事件缺失推出的结论）；重连后以快照为准 [D-10 / 效果#2]。
4. **流程固定且能继续调度**：续接的固定流程为"代次校验 → 一轮快照 → 继续订阅 / 调度"；快照之后调用方**可以继续派发新调用并正常推进**（不只是"看"，还能"接着干"）[D-11 / D-12]。
5. 续接之后使用等待原语（F09 / F10 / F11）对在跑调用仍然以终态为退出条件，不因跨了断线窗口而失效。

## 边界（不包含）

- **不做回放、不做持久事件日志**（否决路径②：D-10 已确认实时信息允许丢）[不做什么#1]。
- 不承诺"断开期间的每一条事件都能补上"。
- **"有无未取结果"由取件面回答（第三次查询）**，本卡不把它并入"两次查询" [效果#3 的口径差见报告疑问]。
- 不做客户端侧的续接实现（本卡约束 hub 侧可判定的行为与流程语义）。
- 不把"hub 的记忆"当恢复依据（D-14）。
- 不承担 hub 自身的可用性判据（F15）与实例重连（F16）。

## 架构维度

**已回填 · A-07（完整契约见 `architecture.md` §4 A-07）**：`epoch = <webBootId>.<routerGeneration>`——web 与 Router 各在启动时生成一次代次（Router 的代次经 `router.status` 结果**追加键 `generation`** 暴露）；web 在需要给出 / 校验 epoch 时**尽力观测一次** `router.status`（失败 ⇒ 沿用最后一次已知值；从未观测到 ⇒ `0`）⇒ **任一进程重启都会使代次变化，同一对进程存续期内恒定**（MI-4 的两半都成立，且不需要常驻轮询）。**出现位置** = `POST /api/principals` / `GET /api/principals/<id>` / `GET /api/health` 的响应字段；**过期判定** = `GET /api/subscribe`、`GET /api/pickup`、`POST /api/pickup/<id>/ack` 的**可选** `epoch` 参数与当刻值不等；**错误形态** = `409` + 新增机器码 `STALE_EPOCH`（追加于既有封闭枚举）。既有面一律不携带 epoch（既有响应形态逐字不变）；与既有存储寿命的关系 = epoch 只描述"易失登记代次"，重启后仍以产物与 DB 为准（D-14）。

## model_inferred

- **MI-4**（验收 1 的口径）：demand 只说"`epoch` 代次 + `409 STALE_EPOCH`"，未定义代次的变更触发面。本卡按"代次在 hub 存储代次更替时变化（至少覆盖 hub 重启），同一 hub 进程存续期间稳定"落卡 —— 若不稳定则每次请求都判过期、条文自毁，等主 agent 确认。
