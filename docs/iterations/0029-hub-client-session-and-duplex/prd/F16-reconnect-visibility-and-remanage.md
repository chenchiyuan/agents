# F16 · 重连可观测与重新纳管

**来源**：demand.md 做什么#3（"`reconnecting` 状态"）；§大概怎么做（恢复："`agents` 必须能区分 `online` / `reconnecting` / `offline`"）；决策 D-12（重启后 ① 客户端能重连 hub ② hub 能重新纳管 agent ③ 系统恢复到可控可调用）；效果#3 / #6；事实 F-5（agent → hub 自动重连已具备）

## 用户价值

**"正在回来"与"已经死了"不再混为一谈**——调用方不会因为一个实例正在重连就误判事故，也不会因为一次重启就以为整套纳管关系断了。

## 验收标准

1. **三态可区分**：调用方从实例快照与实时订阅面能区分 **在线 / 重连中 / 离线** 三种状态 —— 一个正在重连的实例**不被呈现为"离线/死亡"**，也不与"优雅退出后从列表消失"混同 [效果#3 "哪些实例在线/重连中"]。承载形态（既有状态词的第三取值，或独立字段）见 MI-11。
2. **软重启的可见过程**：只重启 hub、保留 agent 进程 ⇒ 在快照中可观察到该实例**先处于"重连中"、随后回到"在线"**（不是"直接消失"或"直接在线"）。
3. **自动重连回来**：hub 重启后 agent **自动**重连回来（既有重连能力：缺省开启 + 指数退避），不需要人工重启 agent 进程 [事实 F-5]。
4. **重新纳管 = 恢复可调用**：重连完成后，调用方按既有角色名寻址对其实例派发一次调用能**正常受理并完成** [D-12 ②]。
5. **不谎报在跑**：重启后的实例快照中**不出现指向已丢失调用登记的"在跑"投影**（不残留重启前的幽灵在跑状态）；实例的投影状态与其真实状态一致 [D-14：hub 登记易失是明文]。
6. **既有语义不回归**：既有 `offline` 墓碑的产生条件、既有实例状态过滤参数的既有行为、既有 `role` 推导不变 [G01 验收 3]。

## 边界（不包含）

- 不做 agent 进程的自动重启 / 不做集群自愈 / 不做实例重新拉起。
- **不保证"重启前的在途调用被恢复登记"**（明文不保证：以产物与 DB 为准，D-14 / 不做什么#4）。
- 不做重连退避参数的调整（既有重连策略不动）。
- 不判定"重连中的实例能否受理派发"（既有派发失败路径行为不变）。
- 不做实例的历史状态时序 / 上下线审计。
- 不承担恢复判据入口本身（F15）。

## 架构维度

**已回填 · A-13（完整契约见 `architecture.md` §4 A-13）**：**判定来源（零新增状态机）** = 在线 `state='online' && connected`；**重连中 `state='online' && !connected`**（租约未过期但无活动连接 = agent 侧既有自动重连的窗口）；离线 = 既有墓碑。**承载形态 = 独立字段**：`router.status` 节点快照与 `/api/agents` 行**追加 `connected: boolean`**，**既有 `state` 词表保持 `online` / `offline` 二值**——依据：① G01 验收 3 要求既有实例状态过滤参数的既有行为不变（`?state=online` 的判据就是 `state === 'online'`，加第三取值会改变它）；② 既有控制台 `web/app.js` 客户端也按 `state === 'online'` 过滤，第三取值会让"正在回来"的实例从列表**消失**（恰是 F16 要消灭的误判）；③ `state` 是 Router 租约机的状态位，第三取值侵入租约核心；④ 仓库既有取向"同一事实不落两处"。**收敛时机** = 重连成功（既有 `agent.register`）⇒ 下一次投影重算（≤ 一个轮询周期）回到 `online + connected`，不依赖租约超时。**软重启窗口**（仅重启 hub）另需一个**运行态名册提示**（`<包根>/.runtime/roster.json`：退出/投影时写、启动时读；名册项以 `online + !connected` 呈现、四字段投影一律清空、`heartbeatTimeoutMs` 内未回归即移除）⇒ 该项列为 **L1-01 待主 agent 确认**（建议纳入；回退口径见 `architecture.md` §7）。
