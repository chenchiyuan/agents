# F03 · 实时事件订阅（第一形态）

**来源**：demand.md 做什么#1（"实时事件订阅（含纳管 agent 的实时状态投影）"）；§大概怎么做（实时：`GET /api/events?principal=&kinds=&agents=`，明示 best-effort）；决策 D-7 / D-8 / D-10

## 用户价值

调用方**接上就有实时感**——agent 上下线、调用起落、调用终态在发生的那一刻到达，不用轮询、不用自建监控脚本。

## 验收标准

1. **事件实时可达**：已注册身份的调用方建立订阅后，hub 侧产生的以下事件在发生时到达该订阅者：① agent 上线 / 下线 ② agent 状态变化 ③ 调用状态变化 / 调用增量 ④ 调用终态 ⑤ 需要调用方注意的通知类（清单取自 demand §大概怎么做，与既有推送面事件类的关系见 A-03）。
2. **可过滤**：按事件类过滤时，未订阅类的事件不出现在该订阅上；按实例 / 角色过滤时，非目标实例的事件不出现在该订阅上；两类过滤同时给出时取交集 [口径见 MI-9]。
3. **best-effort 是明文契约**：协议面写明"本流**不保证不丢 / 不保证不重 / 不承诺回放**"；且**无订阅者时事件被丢弃不产生任何错误**（既有语义保持）[D-10]。
4. **重连不要求补发**：订阅者断开再连，**不要求**补发断开窗口内的事件；重连后的正确性以快照为准（F08 验收 2）[D-11]。
5. **不干扰既有面**：本订阅的存在与断开不影响既有 4 条推送面的订阅者及其事件到达 [G01 验收 1]。

## 边界（不包含）

- **不做回放、不做持久事件日志、不做投递保证**（不承诺至少一次 / 恰好一次）[不做什么#1；否决路径②]。
- 不承担"结果不丢"（F07）与"终态即退出"（F09 / F10）。
- 不新增事件类语义——事件类清单与既有 4 条推送面的关系（含 `notice` 与既有 `confirmation` 类的对应关系）见疑问与 A-03。
- 不做鉴权、不做订阅授权、不做订阅配额。
- 不做"订阅即产生副作"（订阅不触发重放、不改变调用状态）。
- 不覆盖第二形态（F04）。

## 架构维度

**已回填 · A-03（完整契约见 `architecture.md` §4 A-03）**：新增 `GET /api/subscribe?principal=&kinds=&agents=&epoch=`（SSE；**不扩**既有 `GET /api/events`——既有 4 条推送面的"事件类集合逐字不变"由独立路由**结构性**保证）。事件 7 名 / 5 类语义：`agent_online`、`agent_offline`（复用既有名与载荷）、**`agent_state`**（新增：投影行变化，载荷 = `/api/agents` 行形状）、`call_state`、`call_update`、`call_result`（复用既有调用面三名）、`confirmation`（复用既有全局名）。**`notice` = 既有 `confirmation` 类的命名差异（同一类语义，不新增事件类）**。`kinds` = 事件名 CSV（域外 ⇒ 400）；`agents` = 实例名或角色名 CSV（匹配键按事件类固定，实例↔角色归一后比较）；两者 AND。`principal` 必填、携带即声明（upsert + 前移 `last_seen_at`）。**不新增发布点**：挂在既有发布之后的同一投递钩子；无订阅者即丢、不缓存不补发；订阅建立不发初始帧（当前值走快照）。第二形态（F04）顺延。
