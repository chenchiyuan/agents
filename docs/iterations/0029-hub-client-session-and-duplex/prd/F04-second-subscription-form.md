# F04 · 订阅的第二形态（层 B 订阅入口）

> **⛔ 本迭代不交付**（D-16，2026-09-16 用户裁决）：范围收窄为**只交付 SSE 形态（F03）**。本卡保留为已验证的设计输出，**不作为本迭代的验收面**；其 `A-03` 待填项中与第二形态强相关的部分一并顺延。

**来源**：demand.md 做什么#1（"实时事件订阅"）；§大概怎么做（实时："Router 侧 `events.subscribe`（第二形态）"）；决策 D-7（"UDS 长连接为第二形态；**协议只约束语义**"）

## 用户价值

**已经持有长连接的调用方**（本机命令行会话 / 编排器）不必为了拿事件再另起一个 HTTP 客户端——在它已有的那条长连接上就能订到同一组实时事件。

## 验收标准

1. **第二形态存在且可用**：在既有层 B（UDS 长连接面）上通过订阅入口发起订阅后，能收到实时事件（判据：订阅后触发一次可预期的 agent 上下线或调用事件，订阅方收到对应事件）[现状核对依据：层 B 现有 8 条方法中无订阅入口，见 demand 事实 F-2 的清单]。
2. **两形态语义等价**：同一 hub 上同时开两种订阅，针对**同一次调用**产生的事件，两方都收到，事件类与语义一致（**不要求帧格式逐字相同**）[D-7：协议只约束语义]。
3. **第二形态同受 best-effort 条文约束**：不保证不丢 / 不保证不重 / 不承诺回放（与 F03 验收 3 同一契约）。
4. **两形态并存不互斥**：一方断开不影响另一方继续收事件。
5. 层 B 既有 8 条方法的语义与行为不变（既有方法不因新增订阅入口而改变）[G01]。

## 边界（不包含）

- 不新增事件类（与第一形态同一组事件语义；事件类清单见 A-03）。
- 不要求第二形态提供第一形态之外的过滤能力；两形态过滤能力的差异（是否必须对齐）留 A-03 判定，本卡只要求事件语义等价。
- 不做回放 / 不做持久化 / 不做投递保证。
- 不改变层 B 既有身份载体（agent 租约制）的语义。
- 不覆盖 HTTP 侧订阅（F03）。

## 架构维度

**顺延（D-16，本迭代不交付）**：本卡的架构维度**不设计落地路径**——第二形态出本迭代，"两形态是否共用订阅核心 / 订阅在长连接上的生命周期 / 过滤参数形态"三个子问题一并顺延（`architecture.md` §4 A-03 第 6 条）。本迭代的订阅能力由 F03 独立承载。
