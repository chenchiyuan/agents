# F09 · 终态即关流（先订阅、后终态）

**来源**：demand.md 做什么#2（"调用终态即关流（补上那根 0 调用点的线）"）；§大概怎么做（等待：终态关流，复用既有关闭原语）；效果#2；事实 F-3（既有关闭原语存在但调用终态路径上 0 个调用点）

## 用户价值

**等一次调用就是"等这一次调用"**——调用一有结论，等待方当场醒过来；不再靠 15~30 分钟的超时兜底，也不再需要人盯着。

## 验收标准

1. **终态当刻退出**：对一次调用先建立订阅、该调用随后到达终态 ⇒ 订阅在**终态当刻结束**（连接关闭、等待方进程退出），**退出时刻不由任何超时值决定** [效果#2；事实 F-3 / 复盘 G-14：现状 7 个等待作业全部靠超时交付]。
2. **可量化的判据**：退出时刻与调用终态时刻之差为**秒级**，且该差值在把超时值调大 / 调小时**不随之变化**（反证"退出由终态驱动，不由超时驱动"）。
3. **关流范围只到该调用自身**：同一 hub 上既有的**对话作用域调用订阅**在该调用终态后**保持存活**，其后续事件照常到达 [不做什么#6 / §大概怎么做"不动 chat-calls"]。
4. **不吞最后一帧**：订阅者在退出前**先收到终态帧**，再收到关闭（关闭动作不导致终态信息丢失）。
5. **既有断开清理不变**：既有"订阅者断开 → 清理订阅"的行为不变；终态关流是**新增的第二条关闭触发路径**，不替代既有路径 [G01]。

## 边界（不包含）

- 不改变对话作用域订阅面的生命周期与语义。
- **不做补发**（"调用已终态后才来订阅"的路径是 F10）；不做回放。
- 不改变调用事件类的集合与既有帧语义（只是补上关闭动作）。
- **不把"关流"当成状态变更**：关闭不写调用状态、不产生终态、不影响调用本身。
- 不做客户端侧的退出实现（本卡约束服务侧的可判定行为）。
- 不承担调用终态本身的判定（既有终态发布路径不动）。

## 架构维度

**已回填 · A-08（完整契约见 `architecture.md` §4 A-08）**：关流落点 = 既有 `closeKey()` 补上调用点（新增 `transport.closeCallSubscriptions(callId)`，内部只关 `call:<callId>`），**调用点 = 既有唯一终态发布点 `publishCallResult`**，且**先写终态帧、后关流**（同一 tick 顺序写 ⇒ 不吞最后一帧）。**只关按调用订阅**：`chat-calls:<chatId>` 不关（验收 3）；既有"订阅者断开 ⇒ 清理订阅"路径**不动**（验收 5：终态关流是第二条关闭触发路径，不替代既有路径）。不新增发布链、不改既有帧语义（只补一个关闭动作）。
