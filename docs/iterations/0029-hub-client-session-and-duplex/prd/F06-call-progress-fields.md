# F06 · 调用进展字段（最近事件时刻 / 停滞可区分）

**来源**：demand.md 做什么#3（"进展字段（`last_event_at`、`idle_ms`）"）；§大概怎么做（观测投影）；效果#3（"有没有停滞"）；事实 F-9 / 复盘 G-20（现状"正常长跑"与"卡死"在观测面上不可区分）

## 用户价值

**"跑得久"和"卡住了"能分开看**——调用方不必靠"猜状态 + 等超时"，也不会把一次正常长跑误当成事故，更不会把一次真卡死当成正常。

## 验收标准

1. **字段存在且会前进**：调用快照（`GET /api/calls` 每行）含"最近一次事件的时刻"；该调用产生新事件时该值前进；运行中的调用该值非空。
2. **可得出"多久没有新事件"**：由该字段可无歧义得出"距最近一次事件过去了多久"这一量；该量的计算位置（服务端提供 / 客户端导出）留 A-05，本卡只要求调用方**能拿到这个量**。
3. **核心判据 —— 对照实验**：同一时点查询快照，同时观察两个在跑的调用 —— ① 持续推进型（不断产生事件）② 无新事件型（停滞）—— 二者"距最近一次事件的时间"呈现**可区分差异**（①维持低位、②持续增长）⇒ "正常长跑"与"卡死"在观测面上可区分 [复盘 G-20 的正面判据]。
4. **终态不参与停滞判断**：调用进入终态后，该字段不再具有"停滞"含义（终态以既有 `ended_at` 为准）。
5. **既有行字段不回归**：既有 roster 行的既有列与取值不变（本卡为加法）[G01 验收 3]。

## 边界（不包含）

- **不给停滞阈值、不做停滞告警、不做自动取消**：本卡只提供可判据的字段；"多久算卡住"是调用方的判断，不由 hub 代为判定 [MI-2]。
- 不做事件历史 / 不做事件回放 —— 本字段不是事件日志，只是"最近一次事件的时刻"。
- 不承诺"卡死时通知调用方"：无新事件即无广播，订阅面（F03）不因此产生事件。
- 不做用量 / 开销类派生列（沿用既有裁剪边界）。
- 不做调用的自动超时 / 自动终止。

## 架构维度

**已回填 · A-05（完整契约见 `architecture.md` §4 A-05）**：`last_event_at` = Router 任务条目的**既有 `updated_at`**（受理 / 每次 `task.update`（含 `truncated` 控制条目）/ 终态三处已写）⇒ **零新增写入点**；终态后不再前进。承载 = `GET /api/calls` 行**追加**一列（既有 6 列名、取值与派生逻辑不变）。**`idle_ms` 由客户端导出**，服务端只给时刻——服务端自造 "now" 会把"响应生成时刻"与"客户端读取时刻"混为一谈（既有取向：控制台 `fmtAgo` 从时刻渲染相对量）。

## model_inferred

- **MI-2**（验收 3 的口径）：demand 未给停滞阈值，也不应有单一阈值。本卡把判据写成"两个对照调用在同一时点呈现可区分差异"，而**不是**"超过 X 毫秒即停滞"，等主 agent 确认该判据形态。
