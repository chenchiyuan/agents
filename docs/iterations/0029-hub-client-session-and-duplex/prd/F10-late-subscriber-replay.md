# F10 · 晚订阅补发终态（先终态、后订阅）

**来源**：demand.md 做什么#2（"晚订阅补发终态"）；§大概怎么做（等待："晚订阅补发：先取任务，已终态则补发一帧后关流"）；事实 F-4（无订阅者即丢、不缓存不排队不补发）

## 用户价值

**来晚了也能拿到结论**——调用可能几秒前就结束了，订阅者不会因此永远挂着等一个再也不会来的帧。

## 验收标准

1. **晚订阅立即有结论**：对一个**已经终态**的调用建立订阅 ⇒ 订阅者**立即收到该调用的终态帧**（不静默、不永久挂起），并在收到后立即结束 [事实 F-4：现状晚订阅者一条也收不到]。
2. **幂等语义**：不论订阅发生在终态**前**（F09 覆盖）还是终态**后**（本卡覆盖），订阅者都能拿到该调用的终态信封并且退出 ⇒ 订阅这个动作成为"等这一次调用"的可靠原语。
3. **补发内容 = 当刻终态信封**：补发的帧与该调用 `calls get` 的终态信封同形状、同取值；**不补发**中间过程事件 [§大概怎么做："补发一帧后关流"]。
4. **不存在的调用有明确结论**：对一个不存在的调用 id 建立订阅 ⇒ 给出明确的"不存在"结论（不静默挂起、不无限等待）[与既有"不存在"语义同类的可判定结论]。
5. **进行中的调用行为一致**：对进行中的调用订阅，增量照常到达、终态当刻退出（与 F09 同一行为，不因本卡新增而产生第二条路径差异）。

## 边界（不包含）

- **不做过程回放**：中间事件不补发；要看过程走既有转录面。
- 不做对话作用域订阅的补发（只覆盖按调用的订阅）。
- **不做持久化**：hub 重启后对旧调用 id 的订阅按"不存在"处理（调用登记内存化，D-14）。
- 不改变既有帧结构与事件类（只是新增"先补一帧再关"这一条路径）。
- 不做"订阅即等待"的语义扩展（等待入口是 F11）。

## 架构维度

**已回填 · A-08（完整契约见 `architecture.md` §4 A-08）**：补发落点 = `GET /api/calls/<call_id>/stream` 的 handler，判定顺序固定为**先建立订阅、再读当刻状态**（`router.task_get`）：已终态 ⇒ 补发**一帧当刻终态信封**（与 `calls get` 同源同形状、不补发中间过程）随即关流；不存在 ⇒ 沿用既有 `404 NOT_FOUND` 且**不建立订阅**；进行中 ⇒ 与 F09 完全同一路径（不产生第二条行为差异）。**不变量（消掉竞态重复）**：每个调用订阅**至多送出恰好一帧终态帧、至多关闭一次** —— 登记后若已通过实时路径收到终态帧，补发被跳过。
