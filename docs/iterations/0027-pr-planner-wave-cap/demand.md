# 第二段：需求结论

## 做什么

1. 给 `pr-planner` 角色新增"关键路径长度"判断维度：在 Work（分组）阶段把"关键路径 ≤3"作为硬约束参与分组决策，超限时按 D-5 合并规则循环合并耦合最紧的相邻 PR 并重算，直到 ≤3 或某次合并会违反原子性/可审查性锚点为止；后者情形下转出"建议拆分为多个迭代"结论（含具体拆分建议：哪些功能点归第一个迭代、哪些归下一个）
2. 把 `workflow-pb` 的方案确认门从"阶段3→4之间"挪到"阶段4→5之间"；呈现内容从"prd.md+architecture.md"扩展为"prd.md+architecture.md+PR拆分方案摘要（PR数、依赖图、关键路径长度、若有拆分建议一并呈现）"；阶段4完成后的结构性自检（依赖图无环/文件范围不重叠/并发可行性/关键路径压平结果）在确认门之前自动执行完毕

## 不做什么

- 不引入关键路径算法之外的新调度机制——理由：复用现有 `depends_on` 依赖图数据结构已足够计算关键路径，新增时间估算/工时字段是不必要的实体膨胀（与 v0.2.0"并发可行性"维度做出的选择一致）
- 不改变"并发可行性"逐对检查的判断逻辑和 Verify 阶段的位置——理由：这是独立指标，两条检查目的不同，不合并、不互相替代
- 不新增独立的暂停触发类型——理由：确认门挪位后天然覆盖"是否拆分迭代"这个决策点，没必要新增第二套暂停机制增加协议复杂度
- 不改变 PR 文件七字段格式——理由：本次改动只影响分组判断逻辑和确认门时序，不影响 PR 文件本身的契约
- 不追溯已完成迭代（如 0025）的历史产物——理由：0025 已合并完成，新规则只对本迭代之后新产出的 PR 规划生效
- 不设合并循环的次数上限——理由：每次合并前都要过原子性/可审查性关卡，天然收敛，人为限速反而可能在真实可合并的情况下过早转向"建议拆分迭代"
- 不用功能点数量作为触发拆分判断的信号——理由：功能点数和 PR 依赖链深度是两个不同的量，会导致误判（被否决的候选路径，见下）

## 大概怎么做

- **关键路径定义**：依赖图中最长依赖链上的 PR 数（从入度为 0 的 PR 起）
- **合并排序规则**：候选合并对之间，优先合并"该 PR 的验收标准必须等被合并对象产出才能判断"（独立验收价值最低）的相邻对
- **合并前置检查**：每次合并前检查该次合并是否会违反"逻辑原子性/可审查性"锚点（如被迫把互不相关的功能揉进一个 PR，reviewer 需切换心智模型）；违反则停止合并循环，转出"建议拆分迭代"结论
- **检查时机分工**：关键路径检查在 Work（分组）阶段作为硬约束参与决策；"并发可行性"检查维持在 Verify 阶段，在关键路径已压平的基础上再检查
- **确认门位置与内容**：从阶段3→4之间挪到阶段4→5之间；阶段4产出后先自动跑结构性自检（依赖图无环、文件范围不重叠、并发可行性、关键路径压平结果），通过后再把完整方案（含 PR 拆分摘要）交给用户在确认门里做业务判断

**被否决的候选路径**：
- "新增独立暂停触发类型"（专门为"关键路径超限"定义一种新的暂停）——否决理由：确认门挪位后天然覆盖同一决策点，新增第二套暂停机制是不必要的协议复杂度膨胀
- "用功能点数量触发拆分判断"——否决理由：功能点数和依赖链深度不是同一个量，会把"功能点多但依赖浅"的迭代误判为需要拆分，也会漏判"功能点少但依赖深"的迭代

## 达到什么效果

- 任意迭代产出的 PR 依赖图，关键路径长度 ≤3（裸判定：数一下依赖图最长链上的 PR 数，不问作者即可判断）
- 若某迭代关键路径经合并压平后仍 >3（或合并会破坏原子性/可审查性锚点），方案确认门里必须出现"建议拆分为多个迭代"的结论和具体拆分建议，由用户在确认门做选择，不由主 agent 代为拍板
