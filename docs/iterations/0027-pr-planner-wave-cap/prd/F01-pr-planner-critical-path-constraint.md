# F01 · pr-planner 关键路径硬约束与合并压平规则

**来源**：demand.md 做什么#1（前半）；D-1 / D-2 / D-3 / D-5（合并排序规则部分）

## 用户价值

迭代产出的 PR 依赖图关键路径不会无限累加，用户不会再遇到"依赖链最长能到 5 轮，一次迭代要跑 5 轮才能全部合并完"这类规划结果。

## 验收标准

1. `pr-planner.md` 的 Strategy / 判断框架章节中，存在一个明确命名为"关键路径长度"（或等价、无歧义命名）的判断维度，文字定义为：依赖图中最长依赖链上的 PR 数（从入度为 0 的 PR 起算）。
2. 该维度在 Work（分组）阶段作为**硬约束**参与分组决策——文字表述不是"建议""参考"，是不满足则要处理的强制条件；且明确写在 Work 阶段章节（不是仅出现在 Verify 阶段）。
3. 硬上限明确为 3：关键路径长度 > 3 判定为不合格，须处理。
4. 超限处理规则明确为合并循环：候选合并对之间，优先合并"该 PR 的验收标准必须等被合并对象产出才能判断"（即独立验收价值最低）的相邻对。
5. 合并规则明确为循环式：每次合并后重新计算关键路径长度，重复上述合并，直到关键路径 ≤3，或某次合并会违反"逻辑原子性/可审查性"锚点为止（后一种情况的处理见 [F02](F02-pr-planner-split-iteration-suggestion.md)）。
6. 合并循环不设次数上限——文字中不出现"最多合并 N 次"一类限速表述。

## 边界（不包含）

- 不引入关键路径算法之外的新调度机制——不新增时间估算、预估工时等 pr-planner 现有七字段格式之外的新数据字段。
- 不改变"并发可行性"逐对检查的判断逻辑和 Verify 阶段位置——两者是独立指标，关键路径检查前移到 Work 阶段，并发可行性检查仍在 Verify 阶段，在关键路径已压平的基础上再检查。
- 不改变 PR 文件七字段格式本身。
- 合并会违反原子性/可审查性锚点时应转出的"建议拆分为多个迭代"结论——见 [F02](F02-pr-planner-split-iteration-suggestion.md)，本卡不覆盖该分支的验收标准。
