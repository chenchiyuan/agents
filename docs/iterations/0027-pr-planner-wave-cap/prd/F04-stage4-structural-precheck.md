# F04 · workflow-pb 阶段4结构性自检前置于确认门

**来源**：demand.md 做什么#2（后半）；D-6

## 用户价值

用户在确认门里看到的已经是结构正确的方案，不会先花时间挑出"依赖图有环""文件范围重叠"这类结构性错误——这些留给自动检查处理，用户在门里只需要做业务判断（这次迭代方案是否符合预期、要不要拆迭代）。

## 验收标准

1. `workflow-pb.md` 中明确规定：阶段4（PR 规划）产出后，在方案确认门触发之前，须自动执行完以下四项结构性自检：依赖图无环、文件范围不重叠、并发可行性、关键路径压平结果（见 [F01](F01-pr-planner-critical-path-constraint.md)）。
2. 四项自检全部通过，方案才能进入确认门；未通过任一项时，按现有机制处理（依赖图有环走既有的"流程结构错误中止"路径，不触发确认门）。
3. 该自检顺序明确为"确认门之前"，不是"确认门之后由用户发现问题再打回"——文字表述要能区分这个先后关系。

## 边界（不包含）

- 不改变"并发可行性"检查本身的判断逻辑和执行位置——该检查仍在 pr-planner 的 Verify 阶段执行，本卡只规定"确认门必须等这些检查结果都通过"，不重新定义检查怎么做。
- 不改变"依赖图有环"作为流程结构错误中止的既有处理方式（`workflow-pb.md` 已有的"唯一的流程结构错误中止"条款不变）。
- 不新增独立的暂停触发类型——四项自检不通过时的处理方式沿用既有机制，不是新增一种暂停。
- 结构性自检的具体执行方式（是否复用阶段4既有推进条件检查结果，还是独立重新执行一遍）——**架构决策（阶段3已确定）**：复用，不独立重新执行。具体机制：阶段4「推进条件」表新增并发可行性、关键路径压平结果两项，使推进条件本身覆盖四项结构性自检；方案确认门触发条件即"阶段4推进条件全部通过"，只做结果汇总呈现。详见 `architecture.md` §F04。
