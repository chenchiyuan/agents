# F03 · workflow-pb 方案确认门位置迁移与呈现内容扩展

**来源**：demand.md 做什么#2（前半+呈现内容部分）；D-6

## 用户价值

用户在唯一一次确认门里就能看到完整方案全貌（产品维度+架构维度+PR拆分方案摘要，含关键路径长度、若有的"建议拆分为多个迭代"结论），一次性拍板这次迭代最终要跑几轮、要不要拆迭代，不由主 agent 代为拍板。

## 验收标准

1. `workflow-pb.md` 中"方案确认门"章节的触发时机改为"阶段4（PR 规划）推进条件全部通过后、阶段5（PR 实现）开始前"（原为"阶段3→4之间"）。
2. 该章节的"呈现内容"从"产品维度（prd.md + prd/*.md）+ 架构维度（architecture.md）"扩展为三部分：产品维度、架构维度、PR 拆分方案摘要——PR 拆分方案摘要必须包含 PR 数、依赖图、关键路径长度；若 pr-planner 转出了"建议拆分为多个迭代"结论，该结论也必须一并呈现，不能省略。
3. `SKILL.md` 中与方案确认门相关的描述（触发时机、呈现内容、通过条件）同步改为与 `workflow-pb.md` 一致的表述，不要求逐字相同。
4. "通过条件"（用户明确确认后方可进入阶段5；不确认则停在原地，不得由主 agent 自行判定"方案没问题"而跳过）保持不变，只是触发时机和呈现内容变了。
5. "启动前询问"环节（是否开启方案确认门）的措辞中提到的阶段位置（原文"阶段3→4之间"）同步更新为"阶段4→5之间"。

## 边界（不包含）

- 不改动阶段1~3现有暂停触发条件——demand.md 明确要求维持现状（阶段1~3适用范围的用户决策点不变）。
- 不新增独立的暂停触发类型——确认门挪位后天然覆盖"是否拆分迭代"这个决策点，不新增第二套暂停机制。
- 不改变确认门"关闭情况"的开关机制本身（`status.md` 头部 `**方案确认门**` 字段仍为 `enabled`/`disabled`，默认 `enabled`）——只挪触发时机和扩展呈现内容，不动开关本身的存在形式。
- SKILL.md 中需要逐一同步文字的具体位置清单——**架构决策（阶段3已确定）**：frontmatter description 字段、Step 0 第4步询问文案、`### Gate: 阶段3→4方案确认门` 章节标题+内容（含该章节需从当前位置迁移到既有 `### Gate: 阶段 4 → 5 入口` 之后、`### Step 5` 之前），§用户决策点与暂停格式表格**不需要改动**（确认门是独立机制，不属于该表定义的五种暂停场景）。完整清单见 `architecture.md` §F03 第 5 点。SKILL.md 不在本迭代工作区内，由主 agent 手动同步，不由执行角色直接写入。
