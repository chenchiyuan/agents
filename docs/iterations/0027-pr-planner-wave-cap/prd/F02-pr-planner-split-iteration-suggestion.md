# F02 · pr-planner 合并受阻转出"建议拆分为多个迭代"结论

**来源**：demand.md 做什么#1（后半）；D-3 / D-5（合并前置检查部分）

## 用户价值

当迭代范围真的太大、靠合并 PR 无法把关键路径压到 3 以内时，用户能直接看到"哪些功能点归第一个迭代、哪些归下一个迭代"的具体拆分建议，而不是被卡在一个已知跑不动、又没有下一步行动指引的规划结果里。

## 验收标准

1. `pr-planner.md` 明确规定：每次合并前，必须检查该次合并是否会违反"逻辑原子性/可审查性"锚点（例如被迫把互不相关的功能揉进一个 PR，reviewer 需要切换心智模型）。
2. 一旦某次合并会违反上述锚点，立即停止合并循环——不得为了凑够关键路径 ≤3 而强行合并破坏原子性/可审查性的候选对。
3. 停止合并循环后，转出"建议拆分为多个迭代"的结论；该结论必须包含具体拆分建议：哪些功能点归第一个迭代、哪些归下一个迭代（不能只说"建议拆分"而不给出具体的功能点归属）。
4. 该结论是"建议"，不是 pr-planner 自行执行的动作——pr-planner 不自行创建新迭代目录或改动 demand.md，只在报告/产出物里呈现建议，由用户在方案确认门里做最终选择（见 [F03](F03-plan-gate-relocation-and-content.md)）。

## 边界（不包含）

- 不用功能点数量作为触发拆分判断的信号——判断依据始终是关键路径长度和合并是否违反原子性/可审查性锚点，不是数一数功能点有几个。
- 不新增独立的暂停触发类型——这个结论通过 F03 挪位后的方案确认门呈现给用户，不是 pr-planner 自己发起一次新的暂停机制。
- "拆分建议"具体的文档格式/落盘位置——**架构决策（阶段3已确定）**：落盘为 `prs/split-suggestion.md`（仅当合并受阻转出该结论时创建），不是仅存在于 pr-planner 报告文本中；格式定义与选择理由见 `architecture.md` §F02 / `roles/architect/data/0027-pr-planner-wave-cap-decision-notes.md`。
