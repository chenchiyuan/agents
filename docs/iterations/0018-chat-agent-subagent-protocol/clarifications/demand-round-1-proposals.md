## 0. 本轮为什么有 11 条（且其中 3 条互相咬合）

用户的原始表述只有一段（`demand.md` §1.1），它给的是**目标**（hub 调用与客户端原生 sub agent 调用等价），**没给机制、没给边界、没给参照物**。侦察证实：

1. 仓库内**不存在** sub agent 协议的定义（`grep -i 'subagent|sub_agent' oamp/src` 零命中；全仓搜索"等价/subagent"零命中）⇒ 参照物必须由用户钉死（P-1）。
2. 仓内**有两份**互相不同的候选参照（harness `task` 工具契约 vs `principles/execution/model-dispatch-protocol.md` 的 ACP 一次性派发契约）⇒ 不能默认选一个（P-1）。
3. 用户要的"等价"与**三条既有用户裁决**直接冲突或咬合，必须逐条重新征求用户意见：
   - 0015 R-1/R-2「hub 不启动、不关闭 agent」vs sub agent 契约含实例生命周期（P-2/P-9）；
   - 0015 N5「不做 tasks 查询接口」vs 调用身份需要按 id 寻址（P-4）；
   - 0015 N11「不为 codex / omp / claude 实现客户端 SDK 或适配器」vs "等价替换"的交付边界（P-3）。
4. 0017 的项目层（`project_id NOT NULL` + `project` 上下文注入）已随 pr-001~003 落在本迭代的基线分支上，而 0017 本身**未验收**（pr-004 未合并）⇒ 调用面与它的关系需要一句明确的共存口径（P-10）。

**因此：P-1/P-2/P-4 是本轮的三根支柱**——它们决定后面所有条目的含义。其余 8 条是覆盖面逐项收敛。

## 1. 支柱项（P-1 ~ P-4）

### P-1 · 「sub agent 协议」的参照契约与「等价」的判定口径

- **草稿更新**：把用户说的"符合 sub agent 协议"锚定为**harness `task` 工具契约**（`omp://tools/task.md`：调用入参 / 返回值 / 可观测面三面），并把"等价"的判定口径定为 **语义（能力）等价**，不是字面形态等价；凡不能等价的条目，必须写进 `oamp/API.md` 的**差异清单**，逐条可核对。
- **理由**：用户原话是"使用 **omp 等客户端**调用 sub agent"（S-2），而 omp 客户端"直接使用 sub agent"的唯一真相源就是 `task` 工具契约（侦察 B.1）。仓内另一候选 `principles/execution/model-dispatch-protocol.md`（ACP 一次性派发契约）是 **agents 项目自身的派发契约**，hub API 一条都没实现（侦察 B.6），且它的 `completed|failed|blocked` 词汇与 harness 契约不同——选它会把"客户端原生体验"重新翻译一遍，多出一层不必要词汇。
- **选项**：
  - **A（推荐）**参照 = harness `task` 工具契约；判定 = 语义/能力等价，传输形态（HTTP 路由名、字段名、URI scheme）允许不同但必须登记差异。
  - B 参照 = `principles/execution/model-dispatch-protocol.md` 的 ACP 一次性派发契约（与 harness 契约不同的第三套词汇）。
  - C 参照 = 两者合并（调用面照 harness，结果信封照 ACP）。
- **我的推荐**：**A**。
- **推荐理由**：用户要的是"客户端没差别"，客户端认识的是 `task` 契约；B 的参照物**没有任何客户端在用**（hub 零实现、无客户端消费先例）；C 会把两套词汇叠在一起，违反"消除模糊"而不是增加模糊。
- **不确定时的影响面**：选 A vs B 会改变**验收清单的每一条**（字段名、终态词汇、进度事件形态），并决定 P-6/P-7/P-8 三张覆盖表的基准；选错 = 整个阶段 2 的功能卡重做。
- **参考视角（不进入结论，仅供讨论）**：ACP 那份文档的价值不在词汇，而在它已经沉淀了 agents 项目内部的派发语义（`status: completed|failed|blocked`）。若用户确认参照 A，建议**只借用它的终态词汇做 hub 侧枚举**，不引入它的请求/响应结构——但这是架构阶段的事，本清单不据此下结论。

### P-2 · 被调用者是谁：常驻 agent 实例（chat 中的 agent）vs 一次性派发的临时 agent ★

- **草稿更新**：被调用者 = **chat 中的常驻 agent 实例**（一次调用 = 向某个在线 agent 实例派发一个任务），**不是**每次调用新 spawn 一个 agent；"等价"因此限定在**协议面**（调用/响应/展示），**不包含进程生命周期**。差异清单第 1 条写死："hub 调用的被调用者是常驻实例（多轮共享上下文池），原生 sub agent 是每次派发的临时 agent"。
- **理由**：用户原话"通过 hub api 接口调用 **chat 中的 agent** 执行"（S-3）已经把被调用者指死为 chat 里的常驻 agent；而 0015 你已拍板"**hub 不自己启动 agent，也不关闭 agent**，先单纯做连接/路由中心"（r:0015/demand:7,23）。现状 hub 侧也确实是"常驻 agent 节点 + 每任务子进程"（侦察 A.3/A.4）。
- **选项**：
  - **A（推荐）**接受差异：被调用者 = 常驻实例；等价只覆盖三面协议；生命周期差异显式登记。
  - B 引入"每次调用一个新 agent 实例"语义 ⇒ 需要 hub 创建/销毁 agent 进程。
  - C 折中：常驻实例，但每次调用用独立上下文（不共享多轮记忆）。
- **我的推荐**：**A**。
- **推荐理由**：B 与 0015 的 R-1/R-2（你自己拍的"hub 不启停 agent"）**正面冲突**，且现状 Router 无进程管理面（侦察 A.2/A.5）；C 会改变上下文池语义（0017 N9 已明确不改上下文池的键与串行语义），且用户没要求多轮记忆隔离。
- **不确定时的影响面**：这是本轮**最大的范围开关**。选 B = 本迭代从"协议对齐"变成"hub 托管 agent 生命周期"，范围与风险数量级上升，且必须一并改判 0015 R-1/R-2；选 A = 可保持在"新增调用面 + 结构化结果 + 调用级可观测"三件事内。
- **参考视角（不进入结论，仅供讨论）**：客户端侧的"没差别"其实主要来自**调用形态与结果形态**，而不是子 agent 是不是临时进程——多数客户端不在意被调用者是否常驻，只在意"我发一次调用，能拿到结构化结果、能看到进度、能按 id 追踪"。所以 A 未必牺牲体验。（参考视角，非结论。）

### P-3 · 交付边界：只做 hub 侧 API 面，不实现客户端 SDK / 适配器

- **草稿更新**：本迭代交付物 = hub 侧（Router / web / agent 节点）+ `oamp/API.md` + 控制台展示面；**不**为 omp / codex / claude 写任何 SDK、插件或适配器；"等价替换"的验收方式 = **对照清单 + 可粘贴示例**（照着文档能调通），而不是"真的把 omp 改造过"。
- **理由**：0015 你已明确「不为 codex / omp / claude 实现**客户端 SDK 或适配器**；用户要求的是**读了接口文档之后**可以接入使用 hub」（r:0015/demand:248, N11）。且 harness 的 `packages/coding-agent` **不在本仓库**（侦察 B: "该包不在本仓库"）——真做客户端适配就是跨仓库工程。
- **选项**：
  - **A（推荐）**只改 hub 侧；等价性以对照清单 + 文档示例验收。
  - B 同时实现一个 omp 侧适配器（需跨仓库、且推翻 0015 N11）。
  - C 只做接口不做文档/对照表（不满足 0015 的"读了文档就能接入"）。
- **我的推荐**：**A**。
- **推荐理由**：与既有裁决一致、零跨仓库成本；且"等价性"本身是**契约问题**，用对照清单可判定（见 E9）。
- **不确定时的影响面**：选 B 则本迭代需要第二个仓库的改动与验收通道，阶段 4/5 的 PR 边界无法只在本仓库闭合。

### P-4 · 「一次调用」的身份：把既有 `task_id` 升格为 HTTP 一等调用资源

- **草稿更新**：一次调用分配一个**可寻址的调用 id**（**复用 Router 既有 `task_id`**，不新建第二套资源体系）；HTTP 面新增"按调用 id 查询终态 / 订阅进度 / 取转录"三条能力；`chat` 仍是调用的发起容器与消息历史载体，**不必成为调用本身**。
- **理由**：原生 sub agent 的回执核心是"一个 job id + 按 id 取结果/转录"（侦察 B.2）；hub 现状**已经有** `task_id`（`POST /api/messages` 响应里就带，`API.md:458-462`）与 Router 侧任务表（`router.task_get` / `router.task_list`，`router.js:384-402`），但 HTTP 面刻意不暴露（`API.md:980`「tasks 接口…不经 HTTP 暴露」= 0015 N5）。⇒ 用既有 `task_id` 是最短路径，不需要发明新实体。
- **选项**：
  - **A（推荐）**`task_id` 升格为 HTTP 一等调用资源（复用既有任务表；新增按 id 的查询/订阅路由）。
  - B 保持"chat 即调用"，只补齐响应与进度（不引入按 id 寻址）。
  - C 新建独立 call/job 资源（与 Router 任务表并存）。
- **我的推荐**：**A**。
- **推荐理由**：B 无法满足"按 id 追踪"（原生 subagent 的核心回执），C 会造出第二套与 Router 任务表镜像的实体（重复真源）；A 是既有数据的暴露，改动面最小。
- **不确定时的影响面**：**此条需要用户显式解除 0015 的 N5**（「不做 tasks 查询接口 / 任务编排」）。若用户不解除，则 P-7 的"按 id 取终态/转录"与 P-8 的"按调用订阅"都要退化为"只能通过 chat 流观察"，等价性在响应面出现结构性缺口（必须写进差异清单）。
- **参考视角（不进入结论，仅供讨论）**：暴露 `task_id` 时最容易失控的是"顺手把任务编排也做了"（`router.task_list` 全量列出 + 按状态过滤会自然长成一个编排面）。建议把范围钉在"按 id 读自己发起的调用"，不做全量任务列表/编排——这条边界留给阶段 2/3，本清单只提示风险。

### P-5 · 调用面（I1~I11）与寻址命名

- **草稿更新**：调用面按**角色名（agent 名）**寻址，并让角色名可被 HTTP 客户端发现；不照搬 harness 的 `.omp/agents` 完整发现优先级链。
- **理由**：① 原生 sub agent 按 **task-agent 类型名**选择（`scout`/`reviewer`/…，侦察 B.1），而 hub 调用今天只能按**在线实例名** `pb-<role>`（侦察 A.5，role 对 HTTP 不可见）⇒ 客户端无法用它熟悉的名字调用；② oamp 的 `instance_id` 有唯一公式 `pb-<role>`（`role-binding.js:12-32`，不允许 override，`cluster-config.js:23-24`）⇒ **role 可从 instance_id 推导**，不需要动 Router 协议面；③ 本仓库**没有** `.omp/agents`（glob 实测不存在），harness 的发现链（项目→用户→插件→内置）在 oamp 语境下无对应物，照搬等于新造一套发现机制。
- **选项**：
  - **A（推荐）**`GET /api/agents` 增加 `role` 字段（对 `pb-<role>` 形态的实例推导；其余形态为空），调用面按 role 寻址；role 不在线 → `404/409` 明确失败。
  - B 照搬 `.omp/agents` 命名空间与完整发现优先级链。
  - C 维持只按 `instance_id` 寻址（等价性 I1 缺口写进差异清单）。
- **我的推荐**：**A**。
- **推荐理由**：与既有命名公式一一对应、零协议改动（不触碰 0017 N8「不改 agent↔router 协议方法面」）；B 是无对应物的新建；C 会让客户端必须知道 `pb-` 前缀与实例名，破坏"没差别"。
- **不确定时的影响面**：若选 B，需在 oamp 侧新建 agent 发现/定义注册表（新存储 + 新优先级语义），范围显著扩大。

### P-6 · 响应面（R1~R7）

- **草稿更新**：调用响应与终态给出**结构化结果**；转录按"本进程内可读、**不持久化**"提供（不推翻 `API.md:627` 的既有声明）。
- **理由**：原生 sub agent 的返回值是结构化对象（`exitCode / usage / durationMs / resolvedModel / aborted / truncated / structuredOutput / 产物路径`，侦察 B.2），hub 现状只有 `{chat_id, task_id, message_id, warning}` + 一行 chat `out`（侦察 B.5 R1）；而"结构"里有些字段 hub **今天产不出来**（举例：`omp-daemon` 成功体只有 `{text, model, context_id, pid, stop_reason, duration_ms, exit_code}`，无 `usage/tokens`，侦察 A.3 第 8 跳）。
- **选项**：
  - **A（推荐）**：终态结构 = 既有可得字段 + 明确标注"不可得字段"；不可得字段（usage/tokens/成本、aborted 语义）**登记为差异**，不造假数据（"绝不估算"是 harness 自己的原则，侦察 B.4）。
  - B：为补齐 usage/tokens 去动 omp 输出解析（含 `[UNVERIFIED]` 的结构化输出模式）。
  - C：只回聊天文本，不做结构化终态。
- **我的推荐**：**A**。
- **推荐理由**：C 直接不满足用户的原话（"响应…符合 sub agent 协议"）；B 依赖未经证实的 omp 输出能力（侦察 D.1 `[UNVERIFIED]`），把它作为需求承诺会制造无法验收的条款。
- **不确定时的影响面**：选 B 则阶段 3 必须先做一次 omp 输出形态验证，且验收依赖外部进程行为。
