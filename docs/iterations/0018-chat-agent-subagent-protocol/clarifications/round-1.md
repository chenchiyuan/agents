### 维度 2 · 逻辑闭环（why → what）

- **Why 三条**：① hub 能"发消息"但客户端拿不到"一次调用"（`API.md:437-488` 的响应只有 `{chat_id, task_id, message_id, warning}`；`task.update` 不入库 `API.md:627`；无按调用订阅）；② 原生体验来自三面契约而非某条路由；③ hub 展示面只到 chat 粒度（`GET /api/agents` 只有实例快照、SSE 只有 chat 作用域、增量 200 行封顶）。
- **逐条对照**：调用面/响应面/展示面**均可从 why 推出**（闭环成立）；"等价替换"**只能到协议面等价**。
- **产出四处缺口**：
  1. **生命周期缺口（最大）**：原生 sub agent 每次派发临时 agent，用户说的是"chat 中的 agent"，且 0015 R-1/R-2 已拍板 hub 不启停 agent ⇒ 与 0015 直接咬合 → **P-2**。
  2. **交付边界缺口**：客户端侧兑现被 0015 N11 挡住，harness 包不在本仓库 ⇒ 验收只能是"对照清单 + 文档示例" → **P-3**。
  3. **结构性障碍**：转录（R3）无存储底座（`API.md:627` + Router 任务表内存）⇒ 只能"本进程内可读" → **P-6 的 R3 行**。
  4. **旧边界解除**：调用身份需要按 id 寻址，而 0015 N5 明确不做 tasks 接口 ⇒ 必须由用户显式解除（限"按调用 id 读自己发起的调用"）→ **P-4/P-10a**。
- **额外发现的既有立场冲突（新，阶段 1 必须让用户知晓）**：仓库既有文档**多处明确"两者不合并"**（`docs/ds/05-实例配置与初始化集成.md:125-131` 结论「两者不合并」；`docs/ds/README.md:10` 把 `model-dispatch-protocol` 定位为"现有的一次一发的子 agent 派发"）。本迭代的定位是"**在 hub 的 HTTP 面新增一层调用协议**"，不是"合并两者" ⇒ 已写进 C-8，并挂 P-2。

### 维度 3 · 边界完整性

- **用户明说的边界 = 0 条**：用户原始表述只给"要做什么"，无一句"不做什么"。这是本迭代与 0015/0017 最大的差别（那两次都有用户明说边界可用）⇒ 本版**全部边界（N1~N20）均为推导**，逐条附"为什么这次不做"并**集中转呈**（P-5/P-6/P-7/P-8/P-10）。
- 推导边界来源分布：承既有用户裁决 7 条（0015 R-1/R-2/N5/N11、0017 N8/N9、零依赖锁）；由"结构性不可满足"推出 3 条（持久转录、工具级进度、远端渲染）；由范围收敛判断推出 6 条（isolated、effort、嵌套血缘、`local://`、plan mode、steer/取消）。
- **主动收敛判断 5 条**：去掉"取消/终止/steer"（不参与最小链路，且需跨进程中断语义）、"isolated"（与三面正交，带出 worktree 编排）、"工具级进度"（agent 侧无数据源，侦察标注 `[UNVERIFIED]`）、"远端同会话渲染"（无会话镜像模型），"agent 建/杀/复活"（承 0015 R-1/R-2）——最小闭环均成立；**保留**"结构化终态 + 按调用寻址 + 调用级进度"（三者即"能不能把 hub 当 subagent 用"的直接判据）。
