## MI-01 · 角色不可用时的失败口径

**来源卡 / 验收项**: F03 验收 2（及验收 4 的无 role 实例形态）
**demand 留白处**: E2（「角色不在线时得到明确失败（非静默 200）」）/ M-6 / P-5

**问题**：角色不可用有三种情形——① 不存在该角色；② 角色存在但离线；③ 目标实例无法按角色名寻址（无 role，如控制台自身）。`demand.md` 未定义：是否区分这三种、失败取哪类错误码、无 role 实例是"可被发现但不可寻址"还是"彻底不可见"。

**选项**：
- **A（推荐）**：三种情形统一为**一类 4xx 明确失败**，不静默 200；不新增错误码族（沿既有统一错误契约的封闭枚举）；无 role 实例保持 `派生` §6.3-2 的「角色为空值、不被误报为可寻址角色」。
- **B**：区分处理——「不存在 / 无 role 实例」取一个错误码，「角色离线」取另一个错误码（客户端可借此重试策略）。
- **C**（更严，属 `派生` 回退口）：无 role 实例从可发现面上也彻底不可见，且明确不可被调用面寻址。

**推荐理由**：E2 的裸判定只要求「明确失败（非静默 200）」；A 满足判定且错误面最小、不动既有错误契约；B 引入第二套语义但当前无客户端诉求（客户端不在本仓库，N1 / N20）；C 与 `派生` 口径冲突，需要改动上游留痕。

**影响面**：F03 验收 2（及验收 4）；若选 B / C，需同步 F03 边界与 `demand.md` §6.3-2 回退口的落地表述。

## MI-02 · 批量提交的调用粒度

**来源卡 / 验收项**: F04 验收 3；F05 验收 1；F09 验收 1
**demand 留白处**: W2（I2 批量）/ W3（一次调用 = 一个调用 id）/ E3 / E7

**问题**：一次提交多项任务时，调用身份如何生成？`demand.md` 两处读法都成立：W3 说「一次调用产生一个可寻址的调用 id」，E3 说「提交两项 → 返回两条结果」，E7 说「发两次调用后列一次、看到两行」。是「每项 = 一个调用」，还是「一个批次 = 一个调用含多项结果」？

**选项**：
- **A（推荐）**：**每项 = 一个独立调用**——N 项 ⇒ N 个调用 id、N 行 roster、N 个终态；「批量」只是一次提交多个调用的便捷形态。
- **B**：一个批次 = 一个调用 id，终态内含 N 项结果，roster 按批次一行。

**推荐理由**：W3 的「一次调用 = 一个可寻址的调用 id」与 I6「**每项**可选阻塞 / 后台」（项级独立）指向 A；A 让 E3 / E4 / E5 / E7 的判定粒度与单项调用一致，避免出现「批次 id / 项 id」双层标识与两层终态。

**影响面**：F04 验收 3、F05 验收 1、F09 验收 1（roster 行数口径）、F07 验收 1（终态事件数量）；E3 / E4 / E5 / E7 的判定粒度。**若选 B，F05 与 F09 的验收需重写**（引入批次层）。

## MI-03 · roster 的作用域与「不做全量任务列表」的边界

**来源卡 / 验收项**: F09 验收 1、5；F13 验收 2
**demand 留白处**: W3（限「读自己发起的调用」、不做全量列表 / 过滤 / 编排）/ W5（roster 每次调用一行）/ N17

**问题**：W5 要求「调用 roster（每次调用一行）」，W3 / N17 又限定「不做全量任务列表 / 按状态过滤 / 编排面」。roster 的可见范围与语义如何界定才不与 N17 冲突？「自己发起的调用」在无鉴权本机 hub（N19）下指什么？

**选项**：
- **A（推荐）**：roster = **展示面**（面向调用方可见的调用行，取值即读）；**不提供**按状态过滤 / 编排操作 / 任务管理语义。「不做全量任务列表」指**带过滤与编排语义的任务管理面**；「自己」按**范围限定**理解（不做编排面），不引入鉴权可见性隔离。
- **B**：roster 按 **chat 作用域**——列出归属某 chat 的调用，跨 chat 不出现在同一 roster（需要额外的范围口径）。
- **C**：roster = 全部调用（含所有 chat），仅在文档上声明「不是编排面」。

**推荐理由**：A 满足 E7 的裸判定（发两次、看到两行）且不动摇 N17 的字面；B 把展示面变成查询面，需要一个 demand 未给的作用域参数；C 与 N17 字面冲突最大。**注**：本阶段判定此处的 W5 / N17 关系**不是 demand 内部矛盾**，而是边界口径留白（见 `prd.md`「疑问与越界」1）。

**影响面**：F09 验收 1 / 5、F13 验收 2；**若选 B**，F09 需增加作用域口径并同步 F13（控制台默认作用的 chat）。

## MI-04 · 无归属调用的拒绝口径

**来源卡 / 验收项**: F11 验收 2
**demand 留白处**: W6 / E11 / N19

**问题**：E11 要求「不带 chat 归属 → 被拒绝（4xx，明确错误码）」，但未定义「不带」的形态与错误码族：未提供与提供空值是否同判？取参数类还是其它类错误码？

**选项**：
- **A（推荐）**：**未提供与提供空值一律拒绝**（同类 4xx，沿既有统一错误契约的封闭枚举）；**不设**「服务端兜底到某个默认 chat」。
- **B**：仅「未提供」拒绝，「空值」由服务端兜底到某个既有 chat（会产生隐性归属）。
- **C**：空值允许但走另一类错误码（区分"缺参"与"空值"）。

**推荐理由**：E11 的判定是「无法发起不属于任何项目 / 对话的调用」——B 的兜底会产生隐性归属，违背 W6；C 引入两套语义而当前无需求；A 与 0017 对「缺参 / 空值」的既有裁决口径（一律拒绝）一致。

**影响面**：F11 验收 2；错误码族形态归架构 T-14。

## MI-05 · 阻塞模式的时限与断连口径

**来源卡 / 验收项**: F04 验收 4；F07 边界；F06 验收 2（终态词表）
**demand 留白处**: W2（I6：可选阻塞取终态 vs 后台执行）/ W4 / N3

**问题**：「阻塞取终态」在调用耗时长时是否设人为时限？客户端断连或放弃等待后，调用是否继续？

**选项**：
- **A（推荐）**：**不设人为上限**（阻塞至终态）；客户端断连 / 放弃**不终止**调用——调用仍在后台完成，终态可由订阅或按 id 查询取得。
- **B**：设一个上限，超时后转为「受理 + 调用 id」返回（等价于自动降级为后台）。
- **C**：设上限且超时即失败（引入「超时」这一新终态）。

**推荐理由**：A 与 W4「调用方无需轮询」和 N3「不做取消」自洽，且不引入新终态词（与 F06 验收 2 的封闭词表一致）；B 会带来「同一入口两种返回形态」的判定复杂度；C 会扩大终态词表并引入"取消/中断"语义（N3 明确不做）。

**影响面**：F04 验收 4、F07 边界、F06 验收 2；传输形态归架构 T-10。

## MI-06 · 终态「截断标记」的判定对象

**来源卡 / 验收项**: F06 验收 5；F08 验收 4；F10 验收 4
**demand 留白处**: W4（终态字段含「截断标记」）/ E4 / F-6、F-12

**问题**：既有实现里存在多处上限（增量输出行数封顶；过程记录条数封顶后置截断标记）。终态里的「截断标记」指哪一个？超限时标记为真还是另给状态？

**选项**：
- **A（推荐）**：标记 = 「本次调用交付的**输出 / 过程记录**是否被既有上限截断」——**任一**既有上限触顶即为真（具体数据来源留架构 T-02 / T-08）。
- **B**：仅指过程记录（转录）超上限。
- **C**：仅指输出文本被截断。

**推荐理由**：A 让 E4 的「逐项打勾」与 E10 的「零半成品」都能判定，且不锁定数据来源；B / C 会让另一类截断在终态里不可见，出现「内容少了但标记为假」的判定盲区。

**影响面**：F06 验收 5、F08 验收 4（增量与转录一致性对照）、F10 验收 4（超上限呈现）；与架构 T-08 的截断语义直接相关。

## MI-07 · roster 的起止时间口径

**来源卡 / 验收项**: F09 验收 2；F13 验收 2
**demand 留白处**: W5 / E7（字段名「起止时间」）

**问题**：E7 的 roster 行含「起止时间」，未定义「开始」与「结束」的取点，以及进行中调用如何呈现。

**选项**：
- **A（推荐）**：开始 = 调用**被受理**的时间；结束 = 进入**终态**的时间；进行中结束时间为空 / 未填写；结束不早于开始。
- **B**：结束时间在终态前显示「进行中」文案（占位而非空）。
- **C**：以单个「最近活动时间」替代起止两项（裁剪为一项，偏离 E7 的字段名）。

**推荐理由**：A 与 E7 的字段名一一对应、可机械核对，且不与 F05 验收 3 的「进行中明确状态」重复；C 会改变 E7 承诺的字段集。

**影响面**：F09 验收 2、F13 验收 2；roster 数据来源归 T-06。

## MI-08 · 转录的内容范围与超上限表现

**来源卡 / 验收项**: F10 验收 1、4；F08 验收 4
**demand 留白处**: W3（取转录）/ W4（转录本进程内可读、不持久）/ 差异 ⑩ / F-6

**问题**：转录（R3 等价物）应含哪些内容——是否包含「终态那次事件」？超过既有上限时应报错还是提示截断？

**选项**：
- **A（推荐）**：转录覆盖**从发起到终态**的过程记录（**含**终态那次事件）；超上限时**明确呈现「被截断」**（不报错、不静默少给）。
- **B**：转录只含中间步骤、**不含**终态（终态另由按 id 查询 / 投递给出）。
- **C**：超上限时报错（让调用方另想办法）。

**推荐理由**：A 与「把调用从头翻一遍」的用途一致，且与 F08 验收 4（流中增量与转录一致）自洽；C 会让长调用退化为不可读的错误路径，与「诚实标注、不静默不同」的口径相反；B 会造成「实时看得见终态、转录里翻不到」的不一致。

**影响面**：F10 验收 1 / 3 / 4、F08 验收 4；转录入口与截断呈现归架构 T-08。
