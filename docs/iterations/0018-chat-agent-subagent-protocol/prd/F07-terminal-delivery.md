# F07：终态异步投递

**功能 ID**: F07
**来源**: `demand.md` W4（投递侧）+ W3（按调用订阅能力）；裁决 P-6 / P-4；边界 N3 / N11 / N12 / N13；效果 E5
**迭代**: 0018-chat-agent-subagent-protocol
**技术锚点（引用 `demand.md` §3 只读实测，非本阶段决策）**: F-4（结果回流：增量入流不进库、结果落一行消息并入流，另有轮询兜底）、F-11（既有 13 条路由无 cancel / 无 steer / **无按调用订阅**；实时流只有 chat 作用域与全局上线事件流；无重连重放）、F-14（agent 先 ack 再并发执行）

## 用户价值

发起完就不用管了——结果自己会找上门，而且事件上带着调用 id，客户端不用写轮询，也不用在整条聊天流里捞自己那一次。

## 验收标准

1. **终态事件带调用 id**（W4 / E5 / D3）：调用结束时，订阅方能收到该调用的终态事件，事件中带**调用 id**（可与发起时拿到的 id 对应）。
   *判定*：先订阅、再发起 → 流中出现带该调用 id 的终态事件。
2. **无需轮询**（W4 / E5）：订阅路径下，调用方不发起任何查询也能拿到终态；投递不依赖调用方回头来取。
   *判定*：全程只订阅、不查询 → 仍能收到终态。
3. **可按调用订阅**（W3 / W5-D6）：订阅可针对**具体调用**（按调用 id），而不是只能收整个 chat 的流。
   *判定*：两次调用并发进行，只订阅其中一次 → 只收到该调用的事件，另一次的不混入。
4. **投递不被既有回流路径吞掉**（W4 / N18）：终态在订阅面可稳定取得，不依赖「恰好没丢」的兜底路径；既有回流路径的语义不变（→ F14 验收 1）。
   *判定*：连续发起多次调用 → 每次的终态事件均可达（无静默丢失）。

## 边界（不包含）

- 不含终态字段内容（→ F06）、不含过程可见（→ F08）。
- **不重复断言阻塞模式的返回时点**（→ F04 验收 4）；也不重复定义阻塞取终态的传输形态（→ T-10）。
- **不做取消 / 终止 / steer**（N3，差异 ⑯⑮）：投递只向前，不提供回头干预的能力。
- **不做远端同会话渲染一致**（N13，差异 ⑰）。
- **不做工具级进度**（N12，差异 ⑬）。
- **不承诺跨重启重放**（N11，差异 ⑩）：重启后无历史事件可补投。
- 不含控制台呈现（→ F13）。

## 架构（阶段 3 已填；真源 = `architecture.md`）

> 本段只填架构维度；产品维度逐字未动。

- **T-05 调用级事件流的路径与 schema**：**新增两条 SSE 路由，不扩展既有 `/api/stream`**（改既有事件面会撞 F14 验收 1）——`GET /api/calls/stream?chat_id=<id>`（**对话作用域**：可「先订阅、再发起」，验收 1 的载体）+ `GET /api/calls/:call_id/stream`（**按调用**：验收 3 的载体）。事件三类封闭：`call_state` / `call_update` / `call_result`；`call_result` 的 `data` = `chat_id` + 信封逐字段**平铺**（不嵌套）⇒ 事件中带 `call_id` 可机械核对。终态发布**单一发布点** `publishCallResult`，投递路径与**既有对账兜底**（`reconcileTask`）都走它 ⇒ 验收 4 的「无静默丢失」由构造保证。键空间加前缀（`chat:` / `call:` / `chat-calls:`）结构性防串键。
- **T-10 阻塞取终态的传输形态**：与 F04 共用 —— 响应挂起至终态、不设上限、断连不终止（见 `architecture.md` §2.4）。
- **T-12 验证组织形态**：落 `oamp/test/call-protocol.test.js` 组 E（带 `call_id` 的终态帧 / 只订阅不查询 / 两次并发只收其一 / 连续多次无丢失，含「投递被丢弃、由对账路径补投」场景）。
