# F16：新增调用面登记义务与工程锁继承**〔保证项，非新增功能〕**

**功能 ID**: F16
**来源**: `demand.md` W7（工程侧）/ N19 + 硬约束继承（0016 三条漂移锁 + 零依赖锁）+ 效果 E9（锁侧）。**来源条款为 W（工程侧）+ N + E 项**——本卡不引入新能力，只把「新增面必须长进索引与文档、且不引入新依赖」变成可独立验收的载体（体例先例：0017 F10、0016 F06「漂移锁」）
**迭代**: 0018-chat-agent-subagent-protocol
**技术锚点（引用 `demand.md` §3 只读实测，非本阶段决策）**: F-1（web 层与声明式路由表）、F-11（既有 13 条路由与两个实时流作用域——新增面在此基础上登记）

## 用户价值

新接口不会变成「文档里查不到的黑接口」——它自己长到文档页、调试台和给 AI 看的索引里；漏登记当场测试变红，不靠人记得。

## 验收标准

1. **新增路由 / 事件进声明式路由表**（W7）：本次新增的调用面路由与事件在既有声明式路由表中登记，元数据齐备。
   *判定*：读路由表 → 新路由 / 事件在列且元数据完整（漂移锁一通过）。
2. **索引文件同步**（W7）：给 AI / 客户端用的索引文件与路由面一致（逐字节）。
   *判定*：跑既有漂移锁用例 → 绿；人工对照索引与路由面 → 一致。
3. **契约文档路径级双向覆盖**（W7）：契约文档对新路由 / 事件形成路径级双向覆盖。
   *判定*：跑既有漂移锁用例 → 绿；文档中每条新路径可被检索到（协同 F02 验收 2 的示例核对）。
4. **零新依赖**（N19）：不新增第三方依赖。
   *判定*：依赖清单无新增 + 既有零依赖断言绿。
5. **新增面不外露**（N19）：新增调用面仍只在本机监听范围内，不扩大对外暴露面。
   *判定*：检查监听范围，与既有边界一致。

## 边界（不包含）

- 不含既有面回归判定（→ F14）、不含不做项半成品判定（→ F15）。
- 不含文档可用性与示例内容（→ F02）、不含对照表与差异清单内容（→ F01）。
- 不含既有漂移锁用例的改写（既有断言保持；新增断言另落，见 T-12）。
- **不做 `oamp/` 之外的仓库改动**（N20）。
- **不含 0017 遗留的路由登记元数据缺项（D-2）的修复**（主 agent 裁定 C-3：不纳入本迭代）：本卡只覆盖本次**新增**调用面的登记义务，既有路由的元数据不因本迭代被补齐或改动。
- 不含鉴权 / 多用户（N19）。

## 架构（阶段 3 已填；真源 = `architecture.md`）

> 本段只填架构维度；产品维度逐字未动。

- **T-17 登记元数据形态与索引重生成**：新路由一律进既有 `createApiRoutes` 表（末位追加，**顺序 = 匹配优先级**，见 §2.1 的顺序约束），元数据 = 既有 **8 字段**（`method` / `path` / `summary` / `params` / `response` / `errors` / `kind` / `docLink`）+ `params` 的 **5 字段**（`name` / `in` / `type` / `required` / `desc`，可选 `enum`）；`errors[]` 取值 ⊆ 既有 `ERR_CODE` 值集合（**零新错误码**）；`kind ∈ {json, sse}`；**事件登记形态 = SSE 路由的 `response` 字段逐名列出三类事件**（既有体例）+ `API.md` §4.4 事件表；`docLink` 指向新章节锚点（`API.md#314-post-apicalls` … `#319-get-apicallscall_id`）。索引快照重生成 = **`node oamp/scripts/gen-llms-txt.mjs`**（纯函数 `renderLlmsTxt(projectRoutes(createApiRoutes({})))` 的输出写回 `oamp/llms.txt`，漂移锁②逐字节）。文档侧：`API.md` 中每个 `` `METHOD /api/…` `` 反引号签名必须在登记表内（漂移锁③路径级双向覆盖）。
