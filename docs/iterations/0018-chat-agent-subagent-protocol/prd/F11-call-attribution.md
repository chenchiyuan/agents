## 用户价值

hub 里不会出现「不属于任何对话、任何项目」的调用——调用和对话、项目是连着的，不会开出一条飘在外面的旁路。

## 验收标准

1. **调用必须归属 chat**（W6 / E11）：调用请求带 chat 归属；归属的 chat 是该调用的发起容器与消息历史载体。
   *判定*：带归属发起 → 成功，且该调用与所归属的 chat 关联可核对。
2. **无归属调用被拒绝**〔`[user_confirmed MI-04]`〕（E11；用户裁决 = 未提供与空值一律拒绝）：不带 chat 归属（未提供或提供空值）的调用 → 被拒绝（4xx，带明确错误码），**不产生任何调用**（两种形态**同判**；不设「服务端兜底到某个默认 chat」）。
   *判定*：不带 chat 归属直接调调用面 → 4xx；随后列 roster → 无新增行；带空值归属同样 → 4xx、同样无新增行。
3. **继承项目归属**（W6 / P-9）：归属 chat 所属的项目随之成为该调用的项目上下文；调用不绕过项目层。
   *判定*：在某项目下的 chat 发起调用 → 派发内容中可见该项目上下文（承接既有项目上下文透传行为，→ F14 验收 1）。
4. **项目归属与共享说明并存不合并**（W6 / M-11）：项目（环境归属）与本次调用的共享说明（`context`）保持为两个独立项——提供其一时另一项不被覆盖，未提供时也不被伪造。
   *判定*：同时提供两项发起 → 两者都保留且语义不混；只提供其一 → 另一项不被替代。

## 边界（不包含）

- 不含归属校验以外的入参（→ F04）、不含身份规则（→ F12）。
- **不引入无归属的裸调用路径**（W6）：不存在「不属于任何对话 / 项目」的调用形态。
- **不合并项目归属与本次调用共享说明**（M-11）。
- **不处理 0017 的收尾**（N21 / G-2）：0017 的项目层能力按既有基线使用，本迭代不补做、不改写、不验收它。
- 不含鉴权与多用户归属（N19）。
- 不含归属信息的呈现形态（→ T-14）。

## 架构（阶段 3 已填；真源 = `architecture.md`）

> 本段只填架构维度；产品维度逐字未动。

- **T-14 归属的传参形态与错误码形态**：归属 = 请求体 **`chat_id`（必填）**；**未提供 / `null` / `''` / 非字符串一律 400 INVALID_PARAM**（MI-04，两种形态同判、不兜底默认 chat）；`chat_id` 指向不存在的对话 → 同样 400 INVALID_PARAM（体例同既有「项目不存在 → 400」）。**零新错误码**（既有 `ERR_CODE` 五码封闭，MI-01/MI-04）。**判定先于任何写入**（不落 `in` 行、不建任务、不派发）⇒ 验收 2 的「不产生任何调用」由构造保证。归属继承 = 派发时取既有 `db.projectByChat(chatId)` 注入 payload `project`（与既有链路逐字同源，验收 3）；`project`（环境归属）与 `context`（本次调用共享说明）在装配处是**两个独立区块、不合并**（验收 4）。
- **T-01 调用入口与归属参数**：`POST /api/calls`，`chat_id` 在请求体（与既有 `POST /api/messages` 同位置同语义）。见 §2.1 / §2.3。
- **T-12 归属校验的验证组织形态**：落 `oamp/test/call-protocol.test.js` 组 I（带归属成功且经 `GET /api/chats/:id` 的 `messages[].meta.task_id` 关联可核对 / 未提供与空值均 400 且 roster 无新增行 / 项目继承 / `project` 与 `context` 并存不合并）。
