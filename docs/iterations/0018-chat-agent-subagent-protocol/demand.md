### 4.2 逻辑闭环 —— why 能否推出 what

**Why（三条）**：

1. **hub 已经能"发一条消息给 agent"，但客户端拿不到"一次调用"**：发起后只有 `{chat_id, task_id, message_id, warning}`（F-2），结果只能靠 chat 作用域 SSE 或轮询，`task.update` 不入库（F-4/F-7）。
2. **原生 sub agent 的体验来自三面契约**（调用入参、结构化结果、可观测面），不是来自某一条路由（侦察 §B）。
3. **hub 的展示面今天只到 chat 粒度**：无调用级 roster、无按调用的流、无调用级帧订阅（F-8/F-11）；增量输出 200 行封顶（F-12）。

#### 6.1-A P-2 裁决专项：agent 身份规则（**用户原话级结论**）

**用户原话（`user_confirmed`，逐字）**：

> 同hub和agent之前的约定， 同chat下，同名agent是一个agent，共享上下文。 不同chat下agent是不同agent

**落定结论（W8）**：

1. **agent 身份 = `(chat, agent 名)` 二元组**；
2. **同 chat 且同名** ⇒ **同一个 agent，共享上下文**；
3. **不同 chat** ⇒ **不同的 agent**（即使 agent 名相同）。
4. **与既有 `omp-daemon` 上下文池键的关系（`侦察` F-10）**：既有上下文池的键正是 **`(chat_id, agent_id)`**——同键 FIFO 串行（队列上限 8）、异键完全并发、全局上限 8 按 LRU。⇒ **既有实现已符合用户表述的身份规则**，本迭代**不改上下文池的键与并发/串行语义**（沿 0017 N9 / 本文件 N16）；该规则因此是"现状被确认为契约"，不是需要新造的机制。
5. **与寻址的关系**：配合 P-5 的按 role 寻址，"agent 名"在本仓库的对应物 = **role 名**（实例名公式 `pb-<role>` 一一对应，F-9）；即调用面在**指定 chat + agent 名**的坐标下定址到一个 chat 作用域的 agent 身份。
6. **与生命周期差异的关系**：进程载体仍是**常驻 agent 实例**（一个实例可承载多个 chat 作用域的 agent 身份，由上下文池分键）；harness 的"每次派发临时 agent"仍在**差异 ①** 登记，不因 P-2 的身份规则而消失。

7. **`one_shot` 路径的地位（Q-1 裁决 ①，`user_confirmed`，第三轮）**：既有 `one_shot:true` 路径（F-17：`web.js:697-701` → `executor:'omp'` → `omp -p --no-session`，**每次调用独立进程、不共享上下文**）**保留为「调用方主动放弃上下文延续」的显式例外**，并在 `oamp/API.md` 差异清单登记为**差异 ⑲**。⇒ W8 的默认语义（同 chat 同名共享上下文）与 `one_shot` 的例外地位**不再冲突**：前者是默认路径（`omp-daemon`）的身份规则，后者是调用方显式选择的、主动放弃该延续的例外路径。用户未选择 ②（新调用面不提供 `one_shot`）与 ③（彻底废除 `one_shot`）。

## 5. 为什么这么做

- **为什么必须先把参照契约钉死**（W1/P-1）：用户说"符合 sub agent 协议"，但仓库里**不存在**这份协议的定义（F-15），且仓内有两份互不相同的候选（侦察 §B.6）。不钉死参照物，"符合"就是无法判定的句子。
- **为什么等价只能是"协议面等价"**（W2~W5/P-2）：原生 sub agent 的生命周期是"每次派发临时 agent"，而用户说的是"chat 中的 agent"，且 0015 已拍板 hub 不启停 agent。把生命周期也做成等价 = 把 hub 改成进程管理器 = 推翻一条用户已拍的边界。⇒ 差异 ① 登记。
- **为什么 agent 身份是 `(chat, agent 名)`**（W8/P-2 原文）：这是用户给出的身份定义，且**与既有上下文池键 `(chat_id, agent_id)` 完全一致**（F-10）——它把"多轮记忆在哪一层隔离"从隐含实现细节升格为**契约**：同一 chat 同一角色 = 同一条上下文会话（可延续）；换 chat = 换 agent（隔离）。⇒ 本迭代**零改动**地把它确认为行为（N16），并把 E8 作为它的裸判定。
- **为什么响应面必须结构化、且必须诚实标注不可得字段**（W4/P-6）：客户端要"没差别"，最直接的判据是"能不能像读 subagent 结果一样读它"；而 hub 今天确实产不出 usage/tokens（F-13）。写假字段或干脆不写，都会让"等价"无法验收。
- **为什么展示面限定在"调用级"**（W5/P-7）：用户点名"展示"，而 hub 现状只有 chat 粒度；工具级详情需要 agent 侧产出新事件，是 `[UNVERIFIED]` 能力，不能作为承诺。
- **为什么调用身份复用 `task_id` 而不是新造实体**（W3/P-4）：`task_id` 已在响应里（F-2），Router 任务表已维护状态与增量（F-6），HTTP 面只是刻意没暴露（F-7）。新造实体 = 制造第二个镜像真源；而解除 0015 N5 的范围被用户**限定在"按调用 id 读自己发起的调用"**，避免顺手长成编排面（N17）。
- **为什么保持 chat 归属**（W6/P-9）：0017 刚把"对话必属项目"收敛成强绑；新调用面若能绕过 chat，就等于开第二条无归属路径。
- **为什么不做取消/isolated/effort/token**（N3~N12）：都不参与"发起调用 → 拿到结构化结果 → 看到进度"这条最小链路；各自带出独立工程面。**最小边界优于完整边界**。
