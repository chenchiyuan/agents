# 需求合同：workflow-pb history 记录能力

**已收敛。** 草稿 v0 由 demand 角色产出，7 项 `model_inferred` 待确认项已由主 agent 逐条呈现给用户，用户于 2026-09-07 全部确认为推荐选项（A）。本文件为收敛后的最终版，全部结论均为 `user_confirmed`。

## 澄清依据

1. **核心诉求**（`user_confirmed`，用户原始表述）：workflow-pb 支持一个 `history` 选项，默认开启；开启时记录主 agent 的"对话、派发、决策"历史，逐条追加写入本次迭代的 `history.md` 文件，用于后续复盘和 debug 工作流执行过程。

2. **记录范围**（`user_confirmed`）：分三类事件独立记录——①主 agent 发起派发（角色名/阶段/任务摘要）、②收到执行角色报告（报告摘要）、③主 agent 的调度决策节点（阶段推进核查结果、Gate 暂停与用户确认结果、阶段 5 并发槛位释放/爬升触发、PR 失败或阻塞判定）。不记录主 agent 与用户之间除决策结果外的日常说明性对话——完整对话已由会话本身承载，`history.md` 定位是结构化事件流，不是会话记录的重复副本。

3. **存储形式**（`user_confirmed`，用户方案雏形）：单文件、按迭代归档（`docs/iterations/{迭代ID}/history.md`），逐条追加写入，不是流程结束后一次性生成的汇总文档。

4. **记录粒度**（`user_confirmed`）：只记录派发的可变字段摘要（角色名、阶段、任务、输入输出路径、完成定义要点）和收到报告的摘要，不把 v0.6.0 全文注入机制里的角色定义原文写入 `history.md`——角色定义是静态文本，已受 git 版本控制，逐条复制会让文件体积迅速膨胀且高度冗余。

5. **维护责任方与并发顺序**（`user_confirmed`）：`history.md` 由主 agent 自己直接维护（类比 `status.md` 现有惯例），不派发给执行角色代写。阶段 5 同一轮响应内连续发起的多个并发派发，仍按发起顺序各自独立记录一条，不合并、不因"同一轮"而省略。

6. **与 `status.md` 的边界**（`user_confirmed`）：两者并存、职责不同——`status.md` 是当前阶段状态快照，`history.md` 是按时间顺序的事件流水账。本次不改变 `status.md` 现有格式和维护时机。

7. **关闭机制的实现范围**（`user_confirmed`）：本次只做单迭代级别的开关状态字段（默认开启），不做跨迭代生效的全局配置文件。若该字段被显式设为"关闭"，主 agent 读到后跳过记录。

8. **是否要求其他角色消费 `history.md`**（`user_confirmed`）：不建立 `verifier`、`progress-observer` 等角色读取或校验 `history.md` 内容的自动化依赖，定位为人工复盘/debug 用的产物。

9. **期望效果的三个具体维度**（`user_confirmed`）：用户明确"理论上，我通过 history.md 可以知道此次迭代过程的工作详情、派发方式、决策方法"——三个独立的可验证信号，不是笼统的"记录得越多越好"。

10. **用途边界**（`user_confirmed`）：明确用于"复盘"和"debug 流程"，面向人工事后阅读排查。

11. **价值定位补充**（`user_confirmed`）：`history.md` 的价值不仅是"复盘方便"，更是"即使会话被自动摘要压缩，仍保留不丢失的结构化调度记录"——这是"为什么需要专门文件"而不是"回看会话记录就够"的核心原因。

## 需求结论

### 1. 目标与价值

让 workflow-pb 在执行迭代过程中，把主 agent 的派发通信和调度决策，按时间顺序逐条追加记录到该迭代专属的 `history.md` 文件中，使得事后（复盘、debug）不依赖回看原始会话记录，就能重建"这次迭代做了什么派发、为什么这么派发、做了哪些调度决策"。这一价值在会话被摘要压缩后更加明显——`history.md` 作为独立于会话上下文的落盘产物，不会因摘要而丢失细节。

### 2. 做什么

- **新增 `history.md` 产物**，位于 `docs/iterations/{迭代ID}/history.md`，纳入 workflow-pb 现有"文档路径协议"。
- **默认开启**：迭代启动时默认记录，无需额外操作。
- **单迭代级开关状态字段**：在该迭代 `status.md` 中声明 `history` 选项的开启/关闭状态，默认开启；显式设为关闭时，主 agent 跳过记录，不产生/不追加 `history.md`。
- **逐条追加写入**，不是流程结束后一次性汇总生成。
- **记录三类事件**：
  - 每次主 agent 向执行角色发起派发：角色名、当前迭代 ID、当前阶段、任务一句话（不含角色定义全文）
  - 每次收到执行角色报告：报告摘要（沿用各角色"报告契约"已定义的字段结构）
  - 主 agent 做出的调度决策节点：阶段推进核查结果、Gate 暂停触发与用户确认结果、阶段 5 并发槛位释放/爬升触发、PR 失败或阻塞判定
- **并发场景下按发起顺序各自独立记录**：阶段 5 同一轮响应内连续发起的多个并发派发，仍按发起顺序各自独立追加一条记录。
- **由主 agent 自己直接维护**，不派发给执行角色代写。

### 3. 不做什么（最小边界）

- **不记录派发 brief 中角色定义的全文注入内容**。理由：角色文件是静态文本，已受 git 版本控制，逐条复制会让 `history.md` 体积迅速膨胀且大部分内容重复，反而降低可读性。
- **不替代或重写 `status.md` 的既有格式与维护时机**。理由：`status.md` 是"当前状态快照"，`history.md` 是"按时间顺序的事件流水账"，职责不同，本次不合并、不重复定义。
- **不建立其他角色（`verifier`、`progress-observer` 等）读取或校验 `history.md` 内容的自动化依赖**。理由：用户已确认用途是人工复盘/debug，不是自动化验证输入；强行建立消费依赖是本次范围之外的扩展。
- **不实现跨迭代持久生效的全局配置文件来控制默认开关**。理由：用户只提到"默认开启"，未提出"需要跨迭代统一配置"的诉求；引入独立配置文件会增加维护面，YAGNI。
- **不记录主 agent 与用户之间除决策结果之外的日常说明性文字**。理由：完整对话本身已由会话本身承载，`history.md` 定位是"派发与决策"的结构化事件流，不是会话记录的重复副本。

### 4. 大概怎么做

（仅记录用户已给出或已确认的机制轮廓，不做架构阶段的技术选型判断，具体字段结构、时间戳格式、SKILL.md 落点等留给阶段 2/3）

- 单文件、按迭代归档：`docs/iterations/{迭代ID}/history.md`。
- 每条记录追加写入，不做整体重写。
- 开关状态字段声明在该迭代 `status.md` 中，默认开启。
- 具体的字段结构、时间戳格式、与 `SKILL.md` 现有"§ status.md 更新时机"章节的对应关系（是否需要新增"§ history.md 更新时机"一节），留给架构/PR 规划阶段设计——本合同不锁定实现细节，只锁定"逐条追加、按事件类型分类、可读取重建工作详情/派发方式/决策方法"这三项行为契约。

### 5. 达到什么效果（裸判定：不问作者也能判断真假）

- 任选一个走过 workflow-pb 的历史迭代（或本次迭代完成后），迭代目录下存在 `history.md` 文件，且能观察到该文件在迭代进行过程中被多次追加写入（可用 git 记录或文件多次修改时间戳核实），而不是流程结束后一次性生成。
- 读取 `history.md`，能看到每一次角色派发的记录（至少含角色名、阶段、任务），且这些记录出现的先后顺序与该迭代实际执行顺序一致（可与 `status.md` 历史记录或 git 提交时间交叉核对）。
- 读取 `history.md` 中的调度决策类条目（阶段推进/并发槛位变化/Gate 确认结果/失败判定），每条至少包含"决策内容"和"触发依据"两个字段，不需要询问执行者即可判断该决策为何在那个时间点发生。
- 关闭 `history` 选项后，该迭代目录下不产生 `history.md`，或该文件保持为空/不追加。

### 6. 为什么这么做

- 用户已确认目的是复盘与 debug 工作流执行过程。
- workflow-pb 的执行发生在可能被自动摘要压缩的会话上下文中，`history.md` 作为独立于会话的落盘产物，能在摘要发生后仍保留关键调度记录，这是"为什么需要专门文件"而不是"回看会话记录就够"的核心原因。
