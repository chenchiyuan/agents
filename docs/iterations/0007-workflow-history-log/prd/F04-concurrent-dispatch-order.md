# F04 — 并发派发的顺序保真记录

**功能 ID**: F04
**来源**: `demand.md` §2「做什么」第 6 条，§5「达到什么效果」第 2 条
**迭代**: 0007-workflow-history-log

---

## 用户价值

阶段 5 依赖解锁式并发调度下，同一轮响应内可能连续发起多个并发派发；事后复盘时仍需要能还原这些派发真实的发起先后顺序，不能因为它们"同一轮触发"而被合并成一条记录或丢失顺序信息。

---

## 验收标准

1. 阶段 5 同一轮响应内连续发起的多个并发派发，在 `history.md` 中各自对应一条独立的派发记录，不合并为一条。
2. 这些记录在 `history.md` 中出现的先后顺序，与主 agent 实际发起这些派发的顺序一致（即使这些派发在执行层面是并发进行的，记录层面的顺序反映的是"发起顺序"，不是"完成顺序"）。
3. 读取 `history.md` 中任意一段角色派发记录，其出现的先后顺序与该迭代实际执行顺序一致——可与 `status.md` 历史记录或 git 提交时间交叉核对。
4. 补位派发（某个槛位释放后触发的新派发）同样各自独立记录一条，不与触发它的槛位释放决策条目合并为一条。

---

## 边界（不包含）

- 不包含保证顺序的具体写入机制实现（是否需要序号字段、是否需要同步写入避免多条记录交错写入导致顺序错乱），已在下方「架构维度」标注留白。
- 不包含并发派发本身的调度算法（起始并发数、爬升公式、硬上限）——这些是 `0005-pr-concurrent-execution` 迭代已落地的既有机制，本卡只负责这些既有调度事件如何被记录，不改变调度本身。
- 不包含对"发起顺序"和"完成顺序"何者更重要的判断——demand.md 已明确要求按发起顺序记录，本卡不引入替代判定标准。

---

## 架构维度

**不引入序号字段，不引入同步锁**。顺序保真直接依赖一个技术事实：并发发生在"子 agent 执行"层面，不发生在"history.md 写入"层面——主 agent 写 history.md 永远是单线程顺序完成的动作，即使随后在同一轮 assistant 响应中连续发起多个并发 `Agent()` 工具调用。因此文件中记录出现的物理先后顺序，天然等于主 agent 实际发起这些派发的顺序，读者从上到下阅读即可还原发起顺序。

**具体操作约定**：阶段 5 同一轮响应内准备并发发起 N 个 `Agent()` 调用前，主 agent 依次先追加 N 条「派发」记录（记录顺序 = 即将发起调用的顺序），再发起这 N 个并发调用。补位派发同理：先记录一条「调度决策·槛位释放」条目，再依次记录每个补位派发的「派发」条目——两者相邻但独立，不合并（对应本卡验收标准 4）。

**为什么不用序号字段**：比较过引入递增序号字段（如 `#0007-015`）的方案，否决理由：写入本身已经是顺序的，物理顺序已天然满足全部验收标准，序号字段不能多解决任何问题（奥卡姆剃刀检验：不引入它，没有任何验收标准无法满足）。

详见 `architecture.md` §决策 D5。
