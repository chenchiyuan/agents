# F01 — history.md 产物与逐条追加写入

**功能 ID**: F01
**来源**: `demand.md` §2「做什么」第 1/4/7 条，§6「为什么这么做」
**迭代**: 0007-workflow-history-log

---

## 用户价值

把主 agent 的调度记录以独立文件落盘，不依赖回看原始会话记录就能重建"这次迭代做了什么"；这份价值在会话被自动摘要压缩后更明显——`history.md` 作为独立于会话上下文的产物，不会因摘要而丢失细节。

---

## 验收标准

1. 该迭代 `history` 开关处于开启状态时（默认即开启，见 F02），`docs/iterations/{迭代ID}/history.md` 文件存在。
2. 该文件在迭代进行过程中被多次追加写入，而不是流程结束后一次性生成——可用文件的多次修改时间戳或 git 提交记录核实存在至少两次独立的写入时点，且这些写入时点分布在迭代执行过程中（不是集中在流程结束前的同一时刻）。
3. 写入方式是追加，不是整体重写——已写入的历史条目在后续写入后原样保留，不被覆盖或删除。
4. `history.md` 由主 agent 自己直接维护，不派发给任何执行角色代写——不出现由执行角色产出、主 agent 转存的写入路径。

---

## 边界（不包含）

- 不包含具体的字段结构、时间戳格式（已在下方「架构维度」标注留白，见架构待填 AR-01）。
- 不记录派发 brief 中角色定义的全文注入内容——角色文件是静态文本，已受 git 版本控制，逐条复制会让文件体积迅速膨胀且高度冗余。
- 不替代或重写 `status.md` 的既有格式与维护时机——`status.md` 是当前阶段状态快照，`history.md` 是按时间顺序的事件流水账，两者并存、职责不同，本次不合并。
- 不建立其他角色（`verifier`、`progress-observer` 等）读取或校验 `history.md` 内容的自动化依赖——定位为人工复盘/debug 用的产物。

---

## 架构维度

**落盘位置与创建时机**：`docs/iterations/{迭代ID}/history.md`，纳入「文档路径协议」现有目录树，与 `status.md` 同级。工作流启动时（`status.md` 创建之后），若该迭代 `history` 开关为开启，立即创建空 `history.md`（仅含标题行），不等首次事件发生才惰性创建——文件是否存在即可作为开关状态的可观察信号。

**独立成节**：`workflow-pb.md` 新增 `## 历史记录协议（history.md）` 一节，与现有 `## 状态追踪协议（status.md）` 平级并列，不并入 status.md 章节内部；SKILL.md 对应新增 `## § history.md 更新时机` 一节，与 `## § status.md 更新时机` 平级并列。理由：两个文件职责不同，格式定义混在一处会造成"读者无法一眼确认规则管哪个文件"的含糊。

**记录条目格式与时间戳**：见 F03 架构维度（三类事件共用同一套条目格式）。时间戳精度到秒级（`YYYY-MM-DD HH:MM:SS`），理由见 F04 架构维度"为什么到秒级"。

详见 `architecture.md` §决策 D1、D2。
