# F08 · 测试协议 · 约束可独立裁决（每条附判断方式）

**来源**：demand.md §3「大概怎么做」（协议写法：每条约束后附 `判断方式：…`）；§4「达到什么效果」第 3、4 条；验证方法 V-4；仓库一手先例 `roles/workflow-pb/data/scm-protocol.md`

## 用户价值

一个没参与讨论的人（或下一个迭代的 agent）读协议就能判断"某次派发是否违反运行粒度 / 归属 / 清理规则"——不问作者、不查背景、不靠临场解释；协议因此在参与讨论的人换掉之后仍然生效。

## 验收标准

1. 协议内每条约束后都跟一段 `判断方式：…`；逐条点数无遗漏（V-4）。
2. 判断方式的形态是"可事后核查的动作"（查某文件是否存在、查 git 历史或落盘记录、查执行报告的哪一项），不依赖 hook / CI / 工具链的自动强制——与 `roles/workflow-pb/data/scm-protocol.md` 每条规则均带判断方式的既有写法同构。
3. 判断方式覆盖 F03~F07 定义的全部约束组（运行粒度 / 归属与清理 / 阶段 5 零测试判据 / 阶段 6 取证口径 / 保留集重建触发），逐组可定位。
4. 新读者（无讨论背景）仅凭协议文本即可判定一次具体派发是否违规，判定过程不需要向作者求证（§4 第 4 条）。
5. 协议文本在仓库内的位置可被指认并可被读到（§4 第 3 条"存在一份测试协议文件"）；具体落点文件由承载形态决定，见边界。

## 边界（不包含）

- **协议承载形态（写在哪个文件）不在本卡内**：demand.md §7 明示 `user_deferred`（"不重要，之后撰写协议时再定"），本阶段不判定，标注 `[架构待填]` 交阶段 3；本卡只约束协议内容及其可裁决性。
- 不新增任何约束条目本身——约束内容归 F03~F07。
- 不引入 CI / git hook / 第三方依赖（§2）；判断方式是人工可执行的事后核查，不是自动门禁。
- 不新增 test-keeper 角色（Q10）。

## 架构维度

**协议承载形态（阶段 3 定稿 · 决策 D-1，L1）**：协议文本落在 `roles/workflow-pb/data/formats.md` **末尾新增**的 `## 测试协议（Test Protocol）` 一节。本卡不单独占用协议节位置，它定义的是整节的**可裁决性形态**：

- 节内导言显式声明"本协议的约束仅 T1~T5 各条正文"（使 V-4 的逐条点数不含导言）；
- T1~T5 每条紧随一行 `判断方式：…`，全部为人工可执行的事后核查动作，不依赖 hook / CI / 工具链强制（与 `roles/workflow-pb/data/scm-protocol.md` 逐条同构）；
- 节标题唯一且可检索：`grep -n "^## 测试协议" roles/workflow-pb/data/formats.md` 即"位置可被指认"。
- **本卡验收标准 5 的读数**：「协议文本在仓库内的位置可被指认并可被读到」判据 = 上述检索命中；`demand.md` §4 第 3 条的"存在一份测试协议文件"读作"存在一份测试协议（文本）"——§7 明示承载形态后置，故 §4 不可能同时锁定"必须是独立文件"。
- 择取理由（不新增文件、不新增主文件索引段、零引用方同步面、不需要阶段 4 门禁例外）与备选方案对比见 `docs/iterations/0026-test-protocol-and-suite-reset/architecture.md` §3 D-1。
