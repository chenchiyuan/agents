# F07 · 测试协议 · 保留集重建触发条件

**来源**：demand.md 做什么 W-3 第 5 条；结论 Q14；§3「大概怎么做」（下一次迭代阶段 4 出现第一个跨迭代契约时，由主 agent 在该迭代阶段 5 简报中显式声明保留集文件面）

## 用户价值

空集状态有明确出口——不是"以后想起来再说"，而是一个可判定的时点：一旦下一次迭代出现跨迭代契约，回归保护就被重新拉起，不会永久缺席。

## 验收标准

1. 协议中写死触发条件：下一次迭代在阶段 4 出现第一个"跨迭代契约"时触发保留集重建；且"跨迭代契约"在协议内可判别（有定义或明确判据），不是靠感觉判断——只写"出现跨迭代契约时"而不给判据，本卡不通过。
2. 协议中明确触发后的动作：由主 agent 在该迭代的阶段 5 简报中显式声明保留集文件面——复用 `workflow-pb.md` 已有的"简报显式覆盖值"机制（该文件阶段 5 派发段），不新增组件。
3. 协议中明确触发责任方是主 agent，不依赖新增角色（Q10：test-keeper 本次先不做）。
4. 保留集粒度的判据是必要性（跨迭代契约意义），**不是**物理指标（文件行数上限、运行时长上限）——Q3 明确拒绝物理指标作约束。
5. 该约束带 `判断方式：…`（形态见 [F08](F08-protocol-judgeable-constraints.md)）：能判定"某次迭代是否已满足触发条件"以及"触发后是否完成了简报声明"。

## 边界（不包含）

- 不重建保留集本身：本迭代零测试交付（Q8 / Q14），本卡只定义触发条件。
- 不定义"现在应当保留哪些用例"——§6 被否决路径 1（按跨迭代契约意义筛选保留）不得回填。
- 不新增 test-keeper 角色（Q10）。
- 不定义协议承载形态（§7 `user_deferred`，见 F08 边界）。

## 架构维度

**协议承载形态（阶段 3 定稿 · 决策 D-1，L1）**：本卡定义的规则文本落在 `roles/workflow-pb/data/formats.md` **末尾新增**的 `## 测试协议（Test Protocol）` 一节，即其中的**规则 T5（保留集重建触发条件）**——条款正文后紧随一行 `判断方式：…`。

- 触发后的"简报显式声明保留集文件面"路径复用 `workflow-pb.md` 既有的「简报显式覆盖值优先」机制：该节字段列表以「**至少**包含以下字段」起头，附加字段不违反该节，因此**不需要改主文件**。
- 不新增文件、不新增主文件的索引段、不改任何角色文件（不新增 test-keeper）。
- 择取理由、备选方案对比与规则 T5 的结构规格见 `docs/iterations/0026-test-protocol-and-suite-reset/architecture.md` §3 D-1/§3 D-6、§5。
