# F03 · 测试协议 · 运行粒度规则

**来源**：demand.md 做什么 W-3 第 1 条；结论 Q2；§5「为什么」第 3 行（382 次 bash 中 277 次用默认 timeout）

## 用户价值

每次 PR 派发不再重付一次全量套件的固定成本（60s 前台台阶 + 后台化 + 至少一个额外模型回合 + `sleep` 轮询粒度），执行角色也不需要临场发明"这次跑多少"——运行粒度有可判定的默认值，不是每个 agent 各自发挥。

## 验收标准

1. 协议中有一条运行粒度约束，明确"PR 内只运行本 PR 生成的用例"，并把默认值写到可判定的程度：什么算"本 PR 生成的用例"（按文件面或用例面界定）、在什么时点跑、由谁跑。
2. 协议中明确"全量运行只在迭代交付时执行"，并指明触发点与执行者。
3. 该约束带 `判断方式：…`（形态要求见 [F08](F08-protocol-judgeable-constraints.md)）：事后拿一次具体派发，能逐条判定它是否违反运行粒度，不需要询问作者或补背景。
4. 约束以文字规则形式给出默认值，不把"本 PR 用例的范围"留给执行角色自行解释。

## 边界（不包含）

- 不以物理指标（单文件行数、运行时长上限）作为运行粒度的约束——Q3 明确拒绝物理指标、改用必要性判据（必要性判据的落点在 F07）。
- 不定义测试用例的归属与清理（→ F04）。
- 不定义零测试态下的验收判定（→ F05 / F06）。
- 不定义协议承载形态（demand.md §7 `user_deferred`，见 F08 边界）。
