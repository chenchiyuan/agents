# F04 · 测试协议 · 测试归属与一次性脚本处置规则

**来源**：demand.md 做什么 W-3 第 2、3 条；结论 Q4 / Q5（"合成同一条"）；§2「不新增任何测试用例」；§5「为什么」第 4 行（28 处 `/tmp/*.mjs` 一次性脚本零沉淀）

## 用户价值

测试用例与一次性验收脚本不再回流成仓库资产——派发过程中产生的验证手段不会在仓库里堆积成"看起来是资产、实际没人维护"的东西，也不需要下一轮的人去猜哪些还能用；一次性脚本被当作过程产物而不是交付物对待。

## 验收标准

1. 协议中有一条归属约束，明确"PR 默认不落测试用例"：PR 的交付物不含测试文件；例外情形若存在，须写明由谁、在何处显式要求（默认口径与 `roles/dev/dev.md:107`「除非简报明确要求」对齐）；若不设例外，须明确写成"无例外"。
2. 协议中明确"PR 内产生的用例跑完即清除"：给出清除时点（跑完 / 交付前）与清除范围（本 PR 生成的文件）。
3. 协议中明确"一次性验收脚本跑完即删"，并与第 2 条合为同一条约束（Q5 与 Q4 合成同一条）——脚本落点可以自便，删除是硬要求。
4. 该规则与 `roles/dev/dev.md` 现行规则（:107 不写测试用例、:110 不跑全量测试套件）一致：执行角色读完协议与读完 dev.md 得到同一个结论，不产生新的口径矛盾。
5. 该约束带 `判断方式：…`（形态见 [F08](F08-protocol-judgeable-constraints.md)）：事后拿到一次派发的交付面，能判定它是否违反归属或清理规则。
6. 归属与保留的判据不是物理指标（文件行数、运行时长上限）——Q3。

## 边界（不包含）

- 不把任何测试用例落到仓库（零测试交付，§2）。
- 不新增 test-keeper 角色承担清除（Q10：本次先不做）——清除责任落在执行角色自身的规则里。
- 不改 `roles/dev/dev.md`（现行规则已与 Q4 一致，F-4）。
- 不定义保留集重建触发（→ F07）、零测试态验收判定（→ F05 / F06）。
- 不定义协议承载形态（§7 `user_deferred`，见 F08 边界）。
