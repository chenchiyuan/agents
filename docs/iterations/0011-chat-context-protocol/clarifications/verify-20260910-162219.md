### V6（补充条目：兜底机制不得反向破坏既有投递路径）：**fail**

> 补充理由：委托的 V1~V5 未覆盖"兜底路径对主投递路径的副作用"，但该行为直接违反本迭代自身的验收不变量（`prd` F02-1 / `architecture` §4.3：一次提问 = 恰一条 in + 一条 out；`web.test.js:382` 既有用例名即为此契约）。作为独立验证者，该缺陷必须以 fail 级别呈现，不能降格为"偏差记录"。

**缺陷**：对账**达上限即删除 `task_id` 登记**（`web.js:246`）。登记是投递路径唯一的到达凭据（`web.js:283-284`），因此任何**超过 30s**（默认 `5s × 6 次`）尚未见终态的任务，其随后的**合法投递会被静默丢弃**——对话永久停在 `working`，既无 out 也无终态事件。

**实测（隔离拓扑，真实 agent，单次 35s 任务）**：

| 运行 | 树 | 结果 |
|---|---|---|
| 长任务 35s（对照） | 修复前 | `routerState=completed`、`terminalAtMs=35055`、`ins=1`、`outs=1`、`outText=长任务回复`、`chatState=completed`、**pass** |
| 长任务 35s（默认对账 5s×6=30s） | **修复后** | `routerState=completed`、`routerResultText=长任务回复`、`ins=1`、**`outs=0`**、`chatState=working`、stderr：`oamp web: 对账放弃 task=task-226722e5…（6 次未取得终态）`、**fail** |
| 长任务 35s（对账间隔 20s，6×20s=120s 不触发上限） | 修复后 | `ins=1`、`outs=1`、`outText=长任务回复`、无 warn、**pass** |

第三行是**因果隔离**：同一份修复代码、同一场景，仅把上限触发推迟到任务终态之后，out 即恢复正常 → 证明丢回复的因就是上限分支的 `tasks.delete`。

**影响面**：agent 侧默认超时 `DEFAULT_OMP_TIMEOUT_MS = 300000`（`src/agent.js:31`，omp/LLM 任务 300s），shell 任务 `30000`。即**任何耗时 > 30s 的正常 LLM 轮次都会命中**——把原本间歇 20% 的丢失升级为长任务 100% 丢失，并额外把 chat 永久锁在 `working`（对账放弃后无任何终态兜底）。这是对本次补丁目标的实质性反噬。

## 下一迭代候选

- **对账上限与任务真实超时脱钩**：`6 × 5s = 30s` 与 omp 任务默认 300s（`src/agent.js:31`）不匹配；建议上限按任务超时推导，或改为"放弃轮询、保留登记"（本报告 V6 的最小改法）。
- **放弃后无终态兜底**：上限触发后 chat 停在 `working`，既无 out 也无 `chat_state` 事件，前端"进行中"永不收敛。可评估"超时即落一条 `failed` out"或复用启动扫尾（`db.startupSweep`）语义。
- **定时器粒度**：每个在飞任务一个 `setTimeout`（`web.js:254-260`），数量 = 在飞任务数；当前上下文上限 8，风险低，若要扩并发可评估单定时器 + 扫描表。
- **恢复时延**：默认对账首查 = 5s，即"投递丢失"场景下用户最坏多等 5s（本次实测补落即在此窗口内）。若有更低时延诉求，可评估首查退避（如 1s 起）。
- **用例覆盖缺口**：`test/web.test.js` 新增 2 例均以"秒级任务"为背景，未覆盖"任务耗时跨过对账上限"的路径——即 V6 缺陷逃逸的原因；补一条长任务回归用例可锁死该边界。
