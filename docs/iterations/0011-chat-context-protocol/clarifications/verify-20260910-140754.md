### V4 同键串行 / 异键并发 / 队列上限 —— **pass**

- **异键并发**：两个键各自 `prompt` → 两个不同子进程（`pids={80922,80923}`），两轮 prompt 区间**真重叠**（`max(start) < min(end)`），总耗时 776ms < 同键串行 1193ms → 池无全局串行。

### V5 LRU 淘汰 / 释放（chat 关闭）/ 重置（崩溃·超时·淘汰）notice 语义 —— **pass**

- **LRU**：`max=2` 时建 L1 → L2 →（按真实 agent 路径经 `getOrCreate` 触碰 L1）→ 建 L3 ⇒ 被淘汰的是**最久未使用**的 L2（`sessions` 仅剩 `chat-L1`、`chat-L3`）；L2 子进程被 kill（`waitGone(81010)` 通过）；重建后换新 `pid`（81010 → 81011）。淘汰触发点 `context-pool.js:87-96`；`onNotice` 载荷 `{chatId:'chat-L2', kind:'context_reset', text:'上下文已重置，本对话后续回复不再记得此前内容', origin:'web-1'}`。
- **上限生效**：`max=2` 下 `sessions.size` 始终 ≤2。
- **淘汰在飞键的边界**（我补的边界用例，`max=1`）：淘汰一个正在 prompt 的键 → 该轮以 `context_crashed` 收尾（不挂起）、子进程被回收、且只发 **1 条** `context_reset`（不重复提示；去重逻辑 `context-pool.js:154-158` 的 `closed && !removed` 分支）。
- **释放（chat 关闭）**：同一 chat 两个键 → `pool.release('chat-R')` 返回 2，仅移除该 chat 的键（无关键 `chat-O` 存活），发 2 条 `kind:'context_released'`，两个子进程均被 kill。**在飞/排队轮次**：chat 关闭时在飞轮次与排队轮次均以 `context_crashed` 失败（不静默丢弃、不挂起）。
- **命名三态不混用**（§5.2 关键裁决）：agent 侧收到控制消息 `notice{kind:'context_release'}`（`agent.js:444-454` 解析、`:452` release）→ 回发 **SSE 侧** `notice{kind:'context_released'}`（agent 层实测收到 `{"chat_id":"chat-A","kind":"context_released","text":"对话已关闭，上下文已释放"}`）；淘汰/崩溃/超时 → `context_reset`。实测 inbox 中不存在 `kind:'context_release'` 被当作回发提示的情形。
- **释放后重建**：释放后再问 → `context_id` 由 `ctx-81106-1` 变为 `ctx-81112-3`（新 pid），且不再记得 42。
- **dispose（SIGINT）**：agent 收 SIGINT → 退出码 0、日志 `DEREGISTERED`、dev-1 的常驻子进程全部被 kill，且**不误杀** dev-2 的子进程（dev-2 自己 SIGINT 后其子进程亦被回收）。代码位：`agent.js:502-505`（二次 SIGINT → `pool.dispose()` + exit 130）、`:601`（`finally { pool.dispose(); }`）。

### V6 崩溃 / 超时 / 未知模型错误面 —— **partial**（含 1 项 fail：成功轮次 `model` 未取自 ACP `currentValue`）

**通过的子项**

**fail 子项：成功轮次的 `model` 未取自 ACP `currentValue`（验收标准 6 后半 / F06-3 判定依据 / §7.4）**

- 验收标准原文要求：「成功轮次的 `model` 取自 ACP `currentValue`（实际生效值，F06-3 审计面）」；`prd/F06` 卡更明确：「由 agent 从 ACP session 的 `currentValue` 回读后上报（**不是用户输入的回显**）」。
- **证据 1（真实协议帧形态）**：`omp 18.0.11` 的 `session/new` 与 `session/set_config_option` 返回的 `configOptions` 是**数组**：
  `{"sessionId":"01a089e8-…","configOptions":[{"id":"mode",…},{"id":"model","name":"Model","category":"model","type":"select","currentValue":"deepseek/deepseek-v4-flash","options":[…]},…],"modes":[…]}`（`raw-acp.mjs` 原始帧；`configOptions` 判型实测为 `ARRAY`）。
- **证据 2（实现按对象形态读取）**：`oamp/src/acp-client.js:33-36`
  ```js
  function readCurrentModel(result) {
    const value = result && result.configOptions && result.configOptions.model && result.configOptions.model.currentValue;
    return typeof value === 'string' && value !== '' ? value : null;
  }
  ```
  数组没有 `.model` 属性 → **对真实 omp 恒返回 `null`**。被引用点：`:81`（`start()` 后 `this.currentModel = readCurrentModel(created)`）、`:149`（`setModel()` 回读）。
- **证据 3（真实链路上的可观察后果）**：`real-probe.mjs` 真实 ACP 下成功轮 `result.model === null`（`{"text":"记住","model":null,"stop":"end_turn","ctx":"ctx-81225-1"}`）；因此 `prompt()`（`:118-119`：`if (target && this.currentModel !== target) await this.setModel(target)`）因 `null !== target` **每轮都发一次 `set_config_option`**（真实帧日志可见），与 §6.6「若与当前 currentValue 不同 → 切换」的条件语义不符。
- **证据 4（agent 侧以请求回显兜底）**：`oamp/src/agent.js:294` `model: result.model || model` —— `result.model` 为 `null` 时落到本轮**请求值**。真实 agent 协议面实测：显式模型轮 `"model":"deepseek/deepseek-v4-flash"`、未显式轮 `"model":"openai/gpt-5.6-luna"`，二者都是请求链解析值，而非 ACP 回读值。
- **证据 5（测试无法发现）**：产出物测试的 fake 采用**对象形态**（`oamp/test/context-pool.test.js:84` `configOptions: { model: { currentValue: spawnModel, options: [] } }`、`:100` 同形），与真实 omp 的数组形态不符 → 该断言只在 fake 下成立，绿灯不构成契约证据。
- **影响界定（供主 agent 决策）**：用户可见值在本次实测的所有用例中与「实际生效模型」一致（因为 `set_config_option` 对未知模型必报错，而实现又每轮无条件调用它），故 F06-4「明确失败、不回退」未受影响；受损的是 (a) F06-3 的**判定机制**（审计字段来源为请求回显，与卡片明文冲突）；(b) 每轮一次**冗余 RPC**，且该 RPC 一旦失败/超时（`REQUEST_TIMEOUT_MS=10000`）会把"模型本来就正确"的轮次判为 `model_unavailable`/超时（潜在假阴性，本次未实测触发，[INFERENCE]）；(c) 若 omp 将来对模型标识做别名/规范化，审计字段会与实际生效值偏离。
- 修复方向（我只报告，不实施）：`readCurrentModel` 兼容数组形态（`Array.isArray(...) ? ...find(o => o.id === 'model' || o.category === 'model')?.currentValue : ...` 保对象形态兼容），并把 fake 改为真实数组形态。
