### V6 `close(chatId)` / `closeAll()` 语义（含结束连接、chat 隔离、竞态） — **pass**

**证据 1（代码语义）**：`close(chatId)`（`src/transport.js:65-70`）先 `subscribers.delete(chatId)` 再对 `[...set]` 逐个 `res.end()` —— 既移除订阅又**结束连接**，满足 Q1 裁定；`closeAll()`（`:72-75`）按 `[...subscribers.keys()]` 逐 chat 复用 `close()`，与任务图 T1-4 表述一致。

**证据 2（独立复现，真实连接）**：
- `V6a` `close('c1')` → c1 客户端流 `ended === true`，c2 客户端 `ended === false`；随后 `publish('c2', …)` 仍到达、`publish('c1', …)` 未写入：**PASS**（结束连接 + chat 隔离双向成立）。
- `V6b` 同 chat 两条连接，`close(chatId)` 后两条均 `ended`：**PASS**。
- `V6c` 多 chat `closeAll()` 后全部 `ended`，之后 `publish` 不抛错且文本无 `event:` 帧：**PASS**。

**证据 3（竞态修正独立复现）**：`V6d` —— 用假 `res` 精确编排时序：`handle(res_old, chat)` → `close(chat)`（删登记 + `res_old.end()`）→ **同 tick** `handle(res_new, chat)`（新建 `Set`）→ 手动触发 `res_old` 上 pending 的 `'close'` 事件 → `publish(chat, …)`。断言新订阅 `res_new` 仍收到该帧（写入计数 1、文本含 `to-new`），且随后 `closeAll()` 能命中新订阅（`res_new.ended === true`）：**PASS**。

**证据 3b（判别性对照，falsification）**：在 worktree 之外复制模块为变体 `/tmp/verify-pr002/transport-mutant.js`，仅将 `:48` 守卫改为 `if (set.size === 0) {`，同一 `V6d` 场景对照运行（`/tmp/verify-pr002/discriminate.mjs`）：

**证据 4（Node 生命周期顺序，排除写窗口崩溃风险）**：自建探针 `/tmp/verify-pr002/probe-window.mjs`（真实连接，客户端 abort）实测事件顺序为 `res.close(destroyed=true)` → `socket.close` → 其后 `res.write()` 返回 `false`、不抛出、不触发 `res.error`。即订阅集合在 `res` 不可写之前已被清理，且即使窗口内写入也不会产生未捕获错误。结论：`publish`/心跳不存在"向已销毁连接写入导致进程崩溃"的路径。
