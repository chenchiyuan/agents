### R3 请求体 >64KB → 413（原直接断连无响应）—— **闭环**

- 代码复核：超限时 `fail(413, '请求体过大（上限 65536 字节）')`（`src/web.js:65-67`）；`settled` 标志使判错后**丢弃后续 data 而不缓冲**（`:63`，防内存膨胀）；调用点对 413 追加 `connection: close`（`:365`）。
- 实测（raw `node:http`，70KB body）：**413** + `{"error":"请求体过大（上限 65536 字节）"}` + `connection: close`，客户端 **1ms** 内收到完整响应，无超时、无 reset（`destroyed=false`）→ 不存在原缺陷的"无响应悬挂"。
- 交叉验证（curl，两种客户端形态）：默认形态（curl 对大 body 自动带 `Expect: 100-continue`）与 `-H 'Expect:'` 形态均得 `HTTP/1.1 413 Payload Too Large` + `connection: close`，`exit=0`，`time≈1ms`，响应体文案一致。
- **边界值（独立构造精确字节数）**：请求体总长**恰 65536 字节 → 非 413**，进入校验面得 400（缺 agent）；**65537 字节 → 413**。限流语义为"整个请求体 ≤ 65536"，与实现一致。
  - 留痕：本项首轮探针误把 `JSON.stringify({text:'y'.repeat(65536)})`（实际 65547 字节）当作"恰 64KB"，得到 413 后判 FAIL；核对字节数后修正探针（用定长模板精确构造 65536/65537）复测通过——**该 FAIL 是探针算错，不是实现问题**。
- 连续性与鲁棒性：连续 3 次超限请求均 413，之后 `GET /api/chats` 仍 200；另以"声明 `Content-Length: 200000` 但只写 100 字节即销毁 socket"×3 模拟客户端中断 → web 进程存活、服务继续 200、正常发送链路完好、stderr 无未处理异常。
