## 第一段：澄清依据

### 1. 用户原始表述（2026-09-10，user_confirmed）

> 1，每个对话(chat)是一个整体，里面会处理一件闭环且独立的事情。需要 web 服务持久化对话的内容，并且支持基于对话的历史查询。
> 2，在对话内，每次聊天都是一次调用。A(agent)->B(agent)，B agent 收到任务的处理过程要通过协议在对话聊天内实时展示（可以是已有协议，也可以扩展，举例 websocket 就可以）。最后只持久化 A 的输入，B 的结果输出。也就是 chat 下有 输入/输出的列表，按时间排序。
> 3，每个 agent 管理自己的上下文。在一个 chat 中，同名 agent 是一个 daemon 进程，管理一份上下文。举例：chat A 中，我使用 dev，多次任务指派实际调用的是一个 dev agent，这几次任务指派的上下文会累积。也就是 dev agent 不会释放，每次使用新的，是持续对话。新建了 chat B，再调用 dev，实际是启用一个新的 dev agent，上下文内容是新的。
> 4，每个 agent 管理自己的上下文。
> 反例（禁止）：chat A 中每次对话都丢掉之前的上下文、对话 3 次产生 3 个 agent。

## 第二段：需求结论（规范条款）

### 1. 做什么

- **C-1 chat 是闭环容器**：一次 chat 处理一件独立事情；chat 有标题、状态、创建/更新时间，可关闭。
- **C-2 chat 持久化（web 服务负责）**：SQLite 落盘 **只存两类内容**——A 的输入（用户消息）与 B 的输出（agent 最终答复/结果的文本）；过程（流式明细）不落盘。
- **C-3 历史查询**：按 chat 列表检索（时间/状态/agent/关键词过滤）+ 打开历史 chat 读取完整输入/输出序列。
- **C-4 一次聊天 = 一次调用**：A→B 经 OAMP 协议；B 的处理过程**实时展示**在对话内（协议层可替换：本版 HTTP/SSE，未来 WS 同接口替换）。
- **C-5 上下文规范（核心）**：上下文键 = `(chat_id, agent_id)`。
  - 同 chat 同 agent：一个**常驻 omp daemon 进程**、一份持续累积的上下文（多轮问答互相可见）。
  - 新 chat 同 agent：**全新进程、全新上下文**（不得复用上个 chat 的上下文）。
  - 每 chat 多个 agent：各自独立进程与上下文。
- **C-6 上下文由 agent 自己管理**：agent 进程内维护"上下文池"（per chat 一个 omp 子进程），不依赖中央服务持有会话状态。

### 2. 不做什么

- **N-1** 不持久化过程（流式 chunk、工具调用中间态）——过程仅内存 + 实时推送。
- **N-2** 不做跨 chat 的上下文共享（chat 即隔离边界）。
- **N-3** 本版不做 WebSocket（只留替换接口；不引入 ws 依赖）。
- **N-4** 不做鉴权/多用户（沿用迭代 0010 N6 边界）。
- **N-5** 不做历史迁移（0010 内存会话数据不迁移；新库从空开始）。

### 3. 达到什么效果（裸判定）

- **E-1**：同一 chat 内先问"请记住数字 42"再问"数字是多少"，回答包含 42；且全过程复用**同一 omp 进程 pid**。
- **E-2**：新建 chat 后问同样问题，回答**不含 42**（新上下文）。
- **E-3**：重启 web 服务后，历史 chat 列表与输入/输出仍可查（SQLite 落盘生效）。
- **E-4**：提问过程中，浏览器在回答完成前即可看到流式/增量输出（SSE 实时，非等终态）。
- **E-5**：数据库中只有输入/输出记录（无过程明细行）；过程仅存在于运行期内。
