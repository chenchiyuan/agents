# F05：上下文规范（同 chat 累积 / 新 chat 隔离 / 由 agent 自管）

**功能 ID**: F05
**来源**: `demand.md` C-5（上下文键 = (chat_id, agent_id)）、C-6（上下文由 agent 自己管理）、D-2（常驻进程，非每次新起）、N-2（不做跨 chat 共享）；裸判定 E-1、E-2；可行性依据 V-1
**迭代**: 0011-chat-context-protocol

---

## 用户价值

同一个对话里的多轮任务是连贯的——B 记得之前说过什么，用户不用每轮重复背景；换个对话则从零开始，不同事情互不污染。

## 验收标准

1. **同 chat 累积（裸判定 E-1 前半）**：在同一 chat 中对同一 agent 先问"请记住数字 42，只回复『记住』"，再问"数字是多少" → 第二轮回答包含 42（E-1，V-1 已实测该路径可行）。
2. **同一常驻实例（裸判定 E-1 后半）**：上述两轮由同一个常驻 agent 实例处理——两轮可观察到的实例标识一致；若第二轮换了新实例，本卡判定失败（E-1/D-2）。实例标识的观察形式 = 输出记录 `meta` 中的 `context_id`（`ctx-<pid>-<创建序号>`）与 `pid`，两轮相等即同一常驻实例。
3. **新 chat 隔离（裸判定 E-2）**：新建 chat 后对同一 agent 问同样两个问题 → 第二轮回答不含 42（全新上下文）（E-2）。
4. **同 chat 多 agent 隔离**：同一 chat 内对两个不同 agent 分别告知不同内容 → 各自回答只反映自己被告知的内容，互不串扰（C-5）。
5. **反例禁止**：同一 chat 内连续多轮调用不得出现"上文丢失"表现（回答与上一轮已确立的事实无关），也不得表现为每轮新建独立实例（C-5 明列的反例：对话 3 次产生 3 个 agent / 每轮丢弃之前的上下文）。
6. **上下文由 B 自管**：多轮调用中 A 侧不重复传递此前全部对话原文，B 侧仍能正确回忆前文——即上下文的持有者是 B 侧而非中央服务（判定方式：第二轮请求只携带本轮输入，仍满足验收 1）（C-6）。
7. **上下文异常可告知**：上下文因容量压力被释放或实例异常重建时，对话内以明确提示告知"上下文已重置 / 已释放"，不静默丢失（触发条件 = 容量淘汰 / 崩溃 / 超时重置 / chat 关闭；提示形态 = 对话内运行时系统提示条（SSE `notice` 事件，不入库））`[model_inferred]`。

## 边界（不包含）

- 不做跨 chat 的上下文共享（N-2：chat 即隔离边界）。
- 不做中央服务持有会话内容（C-6）。
- 不做上下文的手工重置 / 导出 / 迁移（demand 未要求）。
- 不承诺上下文持久化与重启恢复（E-3 只承诺历史记录可查；上下文存续边界 = web 重启不丢（上下文在 agent 进程内）、agent 重启即丢且不做主动提示）。
- 上下文的具体实现形态不在本卡做技术选定（D-2 已定"常驻、非每次新起"的方向；落地形态 = per-chat 一个常驻 `omp acp` 子进程 + 一个 ACP session，由 agent 进程内的上下文池持有）。

## 架构维度（阶段 3 已填，2026-09-10；详见 `architecture.md` §6.1~§6.4）

- **键与常驻实例形态**：键 = `(chat_id, agent_id)`；每个键 = **一个常驻 `omp acp` 子进程 + 一个 ACP sessionId**（`src/context-pool.js` 持有，位于 agent 进程内——满足 C-6"由 B 侧自管"，A 侧只传本轮输入）。新 chat → 新键 → 新进程（V-1/V-8 实测：上下文只随进程 + session 存活）。**实例标识观察方式**：`context_id = 'ctx-<pid>-<generation>'`（generation 为本 agent 进程内创建序号），与 `pid` 一并随每轮 `task.result` 回到 web、写入该条 out 记录的 `meta` → **两轮 `meta.context_id` 与 `meta.pid` 相等**即判定同一常驻实例（对应验收 2，同时满足 E-1 的 pid 复用字面判定）。
- **并发策略**：同键**串行**（同一时刻至多 1 个 in-flight prompt + FIFO 队列；队列上限 8，超出该轮以 `context_busy` 失败，防无界堆积）；不同键**完全并发**（各自独立进程）；排队轮次的 `timeout_ms` 从**实际开始执行**时计时（对应验收 5 的反例禁止）。
- **上限与淘汰**：全局上限 `OAMP_CTX_MAX`（默认 8，可配置 `context.max`），超出则 **LRU 淘汰**最久未用的键（kill 进程）；**不主动 TTL 回收**（用户决策）。**提示形态**：淘汰/崩溃/超时重置时，agent 向 web 发 `notice{kind:'context_reset'|'context_released', chat_id, text}` → web 转成 SSE `notice` 事件 → 前端在对话流内插一条系统提示条；**该提示不入库**（否则违反 F02-5/E-5"仅两类记录"，对应验收 7）。
- **释放与重启边界**：chat 关闭 → **立即释放**（web 发 `notice{kind:'context_release'}` → agent kill + 移除键），在飞轮次按崩溃路径失败收尾；**web 重启**不影响上下文（上下文在 agent 进程内）；**agent 重启**上下文全丢、后续轮次产生新 `context_id`/`pid`（可从 out 记录 meta 观察），**不做主动提示**（agent 重启后无从知晓历史 chat 清单，主动提示需持久化 chat 清单，超出 N-5 范围）；agent SIGINT → `pool.dispose()` 全部回收。
