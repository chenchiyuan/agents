# F05：上下文规范（同 chat 累积 / 新 chat 隔离 / 由 agent 自管）

**功能 ID**: F05
**来源**: `demand.md` C-5（上下文键 = (chat_id, agent_id)）、C-6（上下文由 agent 自己管理）、D-2（常驻进程，非每次新起）、N-2（不做跨 chat 共享）；裸判定 E-1、E-2；可行性依据 V-1
**迭代**: 0011-chat-context-protocol

---

## 用户价值

同一个对话里的多轮任务是连贯的——B 记得之前说过什么，用户不用每轮重复背景；换个对话则从零开始，不同事情互不污染。

## 验收标准

1. **同 chat 累积（裸判定 E-1 前半）**：在同一 chat 中对同一 agent 先问"请记住数字 42，只回复『记住』"，再问"数字是多少" → 第二轮回答包含 42（E-1，V-1 已实测该路径可行）。
2. **同一常驻实例（裸判定 E-1 后半）**：上述两轮由同一个常驻 agent 实例处理——两轮可观察到的实例标识一致；若第二轮换了新实例，本卡判定失败（E-1/D-2）。实例标识的观察形式 `[架构待填]`。
3. **新 chat 隔离（裸判定 E-2）**：新建 chat 后对同一 agent 问同样两个问题 → 第二轮回答不含 42（全新上下文）（E-2）。
4. **同 chat 多 agent 隔离**：同一 chat 内对两个不同 agent 分别告知不同内容 → 各自回答只反映自己被告知的内容，互不串扰（C-5）。
5. **反例禁止**：同一 chat 内连续多轮调用不得出现"上文丢失"表现（回答与上一轮已确立的事实无关），也不得表现为每轮新建独立实例（C-5 明列的反例：对话 3 次产生 3 个 agent / 每轮丢弃之前的上下文）。
6. **上下文由 B 自管**：多轮调用中 A 侧不重复传递此前全部对话原文，B 侧仍能正确回忆前文——即上下文的持有者是 B 侧而非中央服务（判定方式：第二轮请求只携带本轮输入，仍满足验收 1）（C-6）。
7. **上下文异常可告知**：上下文因容量压力被释放或实例异常重建时，对话内以明确提示告知"上下文已重置 / 已释放"，不静默丢失（触发条件与提示形态 `[架构待填]`）`[model_inferred]`。

## 边界（不包含）

- 不做跨 chat 的上下文共享（N-2：chat 即隔离边界）。
- 不做中央服务持有会话内容（C-6）。
- 不做上下文的手工重置 / 导出 / 迁移（demand 未要求）。
- 不承诺上下文持久化与重启恢复（E-3 只承诺历史记录可查；上下文存续边界 `[架构待填]`）。
- 上下文的具体实现形态不在本卡做技术选定（D-2 已定"常驻、非每次新起"的方向，落地形态 `[架构待填]`）。

## 架构维度（阶段 3 填）

- `[架构待填]` 上下文键的落地形态与常驻实例的具体形态；实例标识的观察方式（验收 2 的判据落地）。
- `[架构待填]` 同键并发调用的排队策略、不同键的并发策略。
- `[架构待填]` 容量上限与淘汰策略；释放/崩溃后的用户可见提示形态与消息类型（验收 7 的落地）。
- `[架构待填]` chat 关闭时的上下文释放时机；web 服务或 agent 重启后上下文的存续边界。
