### 1.1 原文照录（`user_confirmed`）

> 新的需求：实际工作过程中，项目是必须有代码路径，仓库依赖的。也就是迭代都有指定的项目。我们先假定每个chat都是基于一个项目做迭代开发。按照已有的设计，上下文均在项目中。Pr/commit/docs 中有充分的文档，每个role也需要在项目中迭代开发。Hub的web 对话页面之前，需要有全局的设置，也就是对话在项目之下。我需要先新建项目（目前有github地址即可），然后在项目下开启对话。项目和对话是1对多的关系。这样对话就知道自己的项目结构了，执行之初需要在宿主机clone下项目（如不存在，存在就直接进入项目），在项目的根目录下工作，这样所有agent都能对齐目录和上下文。按照之前的设计，记录也会在项目中。

## 4. 六维诊断与澄清结论

### 4.1 明确性（M）

| # | 模糊点 | 澄清结论 | 来源 |
|---|---|---|---|
| **M-1** | "项目"的**最小字段集**是什么？本地路径要不要入库？ | **四字段**：`project_id`（内部键）、`name`（展示名）、`repo_url`（用户填的 GitHub 地址）、`created_at`。**本地路径不入库**——D-2 明确落点由 agent 自控，且同一项目在不同宿主机路径不同，入库的路径是**伪真源**，会让"对话知道项目结构"变成"对话知道某一台机器的目录" | `user_confirmed`（P-1 按推荐采纳） |
| **M-2** | 对话与项目的**绑定强度**：允许"无项目对话"吗？ | **不允许**。S-1「每个 chat 都是基于一个项目」+ S-2「1 对多」⇒ 新建对话必须归属一个项目，`project_id` 为 **`NOT NULL`**；对话列表**以项目为范围**（同一项目内的对话互相可见，跨项目不混列）。**这与现状直接冲突**：今天 `POST /api/messages` 缺 `chat_id` 时凭空造对话（F-4），必须改为"无项目归属则拒绝"（`400 INVALID_PARAM`） | `user_confirmed`（P-2「按推荐：强绑（API 层强制）」） |
| **M-3** | 新建项目的输入与**唯一性**？ | 输入 = **只要仓库地址**（S-4）；`name` 可留空，缺省从地址尾段推导（去尾部 `.git`）。唯一性 = **原样 `repo_url` 字符串唯一**，重复创建 → 拒绝（`409 CONFLICT`，复用既有错误契约 F-18）。**不做 URL 归一化**（`https://x/y` 与 `https://x/y.git` 视为两条）、**不校验地址可达性**（无 GitHub 集成，N1） | `user_confirmed`（P-3 按推荐采纳） |

### 4.2 逻辑闭环 —— why 能否推出 what

**Why（三条，均由 `user_confirmed` 原文/回答给出）**：

1. **对话今天是无根的**：`chats` 表没有项目维度（F-1），对话不知道自己对应哪个仓库 ⇒ agent 无法对齐目录与上下文，PR / commit / docs **无处安放**（S-5/S-6）。
2. **项目是长期容器，对话是工作单元** ⇒ 1 对多（S-2）。项目要能被复用（同一个仓库下开很多次对话），所以项目必须先于对话存在、且可独立列出（S-3）。
3. **agent 分布在各自宿主机，hub 无法操纵其环境**（D-1）⇒ 唯一可行的耦合方式是**传递上下文**，不是远程控制目录或代跑 clone（D-2）。

**逐条对照**：

| 用户给的 what | 从 Why 能否推出 | 结论 |
|---|---|---|
| 新建项目（有 GitHub 地址即可） | **能**。why-2 要求项目是独立可复用的实体；S-4 已把它的最小输入定死 | 闭环成立 |
| 在项目下开启对话（1 对多） | **能**。why-1 要消灭无根对话；why-2 给出基数关系 | 闭环成立 |
| 对话携带项目上下文给 agent | **能**。why-3 排除了其它耦合方式，只剩传递上下文 | 闭环成立 |
| agent 在自己宿主机 clone 并在项目根工作 | **能，但仅到"传达"为止**。why-3 的直接推论是"谁的环境谁负责"；**"agent 自动对齐目录"已由用户裁决不纳入本迭代承诺**（P-4 备注） | 闭环成立（能力边界见缺口 2） |
| PR / commit / docs 落项目仓库 | **能**。why-1 的"无处安放"反命题——产物必须落在对话所服务的那张代码库上 | 闭环成立 |

**必须显式记录的三处缺口**（why → what 的差异比对产出）：

> **缺口 1（必要约束，非新增需求——已由用户采纳）**：`POST /api/messages` 今天能在没有项目的情况下凭空建对话（F-4）。
> 若不改，用户要的"每个 chat 都基于一个项目"**在数据层就是假的**——绕过 UI 直接调 API 即可造出无根对话。
> ⇒ **结论：M-2 的"强绑"不是可选形态，是 S-1 的必要条件**（落 W2）。**用户已裁决采纳 API 层强制**（P-2）。

> **缺口 2（能力前提，必须显式标注，不新增需求项——已由用户裁决确认为"不纳入本迭代"）**：用户期望"执行之初 clone → 在项目根目录工作"。
> 但**现状的 cwd 是进程级常量**（F-11），且**工具开关随 agent 实例固化、不由对话决定**（F-12）。
> 也就是说：**注入了上下文 ≠ agent 自动进入项目根目录**——真正的"进入"发生在 agent 用工具（`cd` / clone）行动的那一步，而那取决于 agent 侧部署时是否开了工具。
> ⇒ **本迭代只保证"上下文被完整、准确地传达到 agent"**；"自动对齐目录"是 agent 侧部署（`roles.<role>.tools`）与 agent 执行习惯的事，**不在本迭代的可保证范围内**。
> **用户已裁决：「不要求」它成为本迭代承诺（留后续迭代）** ⇒ 该边界永久留在 **C-4**，**结论段不得出现"agent 自动在项目根目录工作"这类承诺**，也不得因为"用户想要对齐目录"而把承诺写进结论。依据：D-1/D-4 + P-4 备注。

> **缺口 3（既有硬约束的继承）**：新增项目类 HTTP 面 ⇒ 必须登记进路由表并同步 `API.md` 路径行 + 重生成 `llms.txt` 快照，否则 0016 的三条漂移锁直接红（F-8）。
> ⇒ 这不是新需求，是**上一个迭代已经生效的工程约束**，本迭代照单继承（落 §4.4 C-6 / §3 大概怎么做）。

### 4.3 边界完整性

**用户明说的边界**（`user_confirmed`）：不引入 GitHub 集成（S-4「有 github 地址即可」）；hub 不操纵 agent 环境（D-1）；本地落点由 agent 控制（D-2）；产物全落项目仓库（D-3）；不安装 `.pb-agents`（D-4）；清空旧库（D-5）；不要求"agent 自动在项目根目录工作"（P-4 备注）；不做项目删除/改名/归档（P-7）；不做 URL 归一化（P-3）；不引入迭代实体（P-8）；本迭代文档留在 agents 仓库（P-9）。

**其余边界（N1~N13）均为推导所得，逐条给"为什么这次不做"**（见第二段 §2）。

**主动的边界收敛判断**（去掉它，最小闭环是否还成立）：

- **去掉"项目删除/改名"**：最小闭环是"建项目 → 开对话 → 传上下文 → 落产物"，删除/改名不参与这条链路；而删除必然带出"级联处理该项目的对话（归档？关闭？一并删？）"一整块决策面，收益为零。⇒ **不做**（N5，用户已确认 P-7）。
- **去掉"URL 归一化去重"**：本迭代的痛点是"对话不知道项目"，不是"同一仓库被录了两遍"；归一化要处理 `.git` / 尾斜杠 / 大小写 / SSH 与 HTTPS 形态四类等价，是独立的正确性课题（P-3）。⇒ **不做**（N6）。
- **去掉"项目级权限 / 多用户"**：沿用 127.0.0.1 无鉴权的既有边界（F-18 同源），本迭代不扩大攻击面。⇒ **不做**（N4）。
- **去掉"在 oamp 里建迭代实体"**：迭代是文档层概念，"属于某项目"由产物落点约定表达；建实体等于把 workflow-pb 的概念塞进运行时，是最小闭环外的范围。⇒ **不做**（N11，用户已确认 P-8）。
- **保留"清空旧库"**：看似可延后，但它**不可延后**——引入项目维度后，旧对话的 `project_id` 只能是空值，每一处查询/UI 都要为"无归属对话"准备一条分支，**这是永久性的复杂度税**。D-5 已拍板清空，P-5 进一步把执行方式定为"启动即重建"，正是彻底消除这笔税。⇒ **做**（W6）。

### 4.5 可验证性（裸判定测试）

第二段 §4 的 E1~E9 逐条通过裸判定：判定者不问作者、不读背景，仅凭**刷新首页看首屏是什么 / 建两次同名项目 / 在 A 项目发消息后切到 B 项目看列表 / 打开 sqlite 查两行 / 比对一条消息的原文 / 查 agent 窗口日志里的仓库地址 / 用旧 schema 库启动 / 删库重启 / 对照协议方法清单 / 刷新三面 + 跑测试**即可判真假；无"正常工作""体验良好"类主观词。

刻意留白但**仍可裸判定**的一处：
- **"上下文确实传达到了 agent"（E5）**：判定 = 在项目 A 的对话发一条消息，然后在 agent 侧（集群窗口日志 / 任务载荷）中检索项目 A 的 `repo_url` 字符串——**出现即真，不出现即假**。它**不**判定 agent 是否真的 clone 了（那属 C-4 的能力边界外，且用户已裁决不纳入本迭代）。

### 6.2 留痕：P-5 的用户裁决否决了 demand 的原推荐（供阶段 6 追溯）

- **demand 原推荐（v1.0.0）**：**幂等加列**——沿用 F-2 的既有机制加 `project_id` 列，不写数据迁移；旧库不崩，旧对话因"按项目过滤"自然不可见；用户随时删库即字面清空。推荐理由 = "多一行 DDL，换掉『用户忘记删库 → 启动即崩』的必然踩坑面，且复刻既有模式"。
- **用户裁决（v1.1.0）**：**「启动时删库重建，project_id NOT NULL（我的倾向）」** —— 用户选择了一条比 v1.0.0 已否决备选 ① 更彻底的口径（不是"旧库报错强制手删"，而是"启动即自动重建"）。
- **裁决的技术依据（本轮补记，`实测` F-22）**：SQLite 的 `ALTER TABLE ADD COLUMN` 无法给已有非空表添加 `NOT NULL` 列（除非给非空默认值），而"未指定项目"的默认值恰是 D-5 要消灭的东西 ⇒ **"幂等加列"与"`project_id NOT NULL`"在实现上不可兼得**。用户的"我的倾向"因此不只是偏好，而是与强一致 schema 自洽的唯一路径。
- **用户优先级的可读读出**：**schema 强一致（`project_id NOT NULL`，对话无项目归属在本模型下不合法）> 旧库兼容**；且用户认可旧对话无保留价值（D-5「清空旧库」）。
- **必须让阶段 2 知道的后果**：
  1. **本机现存 73KB 真实历史库将在首次启动时被自动销毁且不可恢复**（无备份代码路径）——E6 是可裸判定的验收点。
  2. 既有 F-2 幂等加列机制**不适用于 `project_id`**；其在新 schema 下是否仍有可达路径（其余两列的守卫）留 `[架构待填]`，但**不得为 `project_id` 恢复兼容分支**。
  3. 既有 `persist.test.js` 的"旧库补列 / 二次 openDb 幂等 / 迁移不引入新表"断言（F-3b）**语义整体反转**：旧库不再被补列，而是被重建、旧行消失 ⇒ 属 C-7 的**必然变更点**，必须逐条改写并写明理由（不是"顺手改测试"）。
- **本版不再保留的备选**：v1.0.0 的 P-5 已否决备选 ②"为旧对话造『未指定项目』兜底项目并回填"——在 `NOT NULL` 口径下同样不成立。

### 6.3 留痕：一条从 P-2 裁决直接推出的次级口径（可回退）

- **内容**：`GET /api/chats` **缺项目参数**时返回 `400 INVALID_PARAM`（不提供跨项目全量列表）。
- **来源**：`派生` —— 用户采纳的 P-2 包含「`GET /api/chats` 以项目为范围」+「API 层强制（"强绑"落在 API 层）」。若允许无参数返回全量，则该接口在缺参时就不是"以项目为范围"，与"跨项目不混列"冲突。
- **为何不是新需求 / 新缺口**：它没有引入任何新的用户意图，只是把已采纳裁决在**列表查询**这一处的直接后果写清楚；不改变 W1~W6 的任何一条。

## 5. 为什么这么做

- **为什么项目必须"先于对话"存在**（S-3）：对话的项目归属是一个**外键级事实**，它不能从对话内容里推断出来（同一仓库的对话可以谈任何事）。⇒ 项目必须是独立可列出的实体，而不是对话的一个标签字符串。（W1/W3）
- **为什么本地路径不入库、不做 clone 编排**（D-1/D-2，C-2）：hub 与 agent 的宿主机之间**没有**控制通道；web 能做的只有"把话带到"。任何"帮你 clone 好"的设计都要先假设 hub 能触及 agent 的文件系统，那是一个当前架构不支持的前提。⇒ 需求层只锁"上下文准确传达"，不锁"环境自动对齐"（**C-4 的边界经用户裁决确认为不纳入**，W4/N14）。
- **为什么必须强绑项目、且落在 API 层**（缺口 1）：今天的 API 能在没有项目的情况下凭空造对话（F-4）。只要这条路径存在，"每个 chat 都基于一个项目"就只是一个 UI 约定，而不是系统事实。⇒ M-2 的强制是 S-1 的必要条件，不是形态偏好；**用户明确采纳"API 层强制"**（P-2）。
- **为什么上下文用结构化载荷而不是 prompt 前缀**（P-4）：前缀会随用户消息进入 `messages.text`，此后每轮重复携带、污染阅读与检索，并把"系统上下文"和"用户说的话"糊在一起。⇒ 结构化字段 + agent 侧注入，把两者分层（E9 是它的裸判定）。
- **为什么产物落项目仓库**（D-3/S-6/S-7）：PR / commit / 迭代文档只有落在**被改的那张代码库**上才对后来者有意义；落在 agents 框架仓库会把"某个业务项目的开发史"混进框架的开发史。本迭代自身是"开发 oamp"，故其迭代文档留在 agents 仓库（C-1/P-9）。
- **为什么清空旧库是"启动即重建"而不是"迁移/兼容"**（D-5 + P-5 裁决）：`project_id` 必须 `NOT NULL`（对话无项目归属在本模型下不合法），而 SQLite 的 `ALTER TABLE ADD COLUMN` 无法给已有非空表加 `NOT NULL` 列 ⇒ **幂等加列与"必填列"在实现上不可兼得**（F-22）。用户裁决选择 **schema 强一致优先于旧库兼容**（旧对话无保留价值）。代价是**本机现存 73KB 历史库在首次启动时被自动销毁**——该后果在 E6 里是裸可判定的。**留痕：demand 原推荐（幂等加列）被用户否决**（§6.2）。
- **为什么不引入 GitHub 集成 / 归一化 / 删除改名 / 迭代实体**（N1/N5/N6/N11）：四者都不参与"对话知道自己属于哪个项目"这条最小链路，且各自带出一整块独立决策面（凭据、等价类、级联删除、运行时实体建模）。⇒ 最小闭环优先（其中删除改名、归一化、迭代实体均经用户确认不做）。
