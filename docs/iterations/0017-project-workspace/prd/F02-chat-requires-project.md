# F02：新建对话必须归属项目（API 层强制）

**功能 ID**: F02
**来源**: `demand.md` W2（新建侧）；决策 S-1 / S-2 / P-2；缺口 1；约束 C-7（必然变更点 ①）；边界 N7 / N9 / N13；效果 E3（部分）/ E4（部分）
**迭代**: 0017-project-workspace
**技术锚点（引用 `demand.md` §3 只读实测，非本阶段决策）**: F-4（`POST /api/messages` 在缺对话标识时用 `chat-<uuid>` 隐式新建对话，可凭空造出无项目归属的对话）、F-18（统一错误契约，`400 INVALID_PARAM`）、F-1（`chats` 表列集）

---

## 用户价值

系统里不再存在"不属于任何项目的对话"——绕过界面直接调接口也造不出来；对话从此知道自己在哪个项目里。

## 验收标准

1. **带项目归属即可新建**（W2 / S-1 / S-2）：在某个项目下新建对话 → 创建成功，且该对话的项目归属 = 该项目。
   *判定*：在项目 A 的工作台新建对话 → 该对话出现在项目 A 的对话列表中（E3）。
2. **缺项目归属的新建请求被拒绝**（W2 / 缺口 1 / P-2）：今天"发一条不带对话标识的消息即凭空造出一个对话"的既有路径，在**缺少项目归属**时返回 `400 INVALID_PARAM`，且**不产生任何对话**。
   *判定*：向该既有路径发送一条不带项目归属的请求 → 4xx（400）+ 对话总数不变。
3. **不存在"无项目对话"**（W2 / E4）：新建对话行的项目归属为**必填**（不可为空）且指向一个真实存在的项目。
   *判定*：用 sqlite 查该对话行，并核对该项目归属列的"不可为空"约束（E4）。
4. **归属指向不存在的项目则拒绝**〔`[user_confirmed MI-02]`〕：以不存在的项目标识创建对话 → 被拒绝（`400 INVALID_PARAM`），不产生对话；**不采用"项目不存在"的 `404` 读法**（用户裁决原文：「一律 400」）。
   *判定*：用一个不存在的项目标识创建 → 4xx + 对话总数不变。
5. **工作台内新建自动归属当前项目**〔`[user_confirmed MI-07]`〕：在项目 A 的工作台内新建对话，用户无需再次选择项目，直接归属 A（用户裁决原文：「新建自动归属」）。
   *判定*：在 A 的工作台点新建并发送 → 该对话出现在 A 的对话列表，**全程无项目选择步骤**。

## 边界（不包含）

- 不含对话列表的范围过滤（→ F03）；不含 UI 页面结构（新建入口落在工作台，→ F05）。
- 不含旧库处理（→ F08）。
- **不引入"未指定项目"的兜底项目、不做旧对话回填**（N7）。
- **不改上下文池的键与串行 / 并发语义**（N9）。
- **不改与项目无关的既有对话行为**：消息处理、归档 / 关闭 / 激活 / 改名的处理顺序与状态机、统一错误契约、无 405 的 404 兜底逐条保持（N13）。
- **不做多项目归属**：一个对话只属于一个项目（S-2 的"1 对多"是项目 → 对话，不是对话 → 项目）。
- 不含项目创建 / 列出（→ F01）。

## 架构落地（阶段 3 已填，见 `architecture.md` §2.1 / §3.3；产品维度未改一字）

- **T-10 归属参数形态与 `400`**：在既有 `POST /api/messages` 的**请求体**新增可选字段 `project_id`（**不新开"创建对话"接口**——验收 2 的判定对象就是今天这条既有路径，另开接口不会让它变安全）。判定规则一句话：**本次请求会创建对话（`db.getChat(chatId) === null`）⇒ `project_id` 必填且必须指向存在项目**；缺失 / 空 / 非字符串 → `400 INVALID_PARAM`（`新对话需要 project_id（对话必须归属一个项目）`）、指向未知项目 → `400 INVALID_PARAM`（`项目不存在: <project_id>`，MI-02"一律 400"，不采用 404）。**目标对话已存在 ⇒ 沿用既有逻辑，`project_id` 不参与判定**（归属不可变，由 `ensureChat` 的 `ON CONFLICT(chat_id) DO NOTHING` 结构性保证；不新增"归属一致性校验"分支）。
- **T-10 与既有处理顺序的关系（C-7 顺序契约）**：新校验插在**既有全部校验之后、`db.insertInput` 之前**——既有顺序逐字保持：读体（400/413）→ agent_id（400）→ model（400）→ `chat_id` 解析 → 只读预检（409）→ ★新校验（400）→ 写库 → 派发。⇒ 既有错误路径的触发条件与顺序**逐字不变**，新 400 只可能出现在"既有路径不可能报错的场景"（那是全新对话，且校验在写库之前 ⇒ **不产生任何对话**）。
- **T-02 归属列 DDL 与关联**：`chats.project_id TEXT NOT NULL REFERENCES projects(project_id)`；`ensureChat` 的插入列与参数同址增列；`insertInput({chatId, projectId, …})` 的 `projectId` **必填**。旧结构检测与重建**不在本卡**（→ F08）。
- **T-01 关联方式**：外键指向 `projects.project_id`（详见 F01 的「架构落地」与 `architecture.md` §2.1）；`project_id` **不进** `CHAT_COLUMNS` ⇒ 既有 `/api/chats` 与 `/api/chats/<id>` 的响应字段面零变化（需要归属时另用 `projectByChat` 一条语句）。
- 数据层保证：`NOT NULL` + 外键 + `PRAGMA foreign_keys=ON` ⇒ 验收 3（不存在无项目对话）由结构与 SQLite 保证，不靠应用层自律。
