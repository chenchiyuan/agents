# F08：旧结构对话库启动即重建（旧对话清空）

**功能 ID**: F08
**来源**: `demand.md` W6（P-5 用户裁决，与原推荐相反）；决策 D-5；约束 C-3 / C-5 / C-7（必然变更点 ④）；边界 N7；效果 E6 / E4（部分）
**迭代**: 0017-project-workspace
**技术锚点（引用 `demand.md` §3 只读实测，非本阶段决策）**: F-1（`chats` 列集）、F-2（既有"按列存在性守卫的幂等迁移"机制，当前 2 条守卫）、F-3（对话库落点 = 包根 `data/sql.db`，本机实测存在 73,728 字节真实历史库）、F-3b（既有测试对 schema 与迁移有逐位断言）、F-22（SQLite 无法为已有非空表添加 `NOT NULL` 列，故"幂等加列"与"必填归属"不可兼得）

---

## 用户价值

升级不用手工清库——系统自己把旧结构的库换成新结构，不留下"一半旧一半新"的中间状态，也不会启动就崩。

## 验收标准

1. **旧结构可被识别**（W6）：启动时，若对话库为旧结构（对话表缺少项目归属列）→ 判定为旧结构。
2. **启动即重建、服务可用且无报错**（W6 / E6）：判定为旧结构后删除旧库、创建全新结构，服务正常启动；此时项目列表与对话列表为空，新建项目与新建对话可用，**无报错**。
   *判定*：拿一份**不含项目归属列的旧库**启动 → 启动成功；用 sqlite 查 `pragma_table_info('chats')` 与两张表行数。
3. **旧对话不残留**（W6 / E6）：重建后历史对话不再存在（对话行数为 0），不为其创建任何兜底归属。
4. **新结构含必填归属**（W6 / E4 / E6）：新库中存在项目表，且对话表的项目归属列为**必填**（不可为空）。
5. **新结构不被重建**（W6 的"缺列才重建"条件 / E6 后半）：已是新结构的库再次启动不发生重建、既有数据保留；删除库文件后重启行为相同（新建空库 + 可用）。
   *判定*：连起两次 + 删库再起一次，三次行为一致。
6. **无兼容路径**（N7 / C-5）：不为旧对话做数据迁移 / 回填 / 造兜底项目；不为项目归属列保留"补列"路径。

## 边界（不包含）

- 不含项目 / 对话本身的功能语义（→ F01~F05）。
- **不做旧对话迁移、不造兜底项目、不保留旧 schema 兼容分支**（N7 / C-5）。
- **不把对话库搬进项目仓库**：对话库仍是本机运行时的对话真源，落点不变（C-3 / M-4）。
- 不含对话库之外的数据清理（不触碰其它文件）。
- 不含"备份 / 可恢复"能力：旧库在首次启动时被自动销毁且**不可恢复**，是 W6 的明示后果（E6 可裸判定）。
- **不得为项目归属列恢复"缺列补列"可达路径**（C-5）；该机制在新 schema 下的存废留架构（**T-03**）。
- 不含对话库落点变更、不含多项目共用一台 web 时的库分片（C-3）。

## 架构落地（阶段 3 已填，见 `architecture.md` §2.1 / §2.2；产品维度未改一字）

- **T-02 归属列 DDL**：`chats.project_id TEXT NOT NULL REFERENCES projects(project_id)`（插在 `chat_id` 之后；既有 9 列相对顺序逐位不变）+ `projects` 表（`project_id TEXT PRIMARY KEY` / `name TEXT NOT NULL` / `repo_url TEXT NOT NULL UNIQUE` / `created_at INTEGER NOT NULL`）；建表仍用 `CREATE TABLE IF NOT EXISTS`（幂等 ⇒ 验收 5 前半：已是新结构的库不重建、既有数据保留）。
- **T-02 触发点 = `persist.openDb()`**（**全仓唯一开库点**，`oamp web start` 必经）：检测与重建写在这里，**不写在 `startWeb`**——否则会制造第二个真源，且测试直连 `openDb()` 时行为会与线上分叉。
- **旧结构判据（唯一真源）**：`pragma_table_info('chats')` **有行 且 无 `project_id` 列** ⇒ 旧结构（验收 1）；`chats` 表不存在（首次运行 / 删库后）⇒ 非旧结构，正常建新库（验收 5 后半）。**不引入** `user_version` / 迁移表（沿用既有判定函数）。
- **T-02 动作粒度 = 删除库文件本体后重开**：`db.close()` → `rmSync(dbPath, { force: true })` → `new DatabaseSync(dbPath)`（**不是** `DROP TABLE` 重建，也不是"清空行"）。只删主库文件即可——检测发生在本次**成功 open 之后**，SQLite 在 open 时已完成热日志回滚 ⇒ 不存在需要一并清理的 `-journal`（多删一类文件是为不可能发生的场景写代码，YAGNI）。**不做备份**（验收 3 / 6：无兼容路径、不可恢复，W6 明示后果）。
- **T-03 缺列补列机制的存废 = 删除**（`MIGRATIONS` + `migrate()` 一并删除）：新 schema 下两条旧守卫**均不可达**——① 缺 `archived_at` / `context_released` 的库必然同时缺 `project_id`（必然走"删库重建"）；② 有 `project_id` 却缺其它列的库**不存在任何产生路径**。保留即死代码，并且会诱导未来把"补列"语义恢复回来（C-5 明确禁止）。
- **验收 2 / 4 / 6**：重建后服务正常启动、项目列表与对话列表为空、旧对话行数为 0、不为旧对话造兜底归属、`chats.project_id` 为 `NOT NULL` 且存在 `projects` 表（E4 / E6 可 `sqlite` 直读核对：`pragma_table_info('chats')` + 两表行数）。
- **观测面与三次启动对拍**：连起两次（第二次不重建、数据保留）+ 删库再起一次（新建空库可用）（验收 5）；是否额外打印一行 stdout 告知重建，见 `architecture.md` §10.3 **D-02**（待主 agent 确认）。
