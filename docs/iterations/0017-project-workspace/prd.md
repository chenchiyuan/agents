## 本次迭代边界说明

### 包含

- **项目实体**（W1 → F01）：项目可创建、可列出；最小创建输入 = 一个仓库地址（名称可留空、缺省取地址尾段去尾部 `.git`）；项目四要素 = 唯一标识 / 名称 / 仓库地址 / 创建时间，**本地路径不入库**；唯一键 = 原样地址字符串，重复创建 → `409 CONFLICT`；不做归一化、不校验可达性。
- **对话归属项目**（W2 → F02 / F03）：每个对话必须归属一个项目（数据层亦为必填，不存在"无项目对话"）；新建对话缺项目归属 → `400 INVALID_PARAM`（含今天会凭空建对话的既有消息路径）；对话列表**以项目为范围**（跨项目不混列），缺项目参数的列表查询 → `400`（`派生`，回退口见「疑问与越界」1）。
- **项目层 UI**（W3 → F04 / F05）：独立**首屏项目列表页**（新建项目 / 进入项目，每行 = 项目名 + 仓库地址 + 对话数 + 最近活动时间，后者零新增存储）→ 进入项目后是该项目的**工作台**（沿用既有三栏布局），顶栏显示当前项目并提供**返回项目列表**入口；不选项目时看不到对话、也不能发消息。
- **项目上下文透传**（W4 → F06 / F07）：派发任务携带结构化项目上下文 = **项目名 + 仓库地址 + 一段相对工作约定**（本地不存在则 clone 至自选落点 / 在该仓库根目录工作 / 迭代产物写入该仓库）；**载体 = 派发载荷的结构化项目字段 + agent 侧注入**（用户消息正文不被写入任何前缀）；**范围 = 常驻与一次性两条 LLM 路径携带，shell 路径不携带**；**不承诺 agent 自动在项目根目录工作**（C-4 / N14）。
- **产物落点约定**（W5 → F07）：PR / commit / 迭代文档 / 分支落**该项目仓库**；本迭代**不在运行时建"迭代"实体**（层级 = 项目 → 对话两级）。
- **旧对话清空**（W6 → F08）：启动时探测旧结构（对话表缺项目归属列）→ **删库重建**全新结构（归属列必填）；不做数据迁移、不保留无归属历史对话、不留兼容路径。⇒ **本机现存 73KB 真实历史库在首次启动时会被自动销毁、不可恢复**（E6 裸判定）。
- **既有约束保持**（N13 / C-6 / C-7 → F09 / F10）：统一错误契约、无 405 的 404 兜底、SSE 语义、归档 / 关闭 / 激活 / 改名语义逐条保持；新增项目类接口自动出现在文档页 / 调试台 / 索引文件三处，0016 三条漂移锁与零依赖锁继续通过。

## 拆分理由（原子粒度判断）

**总原则：按"可独立出现的失败"拆卡；保证项按"独立可被破坏的约束"单列。**

- **W1 一张（F01）**："创建"与"列出"是同一交付面（项目实体及其查询面）、同一失败语义（建不出来 / 列不出来都意味着项目层不存在），且 E2 的两次创建判定需要两者同时在场；不再细分为两张。
- **W2 拆两张（F02 / F03）**：W2 有两个观察面——**写入侧**（新建对话必须带归属）与**读取侧**（列表以项目为范围）。失败互不蕴含：新建强制了但列表仍跨项目混列 → F03 红；列表范围对了但既有"凭空建对话"路径仍在 → F02 红。两者的判定载体（创建请求 / 查询请求）与裸判定（E4 行归属 / E3 切换可见性）也不同。且 F03 承载一条**独立于 W2 主体的 `派生` 口径**（缺参 `400`，带留痕与回退口），需要独立可回退的位置。
- **W3 拆两张（F04 / F05）**：两个页面层级、两个失败模式——"进不去项目层 / 未选项目竟能发消息"（E1）与"进了项目却不知道在哪个项目、退不回去"（W3 顶栏与返回）。合并会让"列表页可用但工作台缺返回入口"变成不可独立判定的部分完成。
- **W4 拆两张（F06 / F07）**：W4 的**载体层**（载荷怎么带、哪些路径带、原文是否被污染）与**内容层**（带什么、注入到哪、约定怎么写）失败互不蕴含：载荷字段齐备但 agent 侧未注入 → F07 红、F06 绿；内容正确但前缀被写进用户消息正文或 shell 路径也带了 → F06 红、F07 绿。E9（原文不被污染）正是这次拆分的裸判定锚点：它锁的是**载体选择**，与"内容写什么"正交。
- **W5 并入 F07 而不单立**：W5 的可验证内容 = 那段相对工作约定里的一条（"docs / PR / commit / 分支写入该仓库"），与 W4 的内容层是同一段文本、同一注入动作；单立会产出两张在同一字符串上重复断言的卡。W5 的另一半（不建"迭代"实体）是**边界**（不做某事），落 F07 边界 + 全局边界即可，不构成独立交付物。
- **W6 一张（F08）**：旧结构识别 → 重建 → 新结构可用 → 新结构不被重建，是同一条件的四步连贯行为，共享同一失败语义（"启动即崩"或"半新半旧"），不可独立拆分交付。
- **F09 单立（回归锁）**：C-7 明确要求"与项目维度无关的既有可观察行为必须零变化"，且本次改动**新引入**了 4 处必然变更点（C-7 逐条列出）。若不单立，"顺手改坏既有行为"与"合理变更"之间没有验收边界，回归风险无人承载。体例直接沿用 0016 的 F02（回归卡）与 0015 的 F08（连接语义不变）。
- **F10 单立（登记义务与工程锁继承）**：C-6 是**既有硬约束的继承**（0016 三条漂移锁 + 零依赖锁），失败模式与 F09 正交：既有行为可以全对而新接口漏登记（锁红），也可以登记齐备而既有行为被改坏。E8 是其专属裸判定（刷新三面 + 跑测试）。体例沿用 0016 的 F06（漂移锁）。
- **未单立的项**：① `demand.md` §3 列出的"已知受影响的既有文件"（数据层 / HTTP 层 / 派发层 / UI 层 / 契约文档 / 测试文件）属实现的已知成本，不是独立功能能力，落各卡 `[架构待填]` 与 F09 / F10，不另立卡；② "本迭代文档不迁移"（N15）、"对话库不搬"（C-3）是全局边界，落本文件，不立卡。
