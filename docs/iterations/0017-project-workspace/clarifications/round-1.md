### 维度 2 · 逻辑闭环（why → what）

- **Why**：① 对话无根（产物无处安放）；② 项目是长期容器、对话是工作单元；③ hub 无法操纵 agent 环境，只能传上下文。
- **五条 what 逐条可推出**（详见 `demand.md` §4.2 对照表）。
- **产出三处缺口**：
  1. `POST /api/messages` 今天可凭空建无项目对话（`web.js:644`）⇒ **强绑不是形态偏好，是 S-1 的必要条件**。
  2. 「注入上下文」**推不出**「agent 自动在项目根工作」——现状 cwd 是进程级常量（`agent.js:589`）、工具开关随实例固化 ⇒ **升格为 C-4 的显式能力边界**（防下游误读）。
  3. 新增 HTTP 面必须继承 0016 的三条漂移锁 ⇒ 不是新需求，是既有工程约束。

### 维度 3 · 边界完整性

- 用户明说边界 6 条（不引 GitHub 集成 / hub 不操纵环境 / 本地落点归 agent / 产物落项目仓库 / 不装 `.pb-agents` / 清空旧库）→ 全部落入 N1~N10。
- 推导边界 N1~N13 每条附"为什么这次不做"。
- **主动收敛判断 5 条**：去掉"删除/改名"（级联决策面）、"URL 归一化"（独立课题）、"权限/多用户"（沿用既有边界）、"迭代实体"（运行时塞工作流概念）——最小闭环均成立；**保留"清空旧库"**——不可延后，否则空值分支成为永久复杂度税。

## 三、本轮的提案形态（遵守"不空手提问"）

全部 11 条 P 项都是 **具体填法 + 理由 + 已否决备选 + 推荐值** 四件套：

- 用户只需回答「**按推荐**」或「**改成 X**」，无需从零生成答案；
- 其中两条是**真正需要拍板**的（形态会直接改变实现面）：**P-4**（项目上下文的内容与注入载体）与 **P-5**（旧库清空的执行方式）；
- **P-4 备注**单独列出「是否要求 agent 自动在项目根目录工作成为本迭代承诺」——这是用户期望与现状能力差额最大的一处（C-4），建议主 agent 明确念给用户听。
