# F04：阶段 5 解锁判据改为"合并进迭代分支"

## 功能 ID
F04

## 用户价值
确保依赖解锁式并发调度机制在两层分支结构下正确运作：PR-B 的 worktree 能从"已合入 PR-A 的迭代分支"拉出，看到 PR-A 的代码产出。

## 验收标准
- [ ] workflow-pb.md §调度指南·阶段 5（依赖解锁式并发调度）中关于"合并进主分支"作为解锁条件的表述改为"合并进迭代分支"（或等效表述）
- [ ] workflow-pb.md §调度指南·阶段 5 中关于"为什么必须以合并作为解锁条件"的技术约束解释同步更新，能让读者理解：PR-B 的 worktree 分支必须从"已经合入 PR-A 之后的迭代分支"拉出
- [ ] 该改动与 F03 的"PR 合并目标改为迭代分支"逻辑一致，能让整个依赖解锁机制在两层结构下闭环
- [ ] 检查 `.claude/skills/workflow-pb/SKILL.md` 中关于"阶段 5 只以合并进主分支解锁"的 CRITICAL 声明和 Important facts 描述，须同步改为"合并进迭代分支"，避免协议文件与 skill 文件表述冲突

## 边界（不包含）
- 不包含迭代分支的命名和概念定义（由 F01 处理）
- 不包含 PR worktree 合并目标的基础改动（由 F03 处理，F04 只处理解锁判据在并发调度中的应用）
- 不改变 `batch` 字段"不作为调度依据"的既有定位

## 架构维度

已补全为决策 D3（见 `architecture.md` §决策 D3）：

- **核心解锁判据改写**：`workflow-pb.md`「调度指南 §  阶段 5（PR 实现）：依赖解锁式并发调度」步骤 2 中"所依赖的 PR 均已**合并进主分支**的已解锁 PR"改为"所依赖的 PR 均已**合并进当前迭代的迭代分支**的已解锁 PR"；步骤 2 末尾"不因此放宽'合并进主分支才算解锁'这一条件"改为"不因此放宽'合并进迭代分支才算解锁'这一条件"。
- **技术约束解释改写**：同小节「为什么必须以"合并进主分支"作为解锁条件，不是"dev 自称完成"」段落，"主分支"二字出现两次，全部改为"迭代分支"（或"当前迭代的迭代分支"）——原文"PR-B 的 worktree 分支必须是从'已经合入 PR-A 之后的主分支'拉出来的，否则 PR-B 的子 agent 在自己的分支里根本看不到 PR-A 的代码"，改为"……从'已经合入 PR-A 之后的迭代分支'拉出来的……"。
- **并发槛位算法补位条件改写**：同小节「并发槛位算法」最后一段"爬升带来的新增槛位，仍然只能分配给依赖已合并的排队 PR，不改变「合并进主分支才算解锁」这一前提"改为"不改变「合并进迭代分支才算解锁」这一前提"；再次出现的"不得因为槛位空闲而放宽解锁条件去提前派发依赖未合并的 PR"改为"不得因为槛位空闲而放宽解锁条件去提前派发依赖未合并进迭代分支的 PR"（使限制的具体对象明确化）。
- **SKILL.md 同步**（已在 F03 描述，此处交叉引用）：见 F03 §架构维度 的 SKILL.md 改动清单，两者是一体的——F03 负责 worktree base 和合并目标，F04 负责解锁判据在并发调度中的应用。
- **progress-observer 核实方式微调**：`workflow-pb.md`「可观测性：progress-observer 自动/按需触发」小节中，`progress-observer` 核实"依赖的 PR 是否真的已经合并"时，检查对象由 main 分支改为迭代分支——如 `roles/progress-observer/progress-observer.md`「PR 依赖核实」示例表（`:100`）"`git log main --grep="pr-001"` 找到 commit abc123"这一行，语义上对应改为"`git log iteration/{迭代ID} --grep="pr-001"`"（修正：原稿误写行号 `:24`，`:24` 实际是 character 字段中的叙述性文字"要去检查 pr-001 是否真的已经合并进主分支"，不是可核对的示例表格行；真正的示例表在该文件「PR 依赖核实」小节，`:100` 行）。此项不改动 progress-observer 角色文件本身（已是通用的"核实一手记录"能力），只在 workflow-pb.md 调度指南中补充一句"当前迭代存在迭代分支时，核实合并状态的 git log 命令以迭代分支为基准，而非 main"。
