# F02：阶段 1 创建迭代分支机制

## 功能 ID
F02

## 用户价值
确保在需求收敛完成后立即创建迭代分支，为后续 PR worktree 提供正确的 base，避免在 PR 规划阶段才发现缺少迭代分支。

## 验收标准
- [ ] workflow-pb.md §阶段定义·阶段 1 的"推进条件"或相关章节明确要求：确认迭代名后立即创建 `iteration/{迭代ID}` 分支
- [ ] workflow-pb.md §调度指南·启动工作流，或§调度指南·阶段 1~4 推进中明确说明迭代分支创建时机是阶段 1 完成后
- [ ] 该机制描述能回答："在哪个阶段、什么时间点、由谁（主 agent 还是执行角色）创建迭代分支"

## 边界（不包含）
- 不包含迭代分支的命名规范本身（由 F01 处理）
- 不包含迭代分支作为 PR worktree base 的规则（由 F03 处理）
- 不包含迭代分支最终合并进 main 的机制（由 F05 处理）

## 架构维度

已补全为决策 D1（见 `architecture.md` §决策 D1）：

- **创建时机**：`workflow-pb.md`「调度指南 § 启动工作流」新增一步，在阶段 1（需求收敛）完成、`demand.md` 通过阶段 1 推进条件之后，主 agent 立即创建迭代分支——不等到阶段 4（PR 规划）才创建。
- **创建方（谁执行）**：主 agent（不是执行角色）。
- **创建基点**：当前 `main` 分支的最新提交（HEAD）——迭代按顺序推进，main 在两次迭代之间始终代表"已完成、已验证"的最新稳定状态，不需要引入更复杂的"指定历史提交点"概念。
- **具体 git 命令**：`git branch iteration/{迭代ID} main`（不 checkout，只建分支指针），随后主 agent 将自己的工作区 `git checkout iteration/{迭代ID}`——此后整个阶段 2~5 期间，主 agent 根目录的当前分支保持在该迭代分支上，直到阶段 6 终验证通过、执行 F05 的最终合并时才切回 `main`。
- **记录**：`status.md` 头部新增 `**迭代分支**` 字段行，创建后立即写入（见 F06 §status.md 字段扩展）。
