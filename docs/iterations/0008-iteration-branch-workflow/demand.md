## 澄清依据

### 1. 核心诉求（`user_confirmed`，用户原始表述直接给出）

Git 开发流程新增一层"迭代分支"：demand 阶段确认迭代名后新建该分支；后续开发和 PR 合并都指向这个迭代分支；全部确认之后，再把迭代分支合并进 main。现状问题：目前大多数情况是 PR 直接合并进 main，没有经过这层迭代分支。

### 2. 现状核查（客观事实，非协商结论，我在 Context 阶段独立核实）

- `workflow-pb.md`（当前仓库版本 v0.7.0，`roles/workflow-pb/workflow-pb.md`）规则 A（worktree 隔离）目前定义"从阶段 4（PR 规划）完成之后……不得直接在主分支（main/master）上提交"，判断方式是"所有变更必须通过 PR 合并进主分支"——协议里"主分支"= main，没有中间层。
- 阶段 5「依赖解锁式并发调度」的解锁判据同样是"合并进主分支"（原文："必须以'合并进主分支'作为解锁条件……这是技术约束，不是可选的保守做法"）。
- `git log --merges` 核实：最近两次真实合并（0005-pr-concurrent-execution、0007-workflow-history-log 的 PR-001）都是 `merge --no-ff` 直接进 main，未经过任何迭代分支。
- 仓库存在孤立分支 `iteration/0004-model-dispatch`，只比 main 多 1 个 commit（`4a524a4 docs: define model dispatch PR plan`），`git merge-base --is-ancestor iteration/0004-model-dispatch main` 判定为 false（未被合并）。命名格式是 `iteration/{迭代ID}`。这是历史上唯一一次"迭代分支"命名的实例，但从未固化进协议、也未走完整合并流程。
- `status.md` 的"PR 实现子状态"表里，"worktree 分支"列的命名惯例并不统一：0005 迭代用的是 `iteration/0005-pr-001-concurrent-dispatch-protocol`，0007 迭代用的是 `feat/0007-pr-001-history-log-protocol`——两种前缀都出现过，协议本身未强制规定 PR worktree 分支的命名前缀。

### 3. 问题动机 / Why（`user_confirmed`，2026-09-07）

main 分支应该始终代表"已完成、已验证"的稳定状态；PR 直接合并 main，意味着单个迭代还没走完全部阶段（比如阶段 6 独立验证还没通过、或用户还没最终点头）时，其中间产出的代码变更已经落在 main 上——一旦该迭代中途被终止或需求有变，main 已经被未完成的变更"污染"，难以干净地整体回退或搭置。这是"为什么要多加一层"的核心理由，用户已确认。

### 4. 迭代分支与 PR worktree 分支的层级关系（`user_confirmed`，2026-09-07）

形成 `main ← 迭代分支 ← PR worktree 分支` 两层结构——PR worktree 分支的 base 从 main 改为迭代分支，PR 合并目标也从 main 改为迭代分支。这会改变现有「规则 A」定义里"主分支"这个词的指代对象（从"main"变成"当前迭代的迭代分支"），是对现有协议措辞的实质性重写。用户已确认采用此两层结构。

### 5. 阶段 5 解锁判据同步改动（`user_confirmed`，2026-09-07，结构性推论）

现有「依赖解锁式并发调度」的核心不变量原文写的是："必须以'合并进主分支'作为解锁条件，不是'dev 自称完成'……这是技术约束，不是可选的保守做法"——理由是 PR-B 的 worktree 分支必须从"已经合入 PR-A 之后的主分支"拉出来，否则 PR-B 看不到 PR-A 的产出。

由于第 4 条两层结构已确认，这条规则里"主分支"必须相应改成"当前迭代的迭代分支"——否则 PR-B 永远等不到解锁：main 只会在整个迭代分支合并时才更新一次，不会随着迭代内每个 PR 逐一更新。这不是可以回避的可选项，是结构性推论：两层模型一旦成立，解锁判据**必须**同步改成"合并进迭代分支"，否则并发调度机制在新模型下直接失效。用户已确认此结构性推论及其对协议核心不变量的改动。

### 6. 迭代分支创建时机（`user_confirmed`，2026-09-07）

demand 阶段（阶段 1）确认迭代名后，立即创建该迭代分支——不是等到阶段 4（PR 规划完成、第一个 worktree 要拉出来）才创建。用户已确认。

### 7. 迭代分支合并进 main 的触发时机与触发方（`user_confirmed`，2026-09-07）

阶段 6 独立验证结论为 pass 之后，主 agent 自动执行合并——与现有"PR 验收通过→主 agent 自动 merge 进主分支"的既有模式保持一致，不额外引入新的人工关卡类型。用户已确认采用此方式。

### 8. 孤立分支 `iteration/0004-model-dispatch` 的处理（`user_confirmed`，2026-09-07，非本次迭代范围）

不在本次迭代内处理，留给后续单独清理。这是历史遗留的技术清理项，不影响本次"是否新增迭代分支层"的核心决策。用户已确认不纳入本次范围。

### 9. 生效范围（`user_confirmed`，2026-09-07）

延续 `workflow-pb.md` 现有"约束生效范围"原则："仅从下一个使用本工作流的迭代起生效，不追溯已完成迭代"。用户已确认延续此原则，不对已完成迭代（0005/0007）进行追溯或补建历史分支。

### 10. 逻辑闭环检查（六维诊断第 2 维，已满足）

用户给出的方案雏形本身相当具体（时间点、合并目标、最终合并动作都说了），第六维"方案雏形"已经被用户主动满足，不需要额外发问"你有没有想法"。方案雏形内部第 5 条指出的结构性矛盾（只加"迭代分支"这一层、不同步改动阶段 5 解锁判据，会导致并发调度失效），已在用户确认层级关系时同时确认了解锁判据必须同步改动。该结构性矛盾在 demand 阶段已被识别并完成确认，不会留到架构阶段才发现。

## 需求结论

### 1. 目标与价值（`user_confirmed`，2026-09-07）

让 main 分支始终只包含已完成、已通过验证的迭代产出，避免单个迭代在阶段 6 独立验证通过、用户最终确认之前，其中间代码变更就已经通过 PR 直接落在 main 上——一旦该迭代中途被终止或需求有变，main 已经被未完成的变更"污染"，难以干净地整体回退或搭置。

### 2. 做什么（`user_confirmed`，2026-09-07）

- 新增"迭代分支"概念，命名格式 `iteration/{迭代ID}`（复用仓库里孤立分支 `iteration/0004-model-dispatch` 已经出现过的命名先例）。
- demand 阶段（阶段 1）确认迭代名后，立即创建该迭代分支。
- PR worktree 分支的 base 和合并目标改为迭代分支（形成 `main ← 迭代分支 ← PR分支` 两层结构）。
- 阶段 5"依赖解锁式并发调度"的解锁判据同步从"合并进主分支"改为"合并进迭代分支"（结构性推论，两层模型一旦成立，此条必须同步改，否则并发调度失效）。
- 迭代分支最终合并进 main 由主 agent 在阶段 6 独立验证通过后自动执行，与现有"PR 验收通过→自动 merge"模式保持一致。

### 3. 不做什么（`user_confirmed`，2026-09-07）

- **不在本次处理孤立分支 `iteration/0004-model-dispatch` 的清理动作**。理由：这是独立的历史遗留技术清理项，不影响本次"是否新增迭代分支层"的核心决策，用户已确认留给后续单独清理。
- **不改变现有「规则 B：PR 文件前置」的字段格式本身**。理由：用户的诉求是分支层级和合并目标，没有提及 PR 文件格式（七字段规范）需要变化。
- **不追溯已完成迭代**，延续 `workflow-pb.md` 现有"约束生效范围"原则。理由：过往历次协议变更均延续此原则，用户已确认本次不对已完成迭代（0005/0007）进行追溯或补建历史分支。

### 4. 大概怎么做（仅记录已确定的机制轮廓，不锁定架构细节）

- 命名：`iteration/{迭代ID}`。
- 创建时机：demand 阶段确认迭代名后。
- 层级关系、解锁判据改动方式、合并触发条件——这些具体机制设计留给阶段 3（技术架构）在关键分叉点确认后处理，本合同只锁定"新增迭代分支这一层"这个方向性事实。

### 5. 达到什么效果（裸判定：不问作者也能判断真假）

- 任选一个走过本次新协议的迭代，`git branch` 或 `git branch -a` 中能观察到一个 `iteration/{该迭代ID}` 分支，其创建时间点在该迭代 `status.md` 记录"阶段 1 完成"之后、"阶段 2 开始"之前（可与 `history.md`/`status.md` 更新日志交叉核对）。
- 该迭代结束后，`git log --merges` 能观察到一次"迭代分支 → main"的合并记录（commit message 或 `git merge-base --is-ancestor` 可验证该迭代分支确实被合并进 main，不再像 `iteration/0004-model-dispatch` 一样孤立悬挂）。
- 该迭代内所有 PR 的合并目标（`git log` 追溯每个 PR merge commit 的目标分支）指向迭代分支，不指向 main。
- 该迭代内如有 ≥2 个可并发 PR，PR-B 的 worktree 分支创建时间点晚于 PR-A 实际合入迭代分支的时间点，可验证解锁判据确实在迭代分支这一层生效。

### 6. 为什么这么做（`user_confirmed`，2026-09-07）

用户在实际执行中观察到协议与实践脱节（协议未定义迭代分支，实践也从未使用过迭代分支，PR 全部直接合并 main），这是本次需求的直接触发点。更深层的"为什么"已经用户确认：main 分支应始终代表已验证的稳定状态，避免未完成迭代的变更过早落地——这是后续架构阶段设计取舍的依据。
