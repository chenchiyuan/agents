### 3.1 agent 生命周期与 hub 能力面

| # | 事实 | 锚点 |
|---|---|---|
| F-1 | 连接只有**一种方向**：agent 主动连入（UDS）→ `agent.register{instance_id}`；**agent 只报 instance_id，session_id 由 Router 生成**（`registry.newSessionId()`）；校验 `isValidInstanceId`（1..64 可打印 ASCII）；同名再注册 = **latest-wins 顶替**（通知旧连接 `agent.replaced` → 50ms 后 destroy 旧 socket，旧 agent 退出且不重连） | `oamp/src/registry.js:7-21`、`oamp/src/router.js:109-155` |

### 4.2 逻辑闭环 —— why 能否推出 what

**Why（改判后）**：用户主动把 hub 的职责收窄为**单纯的连接 / 路由中心**——agent 的创建与终止已经有承担者（`oamp cluster` 与人工终端，F-7），hub 再插一脚会把 Router 变成进程管理器，牵出一串与"路由中心"无关的问题（来源判定、拒绝重连、跨机权责、终止序列）。但收窄后仍有三件事必须做，因为它们**都不依赖"hub 管生命周期"**：

1. **可见性**：现在只有一个数字（`N agents online`），看不到是谁、也看不出谁刚掉线（F-10）；
2. **常态开销**：常驻实例的心跳固定 10s 一发，长期无人使用时是纯开销（F-2）；用户明确要"不用频繁发送心跳"；
3. **程序可用性**：所有能力都困在浏览器里，codex / omp / claude 无法驱动（F-11/F-15）。

逐条对照：

| 保留项 | 从 Why 能否推出 | 结论 |
|---|---|---|
| 只读 agent 列表 | 能。"连接/路由中心"的第一价值就是**看得见连接**；只读不触碰生命周期，与收窄后的职责严格一致 | 闭环成立 |
| 心跳空闲降频 | 能。它优化的是 **agent 自身的常态开销**，与 hub 是否管生命周期无关 | 闭环成立 |
| 开放接口 + 文档 | 能。"路由中心"要能被程序接入才成立；双向（发指令 + 订阅）是"接入"的最小完整形态 | 闭环成立 |

**必须显式记录的一处更新**（改判推翻了旧版的一个判断）：旧版论证"心跳降频的收益依赖 hub 能拉起更多实例"。**该前提已随 R-1 取消而失效**——降频的收益来源改为**用户自己用 `oamp cluster` / 终端起的常驻实例**，与 hub 无关；这反而使本迭代的三块内容彼此**完全独立**（列表 / 心跳 / 接口），不存在跨块耦合，可以各自验证。

### 4.3 边界完整性

- 用户**明说**的边界：**hub 不启动 agent、不关闭 agent**（R-1/R-2，这是本迭代最强的边界，直接写进 N1/N2）；"网页上有的功能"（R-4，接口范围的上界）；"不用频繁发送心跳"（D-3，降频是目的不是纯调参）。
- 其余边界（N3~N13）为推导所得，逐条给"为什么这次不做"。
- **主动的边界收敛判断**：需求收窄后新增了三处"看起来相关但不做"的分支——展示 agent 来源（N3，无台账即无依据）、agent 详情页（N10）、对话功能的语义变更（N13）；去掉它们，三块内容的最小闭环仍成立。

| # | 矛盾 / 约束 | 处理 |
|---|---|---|
| **C-2（生效，本迭代唯一硬技术约束）** | **心跳降频与租约直接冲突**：空闲心跳 60s > 租约 30s（F-2）→ agent 会被判 `offline` + 断连；协议**无 renew**（F-3），改间隔只能重 register 而重 register 会换 session_id（影响对话绑定）；另有不变式 `LEASE_ALARM`（租约 ≥ 2× 间隔，F-4） | **需求层只锁三条约束，不指定机制**（用户 R-3 明确由架构阶段解决）：① 降频**不得使 agent 被判 offline**（用户可见状态不因空闲降级）；② 降频**不得改变 agent 身份、不得中断对话绑定**（session 不因降频更换）；③ 服务端租约与心跳间隔必须联动，维持"租约 ≥ 2 × 间隔"的不变式。机制选型（心跳带状态 / 响应协商 / 服务端策略）留架构（参考视角 §4.6-B1） |

| C-5（生效） | **零鉴权 + "让其他客户端接入"**：F-13 明示无鉴权、F-14 明示跨机另有要求 | 已由 TC-06 消解：本迭代 = **同机接入、不新增鉴权**；跨机不做 |

### 4.5 可验证性（裸判定测试）

第二段 §4 的 E1~E9 逐条通过裸判定测试：判定者不问作者、不读背景，仅凭**列表 UI 与 `oamp status` 逐项比对 / 心跳记录时间戳计数 / 另一终端起停 agent 后浏览器不刷新观察 / 原样照抄文档示例调通 / 界面上找不到启停入口**即可判真假；**无"正常工作""体验良好"类主观词**。

## 3. 大概怎么做（产品级形态；接口路径、模块划分、参数命名、机制选型均留架构阶段）

- **agent 只读列表**（W3/W4）：数据面**已经齐备**——`GET /api/agents` ← `router.status` 节点表（含 instance_id / state / 心跳时间，`实测` F-9/F-11）；主要工作在**前端**：把死链 `Agents`（`index.html:14`）变成可点击入口、把 `setConn` 的计数文案（`app.js:45-50`）接上展开动作、并接 W6 的全局事件流自动刷新。面板形态（浮层 / 侧栏 / 页签）与字段命名留规格 / 架构（参考视角 B-2）。

## 5. 为什么这么做

- **为什么收窄到"连接 / 路由中心"**（`user_confirmed` R-1/R-2）：agent 进程生命周期已有明确承担者（`oamp cluster` 与人工终端，F-7）；hub 接管它需要额外引入"来源判定 / 拒绝重连 / 终止序列 / 跨机权责"一整串问题（旧版 TC-03 / TC-08 / C-1 / C-3 就是这些复杂度的证据）。**用户主动砍掉这部分，等于把这次迭代的验证面砍掉一半**，剩下三块各自独立、各自可验。
- **为什么保留只读列表**（R-2）：它不触碰生命周期，却是"路由中心"最直接的可用性提升——现在只有一个数字，看不到是谁、也看不出谁刚掉线（F-10）。
- **为什么保留心跳降频**（D-3 / R-3）：常驻实例固定 10s 一发心跳（F-2），长期无人使用时是纯开销；这一收益**不依赖 hub 管生命周期**（§4.2 已更新旧版论证的失效前提）。
- **为什么把 C-2 写成硬约束而不是直接定机制**（R-3 的明确要求）：空闲 60s > 租约 30s、且协议无 renew（F-2/F-3），任何机制都必须在"不判 offline / 不换 session / 租约联动"三条约束下成立；在需求层挑机制会越过架构阶段的职责。三条约束已由 E4/E5/E6 兜住可验证性。
- **为什么保留开放接口与文档**（D-4/D-5）：能力困在浏览器里，codex / omp / claude 无法驱动（F-15）；"双向 = 发指令 + 订阅"是"接入"的最小完整形态。
- **为什么列表不展示来源、不做详情页**（N3/N10）：没有启动台账就没有可靠来源；派生指标属观测体系的独立课题。
