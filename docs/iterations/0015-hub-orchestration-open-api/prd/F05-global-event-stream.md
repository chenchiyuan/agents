# F05：全局事件流（不依赖单个对话，覆盖 agent 上下线）

**功能 ID**: F05
**来源**: `demand.md` W6②③；澄清 M-6；矛盾 C-4；效果 E3（数据来源）、E7（订阅部分）；边界 N5 / N8 / N13；现状缺口 F-12（现有订阅强制要求对话标识）
**迭代**: 0015-hub-orchestration-open-api

---

## 用户价值

订阅一次就能一直收到「谁上线了、谁下线了」，不用反复去问、也不用先打开某个对话——网页上的列表能跟着变，外部程序也能跟着变。

## 验收标准

1. **订阅不依赖具体对话**：客户端可以在**不指定任何对话**的情况下建立订阅，并持续收到事件（W6③ / M-6 / C-4）。
   *判定*：不带对话标识建立订阅，连接保持且能收到事件；不因缺少对话标识而被拒绝或立即断开。
2. **覆盖 agent 上线 / 下线**：在另一终端启动一个 agent → 订阅端收到「上线」事件；停止一个 agent → 订阅端收到「下线」事件（W6③ / M-6 / E7 的订阅部分）`[user_confirmed MI-06]`。
   *判定*：两个方向各做一次，订阅端在 **5 秒内**收到对应事件 `[user_confirmed MI-06]`；事件内容**足以识别是哪个实例、是上线还是下线** `[user_confirmed MI-06]`；与另一终端的集群状态查询结果对照一致（不多发、不漏发）。
3. **既有按对话订阅形态不变**：原有的按对话实时订阅及其事件种类保持不变，既有前端与既有调用方不受影响（W6② / N13）。
   *判定*：原有的订阅路径逐条实调，事件照旧到达；既有前端实时表现与迭代前一致。
4. **不做消息内容的全局广播**：全局订阅**不推送对话消息内容**（消息增量仍按对话订阅）（N8）。
   *判定*：全局订阅端收到的事件里不含任何对话的消息文本。

## 边界（不包含）

- **不做对话消息内容的全局广播**（N8）。
- 不含**列表的展示与自动更新**（F01 / F02）——本卡只定义订阅面本身，界面消费方由 F02 承载。
- 不含**统一错误契约**（F06）与**接口文档**（F07）。
- **不改既有按对话订阅的形态与语义**（N13）——本卡是新增订阅形态，不是重写既有订阅。
- 不含 **tasks 相关事件**（N5）。
- 不含**订阅之外的双向写能力**（发送 / 管对话属 F04）。

## 架构维度（阶段 3 已填，2026-09-12；详见 `architecture.md` §4 全节 / §11 AR-05；**硬契约 ②**）

> 以下为阶段 3 定案；产品维度逐字未动。

- **AR-05-a 订阅面形态**：**新增路径 `GET /api/events`**（**不**复用 `/api/stream`）——后者的"无 `chat_id` → 400"强制规则**逐字保留**（既有用例无需改写、既有客户端行为零变化），而"缺参即换资源"会让一个漏参静默变成另一种订阅。传输**复用同一个 `createSseTransport` 实例**，全局订阅键 = `null`（字符串 chat_id 不可能与之相等 ⇒ 零冲突），15s keepalive / `retry: 1000` / 断连自清理**自动继承**。**事件名** `agent_online` / `agent_offline`（与既有 4 类同族命名）；**载荷** `{instance_id, last_heartbeat}` / `{instance_id}`（满足 MI-06 的最小充分：可辨识实例与方向）。**不做**周期快照事件（外部订阅者会被无关流量打扰，且多一个事件类型）。
- **AR-05-b 判定源与时机**：判定源 = `router.status` 的 `state === 'online'` 集合（**注册表为唯一真源**，不是日志、不是新通道）；web 进程**周期拉取 + 差值**（具名导出纯函数 `diffTopology(prev, nodes)` → `{online, offline, next}`，可直接单测），间隔 `OAMP_WEB_TOPOLOGY_POLL_MS`（默认 **2000ms** ⇒ 事件到达 ≤2s + 传输延迟，5s 判定界有 2.5× 余量）。**只在存在全局订阅者时运行**（`transport.globalCount() === 0` ⇒ tick 自停并丢弃基线；无订阅者时零开销）；首个订阅者到达时**播种一次基线且不发事件**（杜绝"虚报上线" ⇒ F05 验收 2"不多发、不漏发"）。Router 短暂不可达 ⇒ 该 tick 跳过（不更新基线、不产生虚假上下线）。
- **AR-05-c 与既有订阅的关系**：按对话（`/api/stream?chat_id=`，4 类事件）与全局（`/api/events`，2 类事件）是同一 transport 的两个**键位**——`publish(chatId,…)` 永不写全局键、`publishGlobal` 永不写 chat 键 ⇒ **结构性隔离**（验收 4 由"键隔离"保证，不靠过滤）。既有 4 类事件、`chat_id` 强制规则、`retry` / keepalive、"不缓存不排队不补发"语义**零改动**。前端同时最多 2 条 EventSource（全局 1 + 当前会话 1）。
- **AR-05-d 连接约定**：服务端沿用 `retry: 1000` 首帧 + 15s keepalive（既有）；客户端断线由浏览器自动重连，**`onopen` ⇒ `loadAgents()` 全量重新对齐**（MI-05：不要求补发断线期间的每一条变化）；重连期间事件不缓存不补发（与既有 SSE 契约同形）。`API.md` 明确要求订阅端"建立订阅后先取一次 `GET /api/agents` 作为基线、重连后重取"（同时消除播种竞态）。
