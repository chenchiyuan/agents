# F04：开放接口面（网页功能全接口化、既有接口零破坏、无 agent 启停接口）

**功能 ID**: F04
**来源**: `demand.md` W6①⑤；澄清 M-2；决策 D-4 / D-5；确认 TC-05 / TC-06；效果 E8、E9（接口部分）；边界 N1 / N2 / N4 / N5 / N6 / N7 / N11 / N13
**迭代**: 0015-hub-orchestration-open-api

---

## 用户价值

网页上能做的事，程序也都能做——codex、omp、claude 这类客户端不用打开浏览器就能列对话、读消息、发消息、管对话；而且老的调用方不用改，网页上找不到的「启动 / 关闭 agent」也不会在接口里冒出来。

## 验收标准

1. **网页功能与接口一一对应**：把网页控制台上的每项功能列成对照表，逐项都能找到对应接口并**实际调通**（W6① / M-2 / E8）。
   *功能清单（按 M-2 原文）*：对话列表（含搜索与过滤条件）、对话详情（含消息）、关闭对话、批量归档、激活归档对话、重命名对话、发送消息（含既有的模型选择与一次性执行等选项）、在线 agent 列表（只读）、按对话订阅实时事件。
   *判定*：对照表逐行实调，无「网页有但接口没有」的缺口，也无"只在网页里能做、接口做不到"的操作。
2. **只读 agent 列表同样可被程序获取**：外部客户端可通过接口取得与网页列表**同一口径**的在线实例集合（实例标识 / 在线状态 / 最后心跳时间），不因它是只读而缺席（W6① / M-2）。
   *判定*：调用该接口，与网页列表逐项对照一致（同一时刻、无多无少）。
3. **无 agent 启停接口（反向验证）**：接口清单里**找不到**任何启动 agent 或关闭 / 断开 agent 的路径（W6① / N1 / N2 / E9 接口部分）。
   *判定*：逐接口检索，零命中；不存在"看起来像启停"的间接入口。
4. **既有接口零破坏**：既有接口在**路径与方法**上保持可用，既有调用方与既有前端**不改动**即可继续使用，且不出现语义变更（W6⑤ / N13）。
   *判定*：既有调用路径逐条实调，行为与本次迭代前一致；既有前端功能全部照旧可用。
5. **不新增鉴权与跨机面**：接口维持既有的本机可用安全边界——**不新增鉴权要求**，也不为跨机访问新增暴露面（N6 / TC-06 / M-7 / C-5）。
   *判定*：从本机调用全部通过且无需任何凭据；接口清单中不出现面向跨机的新入口。

## 边界（不包含）

- **不含鉴权 / 多用户 / 凭据管理 / 跨机访问**（N4 / N6）——本迭代维持"监听本机、无鉴权"的既有安全边界。
- **不含 tasks 查询接口与任务编排**（N5）——网页上本就没有 tasks 功能，接口面不补。
- **不含启动 / 关闭 agent 的接口或按钮**（N1 / N2）。
- **不含为 codex / omp / claude 实现客户端 SDK 或适配器**（N11）——交付物是接口 + 文档，接入实现属各客户端自身。
- **不改变既有连接协议语义**（N7）——见 F08。
- 不含**全局事件流的定义与订阅形态**（F05）与**统一错误契约的字段形态**（F06）；本卡只覆盖"能力有没有"与"既有是否被破坏"。
- **不改对话功能的行为语义**（N13）——接口化只是把既有能力暴露出来（C-7：只读列表约束作用于 agent，不作用于对话类写操作）。
- 不含**接口文档**（F07）。

## 架构维度（阶段 3 已填，2026-09-12；详见 `architecture.md` §6 全节 / §11 AR-04）

> 以下为阶段 3 定案；产品维度逐字未动。

- **AR-04-a 接口清单形态**：既有 9 条路径与方法**零变更** + 新增 `GET /api/events`（全局事件订阅）⇒ 共 **10 条 API**。**网页功能 ↔ 接口对照表定稿**：对话列表（`q` / `agent` / `state` / `from` / `to` / `archived` / `limit` / `offset`）→ `GET /api/chats`；详情（含消息）→ `GET /api/chats/<chat_id>`；关闭对话 → `POST …/close`；批量归档 → `POST /api/chats/archive`；激活归档对话 → `POST …/activate`；重命名 → `POST …/rename`；发送消息（含模型选择与一次性执行）→ `POST /api/messages`（`model` / `one_shot`）；在线 agent 列表（只读）→ `GET /api/agents?state=online`；按对话订阅 → `GET /api/stream?chat_id=<id>`；列表/计数自动更新 → `GET /api/events`。**逐项无缺口**；**反向**：本次未新增任何路由动词 ⇒ 接口清单中不存在启动 / 关闭 agent 的路径（E9 接口面零命中）。
- **AR-04-b 只读 agent 列表接口形态**：**不调整既有响应形态**——`{agents:[{instance_id, session_id, state, last_heartbeat}]}` 逐字不变（`registry.snapshot()` 仍显式投影 4 字段，条目新增字段不外泄）；为"与网页列表同一口径"新增**可选**查询参数 `?state=online`（服务端过滤 `state === 'online'`，其它值 → 400 `INVALID_PARAM`）。与 F01 同源：两者都源自 `router.status`；前端 `loadAgents()` **仍取全量**（面板自行过滤；`@` 补全的离线灰显行为不变）。
- **AR-04-c 回归范围**：既有调用方三类 —— ① **既有前端**：`loadAgents()` 的取数口径不变、`api()` 读的 `data.error` 仍是字符串 ⇒ **零改动**；② **既有测试**：唯一疑似需改写者（`/api/stream` 缺 `chat_id` → 400）被本方案**完整保留** ⇒ 零改写，其余错误断言全部基于 `error` 字符串 ⇒ 新增 `code` 字段不命中；③ **外部使用者**：`error` 字符串与状态码语义逐字不变。**验证方式**：既有 9 条路径逐条实调 + 既有全量套件保持通过（`architecture.md` §9.2 回归锁）。
- **AR-04-d 暴露边界**：`server.listen(port, '127.0.0.1', …)` 逐字不变；零鉴权新增、零跨机入口、零凭据读取（`hygiene.test.js` 静态扫描继续零命中）；边界写进 `API.md` 第 1 节与第 6 节。
