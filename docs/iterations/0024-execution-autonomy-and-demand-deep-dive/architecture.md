### F05: pr-planner新增"并发可行性"判断维度

**目标文件**: `roles/pr-planner/pr-planner.md`

**编辑位置**: "Strategy: 判断框架"章节

**新增维度**(作为独立子章节):
```markdown
### 并发可行性(推进条件)

**定义**: 拆出一个独立PR前,必须能在依赖图上找到该PR与至少一个其他PR的并发重叠窗口(即两者可同时执行的时间区间)

**判断规则**:
- 找不到并发窗口的候选拆分点,判定为"反向实践"
- 处理方式: 合并回其他PR或调整依赖关系,不单独拆出

**检查时机**: Verify阶段(产出PR拆分方案后、交付前)

**并发重叠窗口计算方法**(采用依赖图可达性判定,复用pr-planner已有的`depends_on`依赖图,不引入额外的时间调度模型):
- PR-A与PR-B存在并发重叠窗口,当且仅当在依赖图中A不可达B、且B不可达A(即两者互不为对方的祖先/后继,没有依赖路径连接两者)
- 判定步骤:对每个候选PR,遍历其余PR,做一次依赖图可达性检查(沿`depends_on`边正向/反向各遍历一次);存在至少一个互不可达的PR即通过
- 若某PR与所有其他PR都存在依赖路径(直接或间接依赖关系覆盖全部PR),则判定为无并发窗口

**推进约束**: 这是强制性推进条件,不是"建议考虑",不满足时不得拆出该PR

**决策理由(L2,已选定)**: 依赖图可达性判定 vs 时间调度模型(如关键路径法)两种候选方案中,选择前者。可达性判定直接复用pr-planner已经在构建的`depends_on`依赖图数据结构,不需要新增任何时间估算或调度算法;而时间调度模型需要引入"预估工时"这类pr-planner现有产出契约(七字段格式)之外的新数据,属于不必要的实体膨胀。
```

**编辑位置**: "Verify(验证)"章节

**新增检查项**:
```markdown
- 每个独立拆出的PR,都能在依赖图上找到与至少一个其他PR的并发重叠窗口(见Strategy"并发可行性"维度)
```

#### F08: Work循环替换为"同维度深挖优先+维度收敛状态标记",无轮次硬上限

**编辑位置**: `roles/demand/demand.md` "4. 工作(Work)—— Thought-Action-Observation微循环"章节(整章改写,移除现有"六维诊断驱动循环"描述)

**改写文本骨架**:
```markdown
### 4. 工作(Work)—— Thought-Action-Observation微循环

- **Thought**:当前维度集合(F06角色反射产出)里,哪个维度还有更深的问题可问?
  - 同一维度有更深问题可问时,**优先继续深挖同一维度**,不切换到别的维度
  - 只有当前维度"问不出更深的问题"时,才切换到下一个维度(参考F07调研摘要的优先级排序挑选下一个)
- **Action**:针对当前深挖维度,给出具体提案(推断内容+依据),格式沿用现有"草稿更新/理由"提案格式。用户给出好的回应时,**不表扬,直接顺着问更深的问题**。
- **Observation**:用户的反应更新草稿,同时更新当前维度的收敛状态标记。
- **再循环**:带着更新后的草稿和收敛状态回到Thought。

**维度收敛状态标记**(每个维度必须显式标记,呈现给用户可见):

状态取值:
- `未开始` —— 该维度还没有被提问过
- `深挖中-第N轮` —— 该维度已经问了N轮追问,还在深挖(N从1开始递增)
- `已收敛` —— 该维度问不出更深的问题,或用户明确表示这个维度已经说清楚了

**呈现格式**(架构待填项已决定,采用行内列表,附着在每轮提案之前):
> **维度收敛状态**:
> - {维度1}:已收敛
> - {维度2}:深挖中-第2轮
> - {维度3}:未开始

**退出条件**(无轮次硬上限,不采用pb-v1-talk的5轮硬上限):
- 所有维度都已标记为"已收敛",或
- 用户明确表示"够了"/等价的终止意愿

两者任一满足即退出Work循环,进入Verify阶段。
```

**决策理由(收敛状态标记呈现格式,架构待填项已决定)**: 候选方案对比——
- 方案A(选定):行内文本列表,附着在每轮提案消息前,格式`- {维度}:{状态}`
- 方案B(未选):表格形式,单独渲染
- 方案C(未选):仅在最终交付摘要里汇总展示,过程中不逐轮呈现

#### F09: Verify阶段六维诊断收窄为纯验收清单,与提问机制解耦

**编辑位置**: `roles/demand/demand.md` "5. 验证(Verify)"章节(改写)

**改写文本骨架**:
```markdown
### 5. 验证(Verify)

写入`demand.md`前,用六维诊断(明确性/逻辑闭环/边界完整性/内部一致性/可验证性/方案雏形)作为**纯验收清单**逐条检查最终结论质量——六维诊断在这里只负责"检查已收敛的结论够不够格",不负责驱动上面Work循环该往哪个维度深挖(驱动Work循环节奏的是F06的角色反射维度+F08的深挖优先级,两者是两套独立的东西,不合并)。

逐条检查:
1. **明确性**:最终结论里有没有两种读法的句子?
2. **逻辑闭环**:从已确认的"为什么"能否推导出最终的"做什么"?
3. **边界完整性**:每条"不做什么"是否都有理由?
4. **内部一致性**:结论内部有没有互相矛盾?
5. **可验证性**:每条"达到什么效果"能否裸判定?
6. **方案雏形**:草稿里每个"做什么"条目是否都被问过一次方案雏形?
   - 注意:"方案雏形"作为角色反射推导出的维度列表里**可能出现**的一个具体维度(如果F06反射时判断这次讨论需要覆盖它),不再是六维诊断独占的固有环节——如果F06反射没有推导出"方案雏形"这个维度,Verify阶段仍然要用第6项检查它,两者是两套独立的检查,不互相取代。

**边界收敛规则**(保留自现有版本,不变):
- 每增加一个"做什么",提案里同时给出"去掉它,最小闭环是否还成立"的判断
- 每扩大一次范围,提案里同时说明"为什么这次迭代要包含这个"
```

**决策理由**: F09验收标准第2条明确要求"六维诊断与角色反射维度是两套独立的东西",本次实施在文本中用"两者是两套独立的检查,不互相取代"这句显式声明来满足该要求,避免读者误解为六维诊断被角色反射维度替代或合并。

### L1-2(F08): Work循环完全替换

**为什么是L1**: Work循环是demand角色的执行心脏——本次改动不是给循环加一个新步骤,是把驱动循环节奏的机制整个换掉(从"六维诊断每轮重新扫描"换成"同维度深挖直到收敛"),运作方式发生根本变化。

**不可逆性**: 六维诊断驱动Work节奏的机制被移除后,如果新机制在实际使用中出现"深挖过深、用户不耐烦"或"维度切换判断不准"等问题,不能简单调参数解决,需要重新设计Work循环的驱动逻辑。

### L1-3(F09): 六维诊断与提问机制解耦

**为什么是L1**: 这是demand.md内部模块职责边界的重新划分,属于"改变现有核心模块职责"的典型场景。

**不可逆性**: 解耦之后,若未来任何一方(验收标准或提问机制)需要单独演化,不会牵连另一方——这是本次解耦决策换来的长期收益,但一旦这样分层,demand.md的文档结构（章节顺序、交叉引用方式）已经按此重新组织,想合并回去需要重新设计整份文档结构。

### 疑问1(F02字段命名,不影响推进,仅供确认):`plan_confirmation_gate`字段名选用英文snake_case风格,是否与status.md现有字段的命名风格一致?

### 疑问2(F09潜在缝隙,建议主agent关注,不阻塞推进):"方案雏形"维度在角色反射未选中时,Verify阶段第6项检查可能面临"检查对象缺失"的情况

F09验收标准第3条要求"方案雏形"改为角色反射可能推导出的维度之一,不再是六维诊断独占的固有环节;但F09验收标准第1条同时要求六维诊断作为验收清单继续包含"方案雏形"这一检查项(六维诊断六个维度的具体定义不变,见F09边界说明第1条)。

这意味着:如果某次讨论中,F06角色反射没有推导出"方案雏形"作为维度(比如这次讨论根本不涉及具体做法),Work循环就不会主动问方案雏形相关问题;但Verify阶段仍然要用六维诊断第6项检查"方案雏形是否被问过"。

本架构方案的处理方式(见F09变更映射):把这个情况明确写成"如果F06反射没有推导出'方案雏形'这个维度,Verify阶段仍然要用第6项检查它,两者是两套独立的检查,不互相取代"——即Verify阶段仍会检查,检查不通过时按现有Fix机制(回到Work阶段补充追问)处理,不视为架构缺陷,是"解耦"设计的正常代价(用户结论#12/#14明确要求解耦,解耦必然意味着两者不再自动同步)。

此判断记入`data/`供后续迭代参考(若实际使用中发现这个缝隙导致Verify阶段频繁触发"检查不通过→回Work补充"的返工循环,下一迭代可重新评估是否需要在Plan阶段强制把"方案雏形"设为角色反射的默认候选维度之一)。
