# F02 · 方案确认门开关（Step 0，默认开启，可关闭）

**来源**：demand.md 做什么#1（后半）；结论 #3

## 用户价值

不是每次迭代都需要这道确认门的用户（比如信任度高、改动很小的场景）可以提前关掉它，减少一次交互等待；不主动关闭的用户仍然默认受到保护。

## 验收标准

1. `workflow-pb.md` 的启动工作流 / Step 0 相关章节中，存在明确文字：工作流启动时（Step 0）询问用户是否开启方案确认门，**默认值为"开启"**。
2. 文字明确：若用户在 Step 0 选择关闭，则阶段3推进条件满足后**直接**进入阶段4，不再触发 [F01](F01-plan-confirmation-gate.md) 所定义的用户交互。
3. `SKILL.md` 的 Step 0 章节同步该开关询问逻辑，触发时机和默认值与 `workflow-pb.md` 一致。
4. 存在某种方式，使得阶段3→4 推进逻辑在执行时能够查询到"本次迭代方案确认门是否开启"。**[架构已填]**：记录在 `docs/iterations/{迭代ID}/status.md` 头部元信息区，新增字段 `方案确认门`，取值 `enabled` / `disabled`，默认值 `enabled`。理由见 `architecture.md` §变更映射 F02。

## 边界（不包含）

- 不包含关闭之后能否中途重新开启——demand.md 未提及，不新增此能力。
- 不包含方案确认门本身触发时呈现什么内容——见 [F01](F01-plan-confirmation-gate.md)。

## model_inferred

- **验收标准第4条**：demand.md 没有明确说"需要把开关状态记下来供后续判断"，这是从"关闭后阶段3→4要能不触发确认门直接推进"这一产品逻辑必然推导出的前提（否则无法执行第2条）。需要主 agent 确认这个隐含前提成立，并留给架构阶段决定具体落点。
