# F01 · 方案确认门（阶段3→4之间的触发与呈现）

**来源**：demand.md 做什么#1（前半）；结论 #2

## 用户价值

架构方案完成后，用户能在 PR 真正开始拆分和实现之前，看到完整的产品维度和架构维度方案并亲自拍板，而不是等 PR 已经在跑才发现方向不对。

## 验收标准

1. `workflow-pb.md` 中存在一个独立环节，明确命名为"方案确认门"（或等价的、无歧义的命名），文字明确其触发时机为"架构方案（阶段3）完成之后、PR 规划（阶段4）开始之前"。
2. 该环节的文字要求主 agent 向用户**整体呈现**产品维度（`prd.md` + `prd/*.md`）与架构维度（`architecture.md`）两部分的方案内容，不能只呈现其中一个维度。
3. 该环节的文字要求：只有用户明确确认（拍板）之后，才能进入阶段4；不确认则停在原地，不得由主 agent 自行判定"方案没问题"而跳过。
4. `SKILL.md` 中存在与 `workflow-pb.md` 一致的方案确认门描述（触发时机、呈现内容、通过条件三要素一致，不要求逐字相同）。

## 边界（不包含）

- 不包含方案确认门是否可以被关闭、关闭后的行为——见 [F02](F02-plan-confirmation-gate-toggle.md)。
- 不包含"如何生成呈现给用户的具体文本/格式"这类实现细节 `[架构待填]`。
- 不改变阶段1~3已有的用户决策点（demand.md 明确要求这部分维持现状）。
