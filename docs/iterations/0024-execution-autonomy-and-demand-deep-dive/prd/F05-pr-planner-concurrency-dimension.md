# F05 · pr-planner 新增"并发可行性"判断维度

**来源**：demand.md 做什么#4；结论 #8 #9

## 用户价值

拆出来的每个 PR 都真的能和别的 PR 同时跑，用户不会看到"拆了但其实谁也没法并发、纯粹多了协调成本"的规划结果。

## 验收标准

1. `pr-planner.md` 的 Strategy / 判断框架章节中，存在一个明确命名为"并发可行性"（或等价、无歧义命名）的判断维度。
2. 该维度的文字表述为**推进条件**（即：不满足则不能这样拆），不是"建议"或"可选参考"——用具体的强制性措辞（如"必须""才能拆出""不满足时不得拆出"等）表达，不能是"建议考虑并发性"这类弱表述。
3. 判断规则明确：拆出一个独立 PR 前，必须能在依赖图上找到该 PR 与至少一个其他 PR 的并发重叠窗口（即两者可以同时执行的时间区间）；找不到并发窗口的候选拆分点，判定为"反向实践"，处理方式为合并回其他 PR 或调整依赖关系，不单独拆出。
4. 该维度的检查时机明确写在 pr-planner 产出 PR 拆分方案之后、交付前（即属于 Verify 阶段或等价的自检环节），不是事后由别人核查。

## 边界（不包含）

- 不改变 PR 文件七字段格式本身。
- 不改变依赖图有环检测机制（这是 workflow-pb.md 已有的暂停触发条件，本次不动）。
- 不规定"并发重叠窗口"的具体计算方法/算法。**[架构已填]**：采用依赖图可达性判定——PR-A与PR-B存在并发重叠窗口，当且仅当依赖图中A不可达B且B不可达A（两者互不为对方的祖先/后继）；复用pr-planner已有的`depends_on`依赖图，不引入时间调度模型。理由见 `architecture.md` §变更映射 F05。

## model_inferred

- **验收标准第4条**："检查时机在交付前"是从"这是推进条件"这一定性必然推导出的（推进条件意味着不满足就不能交付），demand.md 原文未显式写出检查时机，需要主 agent 确认这个推导成立。
