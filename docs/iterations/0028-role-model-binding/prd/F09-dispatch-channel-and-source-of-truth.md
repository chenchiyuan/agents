# F09 · 派发通道、寻址与真源唯一

**来源**：demand.md 做什么#5；§执行方式约束表（派发通道 / 角色↔节点 / 模型真源三行）；决策 D-5 / D-14

## 用户价值

本迭代的每一次角色协作都发生在**仓库的运行时**里、并且可以按 id 查回来——而不是发生在宿主会话的临时子代理里；同时"哪个角色跑什么模型"只有一个真源，不会因为某次派发顺手带了个参数而漂移。

## 验收标准

1. **通道**：阶段 2~6 的每一次角色派发都经 hub 调用面完成（`hub api calls create`），每次派发对应一个 `call_id`；**不存在**经宿主本地子代理工具完成的角色派发。判据 = 派发台账条数与实际角色协作次数一致（本地子代理不产生 `call_id`，故台账覆盖全量即排除本地派发路径）。
2. **寻址**：派发按**角色名**寻址（`--agent <role>`），落到实例 `pb-<role>`；对应调用的 `agent` 字段等于该角色名（出现 `null` 即判为未按角色名寻址）。
3. **真源唯一**：除 F02 的 2 条探针外，阶段 2~6 的派发命令中**不含** `--model`（per-call `model` 例外只属于探针期，且探针后关闭）。判据 = 派发台账中逐条登记的派发命令形态 + F02 验收 4 的例外约束。
4. **台账可核对**（R-5 已定形态）：派发台账 = `status.md` 内的「派发台账」最小表，列为「时点 / 角色（节点）/ 用途 / `call_id` / 终态 / 实报 `model` / `truncated`」，每条角色派发一行；`call_id` 与角色名在该表与调用面（`hub api calls get`）之间逐条对得上。chat 归属的核对不走本表，走 F10 验收 1（`hub api chats get` 的 `messages[].meta.task_id`）[已确认 MI-4]。
5. **与既有语义的对照**：角色级 `cluster.json` 是模型真源——除探针外，任何角色的实报模型都不通过派发参数产生；per-call `model` 的既有优先级语义**未被改写**（其"仍优先于角色级绑定"的实证归 F13 验收 2，证据复用 F02 的探针回执）。

## 边界（不包含）

- 不改变 per-call `model` 的既有语义（它仍然优先于角色级绑定；本卡限制的是"本迭代的正式派发不使用它"）。
- 不改造 hub 调用面本身（不加开关、不加校验、不改参数集）。
- 不要求宿主侧的读文件、检索、git 等非派发工具动作也走 hub——本卡只约束**角色派发**。
- 不承担 chat 粒度（F10）、等价性判据（F11）与差距记录（F12）。
- 不规定派发命令的书写风格或封装形态（除验收 1~3 的可核对性要求外）。

## 架构维度

无待填项。**A-03 已收窄为「已定」**：派发台账形态 = `status.md` 内的「派发台账」最小表（时点 / 角色（节点）/ 用途 / `call_id` / 终态 / 实报 `model` / `truncated`），不再留待填（R-5）。其**落点与维护时点**的技术说明见 `architecture.md` §4 A-03（受理即追加行 / 终态即回填三列 / `truncated` 为 `true` 时按 D-16 聚合到差距记录 G-5）。
