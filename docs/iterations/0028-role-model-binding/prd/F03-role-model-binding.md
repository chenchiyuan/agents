# F03 · 角色级模型绑定落盘

**来源**：demand.md 做什么#2；决策 D-4（绑定清单）/ D-5（模型真源）；`demand.md` §大概怎么做（绑定落点）

## 用户价值

「哪个角色跑哪个后端」从会话里的临时决定变成仓库里可 diff、可回溯的两行——以后想知道 dev 跑什么模型，读一次仓库文件就够了，不用问人也不用翻会话。

## 验收标准

1. 仓库根 `cluster.json` 的 `roles.dev` 段存在 `model` 键，取值为 `openai/gpt-5.6-luna`。
2. 同文件的 `roles.verifier` 段存在 `model` 键，取值为 `powerby/grok-4.6`。
3. `roles` 段的其余 **8 个角色**（`architect` / `demand` / `planner` / `pr-planner` / `prd` / `progress-observer` / `retrospective` / `workflow-pb`）的对象中**不存在** `model` 键——保持隐式默认（D-4）。
4. 该文件的 `git diff`（迭代分支 vs main）只新增上述两个键：`session` / `web` / `router` / 8 个未绑定角色段 / `roles.dev` 与 `roles.verifier` 的既有键**逐字不变**；不做键序重排、不做缩进风格改写（即 diff 中除两处新增行外无其它变更行）。
5. 两个取值形态合法：均匹配 `^[A-Za-z0-9._/-]{1,128}$`（既有配置校验的约束形态），且不引入其它非法取值（`permission` / `tools` / `cwd` / 凭据类字段不被触碰）。
6. 本卡不承担"绑定是否生效"的实证（F05 / F06 / F08 承担）：本卡的通过条件是**文件内容**，不是运行时行为。集群能加载该配置即可（不因这两个取值报错）。

## 边界（不包含）

- 不做运行中动态切换角色模型（`demand.md` 明确不做：需要先定义常驻上下文池的建键轮与模型切换语义，是独立架构议题）。
- 不做 web 控制台模型选择 UI（需同时改 API 面与前端）。
- 不做非 omp 后端可插拔抽象（当前无需求来源）。
- 不做集群启动期的模型存在性预检（写错的后果由调用侧实报 `model` 暴露，记入差距记录即可）。
- 不把其余 8 角色写进 `cluster.json`（D-4：保持隐式默认，其正确性由 F07 的对照组抽样承担）。
- 不改动 `cluster.json` 之外的任何文件（其它改动面的归属见 F12 / F13）。

## 架构维度

无待填项（改动面是**既有**配置字段的取值，不涉及技术选型 / 数据模型 / 接口设计；`model` 字段与其校验、注入链路均为既有事实，`demand.md` §二 已登记其证据位置）。
