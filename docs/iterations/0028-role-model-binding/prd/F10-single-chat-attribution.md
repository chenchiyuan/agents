# F10 · 单一 chat 归属与登记

**来源**：demand.md 做什么#5；达到什么效果#3；决策 D-6 / D-21；冲突 C-3（建 chat 无独立端点的消解）

## 用户价值

本迭代的全部角色协作串在**同一条线**上——回头看时是一段连续的协作记录，而不是散在多个对话里需要人工拼起来。

## 验收标准

1. **唯一性**：存在且只存在一个承载本迭代角色派发的对话（"迭代 chat"）——阶段 2~6 的**全部** `call_id` 均可经 `hub api chats get <chat_id>` 的 `messages[].meta.task_id` 在该 chat 内找到；不存在归属其它 chat 的阶段 2~6 派发。判据的取证面 = 既有字段（调用信封不含 `chat_id`，归属核对走对话消息的 `meta.task_id`）。
2. **同址（已按 R-1 读法 (b) 收窄）**：F05 / F06 / F07 的三条实报取证调用**彼此同属一个 chat**（第二集群自己的 chat）；**不要求**与阶段 2~6 的迭代 chat 同源——主集群承载阶段 2~6 派发、第二集群只承载这三条实报，两侧的 chat 归属分别成立即可。
3. **建 chat 的来源**：该 chat 由常驻探针建立（D-21；C-3：建 chat 无独立端点，只能由首条真实调用建立）——判据 = 该 chat 的**首条调用记录**就是探针调用之一。**已由事实满足**（2026-09-15 核对）：`hub api chats get chat-6c89902c-0a9f-4513-a299-90a7f98ae611` 的 `messages[0].meta.task_id` = `task-bfd83f28-2078-434b-8a16-eac455d2e999`，即 gpt 常驻探针调用 ⇒ 不存在 D-21 偏差。
4. **登记**：`status.md` 中记录的 `chat_id` 与该 chat 一致，且该字段在探针建立之后写入。
5. **阶段 1 不落 chat**：该 chat 内不存在 demand 阶段（需求收敛）的派发调用（D-6：demand 阶段留在会话内）。

## 边界（不包含）

- 不承担收口（F08）时主集群两条取证的归属要求——那两次发生在阶段 6 之后，不在"阶段 2~6 单一 chat"的范围内。
- 不要求把需求收敛阶段的会话内容搬进 chat（D-6 恰相反）。
- 不规定 chat 的标题、项目归属或命名（既有对话创建路径决定）。
- 不承担派发通道与真源（F09）或等价性判据（F11）。
- 不要求为核对而新建任何辅助对话。

## 架构维度

无待填项。**A-03 已收窄为「已定」**：逐条核对所依赖的派发台账形态 = `status.md` 内的「派发台账」最小表（R-5），不再留待填。其**落点与维护时点**的技术说明见 `architecture.md` §4 A-03（每次派发受理后即时追加一行、终态到达后回填三列）。
