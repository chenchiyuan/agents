# F08 · 收口生效实证（合入 main 后主集群）

**来源**：demand.md 做什么#4；达到什么效果#4；决策 D-20

## 用户价值

验证的最后一公里：配置只有合进 main、并让**真实（主工作区）集群**加载之后才算真的生效——此前所有证据都发生在迭代工作区里，对使用者仍在运行的集群还不成立。

## 验收标准

1. `iteration/0028-role-model-binding` 已合并进 main：main 的历史中含该迭代的 merge 提交，message 形如 `merge: iteration 0028-role-model-binding {一句话目标} into main`；合并后迭代产物（`docs/iterations/0028-role-model-binding/**`）可在 main 上读到。
2. 合入后**主工作区集群已重启**：重启动作与重启时间可核对（重启记录留痕）；重启后该集群可按只读面列出 10 个角色实例且全部在线（判定时排除 `instance_id = web` 的固有节点）。
3. 主工作区集群加载的是合并后的 main 版本配置（含 F03 的两处 `model`）；不存在"文件已合、集群仍跑旧配置"的状态——判据 = 重启动作发生在合并之后，且重启后实报值见验收 4。
4. 重启后的主集群内，`pb-dev` 与 `pb-verifier` **各存在一条**调用，其终态实报 `model` 分别解析到 gpt 后端与 grok 后端（判定口径同 F05 验收 4 / MI-3）。
5. 收口证据以可核对形式存在于迭代产物中：重启记录 + 两条 `call_id` + 各自终态字段（`state` / `model` / `error` / `exit_code`）。落点与时点由阶段 3/4 决定（A-04）。

## 边界（不包含）

- 不重复证明绑定字段取值正确（F03 / F05 / F06 承担）；本卡只证明"合入 main 后真实集群按绑定运行"。
- 不改变"迭代期间不动主集群"的约束（F04 边界）：本卡的动作是收口时点的**一次**重启，不是迭代期内的操作。
- 不要求第二集群在此之后被清理或 `down`（`demand.md` 未要求）。
- 不承担合并动作本身的操作细节（那由工作流的收口步骤定义，不在本卡验收面内）。
- 不要求对 `pb-dev` / `pb-verifier` 之外的其它角色补取证。

## 架构维度

**已填 · A-04**（见 `architecture.md` §3.4 / §4 A-04）：

- **落点**：承载本卡的 PR 文件「验收证据」小节（重启记录 + 两条 `call_id` + 各自终态字段）∪ `status.md` 的收口登记（`迭代分支` 字段改为 `iteration/0028-role-model-binding（已合并）`）。两处都在 `docs/iterations/0028-role-model-binding/**` 内 —— 即 F13 验收 1 的允许路径。
- **时点**：① 合并进 main → ② 主集群一次 `down` + `up`（**唯一一次**触碰主集群的动作；迭代期内为零次）→ ③ 两条实报 → ④ 证据与收口登记**同批**写入，并作为 main 上合并提交**之后**的一次 `chore(0028): 收口登记` 提交落盘。
- **先例（本仓库既有事实）**：0025 的 `162682d`、0026 的 `8d897a9` —— 均晚于各自的 merge 提交、且只改 `docs/iterations/{迭代}/**`；工作流本身也要求合并后回写 `status.md` 的 `迭代分支` 字段。
- **被否方案**：写迭代分支（收口第 3 步已 `branch -d`，分支不存在）；只在 main 工作区留未提交修改（脏工作区 + 证据不进历史）；收口后再开一个证据 PR（工作流无此步骤，引入新机制）；落在 main 之外的文件系统位置（撞本卡验收 5）。

除此之外无待填项。
