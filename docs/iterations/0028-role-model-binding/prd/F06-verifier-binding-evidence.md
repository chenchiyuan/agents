# F06 · verifier 绑定生效实证

**来源**：demand.md 做什么#3（后半："用实报 `model` 字段证明 verifier 实跑 grok"）；达到什么效果#2；决策 D-4 / D-12

## 用户价值

验证角色确实与实现角色**异源**——"独立验证"成立的前提，是验证方不是实现方的同一套脑子；这条实证把这条前提钉在事实面上（与 F05 是同一次实证的两个独立观察点）。

## 验收标准

1. 第二集群内、**该集群自己的 chat** 内（R-1 读法 (b)：主集群承载阶段 2~6 派发，第二集群只承载本卡与 F05 / F07 的三条实报），存在**至少一条**对 `pb-verifier` 的调用，其**终态**信封的 `model` 字段解析到 grok 后端（provider 前缀 `powerby/`）。
2. 取证面 = `hub api calls get <call_id>` 的执行侧实报值，并留存 `call_id` 与终态字段（`state` / `model` / `error` / `exit_code`）。
3. 取证时该集群的角色级配置中存在 `roles.verifier.model`（F03 的取值）——实报值产生自角色级绑定，不是派发参数。
4. 判据口径同 F05 验收 4：实报值与绑定值**不要求逐字相等**，判据是"解析到同一后端"；指向不同后端即判失败。**实报 `model` 字符串必须如实留存**（原文照录、不改写）——只作可复核的原始事实，不作比较判据 [已确认 MI-3]。
5. **异源可核对**：把本卡证据与 F05 证据并排放，两条实报解析到**不同后端**（gpt 与 grok）——这是"verify 与 dev 异源"这一 why 的直接判据（`demand.md` §为什么）。
6. 绑定生效之前的历史调用不纳入本卡判据。

## 边界（不包含）

- 不判定 verifier 产出的验证质量（那是阶段 6 的事）。
- 不要求对 `pb-verifier` 的每一次调用都取证。
- 不验证"verifier 的验证结论是否正确"——本卡只证明它跑在不同后端上。
- 不承担 dev（F05）与对照组（F07）的取证。
- 不通过派发携带 `--model` 制造本证据。
- 不对"异源"提出更强的模型族/供应商层面的额外要求（超出 D-4 的绑定清单范围）。

## 架构维度

**已填 · A-05**（与 F05 同一待填项，见 `architecture.md` §4 A-05）：**判定 = 不共享** —— 本卡取证调用所在的 chat 由第二集群自己的库（`<工作区>/oamp/data/sql.db`）承载，与主集群的迭代 chat（`<主工作区>/oamp/data/sql.db`）不同源；理由与取舍同 F05（不改主集群、不添 F10 判据噪声、零动作）。
**取证命令形态**：`node <工作区>/oamp/bin/hub.js api calls create --chat-id chat-0028-second-cluster --agent verifier --task "<…>" --mode block --port 7789`；两条实报（本卡与 F05）并排异源可核对（验收 5）。除此之外无待填项（取证面是既有 API 的既有字段）。
