# F05 · dev 绑定生效实证

**来源**：demand.md 做什么#3（后半："用实报 `model` 字段证明 dev 实跑 gpt"）；达到什么效果#2；决策 D-4 / D-12

## 用户价值

「配置里写了」不等于「跑起来用了」——这条实证把"dev 实际跑在 gpt 上"从配置文件里的声明，变成执行侧自己报出来的事实。

## 验收标准

1. 第二集群内、**该集群自己的 chat** 内（R-1 读法 (b)：主集群承载阶段 2~6 派发，第二集群只承载本卡与 F06 / F07 的三条实报），存在**至少一条**对 `pb-dev` 的调用，其**终态**信封的 `model` 字段解析到 gpt 后端（provider 前缀 `openai/`）。
2. 取证面 = `hub api calls get <call_id>` 的**执行侧实报**值（既有语义：不是请求回显），并留存 `call_id` 与终态字段（`state` / `model` / `error` / `exit_code`）。
3. 取证时该集群的角色级配置中存在 `roles.dev.model`（F03 的取值）——即该实报值产生自"角色级绑定生效"的配置状态，而不是某次派发携带的参数（与 F09 验收 3 互为对照）。
4. 判据口径：实报 `model` 字符串**不要求逐字等于**绑定值（provider 别名 / fuzzy 解析可导致写法不同，见 C-1）；判据是"解析到**同一后端**"。若实报值与绑定值指向**不同**后端，本卡判失败。同时，**实报 `model` 字符串必须如实留存**（原文照录、不改写）——它不作为比较判据，只作为可复核的原始事实 [已确认 MI-3]。
5. 绑定生效**之前**的历史调用不纳入本卡判据（不要求回溯既有调用，也不允许用生效前的调用充当证据）。

## 边界（不包含）

- 不判定 dev 产出的内容质量或交付质量（那是各 PR 验收与阶段 6 的事）。
- 不要求对 `pb-dev` 的每一次调用都逐条取证（一条终态即构成实证）；也不要求统计"多少比例的调用跑了 gpt"。
- 不承担 verifier（F06）与对照组（F07）的取证。
- 不通过"派发时带 `--model`"来制造本条证据（那会同时违反 F09 验收 3 与 F13 验收 2）。
- 不改动 per-call `model` 的既有语义（F13 验收 2）。

## 架构维度

**已填 · A-05**（见 `architecture.md` §4 A-05）：**判定 = 不共享** —— 第二集群与主集群各用各自包根下的对话库（`<工作区>/oamp/data/sql.db` 对 `<主工作区>/oamp/data/sql.db`），这是既有包根推导的默认行为，不需要设 `OAMP_DB`、不需要任何配置。理由：读法 (b) 不要求同源；共享须给主集群 web 注入 `OAMP_DB` 并重启 ⇒ 撞 F04 验收 3；两库合一会让本卡的取证对话出现在主集群的对话列表里，给 F10 验收 1 的唯一性判据添噪声；不共享 = 零动作（YAGNI）。
**取证命令形态**：`node <工作区>/oamp/bin/hub.js api calls create --chat-id chat-0028-second-cluster --agent dev --task "<…>" --mode block --port 7789`；复核 `… api calls get <call_id> --port 7789`。除此之外无待填项（取证字段本身是既有 API 的既有字段：调用信封的 `model` 与角色级配置的 `model` 键）。

## model_inferred

- **已确认 · MI-3**（验收 4 的口径）："gpt 系"落地为"解析到同一后端（provider 前缀）而非字符串逐字相等"，依据是 C-1（默认 id 与 provider 清单不同名、靠 fuzzy 解析才成功）证明实报字符串可能不等于配置字符串；并补充"实报字符串如实留存、只作事实不作判据"。
