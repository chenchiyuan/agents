# F07 · 未绑定角色对照组实证

**来源**：demand.md 做什么#3（后半："对照组角色实跑默认"）；达到什么效果#2；决策 D-12（对照组证据）/ D-22（对照组角色 = `pb-prd`）

## 用户价值

证明"没写进配置的角色仍然沿用默认"——否则"只绑两个角色、其余不动"这件事从头到尾没有被验证过，隐患要等到以后某个角色突然跑错后端时才暴露。

## 验收标准

1. 第二集群的 chat 内（R-1 读法 (b)），存在**至少一条**对**未绑定角色**的调用，其终态信封的 `model` 字段解析到**默认链路**的后端（deepseek 系），且该角色的角色段中**不存在** `model` 键。
2. 对照组角色 = `pb-prd`（D-22 已确认）。本卡的取证调用落在**第二集群的 chat 内**（R-1 读法 (b)：第二集群只承载这三条实报）；主集群侧阶段 2 那次由未绑定 `pb-prd` 完成的派发（D-22 括号内的"兼作对照取证"）**不构成本卡判据**，也不被排除为同一现象的独立记录。
3. 该调用的 `call_id` 与终态字段（`state` / `model`）留存为可核对证据；取证面 = `hub api calls get <call_id>` 的执行侧实报值。
4. 判据口径同 F05 验收 4：实报值解析到默认后端即可，不要求与默认取值的字符串逐字相等；**实报 `model` 字符串必须如实留存**（原文照录、不改写）[已确认 MI-3]。
5. 与 F05 / F06 并排可读：三条实报分别落在「gpt 后端 / grok 后端 / 默认后端」三个不同取值上——这构成"绑定生效且未绑定不受影响"的完整对照组（效果#2）。

## 边界（不包含）

- 只抽 **1 个**未绑定角色作对照（D-12），**不要求**对 8 个未绑定角色逐一取证。
- 不把本卡的抽样结论外推为"其余 8 个角色全部正确"（判据只到抽样这一层；外推不属于本卡验收面）。
- 不承担 dev（F05）与 verifier（F06）的取证。
- 不改动 `cluster.json` 中未绑定角色段（F03 验收 3 已锁定"零写入"）。
- 不通过派发携带 `--model` 制造本证据。

## 架构维度

**已填 · A-05**（与 F05 / F06 同一待填项，见 `architecture.md` §4 A-05）：**判定 = 不共享** —— 本卡取证调用所在的 chat 由第二集群自己的库承载，与主集群的迭代 chat 不同源；理由与取舍同 F05。
**取证命令形态**：`node <工作区>/oamp/bin/hub.js api calls create --chat-id chat-0028-second-cluster --agent prd --task "<…>" --mode block --port 7789`（该 chat 由同集群内一条 shell 形态的建 chat 消息建立：`api messages send --chat-id chat-0028-second-cluster --project-id <prj> --agent-id pb-workflow-pb --text '!echo …' --port 7789`，该消息非角色派发、无模型参与，不构成对照组判据）。除此之外无待填项（取证面是既有 API 的既有字段）。
