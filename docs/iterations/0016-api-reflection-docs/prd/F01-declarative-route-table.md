## 用户价值

新增一个接口只要在一处登记，接口文档页、调试台和给 AI 看的索引就自己长出来——不会再出现"接口改了、文档忘了"这种对不上的情况。

## 验收标准

1. **单一登记点**：HTTP 面上每个接口的**方法、路径、一句话说明、参数信息**在系统中只有一处登记位置；不存在需要人工同步的第二份清单（W1 / D-2 / M-1）。
   *判定*：逐个接口检索，上述四项信息均可在同一处登记中找到；在文档页、调试台、面向 AI 的索引三处都找不到需要各自单独维护的接口清单副本。
2. **登记即出现（核心判据）**：在登记处**只增加一项**并让服务加载新登记后，**不改动文档页、调试台、索引文件的任何实现**——刷新文档页可见该接口及其字段、刷新调试台可见该接口的可发送表单、索引文件重新生成后出现该接口的一行摘要（W1 / M-2 / E1）。`[user_confirmed MI-06：判定界是"不改这三处实现"，改登记后服务重载 + 刷新 / 重新生成即出现；不要求运行期热更新]`
   *判定*：实际按上述步骤加一条登记，三个面各自核对同一接口出现；全程不改动三个面的实现。
3. **改登记即变（结构与分发同源）**：把某项登记的**路径改一个字符**，刷新文档页，该接口显示的路径跟着变；调试台中该接口的发送目标同步变化（E9）。
   *判定*：只改一处登记 → 刷新对照，两处同步变化，无其它改动。
4. **分发由登记驱动**：请求的路由结果与该登记一致——请求任一登记路径得到该接口的响应；未登记路径得到既有兜底行为（W1）。
   *判定*：逐条按登记请求，均得到对应接口的响应；不存在"登记了却打不通"或"未登记却能打通"的路径。
5. **三个派生产物零人工同步**：文档页、调试台、索引文件三者都不存在需要随接口变更单独维护的清单（W1 / C-2 的承诺边界）。
   *判定*：新增 / 修改 / 删除一条登记后，三个面分别刷新（索引文件按既有快照方式重新生成），均无需改动这三处的任何实现。

## 边界（不包含）

- **不含"既有 10 条接口行为零变化"**——由 F02 独立承载（本卡只声明"真源成立"，不声明"行为等价"）。
- 不含文档页与调试台的内容形态、交互与可达性（→ F03 / F04）。
- 不含索引文件的内容范围与两份一致性（→ F05）。
- **不新增任何第三方依赖**（N2）。
- **不改变既有接口的任何可观察行为**（N3）——本卡不引入 405、不调整既有参数语义、不改错误文案（这些是 F02 的验收对象）。
- **不做接口版本化 / 兼容层 / 多版本并存**（N8）。
- 不含鉴权、多用户、跨机访问（N1）。
- **不做 demand.md 之外的新增能力**：登记只承载"分发 + 文档 / 调试 / 索引所需的元数据"，不引入权限、限流、重试等表外语义。

## 架构落定（阶段 3；完整契约见 `architecture.md` §3 / §5.2）

- **AR-01-a 登记的物理形态与放置**：选定 **「模块级具名导出的纯构造器 `createApiRoutes(deps)`」+「`startWeb()` 体内以 9 个局部名调用」**（三候选的合取：候选 2 的"体内构造"提供零 handler 改写，候选 3 的"具名导出"提供进程内可测）。表 = **一张有序数组字面量（12 项，含新增 `GET /api/docs`）**，每项 = 元数据 + handler（同一处登记）；构造点必须在 `db`/`transport`/`topologyWatch`/`tasks`/`publishMessage`/`publishState`/`sendTask`/`sendControlNotice` 定义之后、`http.createServer` 之前。**构造器是纯构造**（不调用依赖、不读磁盘、不起定时器）⇒ 漂移锁可直接 `createApiRoutes({})` 拿到真实表项。
- **AR-01-b 表项元数据的字段 schema**：8 个元数据字段 `method` / `path` / `summary` / `params` / `response` / `errors` / `kind` / `docLink` + `handler`；参数子结构 `name` / `in`(`path|query|body`) / `type`(`string|number|boolean|json`) / `required` / `desc`（可选 `enum`）。F03 的"响应形态"落 `response`、错误码落 `errors`；**"是否有请求体"由 `params` 中是否存在 `in:'body'` 派生**（不设重复布尔位）；**F07 的写标记不新增字段**——`danger = method !== 'GET'` 在投影时派生（`architecture.md` §6.6）。
- **AR-01-c 分发实现**：匹配器 `matchRoute(routes, method, pathname)` 顺序遍历、首个命中即返回；匹配规则 C1~C5 = 字面段转义 / **`:` 段编译为 `(.*)`（贪婪、可空、可含 `/`）** / `^…$` 整串锚定 / 参数统一 `decodeURIComponent` / 不做大小写与尾斜杠归一。分发循环：**单 `try`** 覆盖「匹配 + 调用」，handler `await` 后只 `return`（不检查返回值、不自动 `sendJson`），静态面其次，404 兜底文案 `` `not found: ${req.method} ${p}` `` 逐字不变，`catch` → 502 文案逐字不变。
- **AR-01-d 生成时机**：**请求时投影**（`GET /api/docs` 每次请求从当前表生成，**不缓存、不预快照**）；文档页与调试台在页面加载时取一次。⇒ MI-06 的判定界成立（加一条登记 + 服务加载 + 刷新，三个面都变、三处实现零改动）。唯一在"生成时刻"产出的是 `llms.txt` 快照（MI-06 明确允许重新生成）。
- **AR-01-e 与既有实现的结合方式**：handler 体**零改写**——签名行改为 `async ({ req, res, query: qs, num, params }) => {`（解构名与体内既有引用同名），5 处 `decodeURIComponent(p.slice(…))` 改为 `params.chat_id`；其余每一行与迭代前逐字相同（diff 只有结构性行）。

**本卡技术路径的判定面**：验收 4（分发由登记驱动 + 无"登记了却打不通"）由 `test/api-routes.test.js` 的**可达性断言**承担——对每个表项用其自身路径构造探针请求（路径参数代入哨兵），断言 `matchRoute` 命中的正是它自己；被更靠前的表项吞掉即红并点名（`architecture.md` §3.5）。验收 5（三个派生产物零人工同步）由"三个面共用同一份 `projectRoutes` 投影"结构性保证（§5.1）。
