### 4.2 逻辑闭环 —— why 能否推出 what

**Why（合并两条，均由 `user_confirmed` 原文给出）**：

1. **接口在演进，文档靠人肉同步 ⇒ 必然漂移**。同一份接口清单已在**三处**存在（README 表 / API.md 清单 / 代码，F-16），且 0015 刚做过一次手工同步（F-22）；**没有任何测试会发现对不上**（F-14）。人肉纪律不是解法，**派生**才是。
2. **AI 客户端接入缺一个稳定、精简、机器友好的入口**。AI 读到 855 行 API.md 之前，需要一个"这是什么 / 有哪些能力 / 从哪深入"的索引（X-2）。

**逐条对照**：

| 用户给的 what | 从 Why 能否推出 | 结论 |
|---|---|---|
| 在线接口文档（基于反射） | **能**。要根治漂移，文档必须**从结构真源派生**；"反射"= 表中结构与分发同源，文档是它的视图 | 闭环成立 |
| 调试平台（基于反射） | **能**。同一份元数据既能渲染文档，也能渲染表单；接入者"读文档后要试一下"是真实动作 | 闭环成立 |
| llms.txt | **能**。它是 why-2 的最小交付物：一个机器友好的索引入口 | 闭环成立 |

**必须显式记录的一处缺口（逻辑闭环诊断的核心产出）**：

> 用户的三条 what **都在"结构层"闭环，但"动态适应"缺少一个配套机制**。
> 若只做"文档从表生成"，新增接口时人仍可能**忘记写元数据**——自动出现的文档会缺参数说明，**"自动"于是退化成"自动生成一个空壳"**。
> ⇒ 结论：**"动态适应"必须与"元数据必填锁"绑定**（W5）。它不是用户列出的三条之一，但**不做它，用户的 what 无法达成用户自己的 why**。已纳入 W5。

**第二处缺口（用户未提但有真实后果）**：可交互调试台（D-1）意味着页面上能**真实发消息 / 归档 / 关闭 / 改名**（`实测` F-1 全部为写操作），而系统**无鉴权**（本机 127.0.0.1）。⇒ 防护要求 W6。**注意此处不是"安全问题"而是"误操作问题"**（§4.6-B3）。

### 4.3 边界完整性

- **用户明说的边界**：与 API.md **互补共存**（不替换，D-4）；入口形态**顶栏 + 独立 URL**（D-5）；llms.txt **两份**（D-3）。
- 其余边界（N1~N12）均为推导所得，逐条给"为什么这次不做"。
- **主动的边界收敛判断**（去掉它，最小闭环是否还成立）：
  - **不做 OpenAPI / Swagger**：OpenAPI 能达成"机器可读"，但会引入**第二套规范 + 工具链 + 生成器**，与 D-2 已确认的"路由表反射"是两条路；去掉它，`/docs` + `/debug` + `llms.txt` 的最小闭环**完全成立**（N5）。
  - **不做调试台的请求历史 / 环境管理**：那是"Postman 化"，去掉它，调试台仍能完成"发一次、看真实响应"（N6）。
  - **不做文档页搜索 / 全文索引**：10~15 条路由的规模下，搜索的收益低于它的维护面（N10）。

### 4.4 内部一致性（矛盾与约束）

| # | 矛盾 / 约束 | 处理 |
|---|---|---|
| **C-1（生效）** | **"反射 / 动态适应" vs "元数据人工撰写"的表面张力** | **不矛盾，但必须显式分层**：机械可得的是 `method`/`path`/路径参数/有无请求体；**参数语义与示例必然人工**（F-12 实测理由）。⇒ 用 **W5 元数据必填锁**把两者绑定：人写的时候**不可能漏**，漏了测试就红。**"永不过时"的准确表述 = 结构永不过时，语义说明的完整度由必填锁保证** |
| **C-2（生效）** | **"新增接口无需手改文档" vs "API.md 路径级锁"** | **不矛盾，但成本必须讲清**：D-2 的承诺对象是 `/docs`、`/debug`、`llms.txt`（**零手改**）；`API.md` 是**人工叙述文档**（D-4 明确保留），路径级锁只要求**新增路由时补一行路径提及**。⇒ 若用户认为这仍违背"无需手改文档"，可降级为"警告"（§7 待确认 P-1） |
| **C-3（生效·重要）** | **调试台"可写" vs 系统"无鉴权"** | **不矛盾**：调试台**不扩大攻击面**——本机任何进程今天就能 `curl` 打到同一 API（F-1/F-8），调试台只是把既有能力可视化。**真实风险是误操作**（误点归档 / 误关对话 / 误发消息）⇒ **W6 的定位是"防手滑"**：可见风险标识 + 发送前一次显式确认。**不新增鉴权**（沿用 0010 N6 边界） |
| **C-4（生效）** | **调试台"覆盖全部路由" vs 0015"零启停入口"契约（`web.test.js:1601-1635` 硬断言）** | **不矛盾，但有一条架构约束必须写死**：调试台**只能从路由表渲染**，**不得硬编码任何表外路由**。路由表中本就没有 agent 启停路由（F-1 实测 10 条）⇒ 从表渲染即天然满足零启停入口。**若架构阶段为调试台加了"快捷操作"按钮，必须逐个核对不越过 0015 N1/N2** |
| **C-5（生效·硬约束）** | **路由分发重构 vs 既有 39 条用例的行为等价** | **行为不变是硬约束**（用户未要求改变任何既有 API 行为）。**7 条风险必须逐条守住**：① **不得引入 405**（现状 404 兜底，且 `API.md:103-104` 已写进对外契约，F-9）；② 匹配优先级必须与今日逐条短路**同序**（`GET /api/chats/<id>` 前缀路由会命中任何 `/api/chats/...` 形态的 GET，F-2/F-3）；③ `readBody` 留在 handler 体内、`/rename` 的"读体 → 404 → 409 → 400"顺序逐字保持（F-10）；④ SSE 路由独占 `res`，分发层**不得**检查 / 包装 handler 返回值、不得自动 `sendJson`（F-11）；⑤ 整体 `try/catch → 502` 的**覆盖面不得缩小**（F-4）；⑥ `qs`/`num()` 的每请求闭包语义、含 `?state=` 空值视为无参 / `?archived=` 空值走 400 的**既有不一致原样保留**（F-12）；⑦ **不得新增第三方依赖**（F-13，`dependencies === {}` 有测试断言） |
| **C-6（生效·次要）** | **`/llms.txt` 若走静态面 → `STATIC_TYPES` 无 `.txt`** | 两条路都可行，**留架构选**：① 走静态面 = 新增一行 `'.txt': 'text/plain; charset=utf-8'`（零风险但静态面不在统一错误契约内）；② 走专用路由 = 内容由生成函数直接 `res.end`（可控制 content-type，但多一条表项）。**需求层只锁"响应必须是 `text/plain` 且内容等于生成函数输出"**（F-6/F-7） |

### 4.5 可验证性（裸判定测试）

第二段 §4 的 E1~E10 逐条通过裸判定测试：判定者不问作者、不读背景，仅凭**改表后刷新页面 / 故意破坏后跑测试 / 在调试台点一次发送并对照控制台 / 订阅 SSE 后起停 agent / 只读 llms.txt 完成一次调用 / 顶栏点击跳转**即可判真假；无"正常工作""体验良好"类主观词。

刻意留白但**仍可裸判定**的三处：
- **"反射边界诚实"**（E9）：判定 = 把路由表里某条路由的 `path` 改一个字符，刷新 `/docs` 看它是否跟着变；同时看文档是否**明确标注**"参数语义说明为人工撰写"。
- **"元数据必填锁生效"**（E2）：判定 = 手工删掉表中某条路由的 `summary`，跑 `npm test`，**必须失败且指出缺哪条路由的哪个字段**。
- **"行为零变化"**（E3）：判定 = `test/web.test.js` **文本零改写** + 全套 39 条用例全绿。

| **B-1** | 路由表的**物理形态与放置位置**（C-5 的解法方向，**不锁定**） | ① **模块级常量表 + 依赖经上下文对象注入** handler——可测性最好（生成器 / 测试可直接 import 表），但改动面最大（所有闭包自由变量要改成参数）；② **`startWeb()` 体内构造表**（主 agent 侦察的候选，F-23）——diff 最小、自由变量名不变，代价是**生成器要消费表必须先导出或起服务**；③ 折中：体内构造 + 具名导出（0015 对 `diffTopology` 的先例）。**三条都能满足需求层的"单一真源"，具体选哪条留架构阶段** |

| **B-5** | **漂移锁的形态**（C-1/C-2 的落地方式，不锁定） | 常见坑：把生成物测试写成"**读源码正则断言**"（例如 `assert.match(webJs, /summary:/)`）——**重构即碎，且测不到真实生成结果**。更稳的形态：**调用生成函数 → 与产物逐字节比对**（llms.txt）+ **遍历表断言字段非空**（元数据完整性）+ **路径集合求差集**（API.md 覆盖）。**具体测试组织留架构 / PR 规划** |

## 3. 大概怎么做（产品级形态；路由表物理形态、生成时机、页面文件划分留架构）

- **单一真源**（W1）：`web.js` 的分发从顺序 if 链改为"表 + 匹配循环"。**表项至少承载**：method、路径（含路径参数位置）、是否有请求体、handler、以及文档/调试台所需的元数据（summary、参数说明、危险标记）。handler 的**既有逻辑与自由变量名保持不变**（F-3：体内构造时闭包自然成立）。
- **在线文档页**（W2）：内容由表派生，渲染为"接口列表 + 逐接口详情"。`style.css` **无表格与 prose 规则**（F-19），需在新页面专属样式文件中补这两类；复用既有 `:root` token（`--line/--text/--muted/--green/--code-bg` 等）保持视觉一致。
- **调试台**（W3）：渲染层读同一份元数据 → 生成控件 → 发送 → 展示状态码 / 响应体 / 耗时。**写操作防护**（W6）在渲染层统一实施（按表项的写标记决定是否需要确认），**不是每个接口各写一遍**。
- **llms.txt**（W4）：一个生成函数同时服务 HTTP 路由与仓库根文件的写入；根文件是**快照入库**（新增路由后需重新生成并提交——`W5②` 会强制这一点，忘记时测试直接红）。
- **漂移锁**（W5）：三个检查各有独立失败信息，**失败信息必须点名**（缺哪条路由的哪个字段 / llms.txt 差在哪个字节或哪一行 / API.md 缺哪个路径）。
- **静态面与错误契约**（`实测` F-6/F-7）：`/llms.txt` 的响应必须是 `text/plain`；若走静态面需在 `STATIC_TYPES` 新增 `.txt` 映射，若走专用路由则由生成函数直接写响应。**静态面不在统一错误契约内**这一既有事实保持不变（不为它引入第二套错误形态）。
- **既有契约的保持清单**（C-5 的七条风险，逐条落实）：无 405 / 匹配顺序同序 / `readBody` 留在 handler 内且 `/rename` 顺序逐字 / SSE 独占 `res` 且分发层不碰 handler 返回值 / 整体 `try/catch → 502` 覆盖不缩小 / `qs`·`num()` 语义与两处空值不一致原样保留 / 零新依赖。
- **已知受影响的既有文件**（属已知成本，实现阶段同步更新）：`oamp/src/web.js`（分发重构 + 新增路由/表）、`oamp/web/index.html`（顶栏加 2 个入口）、`oamp/API.md`（顶部加 `/docs` 链接 + 新增路由的路径行）、`oamp/README.md`（HTTP 段补文档页与 llms.txt 的指引）、`oamp/test/web.test.js`（**仅追加**新断言，既有断言零改写）。
- **`[架构待填]`**：路由表的物理形态与依赖注入方式；表项元数据的字段 schema；文档/调试台数据的生成时机（请求时 / 启动时）；两个页面的文件划分与共享程度；llms.txt 走静态面还是专用路由；漂移锁三条检查的测试组织形态。

## 5. 为什么这么做

- **为什么必须"反射"而不是"写得更小心"**（D-2）：同一份接口清单今天已存在**三处副本**（README 表 / API.md 清单 / 代码，F-16），0015 刚手工同步过一次（F-22），且**没有任何测试会发现对不上**（F-14）。人肉纪律在接口活跃演进时必然失效；唯一的根治是让文档成为结构真源的**视图**。
- **为什么必须补"元数据必填锁"**（W5①，demand 新增）：用户要的"动态适应"若只做生成，会退化成一个空壳自动生成器（§4.2）。必填锁把"人写的时候会不会漏"从**纪律问题**变成**测试问题**。
- **为什么行为不变是硬约束**（C-5，demand 推导）：用户要的是**文档与调试能力**，不是 API 行为变更。既有的统一错误契约（F-8）与 404 兜底（F-9）已经是对外承诺，任何"顺手改进"（如引入 405、统一 `?state=`/`?archived=` 空值语义）都会破坏既有契约与 39 条回归用例，收益为零、风险为负。
- **为什么调试台的防护是"确认 + 标识"而不是"鉴权"**（W6/C-3）：本机任何进程今天就能直接 `curl` 打到同一 API，调试台**不扩大攻击面**；真问题是**一次点击即生效的误操作**。加鉴权既非用户要求，也解决不了误操作。
- **为什么 llms.txt 是索引而不是全量**（W4/B-4）：用户的目标是"方便 ai 阅读并使用"——AI 需要的是**入口与清单**，不是把 855 行 API.md 全部塞进上下文；索引式还避免了第三份需要同步的副本（N11）。
- **为什么不做 OpenAPI**（N5）：D-2 已确认单一真源是路由表；再引入 OpenAPI 等于让同一份结构有第二个规范表示与独立的工具链，是典型的"第二套真源"陷阱。
