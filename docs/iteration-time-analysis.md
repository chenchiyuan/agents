**分析对象**: 本仓库 0009–0022 迭代（workflow-pb 工作流）

**原始记录规模**: 443 次提交 / 58 次 PR 合并 / **300 次角色派发会话** / 14 个已收口迭代 + 1 个在飞迭代（0022）

## 0. 结论速览

1. **有效算力（agent 真实工作小时）合计 84.3 小时，挂钟合计 54.1 小时**——挂钟比算力短，是因为并发；但挂钟里还有 **11.2 小时（21%）是"零活动死区"**（无任何 agent 事件、无提交、无产物），单看 0021 一次迭代就有 6.9 小时死区（占该迭代挂钟 67%）。
2. **时间高度集中在两个地方**：按阶段，**阶段 5（PR 实现）占 52.6%**；按角色，**verifier 一个角色占 31.7%（103 次派发 / 26.7 小时）**，dev 占 24.0%。也就是说：**一半以上的时间花在"逐 PR 实现 + 逐 PR 验证"这条链上**。
3. **单位成本约为 1.44 小时有效算力 / PR**（83.7h ÷ 58 PR），迭代间波动 1.06–2.57 h/PR。
4. **并发宽度是假的**：工作流配置"起始并发 3 / 硬上限 5"，但历次 PR 依赖图的实际可并发宽度几乎恒为 **2**；实测平均并发 0.73–3.13（多数 1.8–2.7），即"把挂钟压掉一半"已是这套调度在当前 PR 图上能达到的上限，配置中的第 3–5 个槛位从未被使用过。
5. **记录层不能用于度量耗时**：`history.md` 的时间戳不是实测值。0021 的 94 条记录整体偏移 **+5.2 小时**，0011 偏移 **21 小时**；协议只规定了时间戳**格式**，没有规定它必须是**实测读取**。

### 度量口径（全报告统一）

- **engaged（有效工作）**：在一次派发会话内，相邻事件间隔 < 15 分钟的时段之和。15 分钟阈值来自实测分布——53691 个事件间隔中，97.6% < 30 秒、382 个落在 5–15 分钟（正常的单轮 LLM 延迟），≥15 分钟的只有 15 个，且**全部**是 `custom` → `custom_message` 边界（会话被挂起后由新消息唤醒）。阈值把"长思考"与"停摆"干净地分开了。
- **parked（挂起）**：同一会话内 ≥15 分钟的间隔（会话未关闭但无动作，等待下一轮指令）。
- **dead（死区）**：把某迭代窗口内**所有**活动证据（子 agent 的 engaged 区间端点 ∪ 主会话的事件时刻）并成一条时间轴后，≥30 分钟的空档——期间没有任何 agent 产生任何事件。
- **wall（挂钟）**：某迭代首个派发到最后一个派发之间的真实时钟跨度。

- `history.md` 中标注时刻 `16:44` 的条目，正文里自己写着报告路径 `clarifications/verify-pr-005-20260913-215436.md`（文件名 = 21:54:36），同一条记录内自相矛盾。

**影响**：从 `history.md` 无法回答"哪一步慢、慢多少"——本次分析的所有时长结论都来自 §1 的 S1/S2/S3，而不是工作流自己产的记录。这本身是第一个待修项（见 §8-1）。

## 6. 为什么这么长：七条结构性成因（按可归因的挂钟/算力排序）

### A. 阶段 5 是唯一主战场，且是"逐 PR 的三段串行链"（最大项，≈52.6% 算力）

workflow-pb 阶段 5 规定：每个 PR 独立走

```mermaid
flowchart LR
  A[planner<br/>产出 pr-NNN-tasks.md<br/>中位 10.3 分] --> B[dev<br/>实现 + 提交<br/>中位 16.0 分]
  B --> C[verifier<br/>逐条验收<br/>中位 13.2 分]
  C -->|PASS| D[merge 进迭代分支]
  C -->|fail/partial| B
```

一次顺利通过 = **约 40 分钟算力**；实际 58 个 PR 换来 44.4 小时（**≈46 分钟/PR**），差额全部来自返工（§D）。

### B. 并发宽度实际上限 = 2，配置的 3–5 从未被用满

历次阶段 5 的可并发集合：

| 迭代 | 首波可并发 PR | 依赖图形态 |
|---|---|---|
| 0011 | {pr-001, pr-002} | 2 条独立短链 |
| 0012 | {pr-001, pr-003} → {pr-002, pr-004} | 2×2 |
| 0017 | {pr-001, pr-003} → {pr-002} → {pr-004} | 宽度 2 |
| 0020 | {P4, P1} → {P2, P3} → {P5} | 宽度 2 |
| 0021 | {pr-001, pr-003} → {pr-004} → {pr-002} → {pr-005} | 宽度 2 |
| 0022 | {pr-001, pr-004} → {pr-002, pr-005} → {pr-003} | 宽度 2 |

实测平均并发：0018 = 0.93、0021 = 0.73、0022 = 1.00（受死区拖累）；活动期内 1.4–3.1。**"起始并发 3 / 硬上限 5"在依赖图宽度只有 2 时是一条空规则**——爬升公式、槛位释放、补位派发这一整套机制在 14 个迭代里从未改变过派发结果。

### C. 验证面三层重复，验证成本超过实现成本

同一个产物会被验证两次以上：
1. **阶段门**：阶段 2/3/4 合并成一次 verifier（21 次派发 / 4.2 h）；0020 的 Gate 单独派了 **5 轮**（`verify-gate-stage4-20260912-210907` → `…-215004`）。
2. **PR 验收**：每个 PR 一次（58 个 PR → 63 次验收派发）。
3. **阶段 6 迭代级**：14 次 / 3.8 h，0020 与 0021 各跑 **2 轮**（`verify-stage6` + `verify-stage6-r2`）。

另外 progress-observer 按"每个 PR 合并后自动触发"跑了 15 次（2.4 h），产出物是 `progress.md` 快照——它的价值是核实状态一致性，但成本相当于每次合并再多付 9.5 分钟。

### E. 长任务单轮化（architect / prd / pr-planner）

14 次 architect 派发里，有 8 次单轮 ≥30 分钟、5 次 ≥40 分钟（最长 88.7 分钟），中位数 36.9 分钟。这类派发还有一个隐藏代价：**长轮次与"失败即全部作废"耦合**。0021 提供了最直接的一手样本——hub 派发的单轮硬上限 5 分钟把 architect 首轮在 **300.8 秒**处杀掉（`error=timeout`、随后 `CONTEXT_RESET`），产物为零、上下文被重置，必须重派并在简报里重述全部背景（`clarifications/hub-execution-log.md`）。该次失败 + 重派 + 用户指示抬高超时上限重启集群，直接消耗了该迭代前 40 分钟。
