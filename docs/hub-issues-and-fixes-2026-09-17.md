## 2. 逐条详述

### HB-01 · 30 分钟固定上限（P0）

**现象**：调用以 `failed / error=timeout` 结束，`duration_ms ≈ 1800000`；**产物早已落盘**。

**一手证据**

| 实例 | 时间线 | 空耗 |
|---|---|---|
| `prd`（DC-01/DC-08） | 14:17:41 派发 → **14:23 产物全部落盘** → 14:47:44 `failed/error=timeout`（`duration_ms=1802670`） | **≈24 min** |
| `architect`（DC-08） | 14:47:27 派发 → 14:57 `architecture.md` 落盘 → 15:17:28 撞同一上限（`duration_ms=1802677`） | **≈20 min** |
| `pr-planner`（DC-13） | 派发 → **15:18:41 八个 PR 文件全部落盘** → 撞上限（`duration_ms=1802568`） | **≈26 min** |

**合计**：**5 例空耗/零交付、空耗 70 分钟**；**制度性后果 = 用户裁决 D-19，放弃 hub 通道改用本地 subagent**。

**机制根因（三条，均实测）**

1. **上限固定**：`oamp/src/acp-client.js:319` `timeoutMs = 1800000`（shell 任务另一档 `DEFAULT_TASK_TIMEOUT_MS = 30000`，`oamp/src/agent.js:30`）。
2. **调用面不暴露该参数**：`/api/calls` 参数表 = `chat_id / agent / task / tasks / context / output_schema / schema_mode / mode / model`——**无 `timeout`** ⇒ 调用方**无法**为长任务申请更长时间。（实测位置：`oamp/src/web.js:1302-1310`，9 项逐条核对）
3. **上限与"产物完成"解耦**：一次 calling 的 turn 含 **实现 + 汇报/自查/证据整理**；**产物落盘 ≠ 调用结束**，上限常被"报告阶段"吃掉（上表 24/20/26 min 即此）。
4. **连 `block` 模式也躲不掉**：`mode: block` 的文档定义是"响应挂起至终态（**不设人为上限**）"（`oamp/src/web.js:1309`），但**agent 侧**的 `timeoutMs` 仍会截断 ⇒ 上限在**通道层不可绕**。
5. **代码自己承认这是待优化项**：`oamp/src/web.js:76` 注释——"登记软 TTL（默认 30 分钟；**2026-09-13 起 agent 侧 omp 超时上限亦为 30 分钟 ⇒ 覆盖关系由「有余」变为「持平」，待优化**）"。

**修复意见（按性价比）**

| 优先级 | 措施 | 落点 | 验收口径 |
|---|---|---|---|
| ① | `/api/calls` 暴露 `timeout`（可选，带护栏） | `oamp/src/web.js` 调用面 + `acp-client.js` | 传 `timeout` 的长任务不再以 `1800000` 截断；不传时行为不变 |
| ② | **改为可续做**：撞上限不判死，留 `suspended` + 可 `continue` | 同上 + 状态机 | 撞上限后可凭 `call_id` 继续，产物不重做 |
| ③ | 至少**暴露剩余额度/已用时长**给派发方 | `GET /api/calls/<id>` 投影 | 一轮可见"离上限还有多久" |
| ④ | 短期纪律（**不改代码即可用**）：任务切分 + **产物增量落盘** | 流程（阶段 4 已生效） | 单 PR 工作量压在 30 min 内可产出**增量产物** |

### HB-02 · 完成信号不可送达（P0）

**现象**：主 agent 派发后**只能等**——用户体感"连接 hub 仍待机"；阶段 2~4 两次流程**靠用户主动唤醒**才继续。

**机制根因（四条）**

1. **主 agent 没有身份**：CLI 不注册为 Router 实例 ⇒ 消息面**结构性收不到推送**（0028 复盘 §3.1 已侦察确认，本迭代未变）。
2. **结果面默认是"拉"**：`call_result` 投递进 **chat 流**，需**当时在线**的订阅者；**晚订阅不补发**（F04 出本期，见 `demand.md` D-16）。
3. **等待没有原语**：`--mode block` 会阻塞主 agent 自身的 turn；不 block 就只剩轮询 ⇒ **被结构性逼向轮询**。一手代价：主 agent 自建 **5 件**连接/等待层（`nohup` 裸等待 → `sleep` 定时器 → 产物 mtime watcher），且**同一毛病第三次发生**（DC-20，由用户当场指出）。
4. **文档主推路径不教事件驱动**：`skill/hub.md` 序列 1 只教"派发 → `calls get`"（F-8）。

**已消除的部分（本迭代交付）**：过滤订阅 `GET /api/subscribe`（F03）、终态取件 `GET /api/pickup` + `ack`（F05）、一次调用型等待 `GET /api/calls/wait`（F09）、健康三问 `GET /api/health`（F13）、投影字段 `connected/since/last_event_at`（F16）、**文档主推改为"派发 → 等待 → 取件"并明写"轮询是兜底"**（F19）、终态关流（P-D）。

**仍缺的部分**

| 措施 | 说明 | 验收口径 |
|---|---|---|
| **晚订阅补发（F04 语义）** | 订阅方可带 `since` 拿回错过的终态事件；幂等 | 订阅前已终态的调用，订阅后**不必另起取件**也能拿到 |
| **CLI 注册身份** | 身份面已具备（`POST/GET /api/principals`，F01），但 CLI 仍不以身份参与 | CLI 派发带自身 `principal`，可收到投递给它的结果 |
| **一个"事件驱动工作循环"参考实现** | 取代轮询/自建看门狗（把 DC-20 那 5 件私有脚本沉淀为官方路径） | 提供可直接照抄的循环示例（订阅 + 补发 + 取件 + 退出） |

### HB-03 · 终态不可信（P0）

**两个方向都有实例（各 2 例）**

| 方向 | 实例 | 证据 |
|---|---|---|
| `completed` 但**交付物缺失** | pr-005 planner `task-6e2093f3` | 终态 `completed`、`duration_ms=430908`（7.2 min，**远未触上限**），但报告正文止于"…Writing the tasks file."，`prs/pr-005-…-tasks.md` **不存在**、worktree 零提交 |
| 同型 | pr-002 `task-efcf2e6b` | `completed` 但 `duration_ms/text` 均 `null`、工作区零改动（DC-23） |
| `failed` 但**并非没有产物** | prd `task-3d15749f` | `failed/error=timeout`，但产物 14:23 即全部落盘（DC-01） |
| 派发**即死** | `task-eba25366` / `task-21f1c06c` | `failed / error=context_crashed`、`duration_ms=0`；同期实例日志 `RPC_READY → CONTEXT_READY` ⇒ **惰性启动竞态**（DC-21/DC-26，×2） |

**修复意见**

1. **终态信封携带"产物事实"**：终态事件/查询结果里给出产物清单或校验（至少 `changed_files`），让"完成"可被机械核对。
2. **惰性启动竞态加固**：首次上下文建立失败应**重试**而非即死（或在派发时同步等待实例就绪）。
3. 纪律（已确立）：**D-14「产物为权威」**——终态只作参考，交付以仓库产物为准。

### HB-04 · 单实例串行（P1）

**证据**：DC-15——三条 `planner` 调用**同轮并发创建被接受**，但**实例侧串行执行**；`prd` 与 `planner` 多轮高并发派发实测耗时与串行一致。
**推论**：迭代的"并发 3"是**槽位并发**（受依赖图约束），**真实吞吐 = 1**；`queued` 字段在 fire-and-forget 下恒 0（DC-35），占用者只有布尔 `busy`（无 `current_call_id` 语义）。
**修复意见**：① 投影/文档**明写"同角色实例串行"**，队列位置与占用者可见；② 若要真并发，需实例池化（属新增能力，须走需求）。

### HB-05 · 无取消面（P1，主体已修）

**证据**：DC-27——实测 `hub api --help` **无** cancel/kill/stop；DC-28——主 agent 只能对 `pb-dev` daemon 发 `SIGTERM`，该调用终态被记为 `failed / error=context_crashed`、`duration_ms=1485231`（24.8 min）。
**已修**：本迭代交付 `POST /api/calls/<call_id>/cancel`（F11）。
**遗留（建议）**：取消的**终态语义**应为 `cancelled`（带取消者身份与时刻），而非与崩溃同形的 `context_crashed`。

### HB-06 · "产物已落盘"不是可观测事实（P1，部分已修）

**证据**：DC-02/DC-04/DC-08——终态不可靠、`working` 与卡死同形，于是等待只能**盯产物 mtime**（主 agent 私有 watcher，DC-20 第 1 项）。
**已修**：`GET /api/calls/wait`（F09）+ 过滤订阅（F03）。
**遗留**：**晚订阅补发**（HB-02 的 F04 项）——否则"落盘信号"仍只对**在线订阅者**可见。

### HB-07 · 停滞不可判别（P1，部分已修）

**证据**：DC-02——`working` 状态下 daemon 无子进程、CPU 0.1%、日志零事件，与正常执行**同形**；DC-12/DC-16——`transcript` **1000 条封顶**（`oamp/src/web.js:448` 截断标记：过程记录 1000 条封顶 / `event:'truncated'`）且返回**前缀**（看不到尾部），使"最后一条事件"不可得。
**已修**：`last_event_at` / `connected` / `since` 投影（F16）。
**遗留**：`transcript` 支持 **tail/游标**（返回尾部而非前缀）。

### HB-08 · 隔离取证的结构性冲突（P1）

**证据**：DC-36——工作区名使 UDS socket 路径**超过 104 字节**上限，隔离性被迫让步（须用短路径 socket）；DC-31——模糊 `pgrep` 匹配**误杀主集群 `pb-dev`** 进程（同轮发现并恢复）。
**修复意见**：把两条写成**取证硬约束**（短路径 socket 约定 + **禁止按模糊命令行匹配取 PID**，须用精确 PID 来源），并纳入协议文档与执行角色原则。

### HB-09 · 过程记账与 git 事实脱节（P2）

**证据**：阶段 6 终验**三轮**抓出主 agent 自身的记账问题——① pr-007 行状态与同文件"8/8 全部合并"自相矛盾；② 台账口径写"7"而表体实为 **19 行 / 28 个唯一 call id**；③ 新增脚注与阶段 2 一格矛盾。
**修复意见**：阶段推进核查增加**三向机械比对**——PR 子状态表 ↔ merge commit ↔ 派发台账（工具化，一行命令产出差异）。

### HB-10 · 验收证据形态/口径反复返工（P2）

**证据**：DC-19（pr-001/002 因证据段格式不合规返工）、DC-37（pr-006/007 同型"只描述不粘贴命令与输出"）。
**已做**：自 pr-003 起把**验收证据段强制格式内嵌进 dev 简报模板**（治标）。
**修复意见（治根）**：由 **`tasks` 文件冻结证据格式**（planner 产出即约束），而非在主 agent 简报里反复叮嘱。

### HB-11 · 文档主推路径误导（P2，已修）

**证据**：F-8——`skill/hub.md` 序列 1 只教"派发 → `calls get`"，直接把人推向轮询；DC-20 证明**立项人自己都还按拉取式使用**。
**已修**：F19——序列 1 改为 **派发 → 等待 → 取件**，层 B 命令表 8→9 条，明写"**轮询是兜底**"。

## 5. 边界（不做什么）

- **不承诺事件不丢**：实时帧仍为 best-effort；只承诺**终态结果可拿**（延续先例 §一 的两张清单）。
- **不把 hub 记忆当恢复依据**：恢复以 agent/实例自持状态为准（延续 D-14）。
- **不为"并发"改语义**：实例串行是既有事实，槽位并发不改 PR 依赖语义（HB-04 只做**可见性**，池化属新需求）。
- **不在本报告内定稿需求**：HB-01/HB-02 的可选形态（超时参数 vs 可续做）需产品层裁决。
