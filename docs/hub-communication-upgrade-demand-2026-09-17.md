### 三、本轮讨论中明确否决/排除的路径

- **否决：让 hub 主动核实产物是否落盘**(原方案 7-C)—— 协议本身没有"产物"概念,不同任务的产物约定千差万别,没有通用做法,且会把范围拖入"重新定义什么是产物"这个更大话题。
- **否决：无状态负载均衡(池内任意实例接单,不保证会话延续)**(原方案 8-B)—— 会打破角色跨轮次记忆,除非上下文本身可迁移,而这正是 `ContextPool` 存在的意义,不可接受。
- **否决：纯空闲超时,不设绝对安全网**(原方案 6-A)—— 会重蹈 0028 watchdog v2 的误报覆辙,且完全去掉自动兜底会重新打开 G-19 死锁风险(原方案 6-C 同理被否决)。
- **排除：本次不做实例生命周期管理**(hub 不负责启停 agent 实例)—— 用户主动简化,判断这样职责边界更清楚,代价是牺牲池化的灵活性(不能按负载自动伸缩),该代价被接受。
- **排除：终态与产物一致性问题不在协议层解决**——移交给"各 agent 自行管理任务边界"这一更泛的流程规范,不写入本次架构。

## 第二段 · 需求结论

### 做什么

1. **把收件箱(inbox)升格为唯一权威送达路径**：所有 `mode=background` 调用的终态,无论是否显式传 `requester`,都保证有一个可查询的身份(显式或缺省兜底)能在收件箱里拿到结果；SSE 广播保持现状,作为体感加成,不承担送达责任。
2. **给收件箱补一层轻量持久化**：新增一张 SQLite 表,只在终态发布那一刻写一次,使"必达"保证不依赖 hub 进程是否重启过。
3. **把终态语义结构化**：新增封闭枚举 `reason`,让调用方能可靠区分"我自己取消的"/"它崩了"/"等超时了"/"被拒绝了"/"agent 自己执行出错",不再依赖解析自由字符串。
4. **把超时机制从固定总时长改成空闲检测**：复用已有的进展信号(`task.update`/`last_event_at`),空闲超过阈值才判死,同时保留一个远高于当前值的绝对安全网,防止真死锁无限占用资源。
5. **支持角色实例池化**：允许一个角色对应多个已在线的实例,hub 在池内做路由(同会话粘性、新会话选最空闲),不负责实例的启动/停止/伸缩。

### 不做什么（每条附"为什么这次不做"）

1. **不做 Router 任务表全面持久化**(原方案 3-C)—— 会牵动 Router/web.js 两层现有结构,且会把技术债焊死进 schema;真正需要解决的缺口(必达保证依赖进程存活)用范围更小的方案 3-B 已经覆盖。留作独立后续项。
2. **不引入产物核实/产物清单机制** —— 协议不应涉及"产物"这个概念,各 agent 自行对自己的任务产出负责。
3. **不做隔离边界(worktree/UDS路径)的协议层设计** —— 与本次核心问题(身份/推送/持久化/终态语义/超时/并发)无耦合,继续靠执行纪律规避,留作独立后续项。
4. **不做实例生命周期管理**(hub 不自动拉起/关闭/伸缩实例)—— 用户主动选择的职责边界:池子的存在与规模完全交给使用者,牺牲灵活性换取清晰边界。
5. **不做无状态负载均衡** —— 会打破角色的跨轮次会话记忆,与 `ContextPool` 的设计意图冲突。
6. **不修 transcript 1000 条前缀截断问题**(HB-07 遗留部分)—— 与本次五+三项决策无关,是独立的实现缺陷,留给后续单独修。
7. **不修惰性启动竞态 bug**（`completed` 但产物缺失的时序问题）—— 不是设计选择题,是具体代码缺陷,留作后续 PRD 阶段的独立修复卡片,不作为架构决策。

### 大概怎么做（用户已确认的机制方向；技术选型留给架构阶段）

- **送达**：`POST /api/calls` 的 `requester` 变为"可选但总有效"——不传时用 `chat:<chat_id>` 派生缺省身份；`publishCallResult` 终态发布时**必然**写入 inbox（SQLite 持久化新表）；`GET /api/pickup` + `POST /api/pickup/:id/ack` 复用现有端点框架，仅调整"何时写入"的触发条件。
- **终态语义**：终态信封新增 `reason` 字段（封闭枚举），`error` 字段保留但语义收窄为 `detail`（人类可读，不参与程序判断）。
- **超时**：agent 侧执行路径的判死逻辑从"距开始时间 30 分钟"改为"距最后一次 `task.update` 超过空闲阈值，或距开始时间超过绝对安全网"，触发后统一落 `reason=timeout`。
- **并发**：`role-binding.js` 的 `instanceIdForRole` 从 1:1 映射改为查询"当前在线的角色实例池"；新增按 `(chat_id, agent_id)` 的粘性路由表；调用方可显式声明"新会话/不需要延续"以获得池内最空闲实例。

### 达到什么效果（每条均可裸判定）

1. 派发一个 `mode=background` 调用后，无论调用方是否显式声明身份，都能在结果产生后通过 `GET /api/pickup` 拿到终态——不需要提前订阅、不需要一直在线。
2. hub 进程重启后（在收件箱条目未被 ack 的前提下），已产生的终态结果依然可查。
3. 任一失败的调用，调用方能通过 `reason` 字段直接判断是"我自己取消的"还是"它真的崩了"还是"等超时了"，不需要解析自由字符串。
4. 一个正常运行、持续产出进展的长任务，不会因为累计跑了很久而被判死；只有真正停止产出进展超过阈值才会被判死。
5. 用户手动启动同一角色的多个实例后，对该角色的并发派发能被分散到不同实例上处理，不再因为单实例串行而排队等待；同一对话对同一角色的连续多轮请求，仍固定路由到同一个已建立上下文的实例。

### 为什么

- **根因**（`docs/hub-vs-subagent-protocol-comparison-2026-09-17.md` 结论）：hub 的通知模型是"广播给在线连接"，subagent 是"投递给身份"——这一个分歧衍生出 HB-01/02/03/04 四个问题；本次决策集的核心（D-20/21/22）就是把 hub 的送达模型往"投递给身份"这个方向收拢。
- **不做会怎样**：HB 问题清单里标注的"本迭代最贵的一条"（HB-01）和体感最差的一条（HB-02）会持续存在，且历史上已经三次诱发"自建脚本绕开现成功能"（F-9），这个模式会继续复发。
- **为什么现在做**：五项原始决策（D-20~D-24）已经过独立讨论定案，本轮追加的三项（超时机制 D-26~D-29、并发 D-30~D-32）恰好填补了原决策集里唯一还牵动"本迭代最贵一条"（HB-01）和"单实例串行"（HB-04）的两个缺口，形成完整闭环。
