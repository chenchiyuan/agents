# hub 协议机制 vs subagent 机制：逐维度对比与结构性差距

## 一、目的与方法

本文档不产出修复方案，只做两件事：

1. 把 hub（oamp）协议在 13 个维度上的**机制现状**（不是提案、不是文档愿景，是当前 `main` 分支代码实际实现的行为）按一手证据列清楚。
2. 把同样 13 个维度下 **subagent（Claude Code 的 Agent/Task 机制）的现状**列清楚，逐条对比，找出结构性差异。

再把 `docs/hub-issues-and-fixes-2026-09-17.md` 里的 HB-01~HB-11 映射回这些维度，说明每条问题对应的是哪一层的结构缺口——而不是孤立的 bug。

**方法边界**：本文只陈述"是什么"，不评价"该怎么办"。方案讨论在本文档定稿之后另行进行。

---

## 二、协议维度对比（13 个维度）

### 1. 身份与连接建立

**hub 现状**
- Agent 侧：每次 `oamp agent start <instance-id>` 是新进程、新 UDS 连接，无常驻守护、无跨进程连接复用（`agent.js:645`）。注册走 `agent.register`（`node-client.js:144-150`），心跳自重新调度（`node-client.js:157-187`），Router 端按 `findExpired` 判定过期（`registry.js:129-141`）。同实例重复注册触发 `agent.replaced`，latest-wins，旧连接**退出不重连**（`registry.js:65-80`，`agent.js` 主循环 outcome==='replaced' 分支）。
- 客户端（主 agent）侧：`principals.upsert()` 幂等登记，只有 `Map`，**无 TTL、无过期、无持久化**（`principals.js`）。
- CLI 每次调用：新建 socket 连接 + 新 register，命令结束即 `deregister()`（`task.js:51,146,151,166`）——身份存在时间 = 单次 CLI 进程生命周期。

**subagent 现状**
- 每个子代理是一次 `Agent` 调用，身份即"名字"（`name`/`agentId`），**不依赖任何连接存活**——名字在整个会话生命周期内可寻址（`SendMessage` 可用名字重新唤起，即使子代理早已退出/完成）。
- 无需注册/租约/心跳；父会话与子代理之间没有"连接"这个概念，只有一次异步调用 + 一份持久化的调用记录。

**结构差异**：hub 把"身份"和"连接"耦合在**agent 侧**（Router 用连接活性判定在线），在**客户端侧**又完全没有生命周期管理（无 TTL）——两端各自问题不同，但共同点是：hub 里"身份"从未被设计成一个**独立于连接、长期存活、可随时寻址**的东西。subagent 里身份天然就是这个东西（名字本身即地址，与连接无关）。

---

### 2. 派发（dispatch）

**hub 现状**
- `POST /api/calls` 参数：`chat_id`（必填）、`agent`（必填，角色名）、`task`/`tasks`（二选一，支持批量）、`context`、`output_schema`、`schema_mode`、`mode`（`background`/`block`，默认 background）、`model`、`requester`（0029 新增，用于 pickup/自派发判定）（`web.js:1298-1310`）。
- `mode=background`：立即返回受理态信封，不等待。`mode=block`：HTTP 响应挂起直到终态（`web.js:1442,1481-1486`）。
- Agent 进程的 deliver handler 层对 `task.request` 是 **fire-and-forget**，不检查是否已有任务在飞（`agent.js:510-534`）；真正的同键排队发生在更下层的 `ContextPool`（见维度 9），deliver handler 本身无队列概念。

**subagent 现状**
- 一次 `Agent` 调用 = 一个 prompt + 少量结构化参数（`description`/`prompt`/`subagent_type`/`model`/`isolation`），无"批量任务数组"概念；多个独立任务通过在**同一条消息里发出多个 Agent 调用**实现并行，由宿主统一调度并发。
- 调用即返回一个句柄（agentId），完成后由宿主投递通知——这一步不是"block"也不是"background 需要额外查询"，是异步派发 + 保证送达通知的单一模式（见维度 3/4）。

**结构差异**：hub 的 `mode` 是一个二元开关（同步阻塞 or 完全不管），中间没有"异步但保证通知"的第三态；subagent 默认就是这第三态。hub 的批量能力（`tasks[]`）在派发面比 subagent 更强，但派发之后的生命周期管理比 subagent 弱。

---

### 3. 等待/阻塞语义

**hub 现状**
- `--mode block` 的上限在 **CLI/SDK 客户端层**设置为 1800000ms（`cli.js:18`, `surface.js:55`），服务端本身"不设人为上限"（`web.js:1309` 注释）——即上限来自调用方本地默认值，不是协议约束，但实际效果等同硬上限（HB-01 的根源之一）。
- `oamp task watch`：纯轮询循环，默认间隔 500ms（`task.js:204-259`）。
- `GET /api/calls/wait`（0029 新增）：**是真正 push 语义**——对未终态的 call 在 `waiters` Map 里注册 resolve 回调，由 `publishCallResult` 触发释放（`web.js:1646-1730,2179-2186`），附带一个超时定时器包装，不是"轮询假装成等待"。

**subagent 现状**
- 无需模型主动"等待"。子代理完成后，宿主在下一次工具轮次自动把结果作为通知注入对话（见维度 4）。如果确实需要显式阻塞，`TaskOutput` 提供 `block=true/false` 两态；`Monitor` 提供流式事件到达即通知。三种等待原语职责分离清楚：**默认异步自动送达**、**显式阻塞查询**、**显式流式监听**。

**结构差异**：hub 在 0029 之后已经把"等待"做对了一半（`calls wait` 是真 push），但**默认路径仍然是轮询**（`task watch`）或**用户必须主动选择正确的等待原语**——正确性依赖调用方"知道该用哪个"。subagent 的默认路径（什么都不做）就是正确路径，轮询只是补救手段而非常态。

---

### 4. 结果送达/完成信号

**hub 现状**
- 唯一终态发布点 `publishCallResult`（`web.js:2211-2240`）：写终态记录 → 若有 `requester` 则注册 pickup 条目 → 发 SSE 事件 → 关闭该 call 的订阅 → 解除 block/wait 的 Promise。这一步是幂等的（`call.published` 标记）。
- 但存在**第二条**终态发布路径 `settleCancelledCall`（`web.js:2188-2210`）：当本进程没有该 call 的本地登记时（例如另一进程派发、或 web 重启后丢失登记），**绕过** `publishCallResult` 直接发事件，且**不写** `call.terminal`——这是一个结构性的双路径，不是单一权威写点。
- `GET /api/pickup` + `ack`：只有传了 `requester` 的调用才会进 pickup；`ack` 只置标记不删除条目。**没有传 `requester` 的调用（历史上绝大多数 CLI 派发）完全没有这条兜底**。

**subagent 现状**
- 完成信号是**保证送达**的：无论父会话在做什么，子代理完成后的通知会在下一个工具轮次自动出现，不需要父会话提前"订阅"或"声明身份"。没有"忘记传 requester 就收不到"这种条件分支。

**结构差异**：hub 的送达机制是"选择性的、需要正确配置才生效的"（传 requester 才有 pickup；有本地登记才走主路径），subagent 的送达机制是"无条件的、结构上不可能漏"的。HB-02（完成信号不可送达）和 HB-03（终态不可信，两条路径写法不一致）都直接对应这里的双路径设计。

---

### 5. 通知/事件推送

**hub 现状**
- 5 类 SSE 路由（`/api/stream`、`/api/events`、`/api/subscribe`、`/api/calls/stream`、`/api/calls/:call_id/stream`），事件类型分散在各自路由（详见调研报告维度 5）。
- `/api/subscribe`（0029 新增，过滤订阅）明确**不发送初始快照**（`web.js:1059`），迟到订阅者拿不到订阅建立前发生的事件——`transport.js` 对无订阅者的事件"直接丢弃，不缓存、不排队、不补发"（`transport.js:117-123`）。
- 唯一的例外：按单个 call 订阅（`/api/calls/:call_id/stream`）在订阅建立时若该 call 已终态，会补发**恰一帧**（`web.js:1572-1578`），这是单帧兜底，不是通用的历史回放机制。

**subagent 现状**
- 没有"订阅"这个动作，因此不存在"迟到订阅"的问题——通知模型是**推给已知地址（父会话），不是推给临时连接的订阅者**。地址（名字）先于事件存在，事件永远有处可去。

**结构差异**：hub 的推送模型本质是"广播给当前在线的订阅者"，这个模型天然要求订阅者在事件发生时**恰好在线**；subagent 的模型是"投递给一个身份"，身份不需要在线，只需要存在。这是本文档目前发现的最核心的架构分歧——后面第四节会展开。

---

### 6. 决策传达/双向问答（confirmation）

**hub 现状**
- confirmation 链路（agent 侧挂起 promise，`agent.js:270-301`）与普通任务结果送达**是两条完全独立的通道**：独立的消息类型（`notice{kind:'confirmation_*'}`）、独立的 SSE 事件类型（`confirmation`）、独立的 web 侧存储（`inbox.js`，独立 Map）、独立的 REST 端点（`/api/confirmations`）。
- 这条通道的设计模式（"请求方挂起 + 事件推给可寻址面 + 裁决回来 resolve"）恰好就是 0028/0029 复盘反复提到的"理想形态"，但**没有被复用到普通任务结果送达上**——两条链路在同一个代码库里并存，一条做对了，另一条没有照着抄。

**subagent 现状**
- 没有独立的"确认"通道概念；如果子代理需要用户决策，走的是同一套通知机制（工具调用 + 用户回应），不存在两套并行的送达设计。

**结构差异**：这是 hub 内部的**自我不一致**，不是与 subagent 的差异——hub 已经证明自己能做出"请求方挂起+可寻址投递"这种设计（confirmation），但普通任务结果送达用的是另一套更弱的机制（chat 流 + 选择性 pickup）。这一条是本次对比中最值得注意的发现：修复方案的参照物不需要外求，仓库内部已经有一份可工作的正确设计。

### 7. 重连/断线恢复

**hub 现状**
- Agent→Router：有真实的指数退避重连（`agent.js:823`，起始 500ms，上限可配置），`agent.replaced` 处理"新连接顶替旧连接"的冲突。
- Client→Router：有一个"epoch"概念，但实现是**字符串比较**（`webBootId.routerGeneration`，`web.js:210-212`），不是单调游标；Router 重启会改变 `generation`（`registry.js:30`，进程启动时 `randomUUID()`），从而让所有已知 epoch 失效，触发 409。
- roster hints（`ROSTER_FILE` JSON 持久化）是唯一跨 web 重启存活的状态，用于在 agent 短暂离线时给出"可能还在,只是没连上"的启发式提示（基于墙钟时间窗口，非确定性判断）。
- `GET /api/health` 给出 router/web/agents 三问的独立判据。

**subagent 现状**
- 没有"重连"这个概念需要处理——子代理的调用记录和结果不依赖任何连接的存活。父会话进程本身如果重启，调用记录是否存活取决于宿主的会话持久化机制，与 hub 的"Router 进程内存 Map 一失效全丢"是不同量级的问题。

**结构差异**：hub 的重连恢复目前只解决了"连接层"的重连（agent 端有退避重试，client 端有 epoch 失效检测），但**没有解决"状态层"的恢复**——Router 任务表是纯内存，重启即丢（维度 12），epoch 失效后协议给的答案是"你漏了一段，重新做快照"，而不是"状态其实还在,只是要重新建立连接"。这与 `hub-bidirectional-delivery-proposal.md` 里 P-G 提案的方向一致，但 P-G 本身在本轮调研中确认**大部分仍是提案，未落地为代码**（`GET /api/health` 已落地，`reconnecting` 三态已落地，但"重启后调用登记可恢复"这条没有实现，协议文档明写"重启即丢"）。

### 8. 取消/中断

**hub 现状**
- `POST /api/calls/:call_id/cancel`（0029 新增）：幂等，已终态调用重复取消返回原值不变（`web.js:1756-1766`）。取消成功后终态精确写作 `{state:'failed', error:'cancelled'}`（`web.js:2196`）。
- `context_crashed`（惰性启动竞态/子进程异常退出）也是 `{state:'failed', error:'context_crashed'}`——两者的 `state` 都是同一个 `'failed'` 枚举值，区别只在 `error` 字符串。这是代码事实：**主动取消和意外崩溃在 state 层面完全同形**，只有下游读 `error` 字段的调用方才能区分，若调用方只看 `state==='failed'` 就判定失败原因，会把"我自己取消的"和"它崩了"混为一谈。

**subagent 现状**
- `TaskStop` 是显式的取消动作,取消后的状态与"任务自己失败"在语义上分离（工具返回值本身区分成功停止 vs 停止失败），不依赖下游再解析一个自由文本字段来判断"是谁导致的终止"。

**结构差异**：hub 把"终止原因"全部塞进一个自由格式的 `error` 字符串字段（不仅取消/崩溃，还有 `timeout`/`model_unavailable`/`permission_denied`/`context_busy` 等,详见维度 11），而不是让终止原因参与到有结构的状态区分里。这是 HB-05 遗留问题的直接代码位置。

---

### 9. 并发/队列

**hub 现状**
- 两层完全独立、互不知情的并发控制：
  - Agent 进程 deliver handler 层：**无**队列/锁,fire-and-forget（`agent.js:510-534`）。
  - `omp-daemon` 路径的 `ContextPool`（`context-pool.js`）：按 `(chatId, agentId)` 键做同键 FIFO 排队,单 in-flight,队列上限 8,超出即拒绝（`context-pool.js:10,44,112,139-141`）。
- `/api/agents` 的 `queued` 字段来自 Router 任务表里 `state==='submitted'` 的行数统计（真实计数,非硬编码 0),但由于任务几乎立即从 `submitted`→`working`,这个字段在绝大多数正常路径下观测值就是 0——它统计的是 Router 层的队列,**不反映** `ContextPool` 内部真正在排队等待执行的请求。也就是说,当一个角色实例真的因为同键排队而"堆积"时,`queued` 字段本身很可能看不出来。

**subagent 现状**
- 并发模型是宿主显式调度的（一条消息里的多个 Agent 调用并行执行,由宿主统一管理),没有"两层互不知情的排队机制"这种情况。

**结构差异**：HB-04（单实例串行,真实吞吐=1)的根因就在这里——`ContextPool` 的同键排队是真实存在且合理的（保护子进程状态一致性),但**对外暴露的可观测字段（`queued`)统计的是另一层,和真正的排队瓶颈不是同一件事**。这是一个"观测字段名字对但语义不对"的具体案例,而不是完全没有可观测性。

### 10. 观测性

**hub 现状**
- `GET /api/calls`（roster)、`GET /api/agents`、`GET /api/calls/:call_id/transcript` 三个端点覆盖大部分需要的字段,0029 新增了 `last_event_at`、`connected`、`busy`、`current_call_id`、`queued`、`since`。
- `transcript` 的 1000 条截断行为：`MAX_TASK_UPDATES=1000`,超出后**后续更新全部静默丢弃**,保留的是**最先的 1000 条（前缀)**,不是滑动窗口保留最新（`registry.js` 的 `recordTaskUpdate`)。对长任务而言,这意味着"看最新进展"这件事在超过 1000 条更新之后就**看不到**——只能看到任务刚开始时的记录。

**subagent 现状**
- 没有"transcript 截断"这类问题,子代理的输出通过 fork/agent 结果直接返回,不存在一个有硬编码上限的中间缓冲区截断历史。

**结构差异**：这是一个纯粹的实现细节缺陷（HB-07 的一部分),截断方向选错了（该保留尾部却保留了头部),不是架构层面的分歧,但后果是"停滞判断"这件事在长任务上会彻底失效——你想看任务卡在哪一步,恰好看不到最后一步。

---

### 11. 生命周期终态语义

**hub 现状**
- Router 任务表的 `state` 是严格闭集 **`{submitted, working, completed, failed}`**（`registry.js`)。所有"原因"信息（`cancelled`/`context_crashed`/`timeout`/`rejected_by_agent`/`dispatch_failed`/`structured_output_invalid`/`spawn_failed`/`model_unavailable`/`permission_denied`/`context_busy`)**全部塞进 `error`/`result.error` 自由字符串字段**,从未作为独立的 `state` 值出现。
- `web.js` 还有一套完全独立的对话级状态机 `CHAT_STATES = ['working','completed','failed','closed']`（`persist.js`),与 Router 任务表状态是两套不同的定义,只是字符串值部分重叠——容易在阅读代码/日志时把两个不同层的"failed"混为一谈。

**subagent 现状**
- 终态是结构化的（完成/出错/被取消是不同的返回路径),不依赖下游解析一个自由文本字段来判断"到底发生了什么"。

**结构差异**：HB-03（终态不可信)的机制性根因之一就在这里——`state` 只有二元的"活着"或"死了"（就语义上说是 working 或 failed/completed),真正有意义的失败原因分类全部退化成了字符串匹配,任何新增的失败模式都可以随意塞一个新字符串进 `error` 字段而不需要改动状态机,这也是为什么"取消"和"崩溃"能共用同一 state——这个字段设计本身就不区分。

---

### 12. 权威源与持久化

**hub 现状**
- 三层持久化落差非常大：
  - **纯内存,进程重启即丢**：Router 任务表（`registry.js` 的 `tasks` Map)、web.js 的调用登记 Map、`pickup.js`/`principals.js`/`inbox.js` 全部无 TTL 无落盘。
  - **持久化**：对话/消息落 SQLite（`persist.js`,`node:sqlite`)。
  - **半持久化**：roster hints 落一个 JSON 文件,专门为"web 重启后还能猜 agent 是否还在"这个单一目的存在。
- 崩溃恢复动作 `startupSweep()` 只把重启前处于 working 的对话标记为 failed,不做别的状态重建。

**subagent 现状**
- 取决于宿主会话本身的持久化机制,不是本文关注的对比点（subagent 没有独立于宿主进程的"Router"这种中间层需要单独持久化)。

**结构差异**：这一条更多是 hub 自身的架构选择说明,而不是和 subagent 的直接对比——但它解释了为什么 HB-01/HB-02/HB-03 都很难通过"重试"或"重连"完全兜底：**调用的执行状态（在跑什么、跑到哪)和调用的最终产出（磁盘文件、SQLite 消息)是两个持久化等级完全不同的东西**,前者随时可能凭空消失,后者不会。这正是"产物为权威"(D-14)这条纪律存在的原因——不是最优解,是在当前持久化架构下唯一可靠的兜底。

### 13. 隔离边界

**hub 现状**
- 调研未在代码中找到 UDS socket 路径 104 字节限制的校验逻辑（检查了 `config.js`/`router.js`/`rpc.js`/`node-client.js`,均无长度校验或 `ENAMETOOLONG` 专门处理)。HB-08 提到的"路径超限"现象大概率是 **OS 层（Unix domain socket 路径本身的系统限制,通常 104-108 字节,视平台而定)在起作用,而不是 hub 自己的代码逻辑在做限制**——即这是一个平台约束,hub 代码里没有为它做任何防护或提前校验。
- worktree/实例级文件系统隔离：代码库中**未发现**专门的隔离机制。`role-binding.js` 的 `instanceIdForRole` 只是角色名到实例名的字符串映射,不涉及文件系统路径分配。ACP 子进程的 cwd 直接继承自 agent 进程自身的 cwd（`acp-client.js:208`),没有按 chat/agent/task 分配独立工作目录的代码。
- 实际能确认的隔离层次：OS 进程边界（每个 `oamp agent start` 是独立进程)+ `instance_id` 字符串路由 + 按 `(chat_id, agent_id)` 键分配独立子进程（`ContextPool`)。

**subagent 现状**
- worktree 隔离是显式支持的一等选项（`Agent` 工具的 `isolation: "worktree"` 参数),由宿主负责创建/清理,不依赖调用方自己规划文件系统路径。

**结构差异**：hub 目前的隔离手段止步于"进程边界"和"命名约定",没有文件系统层的隔离能力——如果多个角色/实例需要各自独立的工作区（例如同时在多个 git worktree 里工作),这件事完全要靠调用方（主 agent)自己去规划路径、自己规避冲突,协议本身不提供保护。HB-08 里"模糊 pgrep 误杀主集群进程"这类事故,根源正是隔离边界不够清晰,取证/管理时只能靠字符串匹配去猜哪个进程属于哪个工作区。

## 四、核心架构分歧（不是逐条问题,是一句话总结）

对比 13 个维度后,能收敛成一句话的分歧是：

> **subagent 的通知模型是"投递给一个身份"（身份先于事件存在,不要求在线);hub 的通知模型是"广播给当前在线的连接"（事件发生时必须有人正在监听,否则丢弃或需要选择性兜底机制补救)。**

这个分歧解释了本文档发现的几乎所有结构性差距：
- 等待为什么会退化成轮询（维度 3)——因为默认路径下没有"投递给身份"这个动作可用。
- 完成信号为什么会漏（维度 4)——因为送达机制依赖"有没有配置 requester"和"有没有本地登记"这类条件分支,而不是无条件投递。
- 晚订阅为什么拿不到历史（维度 5)——因为推送模型从设计上就是"丢给当前在线者",不缓存。
- confirmation 链路为什么反而是对的（维度 6)——因为它恰好是"请求方挂起 + 事件推给可寻址面"这个正确模式的孤例,只是没有被推广到其他场景。

这一条分歧,以及仓库内部已经存在的 confirmation 链路作为"正确设计的参照物",是下一步讨论优化方案时的核心决策点：**要不要把 confirmation 链路的设计模式(挂起+可寻址投递)当作统一范式,推广到普通任务结果送达上**。这决定了后续修复是"打补丁"还是"补齐一个原本就该存在的通用机制"。

## 五、留给方案讨论的问题（不在本文档回答）

1. 客户端身份（principal)要不要获得和 agent 身份对等的生命周期管理（TTL/心跳/持久化),还是维持"轻量、无状态"的现状?
2. 推送模型要不要从"广播给在线者"改造成"投递给身份"（即收件箱成为一等公民,而不是 pickup 这种选择性兜底)?
3. Router 任务表的纯内存特性,是否需要在这次架构调整里一并处理,还是继续依赖"产物为权威"(D-14)这条纪律?
4. `state`/`error` 的终态语义要不要重新设计成结构化的枚举,而不是自由字符串?
5. 隔离边界(worktree/文件系统)要不要纳入协议范畴,还是继续留给调用方自己管理?

以上问题的答案会决定下一步方案的范围边界,建议在讨论方案时逐条过一遍再动手设计。
