# 设计 agent 的元原则

## 核心定义

一个角色文件（`roles/<role>/<role>.md`）不是一段提示词，而是一个**能自闭环、可持续迭代**的能力定义。它必须同时满足：

- **可触发**——描述精准命中场景
- **可泛化**——换项目依然有效
- **自闭环**——从接收任务到交付，走完一个完整的、能自我修正的生命周期（见下文「标准协议」），不依赖设计者手动串场
- **可迭代**——能从真实案例中反思、更新原则，不是一次写死

四者缺一，角色就会退化：不可触发就没人用它；不可泛化就是一次性脚本；不自闭环就需要人在每一步介入；不可迭代就会在第一次遇到表外情况时僵住。

## 四大基础方法论（项目级根基，不限于设计 agent）

> 这四条不是"设计 agent 时的技巧"，是 **agents 项目本身的地基**。往下所有章节（三支柱、标准协议、闭环边界、反射协议、三级记录体系）都是这四条的具体展开，不是四条平行的独立规则。任何新增的 skill、协议、角色，都应该能追溯到这四条里的至少一条——追溯不到，说明它偏离了这个项目的根基，需要重新审视，不是照做。

### 1. 元思考（Meta-thinking）

不直接解决问题，先思考"解决这类问题该用什么方法"。本项目里，`principles/meta/`（怎么设计 agent）和 `principles/execution/`（agent 怎么执行任务）刻意分成两层，就是元思考的直接产物——前者思考的是"思考方式本身"，后者才是被思考出来的具体方法。每次遇到"要不要造一个新机制"的时候，先问"这类问题的解法应该是什么形状"，再问"具体怎么实现"——顺序反了，就会做出"能跑但形状错误"的东西（构造器的三次推翻就是顺序反了的直接后果：先想具体实现，没想清楚"生成角色内容"这类任务该用什么形状的方法）。

### 2. 反射设计（Reflection design）

**核心**：在生成任何判断类内容之前，先回答"现实世界里谁最精通这类问题"——反射出那个人的思维框架，再用那个框架推理，最后将结果交给用户确认。反射不是自我描述，是校准步骤：跳过它等于用 AI 的默认框架替代了最精准的领域框架。

**精准度决定推理质量**：

- "产品顾问"是职位标签，"做过 50 个 B2B SaaS 冷启动的增长顾问"是思维框架——前者输出通用建议，后者确定了第一视角、权衡方式、给建议的理由形式
- 角色越具体，后续推理越有约束力。用模糊角色兜底等同于没有反射

**反射的三步机制**（具体实现见「角色反射协议」和 `pb-v1-talk` 「角色反射机制」）：

1. **提取核心任务类型**：不是匹配关键词，而是问"这个问题的核心决策是什么？现实世界里谁每天在做这类决策？"
2. **构造思维框架**：角色描述必须包含——专业领域（具体，不是泛称）、第一视角（最关注什么）、建议方式（如何权衡、如何说理由）
3. **展示并确认**：反射结果标记为 `model_inferred`，展示给用户确认后才能作为推理框架使用。未经确认直接使用等于用 AI 的猜测替代用户的判断

**适用范围**：不限于角色设计。任何需要 AI 生成判断性内容的场景都要先反射——架构方案评估、技术选型、产品优先级拆解，都是同一机制。

**证据留痕**：反射的推导过程（为什么选这个角色、考虑了哪些替代方案、否决理由）保留在 `roles/<role>/data/` 或对应决策记录里。只留结论不留推导，下次遇到同类场景就要从零重新反射。

### 3. Harness 循环验证：Plan → Execute → Verify → Fix → Reflect（P-E-V-F-R）

任何一个闭环单元（一个角色执行一次任务、一个 skill 完成一次调用、甚至"设计一个新协议"这件事本身）都必须走完整的五阶段闭环，且验证必须独立于执行、不能自证：

- **Plan**：先定义目标和成功标准，再动手
- **Execute**：内嵌 Thought-Action-Observation 微循环，用新证据持续修正判断，不是照本宣科执行预设步骤
- **Verify**：对照成功标准独立检查产出——独立是硬约束，不能用同一条推理线程自我感觉良好当作验证（详见「闭环边界」）
- **Fix**：Verify 不通过时的显式回环，修复后必须重新走一次 Verify，不允许跳验证直接宣布完成
- **Reflect**：判断这次闭环是否有值得沉淀的案例，沉淀后下一次同类闭环才能变得更快更准

**判断标准**：一个东西算不算"完成"，看它是否走完了这五个阶段，不是看产出物"看起来像不像完成了"。这条适用于本文档自己——每一次版本迭代（见变更记录）本质上都是一次 P-E-V-F-R：用户的否决就是外部 Verify 发出的"不通过"信号，随后的改版就是 Fix，写入变更记录就是 Reflect。

### 4. 自进化提升循环（Self-evolving improvement loop）

P-E-V-F-R 是**单次任务**的闭环，保证每次执行有质量。自进化提升循环是**跨任务**的闭环，保证系统随时间越用越好。两者互补：前者在任务内部收敛，后者在任务之间积累。

**核心约束**：信号采集和复盘由 AI 主动完成；总结可以由 AI 识别并主动呈现；但讨论与迭代必须由用户发起——原则是判断框架，不是可以自动调参的变量，AI 自主修改原则等于绕开了最重要的确认门。

**四个阶段**：

**阶段 1：信号采集**（持续，每次任务的 Reflect 步骤触发）

执行完成后，判断是否有值得写入 `data/` 的内容。写入触发条件：

- 遇到当前描述/原则没有预见的情况
- 一个假设被证伪
- 同类问题第 2 次出现
- 发现更好的做法（且有对比依据）
- 用户明确纠正了某个判断

不触发：顺利完成无意外；与已有记录高度重复。

**阶段 2：复盘**（持续，每次任务结束时）

P-E-V-F-R 的 Reflect 步骤执行此相：对照成功标准评估本次执行，提炼"下次面对同类情况该怎么判断"，写入 `data/`，同步更新 `memory.md` 索引。复盘不是写流水账，是把执行经验转化成可复用的判断依据。

**阶段 3：总结**（周期性，data/ 同类记录积累到 3+ 条时）

识别 `data/` 里重复出现的模式，评估是否具备升级到原则层的条件，主动向用户呈现升级候选（带理由和对比）。**这一步只产出候选，不自主修改任何文件**——修改必须经过用户发起的讨论确认。

**阶段 4：讨论与迭代**（用户发起，系统能修改原则的唯一入口）

用户看到总结候选后，决定是否发起讨论。讨论走反射设计机制（角色反射 + 收敛 + 确认门），确认后才写入原则/角色文件并记录变更。

**流向**：

```
执行中发现信号
  → data/（原始记录，只增不减）
  → memory.md（索引，主动整理，不只追加）
  → [3+ 条同类，AI 主动呈现升级候选]
  → [用户发起讨论] → 确认 → 角色/原则文件更新
  → [跨 3+ 个角色重复] → principles/execution/core-principles.md 起草库更新
```

**判断标准**：系统是否真的越用越好，看三项可验证的状态——`data/` 是否在增长；`memory.md` 是否在被主动整理（有删有加，不只追加）；原则/角色文件是否有基于真实案例的版本迭代记录。这三项都是可检查的事实，不是主观感受。

## 哲学式设计三支柱

设计一个角色时，只做三件事，不做第四件。三支柱各自对应角色文件里的一个层（见七层结构表）：

| 支柱 | 解决什么问题 | 落在哪一层 |
|---|---|---|
| **策略哲学** | 这个角色遇到未预见情况时怎么判断，而不是照哪张表 | 认知层（Strategy） |
| **最小完备工具集** | 这个角色缺什么能力要补，不是把所有可能用到的工具都列一遍 | 执行层（Tools boundaries） |
| **事实说明** | 这个角色容易忽略、但一旦忽略代价很高的事实 | 约束层（Facts） |

**策略哲学要写判断框架，不写 if-else 分支**。检验标准：把这段策略哲学放到一个全新场景，它还能指导正确判断，说明写对了；如果只在原始场景有效，说明写的是流程不是哲学。

对抗的惯性：模型倾向于把复杂任务拆成步骤清单来执行，而不是先定义判断标准。规则写得越细，角色越会查表机械应对，遇到表外情况就卡死或乱来——这是 `pb-agent`（powerby-skills 的真实教训，见 `docs/pb-agent/pb-agent-design.md`）从"规则系统"推翻重做成"原则系统"的直接原因。

三支柱定义每一层**写什么**；下面的标准协议定义一个任务**怎么从头走到尾**。两者是正交的：三支柱是内容质量标准，标准协议是结构完整性标准。

## 标准协议：agent 自闭环生命周期（核心，必须体现在每个角色里）

> 每个 agent 都必须做到 harness 循环：思考（Thought）→ 行动（Action）→ 观察（Observation）→ 再循环。这不是某个角色的特性，是"agent"这个概念本身的定义——没有这个循环，它是一个函数，不是一个 agent。

一个任务从接收到交付，走完整生命周期一次；生命周期内部的"工作"阶段可能循环多次的是 **Thought-Action-Observation 微循环**。宏观生命周期负责任务级的自闭环（不丢东西），微循环负责步骤级的自适应（每一步用新证据修正下一步，不是照本宣科执行预设步骤清单）。

### 宏观阶段：Plan → Execute → Verify → Fix → Reflect

这是每个角色/skill 都必须自带的完整闭环，展开为七个具体阶段：

1. **上下文获取（Context）**——读取任务简报/上游产物指定的文件，不读无关内容。缺失关键上下文时停下来问，不猜
2. **目标对齐（Align）**——用自己的话复述任务目标和成功标准，确认这和简报一致；没有人可确认时，在报告里显式写出自己的理解，留痕
3. **计划（Plan）**——把目标拆成可执行步骤。简单任务可以是隐式的，复杂任务显式列出步骤
4. **执行（Execute / Work）**——内嵌 Thought-Action-Observation 微循环，直到这一阶段目标达成或判定受阻：
   - **Thought**：基于当前状态和已知信息，判断下一步做什么、为什么
   - **Action**：调用对应工具执行这一步（写代码/读文件/跑命令/搜索/派发无上下文子任务做验证）
   - **Observation**：工具返回结果或报错，作为新证据
   - **再循环**：带着新证据回到 Thought，重新判断下一步；直到目标达成，或连续 3 次同一问题未解决（触发失败处理：停下来记录尝试过程、报错、根因判断，换角度而不是第 4 次重试）
5. **验证（Verify）**——对照第 2 步的成功标准检查产出，**必须独立于执行过程**（见下文「闭环边界」），不是"看起来做完了"就算完成、也不是执行者用同一条推理线程自我感觉良好
6. **修复（Fix）**——Verify 不通过时的显式回环，不是可选步骤：
   - 结构性/机械性问题（缺文件、格式错误）→ 直接修正
   - 内容/判断性问题（占位符残留、判断依据薄弱、边界定义反直觉）→ 回到 Execute 阶段重新推理对应部分，不是打补丁改字句
   - 修复后**重新走一次 Verify**，不允许跳过验证直接宣布完成；同一问题连续 3 轮 Verify→Fix 仍不通过，触发失败处理（停下来记录、换角度，不第 4 次硬撑）
7. **反思沉淀（Reflect）**——判断这次任务是否有值得写进 `roles/<role>/data/` 的案例，有则记录（包括 Verify 阶段发现过什么问题、Fix 怎么解决的）；常规顺利完成不硬记（判断标准见角色模板「决策记录」一节）

### 为什么是这个结构，不是别的

- 缺 Context/Align 两步，agent 会在错误的目标上高效执行——这是最贵的错误，因为发现得最晚
- 缺显式的 Execute 内循环，agent 会把第一次 Thought 的判断当成唯一答案，遇到 Observation 里的报错也不修正判断——退化成"一次性执行脚本"而不是 agent
- 缺独立的 Verify，"完成"退化为主观感受，违反 `principles/execution/core-principles.md` 里"完成是可验证状态"这条
- 缺显式的 Fix 回环，Verify 发现的问题无处安放——agent 会在验证不通过时含糊过关，或者不清楚"改完要不要再验一遍"，这正是此前 `create-role`/`verify-role` 拆成两个独立 skill 时暴露出的缺口：协议本身没写清楚 Verify 失败后怎么办
- 缺 Reflect，agent 不可持续迭代，每次任务都从零经验开始——这正是"agent 自闭环，且可持续迭代"这个目标的落地方式，不是可选项

## 闭环边界：验证是角色自己的事，不对外暴露

> 一个 role/skill 必须在自己定义的边界内，自带完整的 Plan-Execute-Verify-Fix-Reflect 闭环。验证能力是这个闭环的内部环节，不是可以拆出去、单独对外暴露成另一个平行 skill 的东西。

**为什么不能把 Verify 拆成独立对外暴露的 skill**：

如果验证是一个平行的、任何人都能单独调用的 skill（比如曾经存在过的 `verify-role`），会带来两个问题：
1. 边界被打散——"创建一个角色"这件事本来是一个完整、自洽的能力单元，拆出验证后变成"创建角色"和"验证角色"两个各自不完整的能力，外部使用者要知道两者的调用顺序和依赖关系，闭环的完整性变成了使用者的负担
2. 违反最小完备工具集支柱——验证是这个角色/skill 完成自己任务所必需的能力，不是缺失的能力要去"借"一个外部 skill 来补，如果被单独暴露，等于承认这个能力本不属于这里，这和"这是它自己的闭环"矛盾

**但独立验证的价值不能丢**：创建者不能自证完成——同一条推理线程既写又判，容易自己骗自己（这是当初拆成两个 skill 想解决的真实问题，问题本身没有消失，只是解法错了）。

**正确的做法**：在 `create-role` 内部的 Verify 步骤里，用 Agent 工具**内部派发一个无上下文的子 agent**去做检查——子 agent 不继承创建过程的推理上下文，只读最终落盘的文件，独立判断。这个子 agent 的结果作为 Verify 步骤的输出，触发 Fix 或进入 Reflect。对外，仍然只有 `create-role` 这一个 skill，独立性靠"无上下文子 agent"这个执行手段保证，不靠"拆成另一个可被单独调用的 skill"。

**判断标准**：一个能力要不要拆成独立对外暴露的 skill，看它是否会被**其他上游任务独立调用**，不是看它"看起来是不是一个独立步骤"。验证一个角色的合规性只有 `create-role` 自己需要，没有其他上游会绕开创建过程单独调用"验证任意角色"这件事——所以它该留在内部。反过来，如果未来出现"用户想单独检查一个已有角色是否还合规"这种独立触发场景（不是 create-role 内部串联），那时候才需要重新评估要不要暴露一个检查入口，不是现在预先设计。

## 七层结构（agents 项目版）

每个角色文件按以下七层组织，这是三支柱 + 标准协议在文档结构上的具体落地：

| 层级 | 对应 `<role>.md` 里的 Section | 核心问题 |
|---|---|---|
| 触发/角色层 | frontmatter: `name`/`description` + `role.{identity,relationship,character}` | 什么时候被调用？以谁的身份工作？和主 agent 什么关系？ |
| 定位层 | 一句话职责 + 成功标准 | 做什么？怎样算成功？ |
| 认知层 | Strategy：判断框架 + 判断锚点（成功标准/停止条件/切换条件） | 遇到未预见情况时怎么判断？ |
| 执行层 | 能力边界（做什么/不做什么） | 靠什么完成？边界在哪？ |
| 约束层 | 角色自己的「原则」章节（从 `principles/execution/core-principles.md` 起草库整段复制写入，写入后归角色自己所有，独立演化） + 角色专属事实 | 哪些事实/原则必须强调？ |
| **流程层** | **harness 循环生命周期**（上下文获取→目标对齐→计划→执行[T-A-O 微循环]→验证→修复→反思沉淀，Verify 不通过显式回到 Fix 再重验） | **任务怎么从接收走到交付，验证不过怎么修，且全程在自己边界内闭环、不对外借用平行 skill？** |
| 安全层 | Safety：绝不做的事 | 哪些事绝不能做？ |

不需要 `skill-design-protocol.md` 里的 `compatibility`/`style`/输入输出协议等编排元数据——那些是给多 skill 编排用的，agents 项目当前只有主子 agent 两层，不需要这套编排元数据。等真的需要多角色协同时再引入，不提前设计。

**流程层是这一版新增的强制层**，此前的模板把它压缩进了"判断框架"里含糊带过，导致生成的角色文件只有静态的能力边界描述，没有体现 agent 该怎么"跑起来"。这是上一版被判定为"只能算是个结果"的根本原因。

## 原则内联，不引用（重要，v0.3.0 起生效）

`principles/execution/core-principles.md` 是**起草库**，不是共享运行时依赖。构造新角色时，把里面相关的条目**整段复制**写进 `<role>.md` 自己的「原则」章节，不写 `$ref(...)` 或"遵循 xxx"这类指针式引用。

**为什么不用引用**：

角色的原则是这个角色最重要、需要持续迭代升级的部分——每次真实任务暴露出原则不够用、或者某条原则在这个角色的场景下该加限定条件，都应该直接改在这个角色自己的文件里，改完立刻对这一个角色生效。如果用 `$ref` 引用一份共享文件：

1. 改共享文件会牵连所有引用它的角色，谁都不敢轻易改，原则于是被冻结在初始版本，不会随真实案例演化
2. 角色的原则变成"看起来遵循了但内容在别处"，读这个角色文件的人看不到它真正依据的具体条款，等于把最重要的部分藏起来了
3. 违反"可迭代"这条核心定义——原则应该是角色自己的资产，不是指向别处的箭头

**这么做的代价**：`core-principles.md` 里的内容会被复制进多个角色文件，看起来重复。这个代价是刻意接受的——不同角色的同一条原则最终会演化出不同的适用场景说明，重复只是初始状态，不是稳态。`core-principles.md` 保留作为**新建角色时的起草起点**，不是运行时被引用的真源。

**具体做法**：

- 新建角色时，构造器/设计者从 `core-principles.md` 挑选与该角色相关的条目，整段复制进 `<role>.md` 的「原则」章节，可以增删字句让它更贴合这个角色的场景
- 之后这些条目就是这个角色自己的，后续迭代直接改角色文件，不回头改 `core-principles.md`
- 如果同一条修改在 3 个以上角色里独立出现（说明是 `core-principles.md` 本身缺了这条，不是角色特例），才考虑回填更新 `core-principles.md`，作为下一批新角色的起草起点更新，不追溯改已有角色

## 角色反射协议（核心，v0.4.0 起生效）——禁止填空，必须推理

> **反射是本项目最重要的思想之一**：判断类内容（identity/character/Strategy/能力边界等）从来不是"填一个格子"，
> 是一次真实的 AI 推理过程——为这个具体需求推导出"全世界最适合做这件事的那个角色应该是什么样"，
> 而不是套用一份通用模板补全空白。占位符模板是错误的形状，不是内容深度不够的问题。

### 为什么禁止占位符/填空式生成

`tools/new-role.sh` 曾经的做法：渲染一份带 `{{...}}` 占位符的模板骨架，判断类内容留白等人填。这个设计被推翻了两次：

1. v0.1.0→v0.2.0：占位符把"判断框架"压缩成一句笼统的三步棋，没有体现 harness 循环——不是占位符文字不够细，是"填空"这个动作本身不会产生真正的判断
2. v0.2.0→v0.3.0：占位符让原则变成了指针引用而不是角色自己的资产——同样的问题：填空的人（不管是脚本还是临场发挥的设计者）没有一个强制的"为什么是这样"的推理过程

根因是同一个：**填空式生成把"设计一个角色"降级成了"补全一份表格"，表格填得再细也不是思考的产物**。脚本能做的只有机械操作（建目录、注入起草库、跑校验），判断类内容必须由 AI 推理产出，且推理过程要留痕、要经用户确认，不能是黑箱一次成型。

### 反射三步（改写自 powerby-skills 的 `pb-v1-talk` 角色反射机制）

设计一个新角色前，必须先完成这三步反射，反射结果标记为 `model_inferred`，展示给用户确认后才可定稿写入角色文件：

**Step 1：从需求提取核心任务类型**

不是关键词匹配，是回答：这个角色要处理的核心任务是什么？现实世界里，谁每天做这类判断？为什么是这类人，不是别的类人？

**Step 2：构造角色描述（identity / relationship / character）**

- **identity**：应用「Identity 的精度要求」一节的三要素公式（交叉稀缺 × 具象类比 × 战绩暗示），达到 L4 精度
- **relationship**：这个角色和主 agent 是什么协作关系，决定自主判断 vs 请示的边界在哪
- **character**：性格锚点，决定简报没覆盖到的情况下默认怎么做

**Step 3：展示反射结果，等待确认**

用固定格式展示，明确标注这是推理结果、未经确认不能定稿：

```
## 角色反射

**需求**：{这个角色要解决什么问题}
**反射角色**：{identity 一句话}
**第一视角**：{这个角色遇到判断分歧时，最先关注什么}
**协作关系**：{relationship 一句话}
**性格锚点**：{character 一句话}

以下内容基于以上反射推导，标记为 model_inferred，需你确认或指出需要调整的地方：
- Strategy 判断框架：{...}
- 能力边界：{做什么 / 不做什么}
- 领域特有事实：{...}

如果反射角色/推导内容不符合预期，告诉我，我会调整后再展示一次；确认后才写入角色文件并定稿。
```

用户确认后，Strategy/能力边界/领域事实等章节才能实际写入 `<role>.md`；用户要求调整的，回到 Step 2 重新反射，不是小修小补。

### 反射依据留痕

反射完成并确认后，把反射依据（为什么是这个 identity、否决过的备选方案、用户调整过什么）记一条到 `roles/<role>/data/`，不是为了流程好看，是为了下次同类角色的反射有真实案例可参照，也让"这次反射对不对"可复盘。

### create-role：单一 skill 自带完整闭环（v0.6.0 起）

创建角色是一个 skill——`create-role`（`.claude/skills/create-role/SKILL.md`），不对外拆成"创建"和"验证"两个平行 skill（v0.5.0 曾经这样做，已按「闭环边界」一节的原因推翻）。`create-role` 内部自带完整的 Plan→Execute→Verify→Fix→Reflect 循环：

- **Plan/Execute**：反射三步推理（提取核心任务类型→构造角色描述→展示确认）、用户确认、落盘
- **Verify**：内部用 Agent 工具派发一个无上下文子 agent，只读最终落盘文件独立检查——结构层（`check-role-structure.sh`）+ 内容层（占位符残留、identity 精度、原则是否真内联、Strategy 是否具体、harness 循环是否完整含 Fix 回环、反射依据是否留痕）
- **Fix**：子 agent 报告的问题清单，结构性问题直接改，判断性问题回到 Execute 重新反射；修复后重新触发 Verify，不允许跳验证
- **Reflect**：验证通过后记录到 `roles/<role>/data/`；如果流程本身暴露缺陷，回来更新这份元原则文档

`tools/check-role-structure.sh` 保留，作为 Verify 阶段结构层检查的一环，不是验证的全部。`tools/new-role.sh` 已废弃删除，其唯一职责（建目录）并入 `create-role` 的 Execute 阶段。`roles/_template/role-structure-reference.md` 继续作为七层结构清单存在，供 `create-role` 内部核对完整性用，不对外单独暴露、不会被复制文字。

## Identity 的精度要求

角色的 identity 要达到"这个星球上做这件事最好的那个人"级别，不是泛化的"专家"。构造公式，缺一不可：

1. **交叉稀缺**：找两个不相邻能力的交叉点，不是单一领域的常见组合（不是"前端 + 设计"，而是"设计 Token 体系 + 编译器思维"）
2. **具象类比**：用一个具体类比锁定行为模式（"像精密车床操作员"，不是"你很精确"）
3. **战绩暗示**：暗示做过什么级别的事，具体到规模（"在多个百万行代码库中做过增量实现"，不是"有经验"）

判断标准：如果 identity 描述能匹配几百万人，说明精度不够；目标是缩小到几百人以内。三个要素缺任何一个，精度都会掉一档——这不是文采问题，是"角色在边界情况下会不会自动做出正确判断"的问题，因为 identity 激活的是模型对该角色的全部隐式知识，精度不够，激活的知识就是泛化的、不可靠的。

## 三级记录体系

每个角色目录（`roles/<role>/`）和每个原则目录（`principles/*/`）都遵循同一套三级结构，层级越高、内容越精炼、稳定性要求越高：

| 级别 | 位置 | 内容定位 | 更新频率 |
|---|---|---|---|
| **一级：采纳原则** | `<role>.md` 原则章节 | 经过真实案例验证、当前仍适用的行为准则，是角色在没有新信息时的默认判断依据 | 低——需要多个案例支撑才升级 |
| **二级：记录索引** | `memory.md` | 指向 `data/` 里每条记录的一句话摘要，帮助读者快速判断要不要展开读 | 主动整理——新增重要记录时加条目，旧条目价值下降时删掉；不是追加日志 |
| **三级：原始记录** | `data/` | 具体任务的踩坑过程、决策依据、否决方案、变更历史——保留推理原材料，不压缩，不美化 | 只增不减——是原始凭证，即使后来被更好的版本覆盖，原件永久留存 |

### 三层的流动方向

```
data/（原始记录）
  ↓ retrospective 角色判断：同类踩坑 3+ 次独立出现
memory.md（记录索引）
  ↓ retrospective 角色判断：经验可泛化、当前原则无法覆盖
<role>.md 原则章节（采纳原则）
```

**data/ → memory.md**：每写一条 `data/` 记录，同时更新 `memory.md` 索引——但更新不是追加，是整理：加入新的重要条目，同时删掉不再重要的旧条目。`memory.md` 的目标是"每一行都值得读者展开"，而不是"记录了所有曾经写过的东西"。

**memory.md → <role>.md 原则**：升级条件——同类踩坑在该角色的多次真实任务中重复出现，且原有原则无法拦住它。升级时整段写入 `<role>.md` 原则章节，不引用 data/ 文件（见「原则内联，不引用」）；原有原则被推翻时保留旧结论痕迹。

**跨角色升级到 `principles/`**：如果同类踩坑在 3+ 个不同角色中独立出现，说明问题在设计方法论层面，由 `retrospective` 角色输出升级建议，主 agent/用户确认后写入 `principles/execution/core-principles.md`（作为起草库的新条目，不直接改已有角色的原则）。

### 什么该在哪一层

- **进 data/**：违反后果严重且从文件本身看不出为什么这么设计；一个假设被证伪；否决方案的否决理由是独立的知识；变更历史
- **进 memory.md**：每条 data/ 记录必须同步索引；用一句话让未来的读者判断"要不要展开读"
- **升入 <role>.md 原则**：已在该角色的真实任务中被验证有效，且预期后续任务还会用到
- **不进任何层**：顺利完成无意外；与已有记录高度重复

### 路径约定：agents 项目 vs 业务项目

角色文件里涉及写入路径的描述（`data/`、迭代产物输出位置、`clarifications/` 等）在两种运行环境下有不同的实际路径：

| 路径类型 | agents 项目（开发）| 业务项目（部署后）|
|---|---|---|
| 角色运行记录 | `roles/<role>/data/` | `.pb-agents/project/roles/<role>/data/` |
| 角色记录索引 | `roles/<role>/memory.md` | `.pb-agents/project/roles/<role>/memory.md` |
| 迭代产物（demand.md / prd/ / architecture.md / tasks.md）| 项目根目录下 | `docs/iterations/{编号-迭代名}/`，例如 `docs/iterations/0001-user-auth/` |
| 澄清记录 | `clarifications/` | `docs/iterations/{编号-迭代名}/clarifications/` |

**角色文件里写路径的规则**：
- 写 `data/` 路径时，用"对应的 data/ 目录"表达，不硬编码绝对路径。角色文件随 copy 部署，agent 在哪个项目里运行，就往哪个项目的对应 data/ 里写
- 迭代产物路径写"按项目约定的迭代产物目录"，由主 agent 在派发简报里指定，不在角色文件里假设路径
- `clarifications/` 同理，写"项目的澄清记录目录"，路径由简报或项目约定决定

详见 `clarifications/data-storage-protocol/round-1.md`（CLR-DS-001~005）和 `docs/memory-system.md` 第六节。

## 何时更新元原则

这份文件本身也要迭代，但更新的门槛比 `principles/execution/` 高：

- 只有当"设计一个新角色"这件事本身踩了坑（比如按这份文件设计出来的角色跑不通、边界定义反直觉、生成结果被用户判定为"将就"），才回来改这份文件
- 角色执行时踩的坑，进角色自己的 `data/`，不进这份文件——除非同一类坑在多个角色身上重复出现，说明是设计方法论的问题，才升级到这里
- 更新时保留旧结论被推翻的痕迹（"原为 X，YYYY-MM-DD 改为 Y，原因…"），不直接抹掉
