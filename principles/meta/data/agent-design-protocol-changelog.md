# agent-design-protocol.md 变更历史

---

## v0.7.0（2026-09-01）

**需求**：用户明确指出"元思考、反射设计和 harness 循环验证是本项目的基础原则，要记录到项目原则和经验中"。

**变更原因**：三条核心方法论散落在各章节行文逻辑里（哲学式设计三支柱、角色反射协议、标准协议各自独立成章），没有被明确标注为"项目地基"，导致每次讨论都要从具体案例（构造器三次推翻、verify-role 被否决）重新反推概念，而不是直接引用一条沉淀好的原则。

**决策过程**：将三条方法论显式提炼为独立章节「三大基础方法论（项目级根基）」，紧跟核心定义之后、在所有具体章节之前，明确这三条不是"设计 agent 的技巧"而是项目本身的地基，后续所有章节都是具体展开。`principles/execution/core-principles.md` 同步新增「Harness 循环闭环」条目。

**经验总结**：方法论散落在具体章节里的代价：读者每次都要自己拼图，设计新东西时不会主动去追溯这三条，只会就近参照最相似的具体章节。显式命名、独立章节、前置放置，能让概念在被引用前就被看到。

## v0.6.0（2026-09-01）

**需求**：用户指出「不应该是基于 tools/new-role.sh 来生成 role，而应该通过一个 create-role skill 创造 role 之后，有验证检查的 skill 来做验证。这里也应该遵循计划、执行、验证、修复、沉淀的 harness 循环」，随后进一步指出「Verify-role 是 create-role skill 中的验证环节，应该在 create-role skill 中自闭环，不对外暴露才对。一个 role 应该具备 Plan-Execute-Verify-Fix-Reflect 整个循环，自己能闭环定义好的边界。这也是一个架构层面的问题，我们需要对齐设计。」

**变更原因**：v0.5.0 把 create-role 和 verify-role 拆成两个平行对外暴露的 skill，违反了"一个能力单元应在自己边界内自闭环"的原则——`verify-role` 是 `create-role` 自己 Verify 步骤的实现细节，独立暴露等于允许任何人跳过创建直接调用验证，形状本身就错了。

**决策过程**：
- 确认验证独立性（"创建者不能自证完成"）的价值保留：改用 Agent 工具内部派发无上下文子 agent 实现，不拆成外部接口
- 确认 dev.md 同步补上显式 Fix 回环（v0.5.0 期间补的 Verify 阶段没写清楚 Verify 失败后怎么办）
- 删除 `verify-role` skill 目录；`create-role` 重写为 v2.0.0，内部自带完整 Plan→Execute→Verify→Fix→Reflect 闭环
- 新增「闭环边界」独立章节，给出判断标准："是否会被其他上游任务独立调用"——当前无此需求，所以不拆

**经验总结**：把验证拆成独立 skill 的直觉来自"单一职责"，但"单一职责"的边界是能力单元，不是函数。验证是创建闭环的内部阶段，不是独立能力。独立性（不自证）是一个执行手段的要求，不是接口拓扑的要求——"内部派发无上下文子 agent"既保留了独立性，又不打破闭环边界。

## v0.5.0（2026-09-01）

**需求**：用户明确指出"不应该是基于 tools/new-role.sh 来生成 role，而应该通过一个 create-role skill 创造 role"。

**变更原因**：脚本建目录 + AI 手动 Write 文件的流程没有内建 P-E-V-F-R 闭环，缺少独立验证环节，等于创建者自己给自己判卷。

**决策过程**：删除 `tools/new-role.sh`；新增 `create-role` skill（反射三步 + 用户确认 + 落盘）和 `verify-role` skill（独立结构+内容检查）。注：此设计在 v0.6.0 中被部分推翻（verify-role 独立暴露违反闭环边界）。

**经验总结**：把"生成角色"升级成 skill 是正确方向（能内建协议），但把验证独立成对外 skill 是过度拆分。

## v0.4.0（2026-09-01）

**需求**：用户明确要求"禁止使用占位符，必须用反射的方法利用 AI 的优势根据需求生成角色"，并指出"我要的不是填空，而是 AI 真正的思考解决问题。反射/元思想是本项目最重要的思想之一，这点写入项目级的经验，后续要参考"。

**变更原因**：v0.1.0～v0.3.0 阶段，角色判断类内容（identity/character/Strategy/能力边界）通过 `{{...}}` 占位符模板填空生成。用户两次判定结果"只能算是个结果"、"将就"，第三次明确说"这是形状本身的问题"：填空式把"设计角色"降级成"补表格"，占位符提示写得再细也不会产生真正的 AI 推理。

**决策过程**：参考 powerby-skills 的 pb-v1-talk 角色反射机制，提炼出三步反射协议（提取核心任务类型→构造角色描述→展示确认）+`model_inferred` 标记+确认后才定稿的流程，新增「角色反射协议」独立章节。构造器脚本职责收窄为纯机械操作（建目录），绝不再渲染判断类内容模板。

**经验总结**：占位符填空和 AI 反射的本质区别不在于内容深度，在于产出来源——填空产出来自模板提示，反射产出来自 AI 对这个具体任务的真实推理。用户拒绝的不是"内容质量不够好"，是"这个东西不是 AI 想的"。

## v0.3.0（2026-09-01）

**需求**：用户明确要求"遵循的原则要写入到 dev.md 中，而不是使用引用表达。角色的原则是最重要的，需要持续迭代升级的部分"。

**变更原因**：v0.1.0、v0.2.0 中角色通过 `$ref()` 或"遵循 `principles/execution/core-principles.md`"的方式引用共享执行原则，CLR-PD-004 当时的决策是"项目级共享+角色级引用"。用户指出这把"最需要迭代的部分"做成了"最难改的部分"——引用指针让原则被冻结在共享文件里，单个角色无法针对真实案例独立演化。

**决策过程**：原则内联，不引用。`core-principles.md` 降级为"起草库"（不是运行时被角色引用的共享文件），新角色从起草库复制相关条目写入自己的 `<role>.md`，写入后独立演化；只有同一条修改在 3 个以上角色中重复出现，才回填起草库。`docs/iterations/0000-project-design/clarifications/protocol-depth/round-1.md` 的 CLR-PD-004 标记"已修订生效"并保留原文字。

**经验总结**：共享 + 引用的架构对"稳定不变的接口"适用；对"需要按具体案例持续演化的原则"是反模式——角色的原则是根据每次真实任务打磨的，不能依赖共享文件的变更来驱动。

## v0.2.0（2026-09-01）

**需求**：用户判定 v0.1.0 生成结果"只能算是个结果，我需要优秀的结果"，并明确指出 harness 循环（角色要有 harness 循环）是核心要求，要求重新设计元原则。

**变更原因**：v0.1.0 把 harness 循环压缩进认知层的判断框架里，生成的角色文件缺少"怎么跑起来"的描述，只有静态边界定义。

**决策过程**：新增「标准协议：agent 自闭环生命周期」独立章节，把 Thought-Action-Observation 微循环和七个宏观阶段（上下文获取→目标对齐→计划→工作→验证→交付→反思沉淀）明确写死为每个角色必须体现的结构；七层结构表新增「流程层」作为第七层强制层级。

**经验总结**：把 harness 循环塞进认知层是"凑合能提"的设计——形式上有、实质上消失了。强制层级（流程层）是让它出现在每个角色里的唯一可靠手段，不是靠"设计者记得"。

---

## v0.1.0（2026-09-01）

**需求**：项目启动，需要一套设计新 agent（角色）时遵循的元原则，基于 powerby-skills/docs/skill-design-protocol.md 一次性借鉴。

**变更原因**：新文件，无前版本。

**决策过程**：提炼 skill-design-protocol.md 的哲学式设计三支柱（策略哲学/最小完备工具集/事实说明）和七层结构（触发/角色层、定位层、认知层、执行层、约束层、安全层，当时流程层尚未独立），形成初版。

**经验总结**：初版没有显式定义角色的自闭环能力（harness 循环），导致生成结果都是"静态描述"而非"能跑起来的能力定义"。这个缺失在 v0.2.0 被修正。
